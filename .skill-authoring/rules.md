# Skill 文档写作规则

> **这一份是什么**：以后写 skill 都按这份来。每条规则带**判据**——能判「有没有违反」，不是口号。
> **这一份不是什么**：不是调研。证据、数字与出处都在 [`docs/research/agent-document-structure.md`](../docs/research/agent-document-structure.md)，这里只留结论和判据，不重复论证。
> **为什么放在 `docs/` 外面**：这里存的是我们的**约定**，不是系统现状、不是决策记录，也不进版本。放在根目录、以 `.` 开头，`check_docs.py` 扫不到它——这是有意的（2026-11-03），审计不按这份规则审任何文档。
> **怎么改**：加一条规则必须同时给**判据**；没有判据的不是规则，是偏好。

## 〇、适用范围

- **适用**：我们自己写的 skill（公开指南、内部 skill）、以及我们给用户写的 skill 建议。
- **不适用**：代码注释怎么写（那是 `code-writing` 的事）、仓库文档放哪个轴（那是 [`docs-architecture`](../.claude/skills/docs-architecture/SKILL.md) 的事）。

## A. 粒度：切到哪儿为止

| # | 规则 | 判据 |
|---|---|---|
| **A1** | 一篇 = **一件能被独立完成或独立回答的事** | 单独拿出这一篇、给一个零背景的 agent，能不能办成或答清？不能 → 还没切到位；能、但还包着第二件事 → 切多了 |
| **A2** | **线性流程不拆**，步骤内联在同一篇 | 这些步骤之间有没有「选了 A 就不做 B」？没有 → 就是一条线，不拆 |
| **A3** | **互斥分支才拆**，判断表留在上一级 | 同一次会话里会不会走两支？会 → 它们不是分支，是步骤，放回同一篇 |
| **A4** | 分支内容**不到一篇的量**（一两段）→ 同篇分节，不拆文件 | 这条分支自己有没有步骤、坑、失败处理？没有 → 分节 |
| **A5** | 每篇 **≤100 行**（中文约 1,000–1,500 字） | 行数 |

> **A2 与 A3 的分界**：互斥的是分支，不互斥的是步骤。一切「先做这个、再做那个」都是步骤，切开就等于把一次会话拆成多次——那是有实测代价的。

## B. 路由：怎么被找到

| # | 规则 | 判据 |
|---|---|---|
| **B1** | **入口只有一个**，所有篇从入口**直接可达**，一层深 | 从入口走到任何一个叶子，中间要不要经过别的文件？要 → 违规 |
| **B2** | 每条路由写到**具体文件 + 什么时候读它** | 有没有条目只写到目录、或只写「详见 references/」？有 → 违规 |
| **B3** | **叶子是终点，不是中转**：禁止「读完这篇去读那篇」 | 把这篇删掉、只剩一句「请去读 X」？是 → 违规。知识可以引用，**控制流不能外移** |
| **B4** | 入口**不超过 150 行**；路由表**按大类分组** | 行数。这是天花板不是配额——实测一套 15 篇的指南，入口只有 64 行；为了凑数写长是错的 |

> **B1 的例外**：只有当某个大类膨胀到十几篇、入口确实装不下时，才在该目录放一张 `index.md` 当二级路由。这是例外，写进那个 skill 的说明里。

## C. 自足：单篇拿出来能不能用

| # | 规则 | 判据 |
|---|---|---|
| **C1** | 开头**两句之内给答案** | 前 50 字有没有把结论说完 |
| **C2** | 禁止「如上所述」「这个功能」「它」开头；小标题**带对象名** | 把小标题单独拎出来，还知道说的是谁吗 |
| **C3** | **一篇一个说法**；同义词只出现在「用户会怎么说」的位置 | 同一篇里有没有两个词指同一件事 |

## D. 内容：写什么、不写什么

| # | 规则 | 判据 |
|---|---|---|
| **D1** | **常见坑放进入口**，不下沉 | 这个坑 agent 会不会「不知道自己踩了」？会 → 必须进入口 |
| **D2** | **同一事实的解释只写一处**；入口与叶子不许重复 | 改这条事实要动几个地方？多于一个 → 违规。**但一条流程里必需的那一句动作可以出现在每个流程里**——每个流程都要能独立走完（C1），不能因为「别处写过」就让它断一步 |
| **D3** | 多步流程**每步写完成信号 + 没做到怎么办** | 每步后面有没有一个**外部可验证**的事实（回显、列表、状态） |
| **D4** | 同一件事的**网页与命令行写在同一篇**的两段 | 这两处步骤有没有可能只改了一处？会 → 该合并 |
| **D5** | 不写「如果用户是……」——那是在猜状态 | 这句话依赖某个账号或环境的具体数据吗？依赖 → 交给能查数据的那一层 |
| **D6** | **公开文档不写内部约定**：分层、交接、谁来查数据、我们内部怎么讨论出这个结论，都不写 | 这句话是写给**用的人**看的，还是写给**做产品的人**看的？后者 → 删。判据：删掉之后用户的办事能力有没有下降？没有 → 本来就多余 |

## E. 触发与验收

| # | 规则 | 判据 |
|---|---|---|
| **E1** | `description` **最后写**，写清「什么时候用 / 什么时候不用」 | 描述里有没有使用条件 |
| **E2** | 验收要测 **agent 实际打开了哪些文件**，不只测内容对不对 | 有没有记录打开率、有没有漏读 |
| **E3** | 发布前跑 `skmr skill check <地址>@<版本码>`，断链不许上线 | 退出码 |

## F. 怎么用这份规则

1. **写之前**：先画入口（一张路由表）和叶子清单。画不出来，说明还没想清楚要写什么。
2. **写完一篇**：A1 / C1 / C2 / C3 这四条当场能判。
3. **写完一个 skill**：A2–A5、B1–B4、D1–D4 整份过一遍。
4. **发布前**：E1–E3。

## G. 还没定的

- **多语言**：目前只有中文，`description` 要不要中英双写未定。
- **文件数量上限**：只有「入口 100–150 行」这个间接约束，还没定一个 skill 最多多少篇。
- **版本化**：skill 自身的版本（草稿→上线）与这份规则的关系未定——规则改了，已上线的 skill 要不要回头改，没有结论。
