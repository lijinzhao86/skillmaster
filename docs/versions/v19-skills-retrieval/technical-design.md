# v19-skills-retrieval · 技术设计

## 架构

```
调用方（CLI / 控制台发现页 / 控制台的"发布"）
        │
        ├─ search(scope, q, filters, limit) ─────────────┐
        │                                                ▼
        │                                    modules/retrieval        ← 本版新增，独立可替换
        │                                       ├─ Embedder（接口）→ 百炼 text-embedding-v4
        │                                       ├─ 近邻查询：pgvector `<=>`，只查自己的表
        │                                       └─ EmbeddingIndex：发布事务里写向量
        │                                                │
        └─ publish(...) ──► 事务：移动指针 → 算向量 → 提交 ─┘
                                       │
                                       ▼
                        PostgreSQL（同一个库：skill 数据 + vector 列）
```

**边界**：`retrieval` 不判断可见性（候选集由 M12 给）、不拥有描述文本（经 `EmbeddingTextSource` 从 M12 读）、不定义状态。状态与权限永远留在原来的模块，检索只是「在给定候选集里的近邻查询」——集合小的时候这个「给定」是精确的 id 清单，集合大到无法枚举时是「先取 `limit × 20` 名（默认 200）再由 M12 过滤」（§检索链）。

**为什么不是一个独立向量库**：状态不复制就没有两份状态要同步；候选集来自与业务同一个库的同一个快照；删除随外键级联。代价是向量检索与业务查询共享数据库资源，规模上限受 PG 约束。

## 发布时的行为（本版对用户最明显的变化）

**发布是一次同步事务，向量在事务里算。** 事务做完才算发布成功——不是"先发布、再慢慢索引"。

```
POST /web/skills/{ns}/{name}/publish
  └─ BEGIN
       ├─ 指针前移 + 元数据投影（recordPublish，会锁住这一行）
       ├─ 读回发布后的文本（title / description / when_to_use；name 自创建起不变）→ 调百炼 → 写 skill_embedding
       ├─ 审计
     COMMIT   ← 到这里才回 200
```

三个直接后果：

| 谁 | 看到什么 |
|---|---|
| 控制台 | 点"发布"后有一段等待（一次向量往返；spike 实测约 350 ms，单条文本一次嵌入）。**不需要新画面**：确认弹窗本来就有进行中态——按钮变成"正在上线…"并禁用（设计 `VersionActions.tsx` 的 `pendingLabel`，实现 `ConfirmDialog.tsx`） |
| 发布失败的调用方 | `503 semantic_unavailable`，**这次发布没有生效**（指针、审计、向量一起回滚）。重发一次即可，版本已经提交过，重发是幂等 |
| 批量发布 | 每条一个事务，所以是 N 次调用、N × 约 350 ms 的额外时间（实测口径同上）。100 条从 5 秒变成 40 秒量级 |

> **这一态设计稿已经覆盖**（2026-10-25 核对：`design/src/console/components/skill/VersionActions.tsx:172`
> 的 `pendingLabel: '正在上线…'`，`components/dialogs/DangerConfirm.tsx:344` 在 pending 时渲染它；控制台 `ConfirmDialog.tsx:392`
> 已实现，按钮同时 `disabled`）。多出来的等待时间落在它上面，**不需要新的设计交付**；要验的是它在这段时间里
> 不闪、不可重复点击（测试方案 T15）。

## 数据模型

**一个 skill 一条向量，没有版本维度。** 检索读的是 `name` / `title` / `description` /
`when_to_use`，四个字段都在 `skill` 行上：`title` / `description` / `when_to_use` 由
`SkillRepository.recordPublish` 写（V21、ADR 0031），`name` 创建后就不再变、不由它写，
**这三个字段只在发布时才动——包括回滚**（`name` 不在其中）。草稿的文本在 `skill_version.frontmatter` 里，不参与检索（2026-10-25 定）。
一个 skill 因此只有一个候选文本，版本进键就是"只有单值的一维"。

```sql
CREATE TABLE skill_embedding (
    skill_id   TEXT NOT NULL REFERENCES skill(id) ON DELETE CASCADE,
    model      TEXT NOT NULL,           -- dashscope:text-embedding-v4:1024
    text_hash  TEXT NOT NULL,           -- sha256(拼好的文本，见 SkillEmbeddingTextSource.compose)
    embedding  vector(1024) NOT NULL,
    updated_at TEXT NOT NULL,            -- RFC3339 UTC，与全库一致（V1）；不是 TIMESTAMPTZ
    PRIMARY KEY (skill_id, model)
);
```

**四条"没有"，每条都是一个被否掉的方案：**

- **没有 `version_id`**。一个 skill 只有一个已发布文本；多这一维只有单值，写的时候还要额外删旧行，
  是"两个机制做一件事"。
- **没有状态列**。live / draft / offline / deleted 一律不复制进来——检索时问 M12（见 §检索链）。
  于是上下线、改可见性**不需要任何向量操作**，也不存在"状态没同步过去"这种故障。软删除不动向量行
  （M12 的谓词会滤掉它），硬删才靠外键级联——而产品里没有硬删。
- **没有 outbox 表**。向量在发布事务里算，所以不存在"提交了但还没算"这个中间态，也就不需要待办表、
  worker 与退避重试。被否方案的代价写在下文 §写入与重算时机。
- **没有文本副本**。`text_hash` 是哈希，不是文本；文本只在 `skill` 行上有一份。

**`model` 进键**：换模型是加法——新模型名算一遍、切读、删旧行；两份向量不可比，所以模型必须进键。
**维度固定 1024**：换到别的维度是一次迁移 + 全量重算，不是改配置。

**规模**：1024 维 float4 ≈ 4 KB/行。10 万 ≈ 400 MB，100 万 ≈ 4 GB——这正是「1 核 1 GB 一万舒适、五万勉强」那个规格判断（§检索链 › 规模与规格）的来源。

## 接口

| 方法 | 路径 | 鉴权 | 作用 |
|---|---|---|---|
| `GET` | `/api/v1/skills?q=&scope=library\|public\|all&semantic=true&limit=10&category=&public_tag=&my_tag=` | 凭据 | 统一检索（与 v14 的列表/发现同一路由） |
| `POST` | `/web/skills/{namespace}/{name}/publish`（现有路由） | 会话 + CSRF | **契约变化**：事务内完成向量写入；失败返回 `503 semantic_unavailable`，发布不生效 |

`search` 的规则：

- `scope` 沿用 v14 的两个线名（`library` / `public`，ADR 0082），**不改成 `mine`**：CLI 与控制台已经
  在用这两个值，改名只会让旧客户端收到 400。本版新增 `all`——**字面档没有并集，`all` 只有语义档能答**，
  带 `semantic=false` 时是一个用法错误。
- `limit` 语义档默认 10、上限 50；`semantic=false` 退回现有 L1；语义档拒绝 `cursor`
  （相似度不是页边界）。
- **过滤在语义档也成立**（2026-10-25 定）：`category` / `public_tag` / `my_tag` 先把候选集收窄，
  再在集合内按向量排序。见 §检索链的"两段式"。
- **`semantic` 在接口层是显式开启的**：不传就是 v14 的老行为（字面检索、可按游标翻页；`limit` 公域默认 20、私域默认 50，上限都是 100）。
  这不是产品默认值的表达——`skills search` 不带任何旗标时**会显式发 `semantic=true`**（PRD #13）。
  控制台不走这条路由的语义开关：`/web/discover` 由服务端按「有没有 `q`」决定（见下）。
  这样改是因为同一条路由还服务着两版之前就存在的列表与翻页，让"没写参数"改含义会让那些调用方在无人察觉时不 400 就换页大小。
- 响应每行带 `score`（0–1，余弦相似度）；低于阈值的行不返回；整批为空时 `skills: []` 且带 `note`。
- **检索侧的故障降级**（PRD #7）：调用 provider 超时（默认 5 秒，`timeout` 可配）或返回非 200 时，接口**不失败**——
  它退回字面检索，并在响应的 `note` 里说明"语义检索暂不可用"。整条路径 `semantic=false` 始终可用。
  三种收尾，说法各不相同（都逐字写在实现里，`SkillsController.endingOf` 与 `WebDiscoverController`）：

  | 情形 | `note` |
  |---|---|
  | 字面检索找到了行 | 「语义检索暂不可用。下面是按字面找到的结果。」 |
  | 字面检索一行也没有 | 「语义检索暂不可用。按字面找也没有匹配的 skill。」 |
  | 这一页在结果之外（`total > 0` 但这一页空） | 只有第一句「语义检索暂不可用。」——说「没匹配」会与同一响应里的 `total` 打架，说「下面是」会指着一页空白 |
  | `scope=all`（没有字面形式） | 「语义检索暂不可用。这一档只能按意思找，所以这次没有结果。」 |
- **不新增控制台操作，也不新开路由**：控制台发现页仍调 `GET /web/discover`，语义词由服务端按"有没有 `q`"决定（见下）。

### 发现页那一条：同一路由，两种形状（2026-10-25 用户定）

`GET /web/discover?q=…&tag=…&p=…`（会话）：

| 什么时候 | 谁回答 | 形状 |
|---|---|---|
| 有 `q` | 语义（`SemanticSearchUseCase`，`PUBLIC`、上限 10——与 CLI 默认一致，所以"同一个问题同一个答案"成立） | `{skills, note?}`：每行带 `score`；**没有 `p` / `page_size` / `total`** |
| 只有 `tag` | 字面检索，六条一页 | `{skills, p, page_size, total}` |
| 有 `q` 但 provider 不可用 | 字面检索 + 说明 | 分页那一种形状，再加 `note`：字面找到时是「语义检索暂不可用。下面是按字面找到的结果。」，字面也没有时是「语义检索暂不可用。按字面找也没有匹配的 skill。」 |

- **判据是"有没有打关键词"，不是再加一个开关。** 搜索框里写的是"我要做成什么事"，那问的就是意思；分类是浏览。
  再让人选一次模式，等于把输入已经说了的事再问一遍。CLI 保留显式的 `--semantic`，因为那条路由还服务着列表与翻页。
- **客户端靠 `total` 在不在判断画不画页码条**——语义没有第二页，相似度不是页边界。
- **那个 10 写在四处，必须一起改**：`SemanticSearchUseCase.DEFAULT_LIMIT`（服务端默认）、CLI 的 `searchPageSize`、控制台的 `SEMANTIC_LIMIT`、设计件的 `SEMANTIC_LIMIT`。目前一致，但没有任何一处从另一处取值——改默认值时要四处一起看，否则 PRD #10 的「同一批结果」当场不成立。
- **结果那一行是按回车才搜**（2026-10-25 用户定）：一次搜索要问一次模型，边打边筛等于每敲一个字付一次钱，
  而且几个请求会互相抢答。框里存草稿、地址里存搜过的词；框边不画「搜索」按钮，回车就是它。
- **空态三句话，各归各的**（2026-10-25，审计后定）：
  - 「没有足够相关的 skill。」——语义档的**空**，在 `/web/discover` 上由控制台按形状自己写（设计件里就是这句），服务端不再给一句，否则同一个态有两种拼法。
    **API 面不同**：`/api/v1/skills` 的整批为空仍然带 `note: 没有足够相关的 skill。`——那边没有页面来写这句。
  - 「没有找到匹配的 skill。换个词，或者换一个分类。」——字面档的空，设计件那句。
  - 词表里没有那个名字、或 provider 不可用（降级）——**只有服务端知道**，走 `note`；有 `note` 时页面就显示 `note` 那一句，不再叠一句空态。
    **开关关闭不在此列**：那是配置态，静默走字面检索、没有 `note`（PRD #8）。

## 写入与重算时机（事务性）

**分两类，绝不混成一个「事务同步」：**

1. **状态（上线 / 下线 / 下架 / 删除 / 恢复）——零同步。**
   状态不复制到向量表；检索时由 M12 按当前状态过滤（§检索链）。**软删除不动向量行**——M12 的谓词把它滤掉就够了；`ON DELETE CASCADE` 只是行真被硬删时的安全网，而产品里没有硬删。
   因此**上下线不需要任何向量操作**，也不存在「状态没同步过去」这种故障。

2. **文本（title / description / when_to_use 变更）——在发布事务内计算。**
   **只有一个写入点**：`PublishSkillVersionUseCase` 在指针真的动了之后调用 `EmbeddingIndex.refresh(skillId)`。
   `recordPublish` 是唯一**改**这三个字段的地方（`name` 创建时写一次、此后不变；创建时 INSERT 还会写
   title/description，但那时 `current_version_id` 还是空，没有东西可索引），回滚也走它。丢弃草稿、改分类、下线、软删除都不动文本，
   因此不产生任何向量工作。顺序就是 §发布时的行为 那张图：

   ```
   指针前移 → 读回新文本 → 调百炼 → upsert (skill_id, model) → 审计 → COMMIT
   ```

   三条边界条件，都必须显式成立：

   - **没有已发布文本就什么都不做**（从未发布、已删除）：不是失败，是没什么可索引。
   - **百炼失败 = 整笔回滚**：指针没动、审计没写、向量没写，调用方收到 503。这是"事务做完才算发布成功"的
     全部含义。
   - **隐私开关关闭时 `refresh` 直接返回**：发布照常成功，只是不产生向量；检索走关键词。

3. **为什么不是 outbox + worker（被否方案）。**
   第一版设计的是："事务里只写一条 `embedding_job`，worker 在事务外算向量、失败指数退避"。它的好处是发布
   不依赖百炼，代价是一整套常驻机制（待办表、调度器、重试策略）与一个"发布成功但几百毫秒内搜不到"的窗口。
   2026-10-25 改为事务内计算，理由是：**发布是人在浏览器里做的一次动作，不是热路径**，值得为"发布成功 ⇒ 一定有
   向量"付一次往返；而仓库已经有过同样的取舍——`SendVerificationCodeUseCase` 就在事务里调阿里云短信，
   注释写的是"短信没发出去，额度就回滚"。

   明知的代价，三条都接受：① 发布期间持住 `skill` 行锁与一个数据库连接，时长为一次 provider 往返（超时 5 秒）；
   ② 百炼不可用时发布不可用，退路是把语义开关关掉；③ 批量发布按条累加延迟。

4. **存量 skill 不会自己长向量**，而 v19 上线时线上没有已发布的 skill（2026-10-25 确认），所以**不做回填**。
   配置里留一道闸而不是一个脚本：部署前跑一次
   `SELECT count(*) FROM skill WHERE current_version_id IS NOT NULL AND deleted_at IS NULL;`，
   结果不是 0 的话，说明这个前提变了，再用一次性脚本补——脚本不预先写，因为它今天没有用户。

## 检索链（最终选型）

**纯向量，不做混排。** 候选集小的时候是精确扫描，大的时候按下面的两段式近似取——两者用的是同一条查询，只是集合来源不同。

依据是**随仓库的标注集实测**（2026-10-25，33 个 skill，`src/test/resources/retrieval/labeled.tsv`，用 `scripts/retrieval-eval.py` 复跑）：

| 查询集 | 向量 `Recall@10` |
|---|---|
| 语义式 66 | 0.909 |
| 名字式 33 | 1.000 |
| 合计 99 | 0.939 |

**口径（重要）**：这 33 个 skill 的 frontmatter 只有 `name` 与 `description`（2026-10-25 逐个核对过本机
`~/.claude/skills`，没有一个带 `title` 或 `when_to_use`），所以实测文本就是这两行——`compose` 的规则仍是
四个字段、空的那一行整行不出现。也就是说，这组数字描述的是「只有名字与描述」的 skill，而这正是真实库里
最常见的那种；一个写全了 `when_to_use` 的 skill 会多一行文本，分数会动，阈值也要重新量。

spike 期的对照是另一组数（同一批 skill 上关键词 0.73 对向量 0.92，混排 0.91/0.97/0.93）——那是 66 + 40 条的另一份查询集，关键词实现也没有随仓库走，**不可复跑**，只用于"要不要做向量""要不要混排"这两个判断，见 [ADR 0095](../../decisions/0095-semantic-retrieval-is-accepted.md) §理由。

混排三组全输：RRF 只看向对名次，弱的关键词臂会用错误结果稀释强信号。**保留 `--semantic=false` 作为退路**，它不是融合。

### 可见性怎么进来：两段式，判据是集合大小（2026-10-25 定）

**不在向量表里复制状态，也不让一条 SQL 跨模块 JOIN**——向量不进 `skill` 表，所以过滤与近邻查询不可能
是同一个语句。顺序反过来（先 top-k 再过滤）在库大时会漏：100 万条里自己的库只占千分之一时，前 `limit × 20` 名
可能全是别人的公开 skill，滤完一条不剩。

所以：**任何 scope、任何过滤组合，先问 M12「这个集合有多大」**（一条 `LIMIT 上限+1` 的查询），再决定走哪条。

| 集合大小 | 做法 | 结果 |
|---|---|---|
| **≤ 20000** | M12 给 id 集合，向量查询 `WHERE skill_id = ANY(:ids)` | **精确**：集合内真正的 top-N，召回不受库规模影响 |
| **> 20000** | 向量取 `limit × 20`（默认 200），再问 M12 这些 id 里哪些符合 scope + 过滤 | **近似**——但只在过滤不具选择性时发生：热门标签几乎不缩小集合，取回的那一段里几乎全是匹配项 |

**判据是集合大小，不是 scope。** 冷门标签的公域检索也是小集合、也走精确；没加过滤的私域大库也会走
过度取回。这样私域、公域、分类、标签是同一条规则，没有两套逻辑要各自维护。

上限取 20000 个 id（约 520 KB 在内存里往返一次）。

**索引策略**：一万条以内不建 HNSW，走精确扫描（召回 100%、几毫秒）；到十万量级建 `hnsw (embedding vector_cosine_ops)`。
`WHERE skill_id = ANY(:ids)` 在两种扫描下都成立，所以换索引不改查询。

**规模与规格**（当前实例 `pg.n1e.1c.1m`，1 核 1 GB）：一万舒适、五万勉强、十万以上需升到 4–8 GB、百万需 16 GB 以上。容量靠升实例，不改代码。

## 开放问题

1. **pgvector 版本**：实例已确认提供 `vector` 扩展（2026-10-25，阿里云 CLI `DescribePostgresExtensions`）；本机测试库上 `extversion` 是 **0.8.7**，满足过滤场景要的 0.8。**生产实例上的版本仍未查**，上线前跑一次 `SELECT extversion FROM pg_extension WHERE extname='vector'`；低于 0.8 时改成不过滤的精确扫描（本版规模下没有召回损失）。
2. **阈值定在哪**（2026-10-25 已定：**0.40**）：两侧都量过了。负样本（`unmatched.tsv`，38 条市场里没有对应能力的请求）上，任何 skill 能给到的最高分是 **0.397**；标注集里**进过前 10 的**正确答案 5 分位是 **0.415**。0.40 是"一条都不漏过"的最低一档，再往上走的代价开始陡增：

   | 阈值 | 被挡掉的命中行 | 整批为空的查询 | 负样本漏过 |
   |---|---|---|---|
   | 0.38 | 2 / 99 | 3 / 99 | 1 / 38 |
   | **0.40** | **3 / 99** | **3 / 99** | **0 / 38** |
   | 0.42 | 6 / 99 | 5 / 99 | 0 / 38 |
   | 0.45 | 9 / 99 | 9 / 99 | 0 / 38 |

   两个边界只隔 0.018，余量薄；**改评测集就要重新量**，它不是常数。数值同时写在 `application.yml` 与 `RetrievalProperties` 的默认值里，两处必须一致。
3. **存量回填**（2026-10-25 已定）：**不做**。线上没有已发布的 skill，所以没有要补的存量。部署前用
   `SELECT count(*) FROM skill WHERE current_version_id IS NOT NULL AND deleted_at IS NULL;` 核对这一前提；
   不为一个今天没有用户的问题预先写脚本，也不新开一条管理路由。
4. **迁移账号权限**：`CREATE EXTENSION` 需要管理员级账号（RDS 上是 `rds_superuser` 一档），Flyway 的业务账号可能不够——上线前必须确认。
5. **隐私开关关闭后的重建**：开关关着的期间发布的 skill 没有向量；重新打开后它们同样要等下次发布。
   线上没有存量（问题 3），所以本版同样不做重建；开关开关是部署级操作，与全量重算不是同一件事。
