## 用例

### T1 · 天天在用也躲不过绝对上限

- **前置**：一个账号，通过 `POST /web/login` 真的建立会话，测试持有那张 cookie。
- **步骤**：把该会话的 `creation_time` 推到 **8 天前**，`last_access_time` 与 `expiry_time` 都设成**刚刚**（也就是「一直在用」），再用那张 cookie 请求一个 `/web/**` 上需要登录的路径。
- **期望**：被要求重新登录（与未登录同一个答案）。
- **判定**：通过／失败。
- **为什么这条是核心**：**旧的滑动规则下它会通过**——这正是本版要防的回归。

### T2 · 差一点没到 7 天仍然可用

- **前置**：同上。
- **步骤**：`creation_time` 推到 **6 天 23 小时前**，其余同上；请求。
- **期望**：正常返回。
- **判定**：通过／失败。
- **它防的是什么**：把上限算错一位（`>=` 写成 `>` 的反面、或把天当成秒），一种在 T1 上照样通过的错。

### T3 · 24 小时空闲失效

- **前置**：同上。
- **步骤**：`creation_time` 是 3 天前，`last_access_time` 与 `expiry_time` 推到 **25 小时前**；请求。
- **期望**：被要求重新登录。
- **判定**：通过／失败。

### T4 · 差一点没到空闲窗口仍然可用

- **前置**：同上。
- **步骤**：`last_access_time` 推到 **23 小时前**（`creation_time` 仍在 7 天以内）；请求。
- **期望**：正常返回。
- **判定**：通过／失败。

### T5 · 退出另一台设备，那台立刻失效，自己不受影响

- **前置**：同一个账号在**两处**建立会话（A、B），各自持有 cookie；A 先 `GET /web/sessions` 拿到 B 的 `device_id`。
- **步骤**：用 A 发 `POST /web/sessions/{B 的 device_id}/revoke`；然后用 B 的 cookie 请求，再用 A 的 cookie 请求。
- **期望**：B 被要求重新登录；**A 正常**。
- **判定**：通过／失败。

### T6 · 退出是当场生效，不是等清扫

- **前置**：同 T5，且**不触发**框架的过期清扫（不等待任何定时任务）。
- **步骤**：退出 B 之后**立即**用 B 的 cookie 请求。
- **期望**：立刻被要求重新登录。
- **判定**：通过／失败。
- **它防的是什么**：「靠一个定时清扫来生效」的实现——那种实现下，被退出的凭据在两次清扫之间仍然可用。

### T7 · 退出其他所有设备

- **前置**：同一账号在**三处**建立会话（A、B、C）。
- **步骤**：用 A 发 `POST /web/sessions/revoke-others`；然后 A、B、C 各请求一次。
- **期望**：B 与 C 都被要求重新登录；**A 继续可用**；响应里说明退出了几台。
- **判定**：通过／失败。

### T8 · 列表不泄露会话 id

- **前置**：一个账号有至少两台设备会话；从库里读出这些会话的 `session_id`（原始值）。
- **步骤**：`GET /web/sessions`，把响应体与（P2 之后的）页面文本拿来比对。
- **期望**：**一个会话 id 都不出现**；也没有其它能直接当凭据用的串。
- **判定**：通过／失败。

### T9 · 拿别人的 `device_id` 发起退出，什么都不发生

- **前置**：两个不同账号，各自有会话；A 拿到 B 的 `device_id`（通过测试直接读库或构造）。
- **步骤**：用 A 发 `POST /web/sessions/{B 的 device_id}/revoke`；再发一个**不存在的** id；最后用 B 的 cookie 请求。
- **期望**：两次返回**同一个答案**（`session_not_found`，不区分「不存在」与「不是你的」）；**B 仍然可用**。
- **判定**：通过／失败。

### T10 · 重置密码结束所有会话，列表随之清空（回归）

- **前置**：一个账号有两台设备会话。
- **步骤**：走既有的重置密码流程；然后两台各请求一次，并用其中一台请求 `GET /web/sessions`。
- **期望**：两台都被要求重新登录；列表为空（新登录后看到的列表里不含旧的两台）。
- **判定**：通过／失败。

### T11 · 错配置启动失败

- **前置**：配置成绝对上限**短于**空闲窗口（例如绝对 1 小时、空闲 24 小时）。
- **步骤**：启动应用上下文。
- **期望**：**启动失败**并说明原因（照 `TokenPolicy` 的既有形状），不是静默让一条尺子失效。
- **判定**：通过／失败。

### T12 · 超过绝对上限的会话那一行也从库里消失

- **前置**：同 T1。
- **步骤**：T1 的请求之后，从库里查该会话的 `primary_id` 是否还存在。
- **期望**：行已不在（读取时的判定把会话作废掉了，不是只在内存里拒绝）。
- **判定**：通过／失败。

### T13 · 集成测试改用签发的 key 取令牌之后，整套仍然全绿

- **前置**：`AbstractIT` 取令牌的方式从「客户端密钥换令牌」改成「登录一次、签一把 key」（`POST /web/login` → `POST /web/keys` → 明文当 bearer）。**`token()` 的函数签名不变，因此 60 多个调用点一个字都不用改。**
- **步骤**：`mvn -o verify`。
- **期望**：全部 IT 通过；库里**没有任何 `grant_types` 含 `client_credentials` 的客户端行**；`AbstractIT` 里不再有 `seedClient`。
- **判定**：通过／失败。
- **它防的是什么**：「改完测试就红，于是把服务端那半个留着」——**那正是这笔欠账活到今天的方式**。

### T14 · CLI 里 `--client-credentials` 及其两个环境变量彻底不存在

- **前置**：删掉那个形状、`loginUnattended`、`auth.ClientCredentials`、两个配置常量、`Revoke` 的密钥分支、`ErrRevocationNeedsSecret`、`ErrNotRenewable`（**它前面那条守卫保留**）。
- **步骤**：`go test ./...`；再在仓库里搜 `client-credentials`、`SKILLMASTER_CLIENT_ID`、`SKILLMASTER_CLIENT_SECRET`。
- **期望**：测试全绿；`skillmaster login --client-credentials` 得到的是「未知参数」，而不是一个已废弃形状自己的报错；上述三处搜索在**用户可见的文本里**零命中（帮助输出、README、任何错误消息都不再有）。
- **参数名本身仍然在测试里，那是这条用例要的答案**：`keys_test.go` 有一行断言它得到「未知的选项」。所以「零命中」只对用户可见文本成立——**判据是「有没有哪句话还在劝人去跑它」**，不是字符串计数。
- **还要断言「没有句子再劝人去跑那条命令」**：`ErrNotRenewable` 的文案与 `revokeReplaced` 那一句都在搜索范围内——**它们正是这次读代码时发现的两个真实位置**，只搜参数名是搜不到的。
- **判定**：通过／失败。

### T17 · 一台还存着无人值守凭据的机器，不会得到死胡同

- **前置**：往本机凭据里放一份**不是 `skm_` 开头、且没有刷新令牌**的东西——这正是 `--client-credentials` 时代留下的形状（今天真用过那条路的机器就是这个状态）。
- **步骤**：（a）让它过期，跑一条需要凭据的命令；（b）再跑 `skillmaster login --with-key`（这一次是**替换**上一份凭据）。
- **期望**：
  - （a）那句话说明这份凭据**没有刷新令牌**，并给出**这个版本里真实存在的**两条出路（浏览器 `login`，或一把 key）——**不能**是「请重新运行 `login --client-credentials`」；
  - （b）输出说明上一份**无法从这台机器撤销**、且它自己会失效——**不是**「上一份已撤销」，也不是一个错。
- **判定**：通过／失败。
- **它防的是什么**：把「删掉一个参数」当成纯减法。删掉之后仍然存在的那类凭据，会从两句**没人会去搜的提示语**里漏出来（T14 只搜参数名，搜不到它们）。

## 环境与数据

- **环境怎么造**：`skillmaster-server` 的集成测试环境——Postgres 从干净状态由 Flyway 建库（`CleanMigrateFlyway`），一个测试账号。会话**通过 `POST /web/login` 真的建立**，cookie 由测试持有；不手工造会话行。脚手架与 `SessionSchemaOwnershipTest`、`ApiKeyIT` 同一套。
- **时间怎么造**：**不引入时钟缝**。照 `ApiKeyIT` 已经建立的做法——测试**直接写库**把 `creation_time` / `last_access_time` / `expiry_time` 推到想要的时刻（`UPDATE spring_session SET creation_time = …`）。
  - **为什么不用可注入的 Clock**：这一版要验的正是「按库里那个时间判定」这件事，而一个可注入的时钟会把被测的那一步换掉。**代价要在用例里写明**：这些测试写的是**框架的表**——这是允许的（`TableOwnershipTest` 只扫 `src/main/java` 与迁移，见它第 40、42 行），但正因为允许，下一个人容易误以为主代码也可以。每个碰这些表的用例都要留一句注释说清这一点。
  - **框架侧的注意**：Spring Session 的 JDBC 仓库在请求开始时读一次会话，因此**先改库、再发请求**，顺序反了测的就是旧值。
- **数据**：账号、会话都是测试自己造的，可复现；不依赖任何外部数据。
- **清理**：测试用的事务/清库流程与既有 IT 一致（跑前 migrate，跑后清）。**不留残留**——被退出的会话行由被测行为自己删掉（T12 就是断言这件事）。
- **范围 #5（删欠账）的验证不另造环境**：T13 与 T15 用既有的 IT 环境，T14 用 CLI 的单元测试，T16 是一次文档搜索。**它们比新功能的用例更容易跑，这也是先做删除的理由之一**——清完之后再写新代码，地基是干净的。

**审计两轮（2026-10-16）。** 第一轮 2 个互相不知情的审计者（服务端 / 控制台 + 设计件对照），**服务端 0 blocker 0 high**，控制台 1 high、2 medium、4 low；第二轮按同一规则起（因为第一轮出了 high），**2 个全新审计者**，各被告知第一轮改了什么。**每条都由我复核后才动手，每条修掉的都配一条会因它而失败的用例**——把修复回退、看那条用例当场失败。修掉的：

- **（high，控制台）** 一次失败的写入留下的 banner **永远不会消失**：列表已经重新读回来了、之后一次写入也成功了，页面上仍然说有个请求没成功，而且没有任何办法把它关掉。密钥屏同一处早就定了规矩（成功的 `load` 清 banner），这里是照它改的——并且把两个写入方设句子的时机挪到**重新读取之后**，否则那次重新读取的成功会把刚失败的答案一起擦掉。
- **（medium，控制台）** `/web/sessions/**` 的 `authenticated()` **一条断言都没有**：把那一行匹配器删掉，`WebSessionsIT` 12 条**全绿**，而匿名请求会落到控制器上抛异常，拿到的是 **500 而不是 401**。补进 `WebSecurityPlaneIT`（那个类就是为这件事存在的），并当场量出这个 500：删掉匹配器 → 新用例失败（`expected: 401 but was: 500`）、`WebSessionsIT` 仍然 12/12 绿——**审计那句「只有新用例会红」是量出来的，不是推出来的**。
- **（medium，文档）** `revoke-others` 的返回值「要在界面上说结果」而控制台没画那句话——**两处权威（TD 与 known-issues）里都没有这条决定**，只在代码注释与交付说明里。已就地写进 [`technical-design.md`](technical-design.md) §接口（说清「结果由状态本身承担」以及为什么不再写一句）。
- **（low，控制台）** 一次写入在飞的时候按 Escape：按钮是 `disabled` 的（鼠标到不了），键盘却能把提问关掉，于是读的人被告知「什么都没发生」而设备正在被退出。Escape 现在也在 `busy` 上把关。
- **（low，控制台）** `address` 为 null 的行会画一个空的标识行——那是**升级前创建的会话**（两个属性它都没有）。改成与同一行的客户端那格同样的处理：没有东西可说就不画，不发明文案。
- **（low，外壳）** 侧栏那个可展开项在有子项是当前页时没有 `aria-current`，而设计件在**同一处**设了它（并注明「三个信号里只有这个读屏器听不到」）。按设计件的取值补上，并把一条**永远不会失败的**断言（`.nav-disclosure.is-active`——那个类两边都不存在）换成它。
- **（low，测试）** 密钥屏的「最后使用」改动**没有任何用例钉着**（该文件里唯一的夹具 `last_used_at: null`），退回绝对时间会照样绿。补一条按设计件夹具的四种写法各断言一次、且**把时钟固定住**的用例。

### 001 · 会话的寿命，界面上一个字都没说（**第二步的设计交付已定：不说**）

`design/partials/auth-overlay.html` · `design/demos/dir3-hara-console.html` · **未验证**

设计件在重置完成那一屏写着「出于安全考虑，这个账号在所有设备上的登录都已经失效」（这条产品里确实实现了）。而**整个设计件里没有任何一处**表达会话的寿命——本版第二步（前端交互设计）交付之后，这一条有了答案：**界面上不说**，登录页不说、设备列表页也不说。

**为什么不说**：这一页要回答的是「这些是不是我登录的」，不是「它们还能活多久」；**看得见**与**能退出**已经覆盖了「我怀疑有人用过我的电脑」这个真实场景。寿命那条尺子服务的是「被遗忘的机器自己会死」，而它的受益者恰恰不在屏幕前——**说给一个不在看的人听没有意义**。参照产品的 Active Sessions 也不讲寿命（它讲的是「Last accessed on」，我们这一页有对应的「最近活动」）。**代价如实记**：周一回来发现要重新登录时，界面里没有任何东西提前告诉过你。

**这一条不是缺陷，是一个被本版带出来、又被第二步定下的设计判断**；写在这里是为了让实现那一步照着做——**别顺手加一句「7 天后需要重新登录」**。
