## 架构

本版**不引入新组件类型**，只在既有的三条边界上各加一小块：

```
                    ┌──────────────── 浏览器 ────────────────┐
                    │  cookie: SKILLMASTER_SESSION            │
                    └───────────────────┬────────────────────┘
                                        │
                    ┌───────────────────▼────────────────────┐
                    │ M1 的会话层（框架拥有，Java 不写其 SQL） │
                    │   spring_session / _attributes          │
                    └───────────────────┬────────────────────┘
                                        │
                     ┌──────────────────▼───────────────────┐
                     │ 绝对上限过滤器（新增，每个请求一次）   │
                     │  创建时间 + 7 天 < 现在 ⇒ 就地作废     │
                     └──────────────────┬───────────────────┘
                                        │
                    ┌───────────────────▼────────────────────┐
                    │ /web/** 链（会话 + CSRF，既有）         │
                    └───────────────────┬────────────────────┘
                                        │
        ┌───────────────────────────────▼──────────────────────────────┐
        │ WebSessionController（新增）                                  │
        │   GET  /web/sessions                  列出                     │
        │   POST /web/sessions/{id}/revoke       退出该设备             │
        │   POST /web/sessions/revoke-others     退出其他所有设备       │
        └───────────────────────────────┬──────────────────────────────┘
                                        │
                    ┌───────────────────▼────────────────────┐
                    │ WebSessionRegistry（既有接口，扩展）    │
                    │  SpringSessionRegistry（既有实现）      │
                    │   走框架 API，不写 SQL                  │
                    └────────────────────────────────────────┘
```

**三个边界各自为什么这么放**：

- **空闲尺子交给框架**（`spring.session.timeout`）。Spring Session 的 `max_inactive_interval` 就是这件事，自己再实现一遍是第二份真相。
- **绝对尺子必须由我们每个请求执行一次**。框架里没有这个概念——`expiry_time` 只表达「最后活动 + 空闲窗口」。**读时执行是权威的**：清扫任务只是让库里不留死行，不能让一个超过绝对上限的会话在两次清扫之间继续可用。
- **列表与撤销走框架自己的 API**，不碰它的表。这不是洁癖：`ModuleMap` 把 `spring_session` 记在 M1 名下（一张迁移里的表必须有主），但同一段注释写明「Java 里任何地方都不许把这两个表名写进 SQL，因为读写它们的是框架」（见 [`SpringSessionRegistry`](../../../skillmaster-server/src/main/java/com/skillmasterai/modules/account/internal/SpringSessionRegistry.java)）。本版延续这一条，**只扩那个接口**。

**数据流（文字）**：请求进来 → 框架解析会话 → 绝对上限过滤器看创建时间 → 通过则进 `/web/**` 链 → 控制器 → `WebSessionRegistry` → 框架 API。被退出的设备**不需要等任何缓存过期**：它下一次请求时，会话行已经不在库里了。

## 数据模型

**不加表。** 设备那句「这是哪台机器」作为**会话属性**存进会话本身，在登录那一刻写一次：

| 属性名 | 内容 | 为什么是它 |
|---|---|---|
| `device_id` | 随机 ULID | **对外用它在 URL 里标识一台设备**，代替会话 id（后者等价于凭据，绝不能出现在页面或响应体里） |
| `device_user_agent` | 登录时的 User-Agent 原文 | 列表上「哪台机器」的唯一来源；解析成可读形状是显示层的事（Q3） |
| `device_login_address` | 登录时的来源地址 | 「这台是不是我」最有效的判据（Q4）；已有 `forward-headers-strategy: framework` 负责取对，见 `application.yml` 那一段 |

**其余全部从框架已有的读**：登录时间 = `Session.getCreationTime()`，最后活动 = `Session.getLastAccessedTime()`。

**为什么不加一张自己的表**：一张 `login_device` 表要把设备和会话对上，就必须存会话 id 或框架的 `primary_id`——那是在框架的表之外再造一份**影子索引**，而框架的表只有框架能读，于是这第二份真相没有任何东西保证它跟着会话一起消失。会话属性是框架自己的字段，用框架的 API 存读，**退出那台设备时它随会话行级联删除**（V3 的 `spring_session_attributes` 已有 `ON DELETE CASCADE`），不需要任何清理任务。

**约束与不写的约束**：

- `device_id` 只在**一个用户的所有会话内**唯一（ULID，碰撞概率足够低）。**不建唯一索引**——它在会话属性里，不是一个列；建索引要先加列，那正是上面拒绝的形状。
- 属性必须可序列化：框架把序列化后的 `SecurityContext` 已经放在同一张属性表里，所以这是既有约定而非新增要求。
- **不动 V3 的 DDL**。`spring_session.creation_time` 就是绝对上限要读的那一列，它已经在了（`Session.getCreationTime()` 读的就是它）。本版**没有迁移**。

## 接口

三个，都在 `/web/**`（会话 + CSRF，与 `/web/keys` 同一套），**没有 `/api/v1/` 上的对应物**——会话与凭据的管理都只在浏览器平面，因为能造凭据的必须是会话（[ADR 0040](../../decisions/0040-api-key-in-the-cli-now-the-browser-path-later.md) §决定 1）。

| 方法 | 路径 | 作用 | 入参 | 出参 |
|---|---|---|---|---|
| `GET` | `/web/sessions` | 列出当前账号的全部登录设备 | — | 每台：`device_id`、设备描述、登录地址、登录时间、最后活动、`current`（是否当前这台） |
| `POST` | `/web/sessions/{id}/revoke` | 退出该设备 | `id` = `device_id` | 空（204/200，照 `/web/keys` 的既有形状） |
| `POST` | `/web/sessions/revoke-others` | 退出除当前这台以外的全部 | — | 被退出的台数（照「退出其他所有设备」要在界面上说结果） |

**错误形状**：`session_not_found` —— **不存在的 `device_id` 与「别人的会话」返回同一个答案**，与 `/web/keys` 对「不是你的 key」的处理一致：不泄露存在性。

**两个必须写明的边**：

- **`revoke-others` 不会伤到当前这台**：被退出集合由「principal 是这个用户**且**会话 id ≠ 当前请求的会话 id」定义，不是「全部再补一个」。
- **`device_id` 不是凭据**，但它是一个**地址**：拿到它的人可以退出那台设备（需要有会话才能发请求，所以实际是「自己退出自己的设备」）。这与 `/web/keys/{id}/revoke` 同一个风险等级，因此沿用同一套鉴权，不额外发明机制。

## 开放问题

**这一节原来有七个问题，它们在 2026-10-16 的讨论里逐条定了**——答案落在下面的「已定」，所以它们不再"开放"。**没有未决项。**

### 已定（2026-10-16）

| # | 问题 | 答案 | 为什么 |
|---|---|---|---|
| Q1 | 一个账号最多同时留几行会话？（原先问成「一台设备几个会话」，把两个轴混了——**会话是按「一次登录留下的那个 cookie 罐」走的，列表是按账号列的**） | **不设人为上限** | **两条尺子已经把它限住了**：被遗忘的机器最多活 24 小时（空闲先到），而常用的浏览器只占一行——同一浏览器里反复登录是复用同一行、只把会话 id 转一下（防会话固定的标准做法）。再定一个数只是照抄参照产品的 100，**而它那边的绝对上限默认是关的**，尺子跟我们不一样 |
| Q2 | 24 小时空闲带来的「周一要重新登录」可接受吗？ | **接受，保持 24 小时** | 周末那两天正是「我忘了那台机器还登录着」最常发生的时候——那正是这条尺子要拦的场景。放宽会正好放过它 |
| Q3 | User-Agent 解析到什么程度？ | **粗解析**（浏览器 + 平台两类），**不引第三方库**；解析不出来就显示原文 | 显示什么由设计交付定，解析程度跟着它走。不引库是因为不值得为一个标签引一个依赖 |
| Q4 | 列表要不要显示登录地址？ | **显示完整地址** | 它是判「这台是不是我」最有效的一条。**前提同时成立**：退出那台时地址随会话行级联删除（见 §数据模型） |
| Q5 | 退出设备要不要写审计事件？ | **写**，照 `audit_event` 的既有形状 | 撤销 key 已经这么做，退出会话是同一类动作 |
| Q6 | 「当前这台」怎么标？ | 服务端比较当前请求的会话 id，**只送一个 `current` 布尔**；会话 id 既不下发也不进 URL | 没有取舍余地：它与「列表里不出现凭据」是同一条规矩 |
| Q7 | 列表一屏放几条、要不要分页？ | **不分页，一屏放完** | Q1 不设上限、两条尺子又把真实行数限在「几个」（遗忘的机器最多活一天、常用的浏览器只占一行），所以它是个**显示问题**；第二步的设计交付就这么画的（[`design/README.md`](../../../design/README.md) §登录设备，`?page=sessions`：夹具三条、没有分页控件）。真长起来时的顺序仍是——先想「是不是该让某几条更早过期」，再想分页 |

**Q1 的答案还有一个推论**：既然不设上限、行数又由尺子限住，真实的列表长度是**几个**。所以这一屏按"一屏放完"设计，而**分页是等它真的需要时才加的东西**。
