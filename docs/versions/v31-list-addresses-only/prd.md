## 用户与场景

**谁在用**：在 agent 会话开始时或缺省看一眼「我库里有什么」的 agent；以及替它们配置规则的人。

**在什么场景下用**：agent 需要一份库的清单——有哪些 skill、它们的地址是什么、接下来要 `invoke` / `read` 哪一个。它不需要在清单里读每一段的说明：**发现**这一步已经由 `skills search` 承担（v27 起规则段默认先搜），清单只需要回答「有什么」。

**现在的替代做法是什么**：

| 做法 | 差在哪 |
|---|---|
| 今天的 `skills list`：地址 + 描述 - 适用场景 | 一个 25 条的库就是 **15.9 KB / 76 行**；每多一条就多 0.6 KB，而且每次调用都整份重进上下文 |
| 只用 `skills search` | 搜索要一句问题；「把库列一遍」不是问题 |
| 逐个 `skill show` | N 次往返，比一次清单贵得多 |

**实测口径**：本机库 25 条（2026-10-30），`skmr skills list` 实测 15,896 字节 / 76 行；只取其中的地址行是 934 字节 / 39 行（含页脚）。

## 范围

### 做

| # | 做什么 | 交付形态 |
|---|---|---|
| 1 | **`skills list` 默认每条只打地址**（`命名空间/名字`，不带版本），一行一个、卡片之间不加空行 | CLI |
| 2 | **默认列出全部**：内部翻完所有页，不再默认停在前 50 条；页脚仍是「（共 N 个。加载某一个：…）」 | CLI |
| 3 | **`--all` 保留但不再改变行为**（1.x 内命令面只增不减，见 `RELEASE.md` §1）；文档写明「现在默认就是全部」 | CLI + 帮助 |
| 4 | **`--verbose` 仍然给描述**：地址 + 缩进的「描述 - 适用场景」+ 缩进的一行详情（来源 / 状态 / 版本 / 更新于，以及卡片上有的分类与公开标签） | CLI |
| 5 | **`skill show` 不动**：它仍是单个 skill 的全量详情 | 无改动，但要有验收守住 |
| 6 | **`skills search` 不动**：地址 + 描述 + 适用场景 | 无改动，但要有验收守住 |

**三个命令的分工（本版确立）**：`search` 回答「哪个可能相关」，`list` 回答「库里有什么」，`show` 回答「这一个是什么」。

### 不做

| # | 不做什么 | 为什么 | 什么时候可能做 |
|---|---|---|---|
| 1 | 默认行里加状态 / 来源 / 版本 / 更新于 | 这些维度已经由 `--show` / `--source` / `--sort` 表达；输出不重复「你是用哪个维度筛出来的」。要它们用 `--verbose` | 若出现「分不清哪条能 invoke」的实际反馈 |
| 2 | 把 `--verbose` 的描述也去掉 | `--verbose` 的语义是「更多」，保留它才能一次调用看完整个库；去掉会让批量总览只能逐个 `show` | 不做 |
| 3 | 新增 `--describe` 之类的第二开关 | `--verbose` 已经是那个开关；多一个只是同义反复 | 不做 |
| 4 | 改 `skills search` 的输出 | search 的相关度判断必须看描述；v30 刚定完它的形状 | 不做 |
| 5 | 给 `skills list` 加 `--json` | v13 起列表不提供 `--json`；本版不翻案 | 未定 |
| 6 | 为超大库加新的硬上限 | 默认列全是本版的明确选择；过大的库用 `--show` / `--namespace` / 分类 / 标签 / 关键词收窄 | 若实测出现 `list` 撑爆上下文 |

## 控制台操作与 CLI 对应

本版没有控制台一侧的改动，没有映射表条目。

## 验收与指标

### 验收标准

| # | 验收标准 | 怎么判定 |
|---|---|---|
| A1 | 默认每行只有地址：`skmr skills list` 的每个非空行要么是 `ns/name`，要么是最后一行页脚 `（…）` | 逐行跑正则；不含缩进行 |
| A2 | 默认列全：库里 N 条时，输出恰好 N 个地址行，且没有「还有更多」 | 与 `skills list --all` 的结果逐字节相同 |
| A3 | `--all` 不报错、不改变输出；`--all` 与不带它逐字节相同 | 两次输出 `cmp` |
| A4 | `--verbose` 保留描述与小字段：每条是地址 + 缩进的「描述 - 适用场景」+ 缩进的「来源 / 状态 / 版本 / 更新于 / 分类 / 公开标签」（空字段不打印） | 读输出 |
| A5 | `skills search` 不变：仍是地址 + 描述 | 同一查询在改动前后输出一致 |
| A6 | `skill show` 不变：描述、适用场景、运行环境、版本、分类、标签都在 | 读输出 |
| A7 | 帮助同步：`skills list --help` 的 Usage / 参数 / 输出 / 例子说明默认只给地址、默认列全、`--all` 保留 | 读帮助页 |
| A8 | 空库与筛选为空：文案不变（不因本版变成一行地址） | 造一个空结果 |

**成立条件**：A1、A2、A4 三条不满足，本版不算交付。

### 指标

| 指标 | 定义 | 怎么量 | 目标 |
|---|---|---|---|
| 清单体积 | `skmr skills list` 的 stdout 字节数 | 本机 25 条的库上 `wc -c`（口径：默认输出、含页脚） | 从 15,896 B 降到 ≤ 1,500 B |

## 依赖与前置

- **决策**：[ADR 0115](../../decisions/0115-list-is-an-inventory-and-descriptions-live-in-show.md)（本版新增）——`list` 是清单，描述在 `search` 与 `show`；v13 的卡片契约在 `list` 上被取代。
- **外部依赖**：平台技能 `skillmaster/startup` 若提到 `skills list` 的输出形状，需要同步改（那是平台技能，走草稿 → 控制台，不在本仓库代码里）。
- **内部前提**：v30 已把 `skills search` 的卡片契约改成「提示 + 地址 + 描述」；本版接着改 `list`，两者合起来才让 `search` 与 `list` 的职责分开。
