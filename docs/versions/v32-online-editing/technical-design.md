## 架构

只动 CLI；服务端、API、控制台都不动。

```
skill edit
  parseEditArgs（--old/--old-file、--new/--new-file、--replace-all、@new 的三个参数）
    → loadEditFiles（读内容文件，UTF-8 校验）
    → 空 old 拒绝
    ├─ @new 分支
    │    resolveNewDraftBase → AuthorFile（底稿内容）
    │      → replaceExactly（诊断用 <地址>@<底稿码>）
    │      → renderHunks(before, after)
    │      → CreateDraft（一读一写）→ 回显 hunk + 「这一版现在是 <地址>@<新码>」
    └─ 普通分支
         writeTarget（地址 → 草稿码）
           → AuthorFileList（清单 + ETag）/ AuthorFileBytes（内容 + ETag）
           → replaceExactly（精确匹配 + 诊断）
           → renderHunks(before, after)
           → AuthorWriteFile（If-Match = 读到的 ETag）
           → 回显 hunk + 「这一版现在是 <地址>@<码>」
```

`skill write` 在一期之后多两道闸，都在发请求之前：

```
skill write
  读内容（标准输入，唯一来源）
    → 空内容且没给 --allow-empty → 用法错误，零请求
    → 整份像 read 的渲染（looksLikeReadOutput） → 拒绝，零请求
    ├─ @new  → resolveNewDraftBase → CreateDraft（edit.op = write，内容走 JSON，仍要求 UTF-8）
    └─ 普通  → editRemote（清单 → 读或建 → PUT，If-Match）
```

新增一个纯函数文件 `cmd/skillmaster/editdiff.go`，放这些事，都不碰网络、不读环境：

| 函数 | 职责 |
|---|---|
| `renderHunks(before, after []byte) ([]string, bool)` | 对旧/新内容做行级 diff，按 git 形状输出 hunk；`bool` 表示是否被截断 |
| `diffMiddle(oldLines, newLines []string) []lineOp` | 变更区间的 LCS；区间过大时退化为「全删再全加」 |
| `diagnoseMiss(content []byte, old, address, relpath string) error` | 0 匹配时挑一种诊断 |
| `stripReadLineNumbers(text string) (string, []int, bool)` | 去掉 `N\t` 前缀与 `read` 的页脚；返回行号用于「编号是否连续」 |
| `multipleMatchesError(content []byte, old string, count int) error` | 多处匹配：出现次数 + 去重后的行号 |
| `looksLikeReadOutput(content []byte) bool` | `write` 的行号防线：整份像 `read` 的渲染（每个非空行 `N\t`、编号连续、末行是注记） |

**为什么回显用 diff 而不是重放替换**：第一稿按「每处替换的位置」拼 hunk，三个缺陷都出在这里——`--old` 带结尾换行时切片越界（`--old-file` 的默认形态）；第二处落在上一段上下文里时被画成「未改动」；整行删除被画成少一行。对 before/after 做 diff 不关心改动是怎么来的，这三个失效模式都不存在。

`replaceExactly` 保留在 `files.go`：0 匹配调 `diagnoseMiss`，多处匹配调 `multipleMatchesError`。匹配与写回的行尾规则见 §接口「匹配与写回」。

## 数据模型

没有变化。改动仍落在草稿行上，`If-Match` 仍是读到的 ETag（版本 digest）。

## 接口

### 命令行形态

```
skmr skill edit <命名空间>/<名字>@<版本码|new> <相对路径>
    (--old <文本> | --old-file <文件>)
    [--new <文本> | --new-file <文件>]
    [--replace-all] [--from <版本>] [--name <版本名>] [--note <说明>]
```

规则：

- `--old` 与 `--old-file` **必须且只能给一个**；`--new` 与 `--new-file` 最多给一个，都不给等于替换成空。**「给了」看参数是否出现，不看值是否为空**：`--new ""` 是明确的「替换成空」，与 `--new-file` 同时出现仍是矛盾。
- 文件按原始字节读；**必须是合法 UTF-8**，否则拒绝（与 `@new` 的文本限制同一道理：JSON 传输会静默替换）。
- 空 `--old`（含空文件）拒绝：没有可匹配的文本。
- 行尾符不参与匹配，替换文本按文件本身的风格写回（见下）。

### 匹配与写回

**为什么跟本地 `Edit` 对齐**：本地 `Edit` 的 LF `old_string` 能匹配 CRLF 文件（[实测](../../research/local-edit-mechanics.md)）。agent 在本地与在线两条路上改同一个 skill 时，匹配规则不同就意味着同一段文本一处能改、另一处改不动。

**匹配**：内容与 `--old` 各投影成「行尾符全换成 LF」的视图（`\r\n` → `\n`，单独的 `\r` → `\n`），在投影上计数与定位。命中区间按投影时记下的来源偏移映射回原始字节，**只替换那一段**，其余字节一个不动。大小写、空格与制表符、Unicode 组合形式仍按精确比较——容的只有行尾符这一项。

**写回的行尾**：数原始内容里的 CRLF 行与 LF 行（`\n` 前面不是 `\r` 的那些）。CRLF 多就用 CRLF，否则 LF，平票判 LF——与本地 `Edit` 的判法一致。选定的行尾只作用于替换文本（先归一成 LF 再按它编码），文件其余部分不重编码。

**与本地 `Edit` 的取舍**：本地改完会按主流风格**整份重编码**，匹配之外的行也可能被统一。这里不做，因为①普通文本文件的重编码已经由服务端在写入口完成（ADR 0117），CLI 再做一遍是两份逻辑；②`.bat` / `.cmd` 被 v33 豁免，整份重编码会改掉调用方没要求改的字节。**代价要认**：一份行尾本来就混杂的 `.bat`，本地会顺手统一，这里不会——只替换匹配那一段。

**BOM 不在 CLI 的范围内**：CLI 读到的字节原样参与匹配与拼接，不去 BOM；写入口的去 BOM 由服务端 `TextCanon` 做（ADR 0117）。所以编辑一份带 BOM 的旧文件时，BOM 会随这次写消失——这是 v33 的口径，不是 `edit` 加的规则。

**与 v33 的关系**：服务端写入口把文本归一成 LF（[ADR 0117](../../decisions/0117-content-is-canonicalized-at-the-door.md)），所以对普通文本文件，「按文件风格写回」的效果最终仍是 LF；这条规则真正看得见效果的是 `.bat` / `.cmd`（v33 明确豁免）和 v33 之前存下的旧内容。服务端统一归一、CLI 不重复做整文件重编码——本地 `Edit` 的整文件重编码在这里没有对应物，也不需要：v33 已经把这件事挪到服务端，而且服务端做它时不必区分是谁写的。

### 没有改动可做

两种情况拒绝，只回一句，**不发写请求**：

| 条件 | 说法 |
|---|---|
| `--old` 与 `--new` 相同 | 「`--old` 与 `--new` 相同，没有可改的内容；文件没有改动。」 |
| 替换后与原文逐字节相同（例如新旧文本只差行尾符，按文件风格编码后还原成同一串字节） | 「替换后与原文相同，没有可改的内容；文件没有改动。」 |

退出码 1（内容层面的拒绝，不是调用形态错误）。本地 `Edit` 对第一种回 `No changes to make: old_string and new_string are exactly the same.`；第二种在本地由整文件重编码顺手吃掉，这里没有那一步，所以显式拒绝。
- 地址、版本码、`@new` 的规则都不变。

### 成功输出（全部 stderr，stdout 仍为空）

```
已修改 SKILL.md（ad6939e4）。
@@ -1,5 +1,5 @@
 # demo
 
 alpha
-npm install
+npm ci
 omega
（这一版现在是 me/demo@K3M9QX2P；再读拿到的就是这份内容。）
```

- 上下文 3 行；两处改动之间不超过 **6 行**未改动文本时合并进同一段 hunk（git 的 2×上下文规则）。
- `@@` 的数字含上下文，`-` 侧是旧文件行号，`+` 侧是新文件行号；计数为 1 时省略 `,1`（git 的写法）。
- 总行数上限 **60**；超出时末尾加一行：
  `…（只显示前 N 行；完整改动：skmr version diff <地址>@<码>。）`，N 是实际打印的行数（≤ 60）。
- 改动只落在行尾（末尾换行、CRLF↔LF）时没有行级 hunk，改打一行：
  `（这次只改了行尾：换行符或末尾的换行，内容行没有变。）`
- 截断不会停在孤零零的 `@@` 头上（正文被切掉的头一并去掉）。
- 行尾没有换行符的那一行不补 `\ No newline at end of file`：hunk 是给人看的摘要，完整与权威的对照是 `version diff`。
- `@new` 路径的首行是既有文案「已修改并建出草稿 `<地址>@<码>`。」加一行「下一步：…」，其后同样打 hunk 与末句，码是刚建出来的草稿码。
- **服务端判定没有变化时只回一句，不打 hunk、不打「已修改」**：`没有改动：服务端归一之后与已存的内容相同，这一版没有变。`
  判据是写请求返回的版本 digest 与 `If-Match` 带回的 ETag 相同（ETag 是版本 digest 的引号拼法）。本地改动确实发生过——非 NFC 的写法、只差行尾的写法都会让本地字节不同——但服务端归一之后与已存内容逐字节相同，走的是 no-op 分支；此时画 hunk 就是在报一个没有落库的改动。

### 0 匹配的诊断（按顺序取第一条成立）

| 条件 | 说法 |
|---|---|
| `--old` 的每个非空行都以 `N\t` 开头、**编号连续**，且（去掉后是整行，或本来就是多行） | 「你给的原文带着 `read` 的行号。去掉行号再试；取原文：`skmr skill cat <地址> <路径>`。」 |
| 每行去掉行尾空白、整段去掉首尾空行后，在内容里**恰好一处**（多处时取唯一的整行对齐那处） | 「只差空白：第 a–b 行的实际写法是：…」（列出实际行，最多 6 行） |
| 首行（跳过开头的空行）与文件里某一行的相似度 ≥ 0.6（Levenshtein：`1 − 距离/较长者长度`） | 「没找到。最接近的是第 N 行：`…`。」（候选行超过 120 个字符时截断加 `…`） |
| 都不成立 | 「这一版里没有找到要替换的文本」+「先 `skmr skill cat <地址> <路径>` 看一眼」 |

所有诊断都追加「文件没有改动。」。`@new` 路径里的 `<地址>` 是解析出的底稿（`<地址>@<底稿码>`），不是 `@new`。

**诊断在归一化视图上做**：行尾符的差异在匹配阶段已经容掉，走到这里的只剩真实的文本差异——所以「只差空白」不再把 `\r` 算进空白（这一条以前会盖住行尾符差异，说出「只差空白」而列出来的两行看起来一模一样）。行号与 `\r\n` 文件一致（`\r\n` → `\n` 不改行数）；**只有 CR-only 文件会把行号算多**，它的每个 `\r` 在归一化视图里都是换行——这与本地 `Edit` 一致（它也在归一化后的文本上定位），接受。

**最接近的行的成本上限**：跳过长度差超过较长者 40% 的候选（这类候选的相似度上限也达不到 0.6），其余按 `|旧|×|新|` 计费，**累计 2000 万格**；**单个候选超预算就跳过它、继续扫后面的候选**，不停止扫描——顶部一条超长行不该把下面的近匹配藏住。预算内找到的最近行照常报告。

### 多处匹配

```
要替换的文本出现了 3 次，在第 1、3、5 行。加 --replace-all 全部替换，
或带上更多上下文只改一处。文件没有改动。
```

- **次数**是出现次数（`--replace-all` 会替换几次）；**行**是去重后的位置。一行里出现两次时是「2 次，在第 1 行」。
- 超过 6 行时列前 6 个，后接「等 N 行」，N 是**去重后的总行数**。

### `skill write`

```
skmr skill write <命名空间>/<名字>@<版本码|new> <相对路径> [--overwrite] [--allow-empty]
    [--from <版本>] [--name <版本名>] [--note <说明>]
```

三条规则，都是新加的；**没有第四条「从文件读」**：

1. **行号防线**（A10）：内容「整份像 `read` 的渲染」时拒绝，退出 1、**零请求**。三条同时成立才算：每个非空行都是 `N\t` 开头；编号连续；末行是 `read` 的注记（`readFooters` 的三种之一）。少一条就走原来的路——内容本身带 `3\tfoo` 是合法的，`read` 的渲染也可能被调用方截掉了注记，那种情况按内容照写。
   句子：
   `这份内容像是 skmr skill read 的输出：每行带行号，末尾是它的注记。写进去这些行号会变成正文。取原文：skmr skill cat <地址> <路径>；改一处用 skmr skill edit。文件没有改动。`
   两个入口：标准输入、两条路（普通版本、`@new`）。
2. **空内容要显式**（A13）：内容为空（标准输入读到 0 字节）而没给 `--allow-empty` → 用法错误，退出 2、零请求：
   `要写的内容是空的；真要写空内容就加 --allow-empty。用法见：…`
   给了 `--allow-empty` 就照写空内容——空内容是合法内容（v8 TD），这条只区分「我要写空」与「输入掉了」。

3. **默认只新建，整份替换要 `--overwrite`**（A14）：目标路径已存在而没给开关 → 拒绝，退出 1、**零 PUT**：
   `这个版本已经有 <路径>；改一处用 skmr skill edit <地址> <路径> --old … --new …；整份覆盖加 --overwrite。文件没有改动。`
   `edit` 走的是同一个读改写，但它本来就只改文本里的那一段，`--overwrite` 的意义对它不存在，所以它不受这条限制。
   **`@new` 上给 `--overwrite` 是用法错误（退出 2）**：那条路没有「已有草稿」，底稿里的同名文件被新内容代替是「新建这一版」的一部分。
   为什么：`--content-file` 关掉的是**入口**，这条改的是**默认值**——默认从「覆盖一份文件」变成「放一份新文件」，覆盖要自己说出来。它挡的是「没想就覆盖」，不是「想覆盖也覆盖不了」。

**为什么没有 `--content-file`**：它不新增能力（标准输入一直能承载同样的字节，`< 文件` 等价），却会让「本地写好、整份传上去」变成顺手的一条路。agent 一旦从本地文件出发就不会再用 `edit`，hunk、唯一性、0 匹配诊断全都用不上——那正是本版要消灭的往返。文件内容进入服务端的唯一正当入口是 `@new` 的首次导入（[ADR 0108](../../decisions/0108-importing-local-skills-is-optional.md)）与 `submit` 的整包导入；「改已有的东西」必须基于服务端的内容。

不要把这条与 `edit` 的 `--old-file` / `--new-file` 混为一谈：那两个是**改动的传输**——`--old` 仍必须与服务端内容匹配，命令仍会回显 hunk；它们传的是一处改动，不是一份文件。

### 退出码

不新增类别：

- 缺参数、两个来源同时给、空 `--old`（含空文件）、`@new` 缺 `--name`、**空写内容且没给 `--allow-empty`**、**`@new` 上给 `--overwrite`** → **2**（用法错误，stdout 空，stderr ≤ 200 字节、结尾「用法见：…」，v16 T10）。
- 文件读不到、不是 UTF-8、匹配失败、没有改动可做、**内容像 `read` 的渲染**、**已有文件却没给 `--overwrite`**、写冲突 → **1**。
- 成功 → 0。

用法错误里不嵌文件路径：200 字节的预算要留给下一步，而不是一个调用方已经知道的路径。

## 分期

| 期 | 交付 | 验收 | 这一期明确不做 |
|---|---|---|---|
| 一期 | `--old-file` / `--new-file`、hunk 回显、三种 0 匹配诊断、多处匹配、帮助、行尾不参与匹配与无改动拒绝 | A1–A8、A13 | 不改 `read` / `write` / `cat` 的既有行为；不给 `write` 加防线或回显 |
| 二期 | `read --raw`、`write` 拒绝行号渲染、默认只新建（`--overwrite`）、空内容要显式、`write` 写进已存在版本的测试补齐 | A9–A10、A13–A14 | 不给 `write` 做 hunk 回显（整文件覆盖没有「改了一处」可画）；不改 `read` / `cat` 的默认渲染 |
| 三期 | `@new` 打印下一条完整命令（不改本机钉） | A11 | 不移动本机钉；不把 `submit` 变成草稿更新器 |

一期的错误文案指向已有的 `skill cat`；二期起统一指向 `read --raw`。

## 开放问题

1. **hunk 上限 60 行够不够？** 已定为 60。复评条件：出现一次「hunk 被截断、看不出改了什么」的实际报告，或一次 `version diff` 被用来补看本可由回显给出的改动。
2. **`read --raw` 与 `cat` 长期是否应合并？** 当前倾向不合并：`cat` 接多个路径、`read --raw` 只接一个并与 `read` 共用版本解析。复评条件：二期实现后，帮助页需要超过两句话才能讲清两者的分工。
3. **`--new-file` 的末尾换行要不要提示？** 当前倾向原样使用、不提示——调用方给什么就是什么。复评条件：出现一次因多/少末尾换行而写坏内容的实际实例（行尾只有换行差异时，回显会给「只改了行尾」的说明，不在此列）。
