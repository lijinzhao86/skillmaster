## 用例

### T1 · 同一内容、不同说明，仍是同一个版本

- **前置**：账号已注册；`alice/pdf-tools` 不存在；准备一份 zip。
- **步骤**：第一次提交带 `note="第一句"`；第二次提交同一份 zip、带 `note="第二句"`。
- **期望**：第一次 201、第二次 200；两次响应里的 `digest` 相同、`draft_id` 也相同；`skill_version` 行数仍为 1；作者面用 `draft:<id>` 读到的是同一份内容（草稿在消费面不可读，这是有意的）；库里那一行的 `changelog` 仍是「第一句」（幂等提交不覆盖）；这一行的 `skill_version.version` 是 NULL（草稿还没有版本号）。
- **判定**：通过／失败（失败时记录实际观察到的现象）

### T2 · 服务端提交带说明

- **前置**：同 T1；持有 `skills:write` 凭据。
- **步骤**：multipart 提交 `file` + `name="split 范围语法"` + `note="把 split 的范围语法写成文档"`。
- **期望**：201；响应 `draft_name` 与提交的名称部分一致（顶层的 `name` 是 skill 名字）、`note` 与提交一致；`skill_version.draft_name` 与 `changelog` 走进同一组值；响应里的 `version.name`（版本号）为 `null`，`version` 这个对象仍在；库里 `skill_version.version` 也是 NULL；提交响应格式其余字段不变。
- **判定**：通过／失败

### T3 · 不带说明仍能提交

- **前置**：同 T1。
- **步骤**：只提交 `file`，不带 `note`。
- **期望**：201；响应 `note` 为 `null`；库里 `changelog = ''`；消费面读版本时不报错。
- **判定**：通过／失败

### T4 · CLI `skill submit --note`

- **前置**：`skillmaster login` 完成；本地目录有 `SKILL.md`；服务端可达。
- **步骤**：`skillmaster skill submit --name "references 路径" --note "修正 references 的路径"`。
- **期望**：请求的 multipart 里确实带 `name` 与 `note` 部分（用测试服务端断言）；终端打印提交结果；服务端那一行 `draft_name` 与 `changelog` 是这两个值。
- **判定**：通过／失败

### T5 · CLI 不带 `--note` 仍成功

- **前置**：同 T4。
- **步骤**：`skillmaster skill submit --name "references 路径"`（非交互、无 TTY）。
- **期望**：提交成功；不因为缺少说明而阻塞或追问；服务端那一行为空说明、名字是给的那个。
- **判定**：通过／失败

### T6 · 作者面版本表读说明，不读 title

- **前置**：提交一版，frontmatter 的 `title` 是「PDF 工具」，`note` 是「重写搜索提示」；另提交一版草稿，两值同样不同。
- **步骤**：以 `write` 档打开 `GET /web/skills/{ns}/{name}`；再看网页「版本」栏。
- **期望**：两行的 `note` 分别是各自的说明；版本表下方的说明显示「重写搜索提示」而不是「PDF 工具」；`title` 仍留在响应里但不再占那一列。
- **判定**：通过／失败

### T7 · 发布：分配版本号，说明随草稿冻结

- **前置**：有一个带 `note="agent 写的初稿"` 的草稿；调用者有 `maintain`。
- **步骤**：`POST /web/skills/{ns}/{name}/publish`，body `{version, release_name:"1.3.0"}`。
- **期望**：返回 200；`skill_version.version` 变成 `1.3.0`，`first_published_at` 写上；作者面与消费面读到的都是「agent 写的初稿」——**发布没有改说明**；`@1.3.0` 可解析；指针前移与版本号写入在同一事务里（回滚测试：让指针写入失败，版本号与 `first_published_at` 都不应留下改动）。
- **判定**：通过／失败

### T8 · 上线后没有写说明的路

- **前置**：T7 之后，该版本已是 `published`。
- **步骤**：再次发布同一版本并带 `note="想再改"`；再带 `release_name="1.4.0"` 发布一次；调草稿改名与改说明接口各一次；再尝试提交同内容、丢弃。
- **期望**：再次发布带 note → 400 `invalid_request`（发布不接收说明）；带 `release_name` → 400 `version_name_is_assigned`；草稿改名接口 → 400 `draft_name_is_frozen`、改说明接口 → 400 `note_is_frozen`；提交同内容返回 200 且名字与说明都不变；丢弃返回 4xx（已上线版本不可丢弃）；库里名称、说明与版本号都不变。
- **判定**：通过／失败

### T9 · 调用者在版本列表里读到说明

- **前置**：发布两版，说明分别是「第一版」与「第二版」；另有一版草稿带说明「别泄露」；调用者持 `invoke` 档凭据。
- **步骤**：`GET /api/v1/skills/{ns}/{name}/versions`。
- **期望**：两行各自带自己的 `note`；草稿行不出现；消费面响应里没有 `draft_name`；`name` / `digest` / `published_at` / `is_current` 不变；没有说明的版本 `note` 为 `null`。
- **判定**：通过／失败

### T10 · 草稿的名字与说明都不泄露

- **前置**：同 T9；名称是「别泄露的名字」，说明是「别泄露」。
- **步骤**：用 `invoke` 档凭据读版本列表、详情、`/metadata`、正文与文件；在响应里搜「别泄露」。
- **期望**：任何消费面响应都不含名称或说明；草稿行不出现；详情里的 `versions` 仍只含已上线版本。
- **判定**：通过／失败

### T11 · 规范的三条定义（界面不标「试用」）

- **前置**：P3 已在 `architecture/model.md` 增加「版本号对调用者的含义」与「生命周期的两条承诺」两节；网页与 CLI 可打开。
- **步骤**：读规范，逐条对照 MAJOR / MINOR / PATCH 的「什么算、什么不算」；建一个 `0.3.0` 的已上线版本与一个 `1.2.3` 的已上线版本；看作者面与 CLI 的版本列表；打开一个草稿的单版页「操作」栏，看发布区块。
- **期望**：三条定义可判定；`0.3.0` 与 `1.2.3` 在作者面与 CLI 的版本列表里只差版本号本身，都不带额外的稳定性章（[prd](../v6-version-management/prd.md) §不做 #15）；两处界面引用的是同一套定义（文案一致，不各写一套）；发布区块第一句点名当前线上版本，三个选项是「只是修正 / 新增能力 / 旧调用会失效」，后面各跟从当前线上算出的建议号（`1.2.4 / 1.3.0 / 2.0.0`），版本号输入框预填建议号且可改；没有线上版本时建议号从 `1.0.0` 起步。
- **判定**：通过／失败

### T12 · 服务端不猜版本号

- **前置**：已有 `1.2.3` 上线；准备三份改动：明显不兼容、新增能力、只改错字。
- **步骤**：① 发布一个草稿，`release_name="1.0"`；② 发布一个草稿，`release_name="1.2.3"`，而 `1.2.3` 已被另一份内容占用；③ 把明显不兼容的改动发布成 `1.2.4`。
- **期望**：① 400 `invalid_release_name`；② 400 `version_already_exists`；③ **成功**——服务端不判断改动性质；响应里没有任何由 diff 推断出来的字段。
- **判定**：通过／失败

### T13 · 旧客户端不受影响

- **前置**：用 v6 之前的 CLI 二进制与旧版网页构建。
- **步骤**：旧 CLI 读版本列表；旧网页读作者详情；旧 CLI 提交（不带名字）。
- **期望**：读请求与解析都成功，新字段被忽略；旧 CLI 提交 → 400 `draft_name_required`，错误消息说清缺的是版本名称；无字段缺失导致的异常。
- **判定**：通过／失败

### T14 · 说明不进搜索

- **前置**：建一个 skill，`title` / `description` / 正文都不含「翡翠」，只在某一版说明里写「翡翠」并发布。
- **步骤**：按「翡翠」搜索；再把「翡翠」放进 `description` 提交一版并发布，再搜。
- **期望**：第一次搜不到（0 条）；第二次搜得到（至少 1 条）。两次用同一个调用者与同一组筛选。
- **判定**：通过／失败

### T15 · 说明的长度与字符校验

- **前置**：同 T1。
- **步骤**：提交 200 个码点的说明；提交 201 个码点的说明；提交含 `\u0000` 的说明；提交含换行的说明。
- **期望**：200 接受；201 返回 400 `note_too_long`；控制字符返回 400；换行折成一个空格后接受，存下来的是一行。**任何情况下都不静默截断**。
- **判定**：通过／失败

### T16 · 幂等提交不覆盖已写下的名字与说明

- **前置**：T1 之后。
- **步骤**：第二次提交同一内容、不同名字与说明；再发布这一版（`release_name="1.2.4"`，不带 note）。
- **期望**：第二次提交返回 200，名字与说明都仍是第一次的值；发布后公开说明仍是第一次那句，版本名称也不变。
- **判定**：通过／失败

### T17 · 回滚时带说明被拒

- **前置**：两个已上线版本 A、B；当前线上是 B。
- **步骤**：`POST …/publish` 目标 A，body 带 `note="改一句"`。
- **期望**：400 `invalid_request`（发布不接收说明）；A 的说明不变；指针不动（失败不产生半次回滚）。
- **判定**：通过／失败

### T18 · 长度的两端

- **前置**：同 T1。
- **步骤**：分别提交 1 个码点、200 个码点、201 个码点的说明；再分别提交 1 个码点、40 个码点、41 个码点的版本名称，并额外用中文、英文、数字、符号混合的 40 码点名称，以及 40 个 emoji 的名称各提交一次。
- **期望**：说明 1 与 200 接受、201 返回 400 `note_too_long`；名称 1 与 40 接受、41 返回 400 `draft_name_too_long`；中文、英文、数字、符号混合的 40 码点名称接受，40 个 emoji 也按 40 个码点接受（不按 UTF-16 单元数算成 80）；错误消息说清上限，不只是一句「参数错误」。
- **判定**：通过／失败

### T19 · 人在前端改版本名称与说明

- **前置**：两个草稿——A 由 `write` 用户 alice 提交，B 由 bob 提交；另有一个已上线版本 C。
- **步骤**：alice 从版本表点进 A 的单版页，改名再改说明；alice 再直接调用 B 的改名接口（B 的单版页上没有入口——看得见不等于改得动）；`maintain` 用户点进 B 的单版页改名与改说明；`browse` 用户打开版本表；任何人改 C。
- **期望**：改名与改说明的入口都在草稿的单版页上，版本表行内没有编辑入口；alice 改 A 成功；alice 改 B 返回 **403**（看得见 B，是这一档不够）；`maintain` 改 B 成功；`browse` 看不到草稿行、也没有入口；改 C 的名字 → 400 `draft_name_is_frozen`、改说明 → 400 `note_is_frozen`（界面上没有入口）。作者面读到的始终是最后一次写入的值。
- **判定**：通过／失败

### T20 · 历史版本只有一种，没有弃用信号

- **前置**：发布 A、B 两版，B 是当前版本；调用者有 `maintain`。
- **步骤**：打开 A 的单版页与版本列表；调用 `…/versions/{A}/deprecate`；按 `@A` 与 A 的 `@sha256:` 各读一次；检查响应头与消费面版本列表。
- **期望**：A 的状态章是「历史版本」，不是「已弃用」；A 的单版页没有弃用 / 取消弃用入口，弃用路由 **404**（本版没有这条能力）；两次钉读都 200，响应头**没有** `Deprecation`；消费面版本列表里 A 仍在，`state=published`、`status=history`；A 的 `published_at` 是它首次上线的时间。
- **判定**：通过／失败

### T21 · 下架只影响消费面

- **前置**：A 与 C 都是历史版本（已发布、非当前）；`maintain` 可用。
- **步骤**：以 `maintain` 在 A 的单版页下架并写原因；再对 C 下架、**不写原因**；用 `invoke` 档凭据按两种钉读 A、读版本列表；用 `maintain` 与 `browse` 档各读一次作者面。
- **期望**：消费面读 A → **410 `version_revoked`**；消费面版本列表不再出现 A；`maintain` 的作者面看得到 A 这一行，写了原因也看得到；`browse` 的作者面看不到这一行；**C 不写原因也能下架成功**，作者面那一行没有「原因：」；下架收到的原因不在消费面任何响应里出现；状态章写「已下架」。
- **判定**：通过／失败

### T22 · 当前版本不能直接下架，指针不会被下架清空

- **前置**：B 是当前线上版本；另有 A 是历史版本；`maintain` 可用。
- **步骤**：以 `maintain` 直接下架 B；把指针回滚到 A；再以 `maintain` 下架 B（此时是历史版本）；读 `skill.current_version_id`、裸地址；重新上架 B；再读裸地址。
- **期望**：直接下架 B → 400 `invalid_version_state`；回滚到 A 后 B 成为历史版本；再下架 B 成功；`current_version_id` 仍指向 A；裸地址继续读到 A；重新上架 B 后它回到历史版本，**不会**自动上线。
- **判定**：通过／失败

### T23 · 生命周期动作的权限

- **前置**：一个当前版本与一个历史版本；五档凭据与所有者各一份。
- **步骤**：`maintain` 在历史版本的单版页下架它，再重新上架；`admin` 对另一个历史版本做同样的事；`write` / `browse` / `invoke` 打开版本表并试着下架；`maintain` / `admin` 试着下线整个 skill；所有者下线再恢复。
- **期望**：`maintain` 与 `admin` 都能下架 / 重新上架历史版本；`write` / `browse` / `invoke` 看不到生命周期入口，直接调接口 → 403；`maintain` / `admin` 下线 skill → 403；只有所有者能下线/恢复服务；直接下架当前版本 → 400 `invalid_version_state`；每次失败都不改变状态。
- **判定**：通过／失败

### T24 · 版本号不复用

- **前置**：`1.2.3` 已上线并被下架。
- **步骤**：用同号 `1.2.3`、不同内容提交一个草稿（提交本身应当成功）；发布时给它 `release_name="1.2.3"`；再重新上架原来那一版；读库里的行与号。
- **期望**：提交成功但 `skill_version.version` 为 NULL（响应里 `version.name` 也是 `null`、`version` 对象仍在）；发布时 400 `version_already_exists`；重新上架后仍是原来那一行、同一个号；没有新行插入。
- **判定**：通过／失败

### T25 · 两个动作都进审计

- **前置**：一个已上线版本；另有第二个历史版本。
- **步骤**：依次下架（带原因）、重新上架；再对第二个历史版本下架（不带原因）。
- **期望**：审计表按目标版本查得到两条，各自含操作者、动作、目标、时间；带原因那条的 detail 有原因；**不带原因那条也成功、也写审计，detail 里没有原因**；没有重复写入。
- **判定**：通过／失败

### T26 · 历史调用的整体承诺

- **前置**：一个 skill 有两版：当前已发布版、已下架的历史版。
- **步骤**：按两种版本各自的 `@版本` 与 `@sha256:` 读；把整个 skill 删除；再读；恢复 skill；再读。

### T36 · CLI 读作者面：版本列表、单版与改动

- **前置**：一个 skill 有线上 `1.2.3`、历史版本 `1.2.2` 与 `1.2.0`、已下架 `1.2.1`、草稿 A（我提交的）、草稿 B（别人提交的）、已丢弃 D（我提交的）。本机一把 `maintain` 档、带 `skills:write` 的 CLI 登录态；另有 `write`、`browse`、`invoke` 三个身份各一份，以及一把只读 API key。`maintain` 看得见 7 行（线上 1 / 历史 2 / 已下架 1 / 草稿 2 / 已丢弃 1），`write` 看不见已下架与已丢弃，共 5 行。
- **步骤**：① 以 `maintain` 跑 `skillmaster version list <ns>/<name>`；② `--status draft`、`--status revoked`、`--status discarded`；③ `--query <名称里的两个字>`；④ `--json --limit 2`，用 `next` 翻到第二页；⑤ 以 `maintain` 依次 `version show` 线上、草稿 A、已下架 `1.2.1`、已丢弃 D；以 `write` 再看已下架那一版与已丢弃 D（两个都应是 404）；以 `invoke` 跑 `version list` 与 `version show`；⑥ 以 `write` 跑 `version diff <name>@draft:A`（不带 `--from`）、`--from 1.2.2`、`--patch --file SKILL.md`（测试服务器记下这一次请求的查询串）；以 `browse` 对比 `1.2.0` 与 `1.2.2` 两个已发布版本；⑦ `skill files <name>@draft:A` 与 `skill read <name>@draft:A SKILL.md`；以 `maintain` 跑 `skill files <name>@1.2.1`，以 `write` 再跑一次；⑧ `skill invoke <name>@draft:A`；⑨ 用只读 key 重跑 ① 与 ⑥（`browse` 能看的那一对）；⑩ 以 `invoke` 跑 `skill versions`。
- **期望**：① 按服务端的作者面顺序列出 7 行（线上 / 历史 2 / 已下架 / 草稿 2 / 已丢弃），每行地址可原样复制，第二行起是状态 · 名称 · 时间与说明；② `--status draft` 2 行、`--status revoked` 1 行、`--status discarded` 1 行；换 `write` 身份后 `--status discarded` 0 行；③ 行按名称或说明收窄，`counts` 不随过滤变（仍是 7 的分布）；④ JSON 是一个对象：版本字段与 TD §作者 API 与 CLI 的版本命令 逐字一致（`address` / `pin` / `name` / `version` / `status` / `note` / `submitted_by` / `submitted_at` / `first_published_at` / `state_at` / `revoked_reason` / `digest` / `files` / `bytes`），列表带 `skill` / `counts` / `next`；`--limit 2` 第一页 2 行、`next` 非空，第二页 2 行且与第一页不重复，直到 `next` 为 `null`；⑤ `show` 给出名称、说明、提交人、首次上线、文件数与摘要；草稿的 `version` 是 `null`、`pin` 是 `draft:<id>`；已下架版带原因，且只有 `maintain`+ 看得到——`write` 身份是 404；已丢弃与已下架同档：`maintain` 看得到、状态是「已丢弃」且没有可做的动作，`write` 身份是 404；`invoke` 身份 `version list` 与 `version show` → 403（消息说需要「浏览」及以上），`skill versions` 仍正常；⑥ 默认基线是上一版（草稿退回当前线上），`--from` 换了基线，`--patch` 给出统一 diff 且只含指定的文件，**这一次请求带 `file=SKILL.md`、不跟 `next` 翻整批**，`--max-lines` 截断时说明还有多少行；`--json` 的改动对象是 `{from,to,added,removed,files[],truncated,next,patch}`，`files[]` 的 `path` 由服务端的 `relpath` 映射、带 `added`/`removed`；`browse` 能对比两个已发布版本（本版把改动门槛降到 `browse`）；⑦ 草稿的文件清单与正文读得到；已下架版的文件对 `maintain` 读得到、对 `write` 是 404；⑧ `invoke` 拒绝 `draft:<id>`，消息指向 `version show` / `version diff`；⑨ 只读 key 读得动 ① 与 ⑥（读草稿要这个人在这个 skill 上够 `write`，但 key 本身不需要写 scope）；⑩ `skill versions` 仍只列可 invoke 的版本（不含草稿、已下架、已丢弃）。
- **判定**：通过／失败

### T37 · CLI 写草稿，以及页面专属动作的拒绝

- **前置**：同 T36 的夹具；写入身份、另一个 `write` 用户（草稿 B 的提交人）、`maintain` 身份各一份；同意屏（`/cli-sign-in`）可打开。
- **步骤**：① `version rename <name>@draft:A --name "compress 用法补全"`；② `version note <name>@draft:A --note "补了按页与按分隔符"`；③ `version discard <name>@draft:A`（不带 `--yes`）；④ 同一条加 `--yes`，再跑一次；⑤ 以 `write` 身份改草稿 B 的名称；以 `maintain` 身份改线上 `1.2.3` 的名称；⑥ 以 `maintain` 身份改已下架 `1.2.1` 的说明；以 `write` 身份再试一次已下架那一版；⑦ 依次跑 `version publish|rollback|revoke|restore|offline|online|delete`；⑧ 直接请求 `POST /api/v1/author/skills/<ns>/<name>/versions/1.2.3/publish`；⑨ 打开同意屏看 `skills:write` 那一行；⑩ `version open <name>@draft:A --print` 与 `--json`；⑪ `version rename <name> --name "x"`（不带钉）；⑫ 用 `--json` 跑一次被拒绝的 `version rename`，看错误对象。
- **期望**：① 成功，`version show` 读回新名称；`--json` 的写响应是 `{ok:true,version:{…}}`，`version` 是改后的那一版；② 成功，说明完整替换（不是追加），200 码点边界报 `note_too_long`；③ **什么都没发生**（再 `show` 仍是草稿、说明未变），退出码非零，打印「这一版无法找回」与加上 `--yes` 的完整命令；④ 草稿变成已丢弃，再跑一次退出码 0 并说「已经是丢弃状态」；⑤ 改别人的草稿 → 403 `insufficient_permission`（说清需要提交人或「维护」及以上）；`maintain` 改已上线版本 → `draft_name_is_frozen`；⑥ `maintain` 改已下架版本 → `note_is_frozen`；`write` 改已下架版本 → 404（看不见，不泄露状态）；⑦ 都不执行：退出码非零，消息说明这个动作由人在网页上确认，并包含 `skillmaster version open <address>`；版本状态与线上指针都没变；⑧ 404（作者 API 没有这条路由，`offline|online|delete` 同理）；⑨ 那一行逐字是「以你的身份提交新版本、管理草稿与共享」，清单里不出现「发布」「删除」；⑩ `--print` 打印 `/skills/<ns>/<name>?tab=versions&version=<pin>`（与单版页同一条路由；`draft:<id>` 也要能解析），`--json` 给 `url` 与 `opened`；⑪ 不带钉是用法错误、什么都没改；⑫ 错误对象是 `{"ok":false,"error":{"code":"insufficient_permission","message":"…","hint":"…","server_code":"forbidden"}}`，退出码非零，stdout 没有半截 JSON。
- **判定**：通过／失败

### T38 · 服务启动时发布 gateway（回归守卫，不映射 PRD 验收）

- **前置**：空库；`gateway/skillmaster/` 的源没有 `version:`；服务能启动。另备一个**升级态**：`skill_version` 里已有一行 `state='published'`、`version IS NULL` 的 gateway 版本（模拟 v6 之前的库）。**造法：先按正常流程跑一次，再把那一行的 `version` 置 NULL**——它的 digest 必须等于当前源的 digest；换一份内容造这个夹具，提交会插入一行新草稿，升级态那条分支就永远走不到。
- **步骤**：启动服务；读 gateway 的版本列表；用同一份源重启一次；再读。
- **期望**：空库启动完成且 gateway 被发布（指针非空）；那一行的 `draft_name` 是系统给的名字（`gateway`），`version` 是**短的** `0.0.<提交序号>`（提交序号即 `SubmittedSkill.number`，不设上限，形状永远是两段点分数字）；第二次启动幂等——不新增行、不报 `draft_name_required` / `release_name_required`，指针与版本号不变。**升级态**启动也成功：已发布且 `version IS NULL` 的旧网关行不要求 `release_name`、保持无名（按 digest 寻址），指针与状态不变。

## 架构与复用检查

### A1 · 模块边界（编译期 / 测试强制）

- **步骤**：`./mvnw -o test -Dtest=ArchitectureTest,TableOwnershipTest`（surefire；`-Dit.test` 只选 `*IT`，这两个都不会跑）。

### A2 · 作者 API 是另一个平面，不是网页的别名

- **前置**：一个 skill 有草稿 D 与已上线版本；一把 `maintain` 档、带 `skills:read` + `skills:write` 的 Bearer 凭据；一把 `invoke` 档凭据；无会话 cookie。
- **步骤**：用 Bearer 调作者 API 的列表 / 单版 / 改动 / 改名 / 改说明 / 丢弃 / 文件；再调 `publish`、`revoke`、`restore`、`rollback`、`offline`、`online`、`delete`；用 `invoke` 凭据调列表与单版；不带凭据调一次。
- **期望**：前者按 §作者 API 的路由表工作，响应是 snake_case 且**不含 `/web` 资源地址**；页面专属动作一律 404（不是 403、不是 405）；`invoke` → 403；无凭据 → 401；GET 缺 `skills:read` → 403 `insufficient_scope`，写缺 `skills:write` → 403。

### A3 · 前端复用只有一处实现

- **前置**：`skillmaster-web` 组件测试与类型检查可用。
- **步骤**：搜索版本选择器的三处调用（文件栏、对比基线、回滚目标）；搜索 diff 行渲染的调用点；搜索 `version=` 的解析；搜索网页对 `/api/v1/author` 的引用；跑组件测试。
