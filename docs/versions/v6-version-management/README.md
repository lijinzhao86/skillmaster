## 目标

让版本从提交到退役有一条说得清的路：**草稿有一个必填的名字（作者面标签）和稳定的 `draft:<id>` 地址，正式版本号在发布时才分配；发布时用规范确认它，调用者读得到这一版改了什么；旧版本保持可读；安全事件里可以「下架」某一版，消费面读不到它，作者面仍可见并可重新上架；当前版本不能被直接下架，先回滚成历史版本再下架；版本级只有下架会让钉住的调用失败（410；skill 级下线是 503、skill 删除后是 404，另算）**。

细节见 [`prd.md`](prd.md) §用户与场景。

## 验收标准

一句话：**版本名称与版本号分得开，两版之间作者说得出改了什么，调用者看得出该不该升级；旧版本退役时，调用者分得清「仍可读」与「读到 410」。**

完整验收与判定方式见 [`prd.md`](prd.md) §验收与指标（映射见 [`test-plan.md`](test-plan.md) §验收映射）。

**最要紧的三条成立条件**：

- **说明不参与身份**——它不进 digest、不进地址；否则改一句话就等于换一份内容，与「自由描述」自相矛盾。
- **版本号的含义是公布的、不是服务端猜的**——服务端只校验形状；按 diff 自动判定 MAJOR 会误判，也会把「作者的声明」降级成「工具的猜测」（[ADR 0033](../../decisions/0033-version-names-are-semver.md)）。
- **所有已发布的版本永久可读，版本级下架是唯一的例外**（skill 级下线是 503、删除后是 404，另算）——下架只作用于消费面，`maintain` 及以上可发起、可选写一句原因、留审计；作者面仍看得到并可重新上架；当前版本不能直接下架。这条守的是内容寻址的根承诺。

## 这一版明确不做什么

摘要最要紧的几条；**完整范围与每条的理由见 [`prd.md`](prd.md) §范围**。

- 不做**分支 / 并行开发线 / 合并** —— 产品是单线，没有合并与冲突的语义；引入 branch 会让人期待一个不存在的模型（[`architecture/model.md`](../../architecture/model.md) §与 git 的对照）
- 不做**可变工作区** —— 工作区在本地；产品接收提交后的草稿（草稿可编辑，本版只开放名字与说明），发布后的版本才是不可变快照（[ADR 0031](../../decisions/0031-submitting-and-publishing-are-two-actions.md)）
- 不做**换版本号** —— 版本号分配一次，回滚/重复上线都不改；要换号只能发一个新版本（地址稳定性的前提）
- 不做**上线后修改说明** —— 公开说明随版本冻结
- 不做**完整 changelog / 多条变更记录 / 富文本** —— 本版只做一句说明
- 不做**版本删除** —— 下架是状态，行与字节都留着；物理删除会让审计与恢复失去证据
- 不做**测试面 / 计划版本对象** —— 测试在本地 + 作者面；未提交的「开发中 2.0」是另一套对象
- 不做**提交时分配正式版本号** —— 正式版本号在发布时分配；`SKILL.md` 的 `version:` 从本版起不再作准（原样透传，不参与地址）；提交时必须给的是**版本名称**

## 与目标态的关系

[`target/`](../../target/README.md) 描述的是**完整形态**。

- **保留的部分**：单线版本模型、发布后的内容寻址、提交与上线分成两个动作——v1 起的托管模型不变；草稿的稳定地址与可编辑性是这一版的扩展。
- **已经分叉的部分**：目标态的版本管理可能包含多人并行与分支；本版明确不引入，单线从 v1 起就是有意的形状。
- **本版走近的半步**：版本号从「作者随手写的字符串」变成「有公开含义的声明」——但含义靠社会约定与界面引导，不靠服务端强制。
- **本版新增的一处**：版本的可用性第一次有了两档——**可读**（线上 / 历史版本）与**不可读**（下架，消费面 410）；另有**回滚**与 **skill 级下线**。目标态里的生命周期因此从「只有上线」补齐到「上线 / 下架 / 重新上架 / 回滚 / 下线」；五状态的分析口径用派生的 `status`，不落库。测试面与计划版本对象仍不做。

**本版的新 ADR**（编号在决策落定后分配；已经有正文的，下面直接给链接）：

1. **版本说明是发布元数据，不参与内容身份**——落在哪个字段、上线后为什么冻结。
2. **skill 的版本号含义按「调用契约」定义**——MAJOR / MINOR / PATCH 对 skill 各指什么；`docs/architecture/model.md` 是这条约定的常驻权威。
3. **版本只有可读与不可读两档，另有 skill 级下线**（见 [ADR 0058](../../decisions/0058-a-version-is-readable-or-not.md)）——所有已发布、非当前的版本都是历史版本；下架只作用于消费面，作者面仍可见并可重新上架；skill 级下线停整个服务，不改版本状态；已发布版本默认永久可读，版本级下架是唯一的例外（skill 级下线是 503、删除后是 404，另算）。
4. **版本号在发布时分配，修订 [ADR 0033](../../decisions/0033-version-names-are-semver.md)**——草稿不写 `version`，`SKILL.md` 的 `version:` 不再作准；丢弃不烧号。
5. **所有改变版本状态的动作发生在一个版本自己的页面上**——见 [ADR 0054](../../decisions/0054-lifecycle-actions-happen-on-a-version-page.md)；**本版修订它的第 4 条**：草稿的改名、改说明与丢弃也移进单版页，版本表只保留导航（行内不画只读动作；只读入口在「更多操作」菜单里）。
6. **草稿有一个必填的名字，与说明、版本号分开**——见 [ADR 0055](../../decisions/0055-drafts-have-a-required-name.md)；名字是作者面标签，不进地址与 digest，发布后与版本号分开展示。
7. **草稿可编辑、发布后不可变，草稿用稳定身份 `draft:<id>`**——内容编辑本版预留，身份不再随摘要变。
8. **回滚是当前版本页的入口，底层仍是上线**——不改版本号、不新建版本。
9. **当前版本不能直接下架，必须先回滚成历史版本**——指针只由上线 / 回滚移动，不会被下架清空。
10. **下架的原因选填**——见 [ADR 0059](../../decisions/0059-delist-reason-is-optional.md)；写了才存、才显示。
11. **丢弃草稿不是危险动作**——见 [ADR 0060](../../decisions/0060-discarding-a-draft-is-not-dangerous.md)；它不进危险区，但仍要弹窗确认（不可找回）。
12. **凭据能对版本做什么，看「调用者会不会读到不一样的东西」**——读作者面与草稿的改名 / 改说明 / 丢弃可以由凭据做；上线 / 回滚 / 下架 / 重新上架 / 下线 / 恢复服务 / 删除只有浏览器面、API 平面没有路由。见 [ADR 0061](../../decisions/0061-what-a-credential-may-do-to-versions.md)，以及 TD §作者 API 与 CLI 的版本命令。

## 影响最大的两个点

完整列表见 [`technical-design.md`](technical-design.md) §开放问题。最要紧的：

1. **`SKILL.md` 的 `version:` 不再作准，怎么让人不误会？** 当前倾向：CLI 在提交时提示一句、版本 tab 的单版页**不预填**文件里的号、ADR 写明它只是内容的一部分；验证是一条带 `version:` 的 skill 从提交走到发布。

2. **下架一个版本，消费面回 410 还是 404？** **已定：410 `version_revoked`**——它曾经可读，调用者也持有钉；410 说的是「有过、被下架了」，404 会把它混成「地址打错了」。这与「解析不出就一律 404」的规则是一次有意的例外，已在 TD 与验收里写清。
