### 2. 服务端：端点层此前没钉住的入参

- **`WebLoginIT` 三条新增**
  - **手机号形状非法 → 400 字段错**（`invalid_format` / 缺失 → `required`）。这与三种「分不清的凭据失败」有意不同：号码的形状不是秘密，它就写在请求里，而「检查你填的号码」与「凭据不对」是两句不同的话。
  - **空密码与完全缺失的密码 → 401 `invalid_credentials`、`details` 为空、两者逐字节相同**。登录从不校验密码的形状——它要描述的那个密码可能属于别人。这一条同时钉住「**别用 500 回答它**」：实测 Spring 的 `BCryptPasswordEncoder.matches(null, …)` 返回 false 而不是抛异常，所以服务端不需要改（换 Spring 版本改了这个行为的话，这条会红，而不是线上出现 500）。
  - **一次成功登录会清掉此前累计的失败次数**（`LoginUseCase` 的 `clearLoginFailures`）。少了它，连续失手的人会被推向一次他什么都没做错的锁定。
- **`WebRegistrationIT` 一条新增**：发码端点遇到形状非法的手机号 → 400 字段错，且**一条短信都没发**（断言的是 Sender，不是状态码——一个「先发了再拒绝」的实现在外面看是同一个 400）。
- **`WebPasswordResetIT` 补一条断言**：`no_account` 这个 **issue 码**本身。此前只断言了 `field`，而它是前端文案表里唯一一句「这个手机号还没有注册」的依据。

`field()` / `issue()` 两个取值助手从 `WebRegistrationIT` 的私有方法提到 `AbstractAccountIT`——现在三个子类都要用。

### 3. 前端：找回密码页此前没有测试文件

`tests/reset-flow.test.ts`（7 条）：开页即取图；发码请求的字段名；**提交体是 `{phone, code, password}` 且没有 `username`**（与注册唯一的形状差别）；204 之后**显示「密码已重置」并且不跳转**（有意不自动登录）；`no_account` 落在手机号字段；`verification_code_invalid` 落在验证码字段；25 个汉字的密码当场拦下。

另有 `tests/countdown.test.ts`（5 条，**假时钟**）与两处补全：`validation.test.ts` 加了 73 字节、`123`、`a--b`、29 字符加尾连字符（后三个是照服务端 `UsernamePolicyTest` 的用例抄过来的，让两侧钉在**相同的答案**上而不是相同的心意上）；`errors.test.ts` 加了两条**词汇表**测试——服务端能发出的每个 issue 码与每个封套码都必须有中文文案，而 API 面专属的四个码**必须回落**（写清楚这是决定而不是遗漏）。

### 4. 一个真缺陷：同一个模式，第二处

`ResetPage` 的手机号字段只渲染第一步（发码）的错误，于是 `POST /web/reset` 的 `no_account` 被静默丢掉——而它是这个流程独有的那条拒绝。用户填完验证码与新密码、点下「重置密码」，屏幕上什么都不变。新增用例先红才暴露，已修（`problems.phone ?? stepProblems.phone`，与 `0004` 修 `RegisterPage` 同一处改法）。

**第 13 条与第 14 条是同一个模式**：页面把「第一步的错误」与「提交的错误」存进两张表，而模板只渲染了其中一张。以后再有人给这两页加字段错误，应该先问这个问题。

### 5. 第二轮：把剩下的也补上

要求从「补齐校验类」扩到「前后端全部补齐」之后，先做了一次**零测试类的普查**（不是按文件名找，而是按「有没有任何测试——包括集成测试——断言过这个行为」找），然后补了剩下两类：

| 新测试类 | 为什么它此前没有任何证据 | 条数 |
|---|---|---|
| `common/CursorCodecTest` | `escape()` 是私有方法，只有 `encode` 走得到，而没有任何 fixture 把 `"`、`\`、换行或控制字符放进游标。**失败是静默的**：载荷是手拼的 JSON，一个没转义的值就不再是合法 JSON → `decode` 返回空 → 读的人当成「从头再来」，查询成功而页是错的。另外把 `decode` 的拒绝形状钉全了（非 JSON、版本不是 1、不是对象、缺 `o`/`k`、类型不对）——那是「坏查询串绝不是 500」这条承诺 | 6 |
| `common/TimestampsTest` | 截断到整秒**不是装饰**：`audit_event(at DESC)` 与键集游标把它当字符串比，带不定长小数时 `…:03.5Z` 按文本排在 `…:03.25Z` 之后，而按时刻是反的。此前没有一条断言说过这件事 | 5 |
| `modules/gateway/internal/WellKnownDigestTest` | 集成测试只断言了形状（64 位十六进制）与「不是版本摘要」。而它是个**内容**摘要这件事靠两条性质：按 path 排序（同样内容、不同顺序必须同摘要，否则客户端每次检查都以为变了、永远重下）、以及 NUL 作分隔符（空格分隔会让 `("a b","c")` 与 `("a","b c")` 撞）。两条都是从反编译的客户端里读出来的，最容易被「顺手整理」掉。另外补了一个**冻结向量**——类注释里写着「下面的冻结向量把它钉在自己身上」，而此前并没有向量 | 4 |
| `modules/version/internal/LikePatternTest` | `%` 与 `_` 已有集成测试，**转义符自己（`\`）没有**：不翻倍的话，搜 `\d` 到 LIKE 那里就是字面 `d`，静默返回错的行。`\` 恰好是查询里最不可能出现的字符，所以也是漏了最不会有人发现的那个 | 5 |
| 前端 `session.test.ts` / `app.test.ts` / `home.test.ts` | 会话状态在**模块级**（有意如此），所以每个用例导入一份全新的模块图。钉住：401 是「没人登录」而不是失败、**请求根本没到也要把 `loaded` 置真**（否则界面永远停在「加载中…」）、页面按路径分发、以及 App **在会话读回来之前什么都不渲染**——那不只是好看，服务端只在**应答**时才写 CSRF cookie，渲染早了的表单第一次提交必被拒 | 18 |
| 前端 `captcha.test.ts` / `code-request.test.ts` / `components.test.ts` | 验证码取不到时**同时清掉 id**（留着 id 就是让人回答一张看不见的图）；发码的两条换图规则（换，以及**不该换的时候不换**）；429 用**服务端给的秒数**而不是客户端自己的一分钟；以及那四个小控件的三态按钮与「没话说时什么都不渲染」 | 23 |

**关键的几条做了突变验证**（把生产代码改回错误行为，确认测试确实变红）：`LikePattern` 去掉转义符那一支 → `escapesTheEscapeCharacterItself` 红；`WellKnownDigest` 去掉 `.sorted(...)` → 乱序那条红。两个文件随后逐字节还原（`git diff` 为空）。

## 为什么

直接触发是「问覆盖率时发现三个类是零测试」（第一轮），随后扩成「前后端全部补齐」（第二轮）。更深一层与前一条已知问题同一句话：**测试全绿不等于被钉住**。

**第二轮的做法值得记下来**：不是按「有没有同名测试文件」去找缺口——那会把几乎所有类都列进来，因为集成测试是打 HTTP 的，类名一次都不出现。找的是**行为**：对每个有分支的类，先读出它编码了哪些边界，再去集成测试里搜那些**取值**（字面量 `%`、坏游标、边界数字），搜不到才算缺口。20 个候选里 4 个是真缺口，其余都是集成测试已经断言过的（例如 `CaptchaService` 的五个分支由 `WebCaptchaIT` 十条覆盖）。

**一处判据上的取舍：不追覆盖率数字，补的是两类东西。** 刻意**不测**「服务端也会拒的那些」（手机号格式、验证码过期、限流本身——那是 135 条集成测试的事）与样式；补的是**前端特有**的与**服务端零覆盖**的。

**速度是硬要求，而且做法已经定了**：要求是「不许真等十分钟」。事实上**这套测试树里没有任何 `Thread.sleep`**（全树只有 `SkillPublishIT` 用 `CountDownLatch`，那是并发同步）。依赖时钟的测试一律**改数据而不是等**：短信冷却与日限把 `auth_throttle.window_start` 那一行挪走（窗口是固定区间，挪行与等一分钟等价），验证码过期把 `expires_at` 改到过去。本轮新增的前端倒计时用 `vi.useFakeTimers()`。**服务端 `clean verify` 整条（编译 + 265 条测试）12.2 秒。**

### 6. 又一个真缺陷，同一个模式：漏了码表

`useCaptcha.refresh()` 的失败分支写的是 `error.value = result.message`——**服务端封套里那句写给看日志的人的英文**（`Too many requests.`），而不是 `codeMessage(result.code, result.message)`。这是全应用**唯一**一处没走码表的地方，于是图形验证码拉取失败时，页面上出现的是英文。新增用例先红才暴露的，已修。

## 影响

- **已交付行为**：服务端**一行未改**——那些规则本来就是对的，只是没被钉住（两处突变验证都是先改坏再还原，已确认 `git diff` 为空）。前端改了两行：`ResetPage.vue` 的手机号字段错误（第 4 条）与 `useCaptcha.ts` 的文案（第 6 条）。
- **测试数**：服务端 **246 → 285**（115 + 131 → 150 + 135）；前端 **48 → 105**（13 个文件）。服务端 `clean verify` 整条 12.0 秒。
- **需要同步的文档**：[`test-plan.md`](../test-plan.md) §结果记这两轮与新的数字，§已知问题加第 14 条（注册页与找回密码页是同一个模式）与第 15 条（漏了码表）。
- **是否需要新开 ADR**：不需要。没有跨版本取舍——「哪些测试值得写」是每一轮重新判断的事，而「不引测试框架、不追覆盖率数字」已有 [ADR 0015](../../../decisions/0015-web-frontend-stack.md) 的形态可循。
- **仍然没有测试的**（这一轮明确判断为不值得）：纯记录与枚举（`ApiError`、`ErrorCode`、`Throttle` 的 sealed record）、只有一行转发的 `Sha256Hex`、以及**服务端那些「服务端也会拒」的规则**（限流行为、验证码过期——135 条集成测试的事，重复一遍只会多一份会漂的副本）。
