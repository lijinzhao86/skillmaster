## 架构

这一版**不引入新组件类型**：把 CLI 那条登录路的目的地与产出换掉，其余全是既有机器。

```
   ┌──────────────── 浏览器（人在，登录着） ────────────────┐
   │  「授权请求」那一屏：预填的名称 / 权限（来自地址）      │
   └───────────────────────┬────────────────────────────────┘
                           │ ① POST /web/cli-sign-ins（会话 + CSRF）
                           │    铸一个短期凭证 + 发一个一次性码
                           ▼
              302 → http://127.0.0.1:<固定端口>/callback?code=…&state=…
                           │
   ┌───────────────────────▼────────────────────────────────┐
   │  CLI 的回环监听（既有：internal/auth/callback.go）       │
   └───────────────────────┬────────────────────────────────┘
                           │ ② POST /cli-sign-ins/exchange
                           │    码 + code_verifier → 凭证本身
                           ▼
              存本机（既有：internal/credentials，钥匙串优先）
```

**三个边界各自为什么这么放**：

- **决定权在会话面，写那一行在兑换那一下**（2026-10-16 校正——原句写的是「铸那一下在会话面：一次性码只是把**已经铸好的**那一个凭证递给 CLI 的运载工具」，而**那个机制做不到**：`access_token` 只存 sha256、`TokenStore` 从不返还明文、码表只存哈希，凭证又不许进 URL，于是兑换那一刻手里没有任何东西可以交出去）。实际的两步：
  - **点「同意并继续」那一下（会话）**写的是**授权那一行**——谁、哪个客户端、哪些 scope、人填的那个名称、以及绝对上限的锚点 `created_at`——再加**那一张一次性的码**（码记着这次授权，见下面那张表的 `authorization_id`）。
  - **兑换那一下（无会话）**写的是 `access_token` 那一行，并把凭证本身交出去。

  这没有放松 [ADR 0040](../../decisions/0040-api-key-in-the-cli-now-the-browser-path-later.md) §决定 1 的规矩。那条规矩的**理由**是「用 key 来造 key：泄漏之后撤不干净」，所以它要的是**凭据造不出凭据**——而码只可能由会话产生，短命、一次性、兑换时还要出示 PKCE 的证明。"有码就能造凭据"这句仍然不成立：**有"一个刚刚由会话产生的码"才能**。
- **递回来的绝不能被直接读走**。码走 URL，而 URL 会进浏览器历史、Referer 与服务端日志；所以 URL 里是**码**不是凭证，码短命、一次性、兑换时还要 CLI 出示 PKCE 的证明。这是 [ADR 0028](../../decisions/0028-cli-uses-a-fixed-loopback-port.md) 那个固定端口当初留的用法。
- **兑换那条路不带会话**（CLI 没有会话），所以它**不在 `/web/**` 链上**，也不在 `/api/v1/**`（那条要求 Bearer 权限）。它是新的一条**公开面**——因此**必须自带限流**，见 §接口。

**数据流（文字）**：CLI 生成 verifier/challenge → **先监听**再开浏览器（顺序与今天一致，见 `auth.Login` 的注释：回调比监听先到就永远丢了）→ 人在页面上点一下 → 服务端铸凭证 + 发码 → 浏览器 302 回本机 → CLI 拿码 + verifier 换凭证本身 → 存。

## 数据模型

**`api_key` 那一族一个字节不动。** 这一版不往它上面加列、不往里写行——短期凭证**不是** key（见 [`prd.md`](prd.md) §不做 #1）。

**短期凭证住在令牌那一族**：`oauth_authorization`（**一次同意**：谁、哪个 client、哪些 scope、框架自己的属性袋）＋ 它下面挂着的令牌行（`access_token` / `refresh_token`，两张表都**只存 sha256**）。

**`oauth_authorization` 要加一列 `label`**（2026-10-16 补——原先全文没说「人填的那个名称存在哪儿」，而它有两个必到的读者：验收 #2 那一行要显示 `CLI · <名称>`（Q6/T2），Q7 的"结束上一份"要靠它找到上一份）。**加列，不塞进 `attributes`**：这一列要**被查询**而不只是被显示（`WHERE principal_name = :user AND label = :label AND revoked_at IS NULL`），而 `attributes` 是**框架的属性袋**（V6 那条注释说的是"别去裁剪它"，不是"它是我们的"）。**加列也是安全的**：`TokenStore.upsertAuthorization` 的 `ON CONFLICT` 只点名 `authorized_scopes` / `grant_type` / `attributes` / `state` 四列（`created_at` 那条注释专门说明"冲突子句没点它，所以它保住了"），所以后续任何一次 save 都不会把 `label` 冲掉。**框架自己写的行这一列留 NULL**——第三方那条路不填它。

**同一张表还要加一列 `address`**（2026-10-16 补，写代码时才发现：**设计件里那一行的上行是完整地址**，而本文原先没给这个值留位置）。它记的是**批准这次登录的那个浏览器访客的地址**——浏览器会话那一行用的是会话自己的地址（Spring Session 已经存着），而 CLI 那一行的地址是「谁在控制台上点了同意」，那一瞬间之后就没有别的地方还拿着它。**不从审计里读**：铸那一刻确实写过一条审计，但 `audit_event` 归 M10，而 `TableOwnershipTest` 会因为别处点名它而红；一个每次渲染都要显示的事实，本来就该住在它所属的那一行上——`api_key.last_used_from` 对另一种凭据记的是同一件事。**可以为空**：框架写的行没有批准者，socket 没暴露时也没有，界面按拿得到的那一半画。

**`oauth_authorization` 还要加一列 `last_used_at`**（2026-10-16 补，P1 那一行要显示「最近活动」时才发现的；**加在哪张表上是 2026-10-16 二次补写的**——加在**授权那一行**上，不是 `access_token` 上。「这一份登录最后一次被用」说的是**授权的活动**，而 `access_token` 那一行只是它下面挂着的一枚令牌，寿命由滑动决定、活动却不由它记；下一段那个"不加列"说的正是为什么令牌行上不需要它）。它**可以从滑动的 `expires_at` 反推**（`expires_at − 闲置`），而那个反推**在最一天是错的**：封顶生效之后 `expires_at` 冻在 `created_at + 绝对` 不动，真实的上次使用却还在往前走——而那时正是这一行最该说准的时候（「最近活动」正是闲置这条尺子存在的意义，见 Q6）。所以照 **`api_key.last_used_at` 的先例**记一列：**由滑动那一次顺带写**，**采样口径完全一样**（只在比一个窗口更老时才重写）——也就是说它最多滞后一个窗口，这与另一种凭据那一列的口径是同一个。**代价如实记**：这一列只服务那一屏，验证路径多写一处。**它落在哪**：`IssuedTokenValidator.slide` 里，与滑动是**同一个决定、同一个采样窗口**，但落到库里是**两条语句**——先滑 `access_token.expires_at`，再按 `t.authorization_id` 更新 `oauth_authorization.last_used_at`（V17 的列注释与那段代码的注释都写作"同一条语句 / the same statement"；那句话说准的是"同一次滑动、同一个窗口"，不是字面上的单条 SQL）。**为什么不去改那两处措辞**：迁移文件一旦被应用就不能再改（Flyway checksum），所以把这句写准的地方是这里。

**绝对上限那条尺子锚在 `access_token.created_at` 上**（2026-10-16 校正：本节上方那张表写的是「`created_at` 已有」，而 `access_token` 与 `oauth_authorization` **两张表都有这一列**，差的是几秒——授权那行写在你点「同意」那一下，凭证那行写在兑换那一下）。**取凭证自己那一列**：这条尺子说的是"这份凭据活多久"，而它的生日就是它被写下来的那一刻。（`TokenStore.pastAbsoluteCeiling` 对刷新那一对锚的是授权行，因为那一对的生命确实从同意算起——两处不同不是疏忽，是量的东西不同。）

**`GET /web/sessions` 的答案多一个 `kind`**（2026-10-16 补，P1 合并两个来源时才定下）。它只取 `browser` / `cli` 两个值，而界面**只拿它决定「退出」那个动作往哪条路由发**——两条路由，而不是一个用同一串 id 猜两遍的解释器（这也正是 `/web/cli-sign-ins/{id}/revoke` 存在的理由）。**合并发生在 `api` 层**：M2 加一个只读的 `listFor(userId)`（`label IS NOT NULL` 就是"这是一次 CLI 登录"），M1 一行不动，控制器问两边、再把答案摆成一份。**M1 不能反过来依赖 M2**：那既是越表，也是环——M2 已经依赖 M1 的 `AuthThrottle`，`ArchitectureTest.modulesAreFreeOfCycles` 会红。

**「退出其他所有设备」从此也要结束 CLI 登录**（2026-10-16 补，合并引入的一处**必须修**的不一致）。那一屏的句子按屏幕上的行数算（「退出后，其他 N 台设备都需要重新登录」，设计件还写着「确认之后只剩当前这一台」），而 `POST /web/sessions/revoke-others` 在 v3 里只结束浏览器会话。合并之后 N 里含 CLI 登录，**那句话就成了假话**。修法是那个端点同时调 M2 的 `TokenRevocation.revokeAllFor(userId)`——它结束该账号的每一次授权，也就是全部 CLI 登录；当前那个浏览器会话仍然活着。**这是 v3 已交付端点的一次扩义**，按文档架构 §2.2 本该开 ADR；这里判成"实现设计件已经许下的那句话"，因为 Q6 把 CLI 登录放上那一屏的全部理由就是**它与浏览器会话是同一种东西**。

**它属于 P1**（2026-10-16 二次补写：这一处原先没写落在哪一期，而它是"那一屏上多了一行"的**连带后果**，只可能在 P1 出现）——见 §分期 P1 行。

**两条尺子怎么表达——不加列**：

| 尺子 | 怎么落 |
|---|---|
| **绝对 7 天** | 上限 = `created_at + 7d`（`created_at` 已有；7 天是配置） |
| **闲置 24 小时** | **滑动 `expires_at`**：每次使用时把它推到 `now + 24h`，**并封顶在 `created_at + 7d`** |

- **`access_token` 没有 `last_used_at` 这一列**（V1 建的是 `token_hash / client_id / user_id / scope / audience / expires_at / revoked_at / created_at`，V5 又加了 `authorization_id`），所以闲置那条**不用再加一列**——滑动 `expires_at` 就是它的表达，而 `expires_at` **本来就有索引**（`idx_at_expiry`）。**注意别把索引说成"清扫"**：今天**没有任何按时间清扫 `access_token` 的任务**（全库没有 `@Scheduled`；这张表上唯一的 DELETE 是按 `authorization_id` 走的，按时间过期的只有 `captcha`）。所以这一列的既有读者**只是索引与校验查询**。
- **滑动必须采样**，照 **`IssuedTokenValidator` 里那条 `noteUse`** 的形状（只在记录值比一个窗口更老时才重写；它不叫 `ApiKeyRegistry.noteUse`——那个类里没有这个方法）——请求路径今天是"近乎只读"的，**这一点不能丢**。**判据就是被写的那个值本身**（2026-10-16 补）：只有 `expires_at` 比 `now + idle − window` 更早时才写，所以**不需要再记一处"上次滑动是什么时候"**——`access_token` 也没有那一列，这与上面"不加列"是同一条。**口径**：滑动最多滞后一个窗口，所以库里那个值不早于「最后一次使用 + idle − window」——**闲置这条尺子的判定最多早一个窗口**（真到点是「最后一次使用 + idle」）。
- **两种到点要靠封顶分辨**（2026-10-16 补，prd 做 #11 / 验收 #5(a)）：滑动之后，"闲置到点"与"绝对到点"在库里都只是"`expires_at` 过了"，所以**只有 `created_at + absolute` 这条封顶说得出是哪一条**——**过了封顶就是「已到期」，没过就是「闲置太久」**。**这不加列**。**代价如实记**：验收 #5(b) 与 T4/T20 里那个"把到期时间改到过去"的夹具**要改成把签发时间一起推到封顶之外**——在滑动机制下，只把 `expires_at` 改到过去**不再是一个真实状态**（真实的 `expires_at` 永远等于 `min(最后一次使用 + 闲置, created_at + 绝对)`）。
- **滑动只对"这一版签发的凭据"生效**（2026-10-16 补）：两条尺子是 CLI 登录那一份的（Q1/Q6），而 `access_token` 这张表上还住着**第三方**的令牌——它保质 1 小时、后面有刷新链，把它滑到一天等于让被截获的那一份**值 24 倍**，而 [Q4](#q4-oauth-那套还在谁在用) 明说本版不动第三方那条路。**判据用 `label` 而不是 client_id**：那一列只由这一版新加的那条路写（V15），所以"有尺子的行"与"有 label 的行"**按构造就是同一个集合**，不是两个会各自漂的字符串。
  **一句区分**：**具名拒绝不分**这条路（两种凭据现在答同一套，见 §接口）——那是给"已经拿着 256 位秘密的人"更准确的话，不改任何行为；**滑动会改行为**，所以它必须分开。
- **不发 refresh token**（[`prd.md`](prd.md) §做 #2）：所以那个凭证的寿命就是它自己的，没有第二条命。**这也是"绝对"那条尺子能被上面这个封顶表达出来的前提**——没有刷新链，就不需要另一处记上限。
- **它怎么被铸出来是 §开放问题 Q5**：改授权服务器给这条路发的令牌的寿命，还是我们自己铸一行。**两条路落到库里都是同一张表的同一行**，区别在**谁写的**。
- **窗口值放在 `skillmaster.tokens.activity-window`（默认 `PT5M`）；跨两条尺子的那条关系在启动时校验**（2026-10-16 补：原句写的是「**`TokenPolicy` 的启动校验**要加一条：绝对不得短于闲置」，但那条关系**跨两个 record**——尺子是 `SessionPolicy` 的 `idle`/`absolute`，窗口是令牌这一族的——所以落点不在 `TokenPolicy` 的构造器里）。
  - **校验什么**：`activity-window ≤ session.idle / 10`。理由是可算的：窗口就是"闲置尺子最多早多少"，所以这条不变式说的是**最多早 10%**；默认那一对是 `PT5M` 对 `24h`（0.35%）。**取比例而不是绝对数**，是因为尺子本身是可配的——把闲置调成 1 小时的人，不该还带着一个按 24 小时挑出来的窗口（1 小时的十分之一是 6 分钟，默认那个 5 分钟仍然过）。
  - **另一条关系：`absolute` 必须严格大于 `idle`**（2026-10-16 二次补写：原句是"绝对不得短于闲置"，照字面读**允许相等**，而 `CliSignInPolicy` 的构造器用的是 `<=`——**相等也拒**）。理由与 `SessionPolicy` 那条同源、但**严一档**：相等会让第一次使用就把到期时间顶到封顶，**闲置那条尺子从此不决定任何事**；`SessionPolicy` 那边相等只是让闲置规则不可达（会话还有框架自己的行为），所以它写 `<`、这里写 `<=`。**这也正是 T8(c) 的输入取"相等"而不是"更短"的原因**——相等是唯一能把这两条规则分开的输入（更短的输入会被 `SessionPolicy` 先拒掉）。
  - **在哪校验**：`activity-window` 那条在 `config/TokenSecurityConfig.java` 里造 `TokenPolicy` 那处 bean——它同时拿得到 `properties.sessions()` 与 `properties.tokens()`；`absolute > idle` 那条在 `modules/token/CliSignInPolicy.java` 的构造器里（文案是 *is not longer than its idle ruler*）。两处形状都照 `SessionPolicy` / `TokenPolicy` 那一类**启动即拒**（抛 `IllegalStateException`，不是记一条日志）。

**新增一张一次性码表**（**一次性**这件事本身就需要状态）：

```sql
CREATE TABLE cli_sign_in_code (
  code_hash      TEXT PRIMARY KEY,   -- sha256，照三张令牌表与 api_key 的既有做法
  authorization_id TEXT NOT NULL,    -- 已经铸好的那一次授权；兑换只是把凭证交出去
  code_challenge TEXT NOT NULL,      -- PKCE，兑换时比对 verifier
  expires_at     TEXT NOT NULL,
  used_at        TEXT,               -- 非空即已用；重复兑换按"没这张码"处理
  created_at     TEXT NOT NULL
);
```

- **只存哈希**：与三张令牌表同一条规矩——库被看走不等于凭据被看走。
- **`authorization_id` 不加外键**：一张**一次性的、几分钟就死**的码，不该因为授权行被删而连带消失——**码失效应由它自己的 `expires_at` 说了算**，而不是由另一张表的生命周期说了算。**代价如实记**：会留下指向已结束授权的码行，靠 `expires_at` 过期（今天也没有清扫任务读它，同上）。
  （**别拿 `access_token.client_id` 当先例**：那条注释说的是另一件事——"a token outlives a client row being re-registered"，令牌比客户端行活得久；而且 `access_token.authorization_id` **今天是有外键的**（`V6`），拿这张表举例"不加外键"正好说反。）
- **不建索引**：按主键查；行数是"几分钟内点过几下"的量级。
- **它的寿命用既有的那个设置**（2026-10-16 补）：`skillmaster.tokens.authorization-code`（默认 `PT5M`）。一次性码与授权服务器自己那个码是同一件事、同一个数，**不再开第二个同义的键**——两个只会各自漂。写进 V14 的列注释里。
- **表归 M2（token）**，与 `oauth_authorization`、`access_token` 同属一处——**照 `ModuleMap` 现在的分法**（`new Module("M2", "token", …, Set.of("oauth_client", "oauth_authorization", "auth_code", "access_token", "refresh_token", "oauth2_authorization_consent", "api_key"))`）；**`ModuleMap` 要加一行**，否则 `TableOwnershipTest` 会红（它要求迁移里的表与 `ModuleMap` 的表集合**完全相等**）。

## 接口

| 方法 | 路径 | 作用 | 鉴权 |
|---|---|---|---|
| `GET` | `/cli-sign-in`（网页路由） | 那一屏：**预填、可改的「名称」**（值来自地址的 `name`，见 ①）/ 权限（来自地址、不可勾选）+ 「**同意并继续**」（寿命是两条定死的尺子，这一屏只**说清**它） | 会话。没登录时先走登录，**回到这一屏**（参数要活过登录） |
| `POST` | `/web/cli-sign-ins` | 铸一个短期凭证 + 发一个一次性码；返回 `{redirect_to}` | **会话 + CSRF**（与 `/web/keys` 同一套） |
| `POST` | `/cli-sign-ins/exchange` | 码 + `code_verifier` → **凭证本身**（只此一次） | **无**（凭码 + PKCE）；**必须有独立限流** |
| `POST` | `/web/cli-sign-ins/{id}/revoke` | **结束一份登录**（「登录设备」那一屏上那一行的动作） | **会话 + CSRF**（与 `/web/sessions/{id}/revoke` 同一套） |
| `POST` | `/web/cli-sign-ins/refuse` | **拒绝这一次登录**：不铸任何东西，只把浏览器送回它来的那个回环地址（带 `error=access_denied`）。那一屏上「拒绝」那一下走这里——2026-10-16 补，原先这一栏没有它，而**那一屏不知道回环地址**（`redirect_uri` 按本节是从注册行读的、不随地址来），所以拒绝没地方可落 | **会话 + CSRF**（与铸码那条同一套） |

**错误形状**：码的问题（不存在 / 过期 / 已用过 / verifier 不匹配）**一律同一个答案** `code_not_found`——与 `/web/keys` 对"不是你的 key"的处理一致：不泄露存在性。"你这个码用过一次了"听起来更有用，但它同时告诉了一个拿着随机码的人"这个码存在过"。（**HTTP 状态是 404**，与 `KEY_NOT_FOUND` / `SESSION_NOT_FOUND` / `SKILL_NOT_FOUND` 一致；400 会让客户端以为请求本身写错了。）

**出参的形状**：凭证本身**只在这一条响应里出现一次**（不落库、不进日志、不进审计——审计记的是"签了一份"，不是那份是什么）。

**结束一份登录是**新增的一条路由**（2026-10-16 校正——这一格原先写着"走已有的那条路，不新造接口"，那是错的：**今天没有任何接口能单独结束一条授权**。`TokenRevocation` 只暴露 `revokeAllFor(userId)`（全撤，它的注释自己写着那个 per-thing 接口是 deferred），而 `/web/sessions/{id}/revoke` 结束的是**浏览器会话**（`spring_session`），不是令牌。它与 `/web/keys/{id}/revoke` 也不是同一个端点：那把结束的是 key，这条结束的是**一次授权**——这正是本版不合并两种凭证的直接后果。**它的分期要说清**（2026-10-16 二次校正）：**这条端点本身在 P0**（§分期 P0 行那"四条接口"里的第三条），**而用它的是 P1**——「登录设备」那一屏上「结束一份」那个动作（§分期 P1 行的"做 #4 的界面那半"）。两者必须都到位，否则验收 #2 的"单独结束其中一份"无处可做；上一版这句话写的是"它必须进 P1 的交付"，与 §分期 P0 行把这条端点列进 P0 相矛盾。

### 这几条路由各自送什么、答什么（2026-10-16 补）

**补的是原表没写到的粒度，不改任何结论。** 上面那张表只有 方法/路径/作用/鉴权，而这一节自己的规矩是"接口形状（路径、入参、出参、错误码）"；地址与请求体不定下来，P1 读什么、P2 拼什么就无从写起。JSON 的字段名是**全局 snake_case**（`config` 里那条命名策略，`/web/sessions` 的 `device_id` 就是它）。

**① `GET /cli-sign-in`（网页路由：CLI 把浏览器领过去的那个地址）**

| 参数 | 谁给的 | 说明 |
|---|---|---|
| `client_id` | CLI | 编译期常量 `skillmaster-cli`；它决定读 `oauth_client` 的哪一行 |
| `state` | CLI 生成 | 回调时原样带回；CLI 用它丢掉不是这次的回调 |
| `scope` | CLI | 空格分隔；这一版是 `skills:read skills:write` |
| `code_challenge` | CLI 生成 | PKCE。**必须随这个地址一起来**：`cli_sign_in_code.code_challenge` 是 `NOT NULL`，也就是**铸码那一刻就得知道它**——而在那一刻，CLI 到服务端唯一的通道就是这个地址 |
| `name` | CLI 读的那台机器的名字 | **那一屏名称框的预填值**（2026-10-16 下午加，[prd](prd.md) §范围 做 #1）。CLI 是唯一知道自己在哪台机器上的那一方：macOS 取 `scutil --get ComputerName`、Linux 取 `hostnamectl --pretty`（退到 `/etc/hostname`）、Windows 取环境变量 `COMPUTERNAME`，**都取不到才退到 `os.Hostname()` 去后缀**——因为 `os.Hostname()` 给的是 `lijinzhaodeMBP.lan` 这种机器名，而「登录设备」那一栏要的是**人给自己机器起的名字**。**可选**：没有它就只是一个空框（旧版 CLI、手写地址），页面照旧要求人填。**服务端不信它**——它只是页面上那个框的初始值，真正写进 `label` 的是人在 POST 里提交的那个 |

- **`redirect_uri` 不随地址来，由服务端从 `oauth_client` 那一行读**。第一方那行是 `["http://127.0.0.1:51004/callback"]`（[ADR 0028](../../decisions/0028-cli-uses-a-fixed-loopback-port.md)：端口固定，且要与那一行**逐字符**相同）。**让请求决定回哪儿，等于把那个地址做成一个跳板**——回环地址也一样：服务端不该替任何人把一份码送到它没登记过的地方。
- **PKCE 的方法固定是 `S256`**，所以不带 `code_challenge_method`：这条路上只有一个客户端，而它是我们的。
- ⚠️ **设计件那个示例地址不是接口规格**——[`design/README.md`](../../../design/README.md) §怎么打开「授权请求」列的是演示件**自己**读的那几个参数（`client_id` / `state` / `scope` / `name`；演示件不做 PKCE，所以没有 `code_challenge`），那里也明说了判定规则是演示件自己的。

**② `POST /web/cli-sign-ins`**

```json
{ "name": "我的 MacBook", "client_id": "skillmaster-cli",
  "scope": "skills:read skills:write", "state": "…", "code_challenge": "…" }
```

- `name` **必填**（设计件：空着时「同意并继续」点不动）。服务端同样拒空——界面挡得住手滑，挡不住绕过界面。
- 后四项是**那一屏从自己地址里读到的**，原样送回来。服务端**一个都不信**：`client_id` 只用来选行、`scope` 要与那一行登记的 scope **求交**（`metadata.scopes`，第一方是 `skills:read skills:write`）、`code_challenge` 只是被存进码里、兑换时才拿出来比对。
- **求交而不是照单全收**：这样"屏幕上看到的那几条"最多**多于**真正授予的，永远不会少于——方向是安全的那一边。
- 答 `201` + `{ "redirect_to": "http://127.0.0.1:51004/callback?code=…&state=…" }`。

**③ `POST /cli-sign-ins/exchange`**

```json
{ "code": "…", "code_verifier": "…" }
```

（**没有 `client_id`**：2026-10-16 校正——本节初稿把它列进来了，而**码本身已经指名了哪一次授权**，客户端由那一行携带，再说一遍既没有读者、也没有可校验的地方。实现按两个字段。）

- 答 `200` + 凭证本身：`{ "access_token": "…", "expires_at": "…", "scope": "…" }`。
- `scope` 一并答出来，是因为它**不一定等于申请的那个**（上面那条求交），而"当前这份凭据能做什么"（Q9）答的正是它。
- **凭证只在这一条响应里出现一次**（见上面「出参的形状」）。

**④ `POST /web/cli-sign-ins/{id}/revoke`**：无请求体，答 `204`。与 `/web/keys/{id}/revoke` 同形；不存在的 id 与不是你的 id 给**同一个答案**（既有规矩，见 [`test-plan.md`](test-plan.md)）。

**⑤ `POST /web/cli-sign-ins/refuse`**（2026-10-16 补）

```json
{ "client_id": "skillmaster-cli", "state": "…" }
```

- 答 `200` + `{ "redirect_to": "http://127.0.0.1:51004/callback?error=access_denied&state=…" }`——**与铸码那条同一个形状**，界面因此只认一种回答。
- **它不铸、不发码、不写任何一行**：拒绝是一次没有发生的登录。
- **为什么不让页面自己跳**：它手里的地址只有 `client_id` / `state` / `scope` / `code_challenge`，**没有回环地址**——那是服务端从注册行读的（本版刻意如此：让请求决定回哪儿，等于把那个地址做成一个跳板）。所以「拒绝」这一下必须回到服务端问路，而问路的答案与铸码那条一样，只可能来自那一行。
- 不记审计：本版的指标量的是「凭据被主动结束的比例」，而这里没有任何凭据产生。

### 两条只读的查询命令（对应 [`prd.md`](prd.md) §范围 做 #9）

**这是本版唯一一条 `prd` 要求、而这张分期表原来没排进任何一期的东西**（2026-10-16 补）。发现它的是实现核对：做 #9 的**后半没有实现，而 P0/P1/P2 三期的验收映射里也没有它**——三期漏掉了，`prd` 的做 #9、验收 #10(b) 与 test-plan 的 T19 却一直要求着它。补的是两条里的**第二条**；第一条（`auth status`，不带参数）已经在线上。

**形状：`auth status [地址]`——给现有那条命令加一个可选的位置参数，不新开命令。**（2026-10-16 定，三个候选里选它：另两个是 `skill access <地址>` 与 `auth check <地址>`。）理由：两条命令问的是同一个问题——"**这份**凭据能做什么"——只是一个不带地址、一个带地址，所以同一族里放一个名字，比在 `skill` 那一族里把同一条规矩再答一遍便宜。

| | 送什么 | 答什么 |
|---|---|---|
| `auth status` | 无 | 今天的行为**不变**（来源 / 账号 / 凭据的事实） |
| `auth status <namespace>/<name>` | 一个 skill 地址 | 上面那些，**再加一段**：这份凭据对这个地址能做什么 |

**那一段有四种结局，每一种都要分得清**（判定见 T19）：

| 结局 | 什么时候 | 说什么 |
|---|---|---|
| **能读、能写** | 详情取到了，且 `can_write` 为真 | 能读、能写 |
| **能读、不能写** | 详情取到了，且 `can_write` 为假 | **还要说清是为什么**——缺 scope（换一份凭据就行）还是账号对这个 skill 没有这个权限（**换凭据没用**）。两句话不一样，因为人能采取的动作不一样（与 §验收 #8 那条同一个道理） |
| **不能读（凭据不够）** | 详情回 **403 `insufficient_scope`** | 「这份凭据没有 `skills:read`」——**换一份凭据有救** |
| **读不到** | 详情回 **404** | 与"这个地址不存在"**同一个答案**，不泄露存在性（既有的 404 规矩，Q9） |

**第三行与第四行不是一句话，别合并**：前者是凭据缺 scope，后者是"没有，或者你没权限"。合并它们就等于把一条有救的路说成没救的。

**服务端要加的是一个字段，不是一张权限表**（Q9 的话：这是那条既有规矩的一次**查询式暴露**）。`SkillDetailResponse` 加 **`can_write`**（boolean）：**这份凭据**对这个 skill 能不能提交新版本、管理共享。**由服务端算**，判据就是资源层今天已经在用的那一条（网关要 `skills:write`、资源层要你是 owner 或 editor）——于是**展示的答案与执行的答案出自同一处**。**客户端不重算这条规矩**，它只负责把"为什么不是"说出来（它自己知道自己的 scope：key 的来自 `/me`，登录态的来自本机那份凭据）。

**为什么不放在客户端算**：客户端只知道自己的 scope，**不知道账号对这个 skill 的角色**；让它去猜，就等于把这套判据抄第二遍——两处一定会漂，而漂的那天，"查出来能写"与"真去写"会给出不同的答案。

**代价如实记：每一次读详情都多一次按主键的查行。** 判角色那一行**上面那次读取已经解析过一遍**（`SkillRepository.Permitted`），只是被丢掉了；把它**穿过 `SkillSnapshot`** 就能免费，代价是给**每一个消费面的读**（控制台、`skill read`、每一个客户端）挂一个权限形状的字段，去服务一条查询命令。所以选了"在造详情时再查一次"——按主键、且只在**真的在造详情**时才发生（读不到就一次都不查）。真要收掉这笔，那就是把 `writable` 并进 `SkillSnapshot` 的那一刻，不是现在。

### 回环页（CLI 自己发的那一页）

**它不是服务端的一条路由**——是 CLI 的回环监听把浏览器留在的那一页（`internal/auth/callback.go` 的 `page` 常量）。**它的样子与文案的权威在设计件**（[`design/README.md`](../../../design/README.md) §授权结果：结构、数值、两句正文，以及"为什么承诺必须拿掉"那一段）。这一节只写**技术上要它做什么**，因为那些是设计件不该管的事：

1. **它是产品的一张卡，不是浏览器默认排版的一页。** 到 2026-10-16 为止它是一个 `<h1>` 加一个 `<p>` 加三行 `body` 样式，落到浏览器里就是默认字体的裸页面。数值**照设计件那张表抄**，改数先改设计件。
2. **三秒之后做一次尽力而为的关闭，页面上不承诺任何会自动发生的事**（做 #13，2026-10-16 改定，**当天收窄过一次**）。加载后 `setTimeout` 三秒调一次 `window.close()`；**没有倒计时、没有"关不掉"的改口**——那两半都是"页面替自己许的愿"，而这一页许不了。**失败了也什么都不做**：不是"读回来再改口"，是根本不说。
   ⚠️ **但"不承诺"不等于"不提"**，这两件事当天被混过一次：成功那一句正文是「**请关闭此页面**回到终端继续。」——**前半是给读者的指令**（人自己动手，说了就一定做得到），**不是**这一页在说自己会消失。所以这一节原来写的"页面上一个字都不说 / 没有任何关于这一页的话"**是收窄前的口径，已经作废**：按那个口径实现会把「请关闭此页面」删掉，而**验收 #15 / T23 要求它必须在**。**判据是"有没有 `/自动/` 这种许愿的话"，不是"有没有提这一页"。**
3. **为什么是"不承诺"，而不是"先说再改口"**：`window.close()` 只对 **script-closable** 的标签页生效，而 HTML 标准对这个词的定义是两条**满足任意一条**——"its is created by web content is true; **or** its session history entries's size is 1"（§7.2.2.1）。**这一页两条都不满足**：开它的是操作系统启动器（`exec.Command("open", …)`）而不是网页内容；而人是先答了上面那张卡才到这里的，那是**一次导航**，所以会话历史是 2 条。**第二条从流程内部无路可走**——这一页地址上那个一次性码正是那次点头铸出来的，所以它**只能被到达，不可能被打开**。于是"三秒后自动关闭"是一句**必然落空**的承诺，而在一张报告"授权成没成"的屏幕上先承诺再当场收回，两半都是错的。**这条结论有两条独立来源**：规范（上面那个定义），与业界先例——LangChain 的 deepagents 把同一套两步（关一次 + 500ms 后改写那句话）**删掉了改写**，理由是"那句话无论关不关得掉都是对的，所以没有东西需要改写"（PR #4463）。
4. **那次尝试留着**：它不要钱，而上面那两条讲的是**这一页**，不是每一个将来会加载这段脚本的页面。关得掉，人省一次点击；关不掉，人读到的是一张说了实话、也没多承诺一个字的卡。
5. **那两句标题属于这一族词**（做 #12）：`授权成功` / `授权未完成`，与请求那一屏、与服务端那几处同词。

### 这条凭据今天的拒绝只有一种（对应 [`prd.md`](prd.md) §范围 做 #11）

`IssuedTokenValidator` 里**两条路是分开的**：key 那条（`validateApiKey`）产生三种**具名**拒绝（`TOKEN_EXPIRED` / `TOKEN_REVOKED` / `ACCOUNT_SUSPENDED`），而 `access_token` 那条（`validateIssuedToken`）的拒绝**全部收敛成一个**（那个类的注释写着 *this path's refusals are all the same one*），`BearerAuthenticationEntryPoint` 的文案也是**硬编码给 key 的**（"This API key has been revoked./expired."）。所以 验收 #11 的四句不同的话**对这条凭据今天给不出**——那是本版要改的一段服务端代码，不是既有能力。

**四句里有一句是新的**（2026-10-16 补）：**闲置**。今天那三个具名码里没有它，而验收 #5(a) 要它与「已到期」分开说——判定方式见 §数据模型「两种到点要靠封顶分辨」。所以这一段要动的是**三处**：`ErrorCode` 多一个值、`TokenValidation.Rejected` 的允许集从四个变五个、`IssuedTokenValidator` 的 `access_token` 那条路**先把行读出来再在 Java 里判**（今天它把活性判断全塞在 SQL 的 `WHERE` 里，所以只能答"过了/没过"）。**那一层文案也要改**：它今天写的是 "This **API key** has been revoked./expired."，而这条凭据**不是 key**——把一句说了假话的话留在报错路径上，正是 [ADR 0038](../../decisions/0038-default-credential-is-an-api-key.md) 那类问题的形状。

### 本版撤掉的一条路由（对应 [`prd.md`](prd.md) §范围 做 #10）

| 方法 | 路径 | 处置 |
|---|---|---|
| `DELETE` | `/api/v1/skills/{namespace}/{name}`（`SkillsController`，实现是 `SoftDeleteSkillUseCase`） | **撤掉**。它今天只由 `skills:write` + owner 把关，也就是**任何凭据**都能删——包括 `skillmaster login` 换来那一份。删除改为**只在浏览器面**发生，而**控制台那处入口不在本版**（属于 skill 管理模块，见 [`prd.md`](prd.md) §不做 #8）——所以在本版与那处入口之间，**删除无处可做** |

**为什么撤而不是加一道闸**：「这个动作只有一个主体能做（人），而且他要在浏览器里做、还要再确认一次」——这是产品对**上线**已经定下的规矩（[ADR 0031](../../decisions/0031-submitting-and-publishing-are-two-actions.md) §决定 2 让 API 平面**没有** publish 路由）。给删除再加一个 scope 会留下第二种答案（"换个凭据就能删"），而这一条要的答案是**唯一**的：凭据删不了。**代价如实记**：无人值守的删除**从此不存在**（今天也只有凭据能删），要删就得人在浏览器里点；如果将来真有自动化删除的需求，那要另开一条 ADR，而不是把它塞回这个 scope 里。

> 这一条**要一条 ADR**：它改的是 [`v2-credentials`](../v2-credentials/prd.md) **已经交付**的能力（拿一把 key 删 skill），属于跨版本的取舍。

### 一次操作的结果落在谁身上

[`prd.md`](prd.md) §一次操作有哪几种结果 是**需求**的权威；这里写**它落在哪些既有的处理器上**——**本版新增的机制是两处**（最后两行，2026-10-16 校正：原先写的是"只有一处"）。

| 情形 | 谁产生的 | 为什么是它 |
|---|---|---|
| key 的 scope 不够 | **既有** `InsufficientScopeAccessDeniedHandler`：403 + `WWW-Authenticate`，**点名缺的那个 scope** | 它是**唯一**一条"换一个凭据能解决"的 403 |
| 账号对这个资源没有权限 | **既有** `NotPermittedException` → `ApiExceptionHandler`：403，**故意不带** challenge | 注释原话：带了它客户端会「re-authorize, get the same 403」——**死循环** |
| 读不到某个 skill | **既有**：渲染成 **404**，不是 403 | 不泄露存在性；判定在 M4 的用例里，不在安全层 |
| 凭据死了 | **半既有**：`BearerAuthenticationEntryPoint` 的 401 **有**，但那三种具名原因码**只由 key 那条路产生**——`access_token` 这条路的拒绝全收敛成一个（见上面「这条凭据今天的拒绝只有一种」） | **四句**各不相同，下一步也不同。**这条凭据要分四种是本版的新工作**（key 那三种 + 这一版新加的「闲置太久」） |
| 没有凭据 / env 里不是 key | **既有**，且**在 CLI 本地**：`ErrNotSignedIn` / `environmentKeyProblem`——**连接都不发** | 这两件事不需要问服务端 |
| **权限不够时说的话** | **本版要改的一处** | CLI 今天把 403 **合成一句泛泛的话**（`internal/api/client.go`：`403, which stays generic on purpose`）。**那条理由是为登录态写的**（重新授权还是同样的 scope）——**对 key 不成立**：key 的 scope 是签的时候选的，换一把就有。所以第 2 种要**按服务端给的理由分开说** |
| **这条凭据的四种死法** | **本版新增的第二处**（做 #11） | 上表第四行：具名拒绝今天只给 key，这段要改 |

|---|---|---|
| **P0** | 服务端：令牌那一族的两条尺子 + 一次性码表 + **四条接口**（发、兑、结束一份、拒绝）+ **这条凭据的四种具名拒绝**（做 #11）+ 审计 + 启动校验；**撤掉 API 平面那条删除路由**（做 #10） | #2 的一半（库里那一行在、**服务端撤得掉**）、#3、#4（服务端那半）、#5、#11、#12 |

**做 #10 只撤路由，不画控制台入口**（2026-10-16 定：入口属于 skill 管理模块，见 [`prd.md`](prd.md) §不做 #8）。**代价是明摆着的、也是接受了的一条**：在入口画出来之前，删除在整个产品里无处可做。反过来说，**先画入口、把路由留着**是那条被否掉的路——同意页那张清单就成了沉默的假话（它不再提「删除」，而凭据仍然删得了，见 [`design/README.md`](../../../design/README.md) §怎么打开「授权请求」与 [ADR 0046](../../decisions/0046-deleting-a-skill-happens-in-the-browser.md)）。

**P0 与 P1 的先后**：契约先成立，界面才有东西可点。**P2 必须在 P1 之后**——CLI 换实现那一刻，那一屏必须已经在线上，否则 `login` 会指向一个不存在的页面（这正是 [`v3-sessions`](../v3-sessions/test-plan.md) T17 给 `--client-credentials` 定的那种错）。

## 开放问题

### 已定（2026-10-16）

**Q1 · 这个凭证的寿命怎么给？** —— **两条尺子，与浏览器会话同一套**：**绝对 7 天**（从签发那一刻算）**＋ 闲置 24 小时**。
**代价如实记**：它让使用稀疏的机器变短——**两天以上才跑一次的机器，每次都要重新点一下**（闲置主导）；天天用的机器由绝对上限主导，约 **7 天**一次。这是这条尺子买到的那个性质的价钱，不是它的缺陷。

**第二条代价，与旧设计正面对照**：今天每条命令在网络上送的是那张 **1 小时的 access 令牌**（短的存在的理由就是"被截获也只值一小时"），而长命的那张 refresh 每 1 小时过一次网。新设计里**送出去的就是凭证本身**，所以：

| | 今天 | 这一版 |
|---|---|---|
| 每条命令在线上送的那个（最常见的截获物） | 值 **1 小时** | 值 **最多 7 天** |
| 线上能捞到的最值钱的那个 | refresh，值 **180 天** | 没有了——**最值钱的就是那 7 天** |
| 撤销它 | **没有入口**（只有重置密码能连带撤，而那会踢掉所有设备） | 控制台上单独结束 |

**两条都要放在一起看**：单次截获的价值上升了，但**天花板降了**（180 天 → 7 天），而**撤得掉**是今天完全没有的东西。这个交换是这一版的主题本身，不是它的副作用。

**Q2 · 它是不是就做成一把 API key？** —— **不是。两种凭证不合并**（[`prd.md`](prd.md) §不做 #1）。
一个是**登录态**（一次授权、会死、要重新点），一个是**长期凭证**（签发时定寿命、粘到各处、给无人值守用）。合起来之后，「API 密钥」那一屏上会同时住着这两样而两者都叫 key——**「key 是长期凭证」这句话就不成立了**，而它是 [`v2-credentials`](../v2-credentials/prd.md) 整版的前提。**本版对 `api_key` 那一族一个字节不动。**

**Q3 · 无浏览器机器怎么办？** —— **不变**：环境变量 + 一把 key（[`v2-credentials`](../v2-credentials/prd.md) §验收 #2 验过）。**不做**设备码流程。

**Q4 · `/oauth/*` 那套还在，谁在用？** —— **只留给第三方**（[ADR 0041](../../decisions/0041-third-parties-reach-us-through-the-cli.md)）。**不删**。

**Q5 · 「往库里写下那一行」由哪段代码执行？** —— **我们自己的代码**（不动框架的授权服务器），而且**在兑换那一下执行**（2026-10-16 补，见 §架构：会话那一下写的是授权那行与码，`access_token` 那一行由兑换写。原文没写这一层，而它决定兑换那一刻手里有没有东西可以交出去）。

它问的**不是"谁决定签发"**——决定权永远在浏览器会话那一边，这一版不动。它问的是**哪段代码写 `access_token` 那一行**。

**为什么自己写**：这一版的主题是**第一方这条路与第三方那条路分开**（与"两种凭证不合并"是同一条思路）。让框架的授权服务器去发一个"第一方特例"，正好把两件事重新缠在一起；而改动落在**我们自己的代码**里，比落在**框架的扩展点**里好查。

**代价如实记**：「往 `access_token` 写一行」从此**有两个作者**（框架一份、我们一份）。接受它只是承认一件本来就成立的事——按 [ADR 0023](../../decisions/0023-spring-authorization-server-with-our-own-storage.md) 的分工，**那张表是我们的**。

**它与"一次性码"是两件事**：不管谁写那一行，投递仍然要走码——**凭证不能经过 URL**（浏览器历史，以及任何一层想记就能记的日志）。

**Q7 · 同一台机器重复 `login` 会攒出多份吗？** —— **不会：替换本机那一份，并结束上一份**。结束发生在**浏览器那一下**，由服务端在同一个动作里做（CLI 永不撤销凭据，[ADR 0040](../../decisions/0040-api-key-in-the-cli-now-the-browser-path-later.md) §决定 4）。这与今天 `revokeReplaced` 的行为一致（它撤的就是上一次的授权），也防止控制台上攒出多行。

**"同一台机器"靠人填的那个名称认出来，那是服务端手里唯一的线索**（2026-10-16 补：原句说了"替换上一份"，没说**凭什么**找到上一份）。CLI 知道自己拿着哪一份，服务端不知道；而 ADR 0040 §决定 4 又把 CLI 排除在撤销之外，所以查询只能是 `principal_name + label + 还活着`。**代价如实记**：**两台机器填同一个名字会互相结束**。这是"名称即身份"这条选择的价钱，而产品在控制台那一行上已经选了它（`CLI · <名称>`，Q6）——**名称因此不能留空**，否则所有没填名字的机器会互相结束（服务端拒空，见 §接口）。

**Q8 · 过渡期残留怎么办？—— 先说清"残留有两种"，它们的话不一样**（2026-10-16 校正；原先这一问只写了第一种，而 prd 与 T12 又按第二种的形状描述它，两边对不上）：

| | 是什么 | 撤得掉吗 | 该说什么 |
|---|---|---|---|
| **(i)** | **旧的浏览器登录**留下的 OAuth 令牌（**有**刷新令牌） | **撤得掉**——`auth.RevokeAuthorization` 拿刷新令牌就能结束那次授权 | 说清它是什么、为什么不再能用、下一步做什么，**并且结束它**。这是这一问原来说的那一种 |
| **(ii)** | v3 删掉的**无人值守路**留下的（**没有**刷新令牌，认证是一个已经不存在的 client secret） | **撤不掉**——发一次撤销请求只会被服务端拒 | 说清它是什么、**为什么从这台机器撤不掉**、以及**它会自己过期**。今天代码里已经写着这句话（`ErrNotRenewable`、`revokeReplaced` 的那条分支），而它明确**不许**说"上一份已撤销"——那是一句不成立的话 |

**两种都要说清，因为它们都在野**：(ii) 是 v3 那次清理留给在跑机器的，(i) 是本版要取代的今天这条路。**把它们当成一种，就会对其中一种说假话**——而这正是校正前 prd 做 #7 与 T12 的问题。
（(ii) 那条与 [`v3-sessions`](../v3-sessions/prd.md) §范围 #5 的"撤不掉的残留"是同一类东西：那一份只能自己失效，所以 v3 也只能"说清"。）

**Q9 · 「查我对某一个 skill 的权限」答什么？** —— **答"当前这份凭据，对这个 skill，能做什么"**，并且**说清是哪一份凭据在起作用**。

**权限不是一个静态的账号属性**：能做什么 = **这份凭据的 `scope` ∩ 账号此刻的权限**（[`v2-credentials`](../v2-credentials/prd.md) §范围 #4 那条规矩）。**公式对两种凭据是同一条**（2026-10-16 校正：原先这里写"登录态不带 scope、就是账号的权限"，那是错的——`access_token.scope` 是 `NOT NULL`，签发时写入、校验时读成权限）；差别在 **scope 的值**：key 的是签发时勾的，登录态的是 CLI 申请的那两个。所以**同一个账号换一份凭据，答案可以不同**——原因不是公式不同，是 scope 不同；而这条命令要答的正是**当前生效的那一份**。

它是那条既有规矩的一次**查询式暴露**，不是一张新的权限表。**读不到的地址与"真不存在"给同一个答案**（既有的 404 规矩）。**命令名与入参 2026-10-16 定了**：`auth status [地址]`——见 §接口「两条只读的查询命令」。**服务端要加的是 `SkillDetailResponse.can_write` 一个字段**，判据就是资源层那条既有的；四种结局（能读能写 / 能读不能写并说清为什么 / 凭据缺 `skills:read` / 读不到）各自的说法也在那一节。

**Q6 · 它进哪一屏？** —— **并进 v3 的「登录设备」那一屏**（2026-10-16 定）。

**理由是两条尺子完全一样**——不是"相似"，是**同一个数**：

| | 闲置 | 绝对 |
|---|---|---|
| v3 的浏览器会话 | 24 小时 | 7 天 |
| 这一版的 CLI 凭证 | 24 小时 | 7 天 |

而那一屏的标题就是**「登录设备」**，它自己的分组理由写着「一个登录会话正是一种以你的名义做事的东西」（[`design/README.md`](../../../design/README.md) §登录设备）。**CLI 那一条是同一种东西**：一台机器以你的名义登录着，同样的两条尺子，同样的动作（退出 → 它要重新登录）。

**那一行的形状是"上下两行"**（2026-10-16 起；原先设计件是"一行竖着堆三段"，改的理由与量到的数见 [`design/README.md`](../../../design/README.md) §登录设备）：**上行是完整地址**，**下行是一句话**「什么设备　·　登录于 …　·　最近活动 …」。两行之间**只有第一段不同**——浏览器那一行是从 User-Agent **猜**出来的 `Chrome · macOS`，CLI 那一行是 **`CLI · ` ＋ 人自己填的那个名称**（而设计件有一条规矩：不画设备类型图标，因为"画错比不画更糟"，人填的名字没有这个问题）。**「最近活动」正是"闲置 24 小时"这条尺子存在的意义**。**「当前设备」那一条 CLI 没有**：你在浏览器里看这一屏，而那一行说的是另一台机器。

**代价如实记**：那一屏是 v3 刚交付、照设计稿做的，所以标题、计数句、空态句与**每一行的第二段**要一起改，v3 的实现（`AccountSessionsPage.vue`）跟着改。

### 仍未决

**没有。** 这一版没有悬着的取舍。
