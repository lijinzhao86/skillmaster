# v65-feedback-attachments · 产品需求

> **最后更新**：2026-11-13
> **所属版本**：[`README.md`](README.md)

## 用户与场景

**谁在用**

1. **终端用户**：在 Claude Code、WorkBuddy 或其它 agent 里做事，遇到界面错位、报错弹窗、操作没反应。一张图片或一段视频比一整段文字更接近现场。
2. **agent**：被用户驱动执行任务。用户把图片或视频**贴进对话**，agent 要把这份附件正确地交给平台，而不是让用户自己去敲命令、找路径、存文件。
3. **平台运营**：在对象存储里查看附件，判断问题；本版仍没有运营界面。

**在什么场景下用**

- 用户贴了一张图片说「就卡在这里」，或贴了一段视频说「点这个按钮没反应」。
- agent 按 v64 的流程写反馈文档；写完后要把用户刚贴的那份媒体一起提交。
- 用户不会手敲 CLI。取图、预览、提交都由 agent 完成；用户只负责贴图和说「可以」。

**现在的替代做法是什么**

v64 的反馈只收文本。用户要么用文字描述界面问题，要么把图片或视频发到别的渠道（邮件、微信），平台拿不到与回执对应的现场。这条缺口让「界面类问题」的反馈质量明显低于「命令类问题」。

## 范围

### 做

| # | 做什么 | 交付形态 |
|---|---|---|
| 1 | `skmr feedback attach`：把用户刚贴的媒体落成一个稳定文件并打印路径。取图顺序：消息里已有的路径（`--copy <路径>`）→ 当前会话的粘贴缓存（`--last-paste`）→ 系统剪贴板（`--clipboard`，随 `--last-paste` 兜底）。输出含来源、类型、大小、sha256 | CLI |
| 2 | `skmr feedback send` 增加可重复的 `--attach <路径>`；预览逐条列出附件（文件名、类型、大小、sha256）与合计大小，仍用 `--consent` 才发送 | CLI |
| 3 | 服务端在带附件时接受 `multipart/form-data`；文本字段与 v64 相同，附件作为重复的 `attachment` part。不带附件的旧 JSON 请求保持可用 | 服务端 |
| 4 | 附件类型按**文件头**识别，不信客户端声明：图片 `image/png`、`image/jpeg`、`image/gif`、`image/webp`；视频 `video/mp4`、`video/quicktime`、`video/webm`。其余类型拒收 | CLI + 服务端 |
| 5 | 每个附件写入**私有 OSS** 的命名对象；M18 新增 `feedback_attachment` 行，记归属、类型、大小、sha256、对象键。对象键不含原文件名 | 服务端 |
| 6 | 撤回时先删每个附件对象、再删归档对象与反馈行（`ON DELETE CASCADE` 带走附件行）；归档 NDJSON 带上附件元数据 | 服务端 |
| 7 | 隐私政策升到 1.3：写清附件收集、私有存储、长期保留、撤回删除、图片或视频不会被自动扫描、元数据可能保留 | 官网法务页 + 设计演示件 |
| 8 | `skillmaster` 与 `skillmaster-guide` 的反馈引导增加「贴图怎么带」：先看消息里的路径，再用 `attach --last-paste`，最后才请用户拖文件；提交前必须把附件清单给用户看 | skill 文本 |

**上限**：每条反馈最多 **5** 个附件；单个图片 ≤ **10 MiB**、单个视频 ≤ **50 MiB**、合计 ≤ **100 MiB**；空文件拒收。服务端是闸，CLI 保留同值常量用于发送前失败。实现后数值以生成的 [`docs/current/limits.md`](../../current/limits.md) 为准。

### 不做

| # | 不做什么 | 为什么 | 什么时候可能做 |
|---|---|---|---|
| 1 | 自动内容审核（图片或视频） | 反馈是私有收件箱：桶私有、无公开链接、只有运营可读，用户可预览与撤回。接阿里云内容安全要新增服务、费用、异步状态机与误杀处理，当前量级不划算。残余风险写进 [ADR 0190](../../decisions/0190-feedback-attachments-are-private-unmoderated-objects.md) | 附件量起来、出现违规内容投诉、或附件需要公开展示时 |
| 2 | 图片元数据（EXIF/GPS、XMP）剥离 | 需要解码或二进制改写；v65 原样保存并在预览里提示「图片或视频可能含位置等元数据」。这是隐私上的已知残余，不是遗漏 | 用户反馈元数据泄露、或合规评审要求时 |
| 3 | 视频转码、封面、在线播放 | 运营只需要看现场；下载原文件即可。转码要引入 ffmpeg 或云转码，收益低 | 运营界面需要内嵌播放时 |
| 4 | 控制台里的反馈提交入口与附件查看器 | v65 只做 agent/CLI；控制台入口是另一拨用户与另一套界面，一加就强制第 2 关界面设计与视觉验收；运营查看附件直接读私有 OSS。**2026-11-13 用户定**：入口放 TODO（见 [`TODO.md`](../../current/TODO.md) 的「控制台反馈入口与附件表单」）；查看器随运营工作台 | 反馈量起来、或需要非技术用户直接在网页提交时，单开一版；运营工作台开版时补查看器 |
| 5 | 附件的公开下载或内嵌路由 | 需要新的鉴权模型与内容分发面；私有桶已经够运营使用，少一条公开路由少一份泄露面 | 运营工作台需要带鉴权的下载时 |
| 6 | 只有附件、没有文字文档的反馈 | 文字是主文档：模板要求写清想做什么、发生了什么、怎么复现；只有图片无法检索与归类 | 出现大量「图多字少」的反馈时，再设计结构化表单 |
| 7 | 断点续传、分片上传、预签名直传 | 单请求 multipart 在 100 MiB 上限内足够；分片与预签名要多一套状态与鉴权 | 单条反馈上限提高到数百 MiB 时 |
| 8 | 非 macOS 的剪贴板读取 | v65 剪贴板只实现 macOS；Linux 用消息路径、会话缓存或拖拽，Windows 目前用消息路径或拖拽（没有会话缓存适配）。平台相关代码先收在一处，避免三套半成品 | 有 Linux/Windows 用户在 agent 里贴图的实际需求时 |
| 9 | 匿名或未登录提交 | 与 v64 同一条：不知道是谁提交的，无法回访、无法撤回 | 出现明确的匿名需求时，由新 ADR 定 |
| 10 | 每条每小时的附件字节预算 | 现有 10 条/小时 + 每条 100 MiB 已是上界；再加一层要新的计数查询与错误码 | 出现大附件滥用时 |

## 控制台操作与 CLI 对应

本版**没有新增或改动控制台操作**；反馈仍然只有 CLI 面：`skmr feedback attach` / `send` / `template` / `delete`。[ADR 0081](../../decisions/0081-every-console-operation-has-a-cli-command.md) 不触发。

## 验收与指标

### 验收标准

| # | 验收标准 | 怎么判定 |
|---|---|---|
| 1 | `skmr feedback attach --copy <路径>` 把消息里的临时文件复制到稳定目录（0700/0600），打印路径、来源、类型、大小、sha256；`--json` 输出同一组字段，另含 `original_name` | CLI 用例 + 临时目录断言 |
| 2 | 没有 `--copy` 时，`attach --last-paste` 先找当前会话的粘贴缓存，找到最新的允许类型文件；缓存没有才读 macOS 剪贴板。两者都没有时退出非 0，提示「拖文件进对话或给路径」，不发送任何请求 | CLI 用例 + 假缓存目录 + 剪贴板测试替身 |
| 3 | `skmr feedback send --file f.md --attach a.png --attach b.mp4` 的预览逐条列出附件与合计大小；不带 `--consent` 时没有任何 POST | CLI 用例 + 抓包断言 |
| 4 | 带 `--consent` 提交后，库里有 `user_feedback` 行与对应 `feedback_attachment` 行；每个对象存在于 OSS；响应含回执与附件元数据 | 接口测试 + 库表断言 + 假 OSS 断言 |
| 5 | 扩展名与内容不符时按内容判定：`.png` 里是 SVG、`.mp4` 里是文本都拒收；SVG、TIFF、HEIC、可执行文件一律拒收，原因可读 | CLI 用例 + 接口测试 |
| 6 | 第 6 个附件、单张图片超过 10 MiB、单个视频超过 50 MiB、合计超过 100 MiB、空文件、读不出的文件都被拒；CLI 本地先拒，服务端仍是闸 | CLI 用例 + 接口测试 |
| 7 | 不带附件的 `POST /api/v1/feedback` JSON 请求与 v64 行为一致；旧版 CLI 不需要升级就能继续提交文本 | 接口测试 + 兼容用例 |
| 8 | `skmr feedback delete <回执> --yes` 删除反馈行、附件行、归档对象与每个附件对象；再次删除返回「没有这条反馈」；对象在假 OSS 里确实不存在 | 接口测试 + 假 OSS 断言 |
| 9 | 归档任务的 NDJSON 包含附件的 `filename` / `media_type` / `size_bytes` / `sha256` / `object_key`；附件对象本身不重复归档 | 归档任务测试 |
| 10 | 另一个账号不能读取或删除别人的附件；不存在任何返回附件字节的 API 路由 | 接口测试 + 路由清单断言 |
| 11 | 隐私政策页（官网与设计演示件）含附件内容（并入「你主动提交的反馈」一节）：收集什么、私有存储、长期保留、撤回删除、不自动扫描、元数据可能保留；版本为 1.3；带 1.2 同意版本的提交被拒并提示重新预览 | 站点用例 + 接口测试 + 人工对照 |
| 12 | `skillmaster` 与 `skillmaster-guide` 的反馈引导写明：先用消息里的路径，再用 `attach --last-paste`，最后请用户拖文件；不得让用户手敲 CLI；提交前把附件清单给用户看 | 文档检查 + skill 文本断言 |
| 13 | Claude Code 真机：用户贴一张图，agent 取到同一个文件（sha256 与缓存文件一致）并成功提交；库里附件行与对象都在 | 人工真机验证 |
| 14 | WorkBuddy 真机：用户贴一张图，agent 能取到并提交；若该宿主沙箱挡住剪贴板与缓存，agent 按引导请用户把文件拖进对话，提交仍然成功 | 人工真机验证 + 记录宿主行为 |
| 15 | 预览后、发送前附件文件被删掉时，CLI 报可读错误且不落半条反馈；服务端不会出现只有反馈行、没有附件行的记录 | CLI 用例 + 接口测试 |
| 16 | 附件对象只存在于私有桶；响应里没有公开 URL；对象键不可从回执推导 | 配置断言 + 接口测试 |

**成立条件**：#4、#6、#8、#11、#13、#14 任一条不满足就不算交付——收得下、拦得住、删得掉、说清楚、两个宿主真机可用各一。

### 指标

| 指标 | 定义 | 怎么量 | 目标 |
|---|---|---|---|
| 带附件的反馈量 | 按自然周计数，只算成功受理且至少有一个附件的记录 | 查 `feedback_attachment` 与 `user_feedback` | 本版不设目标，先建立基线 |
| 附件拒绝原因分布 | 按错误码计数：类型、单文件过大、合计过大、数量超限、空/不可读 | 服务端错误日志或接口测试统计 | 用来决定放宽哪一档 |
| 附件总字节 | 每周新增附件的 `size_bytes` 之和 | 查 `feedback_attachment` | 观察存储成本 |

## 依赖与前置

- **外部依赖**：生产环境已启用私有 OSS 桶（v64 归档已依赖）；不新增第三方服务。附件不做自动审核是产品负责人的明确决定，见 [ADR 0190](../../decisions/0190-feedback-attachments-are-private-unmoderated-objects.md)。
- **内部前提**：
  - v64 反馈链路已合入 `main`（PR #185）。
  - 附件类型、上限、对象键与撤回口径由 [ADR 0190](../../decisions/0190-feedback-attachments-are-private-unmoderated-objects.md) 定；实现按该 ADR 与 [`technical-design.md`](technical-design.md) 走。
  - 隐私政策 1.2 → 1.3：官网 `skillmaster-site/src/legal/legalText.ts`、设计演示件 `design/src/home/legalText.ts`、服务端 `skillmaster.account.privacy-version` 三处同步；旧账号不强制重新同意，提交时按当次版本记录（与 v64 相同）。
  - 取图链路依赖宿主行为：Claude Code 本机版本会把贴图路径写进用户消息（未文档化的内部行为），`--last-paste` 不依赖它；WorkBuddy 的缓存与沙箱行为需真机验证，验证不过就退到「请用户拖文件」的兜底。
  - CLI 只发 beta（既有发布约定），本版不改变发布通道。
- **排除了什么前置**：不需要新通知类型；不需要运营界面；不需要控制台页面；不需要视频转码服务；不需要内容审核服务。
