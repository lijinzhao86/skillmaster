# 0001 · 同步有了进度日志，触发窗口改成仓库变量（默认 60 分钟）

> **日期**：2026-11-07
> **所属版本**：[`../README.md`](../README.md)
> **类型**：小版本迭代——**未改变对外可验收的能力边界**

## 改了什么

- `skillmaster-server/src/main/java/com/skillmasterai/usecase/sync/SyncPipeline.java`——一轮运行新增四行日志：展开开始（`sync run expanding configured=…`，在 `expand()` 之前）、运行开始（`sync run started configured=… entries=…`）、每 10 条一条进度（`sync progress done=…/… created=… unchanged=… blocked=… skipped=… failed=…`）、结束（`sync run finished entries=… duration=…s …`）。逐条结果码不变。
- `skillmaster-server/src/main/java/com/skillmasterai/usecase/sync/SyncJob.java`——删掉定时任务自己那条 `sync run finished entries=N`（pipeline 已经打了带计数与耗时的同一行）。
- `.github/workflows/sync-trigger.yml`——等待时长从硬编码的 20 分钟改成仓库变量 `SYNC_TRIGGER_TIMEOUT_MINUTES`（默认 60，范围 2–350）：curl 的 `--max-time` 由它算出来并短 30 秒，job 的 `timeout-minutes` 固定为 GitHub 的 360 分钟上限（job 级表达式在 step 之前求值，变量写错会让 job 直接死掉）。等待期间用第二条 SSH 尾随 `journalctl -u skillmaster -f`，把 `sync run expanding` / `sync run started` / `sync progress done=` / `sync run finished` 行实时写进 Actions 日志；答复的逐条 JSON 用 `jq` 收成「计数 + 失败条目」。
- `skillmaster-server/src/test/java/com/skillmasterai/usecase/sync/SyncPipelineIT.java`——新增 `aRunSaysWhereItIsWhileItWorks`：12 条条目跑一轮，断言展开行、开始行、`done=10/12`、`done=12/12` 与结束行，且结束行的计数正确。
- 文档：`technical-design.md` §日志与 §手动触发、`deploy/README.md` 的同步一节与配置表、`deploy/sync-sources.yml` 的扫描口径、v50 的 `README.md`（状态行、本版文档表）与 `test-plan.md`（T13/T14/T15 与 §结果）、`docs/current/TODO.md`（同步进度不可查询）。

## 为什么

2026-11-07 首次全量导入（114 条清单条目、展开后 932 个 skill）时暴露的：触发工作流的 `timeout-minutes: 20` 先到，curl 报 `(28)`、job 被标成 cancelled，而服务端仍在跑——**看起来像挂了，其实没有**。更要命的是这段时间完全不可观测：端点在结束时才答复，`journalctl` 上的 `sync entry=` 行按展开后的 skill 打（约 932 行），没有任何一行能回答「跑到第几条了」。

考虑过的做法：

- **只改超时**——解决了「被误报 cancelled」，但依然看不见进度，下次出问题还是两眼一抹黑。
- **加一个 `GET /internal/sync/status`**——能回答得更细（当前条目、已用时），但那是一次新的对外接口与状态机，属于功能改动；这次要的是「最小修复」。记进 [`TODO.md`](../../../current/TODO.md)。
- **把逐条 `sync entry=` 也转发到 Actions**——932 行会淹掉真正的答案；失败条目已经由汇总里的 `failed` 数组带上名字。

如果不改：一次大导入会长时间静默，操作者只能靠「再触发一次看是否 409」做存活探测，而且每次探测都在 Actions 里留一个红叉。

## 影响

- **影响哪些已交付行为**：对外验收边界不变。唯一可观察的变化是触发窗口的默认值 20 分钟 → 60 分钟（以前超过 20 分钟会被 worker 提前放弃，现在会等到 60 分钟），以及服务端多出四行日志、定时任务少掉一行重复的 `sync run finished`。
- **怎么验的**：全量 `./mvnw clean verify` 通过，集成 645 + 单测 426 = 1071（`SyncPipelineIT` 29 条含新增的 `aRunSaysWhereItIsWhileItWorks`）；`check_docs.py`、`impact.py --check`、`scripts/check-file-size.mjs`、CLI `go build ./...` 通过；工作流里的 grep 与 jq 用真实格式的样本行在本机实跑过（2026-11-07），首轮草稿里的 `sync (run|progress)=` 匹配不到任何真实行，已改成 `sync (run|progress) `，jq 字段改成 snake_case 的 `started_at` / `finished_at`。
- **需要同步改哪些文档**：已改 `technical-design.md`（§日志、§手动触发）、`deploy/README.md`（同步一节、配置表）、`deploy/sync-sources.yml`（扫描口径）、v50 的 `README.md`（状态行、本版文档表）与 `test-plan.md`（T13/T14/T15、§结果）；`docs/current/TODO.md` 新增一条「同步进度可查询」。
- **是否需要新开 ADR**：不需要。这是一次补参数与可观测性改动，不改变发布/同步的契约；仓库变量的默认值随文档走，跨版本仍成立的部分只有「端点一次性答复」这一条，它已经在 [ADR 0159](../../../decisions/0159-manual-sync-is-triggered-by-ci.md) 里。
