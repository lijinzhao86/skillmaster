# 0003 · 批量发布超时与同步上限

> **日期**：2026-11-07
> **所属版本**：[`../README.md`](../README.md)
> **类型**：小版本迭代——只改配置与它的绑定测试，**没有改变对外可验收的能力边界**（平台入库上限未动）

## 改了什么

- `skillmaster-server/src/main/resources/application.yml`：
  - 新增 `spring.mvc.async.request-timeout: 5m`。此前没有这一项，所有 `StreamingResponseBody` 接口吃框架默认的 30 秒。
  - `skillmaster.sync.max-files` 200 → 512、`max-file-bytes` 1048576 → 104857600、`max-total-bytes` 10485760 → 104857600。
- `config/SkillmasterProperties.java`：`Sync` 的三处 `@DefaultValue` 跟着改，免得记录默认值与 YAML 各说一套。
- 测试：`SkillmasterPropertiesTest` 的期望值改为新默认值；新增 `ScaleLimitsBindingTest`，用 `YamlPropertySourceLoader` 绑真实的 `application.yml`（并移除本机环境变量源，免得导出的 `SKILLMASTER_SYNC_*` 让结论随 shell 变），断言同步的文件数与单文件上限等于 `IngestLimits` 的对应常量、总量 100 MiB 且不超过 `max-unpacked-bytes`；另一个用例在只提供字符串字段的环境里绑 `Sync`（不加载 YAML），把三处数值上限与 YAML 绑定的结果比较——YAML 总是覆盖 `@DefaultValue`，普通绑定测试看不见它；第三个把 `spring.mvc` 绑到 Boot 自己的 `WebMvcProperties` 上断言 `requestTimeout` 为 5 分钟。
- `docs/current/config.md` 由 `scripts/docs/generate.py` 重出；`test-plan.md` 增 T30；`docs/current/TODO.md` 删除批量发布一条、改写同步上限一条的剩余部分。
- `SyncPipelineFixture` 的三处小上限加了注释：它们是夹具值，不是部署默认值。
- 没有新 ADR：平台契约（`IngestLimits`）没有改。

## 为什么

两条都是 v50 首次全量导入时暴露的（2026-11-07）：

- **批量发布被 30 秒截断**（v18 的老问题，被 53 条的规模第一次撞出来）：界面显示「12 份已上线、41 份没有结果」，库里实际是 13 条——第 13 条在 `AsyncRequestTimeoutException` 断流后 0.2 秒提交，前端没收到。`POST /web/skills/publish-batch` 是 `StreamingResponseBody`，走 Spring 异步请求，默认 30 秒。
- **同步上限比入库严**：`Leonxlnx/taste-skill`（1617 个文件、36 MB）被 `too_large` 阻断，而同一份内容走入库的限额是 512 个文件 / 单文件 100 MiB / 合计 512 MiB。同步用的是 200 / 1 MiB / 10 MiB，等于平台接受的内容会被同步无故拒绝。

**为什么选「提高异步超时」而不是「控制台分批 + 对账」**：三条路由里，提高超时只动一处配置，且文件与整包下载同一条流式路径一并受益；分批要改控制台，并新增「第 2 批失败时第 1 批已经发了」的呈现问题（v18 TD 的开放问题 3 就记着这个取舍）。分批留作超时仍不够时的下一步。

## 影响

- **所有流式接口**（批量发布、文件与整包下载）的最长流式时间从 30 秒变成 5 分钟。**这是总时长，不是空闲超时**：慢速的大文件下载即使一直在传，也会在第 5 分钟被切断。
- **5 分钟不是容量证明**：服务端对批量条数没有上限（500 是发布页列出的 skill 数，`ReadPublishQueueUseCase.LIMIT`），单条约 0.2 秒是 ADR 0161 的**估算，未实测**；检索开启时每条还要一次向量刷新（预算 5 秒）。更大的批量仍可能超时，只是阈值从 30 秒换成 5 分钟。
- **异步线程占用变长**：所有 `StreamingResponseBody` 共用 Boot 默认的 8 线程异步执行器。卡住的流以前 30 秒回收槽位，现在最多 5 分钟；慢客户端并发下载可能把批量发布排在后面。这是这次取舍的代价，需要时再给下载单独配有界执行器。
- **同步与入库只是部分对齐**：文件数与单文件上限直接取 `IngestLimits` 的两个常量；合计取 100 MiB（2026-11-07 用户定的「一个 skill 的大小」），仍低于入库的 512 MiB。另外 `max-repo-bytes`（压缩包）与 `max-unpacked-bytes`（一个仓库解压总量）仍排在前面，媒体型 skill 可能先撞它们；两者这次都没动。
- **taste-skill 仍然进不来**：它 1617 个文件，平台的 `IngestLimits.STANDARD_MAX_FILES` 与同步自己的 `max-files` 都还是 512。同步这条路上先在 `GitHubTar` 解压阶段被拦，走不到 `SubmitSkillUseCase`——要放它进来必须把两侧同批放宽，那是平台文件数上限的决定。留给 `TODO.md` 的剩余条目。
- **需要同步改哪些文档**：`docs/current/config.md`（生成物）、`docs/versions/v50-open-source-sync/test-plan.md`（T30 与结果）、`docs/current/TODO.md`（删除批量发布一条、改写同步上限的剩余部分）、`../prd.md` 与 `../README.md`（不再把批量超时写成未定）、`deploy/README.md`（三个新上限还没接进部署变量，只能改默认值）、[ADR 0161](../../../decisions/0161-imported-skill-state-is-fixed-when-the-draft-is-created.md) 的文件头状态注记与它生成的 `docs/decisions/README.md`（正文冻结，不动）。
- **是否需要新开 ADR**：不需要。平台上限与对外契约没有变；提高异步超时属于实现参数。
