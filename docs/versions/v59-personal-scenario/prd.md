# v59-personal-scenario · 产品需求

> **最后更新**：2026-11-10
> **所属版本**：[`README.md`](README.md)
> **状态**：需求已起草，待所有者确认

## 用户与场景

**谁在用**：把公开 skill 收进自己库、日常通过 agent 干活的开发者与知识工作者。用户基本不打开控制台；入口是对话里的 agent，agent 调 `skmr skills search` 去库里找。

**在什么场景下用**：用户说「帮我做一次循环审计」；agent 把这句话变成搜索词去库里找。作者写的描述和适用场景用的是作者的话（「PDF 提取」「法务审查」），和用户的说法对不上，agent 搜不到或搜错。用户想把「我会怎么说这件事」告诉系统，但不想改 skill 本身。

**现在的替代做法是什么**：

| 替代做法 | 代价 |
|---|---|
| 把整个 skill 复制一份到自己命名空间，再改描述 | 副本会漂移、与作者更新脱节；库里多一个语义几乎相同的候选，路由反而更差 |
| 在 `CLAUDE.md` / 提示词里写死「遇到 X 用 Y」 | 不随库变、不跨 agent、不参与检索 |
| 手动记住 skill 地址直接 `invoke` | 要求用户记住地址，不是搜索 |

### 用户流程

1. **入库**：用户或 agent 把一个公开 skill 收进库（`skill join`）。只有库里的 skill 才能写。
2. **写**：在控制台信息页，或由 agent 调 CLI，写一段自然语言，例如「当我说循环审计时用它」。
3. **用**：下次用户说类似的话，agent 搜索；这段文字参与库内排序，把这条 skill 顶到作者内容之前。
4. **改 / 清**：用户改说法或清除；下一次搜索按新文字匹配。
5. **搜不到时**：agent 在放弃前问用户「要不要把你会怎么找它写进某条 skill 的适用场景？」；用户同意后 agent 才写。

### 显示与召回语义

**能改这个 skill 的人也要维护两套，因为两段是写给两种读者的**：发布用的「适用场景」面向所有能看见这个 skill 的人，必须稳定、随版本走；「我的适用场景」只服务自己在库里的检索，可以用私人的说法，改了不产生版本。两套不是重复，是两个读者——别人怎么判断它、我怎么找到它。只能调用 / 浏览的人不需要这个解释：他改不了发布那句，写自己的找法就够了。

**显示**：

- 信息页：skill 自带的「适用场景」在上，是一整块 16px 正文；库条目在它下面多一块同样结构的「我的适用场景」，搜索时优先按它来找。两块靠小标题（「适用场景」/「我的适用场景」）、标记（时钟 / 小人）与可编辑性（只有我的那块有铅笔）区分，**不写常驻解释**。
- 没写我的：作者那块不变；我的那块显示空态「写一句你平时会怎么找它；搜索时先按你的说法找。」与「添加」。**能改这个 skill 的人（写入及以上）多一句**「上面那句随 skill 发布；这句只影响你自己的搜索，改了不用出新版本。」；只能调用 / 浏览的人没有这句——他们改不了上面那句，讲「两套」只会奇怪。
- 库列表预览：只有一格，显示生效的那段——写过显示我的，没写显示作者的。**CLI 的 `skills search`** 在命中个人层的那一行摘要末尾标「（命中你写的适用场景）」，不新增一段。**控制台本版不画这个标记**：设计稿没有库内语义搜索结果行这个态，控制台也没有对应的语义搜索面；本版控制台只承接信息页与预览的查看 / 编辑 / 清除，不新造结果行 UI。
- `skill show`：两行分开标；没写我的只显示作者的。

**召回**：

- 我的：S1 精确 / S2 语义。
- 作者的 `when_to_use`：**仍在 S3，不因个人层被删除**。
- 两段都命中：按我的 S1/S2 排；作者那段是兜底，不额外压过我的层级。
- 只有作者命中：skill 仍在结果里，S3，排在个人命中之后。
- 「覆盖」的定义：**显示与排序上的优先级，不是把作者那段从召回里删掉**。真正要收窄（「这个场景别用它」）是「不适用场景」的职责，本版不做。

## 范围

**本版同时收口 `SKILL.md` 的字段上限。** 作者的 `description` / `when_to_use` 和「我的适用场景」是同一个字段家族；个人层定 200，作者那句与描述却没有上限，会让同一份 `SKILL.md` 在写入、检索、向量化上留下不一致。趁 v59 还在设计阶段，把三条上限与契约一次定清，不再单开一版。

### 做

| # | 做什么 | 交付形态 |
|---|---|---|
| 1 | **我的适用场景**：复用作者 `when_to_use` 的字段名，每个用户对库里每条 skill 写一份自己的；只对本人可见；不产生版本 / 草稿，不改作者内容 | 服务端数据与接口 + 控制台信息页 + CLI |
| 2 | **入库才可写**：公开 skill 必须先入库；自建 / 共享的 skill 在库里即可写 | 服务端校验 + CLI 提示 |
| 3 | **库内检索生效**：证据分级 S0 名字/标题 → S1 个人精确 → S2 个人语义 → S3 作者内容 → S4 通用语义；个人层只在库内生效；**作者的 `when_to_use` 仍在 S3，不被个人层删除**；两段都命中时按我的 S1/S2 排 | 服务端 M08 / M13 |
| 4 | **自然语言，不维护短语**：精确命中用「查询与说明的最长公共子串」，语义命中用「说明按句切、向量取最大」；同义词表不做 | 服务端 |
| 5 | **三个写入入口**：控制台信息页、CLI、agent 流程（搜不到时提议写）；agent 必须经用户同意 | 控制台 + CLI + CLI 规则块 |
| 6 | **查看 / 编辑 / 清除 + 命中原因**：信息页与库列表预览显示生效的那段，`skill show` 显示；CLI `skills search` 只在命中个人层那一行标「（命中你写的适用场景）」，不新增一段；控制台本版不画结果行标记（设计未定义该态） | 控制台（信息页 / 预览）+ CLI |
| 7 | **最小事件记录**：`search` / `adopt` / `exclude` / `note` 事件，`search_id` 关联；只记录、不训练；复用「个人调用记录」（[`TODO.md`](../../current/TODO.md)「个人调用记录（只看自己）」）的 query 原文与事件管道 | 服务端 |
| 8 | **作者字段的下载 / 上传兼容**：`get --all` → `submit` 后 name / title / description / when_to_use / compatibility / frontmatter 不变；旁车 schema 不动 | CLI + 测试 |
| 9 | **三个字段的上限**：`description` 1–1024、作者的 `when_to_use` 0–200、我的适用场景 1–200，全部按 **Unicode 码点**（汉字、英文字母、标点各算 1）；作者字段写入与**发布**都过同一份契约，我的走自己的 API | 服务端校验 + 控制台 / CLI 字段级回执 |
| 10 | **字段级回执与兼容**：必填缺失、类型不对、超长时拒绝并给出字段路径、问题码、当前值/上限、下一步，一次报完；未知 frontmatter 字段保留，近似拼错（`whenToUse` / `when-to-use`）告警 | 服务端 + 控制台 + CLI |
| 11 | **同步 / 导入不合规拒绝并跳过**：不静默截断作者原文；拒绝原因进日志 | 同步管道 + 测试 |
| 12 | **离开库 / 失去访问时保留**：不删说明；重新入库或恢复共享后还在；`clear` 不要求在库，可清理 | 服务端 + CLI |

### 不做

| # | 不做什么 | 为什么 | 什么时候可能做 |
|---|---|---|---|
| 1 | **「不适用场景」** | 本版只做正向；「什么时候不用」需要独立的抑制机制与语义，本版不设计 | 不做 |
| 2 | **同义词表 / 人工词表** | 用户明确否掉；换说法交给语义 | 不做 |
| 3 | **训练 / LTR** | 本版只记录样本；模型要等 1–3 个月样本与离线评测 | 后续版本单独评估 |
| 4 | **公域个性化** | 个人说明不进公域检索、不进共享向量；公开搜索的结果必须与现状一致 | 不做 |
| 5 | **共享 / 团队说明** | 一人一份，不共享；团队版需要新的权限模型 | 不做 |
| 6 | **自动写说明** | agent 静默改检索会让人不知道结果为什么变；必须经用户同意 | 不做 |
| 7 | **批量导入 / 导出说明** | 本版只做单条；批量需要新的命令面与冲突规则 | 不做 |
| 8 | **说明文本进日志 / 训练** | 说明可能含敏感上下文；只记事件，不落原文 | 不做（训练另立版本） |
| 9 | **说明的版本化 / 历史** | 只保留当前一份；历史不参与检索 | 不做 |
| 10 | **控制台搜索页大改** | 本版只加信息页一块；设计稿没有库内搜索结果行，控制台不画命中标记，CLI `skills search` 有标记 | 不做 |
| 11 | **分类 / 公开标签随包走** | 这次只保证作者字段；旁车升 schema 2 并「只在新建时应用」是独立改动 | 不做 |
| 12 | **拒绝回执的邮件汇总** | 本版只做拒绝并跳过与日志；运营邮箱、发送频率、聚合位置、留存与隐私口径未定，记在 [`TODO.md`](../../current/TODO.md)「同步拒绝的回执汇总发运营邮箱」 | 后续版本 |
| 13 | **「我的说明」列表页** | 离开库后说明保留，但控制台只在库里看得到；本版用 CLI `my-when-to-use clear <地址>` 清理，不做集中列表 | 孤儿多再评估 |

## 控制台操作与 CLI 对应

| # | 控制台操作 | CLI 命令 | 备注 |
|---|---|---|---|
| 1 | 信息页查看「我的适用场景」 | `skmr skill show <地址>`（已有输出加一行「我的适用场景」） | 复用 |
| 2 | 添加 / 编辑 | `skmr skill my-when-to-use set <地址> --text <文字>`（`--text -` 从标准输入读） | 新命令，字段名与作者一致；不给 `--text` 是用法错误 |
| 3 | 清除 | `skmr skill my-when-to-use clear <地址>` | 新命令；幂等，本来没写也退出 0 |
| 4 | 入库 | `skmr skill join <地址>`（已有） | 入库后才可写 |
| 5 | 搜索结果里的命中原因 | `skmr skills search` 的摘要末尾加「（命中你写的适用场景）」 | 改输出；库内结果 |

**移出库时说明保留**：`skill leave` 的回执与控制台的移除确认都写「我的标签与我的适用场景保留，重新入库后还在」；`clear` 不要求在库。

**命令名 `my-when-to-use` 复用 `when_to_use` 字段名并带上归属（`my-`），不新造 `scenario` 这个词**；形状（set / clear / show 由 `skill show` 承担）先锁。没有高风险例外——写 / 清都是可逆、只影响本人的操作，不要 `--yes`。

**作者的「适用场景」不在这条命令里。** 它是 `SKILL.md` 的 `metadata.when_to_use`，是 skill 内容、随版本发布；创作者改它走现有内容流程：`skmr draft create` → `skmr skill edit <地址>@<草稿版本码> SKILL.md` → `skmr version publish`（网页确认）。**不新增 `when-to-use set --public`**：一条不带版本的命令就能改发布内容，会绕开草稿与上线。`my-when-to-use --help` 要写明这一点；`skill show` 打印两行，让人看到两者并存。

## 验收与指标

### 验收标准

| # | 验收标准 | 怎么判定 |
|---|---|---|
| 1 | 写入后在信息页与 `skill show` 显示同一段文字；作者写的与我的分开标 | 写「循环审计」→ 两处都读到同一字符串；左栏依次是「适用场景」（skill 自带）与「我的适用场景」（我的）两块、同档 16px；没写我的时我的那块给出空态（含「写了有什么用」一句）与「添加」 |
| 2 | 只对本人可见 | 第二个账号打开同一 skill，看不到第一段文字；作者也看不到 |
| 3 | 不产生版本 / 草稿，不改作者内容 | 写入前后 `skill_version` 行数不变；`description` / `when_to_use` / `current_version_id` 不变 |
| 4 | 未入库的公开 skill 不能写 | `skill my-when-to-use set` 与控制台都拒绝，提示先入库 |
| 5 | S1 精确命中排在作者内容之前、名字/标题之后 | 构造两条 skill：一条名字命中、一条作者描述命中；给后者写说明；查询命中说明 → 后者排在前者之后、作者描述命中之前 |
| 6 | S2 语义命中能召回换说法 | 标注集改写组：说明写「循环审计」，查询「反复审查」→ 该 skill 进前 5 |
| 7 | 公域搜索不受影响 | `scope=public` 的同一批查询，结果与写入说明前一致 |
| 8 | 清除后不再按说明匹配 | 清除 → 同一查询不再因该说明进入结果 / 排序 |
| 9 | 校验：空文本、超长、非法地址 | 空文本与 >200 个 Unicode 码点拒绝并给出字段级错误；非法地址 404 |
| 10 | 控制台与 CLI 一致 | 控制台能做的写 / 清，CLI 都能做；错误码与文案同义 |
| 11 | 事件可关联 | 每次 search / adopt 能用 `search_id` 串起来；说明原文不出现在日志 |
| 12 | 隐私口径已补 | 隐私政策 §五 的 DashScope 条目写入「个人适用场景的文本」；未补充前 S2 不上线 |
| 13 | 下载→提交后作者字段不变 | `get --all` 一个 skill → 原样 `submit` → 对比 name / title / description / when_to_use / compatibility / frontmatter，全部一致 |
| 14 | 个人说明不删除作者的那段 | 写了我的说明后，构造一个只命中作者 `when_to_use` 的查询 → 该 skill 仍进结果（S3）；构造一个两段都命中的查询 → 按我的 S1/S2 排 |
| 15 | `description` 上限 1024 码点 | 1024 个汉字或英文字母通过；1025 个拒绝；中文与英文各按 1 计；回执给出字段、当前值与上限 |
| 16 | 作者 `when_to_use` 上限 200 码点，且发布复校验 | 200 通过、201 拒绝；旧草稿在规则生效后超限，不能上线，回执指向该字段 |
| 17 | 我的适用场景上限 200 码点 | 200 通过、201 拒绝；emoji 按 1 个码点计，不按 UTF-16 的 2 计 |
| 18 | 同步 / 导入不合规拒绝并跳过 | 超限包被跳过，不截断原文；日志列出地址、来源、字段、问题；未知字段保留，近似键告警 |
| 19 | 离开库保留、重新入库恢复 | 移出库后重新入库，我的适用场景还在；离开后 `clear` 仍可清；它不影响库外搜索 |

**成立条件**：第 5、6、7 条同时满足才算「检索生效」；第 12 条是 S2 的上线闸。

### 指标

| 指标 | 定义 | 怎么量 | 目标 |
|---|---|---|---|
| **Top-1** | 期望 skill 排第 1 的查询数 ÷ 有结果的查询数 | 人工标注集，分字面 / 改写 / 个人触发三组 | 字面组不低于基线；个人触发组 ≥ 90% |
| **Recall@5** | 期望 skill 在前 5 的查询数 ÷ 全部查询数（零结果算失败） | 同上 | 改写组比基线 +20 个百分点 |
| **MRR** | 平均 `1 / 期望 skill 名次` | 同上 | 不低于基线 |
| **误触发率** | 个人层命中、但期望 skill 不在其中的次数 ÷ 个人层命中次数 | 同上 | ≤ 5% |
| **零结果率** | 返回 0 条的查询数 ÷ 全部查询数 | 同上 | ≤ 5% |
| **库内检索 P95** | 服务端处理时间，不含 embedding 服务网络耗时 | 压测 / 日志 | 比基线多 ≤ 10 ms |
| **说明保存 P95** | 写入接口端到端 | 压测 / 日志 | ≤ 300 ms |

## 依赖与前置

- **外部依赖**：embedding 服务（DashScope `text-embedding-v4`）。S2 需要把说明文本发给它；隐私政策 §五 的 DashScope 条目必须先补，否则 S2 不上线。
- **内部前提**：
  - [ADR 0180](../../decisions/0180-personal-scenario-ranks-by-evidence-library-only.md)：证据分级 + 个人层只在库内生效 + v1 不训练。
  - [ADR 0181](../../decisions/0181-text-limits-use-unicode-code-points.md)：文本上限统一按 Unicode 码点；`SKILL.md` 是作者元数据的唯一事实源；写入与发布同契约；未知字段保留、近似键告警。
  - 「个人调用记录」的 query 原文与事件管道（v58 已合并）；P3 的 `search_id` 关联与个人层命中标记由后续 PR 补，不重复落原文。
  - `design/` 的信息页新增块与搜索结果命中原因；第 2 关出设计稿。
  - 阈值校准集（正例 + 近义负例），第 4 关定口径。
- **排除了什么前置**：不需要先做公域 ANN 索引（个人层只在库内）；不需要先做同义词表（换说法交给语义）；不需要先有训练数据（规则版先落）。
