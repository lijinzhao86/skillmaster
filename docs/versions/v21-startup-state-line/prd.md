# v21-startup-state-line · PRD

> **最后更新**：2026-10-26
> **所属版本**：`docs/versions/v21-startup-state-line/`

## 用户与场景

**谁在用**：装好 CLI、登录之后运行 `skillmaster startup` 的人。新人第一次跑，以及走到一半停下来的老人回来再跑，都是同一个入口。

**在什么场景下用**：`startup` 打印的旅程正文是静态的，**唯一因人而异的是它上面那一行「现在的位置」**。这一行是续跑点：它说「下一步：搬运」，agent 就去读 `steps/01-import.md`；说「下一步：写提示词、验证，然后下线」，就去读 `steps/03-prompt.md`（旅程在平台上是 [ADR 0096](../../decisions/0096-guidance-lives-on-the-platform.md) 的决定；阶段到文件的映射在技能自己的起点表里，规则见 [v20 TD](../v20-guidance-on-platform/technical-design.md) §接口 › CLI 的「状态行不再写步号」段）。判错一次，人就被指到错误的文件，后面的步骤也不会报错——旅程照样走到「完成」。

**现在的替代做法（也就是缺陷本身）**：CLI `1.0.0` 按**计数**分支——本机有 skill、线上也有 skill，就认为「线上那些是搬上去的」，于是报「下一步：写提示词、验证，然后下线」。

真实反例（[KI-1](../v17-cli-startup/known-issues.md)，2026-10-26 真机）：本机 33 个 skill、线上 2 条**完全不同名**的 skill、草稿 0。两者毫无交集，本机 33 个一条都没上过平台，状态行却说已经可以写提示词了。人照着走，旅程末端显示「完成」，而 33 个 skill 仍在本地。

**这一版补的**：把判定从「有没有」改成「**是不是同一批**」——按名字判断，并且两种平台读法各自只看**我的**那一份。

## 状态判定规则

这一节是本版的规格本身。代码照它实现，测试照它判定。

### 一个本机名字在平台上的三种位置

| 平台上的事实 | 位置 |
|---|---|
| 我的线上清单里有这个名字 | 已上线 |
| 我的草稿队列里有这个名字（线上没有也算） | 已搬待上线 |
| 两边都没有 | 未搬 |

### 一台机器的判定（从上往下，第一条命中）

结论是**四个固定句子之一**，标点也在内；`technical-design.md` 的 `switch` 与测试逐字引用它们。

| # | 条件 | 状态行的结论 |
|---|---|---|
| 1 | 存在**未搬**的名字 | 下一步：搬运。 |
| 2 | 没有未搬的名字，但**我的**草稿队列非空 | 下一步：上线。 |
| 3 | 本机有名字，且全部在线上 | 下一步：写提示词、验证，然后下线。 |
| 4 | 本机没有名字，我的线上非空 | 已完成：平台可用，本机没有副本。 |
| 5 | 其余（两边都空） | 下一步：搬运。 |

**为什么第 1 条压过第 2 条**：旅程是「搬完再统一上线」（上线在控制台批量做，v18）。本机还有 20 个没搬、同时有 1 份草稿时，先报「上线」会把人拉去发布那一条，回来再做搬运——节奏反了。反过来先报「搬运」，搬完自然落到第 2 条，两步顺序与旅程一致。

### 「我的」怎么算：两种平台读法各有各的口径

- **线上清单**只取 `source=created`。`GET /api/v1/skills` 默认 scope 是 `library`，它的定义是 created / shared / joined 三类之和（`SearchScope.java`）——**同事共享给你的、或你加入库的公开 skill，只要与本机目录同名，就会被判成「已搬过」**，这是 KI-1 换一扇门又回来。
- **草稿队列**是**权限面，不是所有权面**：`GET /api/v1/author/publish-queue` 列出「我能发布的东西」，同事以 maintain 及以上共享给你的 skill，其草稿也在里面（`SkillCatalogRepository.publishQueue`）。所以状态行只认**自己个人命名空间**里的行——先用 `GET /api/v1/me` 取 `user.namespace`，把命名空间对不上的行丢掉；否则同事的同名草稿会让本机副本看起来「已搬」，同样是 KI-1 换一扇门。

### 句子

```
现在的位置：本机候选目录里 33 个 skill（其中 0 个已上线），我的库里有 2 条线上、0 份草稿在等上线 —— 下一步：搬运。
```

- **「（其中 N 个已上线）」**：N = 本机名字 ∩ 我的线上。判定改成名字以后，读者光看结论看不出为什么；补这个数，判定自证。线上清单被截断时写「**其中至少 N 个已上线**」——没被第一页命中的名字可能仍在线上，确数会是一句读起来像事实的假话。
- **「我的库里」**：线上条数与草稿份数都只算自己的（口径见上一节）。原先写「库里」，在含共享 / 加入 skill 的账号上会和 `skills list` 的条数对不上。
- **阶段词，不写步号**：**结论**只出现上面四个固定句子之一，前缀与计数是固定模板；行内不出现「第 N 步」（规则见 [v20 TD](../v20-guidance-on-platform/technical-design.md) §接口 › CLI「状态行不再写步号」）。
- **判不出来就不打印**：任一数据源（本机扫描、`/api/v1/me`、草稿队列、线上清单）失败，整行不打印，不补零。

## 范围

### 做

| # | 做什么 | 交付形态 |
|---|---|---|
| 1 | 判定改为按名字：本机每个名字在「我的线上 / 我的草稿」里的位置 | CLI |
| 2 | 判定顺序按上表第 1–5 条（未搬优先于草稿） | CLI |
| 3 | 只算我创建的：线上取 `source=created`，草稿只取自己个人命名空间的行 | CLI |
| 4 | 句子补「（其中 N 个已上线）」（截断时写「至少」），「库里」改称「我的库里」 | CLI |
| 5 | 单测覆盖上表五种状态、名字来源、队列命名空间过滤、四个数据源的失败；其中「无交集」一格**在旧实现上必须失败** | 测试 |

### 不做

| # | 不做什么 | 为什么 | 什么时候可能做 |
|---|---|---|---|
| 1 | 不新增 CLI 子命令 | 这是既有判定的修正，不是新能力（修复单的约束） | 不做 |
| 2 | 不比较 skill 内容——同名不同内容算「已搬过」 | 设计允许同名（`state.go` 的既有注释）；比较内容等于把导入流程塞进一行，而导入要停下来问人 | 导入流程将来做内容级去重时（[technical-design.md](technical-design.md) §开放问题 Q3） |
| 3 | 不在状态行里罗列名字 | 一行；要名单用 `skills list` 或本机目录 | 不做 |
| 4 | 不判断「提示词写没写 / 验证跑没跑」 | 没有数据源：CLI 不知道人的系统提示词文件长什么样 | 平台能报这两个状态、且出现跨机器续跑的需求时（[technical-design.md](technical-design.md) §开放问题 Q2） |
| 5 | 不为状态行翻页：线上清单一页 50 条、草稿队列一页 500 个 skill（每个可带多份草稿） | 一页覆盖首次使用与绝大多数账号；每次都翻页会让 `startup` 多几个请求。没被这一页命中的本机名字按**未搬**算——两个方向的错代价不对等 | 有用户**自己的**线上 skill 超过 50 条时（TD §开放问题 Q1） |
| 6 | 不改 `skills pending`、`skills list` 的输出，不改控制台 | 本版只改状态行 | 不做 |
| 7 | 不把「已下线」算作已上线（线上清单本来就只取 live） | 下线之后平台没有可用副本，本机副本是唯一能用的那份；**且没有待上线草稿时**状态行把它当未搬，与旅程第一步（重新提交）一致。有草稿时按判定第 2 条走「上线」——发布草稿会把它带回线上 | 产品把「下线」改成只是暂时隐藏、平台仍可用时 |

## 控制台操作与 CLI 对应

本版**不新增、不改动任何控制台操作**（[ADR 0081](../../decisions/0081-every-console-operation-has-a-cli-command.md) 的映射表为空）：改动只在 CLI 的状态行，控制台一个字不动。

## 验收与指标

### 验收标准

| # | 验收标准 | 怎么判定 |
|---|---|---|
| 1 | 本机名字与我的线上、草稿**都无交集**时报「下一步：搬运。」 | 单测：本机 `{a,b}`、线上 `{x}`、草稿 `{}` → 行内含「下一步：搬运」。**同一输入在 `1.0.0` 上得到「写提示词…」，所以这一格在旧实现上必须是红的** |
| 2 | 本机名字全部在线上时报「下一步：写提示词、验证，然后下线。」 | 单测：本机 `{a,b}`、线上 `{a,b}`、草稿 0 |
| 3 | 本机名字全部是草稿时报「下一步：上线。」 | 单测：本机 `{a}`、草稿 `{a}`（1 份）、线上 `{}` |
| 4 | 有未搬的名字时「搬运」优先，即使草稿非空 | 单测：本机 `{a,b}`、线上 `{a}`、草稿 `{a}` → 「下一步：搬运。」 |
| 5 | 平台侧只算我创建的：线上按 `source=created`，草稿只算自己命名空间 | 单测一：假服务端记录请求，`GET /api/v1/skills` 的查询串**含 `source=created`**（与 `show=live` 并存）。单测二：队列里放一条别的命名空间、与本机目录同名的草稿 → 仍判「未搬」，草稿份数也不含它。真机由 #11 复核（账号里没有共享/加入 skill 时，共享那一半只有单测覆盖） |
| 6 | 本机无副本、我的线上非空时报「已完成：平台可用，本机没有副本。」 | 单测 |
| 7 | 句子给出「（其中 N 个已上线）」，N = 本机名字 ∩ 我的线上；线上清单被截断时写「其中至少 N 个已上线」 | 单测：本机 `{a,b,c}`、线上 `{a}` → 含「其中 1 个已上线」；`liveTruncated` 时 → 含「其中至少 1 个已上线」 |
| 8 | 任一数据源失败时整行不打印，不补零 | 单测四格：本机扫描不可读、`/api/v1/me`、队列、线上清单各失败一次 → `("", false)` |
| 9 | 线上清单被截断时，未被第一页命中的本机名字按未搬算；只在本机名字全部命中时才认「全部已上线」。队列被截断时写「N 份以上…」 | 单测三格：截断且本机名字未全部命中 → 「下一步：搬运。」且条数写「50 条以上」；截断但本机名字全部命中 → 照常报尾部阶段；`draftsTruncated` → 「N 份以上草稿在等上线（更早的没有列进来）」 |
| 10 | 行内不出现步号，结论是四个固定句子之一 | 断言行内不含「第」，且结论与判定表逐字一致（含标点） |
| 11 | 真机复现 KI-1 场景得到「搬运」 | 本机任意个名字、线上有不同名的 skill、草稿 0 → 「下一步：搬运。」；与 `skills list --source created`、`skills pending`（只算自己命名空间的行）、本机目录三处人工核对一致；共享 / 加入的同名 skill 不计入线上条数与「已上线」数（账号里有时必查） |
| 12 | 不改动其它输出 | `skillmaster help` 的子命令表与 `1.0.0` 逐行一致 |
| 13 | 本机与库里都空时报「下一步：搬运。」 | 单测：本机 `{}`、线上 `{}`、草稿 0 |

**成立条件**：验收 #1（无交集报「搬运」）与 #5（只算我创建的）是**不满足就不算交付**的两条——前者是 KI-1 本身，后者是它换一扇门复发的路径；其余条目都是它们的边界。

### 指标

| 指标 | 定义 | 怎么量 | 目标 |
|---|---|---|---|
| 状态行与事实不一致的次数 | 同一时刻，状态行的结论与本机目录、`skills list`、`skills pending` 三处对不上 | 真机走一遍 + 单测覆盖五种状态 | 0 |

## 依赖与前置

- **缺陷单**：[`known-issues.md`](../v17-cli-startup/known-issues.md)（KI-1）是本版的需求来源与反例。它的「期望行为」第 2 条把「同名草稿」也写成进入「写提示词」阶段，与它自己的边界段和验证表冲突；本版以**草稿 → 上线**为准。
- **阶段词与无步号**：[v20 TD](../v20-guidance-on-platform/technical-design.md) §接口 › CLI 的「状态行不再写步号」段定下了这条规则；阶段到文件的映射在技能自己的起点表里。[ADR 0096](../../decisions/0096-guidance-lives-on-the-platform.md) 是「旅程在平台上」这个更大的决定。
- **被修正的是实现，不是验收**：v17 验收 29（[`prd.md`](../v17-cli-startup/prd.md) §旅程本身）的条件本来就是状态——「全部上线且本机仍有副本时」才报尾部阶段；`1.0.0` 用计数近似（`localCount > 0 && live > 0`），没有满足它。本版把判定规则写死成名字口径并在自己的验收里钉住，v17 正文不改（已交付版本的记录）。
- **服务端能力已就位、零改动**：`GET /api/v1/skills` 的 `show=live` 与 `source=created` 过滤都已存在（`LibraryRepository.where()` 的 `sources` 分支，v14/v19）；`GET /api/v1/author/publish-queue` 由 v18 提供（**不是**控制台的 `/web/publish-queue`——那条要会话）；`GET /api/v1/me` 给个人命名空间 `user.namespace`。
- **本机扫描已就位**：`internal/local.Scan`，状态行今天就在用。
- **无设计稿改动**：改的是 CLI 打印的一行文本，不是界面；`design/` 不涉及。
- **发布**：随下一个 CLI 版本随常规发布流程走；本版不改变 API 代次（[ADR 0088](../../decisions/0088-cli-major-version-is-the-api-generation.md)），因此不改主版本号。
