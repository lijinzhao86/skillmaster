# v68-cloud-device-login · 让没有浏览器的机器也能登录

> **最后更新**：2026-11-14
> **状态**：已实现（服务端、控制台、CLI 与设计件完成；五轮审计通过；本机与 WorkBuddy 沙箱的端到端已跑通；待合并）
> **含收费**：否

## 目标

把 CLI 的登录收敛成一条流程：**CLI 给一条一次性链接，用户在任何有浏览器的设备上批准，那台机器自己取回凭据**。细节见 [`prd.md`](prd.md)。

## 验收标准

一句话：在无浏览器的机器上能完整登录、在桌面上不少一步、在无人值守时仍然正确地回到 API Key。完整验收见 [`prd.md`](prd.md) §验收与指标。

**成立条件**沿用 [`prd.md`](prd.md) §验收与指标：验收 #1、#2、#5、#8 四条全部满足才算交付。

## 这一版明确不做什么

- 不做移动端 App —— 一张网页已经覆盖批准这一步，App 是第二套客户端、授权与存储
- 不做终端二维码 —— 一条链接已经够用，二维码只省打字
- 不做宿主注入凭据 —— 要逐个宿主适配，先让通用流程成立

完整范围与每条理由在 [`prd.md`](prd.md) §范围。

## 与目标态的关系

[`target/`](../../target/) 没有单独定义登录终端；这一版不改变目标态的产品形态，只是让「换一台机器也能用」在云端设备上成立。没有分叉需要登记。

## 影响最大的未决问题

工程侧完整列表见 [`technical-design.md`](technical-design.md) §开放问题；产品侧未定项见 [`prd.md`](prd.md) §不做。按重要性排：

1. **设备上的凭据活多久**：沿用浏览器会话的 24 小时闲置 / 7 天绝对，还是给服务器更长的窗口（TD Q1）。
2. **要不要终端二维码**：一条链接已经能用，二维码只省打字（PRD §不做 2）。
3. **宿主注入凭据什么时候叠上来**：WorkBuddy 沙箱那种「平台直接给令牌」的形态最顺，但需要逐个适配（PRD §不做 3）。
