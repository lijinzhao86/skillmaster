## 目标

一次失败之后，控制台显示服务端给出的具体原因，而不是通用的「提交的内容有问题」；同一次动作下一次成功时不会把上一次的失败留在屏幕上，无关的读取成功也不会擦掉写失败。细节见 [`prd.md`](prd.md)。

## 验收标准

十条（A1–A10），摘要其中四条：共享给一个不存在的用户名时看到「没有这个用户名，检查一下拼写。」；共享给自己时看到「不用共享给自己——这个 skill 本来就在你名下。」；失败后紧接着一次成功的共享，横幅消失；所有 `codeMessage`、编辑器 `showFailure`、`FailureReporter` 的调用都带上 `details`（类型层面不能再漏）。完整验收见 [`prd.md`](prd.md) §验收与指标。

**成立条件**：第 1 条不满足就不算交付——这一版的目的就是让服务端已经给出的具体原因真的到屏幕上。

## 这一版明确不做什么

- 不改服务端错误码、`details` 的形状或错误文案本身——服务端已经发送详情，缺的是客户端没有接。
- 不新增字段级错误位置——设计稿的「共享给」没有字段错误态；具体句子放进现有横幅。
- 不引入全局错误中心 / toast——只修「丢掉 details」与「旧横幅」。
- 不改 CLI——本版没有新增控制台操作。

## 与目标态的关系

[`target/`](../../target/) 描述产品完整形态。本版是其中的错误反馈子集：保留「每条失败都说清下一步」，只把客户端丢掉的那部分接回来；没有新增能力，也没有与 `target/` 分叉。

## 影响最大的未决问题

完整列表见 [`technical-design.md`](technical-design.md) §开放问题。按重要性排前两条：

1. **Q1 用户名错误放在哪里**——本版放横幅，因为设计稿的「共享给」没有字段错误态；设计补了这一态之后再搬。
2. **Q4 横幅什么时候清**——动作开始时清，读取成功时只清自己上一次读失败留下的横幅；写失败不被无关读取擦掉。
