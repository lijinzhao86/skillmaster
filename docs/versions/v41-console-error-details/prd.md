# v41-console-error-details · 需求

## 用户与场景

作者在控制台管理 skill 时，失败提示是他唯一能知道「哪里错了、下一步做什么」的地方。今天有两类失败被吞掉：

1. **具体原因被通用句盖住。** 服务端在 `details[]` 里给出字段与规则（例如共享给一个不存在的用户名时 `field: handle, issue: no_such_user`），但控制台多数调用只把 `code` 与 `message` 交给 `codeMessage`，`details` 没有传。结果是多数调用点上的 `invalid_request` 都显示「提交的内容有问题，请检查后重试。」——共享页、密钥页、版本页、设置页都会碰到。
2. **成功的动作不清旧横幅。** 一次共享失败后横幅写着原因；下一次共享成功，名单已经更新，横幅还挂着，页面看起来仍在失败。

用户不需要知道 `details` 是什么；他只需要看到「没有这个用户名，检查一下拼写。」而不是「提交的内容有问题」。

## 范围

### 做

1. **把 `details` 接到所有能拿到它的失败调用。** `codeMessage` 的 `details` 参数从可选改为必填；新增 `failureMessage(result)`，把一个失败结果整体交给它。控制台里所有 `codeMessage(result.code, result.message)` 的写法改成 `failureMessage(result)`；只有拿不到 `details` 的调用（例如批量发布里的一行）才显式传 `[]`。**例外**：`useCodeRequest` 先过滤掉 `field: phone` 的详情后仍用 `codeMessage`——号码在飞行期间可以被改，旧号码的句子不能出现。
2. **失败横幅的生命周期统一。** 用户发起的动作在开始时清空自己的横幅；读取成功时清掉上一次读取失败留下的横幅；成功路径不保留旧横幅。
3. **覆盖范围**：协作者（共享、改档位、撤销、批准、拒绝、名单读取）、标签与加入/移除、密钥（新建、撤销、续期）、版本（改名、说明、上线/下架/恢复/丢弃）、文件读取、skill 详情读取、申请/撤回访问、单文件 diff、会话读取、图形验证码、设置（可见性、下线、删除）、skill 恢复、会话结束、登录/注册/找回/CLI 授权页、发现页与发布页、导入失败。具体文件见 [`technical-design.md`](technical-design.md) §接口。
4. **测试**：下面每一条验收都有用例；全量控制台测试保持绿。

### 不做

| 不做 | 理由 | 什么时候可能做 |
|---|---|---|
| 改服务端错误码、`details` 形状或错误文案 | 服务端已经发送；本版只把客户端丢掉的部分接回来。改文案是 voice-spec 的另一个动作 | 出现「服务端没发 details」的新失败时 |
| 在「共享给」输入框下新增字段级错误位 | 设计稿的「共享给」没有字段错误态；本版把具体句子放进现有横幅。新增位置要先改设计稿 | 设计稿补了这一态之后 |
| 引入全局错误中心 / toast / 统一拦截器 | 超出「丢掉 details」与「旧横幅」两个缺陷；会把一次修复变成一次架构改动 | 出现跨页面的错误呈现需求时 |
| 改 CLI | 本版没有新增控制台操作；错误文案在 CLI 侧已经由各自命令处理 | 不适用 |
| 改「服务端英文 message 是否上屏」的兜底策略 | 现有策略是「有中文就用中文，没有才回退服务端原句」；本版不扩大也不缩小 | 需要统一未知错误码时 |

## 控制台操作与 CLI 对应

本版**没有新增控制台操作**：它只改已有失败提示的呈现与生命周期。控制台的共享、密钥、版本、设置等操作在 CLI 上的对应命令不变；本版不申请 [ADR 0081](../../decisions/0081-every-console-operation-has-a-cli-command.md) 的例外。

## 验收与指标

| # | 验收标准 | 怎么判定 |
|---|---|---|
| A1 | 共享给一个不存在的用户名，横幅显示「没有这个用户名，检查一下拼写。」 | 组件测试：`POST /grants` 返回 400 `invalid_request`，`details: [{field:'handle', issue:'no_such_user'}]`；断言 `.banner` 文本 |
| A2 | 共享给自己，横幅显示「不用共享给自己——这个 skill 本来就在你名下。」 | 同上，`issue:'already_yours'` |
| A3 | 一次共享失败后紧接着一次成功的共享，横幅消失 | 组件测试：第一次 400，第二次 201；断言成功后再无 `.banner` |
| A4 | 一次读取失败后紧接着一次成功的读取，旧横幅消失 | 组件测试：协作者名单先失败；在搜索框输入一个词，200 ms 后触发一次**只读**重读并成功；断言 `.banner` 不存在 |
| A5 | 所有 `codeMessage`、编辑器 `showFailure`、`FailureReporter` 的调用都带 `details`，类型层面不能再漏 | `npm run type-check` 通过；三处 `details` 都已改为必填，漏传会编译失败 |
| A6 | 控制台既有测试全绿 | `npm test` |
| A7 | 界面结构与样式不变，只改句子与横幅的显隐 | 代码 diff 里没有 CSS / DOM 结构变化；组件测试的 DOM 断言不变 |
| A8 | 标签或加入/移除失败后一次成功，旧横幅消失 | 组件测试：失败一次、成功一次；成功后页面横幅不存在 |
| A9 | 一次无关的读取成功不擦掉写失败的横幅 | 组件测试：共享失败后，在搜索框触发一次成功的只读重读；横幅仍是共享失败的句子 |
| A10 | 写请求期间改了用户名，不显示针对旧用户名的详情 | 组件测试：共享请求挂起时改输入，再返回 `no_such_user`；横幅是通用句，不是「没有这个用户名…」 |

**指标**：没有单独的量化指标。判据是 A1–A10 全过。

## 依赖与前置

- 服务端已经发送 `details[]`（`ErrorDetail` 在 [`api/types.ts`](../../../skillmaster-console/src/api/types.ts)），本版不依赖服务端改动。
- 文案来自 [`api/errors.ts`](../../../skillmaster-console/src/api/errors.ts) 的 `FIELD_SPECIFIC` / `ISSUE_MESSAGES`（这两句不在 [`design/voice-spec.md`](../../../design/voice-spec.md) 里；voice-spec 管语气与名词）；本版不新增文案，只让已有文案真的显示。
- 无新增 ADR：这是对既有约定（失败要说清原因）的实现修复，不是跨版本取舍。
