## 用例

### T1 · 五档逐档兑现

- **前置**：账号 A 建 `a/pdf-tools` 并上线一版（三个文件，正文点名提到其中一个）。账号 B、C 存在。测试库已跑完 V18–V20。
- **步骤**：A 依次把 B 的档位设成 `调用` → `浏览` → `写入` → `维护` → `管理`，每一档都用 B 的凭据把该档允许的动作全跑一遍。
- **期望**：逐档**只多出它那一档的能力**——
  - `调用`：`/metadata` 200、`/body` 200、`/files/{正文点名的那个}` 200、`/files/{没点名的}` 200（路径点名即可取，与今天相同）；**详情 `/api/v1/skills/a/pdf-tools` 403**；`/versions` **200，但响应里只有 `published`**（草稿不给）；**控制台打开时是「信息」与「版本」两栏，版本栏没有草稿**（prd #1）；`/metadata` 与今天**逐字段相同**——完整的 `frontmatter`（含 `allowed-tools`）与 `digest` 不因梯子收紧，收紧的只是控制台「信息」栏**显示**的那一部分
  - `调用` **并且用 CLI 真的走一遍**——这一条是设计时漏掉、后来又补上的：`skillmaster skill invoke a/pdf-tools` 与 `skillmaster skill read a/pdf-tools <正文点名的路径>` **都要成功**（它们必须从 `/metadata` 解析出版本、再自己拼 `/body` 与 `/files/{路径}` 并带 `X-Skill-Version`，**不能从详情进**）；而 `skillmaster skill files a/pdf-tools` 在这一档 **403**——它就是列目录，归 `浏览`
  - `浏览`：上面全部 + 详情 200（**含完整清单**）+ **控制台的详情 / 正文 / 文件栏打得开**（作者面，[ADR 0051](../../decisions/0051-the-author-plane-serves-by-tier.md)），**但版本列表里没有草稿**——**这两条要一起验**，因为「进得去」与「看不到草稿」是同一档的两半，只验前一半会把一个漏了过滤的实现放过去
  - `写入`：上面全部 + `POST …/versions` 201 + 丢弃**自己提交的**草稿 204 + `GET /web/skills` 的默认列表里能看到这个 skill（`authorPage` 认被授 `write` 的）
  - `维护`：上面全部 + `publish` 200（含**回滚**：B 先提交并上线一个新版本，再上线 v1——它之前**已上线**的那一版，不是 A 的草稿）+ 丢弃**A 提交的**草稿 204（A 的草稿要留到这一步，前面的档位不碰它；**改描述不在这一档的期望里**——它归元数据那一版，见 [prd §不做 #8](prd.md)；设计件那一格写着它，而本版不交付）
  - `管理`：上面全部 + `…/grants` 三个动词都通 + `PATCH …/visibility` 200 + `GET /web/skills` 默认列表里仍有它
- **判定**：通过／失败（失败时记下**哪一档多给了或少给了哪一条能力**）
- **形状**：这个用例的每一条断言都要在**五档各跑一次**，所以它是一张「档位 × 动作」的表，逐格判——写成一个参数化的 IT，不是五份手写的用例。

### T2 · 每一档的负向能力（本版最容易做没的东西）

- **前置**：同 T1，B 被授 `管理`。
- **步骤**：用 B 的凭据逐条试它**不该**能做的事。
- **期望**：
  - B（`管理`）**删不了** `a/pdf-tools`：`POST …/delete` → 403
  - B（`管理`）**恢复不了**任何东西：这一条在 T10 里验（那里有已删的 skill，`POST …/restore` → 403）；本用例不重复造那个态
  - B（`管理`）改不了归属/所有者：**根本没有这条路由**（404，不是 403）
  - B（`写入`）**不能**丢弃 A 提交的草稿、**不能**上线、**不能**改可见性
  - B（`浏览`）**不能**提交版本
  - 「所有者」**不出现在任何可授档位的名单里**：授权接口用 `role: "owner"` → `400 invalid_request`；控制台的档位下拉里也不出现它
  - **旧的词被明确拒绝**：授权接口用 `role: "viewer"` / `role: "editor"` → `400 invalid_request`（**不是**静默当成 `browse` / `write`）；CLI 的 `skill share --role viewer` 同样报错退出、且**不写任何授权行**。这一条是接口级的契约（[技术设计 §一处要连带改的契约](technical-design.md)），不验它就会有一条「回『已授权』而实际授了别的档」的路
- **判定**：通过／失败
- **为什么要单列**：这一条的每一条断言都是**今天不存在**的边界。实现时最自然的写法（把 `mayAdminister()` 改名成 `atLeast(ADMIN)`）会让删除被静默放开。

### T3 · 已有的两条授权按语义平移

- **前置**：一台 **Flyway 上限停在 V17** 的库（`spring.flyway.target=17`），里面有 `role='viewer'` 与 `role='editor'` 各一行。
- **步骤**：放行 V18，断言回填结果；再在跑完 V18 的库上，**把 `SkillSharingIT` 的 12 例按新词表重写**（`share("viewer")` / `share("editor")` 换成 `share("browse")` / `share("write")`，旧词那几条改成断言 `400 invalid_request`），然后再跑一遍。
- **期望**：
  - `viewer → browse`、`editor → write`，`role` 不再是旧词的**行数为 0**
  - CHECK 生效：插入 `role='viewer'` 被拒
  - 重写后的 12 例**逐条与迁移前相同**，只除了**一处有意改变**：`browse` 比今天的 `viewer` 多出**作者面读**（详情 / 正文 / 文件，[ADR 0051](../../decisions/0051-the-author-plane-serves-by-tier.md)）。另有一条**必须保持的边界**：`write` 仍是「提交 + 丢弃自己的草稿」、**不含**上线能力。两样都要单列成断言，不能算作翻转；**旧词被拒是另加的一组契约断言**——旧词今天合法、本版起 `400`，它不属于这 12 例的能力对比
- **判定**：通过／失败
- **说明**：这条**不是常规 IT**（常规 IT 从空库跑起，复现不出「迁移前」），是一次性的一次验证。跑法与结果写进 §结果。

### T4 · 三种可见性选择的读边界

- **前置**：A 有 `a/pdf-tools`（已上线），D 是**与它毫无关系**的账号（没被授过任何档）。
- **步骤**：把可见性依次设成三种选择（私有、公开 · 调用、公开 · 浏览），每种选择用 D 的凭据把读路径全跑一遍，并试写。
- **期望**：
  - `私有`：D 在**所有**读路径上都是 404（与今天相同），搜索里搜不到
  - `公开 · 调用`：D 能 invoke、能 `/metadata`、能按路径取单个文件（**路径点名即可**）；`/versions` 200（只列 `published`）；控制台打开时是「信息」与「版本」两栏、**版本栏无草稿**；**API 详情 403**（拿不到清单）；搜索**搜得到**；**写一律 403**
  - `公开 · 浏览`：上面全部 + **API 详情 200（含清单）** + **控制台的详情 / 正文 / 文件栏打得开**（`公开 · 调用` 那一档打开同一页时只有「信息」与「版本」两栏，见 [ADR 0051](../../decisions/0051-the-author-plane-serves-by-tier.md) §决定 2a）
  - 三种选择下 D 的**写操作一律被拒**（提交版本、丢弃、上线、改可见性、授权、删除、恢复）
- **判定**：通过／失败
- **注意**：`公开 · 调用` 那一档的「API 详情 403」与「搜索搜得到」**同时成立**——这两条看起来矛盾，其实是同一件事的两面（够得到这个 skill，够不到它的目录）。这一格做错最容易。

### T5 · 删除是所有者独有的（收紧的那条边界）

- **前置**：B 被授 `管理`；B 名下的凭据齐全（会话 + `skills:write` 的 API key + CLI 登录态）。
- **步骤**：B 用三种凭据分别试删除。
- **期望**：**三种都失败**——网页面上没有那个按钮、直接打接口 403；`DELETE /api/v1/skills/{ns}/{name}` **404（路由不存在）**；CLI 没有这个命令。
- **判定**：通过／失败
- **连带**：A（所有者）自己删得掉——所以这个用例验的是**边界存在**，不是「删不了」。成功的那次留一条删除审计（actor、动作、目标对得上）。

### T6 · 可见性与授权取较高的一档

- **前置**：A 把 skill 设成 `公开 · 调用`；B 被授 `写入`；C 被授 `调用`。
- **步骤**：B 与 C 各跑一遍读路径与写路径。
- **期望**：
  - B 拿到的是 **`写入`**（授权比公开高）：能提交版本，**且**能拿详情（因为 `write > browse > invoke`）
  - 把可见性改成 `公开 · 浏览` 之后，C 拿到的是 **`浏览`**（公开比授权高）：能拿清单了，但**仍然不能提交版本**
  - 两次都不发生「谁覆盖谁」——B 的档位不因公开而变，C 的授权行不因公开而消失（**A** 用 `…/grants` 查，B 与 C 都够不到这条路由；那一行还在）
- **判定**：通过／失败

### T7 · 改可见性要「管理」档

- **前置**：B 被授 `写入`，C 被授 `维护`，D 被授 `管理`。
- **步骤**：三人各试一次改可见性。
- **期望**：B 与 C 都是 **403**（`维护` 不够——梯子给「维护」的是上线与丢弃别人的草稿，不含可见性）；D 是 200。
- **判定**：通过／失败

### T8 · 删除的入口与后果

- **前置**：A 拥有 `a/pdf-tools`，控制台打开着。
- **步骤**：点删除，观察就地出现的确认；**先取消**，再点一次并确认。
- **期望**：确认**先写后果**（「删除后，该名称将无法用于创建新 skill，当前地址立即失效。」），两个答案各自说清去向，不写「确定吗」（`design/voice-spec.md` §不可逆动作的确认）；取消之后动作与后果都回到原位；确认之后跳到「已删除」那一份（`?page=skills&show=deleted`），它在里面可以恢复，「在用」那一份里不再有它。
- **判定**：通过／失败
- **视觉那一半由人做**：这一处是新画的界面，出图 + 打开给用户看（SOP §五）。

### T9 · 删除之后地址失效，而它还能被找回来

- **前置**：同 T8 已删。
- **步骤**：① 用消费面与作者面分别读那个地址；② 从那个 404 页点「查看已删除的 skill」，应当落到**已删除**那一份列表；③ 点恢复。
- **期望**：① **两面都是 404**，且与「从来没有过这个 skill」给**同一个答案**（同一个错误码、同一句话）；② 它出现在已删除那一份列表里（且**只出现在我拥有的**那一份里——别人看不到）；③ 恢复之后地址立刻可用，**版本、当前指针、授权、可见性原样回来**（删除没有动过它们），并留一条恢复审计
- **判定**：通过／失败

### T10 · 恢复要重新问一遍所有权

- **前置**：同 T9，`a/pdf-tools` 已删；B 被授过 `管理`。
- **步骤**：B 试恢复。
- **期望**：403（甚至看不到它——已删除列表只列我拥有的）。**恢复的能力不随授权走**，与删除对称。
- **判定**：通过／失败

### T11 · 删除不释放名字

- **前置**：`a/pdf-tools` 已删。
- **步骤**：提交一份同名的新 skill。
- **期望**：**明确拒绝**（`400 invalid_request`），不是静默复活、也不是建出第二个。恢复之后那个名字仍然是**原来那一个** skill（版本与授权都还是旧的）。
- **判定**：通过／失败

### T12 · 「已删除」那一份只看得到自己的

- **前置**：A 与 B 各有已删的 skill；A 被授过 B 的某个**活着**的 skill 的 `维护` 档。
- **步骤**：A 打开已删除那一份。
- **期望**：只列出 **A 自己拥有的**已删的；B 的不出现。（对照：默认的 `live` 那一份里，A 能看到 B 授给他的那一个——两份的可见范围**故意不同**，因为恢复是所有者独有的。）
- **判定**：通过／失败

### T13 · 申请一档：申请本身不授权，批准才授权

- **前置**：A 拥有 `a/pdf-tools`，可见性 **公开 · 调用**。B 是看得见它的人（被它覆盖）；D 是够不到它的人——**第 2 步之前把可见性改回私有**，这样 D 才够不到它。
- **步骤**：
  1. B `POST …/access-requests` 体 `{"rung": "write"}` → **201**。然后用 B 的凭据把 T1 里 `调用` 的那几格再跑一遍（应全部通过）；`浏览` 的那几格再跑一遍——**API 详情仍 403**，控制台仍只显示「信息」与「版本」，详情 / 正文 / 文件栏不渲染。
  1b. 另一个账号 C 先被授 `写入`，再申请 `维护` → **201**；批准前他的能力仍是 `写入` 那一档（**申请更高的一档不会让他越过当前档**）。随后 C 再发一次 `{"rung": "write"}` → **400**（不高于当前实际档位的申请被拒，且**不改动**已有的 `维护` 申请——先校验、后写入），再撤回 `维护` 那条（`DELETE …/access-requests/me`），后面那一步的列表里只剩 B 那一条。
  2. D 对同一个（私有）skill `POST …/access-requests` → **404**。
  3. A `GET …/access-requests` → 恰好一条，`requester` = B、`wanted_role` = `write`。
  4. A `POST …/access-requests/{B}/approve` 体 `{"rung": "maintain"}` → **204**。B 现在按 `维护` 得到能力——**不是**他申请的 `写入`：批准的那一档说了算。
  5. 再来一遍：B 申请 `{"rung": "admin"}`（他此时是 `维护`，唯一更高的一档）、B `DELETE …/access-requests/me` → 撤回；A 的列表里没有它。
  6. 拒绝：B 再申请 `{"rung": "admin"}`、A `…/deny` → 申请消失，`skill_grant` 不变，B 的能力与申请前逐条相同。
  7. 重复提交：C 先申请 `{"rung": "maintain"}`、再申请 `{"rung": "admin"}` → `GET …/access-requests` 里 C 只有一条，`wanted_role` 是 `admin`（覆盖）；C 撤回。
  8. 最高档没有可申请的：A 把 B 提到 `管理`；B 再申请 `{"rung": "admin"}` → **400**（他已在最高可授档）。
- **期望**：第 1 步的复核是**这一步的全部意义**——申请存在时，B 的能力**一步也没多出去**（[ADR 0052](../../decisions/0052-a-request-is-not-a-grant.md) §决定 1）。第 2 步要的是「私有就是没人知道它在」：够不到的人连「可以申请」这个答案都拿不到。另外两条负向：被授 `维护` 的人 `GET …/access-requests` 与 `…/approve` 都是 **403**（看得见 skill，是这一档不够）；批准之后再批准同一个人 → 404（那条申请已经不在了）。申请、撤回、批准、拒绝各留一条审计（`audit` 里动作、目标与 actor 对得上；**每次**被接受的 `POST` 都记一条，重复提交也是又一次申请）。
- **判定**：通过／失败

## 环境与数据

- **环境怎么造**：沿用 v1 起就在的那套——`AbstractIT`（真端口 + 真库）、`AbstractAccountIT` 的 `Browser`（浏览器面）、failsafe 跑 `*IT`。测试库先 `scripts/init-test-db.sh`。
- **每个浏览器面 IT 要带 `@Sql("/sql/truncate-business-tables.sql")`**：本版新增了一张 `skill_access_request`。那个脚本靠 `TRUNCATE … RESTART IDENTITY CASCADE` 清子表（`skill_grant` 就是这样被清掉的），所以**不加也不会互相看见**；加一行只是把这张表显式写出来，可选。
- **数据**：四个账号——**所有者 A**、**被授权的两个 B 与 C**（分档位验能力时各拿一档）、以及**一个无关账号 D**（可见性用，从没被授过）；一个 skill、两个版本（一版已上线、一版草稿）。**全部靠接口造**，不手工插库——除 T3 那条迁移验证之外。
- **清理**：`@Sql` 清业务表之后互不可见；T3 那次一次性验证跑在一台**独立的、上限停在 V17** 的临时库上，跑完丢弃。
- **跑法**：`./mvnw -o verify -Dit.test=<IT>`（只跑改动那一处；全量回归由用户指令触发）。

## 已知问题

**本版尚未实现，所以还没有本版范围内的缺陷。** 下面记的是**实现时已知会踩的三处**，留在这里提醒，不当作缺陷计数：

### 001 · 公开档进谓词时漏一处会造出「搜得到但打不开」

`路径:行号`——`SkillRepository.permitted()`（单条读）与 `SkillCatalogRepository` 的搜索 `page`，**两处**都要认公开档（作者面 `authorPage` 不认——它问的是「我能以作者身份参与哪些 skill」，见 [ADR 0051](../../decisions/0051-the-author-plane-serves-by-tier.md) §决定 3）。改了一处漏一处时，症状是**列表里有它、点进去 404**，而两边的测试各自都是绿的。

**状态：未验证**（尚未实现；这一条是设计期识别出的实现风险，不是跑出来过的事实）。

### 002 · 作者面的读漏了按档位滤草稿

`路径:行号`——详情端点降到 `browse` 之后，响应的版本列表**必须**按档位把 `draft` 的行滤掉（[ADR 0051](../../decisions/0051-the-author-plane-serves-by-tier.md)）。漏了呢，`浏览` 档的人看到的是**还没上线的内容的版本号与说明**，而它们与已上线的那几行**格式完全一样**——同一个列表、同一个字段、同样的排法，看起来就是一个正常的版本列表。

**状态：未验证**（尚未实现；设计期识别出的实现风险）。

### 003 · 「浏览」档打开一个还没上线过的 skill 时页面是空的

一个够得到、但还没上线过任何版本的 skill（版本全是草稿或被丢弃），`浏览` 档的人打开那一屏会看到一个**空的文件树**——而同一个 skill 在消费面是 404。两个答案不一样，而那个不一样**是对的**（他确实够得到它，只是里面还没有公开的东西），但它要对得上文案，否则读起来像出了错。

**状态：未验证**（尚未实现；[ADR 0051](../../decisions/0051-the-author-plane-serves-by-tier.md) §后果 末尾点名了它，要一次文案决定）。
