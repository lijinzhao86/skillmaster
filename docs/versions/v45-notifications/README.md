# v45-notifications · 平台通知底座与共享确认

> **最后更新**：2026-11-04
> **状态**：进行中（P0 服务端 / P1 控制台 / P2 CLI 已实现，待视觉与端到端验收）
> **含收费**：否

## 目标

给平台加上通知能力：平台消息、共享邀请、权限申请与申请结果都落在同一个站内通知面；共享从「即时授权」改为「邀请—接受」。细节见 [`prd.md`](prd.md)。

## 验收标准

十九条验收（A1–A19），摘要其中七条：共享后 B 接受前权限不变；控制台与 CLI 都能接受 / 拒绝邀请；已读不等于已处理；处理完的通知留档；铃铛点击展开快速查看、仅悬停不打开；「查看」按结果分流、有去向的行整行可点；CLI 能带 `--yes` 批准 / 拒绝申请。完整验收见 [`prd.md`](prd.md) §验收与指标。

**成立条件**：A1（共享后权限不变）、A2 / A3（控制台与 CLI 都能处理邀请）、A6（已读不等于已处理）、A14（处理完留档）、A19（CLI 能批准 / 拒绝申请）不满足就不算交付——这六条就是「共享要确认」「通知只是指针」「操作要留档」「CLI 也要能把申请答完」四件事本身。

## 这一版明确不做什么

- **平台公告的发布入口** —— 本版只留底座，后续直接在它上面加发布面。
- **邮件、短信、推送与实时通道** —— 第一版只做站内，把底座与交互做对。
- **在控制台通知行里直接批准 / 拒绝权限申请** —— 通知行用「去处理」把人带到协作者页那一屏；CLI 另有 `notifications approve / deny`（[ADR 0140](../../decisions/0140-cli-can-approve-access-requests.md)），两边调用同一条用例。

完整范围与每条的理由在 [`prd.md`](prd.md) §范围。

## 影响最大的未决问题

完整列表见 [`technical-design.md`](technical-design.md) §开放问题。按重要性排前三条：

1. **`administeredSkillIds` 的规模**：直接作为查询参数传到多大要换？当前倾向：先直接传，超过 1000 再改。
2. **只读密钥不能标已读 / 接受 / 拒绝**：这是按方法 scope 的直接结果，还是需要一条新的 scope 规则？当前倾向：接受现状，CLI 帮助先写清楚。
3. **公告的扇出**：用户量变大后仍物化收件人行，还是改成读时懒建？当前倾向：本版物化；十万级时另开 ADR。
