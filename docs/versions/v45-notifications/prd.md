# v45-notifications · 产品需求

> **最后更新**：2026-11-04
> **所属版本**：[`README.md`](README.md)

## 用户与场景

**谁在用**：

- **A**：一个 skill 的所有者，或持有 `管理` 档的协作者。他能批准别人要权限的申请，也能把 skill 共享给别人。
- **B**：被 A 共享的人，或向 A 申请权限的人。今天他被动地拿到权限，或者申请之后石沉大海。
- **平台运营者**：需要向所有账号发布一条消息的人。本版只为这件事留底座，不提供发布入口。

**在什么场景下用**：

- A 在聊天里说「我把 skill 共享给你了」。B 不知道产品里该去哪确认，权限却已经生效。
- B 想给这个 skill 提交一版，在 skill 页申请 `写入`。A 三天后打开那个 skill 才看到待批数字。
- 平台要告知一次维护或规则变化。今天只能发在站外，产品里没有任何入口。

**现在的替代做法是什么**：

- **共享即授权**：`skill_grant` 一写就生效，B 没有知情、也没有拒绝的机会。A 也不知道 B 有没有用上。
- **申请靠数字标**：A 只有打开那个 skill 的页面，才在「设置 › 协作者」看到待批数量；没有全局入口，也没有任何主动提示。
- **公告靠站外**：群聊、邮件或口头，产品里没有渠道。

**为什么现在做**：[ADR 0052](../../decisions/0052-a-request-is-not-a-grant.md) §决定 4 已经把通知面写成「将来」的挂载点，并明确「它挂在这同一个对象上，不改变这个模型」。而共享要改成「先确认」，就必须要有一个「告诉 B」并且「让 B 答」的地方——这两件事都落在通知底座上。

## 范围

### 做

| # | 做什么 | 交付形态 |
|---|---|---|
| 1 | **通知底座**：一条通知记录「谁对什么做了什么」；收件人各自持有已读状态。支持**定向**（一个或多个收件人）与**广播**（正文存一份，每个收件人一条已读状态）两种形状。请求型通知只是业务对象的指针——邀请、申请的真实状态仍在它们自己的表里。事情处理完之后通知**留档**，记下结果（已接受 / 已拒绝 / 已过期 / 已撤销 / 已批准 / 未通过 / 已撤回），列表可按「待处理 / 全部」筛选 | 服务端 + 迁移 |
| 2 | **共享改为邀请制**：A 共享只产生一条待接受邀请，不产生授权；B 接受才落 `skill_grant`，拒绝则邀请行消失、什么也不发生，通知留档为「已拒绝」。**邀请 30 天后失效**：过期后不能再接受，A 可以重新共享。同一收件人同一 skill 最多一条**待接受**邀请，再次共享更新目标档位。对方已有同级或更高授权时不产生邀请，直接回显现有档位 | 服务端 + 控制台 + CLI |
| 3 | **权限申请通知与结果回执**：B 申请时，给这个 skill 的**所有能批准这条申请的人**（所有者 + `管理` 档）各发一条通知；A 批准或拒绝后，B 收到一条结果通知（批准时说明最终档位），A 侧的通知变成带结果的留档 | 服务端 + 控制台 |
| 4 | **控制台通知中心**：顶栏铃铛 + 未读数；**点击铃铛展开快速查看**（最近 5 条待处理或未读，可直接接受 / 拒绝，底部「查看全部」）；通知列表（时间倒序、分页）；「待处理 / 全部」筛选；已处理的通知显示结果（已接受 / 已拒绝 / 已过期 / 已撤销 / 已批准 / 未通过 / 已撤回）；单条已读；全部已读。**去向按结果分流**：已接受 / 已批准 / 未通过 → 该 skill 详情页；已拒绝 / 已过期 / 已撤销 → 不出现「查看」；待处理申请 → 所在 skill 的「设置 › 协作者」；有去向的行整行可点。未读数显示封顶 `99+`；**窄屏（≤640px）不展开快速查看，铃铛直接进通知页** | 设计件 + 控制台 |
| 5 | **CLI**：列出（可按待处理 / 全部筛选）、查看、标记已读、全部已读；接受或拒绝共享邀请。通知与未读状态与控制台共用同一份服务端状态 | CLI |
| 6 | **协作者页显示待接受与已过期邀请**：A 在「设置 › 协作者」看得到谁还没接受、可以撤销，也看得到谁错过了 30 天；已生效、待接受、已过期分成三组显示。**已生效协作者的降档是直接动作**，升档仍走邀请 | 控制台 + CLI |
| 7 | **广播形底座**：数据形状与已读状态按广播实现，并用测试夹具造一条广播通知验证；本版**没有**发布入口 | 服务端 |

### 不做

| # | 不做什么 | 为什么 | 什么时候可能做 |
|---|---|---|---|
| 1 | **平台公告的发布入口**（控制台运营页或 CLI 命令） | 2026-11-04 与所有者对齐：本版只留底座，后续直接在它上面加发布面 | 下一版 |
| 2 | 邮件、短信、企业微信、浏览器推送 | 2026-11-04 定：第一版只做站内，先把底座与交互做对；外发通道是新建能力，不是开关 | 需要产品外触达时 |
| 3 | 实时推送（SSE / WebSocket） | 通知种类少、量小，进入页面拉取就够；长连接要处理重连、多端同步与网关超时 | 未读数成为高频刷新需求时 |
| 4 | 按用户、按类型的通知偏好开关 | 本版只有这四类通知（邀请、申请、申请结果、公告底座），且都是「与你有关」的事件；过早做开关会让底座多一层没人验证的配置 | 通知种类变多、出现打扰反馈时 |
| 5 | 通知本身的自动过期与清理 | 2026-11-04 定：通知要留档，用户才能回看自己过去做过什么；只有**邀请**按业务规则过期，通知不删 | 数据量上来，或隐私要求变化时 |
| 6 | 在**控制台通知行**里直接批准 / 拒绝权限申请 | 网页的决定界面比一行通知多两件事：看申请人当前档位、在批准前改档位；控制台的通知行用「去处理」把人带到那一屏。CLI 另有 `notifications approve / deny`（[ADR 0140](../../decisions/0140-cli-can-approve-access-requests.md)），两者调用同一条用例 | 控制台那一行要做成能改档位的完整决定时 |
| 7 | 存量授权的迁移或回收 | 邀请制只管新共享；升级前已经生效的 `skill_grant` 继续有效，B 不会突然失去权限 | 不适用 |
| 8 | 公告的富文本、图片、分类与已读统计报表 | 发布面还没有，正文形状跟着发布面一起定 | 做发布面时 |
| 9 | 免打扰时段、通知聚合摘要 | 通知量不足以证明需要；先观察真实打扰 | 通知量上来后 |
| 10 | 通知的删除（只做已读，不做单条删除） | 留档是这一版的明确要求；把历史从眼前删掉反而让用户更说不清自己做过什么 | 出现清理诉求时 |
| 11 | 自定义邀请有效期（7 天 / 90 天 / 不过期） | 本版固定 30 天；没有邮件提醒，选项越多越难解释，也不解决「过期后怎么通知到人」 | 出现真实的分档需求时 |

## 控制台操作与 CLI 对应

| 控制台操作 | CLI 命令 | 说明 |
|---|---|---|
| 看通知列表与未读数 | `skmr notifications [list] [--status attention\|pending\|all] [--unread] [--page <n>]` | 默认 `attention`（待处理 + 未读，与铃铛下拉同一份）；不带子命令等同 `list`。`pending` 只看要处理的；`all` 含已处理留档；`--unread` 只列未读。每条下面打印可复制的下一步命令 |
| 看一条通知的完整内容 | `skmr notifications show <id>` | 回执里给出对应 skill 地址与下一步命令 |
| 打开一条通知（查看 / 去处理） | `skmr notifications show <id>` | 控制台里打开时自动标为已读；CLI 的 `show` 只读、不自动标记 |
| 标记一条已读 | `skmr notifications read <id>` | 幂等；控制台里处理（接受 / 拒绝）或打开时也会标记 |
| 全部标记已读 | `skmr notifications read --all` | 只影响当前账号 |
| 接受共享邀请 | `skmr notifications accept <id>` | 成功回显拿到的档位 |
| 拒绝共享邀请 | `skmr notifications decline <id>` | 邀请行消失、不产生授权；通知留档为「已拒绝」 |
| 把 skill 共享给某人 | `skmr skill share <地址> --to <handle> [--role <档>]` | 同一动词，语义从「即时授权」变为「发出邀请」；回执说「等待对方接受，30 天后过期」，并给出下一步 `skmr skill shares <地址>`（A 的待接受名单）；对方在 `skmr notifications` 里接受 / 拒绝 |
| 撤销未接受的邀请 / 撤销已生效授权 | `skmr skill unshare <地址> --user <handle>` | A 侧的动作；两种情况都删掉那一行，回执说明删的是哪一种 |
| 看一个 skill 的授权名单（含待接受、已过期） | `skmr skill shares <地址>` | A 侧；已生效、待接受、已过期分组列出。**这里没有接受 / 拒绝**——那是收件人 B 在 `skmr notifications` 里的动作 |
| 改已生效协作者的档位 | `skmr skill role <地址> --user <handle> --role <档>` | 只降不升：降档直接生效并记审计；升档要用 `skmr skill share` 发邀请，对方接受后生效 |
| 批准 / 拒绝权限申请 | `skmr notifications approve <id> [--role <档>] --yes` / `skmr notifications deny <id> --yes` | `--yes` 必填；不带只打印后果与完整命令，不执行。批准默认按申请的那一档，`--role` 可改；控制台仍保留自己的决定界面，两边调用同一条用例（[ADR 0140](../../decisions/0140-cli-can-approve-access-requests.md)） |
| 发布平台公告 | **例外，本版没有这个操作** | 见「不做」第 1 条 |

**一个已知取舍**：CLI 的 `--yes` 可以由 agent 代填，因此 agent 能自动批准别人的申请。它不带来新能力（同一把 `admin` 密钥本来就能发出共享邀请），但「自动批准」比「自动邀请」更值得看审计；真正的边界是审计记录与密钥保管（[ADR 0140](../../decisions/0140-cli-can-approve-access-requests.md) §理由）。

## 验收与指标

### 验收标准

| # | 验收标准 | 怎么判定 |
|---|---|---|
| A1 | A 共享后、B 接受前，B 对该 skill 的权限**没有**变化：按可见性规则读不到、调用不了，`skill_grant` 里没有这一行 | 用一个私有 skill（或共享的档位高于公开档）验证：B 的凭据调用它、读授权名单，两处都按「未授权」处理；数据库里查不到对应 grant 行 |
| A2 | B 在控制台通知中心看到这条邀请；点「接受」后拿到目标档位，邀请从「待处理」筛选里消失、在「全部」里显示为已接受；点「拒绝」后邀请消失、不产生授权 | 两个账号、两条路径各走一遍；每步核对 B 的实际档位、A 侧的邀请列表与两个筛选 |
| A3 | B 能在 CLI 完成同样的接受与拒绝：`skmr notifications` 默认列「待处理 + 未读」，每条给出可复制的下一步命令；`accept` / `decline <id>` 成功，回执说清拿到的档位或「已拒绝」；A 的 `skmr skill share` 回执链到 `skmr skill shares <地址>`（待接受名单），A 侧没有接受 / 拒绝 | CLI 用例跑通；接受后 `skmr skill shares` 在 A 侧出现 B 的授权行；默认列表里既有待处理邀请也有未读结果 |
| A4 | B 申请某 skill 的权限后，该 skill 的所有者与每个 `管理` 档协作者各收到一条通知；没有批准权的人（`维护` 及以下）不收到 | 造三个账号（所有者、`管理`、`维护`），B 申请；核对三人的通知列表与未读数 |
| A5 | A 批准或拒绝后，A 侧的通知变成「已批准 / 未通过」留档；B 收到一条结果通知（批准时说明最终档位，可能与他申请的不同）；双方的未读数按各自规则变化 | 走批准与拒绝各一次；A、B 两边的通知列表与未读数前后各取一次 |
| A6 | **已读不等于已处理**：标记已读只改变未读数，邀请仍然待接受、申请仍然待批；业务对象处理完，通知变成带结果的留档，而不是消失 | 标记已读后核对业务状态；再处理业务对象，核对通知仍在、结果正确 |
| A7 | 广播型通知一条正文只存一份；每个收件人各自持有独立的已读状态与未读数，收件人再多也不复制正文 | 测试夹具造一条广播、两个收件人；A 读掉后 B 仍未读；数据库里正文只有一行 |
| A8 | 通知列表按时间倒序、可分页；未读数显示封顶 `99+`，实际数量仍可从接口读到 | 造 120 条未读，核对列表顺序、分页边界与显示值 |
| A9 | 升级前已生效的授权不受影响：存量 `skill_grant` 仍然生效，B 不会因为改成邀请制而失去权限 | 用迁移前的数据造一条 grant，升级后核对 B 仍能读、`skill shares` 仍列出 |
| A10 | 同一收件人对同一资源的**未处理**通知最多一条：重复申请、重复共享都不会产生多条 | 连续申请两次、连续共享两次，核对未处理通知条数仍为 1 |
| A11 | 失去处理权的人看不到、也点不动那条通知：A 不再是某 skill 的 `管理` 后，该 skill 的申请通知不再出现在他的列表里；直接请求那条通知返回 404，不泄露内容 | 改档后核对列表与单条读取 |
| A12 | 控制台与 CLI 的已读状态一致：在一边读掉，另一边下一次读取就是已读；未读数相同 | 控制台读掉 → CLI `list --unread` 不再出现；反向再走一次 |
| A13 | 所有离开页面的提醒都不依赖轮询之外的实时通道：进入通知中心或顶栏初始化时拉到最新状态 | 网络面板里没有 SSE / WebSocket；刷新页面后未读数正确 |
| A14 | 事情处理完之后通知**留档**：邀请被接受 / 拒绝 / 过期 / 撤回、申请被批准 / 拒绝 / 撤回后，那条通知仍在列表里，显示结果与时间；「待处理」筛选下不再出现，「全部」筛选下按时间倒序可见 | 每种结果各走一次，核对两个筛选下的出现与不出现 |
| A15 | 共享邀请在发出 **30 天**后失效：B 不能再接受（接受返回明确错误），A 侧显示「已过期」，A 可再次共享；过期在读取时按 `expires_at` 判定，不依赖后台任务 | 把一条邀请的 `expires_at` 调到当前时间之前，核对接受被拒、两边显示与重新共享 |
| A16 | 一方撤回也能收口：B 在 A 处理前撤回申请，A 侧那条通知变成「已撤回」；A 撤销一条待接受邀请，B 侧那条通知变成「已撤销」 | 两条路径各走一次，核对双方通知状态与业务对象都已消失 |
| A17 | **铃铛的快速查看**：点击展开最近 5 条待处理或未读；共享邀请可在行内接受 / 拒绝；底部「查看全部」进通知页；**正文最多两行**，过长的地址与公告截断、不撑破浮层，全文在通知页可读；Esc 关闭并把焦点还给铃铛，点外面也关；**仅悬停不打开**；≤640px 不展开、直接进通知页 | 鼠标点击、键盘 Enter、Esc、点外面、仅 hover、400px 各走一次；再用最长地址与最长公告各看一次截断与全文；核对关闭方式与焦点落点 |
| A18 | **「查看」按结果分流**：已接受 / 已批准 / 未通过 → 该 skill 详情页；已拒绝 / 已过期 / 已撤销 → **不出现「查看」、整行也不可点**；待处理申请 → 所在 skill 的「设置 › 协作者」；有去向的行**整行可点**（Enter / Space 同效），行内按钮不触发整行；公告本版没有动作 | 逐个结果状态点行与按钮，核对落地页与是否有可点样式；用键盘走一遍整行；已拒绝 / 已过期 / 已撤销三种核对没有「查看」、没有悬停手型 |
| A19 | **CLI 能批准 / 拒绝申请**：`skmr notifications approve <id> [--role <档>] --yes` / `deny <id> --yes`；不带 `--yes` 不执行、只打印后果与完整命令；批准默认按申请的那一档，`--role` 可改；批准 / 拒绝后 A 侧通知收口、B 收到结果回执、审计记下两档，与控制台一致 | CLI 走批准与拒绝各一次，与控制台同一申请的结果对比；不带 `--yes` 时核对退出码非 0 且数据库没有变化；只读密钥调用得 403 |

**成立条件**：A1、A2、A3、A6、A14、A19 不满足就不算交付——这一版的目的就是「共享要确认」「通知只是指针」「操作要留档」与「CLI 也要能把申请答完」；A7 不满足说明广播底座没有真的成立，后续公告面会返工。

### 指标

| 指标 | 定义 | 怎么量 | 目标 |
|---|---|---|---|
| 同一收件人同一资源的未处理通知数 | 按收件人 + 业务对象分组，统计未处理通知条数 | 数据库查询；用例 A10 同时断言 | ≤ 1 |
| 通知列表与未读数的一致性 | `list --unread` 的条数与未读计数接口的返回值 | 用例 A12 的两次核对 | 100% 一致 |

## 依赖与前置

- **已定的决策**：[ADR 0052](../../decisions/0052-a-request-is-not-a-grant.md) §决定 4 给出通知的挂载点；[ADR 0073](../../decisions/0073-asking-for-access-splits-by-plane.md) 的批准 / 拒绝只在网页这一半由 [ADR 0140](../../decisions/0140-cli-can-approve-access-requests.md) 取代——CLI 也能批准 / 拒绝，`--yes` 必填；待批列表仍在网页。共享从即时授权改为邀请，由 [ADR 0138](../../decisions/0138-sharing-is-an-invitation.md) 记录；通知的边界由 [ADR 0139](../../decisions/0139-a-notification-points-at-a-business-object.md) 记录。
- **既有对象**：`skill_access_request` 已经是「申请不是授权」的独立对象，本版只给它加通知，不改它的形状；共享需要新增一个与它对称的邀请对象，而不是给 `skill_grant` 加状态列。邀请的 30 天有效期按行上的 `expires_at` 判定，不引入状态列，也不依赖后台任务。
- **留档与业务状态的关系**：通知记录结果，但业务对象仍是权威——邀请是否还能接受看邀请行与它的 `expires_at`，申请是否还待批看申请行；通知的「已处理」只是展示层对结果的快照。
- **迁移**：`skill_grant` 与 `skill_access_request` 都已存在；本版新增通知与邀请两类表，迁移号从 `V34` 起（`V33` 已被活动分支 `feat/cli-read-write-contract` 占用，合并前须再核一次）。
- **设计前置**：控制台顶栏与通知中心必须先在 `design/` 出稿（第 2 关），再改控制台实现。
- **并行前置**：CLI 的命令声明与分发表与 `feat/cli-read-write-contract` 相交；那一段等它合入后 rebase，或基于它做栈式分支。
