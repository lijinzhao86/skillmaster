# v57-draft-loop · 产品需求

> **最后更新**：2026-11-10
> **所属版本**：[`README.md`](README.md)

## 用户与场景

**谁在用**：写 skill 的人，以及替人改 skill 的 agent（Moss、Claude Code 这类）。他们本机有改好的文件，要在草稿上整份覆盖；改完还想在发布前把脚本真跑一遍。

**在什么场景下用**：一轮审计或修复下来，同一份草稿里有多个文件要换掉——2026-11-09 的实录是 3 个脚本 + `SKILL.md` + 2 个 references，共 6 个；以及改完之后要执行 `skmr run <地址>@<版本> -- python3 scripts/… <参数>`，确认它真的能跑，而不是「看着对」。

**现在的替代做法是什么**：

- 批量覆盖只能 read→write 严格交替 N 轮。**一条命令带多个 `--from` 也不成**：每传完一个文件，整版摘要就变一次，其余文件的读凭证随之作废，从第 2 个起连环被拒。实录是 3 轮才把 6 个文件传上去，脚本化上传完全做不了。
- 草稿不能 run。`skmr run <地址>@<版本码>` 被服务端 400 挡下（`X-Skill-Version must be a version name or a sha256: digest`），只能先发布再测、测出问题再发一版。本次 bilibili 草稿里一行必崩的 bug 就是这么漏出去的——打包进 skill 的脚本从未被执行过。

## 范围

### 做

| # | 做什么 | 交付形态 |
|---|---|---|
| 1 | `write --overwrite` 的读凭证改绑**文件自身的 sha256**：写过别的文件不作废本文件的凭证 | CLI（`read_proof.go`、`internal/pins/reads.go`） |
| 2 | 一条命令的多个 `--from`、以及循环写，在「每个被覆盖的文件都读过」之后一次过 | CLI（`write_local.go`、`files_write.go`） |
| 3 | `skmr run` 接受草稿版本码：公开面不认的 pin（含本机记住的草稿码）改由作者面解析 digest | CLI（`run.go`；复用既有的 `api.Client.ReadAuthorVersion`，`author.go` 不改） |
| 4 | 服务端 400 原文（`X-Skill-Version must be…`）换成中文句子并给下一步 | CLI |
| 5 | `skill write --help` 与真实放行条件一致（不再写「整版摘要」） | CLI 帮助 |
| 6 | 批量写入中途失败时，报出**已写入 / 失败 / 未开始**三组文件与原因，并提示「修好后重跑同一条命令」；重跑真的能补齐。上传成功但读不回新清单时另报「已上传、基线未知」并给出先读它的命令。写前另有两条校验：目标已存在而没带 `--overwrite`、两个 `--from` 落到同一远端路径 | CLI（`write_local.go` 的失败路径） |

### 不做

| # | 不做什么 | 为什么 | 什么时候可能做 |
|---|---|---|---|
| 1 | 不做 `--force` / 跳过读检查 | [ADR 0136](../../decisions/0136-cli-file-verbs-follow-intent.md) 定过：把「读过」当许可证，比再加一个确认开关更接近「知道自己在覆盖什么」 | 不做 |
| 2 | 不做整批原子落盘（第 3 个失败时，前 2 个保留）；改为报出已写入 / 失败 / 未开始的清单，修好后重跑同一条命令 | 服务端是逐文件 PUT，没有跨文件事务；补偿删除违反 [ADR 0101](../../decisions/0101-the-cli-never-deletes-files.md)。凭证让重跑不必重新读，但重跑仍会把每个文件按同样内容重放一遍（PUT 幂等），比「假装原子」便宜 | 服务端出现批量事务时 |
| 3 | 不改 `read` 的默认输出（行号 + 末尾注记仍是默认） | `--raw` 已经有了；改默认会打断所有在读这块输出的脚本 | 不做 |
| 4 | 不让作者以外的人 run 草稿 | 草稿只有作者可见，授权仍由作者面回答；CLI 不另造一套可见性 | 不做 |
| 5 | 不改服务端、不加新路由 | 作者面已经认版本码（实测 `skmr skill get <地址>@JD0T518T --all` 成功，整版 ETag 就是草稿 digest） | 不做 |
| 6 | 不修 guide 的教学漂移 | 属于另一个交付单元（已发布 skill 的内容），细节记在 [`docs/current/TODO.md`](../../current/TODO.md) 的「guide 的教学落后 v44 后的 CLI」 | 下一次改 guide 时 |
| 7 | 不给 `run` 加依赖安装，也不放宽沙箱判断 | v51 已明确不做（[ADR 0167](../../decisions/0167-sandbox-compatibility-is-capability-based.md)） | 不做 |

## 验收与指标

### 验收标准

| # | 验收标准 | 怎么判定 |
|---|---|---|
| A1 | 同一草稿上先读完 3 个已存在的文件，再用一条命令带 6 个 `--from`（3 个覆盖 + 3 个新建）→ 全部成功，中途不必补读 | CLI 集成测试 |
| A2 | 写过文件 A 之后，之前读过的 B 仍可覆盖，不报「这一版变过」 | 单元 + 集成测试 |
| A3 | B 在读过之后、覆盖之前于服务端被改过（其 sha256 变了）→ B 的覆盖被拒，报错指认是 B 变了。`read` 记账本身与「取字节」之间的窄竞态不在本版保证内，见 test-plan §已知问题 | 集成测试 |
| A4 | 没读过的文件仍被拒；除 `--overwrite` + 读凭证外没有绕过路径 | 单元测试 |
| A5 | 草稿版本码 + `run` 能取到并执行 `scripts/` 下的脚本，首次执行仍有 `--yes` 确认 | 集成测试（草稿 archive 里的脚本真的被执行） |
| A6 | 同一 digest 第二次 run 不再问；内容不变时发布后命中同一缓存目录 | 集成测试 |
| A7 | 上述路径不再出现 `X-Skill-Version` 原文；报错给下一步命令 | 集成测试断言 stderr |
| A8 | `skmr skill write --help` 与真实放行条件一致，不再写「整版摘要」 | help 一致性测试 |
| A9 | 一条命令 6 个文件、第 3 个因服务端报错失败：stderr 列出已写入的 2 个、被拒的 1 个及原因、未开始的 3 个；按提示重跑同一条命令后 6 个全部落盘 | 集成测试 |

**成立条件**：A1 与 A5 是「不满足就不算交付」——它们正是这次要修的两条断点。

### 指标

| 指标 | 定义 | 怎么量 | 目标 |
|---|---|---|---|
| 批量覆盖的命令数 | 同一草稿、3 个已存在文件要覆盖、3 个新文件；从「读过」到全部写完需要的命令条数 | 按 §用户与场景 的场景计一遍 | 现在 12 条（6 read + 6 write，且要交替），目标 4 条（3 read + 1 write） |
