## 用户与场景

**谁在用**：从站点安装 SkillMaster 的人，以及替他执行安装的 agent。

**在什么场景下用**：安装说明的第一步是下载 [`skillmaster.tgz`](../../../skillmaster-site/public/install/skillmaster.md)，解开后 agent 读到的就是包里的那一个 `SKILL.md`。这份正文决定了它之后每一次「先查 skill、再 `invoke`」的行为——它不是说明文档，是 agent 照着执行的操作规范。

**现在的替代做法是什么**：作者本机的 `~/.claude/skills/skillmaster` 是一份手工维护的版本，已经和仓库、线上包分叉。同一个人换一台机器、或把安装说明发给别人，拿到的就是另一套指令；而本机那份「好用」不会出现在任何地方的证据里。

**为什么还要做**：仓库里的 `skills/skillmaster/` 是技能包的源；本机副本与发布包都是它的产物。否则「我本机好用、别人装的不好用」只能靠对比两份文件才能定位。**从 v42 起，源在仓库**；本机副本是部署产物，不再反向当参考。

## 依赖与前置

- **外部依赖**：站点部署需要人工触发 `workflow_dispatch`（[`site.yml`](../../../.github/workflows/site.yml) 的 deploy 只在手动触发时跑）；合并本身只跑检查、不上线。
- **内部前提**：包形状由 [`site.yml`](../../../.github/workflows/site.yml) 的三处断言与安装文档共同钉住；本版把两边的数一起改成 1。
- **一个本版不产出、但正文依赖的东西**：本地 `SKILL.md` 把读 / 写 / 改 / 管理等操作的说明指到公开技能 `skillmaster/skillmaster-guide`。**那个技能由技能主人在平台上发布，本版不创建也不发布它**；它不存在时，`invoke` 会失败，agent 只剩 `skmr help` 与现场报错。上线顺序必须是**先发指南技能，再发本包**。
- **排除了什么前置**：不需要服务端、控制台、CLI 改动，也不需要设计稿；全局版来源是用户本机的 `~/.claude/skills/skillmaster`，一次迁移进仓库后，仓库就是源；本机副本的同步不在 repo 验收里。
