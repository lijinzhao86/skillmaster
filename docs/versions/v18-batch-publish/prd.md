# v18-batch-publish · PRD

## 用户与场景

**谁**：有多个 skill 的作者——尤其是手上同时躺着几份草稿的人。

**什么时候**：

- 一次改了好几个 skill，每个都提交了一份新草稿，等着发布。
- 攒了一批，各自躺在自己的 skill 页里，没有一处能把它们摆在一起看。
- 刚从别处搬来几十个 skill，一份都还没发布过。

**他要什么**：把等着的草稿一起发出去，而不是逐个进 skill 页、逐个点、逐个填号、逐个确认。

**现在的替代做法**：进 skill 页 → 找到那份草稿 → 点发布 → **在弹窗里填一个版本号** → 确认。一个 skill 一趟。几十个 skill 就是几十趟，而且每一趟都要回忆起"上次发到几了"。

**这一版补的两件事**：

1. **版本类型取代填号。** 草稿可以带一个「这次改动是主版本 / 次版本 / 修订」的声明，号在发布那一刻按当前线上版本算出来。写的人知道量级，发布的人不必记得数字。
2. **一处待上线队列。** 把「有哪些草稿在等我发」变成一个看得完、处理得完的地方。

## 范围

### 界面上的词（2026-10-25 定）

这一版新增的那一页，界面上**不叫「发布」**：

| 概念 | 界面上 | 代码 / 接口 / ADR 里 |
|---|---|---|
| 那一页（导航项与页标题） | **待上线** | 路由 `/publish` |
| 那个动作（按钮、确认单、预演句） | **上线** | `publish` |
| `release_type`（主版本 / 次版本 / 修订） | **版本类型** | `release_type`、CLI `--release` |

理由写在 [`design/voice-spec.md`](../../../design/voice-spec.md) §三：「发布」2026-10-16 就已经被从界面词表里请出去（skill 页与其余各处同一个动作写的是「上线」），而这一页最初是为"将来的批量操作"留的家——可见性与授权是 **skill 自己的属性**，归「我的 skill」的多选动作条，不归这张草稿单子，所以这个理由不成立。**本文档下文沿用「发布」指同一个系统动作**，与 ADR 0031 / 0090 / 0091 的原话一致；引号里的是界面原文，一律用上表左列的词。

### 做

| # | 做什么 | 交付形态 |
|---|---|---|
| 1 | **版本类型**：草稿多一个可选属性 `release_type`——主版本 / 次版本 / 修订（`major` / `minor` / `patch`）。提交时可以给，草稿期可以改、可以清空，发布后冻结。**不给就是空——不继承同一个 skill 上一次提交的类型，也不从任何地方推断**（[ADR 0091](../../decisions/0091-release-type-decides-the-version-number.md)） | 服务端（V29 迁移）+ CLI + 控制台 |
| 2 | **发布时算号**：号有三个来源，**先看前两个**——① **草稿自己已经带着号**（今天的提交路径对草稿一律写 `NULL`，所以这类行只能由直接改库造出，T22 就是这么造的）：沿用它，请求里另给一个不同的号就是 400 `version_name_is_assigned`；② **请求里给了显式版本号**就用它（预发布 `1.0.0-rc.1`、"我就要钉这个号"走这条）；③ 两个都没有，则按类型与**当前线上版本**算——主 `X+1.0.0`、次 `X.Y+1.0`、修订 `X.Y.Z+1`。**从未发布过的一律 `1.0.0`**，类型不参与；**基线不可用时类型不可用**——当前版本带预发布标记、没有号（空）、或根本不是合法 semver，都必须显式给号；算出来撞上已有版本 → 这一条失败，**不顺延** | 服务端 |
| 3 | **CLI 入口**：提交时 `--release major\|minor\|patch`（可选）；改草稿类型 `skillmaster version release-type <地址> <major\|minor\|patch\|none>`。**权限是 `write`**——能提交草稿的人就能声明这次改动多大；`maintain` 管的是发布、回滚、丢弃别人的草稿 | CLI |
| 4 | **控制台预演**：队列里每份草稿显示「将以 `1.3.0` 上线（次版本）」——基线在本组的表头那一格（只有一份的 skill 则在它自己那一行），不再重复写进那句话。队列里**那个号本身可点**，点开换一档、号立刻重算并写回服务端；首次上线那一行（写死 `1.0.0`）点不动。**预演不是承诺**（见 #8） | 控制台 |
| 5 | **待上线队列**：**一行一份草稿**，同一个 skill 的多份草稿归在它下面（攒了两份以上才有那一行表头，只有一份的仍是一行）。每行给 **版本名称**、提交时间、这一份上线后会是多少号；**skill 名在名字那一格，当前线上版本在状态那一格**（表头行是这样；只有一份草稿的 skill 没有表头，那一行自己就是这么写的。子行的状态格是空的——同一个 skill 的线上版本已经在表头说过了，每行再说一遍是把同一个事实说三次）。线上版本那一格有两种「没有」，**它们是两件事**：从没上线过写「从未上线」；上线过、但那一版没有版本号（V11 加了这一列却没回填，而今天的提交路径一律写 `NULL`——这类行只能靠直接改库造出来）写 `—`。同理，v6 之前没有 `draft_name` 的草稿没有名字，那一格写「未命名」——名字缺不影响能不能发；按最新提交排在前。**只列我够得着上线的 skill**（档位是 `owner` / `maintain` / `admin`）——`invoke` / `browse` / `write` 的 skill 不进来。**圈定它的是权限，不是作者**：别人提交到我能发布的 skill 上的草稿，照样进我的队列（`maintain` 的人该知道自己欠着哪一份）。**已删除的 skill 不进队列**——它的草稿发不出去，摆一行只会让人点一次没有结果的确认。**按命名空间分开看**：页头一个单选的命名空间（没有"全部"），一次只看、只发一个；每个选项后面跟着它自己的待发份数。**从未上线过的与「已上线又有新草稿」的都在里面**——后者才是日常里最常见的那种。页头有**搜索**（skill 名或版本名称）与**按草稿状态的筛选**（全部 / 缺少版本类型 / 有多份草稿）——队列最多 500 个 skill，找"卡住我的那几条"不能靠一屏屏翻 | 控制台（新页面） |
| 6 | **多选与全选**：勾选若干行，底部说出「已选 N 份」。**没有类型、又需要类型才能算号的行，先选一档才能勾**；选完立刻写回服务端，不是客户端状态——否则 CLI 与控制台各说一套。**全选取每个 skill 最新提交的那一份**：多份草稿的 skill 只勾最新那份（整行染色，可以在行上换）；**已经选过的不覆盖**。**缺版本类型的行在选档之前勾不上，选了就能勾**；**基线不可用的那两种（基线是预发布、线上那一版没有号或不是一个版本）根本勾不上**——不只是不进全选，手动也勾不了，行上各写各缺什么。动作条说清全选做了什么——「已选 4 份 · 2 个 skill 取最新草稿、2 份未指定版本类型」。**一批里同一个 skill 只能发一份**：页面上第二份勾不上；服务端对同一批里重复的 skill 整批拒绝（`duplicate_target`） | 控制台 + 服务端 |
| 7 | **一次确认**：点「上线所选」弹出一张单子，**逐行**写「skill · 版本名称 → 将要上线的版本号」（一行是一份草稿，草稿名称是这一行的身份——skill 名相同也要看清是哪一份草稿）；确认后一次提交（[ADR 0090](../../decisions/0090-batch-publish-confirms-once.md)） | 控制台 + 服务端 |
| 8 | **逐条结果**：成功与失败分开报，失败的写清原因；成功的行离开队列，失败的留下，可以再点一次只发剩下的。**号以发布那一刻算出的为准**——与确认单上的预演不同（撞号、或有人抢先发布了更高版本）必须说出来，不能悄悄换一个号让人以为发的是别的。发布走的是同一个发布动作，agent 下一次 `skills list` 就能看到这些 skill | 控制台 + 服务端 |
| 9 | **执行与结算**：确认之后**确认单不关**，就地变成执行单——一行一条地落定（成功的写上实际号，失败的写上原因），标题下一行是「已落地的条数 / 总数」的进度，**只数已经落地的，不按时间估**；**批次比弹窗高时，正在走的那一条始终被送到正中**，结算则回到第一条（这一屏的活从看它跑变成了看结果），单子自己滚、底边在下面还有时淡出去。走完停在结算：一句话说完成什么样（`3 份已上线，1 份失败`），只有一颗「完成」，**不自己关**。执行中不给取消（已经落定的不会回滚；见不做） | 控制台 + 服务端（逐条流式返回，见 TD §接口） |

### 不做

| 不做 | 原因 | 什么时候可能做 |
|---|---|---|
| 提交流程之外的"预分配版本号" | [ADR 0055](../../decisions/0055-drafts-have-a-required-name.md) 否掉过：草稿占号、丢弃烧号。`release_type` 不占号，这也是它与"预分配"的分界 | 不会——除非 ADR 0055 被取代 |
| 从预发布版本往上递增 | `1.0.0-rc.1` 往上是 `1.0.0` 还是 `2.0.0`，各家做法不同。基线带预发布标记时要求显式给号，比发明一套规则诚实 | 有人拿出一条能站住的通行规则时，另开一条 ADR |
| 批量丢弃草稿 | 丢弃一票不可反悔（ADR 0031 决定 5）。批量放行一个不可逆动作，与"省掉几十次相同判断"的理由正好相反——那几十次判断本来就不一样 | 不会；批量上线之所以可以，是因为它逐条成功或失败、每一步都能撤回——**已上线过的 skill 可以回滚到上一版；首次上线的那一份不行，只能把整个 skill 下线** |
| 批量下架 / 上架 | 是另一个动作（ADR 0058），没有被要求，也不该顺带做 | 有人提出来时单独设计，不搭这一版的车 |
| 定时 / 自动发布 | 发布要保持"人在场的一次动作"（ADR 0031）。定时等于让它脱离人在场 | 不会——这与 ADR 0031 的立场相同 |
| 跨账号批量 | **队列是权限面的**：只列我够得着发布的 skill（`owner` / `maintain` / `admin`）。别人共享给我、而我只到 `invoke` / `browse` / `write` 的 skill 不在队列里 | 不会；要为别人的 skill 发布，先拿到 `maintain` |
| 批量的 CLI 命令 | **例外 1（高风险）**：发布改变 agent 能读到什么，ADR 0031 规定它只在浏览器面，并明说「能跑 CLI 的人不该因此获得上线的权力」。按 [ADR 0081](../../decisions/0081-every-console-operation-has-a-cli-command.md) 记为例外；产品负责人 2026-10-25 确认 | ADR 0031 改主意的那一天。**读**不受影响：队列的读已经有 `skills pending` |
| 执行中「停止剩下的」 | 已经落定的那几条不会回滚（逐条各自一个事务），所以这个按钮能做的只是"不再发剩下的"——而它与「关闭页面」是同一件事 | 真有人一次发上百份时再回来做 |
| 结算里的「重试失败的」 | 失败的那一份**已经留在队列里**，队列就是重试的入口。再给一颗按钮，等于给同一个动作第二个入口 | 不会（voice-spec §四：同一个位置不出现两个同义动词） |
| 草稿页（单版页）的发布区块改成「声明类型 + 预演」 | v18 只把类型放进队列这一处。单版页今天仍是旧形态（选改动量级 → 预填一个号 → 可手改），改成新模型要动那一屏的操作栏，属于独立的一轮设计。**类型在队列行与 CLI 上都能改** | 下一版若还要改单版页，就一并换掉（2026-10-25 定） |
| 队列分页 | 作者面一次最多取 500 个 skill（队列读有自己的常量）。超过 500 的库本版不分页，**但要如实说**「只列出了最近 500 个 skill」 | 有人的库稳定超过 500 时；那时还要先想清"第 2 页失败、第 1 页已发"的呈现 |

## 验收与指标

### 版本类型

| # | 验收 | 怎么判定 |
|---|---|---|
| 1 | **CLI 提交时**可以给类型（网页与作者面这版不带，见 TD §提交），草稿期可以改，发布后冻结；**不给就是空** | `submit --release minor` 之后读回草稿，类型是 `minor`；再改成 `patch` 成功，`none` 能清空；发布之后改，被拒且给出原因。**另造一次：同一个 skill 再提交一份，不带 `--release` → 新草稿的类型是空，不是 `patch`** |
| 2 | 改类型的门槛是 `write`，不是 `maintain` | 一个有 `write`、但不是提交人的账号能改这份草稿的类型；只有 `browse` 的账号拿到 **404**——草稿对 `browse` 不可见，本仓库的规矩是"看不见就是不存在"，既有的 name / note 路由也这么答；同一个人**发不了**这份草稿（发布要 `maintain`，那是 403） |
| 3 | 已发布的 skill：按类型与当前线上版本算号 | 线上是 `1.2.3`，草稿 `minor` → 发布后是 `1.3.0`；另造 `major` → `2.0.0`，`patch` → `1.2.4`（各自独立造一次） |
| 4 | 从未发布过的一律 `1.0.0`，且不可选类型 | 一份从没发布过的 skill 的草稿，无论类型是空 / `major` / `patch`，发布后都是 `1.0.0`；界面上那一行不提供类型选择 |
| 5 | 显式版本号优先 | 草稿带 `minor`，发布请求里给 `1.9.0` → 发布后是 `1.9.0`，不是算出来的号 |
| 6 | 基线不可用时类型不可用（**两种情形、三种样子：带预发布标记 / 线上那一版没有号（空，或根本不是合法 semver）**） | 线上当前是 `1.0.0-rc.1`，草稿带 `patch` → 发布被拒 `release_type_needs_explicit_name`；显式给 `1.0.0` 则可以。另造一个**上线过、但那一版没有号**的 skill（直接改库），草稿带 `patch` → 同样是 `release_type_needs_explicit_name`；显式给号则成功。**页面上这三种都不给类型选择器、都勾不上**，行上写「基线为预发布版本，需指定版本号」或「线上版本没有号，需指定版本号」 |
| 7 | 算出来撞号只失败不换号 | 造一条算出来是 `1.2.4`、而 `1.2.4` 已被占用的草稿 → 该条失败 `version_already_exists`，没有产生 `1.2.5` |
| 25 | 历史草稿自己带的版本号被沿用，不会被算号覆盖 | 直接改库造一份 `version` 非空的草稿：不带号发布 → 发出去的号就是它原来那个（算号规则不参与）；同一种草稿带一个**不同**的显式号发布 → 400 `version_name_is_assigned`，那一行仍是草稿，没有产生新版本 |

### 待上线队列

| # | 验收 | 怎么判定 |
|---|---|---|
| 8 | 队列列出所有**我够得着上线的**、有草稿的 skill，**按各自最新一份的提交时间倒序**；**按命名空间分开看** | 造 4 个 skill：A 从未上线（1 份草稿）、B 已上线 `@1.2.3` 且有新草稿、C 已上线无草稿、D 是别人共享给我、我只到 `write` 且有草稿。队列里**有 A 和 B，没有 C 也没有 D**（「我的 skill」照常显示 D，只是它不进待上线队列——这条读只返回我够得着上线的 skill）。另造 `yuhan` 下的一个 skill：切到 `yuhan` 只看见它，**两个空间的草稿不会同时出现在一张单子上** |
| 9 | 没有类型、又需要类型的行要选一档才能勾；**已有类型的行点版本号能改一档、号跟着重算** | B 的草稿没类型 → 勾不上，行上有选档位；选「次版本」后能勾上，且服务端读回这份草稿的类型是 `minor`。另造一条线上 `0.9.0`、类型 `major`（号 `1.0.0`）的草稿 → 点 `1.0.0` 换成「次版本」→ 号变成 `0.10.0`，服务端读回是 `minor` |
| 10 | 没有草稿时是空态，不是空表 | 清空所有草稿后打开队列：一句说明「没有待上线的草稿」，不是一张空表格 |
| 11 | 可以多选、全选、取消全选；**全选取每个 skill 最新的一份，且不覆盖已选的** | 队列里 5 个 skill：3 个各一份、2 个各三份，**那 3 个单份的 skill 里有 1 个缺版本类型**（只有那两个多份的 skill 需要**挑**一份；单份的直接勾它唯一的一份） → 点「全选」→ **每个能算号的 skill 恰好勾上一份，且都是各 skill 里最新提交的那一份**；最新那份缺类型的那个 skill 一份都没进，动作条写「已选 N 份 · 2 个 skill 取最新草稿、1 份未指定版本类型」。再先把某 skill 手动勾成第二新的那份、点「全选」→ **它没被换掉**；再点一次（按钮此时写「取消全选」）→ 清空 |
| 12 | 一次确认，确认单逐条列出名字与版本号 | 选 4 份（其中 1 份会撞号）→ 点「上线所选」→ 确认单上**这 4 行都在**，每行写清「skill · 版本名称 → 版本号」 |
| 13 | 取消确认什么都不发生 | 接 #12，点「取消」→ 这 4 条仍是草稿，队列不变，服务端无变化 |
| 14 | 逐条成功或失败，不全有全无 | 接 #12 的 4 份（1 份撞号）→ 结算写「3 份已上线，1 份失败」，并给出那一条的原因；另外 3 条照常上线 |
| 15 | 成功的离开队列，失败的留下可重试 | 接 #14：成功的 3 条从队列消失，失败那条还在并标着原因；再点一次只处理它 |
| 16 | 结果里的号是实际值 | 在确认单打开后、提交前抢先发布一个更高版本（脚本造），使算号结果与预演不同 → 结果里写**实际**的号，并说明它与预演不同 |
| 17 | 发布之后 agent 立刻能取到 | `skillmaster skills list`（**默认口径，不加 `--show`**）出现这些 skill；对其中一条 `skill invoke` 成功 |
| 18 | 发不了的 skill 不进队列；页面过期时那一条失败、不连累整批 | ① 用一个只有 `write` 档的账号：它能在别人的 skill 上提交草稿，但**那条不出现在它的队列里**，直接调批量接口选上它 → 那一条失败并写明原因（不是整批 403）。② `maintain` 的账号打开队列后先被撤掉其中一条的 `maintain`，再点发布 → 同一条失败、其余照常成功 |
| 19 | 超过 500 条时如实说明 | 造 >500 个 skill：页面有一句「只列出了最近 500 个 skill」，不是静默截断 |
| 20 | 执行过程一条一条地看得见，而且只数真的落地的 | 发 4 份（其中 1 份会撞号）：确认之后那 4 行的状态依次变成"走完 / 走完 / 正在走 / 还没轮到"，标题下方的计数从 `0 / 4` 走到 `3 / 4`，最后一条落定后进度条整体撤掉、标题换成结算；**执行中关不掉单子**（Esc 也不管用、没有取消按钮；结算态不是这样——那里 Esc 等于「完成」）；**接口若一次性返回，四条会在同一刻一起变**——这一点在联调时确认一次，两种实现都不许在"已经发完"之后还让计数继续爬 |
| 21 | 一批比弹窗高时，跟着走、算完结也看得全 | 发 17 份：执行中正在走的那一条始终落在单子的**正中**（偏不超过 40px），单子底边淡出；结算时单子**回到第一条**，能滚着看完 17 条 |
| 22 | 结算不自己关；关掉之后队列是结果的样子 | 最后一条落定后单子弹窗不消失，标题是「3 份已上线，1 份失败」，只有一颗「完成」；点它之后：成功的 3 条离开队列，失败那条还在并带着原因 |
| 23 | 搜索与筛选在队列上真的能筛 | 默认命名空间（7 份 / 4 个 skill）：搜 `triage` 只剩 `log-triage` 那一组（**别用 `log` 验——`changelog-writer` 也含这三个字母，子串匹配会命中两组**）；筛「有多份草稿」只剩 `log-triage` 与 `changelog-writer` 两个 skill；搜索与筛选同时用，两个条件都生效。**切到另一个命名空间再筛「缺少版本类型」**——只剩那两份没选类型的行（那个空间里的第三条**故意没选类型**，但它的基线是预发布——那不是"缺类型"，不属于这一档）。**筛过之后已勾选的不丢**（动作条仍说「已选 N 份」） |
| 24 | 一批里同一个 skill 出现两次 → 整批拒绝；页面上第二份勾不上 | 页面上同一个 skill 选了一份之后，另一份的勾选框不可用、行上写着原因；绕开页面直接调批量接口带上两份 → 400 `duplicate_target`，**一条都没有上线**（不是第一条成功、第二条失败） |
| 26 | 连接断在中间时，结算只说有结果的那几条 | 发 4 份（其中 1 份会撞号），在第 2 条之后切断连接（T24 的做法）→ 标题写「1 份已上线，1 份失败，2 份没有结果」——**成、败、没有结果各说各的**，已经把原因写在行上的那一条不会被并进「没有结果」；后两行回到"还没轮到"的样子，不是失败也不是已上线；正文写「连接中断了：已上线的不会撤回，其余的请重新上线。」；点「完成」后，已经落定的行按各自结果离开或留在队列 |

**指标**：一次批量发布之后，**本批里每一个成功的 skill 都能被 `skills list`（默认 live）看见、且能 `invoke`**。⚠️ 不要用"条数增量"量它：`skills list` 一行是一个 skill，给**已上线**的 skill 发新版本不增加条数——而 PRD 做 #5 自己说了，「已上线又有新草稿」才是日常最常见的那一种。条数增量只在"本批里从没上线过的 skill"那一档成立，要量就先按那一档过滤。

## 依赖与前置

- **发布只在浏览器面**：[ADR 0031](../../decisions/0031-submitting-and-publishing-are-two-actions.md)。批量因此是控制台操作。
- **一次确认放行多次**：[ADR 0090](../../decisions/0090-batch-publish-confirms-once.md)，它规定了确认单必须逐条列出。
- **版本类型**：[ADR 0091](../../decisions/0091-release-type-decides-the-version-number.md)。它是这一版的前提——没有它，队列里"已发布又有草稿"的那些行根本选不了。
- **队列要一条新读**（2026-10-25 审计改）：`GET /web/skills` 每个 skill 只给草稿**份数**与最新那一份的 digest，没有草稿名称、没有行码（pin）、没有每份草稿的提交时间与版本类型，也没有调用者的档位——这一页要的三样它一样都没有。本版新增 `GET /web/publish-queue`，形状见 TD §接口。
- **设计稿已覆盖这一屏**（2026-10-25）：待上线页与「确认 → 执行 → 结算」三态都在 `design/`，逐项见 TD §界面。实现从设计件搬（仓库约定）。
- **控制台操作映射**：[ADR 0081](../../decisions/0081-every-console-operation-has-a-cli-command.md) 的映射表见下。
