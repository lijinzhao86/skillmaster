# v72-fixed-labeling · 用固定规则给公域 skill 打上运行环境标签

> **最后更新**：2026-11-14
> **状态**：进行中（实现完成，单元与集成测试通过；T13 金标集达标，T6 导入端到端通过；**待提交与合并**）
> **含收费**：否

## 目标

在 OPS 里实现一个可复算的规则函数，从 `SKILL.md` 与文件清单判断 `runtime` 标签；导入时自动调用，后台可整体刷新，写进 server 的最终表。细节见 [`prd.md`](prd.md)。

## 验收标准

一句话：21 个 `runtime` 值都有规则、每条标签都有可核对的证据、导入即打、刷新能纠错、生产表只剩两列。完整验收见 [`prd.md`](prd.md) §验收与指标。

成立条件：A2（证据）、A3（`gpu` / `docker` / `database` 口径）、A4（导入链路）、A5（刷新）、A7（生产表干净）、A12（金标集准确率）任一不满足就不算交付。

## 这一版明确不做什么

摘要三条最要紧的；完整范围与每条的理由在 [`prd.md`](prd.md) §范围。

- 不做 Agent / 模型抽取与 `outcome` —— 那是 v66 P1，有自己的外发边界与抽样验收
- 不做分类与定价 —— 分类是语义判断，价格几乎不写在仓库里
- 不做运营覆盖文件与运营 CLI —— 规则错了改代码重跑，不设人工干预路径

## 与目标态的关系

[`target/`](../../target/) 描述的是完整形态。这一版只补「谁标、标什么」里的**确定性一半**：

- 保留的部分：标签是平台对公域 skill 的主张；用户看到的仍是同一组字段（[`target/design.md`](../../target/design.md) §2.8 的标注一小块）。
- 已经分叉的部分：没有新增分叉；`outcome`、分类、评价与治理仍按目标态留给后续版本。

## 影响最大的未决问题

完整列表见 [`technical-design.md`](technical-design.md) §开放问题。前三条：

1. **公域实际有多少条** —— 决定一次全量刷新要多久、要不要分批；第一轮刷新时数一遍。
2. **规则命中的「够不够严」** —— 金标集 77 条实测已把 `online-service` / `account` 从「只认显式声明」扩到 CLI、URL、`platforms`、`bins`、`--as user`；公域首轮刷新后仍应抽 50 条复核。
3. **导入端到端已经跑通（T6）** —— 本机独立栈上导入了一条真实 skill，`label_claim` → `label_entry` → `skill_label` → 公开读接口全部有证据；剩下的是提交与合并，不再有验证闸。
