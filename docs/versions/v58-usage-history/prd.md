# v58-usage-history · 产品需求

> **最后更新**：2026-11-10
> **所属版本**：[`README.md`](README.md)

## 用户与场景

**谁在用**：

1. **使用 skill 的人**。在控制台或 CLI 里搜过、调用过 skill，过几天想找回来——「上周试过的那个 PDF 工具叫什么来着」；并且要能回答「我搜的那个词，最后用的是不是搜到的那条」——这是优化搜索词与 skill 选择的第一手线索。
2. **skill 的所有者**。想知道自己的 skill 有没有人用：公域里只看总统计；分享给协作者时，要能按协作者看使用量，但不需要看到对方的操作明细。
3. **内部运营与审计**。要回答「这个账号最近做了什么」「这条 skill 到底有没有人用、用了哪一版」，今天只能从应用日志、`audit_event` 和零散的表里拼。

**在什么场景下用**：

- 用户翻自己的使用记录，找回一个搜过或调用过的 skill；并回看**一次交互**：搜索词是什么、返回了哪几条、最后调用了哪条、排第几。**先一行扫过更多历史，再决定展开哪一条看搜索结果**。
- 用户判断「搜索意图」与「最终选择」是否一致：搜出来的清单里有没有想要的那条，agent 最后拿的是不是那条。
- 所有者判断一条 skill 是否值得继续维护、哪个协作者在用。
- 运营排查「用户说用不了」：看他最近 invoke 了哪一版、读了哪些文件。
- 审计一个账号或一条 skill 的行为面。

**现在的替代做法是什么**：

- 用户侧：浏览器历史、终端 scrollback、重新搜一遍。没有一处能按账号列出「我搜过什么 / 我 invoke 过什么」。
- 所有者侧：公开 skill 只有分桶的不同账号数与累计次数；共享出去的私有 skill **完全没有使用数据**。
- 内部：应用日志按时间滚，`audit_event` 只覆盖写操作；**搜索、浏览、读取完全没有留痕**，invoke 只有 M15 的聚合计数，还原不到具体账号与时刻。

## 范围

### 做

#### 1. 行为明细日志

记录已登录用户的全部行为，**完整日志 = `audit_event` 与新 `activity_event` 的并集**，两者都在同一个 PostgreSQL 库里，按账号与时间可合并查询：

| 事件族 | 例子 | 落到哪 |
|---|---|---|
| 检索 | 带 `q` 的搜索、浏览发现页、看 skill 详情、列版本 | `activity_event` |
| 使用 | invoke（API 的 `/api/v1/.../body`；网页 `/web/.../body` 是预览，记读取）、读文件（`/files/*`）、整版下载（`run` / `get`） | `activity_event` |
| 账号会话 | 登录、登出 | `activity_event` |
| 作者 | 新建、写文件、提交、发布、回滚、下线、恢复、删除、复制 | `audit_event`（已有，补齐缺口） |
| 共享 | 邀请、接受、拒绝、撤销、申请、审批、改角色 | `audit_event`（已有） |
| 库 | 加入、退出 | `audit_event`（已有） |
| 凭据 | 创建、绑定、解绑、轮换、共享、撤销、删除 | `audit_event`（已有） |
| 标签 | 定义增删改、挂 / 摘 | `audit_event`（已有） |
| 同步 | 导入、建草稿、发布（系统动作） | `audit_event`（已有） |

- 写入类**不复制**到 `activity_event`：`audit_event` 是它的权威。
- 明细保留 **90 天**；按周分区，到期 `DROP` 旧分区，不做 `DELETE`。

**搜索与调用的关联**：

- 搜索事件额外记录**这次查询返回过的 skill 列表**（按名次，最多 50 条）与总命中数。
- **翻页并入同一次搜索**（2026-11-10 用户定）：同一账号、同一查询词与筛选、首条搜索在 30 分钟内，第 2 页及以后的结果**追加到同一条搜索**上（按顺序、去重、最多 50）；「搜索次数」仍算 1，明细仍是一行。**两个平面都比对筛选**；API 的游标请求要重发筛选（CLI 已这样做）。超过 30 分钟的翻页另起一条——它是另一段查询会话。
- 调用事件记录 skill 与版本；服务端在写入时做一次**时序匹配**：同账号、30 分钟内、该 skill 出现在某次搜索的返回列表里，取**最近一次命中的搜索**，把这次调用挂到那条搜索下。匹配不上就是「直接调用」。**先搜 A、再搜 B、两条结果都含同一 skill**：只挂最近一次（B），A 显示「未调用」。
- **一次搜索之后可以有多条调用**（2026-11-10 定）：都挂同一次搜索；明细行把多条调用**分行列出**（不折叠、不靠悬停），行内展开的结果面板里被调用的那几条都加粗并标「已调用」；统计按全部调用计。
- **不引入 `search_id` 透传**：CLI 与 agent 不需要为此改任何东西。误关联由四条规则压住：同账号、30 分钟、结果命中、取最近一次。

#### 2. 四层可见性

| 层 | 谁能看 | 看到什么 |
|---|---|---|
| **1 公域** | 公开 skill 的所有者 | 不同账号数（**分桶**）、累计调用次数（**分桶**，沿用 ADR 0152 的累计分桶）、入库人数（精确） |
| **2 共享** | 私有 skill 的所有者 | 每个协作者的**档位、调用次数、提交版本数与最近活跃**（采用 + 贡献）；**读取次数与文件级写入不展示**——它们不指向管理动作，原始事件仍全量记录、内部可查；不含搜索词，不含操作明细。表里**第一行是所有者自己**，「所有者」写在档位列。**管理档不因「管理」获得这一层**：它能管名单与档位，按人的用量仍只给所有者。所有者另有**两个视图**：「全部使用」看总量与协作者，「我的使用」看自己在这条 skill 上的调用——所有者也是使用者 |
| **3 本人明细** | 每个账号 | 自己的**交互明细**：搜索词 → 返回结果 → 实际调用（含原名次）——自己调自己的、自己调别人的，都只看自己的。读取与写入**全量留痕，但不在这页展示**，内部可按账号查（第 4 层） |
| **4 内部** | 运营 / 审计（数据库） | 按账号的全量明细，**不建产品界面、不做导出** |

- 协作者之间互不可见；协作者看不到自己以外的任何人。
- 公开面仍只给分桶，不给精确人数，不给「谁用过」。

#### 3. 产品面

| 做什么 | 交付形态 |
|---|---|
| 「使用记录」页：**我的交互明细**（搜索 → 结果 → 调用）/ 我的统计 | 控制台 |
| 同一份数据给 CLI（**CLI 是第一前端，网页上的每一处使用信息都要能在这里读到**）：`skmr usage`（交互明细，`--expand` 展开每次搜索的返回列表）、`--stats`（我的统计）、`skmr usage <地址>`（全部使用：聚合 + 使用者表）、`--users`（只要使用者表）、`--mine`（我在这一版上的使用，含版本状态） | CLI |
| 本人记录查询接口：只能查本人（账号来自凭据，没有指定他人的参数）；所有者聚合与使用者表对非所有者 404 | API |
| 日汇总：按「所有者 × skill × 协作者 × 天」聚合**调用次数与提交版本数**（读取/写入的原始事件留在明细里，供第 4 层查），保留 1 年；第 2 层与趋势读汇总，不扫明细 | 服务端 |
| 账号注销时，账号资料与个人命名空间内容按 v56 的 30 天窗口删除或去标识化；**行为明细与汇总不删除**，按保留期作为内部安全、审计与分析记录（日志里只有去标识化账号 id）；本人命名空间里的 skill 被删除时，指向它的汇总行随外键级联删除 | 服务端 |

#### 4. 存储与分层

- **热**：PostgreSQL，**同实例、同一 schema、新增两张表、原生周分区**；明细保留 90 天。不引入 SLS、不引入 TimescaleDB（阿里云 RDS 是 Apache-only 构建，压缩与保留策略不可用，见 [`docs/research/activity-log-storage.md`](../../research/activity-log-storage.md)）。
- **温**：日汇总（所有者 × skill × 协作者 × 天）保留 1 年，体量小，可在线 join。
- **冷**：90 天前的明细分区导出为 **NDJSON（每行一个 JSON 对象）gzip 压缩后上传到 OSS**，对象键是 `activity/activity_event_<周起始>.jsonl.gz`；核对行数后再 `DROP` 分区。不参与在线查询；今天用 DuckDB 的 `read_json_auto` 直接读，未来 MaxCompute / Hologres 建外表读同一批文件，不需要搬迁。**为什么不是 Parquet**：服务端没有 Parquet 写入依赖，为一个每日归档任务引入整套 Hadoop/Parquet 栈不值得；NDJSON 可以边查边写、行数可逐行核对，DuckDB 一样能读。低频约 ¥0.07/GB/月。
- **审计**：`audit_event` 永久保留在 PG。
- 存储与归档都藏在接口后；日事件量超过 100 万、或明细 + 索引超过 30 GB 时，再评估独立实例或 SLS。

### 不做

| # | 不做什么 | 为什么 | 什么时候可能做 |
|---|---|---|---|
| 1 | 不向任何人展示别人的**明细** | 明细是可还原的个人行为；与 ADR 0149 的最小数据口径一致 | 不做 |
| 2 | 公开面不给精确人数 | ADR 0149：小样本可反推具体的人 | 需要推翻时另开 ADR |
| 3 | 第 2 层不给协作者的搜索词 | 用户已定：只统计调用次数、提交版本数与最近活跃 | 不做 |
| 4 | 不做内部分析看板、报表、导出 | 本版只把事实落下来；分析先走 SQL | 运营侧策展工作台开版时 |
| 5 | 不做按条删除 / 清空我的历史 | 行为日志是内部安全与审计记录，按保留期保存；注销不删除（2026-11-10 用户定） | 隐私需求明确时 |
| 6 | 不记匿名行为、IP / UA / 设备指纹 | 所有读写都要求登录 | 不做 |
| 7 | 不把整版下载展示成「调用」 | 调用口径由产品负责人定为 invoke；下载仍记入日志，只是不在「调用」里显示 | 需要区分「运行」与「阅读」时 |
| 8 | 不复制写入日志到 `activity_event` | `audit_event` 已是写操作的权威，复制会漂 | 不做 |
| 9 | 不在本版接 SLS / 独立日志实例 / TimescaleDB | 现阶段量小，同实例最省；迁移触发条件已写在研究文档 | 达到触发条件时 |
| 10 | 不做作者看板与平台看板 | 那是 `target/design.md` §2.7 的目标态 | 后续版本 |
| 11 | 不做 `search_id` 透传、不为关联改 CLI / agent | 关联靠服务端时序匹配已够用；让 agent 多记一个 id 是把复杂度推给调用方 | 误关联成为主要投诉时 |
| 12 | 不把搜索与调用分成两份互不相干的列表 | 分开只能证明「发生过」，回答不了「搜到的和用的是不是同一条」 | 不做 |
| 13 | 不在明细的默认视图里铺返回结果 | 默认一行、搜索结果收起；行内展开后才按当时的顺序显示（最多 50 条）。默认铺开会把「翻历史」变成「读榜单」 | 用户要求默认展开时 |
| 14 | 不在「使用记录」里展示读取、写入与分享管理 | 页面只回答「搜到的与用的是不是同一条」；写入与分享已有版本页、协作者页显示当前状态，日志里再列一份会是第二份会漂的清单；所有者那侧也只给次数与贡献，不给明细。全量日志照记（ADR 0179 决定 1），不因不展示而减少 | 用户要看自己的写入 / 分享历史时，另开一个读 `audit_event` 的「活动」页签，不塞进这张表 |
| 15 | 不让管理档看到协作者的用量 | 管理档的职责是「谁能进、什么档位、该不该收回」，是按人的权限治理；按人的用量回答的是「用得勤不勤」，那是所有者的授权关系与问责。多人管理时会变成互相看用量。管理者仍是看自己的记录，名单与档位在「设置 › 协作者」 | 组织确实需要管理者代行统计时，另开一条可见性决策（新增 ADR 层），不在本版改 |
| 16 | 不在所有者那张表里展示读取次数与文件级写入次数 | 读取基本是调用的影子（agent 调用后读附属文件），只读不调的人是在看、不是在用；文件级写入改 30 个文件算 30 次，噪声大，且调用档永远为 0。两者都不指向管理动作。改用「提交版本数」看贡献，用「档位」解释 0 次。原始事件仍全量记录，第 4 层可查 | 分析方法（内部）要看读写时直接查日志；不回到所有者界面 |

## 控制台操作与 CLI 对应

| 操作 | 界面 | CLI |
|---|---|---|
| 看我的交互明细 | 「使用记录」页 → 明细 | `skmr usage` |
| 看我的调用统计 | 「使用记录」页 → 统计 | `skmr usage --stats` |
| 看我的 skill 的公域聚合 | skill 详情页 → 使用 | `skmr usage <地址>` |
| 看共享 skill 的协作者统计 | skill 详情页 → 使用 → 全部使用 → 协作者 | `skmr usage <地址> --users` |
| 看自己在这条 skill 上的调用 | skill 详情页 → 使用 → 我的使用 | `skmr usage <地址> --mine` |

本版没有高风险操作，也没有产品负责人豁免项。

## 验收与指标

### 验收标准

| # | 验收标准 | 怎么判定 |
|---|---|---|
| A1 | 账号甲 `invoke` 一个 skill 后，控制台「使用记录」与 `skmr usage` 都能立刻看到这一条：地址、版本、时间一致 | 集成测试 + 控制台页断言 |
| A2 | 账号乙看不到账号甲的任何明细：明细接口只按凭据返回本人（没有指定他人的参数），乙请求到的是乙自己的数据；所有者聚合与使用者表对非所有者返回 404，不泄露存在性 | 集成测试（两个账号） |
| A3 | 带 `q` 搜索一次后，本人明细新增一条交互：query、总结果数、返回列表（最多 50 条）；不带 `q` 的浏览不新增 | 集成测试 |
| A16 | 同一账号 30 分钟内先搜 A、再搜 B，最后 invoke 一个只在 A 结果里的 skill → 挂到 A（最近一次包含它的搜索），不挂 B；invoke 一个不在任何最近结果里的 skill → 显示「直接调用」 | 集成测试（固定时钟） |
| A17 | 明细是一张日志表：时间 / 操作 / 调用的 skill 三列；搜索结果默认收起，**点搜索行任意位置**（行内不再放链接）在**行内展开的面板**里按当时的顺序列出（最多 50 条），**被调用的那几条加粗并标「已调用」**；直接调用用图标区分、与搜索同一种行；长地址与长搜索词单行省略 | 集成测试 + 控制台断言 |
| A22 | 一次搜索后调用了多个结果：明细仍是一行交互，但把**每条调用分行列出**（不折叠、不靠悬停）；展开面板里被调用的每条都加粗并标「已调用」；接口的 `invocations` 是长度等于调用次数的数组（按时间升序）；统计的调用次数按全部计、转换只算一次搜索；CLI 默认就分行列出每一条 | 集成测试（固定时钟）+ 控制台断言 |
| A23 | 同一查询翻到第 2 页（首条搜索 30 分钟内）：明细仍是**一行**，「搜索次数」不变，结果按翻页顺序追加、去重、最多 50；翻到的那一页里的 skill 被调用时照常关联；首条搜索 31 分钟后再翻页则另起一条 | 集成测试（固定时钟 + 两页响应） |
| A18 | 统计与明细同源：页面上的调用次数等于明细里的调用行数，「按调用次数」各行之和等于这个数，搜索后调到 + 没有调到等于搜索次数；「用过的 skill」等于列表行数 | 控制台断言（同一账号、同一窗口） |
| A4 | 91 天前的明细在页面与 CLI 都不再出现；90 天内的还在；旧分区被 `DROP`，不是 `DELETE` | 集成测试（造旧数据）+ 迁移检查 |
| A5 | 自己的 skill、别人分享给自己的 skill、公开 skill 三种，本人都只看得到自己的明细 | 集成测试（三种关系） |
| A6 | 公开页的使用信号仍是分桶值，不因本版变成精确数 | 既有接口契约测试 |
| A7 | 账号注销后，账号资料与个人命名空间内容按 v56 处理；该账号的行为明细与汇总**不删除**，仍按保留期保存，日志里只出现去标识化账号 id（本人命名空间里的 skill 被删除时，指向它的汇总行随外键级联删除） | 集成测试 |
| A8 | 内部按账号可查到检索、使用、会话三类明细；写入类从 `audit_event` 读得到；两者并集覆盖九类事件族 | SQL 验证（测试库） |
| A9 | 同一查询在控制台与 `skmr usage` 的结果一致 | 集成测试（同一账号、同一窗口） |
| A10 | 公开 skill 的所有者看到四张数卡：不同账号数与累计调用次数都是分桶值（不是精确数）、入库人数、最近使用；与 M15 的公开口径一致 | 集成测试 |

**成立条件**：A1、A2、A10、A11 是「不满足就不算交付」——本人看得到、别人看不到、所有者看聚合、按协作者统计，正是这一版要立住的四条。

### 指标

| 指标 | 定义 | 怎么量 | 目标 |
|---|---|---|---|
| 找回一个用过的 skill 所需动作 | 从「想找回来」到再次拿到它 | 按 §用户与场景 计一遍 | 现在只能重新搜；目标 1 次打开「使用记录」 |
| 行为留痕覆盖 | 九类事件族里有多少能在事后按账号还原 | 对数 `activity_event` 与 `audit_event` | 九类全覆盖；写入类不重复 |
| 本人明细查询延迟 | 单账号 90 天窗口、一页 50 条 | 集成测试计时 | p95 < 300 ms |
| 所有者统计延迟 | 单 skill、90 天、按协作者分组 | 集成测试计时 | p95 < 300 ms |

## 依赖与前置

- **决策**：[ADR 0179](../../decisions/0179-personal-usage-is-visible-only-to-its-owner.md) 定可见性四层、90 天、公开面只给分桶。
- **法务**：搜索词与读取路径扩大了个人信息面，**隐私政策需要补一段说明**，并写明账号注销后行为日志仍按分层保留期保存（在线明细 90 天、归档最多 3 年、汇总 12 个月）、账号已去标识化；上线前由产品负责人确认是否单开一次法务小版本。
- **运维**：生产 RDS 目前 20 GB，本版前要扩到 **50 GB**（同实例方案）。只扩存储一次性约 **¥348.41**（剩余周期），**不中断业务**；若要同时升到 2 核 4G（`pg.n2e.2c.1m`），一次性约 **¥1,022.00**，续费后 ¥118/月，规格升配有短暂闪断。归档需要一只 OSS bucket，并为 `activity/` 前缀配置 1095 天（最多 3 年）的生命周期规则——冷层上限靠这条规则，当前仓内没有配置，上线时核实。
- **已知风险**：RDS 是 1 核 1G，日志写入与业务查询共享资源；用窄行、四条索引（TD §数据模型）、日汇总与查询上限控制。达到研究文档的迁移触发条件时再拆实例。TD 的容量估算按 2C4G 算；停在 1C1G 时以实际延迟为准，必要时把升配列入上线动作。
- **内部前提**：CLI `invoke` 走 `/body`、`read` 走 `/files/{relpath}`、`run` / `get` 走 archive 路由，采集点因此可区分调用、读取与下载，不需要客户端新加标记。
- **外部依赖**：无。
