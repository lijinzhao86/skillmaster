## 用户与场景

**谁在用**：

- 用 CLI 提交、修改 skill 的 agent 与作者（Windows / macOS / Linux 都可能）
- 从库里下载 skill 的人（多数在 macOS 或 Windows）
- 在控制台「导入本地 skill」的人

**在什么场景下用**：作者在 Windows 上写好一份 `SKILL.md`（CRLF、可能带 BOM），或在 macOS 上敲出带重音的字符（NFD），压缩后上传；另一个人在 macOS 或 Windows 上下载。

**现在的替代做法是什么**：

| 现状 | 差在哪 |
|---|---|
| 字节原样入库（ADR 0005） | 同一段文字，Windows 提交与 macOS 提交算出两个 digest → 两版看起来一样的内容；编辑/对比时显示「全文件都变了」 |
| 文件名原样入库 | 大小写碰撞（`A.md` / `a.md`）在 macOS / Windows 上下载时**静默覆盖**，用户少一个文件且不知道；Windows 非法字符要到解压时才报错 |
| 打包垃圾原样入库 | `__MACOSX/`、`.DS_Store`、`Thumbs.db` 进了 manifest，每份 skill 都多几个没用的条目 |

**实测（2026-10-30）**：macOS 上写入 `A.md` 再写 `a.md`，目录里只剩一个；把两个名字打进同一个 zip 再解压，`unzip` 报两条 extracted、退出码 0，目录里仍只剩一个——**静默丢失**。

## 范围

### 做

| # | 做什么 | 交付形态 |
|---|---|---|
| 1 | **文本归一化，在入口统一**：CRLF / 单独 CR → LF；去掉 UTF-8 BOM；有 BOM 的 UTF-16 转成 UTF-8；Unicode 统一为 NFC | 服务端 |
| 2 | **四个写入口共用同一套规则**：zip 上传（CLI `submit` / 网页导入）、`write`、`edit`、从底稿建草稿 | 服务端 |
| 3 | **路径归一与校验**：路径段统一 NFC；归一后碰撞、大小写碰撞、Windows 非法字符（`< > : " \| ? *` 与控制字符）、Windows 保留名（`CON` / `PRN` / `AUX` / `NUL` / `COM1–9` / `LPT1–9`，含带扩展名的形式）、段尾的空格与结尾的点、路径过长（单段 > 255 字节或整路径 > 1024 字节）→ **拒绝** | 服务端 |
| 4 | **zip 文件名编码**：解出来带 `U+FFFD`（替换字符）的名字 → 拒绝，提示重新用 UTF-8 打包 | 服务端 |
| 5 | **丢弃打包垃圾并报告**：`__MACOSX/`、`._*`、`.DS_Store`、`Thumbs.db`、`desktop.ini`、`~$*`；`.git/` / `.svn/` 同样丢弃 | 服务端 |
| 6 | **拒绝时给出理由**：每条 `details` 是「路径 + 原因码」。CLI `submit` 逐条列「路径 → 原因 → 怎么改」，超过 10 条只列前 10 条并给总数；网页**在写的那一刻挡**——编辑器新建 / 重命名时行内标红、按 Enter 不创建，导入压缩包失败时点名前 3 个；碰撞类给出**两条** detail 分别指向两个文件 | CLI + 控制台 |
| 7 | **审计留痕**：每次入库记录这次归一化了哪些文件、丢弃了哪些（`normalized[]` / `dropped[]`），让「digest 变化比预期大」有据可查 | 服务端 |
| 8 | **一个模块**：`modules/canon`，纯函数，上传校验与写路径共用；不改 frontmatter、不 trim、不重排、不动二进制 | 服务端 |
| 9 | **`.bat` / `.cmd` 不归一化**：按二进制对待（cmd.exe 对只有 LF 的批处理可能出错） | 服务端 |

**为什么在入口统一，而不是在读取时**：读取路径必须原样服务存储字节（`bodyOf` 的承诺），否则每次读都要重算，digest 与内容就永远对不上。归一化只发生一次，发生在写入的时候。

**网页在写的那一刻挡，不等到上传之后**：编辑器的新建 / 重命名本来就是行内输入 + 行内报错（`.editor-field-error`，按 Enter 创建、按 Esc 取消）。跨系统这几条规则加进同一个纯校验函数（`validatePath` / `validateCreatePath`），名字不对就标红、按 Enter 不创建——**不是先建出来、再在别处报错**。服务端仍是最后一道：绕过页面直接写，返回同一原因码。导入压缩包没有这个机会（文件在包里），只能失败后点名。

### 不做

| # | 不做什么 | 为什么 | 什么时候可能做 |
|---|---|---|---|
| 1 | 不改旧版本（线上与历史版本保持原样） | 版本不可变（ADR 0005 / 0064）；回写会改掉 digest，等于换一份版本 | 不做。旧内容在「复制成草稿再改」时自然归一化 |
| 2 | 不自动改名、不改写正文里的链接 | 改名要同时改所有引用（markdown 链接、反引号路径、代码字符串），猜错一个就是悄悄坏掉 | 不做 |
| 3 | 不猜非 UTF-8 编码 | 只认 UTF-16 的 BOM；GBK / Shift-JIS 等不猜，避免把内容转坏 | 若出现大量非 UTF-8 的真实上传，再评估 |
| 4 | 不统一文件末尾有没有换行 | 补一个换行是改内容；也没有跨系统的一致预期 | 不做 |
| 5 | 不保存可执行位与时间戳 | 包格式里没有 mode；保存与还原是另一个话题 | 若出现「脚本下载后不可执行」的实际反馈 |
| 6 | 不做「接受但警告」 | 可见失败的文件（非法字符、保留名、过长）如果在下载时才坏，用户不会知道原因；警告只在上传时给作者看，挡不住用户拿到一份跑不起来的 skill | 若一个月内出现 ≥5 个真实作者报告「名字合法却被拒」 |
| 7 | CLI 不做本地预检（一期） | 规则只写服务端一份；客户端负责把服务端返回的 details 讲清楚即可 | 二期若上传量大、往返成本明显 |

**关于「拒绝还是警告」**：本版一律拒绝，因为平台承诺的是「谁下载都能原样还原」。之前讨论过的「可见失败放宽成警告」没有采用——它把问题推迟到下载那一刻，而且那时作者已经不在场。

## 控制台操作与 CLI 对应

本版没有新增控制台操作。网页上有两处会变：**编辑器的新建 / 重命名**（行内校验多出跨系统这几条，标红、按 Enter 不创建）与**导入压缩包的失败那一刻**（从一句笼统的话变成点名文件）。CLI 侧对应 `skmr skill submit` 的失败输出，三处用同一套原因码与同一套句子（控制台的文案以 `design/voice-spec.md` 为准，需要先补设计稿）。逐字文案见下一节。

## 措辞（文件名校验失败）

三个地方，同一套原因码与同一套事实，各自用当下的那个动词：

| 地方 | 动词 | 形状 |
|---|---|---|
| CLI `skill submit` | 提交 | 一行结果 + 每条一行 + 一行下一步 |
| 网页编辑器 · 新建 / 重命名 | 创建 | 输入框下一行红字，按 Enter 不创建 |
| 网页 · 导入压缩包 | 导入 | 弹窗里一段红字（最多点 3 行）+ 一行下一步 |

### CLI（submit）

形状：一行结果 + 每条一行 + 一行下一步；退出 1，stdout 为空。

```
错误：4 个文件名在 macOS 或 Windows 上不可用；这次提交没有落库。
  报告:v2.md：冒号不能作为文件名（Windows）。改成「报告-v2.md」
  CON.md：CON 是 Windows 保留的设备名。改成「_CON.md」
  A.md 与 a.md：两个名字在 macOS 和 Windows 上会被当成同一个文件。改掉其中一个
改完再提交：skmr skill submit <目录>
```

- **一次列全**，最多 10 条，超出写「还有 N 个。」——agent 一轮改完，不用来回试。
- 每条三段：**文件 → 原因 → 怎么改**。碰撞类一行写两个名字，因为要改的是它们俩的关系。
- `write` 只有一条，首句换成「错误：这个文件名在 macOS 或 Windows 上不可用；草稿没有改动。」，末句「改完再写一次。」
- **建议的新名字只在能确定时给**：非法字符换成 `-`、保留名前加 `_`；给出来之前要确认它不和这一版里已有的路径重名，给不出就不给。

### 网页编辑器（新建文件 / 新建文件夹 / 重命名）

行内：与现有 `路径不能为空。` 同一处、同一个 `.editor-field-error`，标红、输入与焦点都留着、**按 Enter 不创建**。

```
文件名或路径  [报告:v2.md      ]
按 Enter 创建，按 Esc 取消
冒号不能作为文件名（Windows）。
```

- **一次只说一条**（先命中的那条），与现有路径校验同一条路——改完再按 Enter，下一条才出现。
- **不给改名建议**：框就在眼前，建议名还要确认不重名；行内只说事实。
- **碰撞句点名已有的那个文件**：`与已有的 a.md 在 macOS 和 Windows 上会被当成同一个文件。`
- 输入的路径按 NFC 归一之后再比对、再显示（与服务端同一条规则），否则同一个名字的两种写法会同时出现在树里。
- 重命名同一句式。服务端仍是最后一道：绕过页面直接写时返回同一原因码，页面上它停在**保存失败的横幅**里（行内那一行只由本地校验产生）。

### 网页导入（压缩包）

弹窗不关、文件仍选中；错误区照今天的「一行危险色」，**最多点 3 行**——首句数的与「还有 N 个」数的都是**文件**，碰撞一行两个名字。

一个文件：

```
压缩包里的 CON.md 不能用在所有系统上：CON 是 Windows 保留的设备名。
改好压缩包再选一次。
```

多个：

```
压缩包里有 4 个文件名不能用在所有系统上，没有导入。
报告:v2.md：冒号不能作为文件名（Windows）。
CON.md：CON 是 Windows 保留的设备名。
A.md 与 a.md：两个名字在 macOS 和 Windows 上会被当成同一个文件。
改好压缩包再选一次。
```

- **最多点 3 行**；更多时在末句前补一行「还有 N 个。」——弹窗里放不下，也不该把这一屏变成清单。
- 网页没有改名能力，所以不给「改成 xxx」，只给事实与下一步。

### 逐条句子

| 原因码 | 句子（三处共用） | CLI 追加的「怎么改」 |
|---|---|---|
| `windows_invalid_char` | 冒号不能作为文件名（Windows）。 | 改成「报告-v2.md」 |
| `windows_reserved_name` | CON 是 Windows 保留的设备名。 | 换一个名字 |
| `trailing_space_or_dot` | 结尾有一个空格（或点），Windows 会去掉它。 | 去掉它 |
| `path_too_long` | 路径太长（单段超过 255 字节，或整个路径超过 1024 字节）。 | 缩短文件名或目录名 |
| `case_collision` | 两个名字在 macOS 和 Windows 上会被当成同一个文件。 | 改掉其中一个 |
| `unicode_collision` | 两个名字只有编码写法不同，macOS 会把它们当成同一个文件。 | 改掉其中一个 |
| `invalid_zip_name` | 有一个文件名解不出来（压缩包不是 UTF-8 编码）。 | 用 UTF-8 重新打包 |

**表里的名字与字符都是占位**：实际句子里换成真正出问题的那个——`报告:v2.md` 换成那条路径，`CON` 换成真正的保留名，`冒号` 换成真正的字符（冒号 / 星号 / 问号 / 竖线 / 尖括号 / 引号 / 控制字符）。**识别由客户端做**，服务端只给原因码。控制字符没有名字，那一句就是固定的「控制字符不能作为文件名（Windows）。」。碰撞句在编辑器里带上已有的那个文件：`与已有的 a.md 在 macOS 和 Windows 上会被当成同一个文件。`

**刻意的选择**：

- **「不可用」而不是「不合法」**：合法是规则视角，不可用是结果视角；用户关心的是「传不上去、别人下载会坏」。
- **碰撞句写「会被当成同一个文件」**，不说「冲突」——冲突听起来像系统要去解决，实际是用户要改名字。
- **尾随空格必须写出来**：它在屏幕上看不见，句子里明说「结尾有一个空格」，否则用户会以为系统在乱报。
- **`invalid_zip_name` 没有路径可写**：原名在解码时已经丢了，这行只给原因和下一步。

## 验收与指标

### 验收标准

| # | 验收标准 | 怎么判定 |
|---|---|---|
| A1 | 文本归一化逐项成立：CRLF / CR → LF；UTF-8 BOM 去掉；UTF-16（带 BOM）转 UTF-8；NFC；**二进制与 `.bat` / `.cmd` 原样** | 每种造一个文件的字节前后对比 |
| A2 | 跨平台幂等：同一段文字用 CRLF + BOM 提交，与用 LF 提交，得到**同一个 digest**、只产生一版 | 两次提交，比较返回的 digest |
| A3 | 路径拒绝逐条成立，且每条都带**出问题的路径**与原因码；CLI 显示「路径 → 原因 → 怎么改」 | 每种造一个路径，读 CLI 输出 |
| A4 | 碰撞类（大小写、NFC 归一后）给出**两条** detail，分别指向两个文件 | 读错误响应与 CLI 输出 |
| A5 | 打包垃圾被丢弃且报告：上传成功，结果里说明忽略了哪几个 | 造一个带 `__MACOSX/`、`.DS_Store` 的包 |
| A6 | 审计记录 `normalized[]` 与 `dropped[]` | 查 `audit_event.detail` |
| A7 | 网页两处都成立（设计稿到位后）：新建 / 重命名时坏名字**行内标红、按 Enter 不创建**；导入失败时按 §措辞 点名，最多 3 个 | 在编辑器里建一个 `CON.md`，再建一个与已有文件只差大小写的名字；导入一个含坏名字的包 |
| A8 | 旧版本字节不变：本版之前入库的 CRLF 内容原样可读、digest 不变 | 读旧版本并核对 digest |
| A9 | 拒绝时零落库：整次请求失败，草稿/版本不变 | 失败后核对文件列表 |
| A10 | 文案与 §措辞 逐字一致：CLI 的首句、每条、末句；网页的标题行、每条、末行 | 对照 PRD 读 CLI 输出与页面 |

### 指标

| 指标 | 怎么量 | 目标 |
|---|---|---|
| 同一段文字产生的重复版本 | 同一 skill 下内容仅在换行/编码上不同的版本数 | 0 |
| 「全文件都变了」的 diff | 因换行风格导致的整文件 diff 次数 | 0 |
| 被拒上传的修复次数 | 从第一次被拒到成功提交的尝试次数 | 1 次（错误里说清改哪里） |

## 依赖与前置

- **ADR 0117**：取代 [ADR 0005](../../decisions/0005-content-addressing.md) §后果里「上传时不得改写内容」这一句；内容寻址、digest 算法、幂等都不变。
- **设计稿**：控制台两处先改 `design/`——编辑页新建 / 重命名的行内报错（`editor-field-error` 那一行多出跨系统的句子、按 Enter 不创建），导入失败那一刻的点名（最多 3 个）。`voice-spec.md` 管词与句式，逐屏句子放在 `design/README.md` 的编辑与导入两节。
- **CLI 文案**：七个原因码在 `cmd/skillmaster/uploadissues.go` 里有自己的句子与「怎么改」（它们不是 `invalid_request` 的 issue，`issueMessages` 管不到）；首句、每条、末句按 §措辞。
- **控制台文案**：同一批原因码进 `errors.ts` 的 `details[].issue` 文案表（`invalid_upload` 的通用句会先把 details 盖掉，见 `design/README.md` §导入）；编辑器行内的规则在设计件 `fixtures/editor.ts`（`validatePath` / `validateCreatePath` / `validateNameCollision`）与产品的 `src/nameRules.ts`（`pathIssue` / `collisionIssue`，由 `editor/files.ts` 的 `validatePath` 调用）各一份，句子逐字一致。
- **服务端模块**：`modules/canon` 与四个写入口的接入。
- 外部参照：[`docs/research/cross-platform-canonicalization.md`](../../research/cross-platform-canonicalization.md)。
