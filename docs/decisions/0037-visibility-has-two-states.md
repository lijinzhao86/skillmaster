# ADR 0037 · 可见性只有私有与公开两档，公开即被搜到

- **状态**：已采纳
- **日期**：2026-10-10
- **依赖**：[ADR 0034](0034-skill-level-sharing.md)（可见性管「任何人」、授权管「某个人」，两者不混）
- **修订**：[ADR 0034](0034-skill-level-sharing.md) §理由 表格里否掉「用 `skill.visibility` 做共享」那一行中的一句（原文：「而 v1 只写 `private`，另外两个值是留给公共发现的」）——「另外两个值」现在只剩 `public`。**该 ADR 正文四段保持原样**

## 背景

`visibility` 这一列在 schema 里出现两次——`namespace`（§3.2）与 `skill`（§3.3），两处都是同样的三个值、同样一句注释。`skill` 那处（`skillmaster-server/src/main/resources/db/migration/V1__baseline.sql`）原文是：

```sql
visibility         TEXT NOT NULL DEFAULT 'private',
...
COMMENT ON COLUMN skill.visibility IS
  'public | unlisted | private. v1 only ever writes private.';
```

三个值各有各的说法：`private` 是今天唯一的实况；`public` 是「谁都能搜到」；`unlisted` 在目标态文档里的定义是「**不可搜到，但拿到链接可访问**」（`docs/target/design.md` 的可见性值表），并且 S11 专门用一个场景表达它——「通过 unlisted 链接分享给外部同事」。

v1 不做公共发现（[`prd.md`](../versions/v1-hosting/prd.md) §范围 不做 #7），所以到今天为止这三个值**一个都没被写进去过**——没有任何一条已交付行为依赖它们，也没有接口读它们。

要定这件事的是设计控制台演示件的权限页那一轮（2026-10-09）。那一页按 [ADR 0034](0034-skill-level-sharing.md) §10 把「可见性」与「被授权的人」摆成两节，而可见性一节要摆几档，取决于一个必须先答的问题：**「公开」是一件事，还是两件事？**

## 决定

1. **`visibility` 只有两个值**：`private` / `public`。**两张表都是**——`skill.visibility` 与 `namespace.visibility`。
2. **`public` 的全部含义是「谁都能搜到它、谁都能调用它」。** 搜索可见性不单独存在：没有「公开但搜不到」这一档。
3. **`unlisted` 被放弃，不是延期。** v2 也不会有它。
4. **「公开之后别人能做什么」是另一个问题**，由权限回答（能不能列出文件结构、能不能读文件），不挤进 `visibility`。

## 理由

- **为什么不把「搜得到」与「进得去」当成两个轴。** 两条轴一交叉，「`public` 但不可搜」与 `unlisted` 就是同一个状态的两个名字——而后者还更短，于是人会开始用两个词说同一件事。同一个状态有两个名字，就是两份会漂的真相。
- **为什么不把 `unlisted` 留给 v2。** 它只有一种用途：把链接给特定的人，但不让搜索看见。而这件事已经有一条更精确的路——`skill_grant`（[ADR 0034](0034-skill-level-sharing.md)）：把**一个** skill 给**一个**用户。`unlisted` 是「给任何拿到链接的人」：谁拿到了谁就有、给出去收不回、也没有一份名单。目标态 S11 想要的是「分享给外部同事」，而分享的真实要求是**知道给了谁、能收回**——`skill_grant` 给得了，`unlisted` 给不了。
- **为什么不是「`public` 但作者可选不进目录」。** 进不进目录是一个**搜索结果**的问题，不是这个对象的状态问题；而 `public` 的定义就是被搜到。想让它不被搜到，唯一诚实的表达是「不公开」——否则这个开关只是 `unlisted` 换了个名字。
- **为什么命名空间那一列一起收。** 那两处列注释是同一句话抄了两遍，值域也是同一个概念（「这个对象要不要出现在别人的搜索里」）。只改一处会留下一个**同名列、不同值域**的 schema，而消灭的正是这种两处不同步——`namespace.visibility` 是同一个问题的第二个实例，不是另一个问题。
- **为什么这条要单独记。** 它把 schema 与目标态都写着的三个值收成两个，而**不会有任何一条测试因此失败**：v1 不写这一列、也没有接口读它。这种不一致在没有记录的情况下会一直躺在列注释里。

## 后果

- **迁移里那两处列注释现在是错的**（`V1__baseline.sql` §3.2 与 §3.3；`V2__seed_owner_and_namespaces.sql` 里还有一句「public/unlisted are reserved for v2」是同一件事的第三次复述）。**本次不改迁移**：迁移一旦应用就不该回改（会破坏 Flyway 的校验和），而 v1 只写 `private`，改注释不改变任何行为。更正挂到下一次真正需要动这两张表的迁移上。
- **目标态文档仍然是四档**（`docs/target/design.md` 的可见性值表把 `unlisted` 定义为「不可搜到，但拿到链接可访问」，S11 用它表达分享）。差异记在 [`docs/target/README.md`](../target/README.md) 差异清单第 10 条。**本次不改 `design.md`**：要改 S11，得先回答那个场景改用 `skill_grant` 之后长什么样。**target 的 `org` 不在本条范围内**——那是「没做」（v1 不做组织模型），不是「不要了」。
- **v1 的已交付行为不变**：不做公共发现、这一列只写 `private`、没有接口读它、没有测试覆盖它。三个值收成两个，改的是文档与将来的设计，不是今天的行为。
- **控制台演示件照此实现**（`design/demos/dir3-hara-console.html`）：权限页上是三档「私有 / 公开 · 只能调用 / 公开 · 可以看整个文件夹」——那是 `visibility`（两态）与权限的组合，不是三个可见性。「公开 · 只能调用」要的是**一个新权限位**（今天 `invoke` 拿到正文，而「清单 / 正文 / 单个文件」是同一个用例、同一个判据），那是另一条待写的取舍。
