# ADR 0171 · API key 的有效期是用户的选择，不是部署的一个数

- **状态**：已采纳
- **日期**：2026-11-09
- **依赖**：[ADR 0038](0038-default-credential-is-an-api-key.md)（第一方的默认凭据是用户自己签发的 API key）、[ADR 0039](0039-api-key-defaults-and-their-edges.md)（90 天预选、配置只约束新建）、[ADR 0040](0040-api-key-in-the-cli-now-the-browser-path-later.md)（签发只在控制台）、[ADR 0042](0042-the-expiry-setting-is-a-cap.md)（部署的有效期配置是上限）
- **取代**：[ADR 0039](0039-api-key-defaults-and-their-edges.md) §决定 1 的「关掉则新 key 可以不过期」与 §理由 的「为什么预选 90 天而不是 365 天」；[ADR 0042](0042-the-expiry-setting-is-a-cap.md) 的「一个数兼默认值与上限」。**0038 §决定 3 的 365 天默认不恢复**；新的默认仍是 90 天。旧 ADR 的正文保持提交时的样子，状态行记这次收窄
- **不改**：[ADR 0039](0039-api-key-defaults-and-their-edges.md) 的「写蕴含读」「配置只约束新建」「续期换一把新的」「两条审计信号」；[ADR 0040](0040-api-key-in-the-cli-now-the-browser-path-later.md) 的「签发只在控制台」；[ADR 0042](0042-the-expiry-setting-is-a-cap.md) 的「上限是上限、不是建议」

## 背景

0039 把有效期从 0038 的「缺省 365 天」降到「界面预选 90 天」，理由写得很清楚：参照产品的 365 天是挂着一整套 60 / 30 / 7 天邮件提醒的，而本产品没有邮件通道，一年之后 N 台机器会在同一天静默失效。0042 又把 `lifetime` 钉成「默认值兼上限」，让运维的唯一一个安全旋钮不能被客户端绕过。

这两条一起造成一个结果：**用户只有「90 天内的某一天」一个选择**。想要一年，得让运维改部署配置；想要不过期，得关掉整个部署的过期开关，而那会让**所有人**的新密钥都不过期。用户真正想说的是「这把 key 用在哪、该活多久」，而不是「请给我一个日期」。

2026-11-09，产品负责人要求与 GitHub 对齐：GitHub 的创建表单给默认档与自定义日期，fine-grained PAT 的 API 接受 **1–366 天或 `none`**，并对**一年未使用**的 PAT 自动撤销。来源：[managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)（2026-11-09 查）与 [token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation)（2026-11-09 查）。这是一次**有意的取舍反转**：接受更长的寿命，同时补一个自动兜底。

## 决定

1. **每条 key 自己选有效期**：新建表单给 **30 / 60 / 90 / 365 天、自定义日期、不过期**；默认预选 **90 天**。
2. **上限固定 365 天，不再是一个部署配置**：`skillmaster.api-keys.lifetime` 与 `SKILLMASTER_API_KEYS_LIFETIME` 删除；`ApiKeyPolicy` 里是两个常量——`MAX_LIFETIME = 365 天` 与 `DEFAULT_LIFETIME = 90 天`。`defaultExpiry` 取 `now + 90 天` 与上限的较早者（90 < 365，所以总是 90 天）。
3. **「不过期」是一个部署开关加一个每把 key 的选择**：`skillmaster.api-keys.allow-no-expiry`（默认 `true`）决定表单是否出现这一档；部署关掉它时，直接请求「不过期」被拒绝。旧的 `api-keys.expire` 删除。**部署留下的有效期开关只有这一个。**
4. **请求上用独立的 `never_expires` 字段**：`expires_at: null` 的含义仍然是「用部署默认值」，不能同时表示「永不过期」。两个字段同时出现是 400。
5. **续期保留「不过期」这个选择**：旧 key 没有日期时，新 key 也没有日期（部署仍允许时）；部署已不允许时拒绝，让用户新建一把带日期的。有日期的 key 仍按默认 90 天重算（0039 §决定 3 不变）。
6. **365 天未使用自动撤销**：每日任务把 `COALESCE(last_used_at, created_at)` 早于 `now - 365 天` 的未撤销密钥标成 `revoked_at`——**保留行、不删除**，每把写一条 `api_key_auto_revoke` 审计（`actorUserId = null`）。这是连续 365×24 小时，不是 365 个日历日；阈值与到期日是两个口径。
7. **不提供 7 天档**：比控制台「两周内到期」的窗口还短，对续期节奏没有意义。

## 理由

**为什么敢反转 0039 的 90 天。** 0039 自己写着「90 天是启发式起点，不是依据」；它成立的前提是「没有提醒通道，所以不能给长寿命」。这次产品负责人选择接受这个代价：长寿命换来的是「贴一次、一年不用回来」；兜底从「提醒」换成「一年未使用自动撤销」——**后者不是提醒，是清理**，这一点必须说清楚：它不会在失效前告诉任何人，只会让一把长期没人用的 key 消失。控制台的「两周内到期」计数仍在，但只有打开页面的人看得到。

**为什么是 365 天，不是 366。** GitHub fine-grained 的 API 上限是 366 天，classic 的「一年」走自定义日期；本产品的其余寿命都以天为单位（`P90D`、`latestDay` 的按日算术），365 是同一套语言。多出的一天不会让任何真实场景多活一天，却会让「一年」在闰年与平年之间换一个数。

**为什么默认仍是 90 天，而不是 GitHub 的 30 天或一年。** 90 是 0039 已经论证过的启发式：短到能给一次泄漏封一个季度，长到不会让「贴一次、到处用」每个月重来。GitHub 的 30 天有它的表单与提醒体系托着；我们没有。默认值不等于上限，想选一年的人可以在下拉里选。

**为什么这次把上限收回产品。** 0042 曾经把 `lifetime` 留在部署手里，理由是它是这个体系里唯一由运维决定的安全参数。这次产品负责人选择**固定 365 天**：一个产品、一个上限，模型更简单，表单永远只有六档，不需要「部署把上限调小后哪些档位消失」这套分支。代价是这个旋钮没有了——一个想把自己部署里的 key 限制在 90 天以内的运维，只能靠产品默认值 90 天本身，不能再收紧；想禁止不过期仍然可以（`allow-no-expiry=false`），但禁不了 365 天这一档。这是明确的取舍，不是漏做。

**为什么每把 key 自己选，而不是继续用部署开关。** 部署开关逼所有 key 共用一个答案：CI 想要不过期，临时试用想要 30 天，家里的机器想要一年——它们在同一张表单上。每把 key 的选择把答案放回它该在的地方；部署开关只剩「允不允许不过期」这一件事，名字也从 `expire` 改成 `allow-no-expiry`，因为它现在的含义与旧名正好相反。

**为什么「不过期」要独立字段。** `expires_at: null` 在签发请求里已经有一个含义：用部署默认值（0039 §决定 1）。同一位置再表示「永不过期」会让两个相反的意思共用一个 `null`——一个客户端想「什么都不指定」时会被读成「永不过期」，而这是最不该被默认选中的那个。`never_expires: true` 是一次显式的选择，漏写不会得到它。

**为什么自动撤销是软撤销。** 删行会让列表再也说不清「它曾经存在过」，也会抹掉 0039 §决定 4 买回的「已撤销的 key 再次出现」这条审计信号——一把被自动撤销的 key 如果还在某台机器上，再出现时我们仍要认得出它。软撤销把「何时停止工作」写进 `revoked_at`，列表显示「已撤销」，CLI 拿到的仍是现成的 `token_revoked`。

**为什么续期要保留不过期。** 0039 说「续期换的是新签发的默认日期」，那是因为有日期的 key 有一个旧日期可搬、搬旧日期会让续期指向落空。不过期的 key 没有日期可搬；把它续成 90 天等于在用户没要求的时候静默缩短寿命。保留这个选择是同一原则的另一半：续期不改变用户的选择，只换一串新的。

**为什么拒绝「部署已不允许不过期」时的续期，而不是降级。** 降级会让「我续了一下，它变成 90 天了」成为一句用户没说过的话。拒绝并说清「这个部署不再签发不过期的密钥，请新建一把带日期的」，把选择交回用户。

## 后果

- **0039 的「为什么 90 天」不再成立为一条安全论证**，而是一条产品默认值的选择。0039 的正文保持原样；状态行记这次收窄。
- **0039 §决定 1 与 0042 的「一个数」被取代**：默认 90 天与上限 365 天都是产品常量（`ApiKeyPolicy.DEFAULT_LIFETIME` / `MAX_LIFETIME`）；`lifetime` 部署配置已删除。0042 的「上限按天、按上海日、由服务端下发」全部保留。
- **配置契约变了**：`SKILLMASTER_API_KEYS_EXPIRE` 与 `SKILLMASTER_API_KEYS_LIFETIME` 都删除；唯一留下的有效期开关是 `SKILLMASTER_API_KEYS_ALLOW_NO_EXPIRY`。`expire` 的语义还反了——旧的 `false` 是「所有新 key 都不过期」，新的 `allow-no-expiry=false` 是「不允许不过期」。已核实 `deploy/`、`.env.example` 与 compose 都没有设置这两个变量，所以没有线上部署要迁移；将来有部署显式设过它们，要按新的含义重写，`LIFETIME` 则无处可设。
- **部署不能再收紧上限**：一个想把 key 限制在 90 天以内的部署，只能依赖默认值 90 天，不能再把 365 天的档位拿掉。想禁止不过期可以，想禁 365 天不行。这是这次选择买掉的旋钮，不是漏做。
- **更长的寿命是真的更长**：一年期的 key 泄漏之后，窗口从 90 天变成 365 天；「不过期」的 key 泄漏之后，唯一的发现途径是用户自己看 last-used，或等一年未使用的清理——**而正在被使用的泄漏永远不会触发清理**。这是这次取舍买掉的东西，不是意外。
- **没有提前通知**：自动撤销不会发邮件、不会发站内信（没有通道）。控制台是唯一能看到「快到期 / 将被清理」的地方；「两周内到期」只覆盖有日期的 key，不覆盖「长期未使用」。
- **列表状态会移动**：一把过期且 365 天未用的 key 会从「已过期」变成「已撤销」；四格计数跟着动。这是软撤销的可见结果。
- **清理的时钟与到期日不同**：清理按连续 365×24 小时，到期日按上海日末。一把到期日仍在今天的 key，可能先被清理任务标成「已撤销」；这是「未使用」而不是「已过期」的直接结果，不是漏做。
- **CLI 不需要改**：`skmr auth status` 已把 `expires_at: null` 显示成「不过期」；`token_expired` / `token_revoked` 两条路都已存在。CLI 签发仍是 [ADR 0040](0040-api-key-in-the-cli-now-the-browser-path-later.md) 的例外，已另记 [`docs/current/TODO.md`](../current/TODO.md) 的「CLI 签发 API 密钥」。
- **接口与测试要一起改**：`GET /web/keys` 的 `policy` 换形状（`allow_no_expiry` / `default_days` / `lifetime_days` / `latest_day`），`POST /web/keys` 多一个 `never_expires`，错误用 `invalid_expiry` 承载 `field=never_expires` 的 `not_allowed` / `conflicts_with_expiry`。服务端、控制台、设计件与测试在同一版里改，不留给部署去猜。
- **将来要做的**：通知通道（到期前提醒、自动撤销前提醒）能把这次取舍的代价降回来；按 key 的「续期保持原有效期」开关仍不在范围内（0039 已否过）。
