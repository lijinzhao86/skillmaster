# ADR 0088 · CLI 的主版本号就是它说的 API 代次

- **状态**：已采纳
- **日期**：2026-10-25
- **依赖**：[`versions/v17-cli-startup/technical-design.md`](../versions/v17-cli-startup/technical-design.md)（发布产物、`--version`、安装说明页）

## 背景

CLI 今天没有版本号：没有 `--version`，没有版本变量，也没有发布流程。它第一次要以二进制形式发给陌生人，于是三个问题同时摆上来——二进制放哪、版本怎么编、**服务端接口换代之后，已经发出去的旧 CLI 怎么办**。

第三个问题是真正的难点。`/api/v1` 这个代次在 CLI 里写成 **29 处字面量、散在 9 个文件**，没有集中的前缀常量。服务端一旦换到 v2，今天发出去的每一个二进制都会在所有命令上失败，而用户看到的多半是「skill not found」这类**错的诊断**——他不是找不到 skill，是整个地址都不存在了。约束因此是：**旧 CLI 必须能自己说出「我太旧了」，而不是让每个人去猜。**

候选三条：

1. **标准 semver**：主版本只表示 CLI 自己的破坏性变更，API 代次写在 `--version` 的输出和文档里（形如 `skillmaster 3.1.0 (API v2)`）。不破坏 semver 的通行含义，但把「这个二进制跟哪一代服务端说话」这个**最要紧的事实**放进了括号。
2. **主版本 = API 代次**：`1.x.y` 说 `/api/v1`，`2.x.y` 说 `/api/v2`。版本号本身就是一句兼容性断言，一眼可读；代价是主版本不能再表达「CLI 自己改了命令」。
3. **对齐服务端产品版本**（kubectl 之于 Kubernetes 那种）：主版本恒为 1，次版本追服务端。这里没有对象——我们的服务端没有对外的产品版本号，只有部署 sha。

## 决定

1. **主版本号 = CLI 说的 API 代次**：`1.x.y` ↔ `/api/v1`，`2.x.y` ↔ `/api/v2`，依次类推。**第一个正式版因此是 `1.0.0`，不是 `0.x`**——它说的是 v1。
2. **同一主版本内，CLI 的命令面只增不减**。改名的做法是「新名 + 旧名留作别名 + 弃用提示」，删除与语义改变一律留到下一个主版本。次版本表示新增能力，修订号表示修缺陷。
3. **代次编译进二进制**：`internal/api` 里一个前缀常量是 `/api/v1` 的唯一来源（今天非测试代码里那 **17 处**字面量收进它，2026-10-25 实测）。`--version` 同时打印两者：`skillmaster 1.0.0 (API v1)`。
4. **换代的协议**：服务端换到新一代时，新旧两代**并行一段时间**；旧代退役后，旧路径返回 **410** 与 `{"code":"api_generation_retired","supported":["v2"]}`。CLI 遇到这个码，渲染成一句能照着做的事：「这个 CLI 说的是 API v1，服务器已经只支持 v2。按 https://www.skillmasterai.com/install/skillmaster.md 重装。」**判断由码决定，不由句子决定。**
5. **发布物**：阿里云 OSS 上的自有域名 `https://dl.skillmasterai.com/`，由 tag `cli/vX.Y.Z` 触发构建与上传。资产名**不带版本号**——六个包（macOS / Linux / Windows × arm64 / amd64）、`checksums.txt`、两个安装脚本——因此安装说明里的地址**永远不需要跟着发版改**。**不放 GitHub Releases**：目标用户在国内，GitHub 的下载地址对他们不可用；git tag 仍然标记版本历史，但产物只有一个家。
6. **推翻这一条要走 ADR**。「CLI 需要破坏性变更、但服务端不换代」这种情况真的出现时，先写一条取代本条的 ADR，不许靠把某个次版本号说成「其实是破坏性的」糊过去。

## 理由

- **版本号要回答用户真正会问的那个问题。** 用户不会问「这一版 CLI 的接口与上一版兼容吗」——那是我方内部的语义；他会问「我这版还能不能连上」。把代次放进主版本，这个问题不读文档就能答；放进括号就等于告诉他「去读文档」。
- **「只增不减」是这套编号的代价，也是它的收益。** 主版本被代次占走后，CLI 不能靠 bump 一个数字来宣布改名。于是每次改名必须先加别名、先发弃用提示——而这正是本仓库一直在做的事（一个东西一个名字，改名要留旧名）。约束与既有纪律同向，不是新增负担。
- **被否的第 1 条不是坏设计**，它只是把最要紧的事实降级。用户拿着一个连不上的二进制时，`(API v2)` 这个括号救不了他——他得先知道括号是有意义的。
- **被否的第 3 条在这里找不到对应物**：追服务端版本要先有服务端版本号，而我们的是部署 sha。
- **资产名不带版本号，是为了让安装说明稳定。** 带版本号只有两种结局：文档跟着每次发版改（漂移的来源），或者文档写死一个版本（很快过期）。`dl.<域名>/<名字>` 这个稳定地址，只有在文件名本身不带版本时才成立。
- **下载地址要放在用户打得到的地方。** 这不是技术偏好：一个装不上的 CLI 等于没发布，而 `releases/latest/download/` 再优雅，对连不上那个域名的人也是 0 字节。代价是自建域名与证书要有人管——认了。
- **410 而不是 404**：与 [ADR 0058](0058-a-version-is-readable-or-not.md) 同一个理由——这个地址**存在过**。退役不是「没有这个东西」，是「它曾经在、现在不在了」。404 会让 CLI 和用户都往「拼错了」或「被删了」上想。

## 后果

- **v17 文档里凡指 CLI 版本的那些 `0.1.0` 全部改成 `1.0.0`**（PRD 验收 1、TD 的产物名与 `--version`、test-plan T01），`--version` 的输出形状定为 `skillmaster 1.0.0 (API v1)`。**TD 里另有一个 `0.1.0` 是 skill 的草稿版本名**，与 CLI 版本无关，不受本条约束。
- **`internal/api` 要收一个前缀常量**，替掉 9 个文件里的 29 处字面量。这是 v17 P0 的一部分——否则「把代次编译进去」只是一句口号。
- **服务端要多一个错误码**（`api_generation_retired` → 410）。**本版不实现**：它是 v2 到来时的义务，记在这里，免得到时候重新发明一次。
- **发布流水线要注入版本**（`-ldflags -X`），发布构建还要把服务端地址注入成生产地址（`config.DefaultServer` 由 `const` 改 `var`）——见 v17 TD §接口。
- **`skillmaster help env` 今天写着「默认 https://skillmasterai.com」，与代码相反**，随本版修掉。
