# 0139 · 通知指向业务对象，不是第二份状态

- **状态**：已采纳
- **日期**：2026-11-04
- **所属版本**：[`v45-notifications`](../versions/v45-notifications/README.md)
- **依赖**：[0052](0052-a-request-is-not-a-grant.md)（申请不是授权；§决定 4 已预判通知面挂在同一个对象上）、[0138](0138-sharing-is-an-invitation.md)（共享是邀请）

## 背景

[ADR 0052](0052-a-request-is-not-a-grant.md) §决定 4 写下过一句话：「没有通知系统……将来有了通知面，它挂在这同一个对象上，不改变这个模型。」v45 就是那个「将来」。同一时期还有第二件事要落在通知面上：平台公告（本版只留底座，不做发布入口）。

于是通知面要同时承接两类东西：

- **请求型**：共享邀请、权限申请、申请结果。它们背后都有一个业务对象（`skill_invitation`、`skill_access_request`），对象自己回答「还能不能处理」。
- **消息型**：平台公告。背后没有业务对象，只有「读没读」。

最直接的诱惑是让通知自己变成状态机：一条通知有 `pending / accepted / rejected`，点「接受」就改通知的状态。这样看起来最省事——一个列表、一个状态列、一个动作。但它会让同一个事实有两个家：邀请行说「待接受」，通知说「待处理」；两边一旦不一致，没有第三个地方能判谁对。

摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 通知自己持有业务状态 | 业务对象与通知各有一份状态，必须永远同步；删除、过期、撤回的每一条路径都要写两处。这正是 [ADR 0052](0052-a-request-is-not-a-grant.md) 拒绝给 `skill_grant` 加状态列的同一个错误，只是换了一张表 |
| b | **通知是业务对象的指针；结果作为快照留档** | 采纳 |
| c | 不做通知，只在协作者页放数字标 | 申请人永远不知道结果（[ADR 0052](0052-a-request-is-not-a-grant.md) §后果 已记下这条欠账）；B 也永远不知道有人共享过 |

## 决定

1. **请求型通知只是指针。** 通知记「谁、对哪个业务对象、做了什么」；「还能不能接受 / 批准」由邀请行、申请行回答。通知**不读也不改**那个答案。
2. **业务对象收口时，通知留一份结果快照。** 接受 / 拒绝 / 过期 / 撤销 / 批准 / 未通过 / 撤回写进通知的 `outcome` 与 `resolved_at`。快照是给历史看的，不是权威：想再确认，看业务对象或审计。
3. **已读与已处理正交。** 已读是每个收件人自己的 `read_at`；已处理是业务对象的结局。读过不等于处理过，未读也不等于还没处理。
4. **处理完的通知留档，不删。** 「待处理」按业务状态筛（`outcome IS NULL` 且未过期），「全部」按时间倒序包含历史。用户回看得到自己过去做过什么。
5. **消息型通知没有业务对象。** 公告只有标题、正文与每个收件人的已读状态；它不进入「待处理」，也不产生动作。
6. **第一版只做站内。** 没有邮件、短信、推送，也没有 SSE / WebSocket；进入页面时拉取。**因为没有外部投递，写入与通知落在同一个事务里**，不需要 outbox。
7. **读的时候按当前权限过滤。** 一条申请通知只对现在仍是那个 skill 的 `管理` 及以上的人可见；一条已接受 / 已批准的通知，如果当事人后来失去了对那个 skill 的读权限，「查看」不再出现。通知的历史不因为权限变化而删除，但也不泄露他此刻打不开的东西。
8. **不把通知做成第二套审计。** 谁对谁做了什么仍记在 `audit_event`；通知是给人看的事件流，不是合规记录。

## 理由

**为什么快照不算「第二份状态」。** 快照写的是**已经发生的事**：邀请被拒绝了，这件事不会再变。业务对象写的是**现在还能做什么**：邀请行还在不在、申请行还在不在。两者不是同一个问题的两个答案，而是一条时间线与一个当前状态。把它们混在一起，才会出现「通知说待处理、邀请行已经没了」这种自相矛盾。

**为什么留档而不是处理完就删。** GitLab 的 To-Do 在处理完后就消失，因为它的定位是「待办」；2026-11-04 与所有者对齐时，这一条被明确否掉：**用户自己可能都不记得过去做过什么操作**。留档的代价是列表会变长，用「待处理 / 全部」两个页签解决；收益是通知面同时能回答「现在要做什么」与「以前发生了什么」。

**为什么站内第一版不需要 outbox。** outbox 解决的是「业务写成功了、外部投递失败了」的双写问题。这里没有外部投递：通知是同一数据库里的一行，和业务写入在同一个事务里，要么都成、要么都不成。等到加邮件或推送时，那条通道才是需要 outbox 的地方——那时补，不是现在预先造一套没有失败模式的机制。

**为什么读的时候还要按权限过滤。** 通知是「当时发生的事」，但它的收件人名单会过时：一个 `管理` 被降成 `维护` 之后，他不再有资格处理那条申请。GitLab 的做法是失去权限后一小时内删除相关 To-Do；我们保留历史，但在读取时把不再有权处理的通知挡在列表外、把打不开的「查看」收起来——**保留事实，不保留一个点下去会 404 的动作**。

## 后果

- **两张表**：`notification`（事件与结果快照）与 `notification_recipient`（每个收件人的已读状态）。广播型公告的正文只存一份，收件人一人一行已读——这是 [PRD A7](../versions/v45-notifications/prd.md) 的验收对象。
- **通知模块（M14）不依赖 skill 模块。** 它只读写自己的两张表；收件人名单、当前权限、skill 地址都由顶层用例从 M12 取来再传进去。这样 M12 可以调用 M14 发通知吗？也不——两者都不互相 import，编排在 `usecase/`。这是模块规则 1 的直接结果。
- **通知可能比业务对象活得久。** 邀请行被删掉之后，通知仍记得它被接受过；`skill_id` 指向的 skill 如果被硬删，通知随外键级联删除（不保留一条指向 404 的历史）。
- **没有实时推送，就没有「立刻看到」。** 未读数在进入页面时拉取；同一账号在另一台设备上读掉一条，这一台要等下一次拉取。这是 v45 这一版接受的代价，不是遗漏。
- **加外部通道时要补的东西**：outbox、每个通道的偏好、投递状态与重试、保留期。这些都不在本版，也不应该被半做进通知表。
