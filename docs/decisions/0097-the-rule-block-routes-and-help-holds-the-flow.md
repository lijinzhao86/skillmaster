# ADR 0097 · 规则段只触发与指路，流程写在 CLI help 里

- **状态**：已采纳
- **日期**：2026-10-27
- **依赖**：[`versions/v22-cli-help-and-prompt/`](../versions/v22-cli-help-and-prompt/README.md)、[0096](0096-guidance-lives-on-the-platform.md)（两段引导都在平台技能里）

## 背景

v22 之前，引导只有两层：用户粘进指令文件的**规则段**（[0096](0096-guidance-lives-on-the-platform.md) 定的三行）与随二进制发布的 **CLI help**（v16）。两层各自都对，但中间没有约定——「消费」「本地创作」「在线创作」这些跨命令的流程不属于任何一层，于是 agent 只能逐条试命令。v22 的调研在这些缝里找出 35 条问题，其中 12 条会让 agent 静默做错或根本走不完一趟旅程。

把一条多步流程补进去，有三个位置可选：

| | 放在哪 | 代价 |
|---|---|---|
| 1 | 规则段 | 每一轮会话都占上下文，而且粘过的人不会自动更新 |
| 2 | CLI help（新增主题） | 只有真正需要时才读；随发版传播 |
| 3 | 新增一个官方技能（如 `skillmaster/authoring`） | 多一个入口，多一次「该不该用」的判断 |

## 决定

1. **规则段只回答三个问题**：什么时候该用 SkillMaster、第一步做什么、去哪查。不写流程、不写参数名。
2. **多步流程写在 CLI help 的两个主题里**：`skillmaster help workflow`（消费 / 本地创作 / 在线创作三条主流程）与 `skillmaster help auth`（两种凭据）。
3. **两层之间只有一条单向引用**：规则段末尾指到这两个主题。
4. **规则段有硬预算**：≤ 3 行 / ≤ 300 字；参数名一律不出现，`--scope public` 是唯一例外（它改变的是「问的是哪一类东西」）。
5. **help 文本按「上下文税」写**：一句一个事实、示例能表达的不再复述、不写框架词、失败给动作、不复述参数名。

## 理由

- **上下文税是最贵的成本。** 规则段每一轮都在 agent 的上下文里；流程有十几步，写进去等于每次会话都付一遍，而绝大多数会话并不做这件事。
- **更新必须能传播。** 规则段一旦被用户粘进自己的文件，CLI 改得再好也到不了那里；放在 help 里则随发版生效，改动只需要用户升级 CLI。
- **被否的第 1 条**：把流程写进规则段，等于把「参考」当「守则」——它会在每次会话里出现，且改一次就要请所有人重粘。
- **被否的第 3 条**：新增技能会增加一次「该不该加载」的判断，而这项判断本身就是 agent 容易做错的地方；两个主题已经能装下。
- **不追求自动更新用户的文件**：那是用户的文件，CLI 只在旅程里、经人同意才改。

## 后果

- **help 成了流程的权威**：流程改动随 CLI 发版传播，不再有第二份会漂的副本。
- **规则段更新后老用户不会自动知道**：本版不做版本标记（v22 PRD §不做 6），粘过的旧规则会一直生效到用户重跑一次旅程。这是已知代价。
- **help 的写作有了约束**：新增主题各 ≤ 512 B；其余帮助页仍受 v16 的「八项 + ≤ 2 KB」。涨预算要单独评估，不能顺手放宽。
- **规则段的权威仍在平台上**：`skillmaster/startup` 的 `steps/03-prompt.md` 是唯一正文，本 ADR 只定它写什么、不写什么。
