# 0191 · 反馈附件是私有、不自动审核的命名对象

- **状态**：已采纳
- **日期**：2026-11-13
- **所属版本**：[`v65-feedback-attachments`](../versions/v65-feedback-attachments/README.md)
- **依赖**：[0130](0130-large-blobs-live-in-object-storage.md)（对象存储的接缝）、[0189](0189-feedback-is-kept-indefinitely-with-an-object-copy.md)（反馈长期保留与归档）、[0188](0188-feedback-consent-lives-on-the-agent-channel.md)（同意记录在 agent 通道）
- **相关**：[`v64-feedback`](../versions/v64-feedback/README.md)

## 背景

v64 的反馈只收一份文本；用户贴的截图与录屏只能留在对话里，平台拿不到与回执对应的现场。v65 要把图片与短视频一起收下。摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 复用 M6 的内容寻址 `blob`：附件按 sha256 存，撤回时不管字节 | 内容寻址没有「这一条反馈的这份附件」这把引用；撤回要等引用计数清扫，做不到「撤回即删」；大文件还会把数据库撑大 |
| b | **私有 OSS 的命名对象 + M18 的附件行** | 采纳 |
| c | 预签名直传：CLI 拿 URL 直接写桶，服务端只记键 | 多一套鉴权与过期清理；100 MiB 的单请求已经够用，当前量级没有收益 |
| d | 公开桶或可分享的下载链接 | 反馈是私有收件箱；公开链接把「只有运营能看」变成「知道链接就能看」 |
| e | 接阿里云内容安全，上传即审 | 多一个云服务、费用、异步状态机与误杀处理；反馈不公开、量小，当前不划算 |

## 决定

1. **附件由服务端接收并写入私有 OSS**，作为命名对象；对象键为 `feedback/attachments/YYYY/MM/DD/<ULID>.<ext>`，不含原文件名，不含回执号。CLI 不直写桶，也不拿预签名 URL。
2. **M18 新增 `feedback_attachment`**，记归属、顺序、原文件名、服务端识别的媒体类型、字节数、服务端计算的 sha256 与对象键。数据库是附件元数据的主，OSS 是字节的家。
3. **提交时单请求 `multipart/form-data`**：文本字段与附件 part 在同一个请求里；不带附件的 JSON 请求保持 v64 的形状，旧客户端不升级也能继续提交。
4. **不做自动内容审核**。v65 只做技术校验：文件头识别、类型白名单、单文件与合计大小、数量、空文件与不可读。残余风险由「私有桶 + 无公开路由 + 只有运营可读 + 用户可预览与撤回」承担；附件量起来、出现违规内容投诉、或附件需要公开展示时重开这条决定。
5. **不剥离图片元数据**（EXIF/GPS、XMP）。v65 原样保存证据，预览里明确提示「截图可能含位置等信息」。用户反馈元数据泄露或合规评审要求时，另开一条 ADR 决定剥离方式。
6. **不提供任何返回附件字节的 API 路由**，也不生成公开链接。运营按数据库里的对象键直接读私有桶；将来运营工作台要下载时，另做带鉴权的路由。
7. **撤回先删对象、再删行**：先删每个附件对象与归档对象，再删 `user_feedback` 行（附件行随 `ON DELETE CASCADE` 消失）。对象删失败就整笔回滚，行留着，下一次还能按键重试。归档 NDJSON 只带附件元数据，不复制字节。
8. **隐私政策升到 1.3**：写清附件的收集、私有存储、长期保留、撤回删除、不会自动扫描图片内容、元数据可能保留。同意版本随每次提交记录。

## 理由

**为什么不是内容寻址的 `blob`。** v64 的撤回是「删对象 + 删行」两件确定的事；`blob` 的删除靠引用计数扫描，撤回要等清扫，和「运行 `skmr feedback delete` 后查不到」的验收冲突。附件也不做去重：同一张截图在不同反馈里是两个证据，不该共享一条引用。

**为什么不是预签名直传。** 它把桶的写权限短暂交给客户端，要新增签名、过期、未完成上传的清理；而单请求 multipart 在 100 MiB 上限内已经够用。等单条上限到数百 MiB 再谈分片与直传。

**为什么可以先不审核。** 反馈不是公域内容：桶私有、没有公开链接、没有运营界面，只有持有 RAM 凭据的运营能读。审核要解决的是「公开传播」与「平台背书」，这两件事今天都不成立。代价是：如果用户上传了违规内容，平台在运营读到之前不知道；这条残余风险写在这里，不藏在实现里。

**为什么原样保存图片。** 截图与录屏是证据，重编码会改变字节、可能损坏证据；剥离 EXIF 要做 JPEG 段/PNG chunk 级的二进制改写，v65 没有把握在不损伤文件的前提下做对。先提示，后处理。

**被否掉的：** 内容寻址（撤回做不到即删）、预签名（多一套鉴权与清理）、公开桶（私有边界失守）、自动审核（当前量级成本大于收益）。

## 后果

- **OSS 从「归档副本」变成「提交链路的一部分」**：附件提交要求部署启用对象存储；对象存储不可用时返回可读的 503，文本反馈不受影响。
- **上传先于数据库事务**：对象存储不能加入数据库事务。提交顺序是「校验 → 上传对象 → 一个事务写反馈行、附件行、通知与审计」；写库失败时按已上传的键逐个删，删不掉就记日志留键。进程在两步之间崩溃会留下没有行指向的对象——量小，先接受；将来可以用前缀列举与行比对做清扫。
- **运营的读路径是 OSS 控制台 + 数据库查询**：按回执查 `feedback_attachment` 拿对象键，再在桶里看。没有新的鉴权面，也没有新的泄露面。
- **附件内容不经过文本扫描**：密钥前缀替换只作用于文档；图片里的密钥、个人信息与元数据不会被自动发现。隐私政策与预览必须如实说清，这是本条决定的产品代价。
- **类型与上限是版本契约**：5 个、图片 10 MiB、视频 50 MiB、合计 100 MiB；改数值是改对外契约，按大版本走。
- **`source` 仍只有 `cli`**：控制台入口已记进 [`docs/current/TODO.md`](../current/TODO.md) 的「控制台反馈入口与附件表单」，将来加 `console` 时复用同一接口与存储。
- **CLI 的临时附件不删除**：发送成功后截断为 0 字节，不 `unlink`（[ADR 0101](0101-the-cli-never-deletes-files.md)）；`$TMPDIR/skmr-feedback/` 会留下空壳，由系统的临时目录清理收走。字节不再留在磁盘上，但文件本身还在——这是 ADR 0101 与隐私的最小交点。
