# 0071 · 提交到已删除的名字答 409 `skill_deleted`，不是泛泛的 400

- **状态**：已采纳
- **日期**：2026-10-21
- **依赖**：[0050](0050-deleting-a-skill-can-be-undone.md)（删除留名、恢复是一个有意的动作）
- **这一条修订 [0050](0050-deleting-a-skill-can-be-undone.md) 中「提交到已删名字 → 400 `invalid_request`」那一条的状态码与码名**：决定本身（拒绝而不是复活）不变

## 背景

[0050](0050-deleting-a-skill-can-be-undone.md) 定的是「提交不能让删除变成建议」：一个无人值守的 `skillmaster skill submit` 不该把删掉的东西复活。它的落法是 400 `invalid_request`——请求本身不成立，客户端没有可分支的东西。

v9 给网页加了两个「把名字带进来」的入口（导入到我的 skill、新建 skill），这两个入口在名字被已删除的 skill 占着时，**唯一正确的下一步是去恢复**。一个泛泛的 400 在页面上只能显示一句失败；用户看不出这是「名字被占着」，更不知道恢复在哪儿。CLI 侧同理：`skill submit` 拿到 400 只能打印服务端的英文原句。

## 决定

1. **这个名字被已删除的 skill 占着时，答 409 `skill_deleted`**，消息说明恢复在网页上（`POST /web/skills/{ns}/{name}/restore`）。
2. **只换状态码与码名，不换语义**：仍然是拒绝，仍然不复活，仍然要求一个人显式去恢复。
3. **两个入口的差异保留**：个人命名空间的提交与「我的 skill」导入看得见已删除行，因此拿 `skill_deleted`；地址式提交（`--to` / 版本列表导入）看不见已删除的 skill，仍是 404 `skill_not_found`——与「看不见的行与不存在的行不可区分」这条既有口径一致。
4. **网页把码翻成一句可执行的提示**：「这个名字属于一个已删除的 skill。」并给 `去恢复`；CLI 翻成一句中文并给退出码 1。

## 理由

**为什么是 409 而不是 400。** 请求本身完全成立，冲突的是名字的当前状态；409 表达的正是「与资源当前状态冲突」。400 会让客户端以为参数写错了，而参数没错，错的是时机。

**为什么值得一个具名码。** 拒绝的出路只有一条，而那条出路（恢复）不在这个请求里。一个能被客户端识别的码，才能让页面把用户直接送到那儿；否则每个入口都要靠匹配英文消息来猜。

**为什么地址式提交不跟着改。** 那个入口连已删除的行都看不见（`deleted_at IS NULL` 过滤），给出 `skill_deleted` 等于告诉调用者「这个名字曾经存在」——那正是 404 的「不泄露存在性」要避免的。

## 后果

- `ErrorCode` 多一个值；`ApiExceptionHandler` 里 `SkillDeletedException` 的映射从 400 `invalid_request` 改成 409 `skill_deleted`。
- CLI 的提交路径要能读到 409 的码（今天 409 只落成一句「服务端答 409」），否则中文提示命中不了。
- 网页两个入口多一个「去恢复」的链接；新建 skill 那条把它与 `skill_already_exists` 并列成两种冲突。
- ADR 0050 正文不改，只在文件头标注这一条修订了它的状态码。
