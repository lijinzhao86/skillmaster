# 0165 · `skmr run` 起进程，只改写 `scripts/` 内的相对路径

- **状态**：已采纳（§7 的解析路径由 [ADR 0178](0178-run-resolves-drafts-through-the-author-plane.md) 扩展）
- **日期**：2026-11-08
- **所属版本**：[`v51-skill-runtime`](../versions/v51-skill-runtime/README.md)
- **依赖**：[ADR 0164](0164-state-is-tiered-by-what-it-writes.md)（缓存位置）、[ADR 0101](0101-the-cli-never-deletes-files.md)

## 背景

真实 skill 的 `SKILL.md` 里有两种调用写法，抽样都见过：

- **作者站在 `scripts/` 里**：`python3 plan_validation.py --list-frameworks`、`python x.py` —— 没有路径，隐含的工作目录是 `scripts/`。
- **作者站在 skill 根**：`node "<skill-dir>/scripts/relay.mjs"`、`bash <skill-dir>/scripts/idea-refine.sh` —— 自己发明了一个目录占位符。

两种写法在作者本机都对，因为**他知道自己当时站在哪**。平台不知道。而 agent 的 Bash 工具用哪个工作目录，也不是我们能控制的。

同时，生态里没有任何客户端提供统一的「skill 目录」变量：Claude Code 有 `${CLAUDE_SKILL_DIR}`，其余三家没有；要求作者改成那个写法，等于让现存的绝大多数 skill 重写一遍。

## 决定

`skmr run <地址>[@版本] [--cwd <目录>] [--cache-in <目录>] [--no-cache] [--yes] [--json] -- <命令...>`

1. **CLI 起进程，并回传子进程的退出码。** 不是「只做准备、让 agent 自己跑」——那样工作目录仍然不受控。
2. **只改写能解析到 `scripts/` 内相对路径的参数。** 逐个看参数：不是绝对路径、不以 `-` 开头、且扩展名在白名单里（`.py .sh .js .ts .rb .pl .ps1` 等）的，才去 `scripts/` 下找；找得到就替换成绝对路径，其余参数**一个字节都不动**。白名单而不是「不像旗标就当路径」——命令里的输入 CSV、输出目录、URL 都是参数，改写它们等于把脚本没要的路径塞给它。命中多个或找不到就报错，列出 `scripts/` 下有什么，不猜；`../x.py` 这类解析到 `scripts/` 之外的，按找不到处理。
3. **默认工作目录是 `<skill>/scripts/`**（不存在时是 skill 根），`--cwd` 覆盖。
4. **环境原样继承**，只额外注入一个 `SKILLMASTER_SKILL_DIR`。
5. **不推断解释器**：命令的第一个词就是可执行文件，原样执行；解释器不存在时说清缺什么。
6. **首次执行某个 digest 前确认一次**，之后记在状态目录里；`--yes` 跳过。粒度是 digest 而不是地址：同内容的两个地址是同一份代码，问两次没有多问出一个决定。
7. **缓存按 digest 寻址，地址到 digest 的解析结果本机记一份。** 缓存目录名是 digest，而 digest 只有服务端知道；不记住上一次的答案，断网时就没有任何办法把 `dev/x` 变成缓存里的那个目录。

## 理由

- **为什么起进程。** 「工作目录」是这一版要解决的核心问题之一，而它只有在我们自己 `exec` 时才能保证。把准备和执行拆开，等于把最容易出错的一步留给 agent 的 cwd。
- **为什么只改 `scripts/` 内的路径。** 位置的约定是「只有 `scripts/` 可执行」（PRD 做 #2）。改写别的目录会越权，也会把数据文件误当脚本。命中不唯一时不猜，因为猜错的表现是「跑了一个不该跑的文件」，比报错危险得多。
- **为什么默认 `scripts/` 而不是 skill 根。** 抽样里 `python x.py`（站在 `scripts/`）与 `python scripts/x.py`（站在根）并存；后者写成带路径的形式时**在 `scripts/` 下也能解析**（`scripts/x.py` 会被解析成绝对路径），而前者只有站在 `scripts/` 才对。所以默认 `scripts/` 两种都能跑；反过来则只有一种能跑。
- **为什么环境原样继承。** 用户的 `PATH`、`PYTHONPATH`、虚拟环境激活状态、企业代理变量都在调用者的环境里。清空环境看起来「干净」，实际是制造「本机能跑、这里跑不了」。
- **被否掉的：**
  - **要求作者改写 `${SKILL_DIR}/...`**：现存 skill 绝大多数要改，且除 Claude Code 外没有客户端认这个变量。
  - **只准备环境、不起进程**：工作目录仍然不受控，问题没解决。
  - **对整条命令做解析/替换**：任何「像路径的东西」都可能被误改，包括正则、SQL、URL。
  - **自动推断解释器**（看 shebang 决定用 `python3` 还是 `node`）：多一次猜，且作者已经写明了解释器。
  - **每次都确认**：沙箱里跑一次要点一次，体验不可接受；按 digest 记住即可。

## 后果

- **退出码与 [ADR 0087](0087-cli-exit-codes-are-a-public-contract.md) 的关系**：`run` 成功启动子进程时，它的退出码**就是子进程的退出码**（可以是任何值）；只有 `run` 自己失败（地址不存在、拉取失败、路径解析不唯一、解释器缺失）才用 0/1/2/4 那套词汇。这是对 0087 的一处显式例外，`--json` 里同时给出 `exit_code`。
- 命令里的相对路径如果指向 `scripts/` 之外（比如 `assets/` 里的数据文件），`run` **不会**改写它；作者需要在正文里写清楚，或改用绝对路径。
- 依赖可执行位直接执行的写法（`./run.sh`）在缓存目录里可能遇到 `noexec`；推荐写法是用解释器调用脚本，这一点写进作者约定。
- 缓存目录名带 digest，同一 skill 的不同版本并存，不会互相覆盖。
- 首次拉取需要网络。之后**连不上服务端时**（而不是「每次都」）用本机记住的 digest 跑缓存里的那份，并在 stderr 说明用的是上次解析到的版本；服务端答了 404 / 403 则不作降级——那是它的意见，缓存没有资格反驳。`--no-cache` / `--cache-in` 是仅有的两个缓存开关，不做后台回收（[ADR 0101](0101-the-cli-never-deletes-files.md)）。
- 这一条取代 [ADR 0008](0008-no-script-execution.md) 的「不在客户端执行脚本」那半：0008 反对的是服务端代跑与破坏「不落盘」，而 v51 的形态是**在用户自己的机器上、用户自己的目录里**执行，缓存落在 `$TMPDIR`，两边都不成立。0008 的平台侧结论不变。
