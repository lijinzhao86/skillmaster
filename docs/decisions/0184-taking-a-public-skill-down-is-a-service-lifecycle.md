# 0184 · 公开 skill 的退场按服务生命周期

- **状态**：已采纳
- **日期**：2026-11-11
- **所属版本**：[`v61-skill-deletion`](../versions/v61-skill-deletion/README.md)

- **相关**：[0175](0175-account-deletion-is-immediate-with-a-fixed-retention.md)（账号注销时的 `skill_unavailable`）

## 背景

SkillMaster 既是 skill 的托管，也是给调用方的服务。一个公开 skill 被下线或删除，不只是「仓库少了一个条目」——别人的服务、定时任务与 agent 会当场拿到错误。今天这件事没有任何预告：

- 下线是**即时**的：`skill.offline_at` 一写，调用方立刻得到 503 `skill_offline`，公域不再出现；
- 删除也是**即时**的：对所有人不可见，地址返回 404；
- 被授权的人、把 skill 入库的人，**不会收到任何通知**；
- 唯一会通知的情形是作者注销账号（`skill_unavailable`），单独删一个 skill 反而不通知。

参照的是服务型产品的通行做法，而不是仓库托管：Google Enterprise APIs 对 GA 服务承诺至少 12 个月通知，Azure 对 REST API 版本同样是 12 个月，AWS 的服务生命周期通常也按 12 个月安排（Google Cloud Deprecation Policy、Microsoft API 与 SDK 生命周期政策、AWS 服务下线公告，2026-11 查阅），[Google AIP-185](https://google.aip.dev/185) 建议 beta 功能也有 180 天。[RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html) 与 [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594.html) 把这件事拆成两个标准信号：`Deprecation`（开始弃用）与 `Sunset`（下线日期），到期后返回 410 Gone，而不是静默 404。

但 skill 比云 API 小得多，一个 `copy` 就能把依赖变成快照；照搬 12 个月会把作者锁得太久。摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 即时删除，只通知受影响的人 | 通知发出去时服务已经断了；对定时任务没有意义 |
| b | 所有公开 skill 一律公告期 | 没有入库者时没有任何依赖方，npm 也只在有依赖者时限制下架；对刚发布、无人使用的 skill 是纯负担 |
| c | **只有「公开、有线上版本且有入库者」才需要过渡期**，期限固定 | 采纳 |
| d | 有入库者时禁止删除，必须运营审批或交接到别人名下 | 冻结了作者对自己内容的所有权；保护可以用通知 + 迁移做到，不需要夺走控制权 |
| e | 另造一个「弃用」状态 | 与「下线」是同一件事的两半，多一个词只会让作者与调用方都要多学一套 |

## 决定

1. **入库是显式的依赖声明。** 保护只附着在 `join` 过这个 skill 的人身上；一次性 `--yes` 调用不算。`join` 的既有语义不变：它是引用，不复制。
2. **公开、有线上版本且有入库者的 skill，下线走三段链路**：在线 → **下线中** → **已下线**。下线中固定 **30 天**，期间**照常可调用**；每次调用都带一条警告，写明下线日期；公域与信息页标「下线中」。**下线中不接受新入库**：入库确认与 CLI 都拒绝 `join`，避免有人刚声明依赖就进入倒计时。没有线上版本时没有可调用的内容：即时下线，仍通知入库者与授权者。
3. **下线中开始与结束时都通知入库者与授权者**（去掉所有者），通知里给出「复制到我的库」的迁移指引——把引用变成快照，是调用方保住自己服务的路径。
4. **没有入库者的公开 skill、以及任何私有 skill（无论共享给谁）**：下线即时完成，删除即时生效；删除后通知入库者与授权者。
5. **公开、有线上版本且有入库者的 skill，必须走完已下线才能删除**；在线时点删除，先引导去下线，而不是直接删。
6. **删除确认显示影响面**：是否公开、授权人数、入库人数。删除后通知所有受影响的人（复用账号注销已有的通知通道与收件人定义：授权者 + 入库者）。
7. **地址语义**：公开且曾发布的 skill 删除后返回 **410 + 原因**；公开但从未发布、以及私有，删除后仍是 **404**；已下线返回 **503 `skill_offline`**（可恢复，调用方据此区分「暂时下线」与「永久消失」）；私有删除保持 **404**，不暴露曾经存在。
8. **作者可以取消下线**：回到在线，警告消失，入库者与授权者收到取消通知。
9. **删除仍然只有所有者能做**；`admin` 不因此获得删除权（[0047](0047-permissions-are-a-ladder.md) 不变）。

## 理由

**为什么保护附着在入库而不是调用。** 入库是用户明确说「我要依赖它」；一次 `--yes` 只是此时此刻读一下。按调用量判定会让作者因为别人偶然用过一次就被锁 30 天，而且作者事先看不出自己受不受约束。npm 的判据也是「有没有依赖者」，不是「有没有下载过」。

**为什么是 30 天。** 它比云服务的 12 个月短得多，因为迁移成本只有一个 `copy` 命令；又比一周长，足以让定时任务的主人在下一轮维护里看到通知并处理。固定 30 天而不是让作者自选，是因为下限一旦可调，一条一天的弃用就把保护变成形式。

**为什么下线中仍然可调用。** 如果立刻停服，这个状态就退化成现有的下线，30 天只剩一个倒计时。它的价值在于「还在服务，但已经宣告退场」，调用方能在继续工作的同时迁移。

**为什么下线中不接受新入库。** 入库是「我要依赖它」的声明；让一个人刚声明依赖就进入一个已知会消失的倒计时，是产品给出一个坏承诺。把新入库挡在门外，比事后通知他「你入库的东西 10 天后消失」更诚实。

**为什么删除要等已下线。** 删除是永久消失；对已经声明依赖的人，至少要走完一次预告。已经下线的 skill 已经不再服务，删除只是把墓碑也收起来。

**被否掉的：** 即时删除（通知晚于断服）；所有公开一律公告（无依赖者的负担）；禁止删除或运营审批（夺走所有权）；单独的弃用状态（同一个状态机的两个名字）。

## 后果

- **新增一个状态与一个到期任务**：下线中需要记录开始时间与到期时间；到期任务把状态推进到已下线，并发出结束通知。取消则清掉这两列。具体列名、表结构与任务进技术设计。
- **调用方会多看到一种输出**： `skill invoke` 在下线中每次打印警告；公域卡片与信息页显示日期；已下线后仍是既有的 503 `skill_offline`。
- **公开且曾发布的删除从 404 改成 410**，[0012](0012-addressing-and-version-pinning.md) 的「删除与从未存在不可区分」对私有面与从未发布的公开 skill 继续成立。
- **通知新增一个 kind**（下线中通知），完成/取消/删除复用公告形态；收件人定义复用账号注销的（授权者 + 入库者），并在完成时不再提示 copy（那时消费面已经关了）；账号注销路径不变。
- **入库确认要写清契约**：入库是引用、作者下线会提前 30 天通知、要长期独立运行请 `copy`；下线中不显示入库入口，CLI 的 `join` 返回拒绝。
- **立即下线不作为产品功能**：作者遇到安全/违规等紧急情况，联系官方邮箱，由平台在后台处理并通知受影响的人。本 ADR 不定义后台流程，也不在界面或 CLI 上开放跳过 30 天的开关。
