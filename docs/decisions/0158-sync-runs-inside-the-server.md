# 0158 · 同步任务留在 server 进程内，按可抽出的接口分层

- **状态**：已采纳
- **日期**：2026-11-06
- **所属版本**：[`v50-open-source-sync`](../versions/v50-open-source-sync/README.md)
- **依赖**：[ADR 0156](0156-sync-writes-as-the-official-namespace.md)（官方写入）、[ADR 0157](0157-sync-is-a-source-neutral-pipeline.md)（底座与适配器分开）

## 背景

v50 要按清单周期同步外部内容。放哪里有三条路：

1. **server 进程内**：新增一个 `@Scheduled` 任务，与现有两个定时任务（来源快照刷新、用量清理）同一做法。
2. **独立子项目、共享同一个库与 domain 代码**：多一个 jar、多一个 systemd unit、多一条部署链路；需要先把 server 拆成多模块，并决定谁跑 Flyway、谁持有 OSS 与 GitHub 凭据。
3. **独立子项目、通过新开的内部 API 写入**：隔离最彻底，但要新增 service token、内部鉴权与内容上传通道。

真正难搬的不是拉取和扫描，是**写官方草稿**：它要经过版本状态机、内容摘要、文件存储、来源与许可表、索引刷新。第二部分是纯函数，放哪都行；第一部分今天只能在 server 里做。

仓库的现实约束：服务端是一个 jar，跑在 ECS 的 systemd 下，没有容器编排；架构规则规定事务只能声明在 usecase，模块内部不可跨模块引用。独立进程要写草稿，要么复制这套 domain（危险），要么新开内部 API（面积更大）。

2026-11-06 产品负责人选了「全部在 server」。

## 决定

1. **同步任务跑在 server 进程内**，用 Spring `@Scheduled` 的 cron：频率与时间由表达式决定，按北京时间解释（默认值见 `config.md`）。启动与服务重启不触发同步，需要立刻跑用手动触发。不新建子项目，不用系统 crontab。
2. **进程内仍然分三层**：来源无关的 pipeline、来源适配器、domain 写入器。pipeline 不 import 任何具体来源，只依赖 `ContentSource` 接口与 M4 / M5 / M7 / M12 的公有只读方法；适配器不碰 domain；写入器是唯一**写** skill / version / blob 模块的层。
3. **可抽出的边界先定好**：适配器、安全扫描、许可判定都是纯组件；将来要拆 cronjob，只搬这三样，写入器通过一个窄接口留在 server（届时把接口实现换成内部 API 客户端，pipeline 不改）。
4. **资源有界**：拉取与扫描阶段有界并发（可配 1–16，默认值见 `config.md`），写入阶段串行；每个上游请求有连接、响应头与整体读取超时，文件数、单文件字节、总字节、整包字节、解压字节都有上限；不执行上游代码，扫描只在内存里做。
5. **单实例假设延续**：与现有两个定时任务一致；将来多实例时先加数据库锁，再谈拆分。
6. **何时重新评估拆分**：扫描变成 CPU/内存大头、同步量让单次运行超过分钟级、需要独立伸缩或独立重启、或要执行不可信代码（本版明确不做）。

## 理由

- **domain 写入是最重的部分，也最不该复制。** 两个进程都能写草稿，等于两套状态机与两套摘要规则；它们迟早会漂。
- **一个部署面比两个便宜。** 新子项目要新增 jar、systemd unit、部署 workflow、环境变量与 Flyway 所有权；这些成本每天都在，同步只是周期性跑。
- **进程内也能隔离。** 同步不执行上游代码，只做 HTTP 拉取与正则扫描；用超时、单线程与大小上限，就能把对 API 的影响压在可接受范围。现有的来源刷新任务已经在 API 进程里做 GitHub 往返。
- **并行只加在拉取上，写入仍串行。** 提交路径对 `version_file` 取表级 `SHARE ROW EXCLUSIVE` 锁，多个条目并行写入也只在同一把锁上排队，还多占连接；所以并发只用于网络拉取与扫描，写入保持一条一条，失败归因与日志也清楚。
- **可抽出性不靠承诺，靠接口。** 只要 pipeline 不 import 具体来源、写入器只通过窄接口被调用，拆分就是换一个实现，不是重写。
- **多实例先加锁，不先拆进程。** 两个实例重复拉取不会损坏数据（写入按 revision 幂等），真正的问题是重复劳动；一把数据库锁比一套新部署便宜。

被否掉的：**独立子项目共享 DB 与 domain**（多模块改造、Flyway 所有权、双份凭据与部署面）；**独立子项目 + 内部 API**（service token、内部鉴权与上传通道，面积超过任务本身）；**系统 crontab**（多一个部署面，还要处理凭据与进程）；**等有队列基础设施再做**（现有两个定时任务已经证明够用）。

## 后果

- 同步任务与 API 共享 JVM：一次异常或内存峰值会影响 API，必须靠大小上限与超时兜住；上线前要验证单条失败不会拖垮其它条目。
- 同步逻辑改动要随 server 发版；不能单独重启或回滚同步任务。
- 将来拆 cronjob 时，`ContentSource`、扫描器与许可判定的接口必须保持稳定；改契约等于改所有来源。
- 多实例部署前必须先加数据库锁，否则两个实例会重复拉取与重复建草稿（幂等能防重复内容，但防不了重复劳动）。
