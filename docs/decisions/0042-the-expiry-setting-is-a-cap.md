# ADR 0042 · 部署的有效期配置是上限，不只是默认值

- **状态**：已采纳
- **日期**：2026-10-15
- **依赖**：[ADR 0038](0038-default-credential-is-an-api-key.md)（第一方的默认凭据是自己签发的 API key）、[ADR 0039](0039-api-key-defaults-and-their-edges.md)（缺省 90 天、部署可配、配置只约束新建）
- **不改**：[ADR 0039](0039-api-key-defaults-and-their-edges.md) 的结论（90 天、写蕴含读、只约束新建、续期重算、两条审计信号全部不变）。本文只钉死它 §决定 1 里「部署可配」那一句被读成两样的地方；**0039 的正文保持提交时的样子不动**（它记的是当时为什么那么选）

## 背景

0039 定下「界面预选 90 天，有效期**部署可配**（关掉则新 key 可以不过期），而配置只约束新建」。写的时候这句话有两处可以读成两样：**那个数是「没人指定时用它」，还是「谁都不许超过它」**。0039 的 §理由 用的是「上限」——「把**上限**调低不改任何已存在的 key」；[`v2` 的技术设计](../versions/v2-credentials/technical-design.md) §接口 照着写「把有效期**上限**调低」。而实现只做了默认值：签发时只校验「在将来」，没有上界。

后果不是理论上的：

- **控制台永远送一个日期**（表单按部署的预选值填好），所以「默认值」在真实路径上一次都不生效；
- 一个 `curl` 客户端可以签一把 `9999-12-31` 到期的 key，哪怕这个部署把 lifetime 设成 7 天——**运维配的是一个可以被调用方单方面取消的数字**。

发现于 2026-10-15 的独立审计（一轮四份，分头读服务端 / CLI / 控制台 / 三端接缝）。

## 决定

`skillmaster.api-keys.lifetime`（原 `default-lifetime`）**同时是默认值和上限**：

1. 请求没带 `expires_at` → 取 `now + lifetime`，**但不超过第 2 条那个上限**（取两者的较早者）；`expire: false` 时是「不过期」。取小者是因为 `P1DT12H` 这类**不是整天**的 lifetime 会越过它自己那一天的上限——而默认值绝不能是一把这个部署**会拒绝**的 key，「一个数一个含义」在边界上也要成立。
2. 请求带了 `expires_at` → 必须**在将来**且**不晚于「`lifetime` 天之后的那个日期所在时区的最后一秒」**，否则 `400 invalid_expiry` / `beyond_maximum`。**上限是「某一天的结束」，不是一个瞬间**：`now + lifetime` 会在当天已经过去的那几秒上比「那一天的结束」早，于是**控制台表单按预选日期提交的那一次必然被拒**（表单送的正是当天结束；实测把这条写成 `now + lifetime` 时，默认表单每次都 400）。日子在哪一天结束由**控制台写日期的那个时区**决定（那里是 `Asia/Shanghai`，见技术设计 §分期 P1 ③）——两处必须同一个时区，否则上海已经跨过零点的那八个小时里上限会比预选日期早一天。这条是 2026-10-15 第二轮审计逼出来的：**原先写的是 `now + lifetime`，两个字读起来一样，含义差一天。**
3. `expire: false`（关掉开关）= **没有上限**。这与「关掉之后可以签一把不过期的」是同一个决定的两面：关掉就是「这个部署不管有效期」，再留一个上限等于关了一半。
4. **仍然只约束新建**：改配置不动任何已存在的 `expires_at`；续期按新配置重算（0039 §决定 2、3 不变）。
5. 控制台的日期选择器把 `max` 设成同一天，并在提示里写出这个上限——**界面不再给出部署会拒绝的日期**。**这一天的值由服务端算好发下来**（`policy.latest_day`），不由客户端按自己的钟重算：两个钟不会一致，而客户端快出的那几秒足以让本地算出的「90 天之后」比服务端的上限晚一天，于是表单拒掉自己的预选值。**界是一个事实，就由拥有它的那一边给出。**

## 理由

**被否掉的：「就当默认值，只改文档」。** 那让运维的配置变成一句无法兑现的承诺：他以为这个部署里的 key 活不过 7 天，而任何客户端都能绕过去。而 lifetime 恰好是这个体系里**唯一由运维决定**的安全参数——熵由代码定，撤销由人决定——把它从安全面挪回「建议面」，等于让唯一一个能被运维调紧的旋钮失效。

**被否掉的：再加一个 `max-lifetime`，默认值归默认值。** 两个数会让「为什么这里能签出 200 天的 key」变成要读两行配置才知道的事，而这两行在部署里多半会一起改。**一个数、一个含义**：这个部署里 key 能活多久。这也是 0039 §背景 里那条经验的延伸——参照产品的 365 天之所以成立，是因为它挂着一整套提醒；一个数字的意义取决于托着它的东西。

**被否掉的：续期时继承旧日期，好让上限只作用于新建。** 那会让「续期」变成把一个过期日期搬到新串上（0039 §理由 已经否过这条：验收 1 要求终端把过期指向控制台续期，而搬旧日期等于指向落空）。

## 后果

- **控制台多一处约束，而这是好事**：选择器给不出部署不接受的日期，人不会先填完再被打回。代价是「想签一把更久的」必须先改部署配置，而不能在表单里绕过。
- **多一个 400 issue**（`beyond_maximum`，归在既有的 `invalid_expiry` 这个 code 下），HTTP 客户端要处理它。
- **配置项改名**（`default-lifetime` → `lifetime`），因为旧名字现在只说了它一半的含义；线上的 `SKILLMASTER_API_KEYS_DEFAULT_LIFETIME` 也跟着改成 `SKILLMASTER_API_KEYS_LIFETIME`。v2 尚未发布，没有需要迁移的部署。
- **不追溯**：把 lifetime 从 365 天改成 90 天的部署里会同时存在两种寿命的 key。这是 0039 §决定 2 的代价，在这里再出现一次——**改一个开关不该悄悄弄死别人正在用的凭据**。
- **`expire: false` 的部署没有上界**，所以「部署可以有多严」这件事取决于它开不开开关；一个既想允许不过期、又想限制最长寿命的部署，本版表达不出来（要表达就得是上面被否掉的那个第二个数）。
- **上限按天，不按秒**：`lifetime` 的秒级零头（`P1DT12H`）在算「第几天」时被丢掉，所以上限可能比字面宽最多一天。这是一个以天为单位的旋钮，用它表达小时没有意义——**所以不到一天的 lifetime 由代码直接拒绝**（`ApiKeyPolicy` 构造时抛，应用起不来）。截断在「不到一天」这一档上不是宽一天，而是**含义反转**：`toDays()` 给出 0，上限落在今天，而今天在 23:59:59 之后就已经过去了，默认值取小者于是一把「出生即过期」的 key——而续期请求根本不带日期，必然走默认值。这是 2026-10-15 第四轮审计量出来的（`PT12H`、上海 23:59:59.5 → `default = 2026-10-15T15:59:59Z`，早于 now），当天按「启动时拒绝」修掉。
- **服务端因此有了第一个时区假设**（`ApiKeyPolicy.DAY_ZONE`）。它与控制台那份是同一件事的两半——控制台按上海日写日期，服务端的界就得按上海日算——而这条依赖是这条 ADR 自己引入的：上限若按 UTC 日算，上海已经跨过零点的那八个小时里，界面预选的日期会被拒。将来读者不在一个时区时，这里要连同控制台的日期语义一起改。
