# ADR 0099 · CLI 有一条 beta 通道，版本串固定、构建身份用提交号

- **状态**：已采纳
- **日期**：2026-10-27
- **依赖**：[0088](0088-cli-major-version-is-the-api-generation.md)（版本号的含义）、[`skillmaster-cli/RELEASE.md`](../../skillmaster-cli/RELEASE.md)（发布的唯一权威）

## 背景

CLI 还没有对外上线，但已经有人要用：`skill check`、重写过的帮助、`grep` 的新范围都在 main 上，而下载站上的正式版停在 `1.0.2`。

接下来一段时间的工作形态是**边用边改**：试用者装一个版本，用着用着提 bug，改完再装。如果每一次修完都走一次正式发布，就会得到 `1.0.3`、`1.0.4`、`1.0.5`……一串只差几天、彼此没有语义差别的版本号。`RELEASE.md` §1 的规矩是「修订号修缺陷、次版本加能力」，而这些号既不值得记，也没有人会对得上「哪一版改了什么」。

同时，正式发布那条流水线有不少代价换来的规矩：tag 必须落在 main、站点只能往前走、`version.txt` 是唯一的「现在发的是哪一版」。**这些规矩对 beta 全是反的**——beta 的版本串不动，每次构建就是该覆盖上一次。

三条路考虑过：

| 方案 | 问题 |
|---|---|
| 每次修完打个正式 tag | 版本号被吃掉，`RELEASE.md` §1 的语义名存实亡；而且正式站点会给还没验收的东西盖章 |
| `cli/v1.1.0-beta.1` 这样每次一个 tag | 版本串仍然在动（`-beta.1`、`-beta.2`…），正是要避免的东西；而且 beta 不该占用 main 之外任何需要保护的引用 |
| **beta 通道：手动触发、版本串固定、`beta/` 前缀** | 要建一条新流水线，并接受「同一版本串对应多个字节」，这要由提交号补上身份 |

## 决定

1. **有一条独立的 beta 通道**，由 `.github/workflows/cli-beta.yml` 实现，**手动触发（`workflow_dispatch`）**，不认任何 tag。正式发布那条流水线（`cli-release.yml`）一个字节都不动：它仍然只认 `cli/v*`、仍然只有正式版上传、仍然管着站点根键与根 `version.txt`。
2. **版本串在测试期内固定**：`1.1.0-beta`。它在 beta 期间不变，正式发布时同一个东西叫 `1.1.0`。
3. **构建身份是提交号**：`--version` 打印 `skillmaster 1.1.0-beta (a1b2c3d) (API v1)`。`internal/version.Revision` 由 beta 构建注入；正式构建不注入，输出与今天逐字相同。
4. **beta 写 `beta/` 前缀**：`beta/skillmaster_*`、`beta/checksums.txt`、`beta/install.sh`、`beta/install.ps1`、`beta/version.txt`（内容 `1.1.0-beta (a1b2c3d)`），以及 `beta/releases/<版本>-<提交号>/` 的暂存区。正式站点的任何键都不被 beta 写过。
5. **安装方式是同一个脚本、另一个地址**：`SKILLMASTER_DL_URL=https://dl.skillmasterai.com/beta`（`install.sh` / `install.ps1` 本来就认这个变量，**不改脚本**）。
6. **beta 不承诺任何兼容性**：命令面可以增删改，状态可以丢，随时可能整个换掉。它只承诺一件事：装上去的那个构建，`--version` 说得出来它是哪一次提交。

## 理由

- **正式那条流水线不该为 beta 长第二套逻辑。** 先把 beta 塞进 `cli-release.yml`（加一个 dispatch 分支、把九个对象的键前缀参数化）是写过的，代价是那条流水线里「只有正式版上传」「站点只会往前走」这些用事故换来的规矩，全部要多想一遍「对 beta 还成立吗」。分开两条，各自只有一套规矩。
- **beta 不占版本号，是因为版本号是给人对账用的。** `1.0.3` 与 `1.0.4` 之间若只隔三天且没有语义差别，这个号就没有信息量；而 `1.1.0-beta (a1b2c3d)` 把「这是哪条线」和「这是哪一次构建」分开说，两件事各自都清楚。
- **固定版本串必须配构建身份，否则就是一个说不清的版本。** 没有 `Revision` 时，两个人手里都写着 `1.1.0-beta`，而字节不同；提 bug 的人说不清自己在哪一版上，修的人复现不了。这是把「版本号不动」变得可接受的**前提**，不是附带好处。
- **`beta/` 前缀而不是第二个 bucket 或另一个域名**：同一个 bucket、同一个域名、同一个证书、同一套 nginx，只多一个前缀；将来不要 beta 了，删前缀、删流水线文件即可，正式站点的形状一点没变。
- **否掉「用 `-rc` tag」**：`-rc` 在 `RELEASE.md` §2 里的意思是「演练流水线、构建但不发布」，它没有站点、没有安装地址；而 beta 需要的是「能装、能更新、能一直装」。两者的目的不同，共用一个名字只会让两边都含糊。

## 后果

- 下载站多出 `beta/` 前缀，与正式键**同一份公共读 bucket**。它是公开的：任何人都能装 beta，这正是内测的意思；正式用户走根地址，不会碰到它。
- **同一个版本串对应多个字节**。凡是按版本号做判断的地方都不能对 beta 生效——例如正式那套「站点只能往前走」的守卫，在 beta 里没有意义（`beta/version.txt` 每次都会被重写）。
- 每装一次 beta 都要重跑安装命令；CLI 的自动更新还没做（在 todo 里）。在那之前，让试用者知道「更新 = 重跑一次安装命令、看 `--version` 的提交号变没变」。
- 正式发布 `1.1.0` 之后，beta 通道要么继续跑 `1.2.0-beta` 这条线，要么关掉。**关掉时**：删 `beta/` 前缀与 `.github/workflows/cli-beta.yml`，正式站点的任何键都不受影响——这是把它做成前缀而不是第二站点的原因。
- 每次 beta 构建会留下一个 `beta/releases/<版本>-<提交号>/` 暂存区（约 50 MB），与正式发布同一条手工清理习惯。
