# 0050 · 删除是可以撤销的，而名字不释放

- **状态**：已采纳
- **日期**：2026-10-17
- **所属版本**：[`v5-skill-management`](../versions/v5-skill-management/README.md)
- **依赖**：[0046](0046-deleting-a-skill-happens-in-the-browser.md)（删除只在浏览器面）、[0047](0047-permissions-are-a-ladder.md)（删除是所有者独有的能力）、[0012](0012-addressing-and-version-pinning.md)（地址解析不出就一律 404）
- **兑现**：[0046](0046-deleting-a-skill-happens-in-the-browser.md) §后果 留下的那个空档——「删除在控制台入口画出来之前无处可做」。**该 ADR 正文四段保持原样。**
- **状态码与码名被 [0071](0071-a-deleted-name-answers-with-its-own-code.md) 修订**：提交到已删名字从 400 `invalid_request` 改为 409 `skill_deleted`；「拒绝而不是复活」的决定不变。

## 背景

[ADR 0046](0046-deleting-a-skill-happens-in-the-browser.md) 撤掉了 API 平面那条删除路由，把删除定成「只在浏览器面、点下去先问后果」。它同时如实记下：控制台那处入口不在 v4 画，「**所以在这一版与控制台入口之间那一段时间里，删除在整个产品里无处可做**」。这一版画那处入口。

画之前有两件事从来没被决定过，而它们都不是实现细节：

1. **删掉之后能不能找回来。** 今天的删除是**软删**——写 `deleted_at`，行与字节都留着，回收的引用集是 `SELECT DISTINCT blob_sha256 FROM version_file`，不看这一列。也就是说**数据一直都在**。而 `SoftDeleteSkillUseCase` 今天没有任何路由调用它，`SkillDeletedException` 的注释承诺过「§4.3 gives restoring its own endpoint」——那个端点从未实现。而 `SkillRepository` 的注释明确写着 `deleted_at` **不被清空**，为的是让「已删除」与「不存在」分得开。
2. **名字释不释放。** `skill` 上有一条 `UNIQUE (namespace_id, name)`。软删的行**还在表里**，所以那条唯一约束**仍然占着那个名字**——删掉 `alice/pdf-tools` 之后，同名的新 skill 建不出来。

摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 真删（删行、删版本、让 GC 收掉字节） | 它推翻 v1 的整个形状（那个版本的定调是「一次都删不掉东西」），而且要处理审计行、引用计数与并发读；得到的只是「名字能重用」这一件事 |
| b | **软删 + 可恢复 + 名字保留** | 采纳 |
| c | 软删 + 可恢复 + 删掉即释放名字 | 释放之后**恢复就没地方恢复了**——如果那个名字已经被别人建走，恢复会把两个 skill 撞在一起。要么恢复拒绝（那它就是有条件的能力，而条件发生在别人手里），要么恢复覆盖（那是数据丢失） |

## 决定

1. **删除仍然是软删**，一条都不改：写 `deleted_at`，行、版本与字节全部留着。
2. **删除可以撤销。** 恢复 = 清掉 `deleted_at`。版本、指针、授权与可见性**原样回来**——删除期间它们只是一个读不到的行。
3. **名字不释放。** `UNIQUE (namespace_id, name)` 继续对已删的行生效。提交一份与已删 skill 同名的内容是**明确拒绝**，不是静默复活。
4. **删除只由所有者发起**（[ADR 0047](0047-permissions-are-a-ladder.md) §决定 3），只在浏览器面（[ADR 0046](0046-deleting-a-skill-happens-in-the-browser.md)）。
5. **恢复的入口在作者面的「已删除」那一份列表里**，不在地址上——地址对已删的 skill 一律 404（[ADR 0012](0012-addressing-and-version-pinning.md)），所以恢复**不可能**在地址上发起；那个 404 页只提供一条出路，指向那一份列表（「查看已删除的 skill」），动作仍然只能在列表里做。

## 理由

**为什么给恢复。** 因为数据一直都在，而「我们有能力让你找回它，但我们不给这个入口」不是一个能对用户解释的答案——它只是在保护一个不该由产品持有的立场。参照产品对仓库的删除给的就是三十天可恢复，而它背后恰恰也是「行还在，只是不再返回」。**代价是零**：恢复是一个 `UPDATE` 清一列。

**为什么名字不释放。** 三条，按分量排：

1. **恢复需要一个稳定的名字。** 这是决定性的那条——释放与恢复不能同时成立（见选项 c）。
2. **地址一旦发出去就有引用。** `alice/pdf-tools` 可能已经写在某个 agent 的配置里、某份文档里、某个人的终端历史里。释放之后，**下一个人建出同名的东西，那些引用会静默地指向一个新的东西**。这是这个系统里最坏的一类失败：不报错、且看起来正常。
3. **它是一条钓鱼路。** 一个被删掉的、有点名气的 skill 名字，如果可以被任何人重新注册，那么「等它被删，然后照着它建一个」就是一条现成的路，而拿到旧引用的人不会察觉换了作者。

**为什么「提交到已删的名字」是拒绝而不是复活。** 这条今天已经这么定了（§4.3：`400 invalid_request`，理由原文是「让提交兼任恢复会让删除变成建议」）。本决定只是把它与恢复放在同一张图上：**恢复是一个人有意的动作，提交不是**——让一个无人值守的 `skillmaster skill submit` 能把删掉的东西复活，等于把删除降级成一次可被自动化撤销的建议。

**为什么恢复只从列表进，不从地址进。** 已删的 skill 在地址上必须与「不存在」给同一个答案（[ADR 0012](0012-addressing-and-version-pinning.md)）——否则「这个名字曾经存在过」会变成一条能从外面探测到的信息，而删除恰恰是最需要它探测不到的动作。于是恢复只能从「我知道我删过什么」的那一面进去，那正是作者面列表。

## 后果

- **名字是永久占用的。** 删掉 `alice/pdf-tools` 之后，**这个名字再也建不出新 skill**——除非把旧的恢复回来。这是本决定最实在的代价，要在界面上说出口（删除的就地确认里那句话），否则人会在半年后撞上一个自己解释不了的「这个名字已被占用」。
- **`SkillRepository` 里那条注释要改。** 它今天写着 `deleted_at` **不被清空**（「让调用方能区分 deleted 和 created，并拒绝而不是复活」）。前半句仍然成立——消费面与作者面的正常读路径**照旧看不见已删的**；变的只是多了一条**有意的、所有者的、从列表出发的**路能把那一列清掉。
- **恢复那条路由要自己解析已删的行。** 它是**唯一**一条**按地址**解析已删行、并把 `deleted_at` 写回去的路径（作者面的「已删除」那一份也读已删行，但它只列调用者自己拥有的、不走地址解析），所以它不能走 `permitted()`（那个谓词里有 `AND s.deleted_at IS NULL`）——它得自己按 `(namespace_id, name)` 找到那一行（含已删），再要求调用者是所有者。**这是本决定里最容易写错的一处**：顺手复用 `permitted()` 会让恢复永远 404，而复用得太宽会让已删的 skill 从别的路径漏出去。
- **作者面列表多出第二份**：「已删除」。**它是一份单独的列表，不是筛选**（2026-10-17 定稿时改的）：那一份里每一行能做的只有恢复，做成筛选项等于说两份是同一个列表的两种看法。凭据那一屏的「活跃 / 已撤销」只在取数参数上同形（`state`），界面上不是同一个做法。
- **一条能力边界要写进测试**：恢复之后**消费面立刻可读**，前提是它删之前就是可读的（可见性与授权原样回来，因为删除没有动过它们）。
