# ADR 0152 · 累计调用次数是一份独立信号

- **状态**：已采纳
- **日期**：2026-11-06
- **所属版本**：[`v49-public-signals`](../versions/v49-public-signals/README.md)
- **依赖**：[ADR 0149](0149-use-is-counted-per-account-per-day.md)（按账号 × 天去重、只展示分桶）
- **修订**：决定 1 的主键由 [ADR 0153](0153-usage-metrics-is-its-own-module.md) 加 `scope`；决定 2 的「同一个事务」由 0153 改为读事务之后的独立事务

## 背景

ADR 0149 给的是「这个 skill 有没有人在用」：`skill_usage_day` 以「账号 × 天」去重，聚合出近 30 天不同账号数，只对外给分桶。但结果行要回答的还有「它被用得多不多」——一屏十几条里，`1k+ 次调用` 比 `100+ 个账号用过` 更直观，也是使用者在比较时真正看的那一个数。

去重表算不出它：同一个账号一天读三次，在 `skill_usage_day` 里只有一行。用行数冒充调用次数，会把重复使用抹平——那正是这个数想说明的事。

## 决定

1. **单独一张计数器** `skill_usage_total(skill_id PRIMARY KEY, calls BIGINT)`，一个 skill 一行。
2. **与 `skill_usage_day` 同一次读里加一**：同一个「公开、有线上版本、未下线、非作者」的判断，同一个事务。累计数不随版本走。
3. **只对外给分桶**：0 不画、1–9 写「少于 10 次调用」、其后 10+ / 100+ / 1k+ / 1万+ / 100万+；精确次数不出接口，与账号分桶同一条口径。
4. **90 天清理只删 `skill_usage_day`**，累计数不清。

## 理由

- **两个问题不同，两份数据。** 去重表答「有没有人在用」，计数器答「被用得多不多」；用一份数据答两个问题，其中一个一定答错。
- **一次 `UPDATE … SET calls = calls + 1` 是热路径上最便宜的事。** 它不参与任何查询计划，也不改变读路径。
- **精确值没有必要外传。** 分桶已经足够比较；精确次数会让每一次加载都可被外部逐次核对——与 ADR 0149 不展示精确账号数是同一个理由。
- **不写进 `skill` 行。** 那张行是元数据与当前版本指针，发布时被更新；把每次读都压到同一行上加锁，会与发布写争锁。

被否掉的：**用 `skill_usage_day` 行数当累计**（口径错，重复使用被抹平）；**只显示账号分桶**（设计判「看不出被用得多不多」）；**把计数塞进 `skill` 行**（热路径与发布写争锁）。

## 后果

- 多一张一行的小表、一次热路径 UPDATE，以及一条迁移。
- 累计数是单调增的：删版本、回滚、下架都不会减；清理任务不碰它。
- 它与 ADR 0149 §决定 4 并存：那边说的是「近 30 天账号分桶不上精确值」，这边说的是「累计调用另记一份、同样只给分桶」。
