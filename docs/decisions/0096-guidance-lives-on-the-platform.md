# ADR 0096 · 引导内容放在平台上的官方技能里

- **状态**：已采纳（取代 [ADR 0094](0094-load-the-library-at-session-start.md)；并取代 [ADR 0093](0093-no-skill-discovery-index.md) 里「保留 `/gateway/STARTUP.md` 这一条匿名路由」那一条）
- **日期**：2026-10-26
- **依赖**：[`versions/v20-guidance-on-platform/`](../versions/v20-guidance-on-platform/)
- **勘误**（2026-10-26）：§后果 第一句写「新增的依赖只是『技能没被下线』」——不准确。旅程正文原先走**匿名**路由，现在走需要凭据的 API，所以新增的依赖是**网络、一个在线的公开技能，以及一份服务端接受的凭据**。凭据被拒（过期、撤销、无读权限）时 `startup` 以退出码 4 结束、不再打印正文；这是有意的（一份明确的错误比一份过期的正文好），但代价比原文写的大。

## 背景

v17 把两段引导内容分别放进了两个二进制：

- **旅程正文**（六步的搬运、上线、写提示词、验证、下线）编进服务端的 jar，由匿名路由 `GET /gateway/STARTUP.md` 提供（ADR 0089、0093）；
- **用户要粘进系统提示词的规则**编进 CLI 的 `help usage` 主题（ADR 0094）。

两段都是**内容**：它们的更新节奏取决于 agent 生态怎么变、措辞怎么改，而不是取决于代码怎么改。但放在二进制里，改一句话就要发一版 CLI，改一段旅程就要发一版服务端；而且两段各改各的，已经出现过口径不一致。

2026-10-26 官方账号建成、旅程以技能 `skillmaster/startup` 在平台上线之后，第三条路变得可行：

1. 两段都留在二进制里，按发版节奏更新；
2. 旅程搬到技能，规则留在 `help usage`；
3. **两段都放进平台上的官方技能**（本次采纳）。

## 决定

1. **旅程正文与规则段都是 `skillmaster/startup` 的内容**：旅程按「一步一个文件」组织（`SKILL.md` 给规则与起点，`steps/NN-*.md` 各给一步），规则段写在第三步的步骤文件里。
2. **`skillmaster startup` 只做三件事**：确保登录、打印现场状态行、加载这个技能（并把版本钉在本机，后续 `skill read` 沿用同一版）。
3. **`help usage` 退休**。help 只讲命令；规则不在二进制里。
4. **服务端退休 `/gateway/STARTUP.md` 与 `gateway/skillmaster/STARTUP.md` 资产**。匿名发现通道上不再有引导文档。
5. **规则文本以 2026-10-26 批准并实测的那三行为准**：按需检索（`skills search`，未命中可加 `--scope public` 搜公域）、`skill invoke` 加载、其余查 `help`。会话开始先 `skills list` 的那一条随之取消。

## 理由

- **内容的更新速度由内容决定。** 规则里写着命令名和触发条件，这两样会随产品走向变；把它们放进技能，改一次对所有人生效，不必等一次 CLI 发版，也不必保证「所有人的 CLI 版本都升到了」。
- **一个事实只有一个权威位置。** 规则曾经同时出现在 `help usage`、旅程正文、以及用户粘好的指令文件里，三处各自都会过期。搬进技能后，平台上的那一份是唯一权威，用户文件里的那一份是**写下时的样子**——两者关系在旅程里写明。
- **旅程要分步加载，一份文档做不到。** 用户明确要求「做完一步再看下一步」，否则 agent 会把六步一起作用于当前状态。技能的引用文件天生就是按需加载的；一条「把整份文档返回」的匿名路由只能一次性给全部。
- **help 是命令参考，不是行为守则。** 它回答「这条命令怎么用」，规则回答「什么时候该用这套东西」。两者放在一个主题里，改规则的措辞要动命令文档，改命令要回头核对规则。
- **被否的第 1 条**：发版节奏本身没错，错在把内容绑在二进制上——一次措辞校对要等一个发布窗口，而平台发布只要一次上线点击。
- **被否的第 2 条**：留 `help usage` 做指路（只写「规则在平台上，命令是…」）也不行。它多一次阅读，还留下一个会过期的名字；规则既然只有一处，指针也不必留在二进制里。
- **没有保留轻量兜底**（技能不可用时打印内置副本）：兜底就是第二份文本，而它注定会漂；失败时说清楚比给一份可能过期的正文更诚实。

## 后果

- **`startup` 需要网络与一个在线的公开技能。** 它本来就要求登录（顺序上先登录，再加载），所以新增的依赖只是「技能没被下线」。技能缺失时旅程不可用，CLI 报错并指路控制台——这是运维事故，不做兜底。
- **ADR 0094 的规则文本与位置被取代**，它关于「这是指令不是保证」的判断仍然成立（规则依然是写给模型的文字，不是机制）。
- **v17 的若干验收要回写**：`help usage` 的快照、`--no-login` 那条唯一例外、以及「旅程正文托管在服务端 `/gateway`」的架构描述，都以本 ADR 为准。
- **规则段有了发布流程**：改它要经过控制台的草稿与上线，和改一个 skill 的正文一样。这带来一个好处（谁能改不再取决于谁发版）和一个代价（改规则不再是一次提交）。
- **老客户端拿到的答复变模糊。** 路由退休后，`/gateway/STARTUP.md` 返回 404（代理仍把这个前缀转到服务端，见 v20 TD §接口），不是一份引导。升级是唯一出路，这一点在发版说明里要写。
