# 0133 · `wc` 流式计数，不受 16 MiB 文本上限

- **状态**：已采纳
- **日期**：2026-11-02
- **取代**：[ADR 0130](0130-large-blobs-live-in-object-storage.md) 决定 4 中关于 `wc` 的那一半

## 背景

[ADR 0130](0130-large-blobs-live-in-object-storage.md) 决定 4 写的是「`grep` / `wc` 只扫描不超过
16 MiB 的文本文件，超过的文件明确跳过并说明」。这条限制的理由是内存：扫描要把文本读进来。
`grep` 的匹配确实需要一份可回看的文本，所以它保留这个上限；`wc` 只需要按块读、边走边数，
v39 的实现已经是流式计数，任何大小的文件都不会整份进堆。

把两者绑在同一个上限上会让一个本来能完成的命令主动拒绝输入——「能写不能扫」的反向回归。

## 决定

1. **`grep` 保留 16 MiB 文本上限**：超过的文本文件不扫描，结果里以 `skipped` 明确列出。
2. **`wc` 不设文本上限**：按流计数，16 MiB 以上、甚至 OSS 里的文本也照常计数。它不是
   「扫描」，不产生需要回看的内容。
3. 两个命令共用同一个词「文本处理上限」时，必须说清是 `grep` 的。

## 理由

**否掉「让 `wc` 也跳过」。** 那会让一个只需常数内存的操作拒绝一份完全合法的文本，用户看到
的是「这个文件数不了」，而真实原因（为 grep 设计的上限）与它无关。规格里写错的一半应当改掉，
不该为了字面一致去削弱实现。

**否掉「让 `grep` 也流式化、取消上限」。** 匹配需要跨块的上下文与回看，流式实现可以做，但
正则的最坏情况（灾难性回溯）要在可预测的输入量上才有意义；16 MiB 是现有的保护边界，与
ADR 0062 的扫描口径一致。

## 后果

- PRD §做 #3、TD 附录 A、test-plan T25 的说法改成「`grep` 有上限、`wc` 流式」。
- `wc` 在大文本上仍依赖 OSS：文件超过 1 MiB 就在桶里，OSS 不可用时它和媒体一样读不到。
- 以后若要给 `wc` 加限制，那是另一个决定——不能从 ADR 0130 的这句话里推出来。
