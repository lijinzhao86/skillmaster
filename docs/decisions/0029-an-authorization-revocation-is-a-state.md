# ADR 0029 · 授权的撤销是一个状态，记在它自己的行上

- **状态**：已采纳
- **日期**：2026-10-05
- **依赖**：[ADR 0021](0021-opaque-tokens-not-jwt.md)（撤销必须立刻生效）、[ADR 0023](0023-spring-authorization-server-with-our-own-storage.md)（存储自带，所以这条规则落在我们自己的实现里）、[ADR 0024](0024-refresh-replay-grace-window.md)（刷新与撤销的规则在这里被扩展）
- **扩展**：ADR 0024 —— 它定的那条「窗口外重放则整链撤销」不变，变的是**「整条授权结束了」这件事怎么表达**

## 背景

`V6` 给三张令牌表加了一个父行 `oauth_authorization`，撤销从此有了「一行」可以够，而不是靠 `(client_id, user_id)` 那种会误伤同一个人在另一台设备上的另一条链的近似。但那一行上**没有地方写「我结束了」**：撤销表达为「把它的码、access token、refresh token 一起标掉」，于是「这次授权结束了」是一个**推断**——「它下面一条活的都没有」。

**那个推断撑不住一个竞态，而竞态在 2026-10-05 的审计里被指出来并确认了。** 刷新要保存新令牌时，先读「这条授权下现在哪一张 refresh token 是活的」来区分「轮换」与「结束」（ADR 0024 的整套记账就靠这一个比较）。撤销是一组 `UPDATE`，写入是一次 `INSERT`，而**任何一组 `UPDATE` 都不可能和它没见过的 `INSERT` 原子**。所以要发生的是：

1. 一次刷新加载了授权、框架签好了新的一对，还没有写
2. 撤销落地（登出、改密码的 `revokeAllFor`、停用）——把所有令牌行标掉
3. 刷新写入。它读到「没有活的」，而**那也正是「一条全新授权第一次插入」的样子**，于是 `rotated` 为假，新签的 refresh token 被以「活的」写进去

那条授权于是**带着剩余几个月的上限回来**（上限锚在父行的 `created_at`，见 ADR 0024），而「客户端登出了」与「客户端还能用很久」同时为真。ADR 0024 的宽限窗口兜不住它：那个窗口只管**被呈现**的令牌，这是**写入**。

同一根因还有第二处形态：`POST /oauth/revoke` 递上来的是 **access token** 时，只标了那一行——refresh 还活着，授权还在。

## 决定

**「这次授权结束了」记在父行上**：`V9` 给 `oauth_authorization` 加 `revoked_at`，撤销时先写它、再标子行；而**它是权威**，不是子行的副产物。四处读它，缺一处这个洞就在：

- **载入路径**（`load()`）：读到父行已撤销，就把它下面**每一张**令牌都当成失效交给框架。于是一条**逃过扫描的活行是惰性的**——正确性不再依赖扫描是否完整。这也是这一条 ADR 最实质的部分。
- **`refreshToken` 的 `familyAlive`**：先问父行。否则那条活行会被当成「活着的继任者」，宽限窗口于是会把一次**有意结束**的授权救回来（ADR 0024 的窗口只在家族还活着时才生效——现在「还活着」由父行说了算）。
- **三个 upsert 的写入**：父行已撤销时，新行直接写成已撤销，不再制造逃逸行。
- **`IssuedTokenValidator`**：它**不走这个存储**，是 API 那条路上唯一决定「这张令牌能不能做事」的查询，所以它单独加了一个对父行的 `EXISTS`。

**同时补上第二处形态**：撤一张 access token 就是撤整条授权。前提是一个**被读字节码确认**的事实——刷新**不会**让它替换掉的 access token 失效（7.1.1 的 refresh provider 里 `invalidate` 一次都没出现），所以「递上来的 access token 是失效的」只能来自撤销端点或授权码重放。

## 理由

**被否掉的第一条：继续用推断，不加密列。** 这在当天就能修掉那个竞态——判据可以是「这条授权下**存在过** refresh 行、而现在一条活的都没有」，那与「全新授权的第一次插入」可区分。否掉的理由是它是**又一层推断**：它把正确性继续挂在「扫描有没有跑完」上，只是把窗口缩小；上面第二处形态（撤 access token）它完全管不到，因为没有东西可以问。而这一条 ADR 换来的是一个**可查询的事实**——问一次父行，答案就是答案。

**被否掉的第二条：把保存包进一个事务 + 对父行 `SELECT … FOR UPDATE`。** 这是教科书答案，在这里被否有两个理由。一是**本仓库把事务边界划在用例层**（`ArchitectureTest.transactionsAreDeclaredOnlyInUseCases`，理由见技术设计 §2.5）：让 M2 自己开事务，就是把一个跨模块的约定挪进一个模块里。二是**它并不比父行标志更强**：锁只能串行化**同一份代码**的两条路径，而「一行活令牌被写出来」这件事的读者不止一个——`IssuedTokenValidator` 根本不走这个存储。锁保护的是写入，标志保护的是**读到的结论**，而后者才是要保的东西。

**被否掉的第三条：只在写入侧加判断（「父行已撤销就不写活令牌」）。** 这条**留下了**，但它不够：它防的是**以后**不再产生逃逸行，防不住**已经**逃逸的那一行（一次崩溃落在两条 autocommit 语句之间就够了），也防不住「读者拿到的结论」。写入侧的判断与载入侧的判断是两件事，两条都在。

**为什么不是 ADR 0024 的就地修改**：0024 的正文记的是**当时**面对重放问题时知道什么、选了宽限窗口——那段历史不变。这一条扩展的是它没覆盖到的那一半：**「结束」这件事本身怎么表达**。

## 后果

- **多一列，多一次读。** 载入路径每次多读父行的一个字段（同一个 SELECT 里，不是多一次往返）；写入侧每个 upsert 多一次 `count` 查询——**这是这一条最实在的代价**，而它换掉的是一个自我维持的洞。
- **撤销变便宜了一点**：`revokeAuthorization` 先写父行、父行本来就不是 NULL 就直接返回——不会重复扫描，也不会重复记审计（框架会把读回来的授权再存一次，撤销因此可能被走到第二次）。
- **`revokeAllFor` 必须认识两种拼法**：浏览器那条授权把 userId 写在 `principal_name` 上，无人值守那条写的是 **client id**（框架对 `client_credentials` 的主体是客户端认证，而令牌行写的是它代表的账号——ADR 0022）。只按 `principal_name` 扫会留下父行，而父行正是权威。第一轮审计的定向复核抓到过这一处。
- **审计的 `trigger` 不总是原因**：授权码重放也会走到「递上来的 refresh token 已失效」那个分支，于是记成 `refresh_token_revoked`。分辨不出来——换过码的授权，其码本身也已经失效——所以不去猜，写进 M02，原因仍可从那张码的 `used_at` 复原。
- **`oauth_authorization_consent` 不受影响**：删同意记录仍然不撤销已签发的令牌，两者各有各的入口（与 `V6` 那条一致）。
