# ADR 0059 · 下架的原因是选填

- **状态**：已采纳
- **日期**：2026-10-20
- **依赖**：[ADR 0058](0058-a-version-is-readable-or-not.md)（版本级的「撤回」叫下架）、[ADR 0056](0056-dangerous-actions-are-confirmed-in-a-modal.md)（危险动作弹窗确认）
- **取代**：ADR 0058 §决定 3 中「下架必须写一句原因」这一句

## 背景

v6 定义阶段把「下架必须写一句原因」写进了 ADR 0058、PRD 范围 #8 与 TD（`revoked_reason` 非空、接口校验 1–200 码点）。产品在评审确认弹窗时提出：**最常见的情形是「这一版没人调用了，所以下架」**，站在那个输入框前，用户不知道该写什么。

问题于是变成：这个字段是在收集信息，还是在对每一次下架一律收费？

## 决定

1. **下架的原因是选填**（0–200 码点）。不填也能确认；填了才存、才在作者面显示、才进审计 detail。
2. **数据库约束**从「已下架 ⇔ 有原因」改为「原因只出现在已下架的行上」：`CHECK (revoked_reason IS NULL OR state = 'revoked')`。重新上架时清空原因不变。
3. **弹窗里的字段**仍叫「原因」，标注「可选」；占位提示引导真正需要记录的少数情形（安全事件、这一版有问题）。
4. **状态条与版本事实**只在有原因时显示它，不出现空的「原因：」。

## 理由

**必填的前提是人答得出来。** 多数下架的原因就是「没人用了」——这句话对后来者没有信息量，却要每一次都写；写出来的「没人用了 / 清理」与空着等价，还把这个字段训练成走过场的地方。

**真正需要原因的是少数**：安全事件（版本泄密、被投毒）、这一版有缺陷。这些情形本来就有人会主动写；在提示里点出来即可，不必用必填让所有人陪跑。

**为什么被否的是这两条：**

- **保持必填。** 代价是常规清理多一道没有答案的题，还会逼出垃圾输入——一个大部分回答都是「没人用了」的必填框，读的人也不会再信它。
- **改成点选常用原因**（没人用了 / 有安全问题 / 这一版有问题 / 其他）。它比自由文本更容易统计，但要维护一套分类，而最常见的那一格仍然零信息量；等真的有按原因统计的需求再谈。

**与「丢弃」的区别。** 丢弃没有恢复入口，原因记下来是对终态的解释；下架可以重新上架，记录的必要性本就弱一档。

## 后果

- PRD #8 / #13 / #17、TD 的约束与接口、test-plan 的相应期望改成选填。
- ADR 0058 §决定 3 的「下架必须写一句原因」由本条取代；0058 文件头标注修订。
- 审计 detail 有原因才带；分析不能假设每一次下架都有原因。
- 演示件：确认弹窗的原因框可选，空着时确认按钮可用；占位提示给出安全事件的例子。
