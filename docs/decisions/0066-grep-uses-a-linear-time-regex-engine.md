# 0066 · grep 的正则由线性时间引擎执行

- **状态**：已采纳；**决定 1 与 6 被 [0067](0067-grep-has-a-cost-ceiling.md) 修正**（`-F` 不再经过引擎，正则另有成本上限）
- **日期**：2026-10-20
- **依赖**：[0062](0062-grep-is-a-scoped-scan-not-an-index.md)（grep 是有界扫描）、[0047](0047-permissions-are-a-ladder.md)（`write` 档就能调用它）
- **这一条只回答「拿什么执行调用方给的正则」**，不改变 [0062](0062-grep-is-a-scoped-scan-not-an-index.md) 的「不建索引、服务端扫描」结论。

## 背景

v7 的作者面 grep 接受调用方提供的正则。第一版实现用的是 `java.util.regex`，而它没有执行预算：一个形如 `(a+)+$` 的合法表达式，配上一行足够长的 `aaaa…`，会让匹配线程在指数级回溯里出不来。`grep` 是 `@Transactional(readOnly = true)`，所以卡住的不只是一个请求线程，还有它占着的那条数据库连接；一个有 `write` 档的普通账号用几个请求就能把连接池拖垮。

摆在桌上的四条路：

| | 做法 | 代价 |
|---|---|---|
| 1 | 继续用 Java 正则，加超时 | JVM 没有可用的正则超时；`Thread.interrupt` 不会让匹配退出，线程杀不掉，只能泄漏 |
| 2 | 继续用 Java 正则，限制 pattern / 行长度 | 回溯是指数级的，几十个字符就够卡死；限制长度只是把门槛挪低 |
| 3 | 静态检查「危险写法」后拒绝 | 判定不可靠，绕法很多；拒绝合法表达式也是一次语义变更 |
| 4 | 换成线性时间引擎（RE2/J） | 放弃反向引用与 lookaround；语义与 Java 正则不完全相同 |

## 决定

1. **服务端 grep 的正则由 RE2/J 执行**（`com.google.re2j:re2j:1.7`）。不带 `-i` 的固定串（`-F`）走 JDK 的字面子串搜索；`-F -i` 与正则都经过引擎。
2. **RE2 不支持的写法**（反向引用、lookaround 等）与语法错误一样，返回 400 `invalid_request`，detail 为 `bad_pattern`；**不做静默降级**。
3. **pattern 长度上限 1000 字符**，超出返回 400，detail 为 `too_long`。
4. **逐行迭代用下标推进，不用 `split("\n", -1)`**：一份 16 MiB 的换行文件不应先产生千万个字符串数组。
5. **命令帮助写明引擎与边界**（`skill grep --help`）：线性时间、不支持反向引用与 lookaround、`$` 只匹配输入末尾（Java 的 `$` 还会匹配末尾换行之前；逐行输入里 CRLF 的 `\r` 会参与匹配）、二进制文件不参与、命中过多会截断。
6. **`-i` 是修饰符，不是固定串**：不带 `-F` 时 `-i` 让正则大小写不敏感（RE2 的 `CASE_INSENSITIVE`）；带 `-F` 时 `-i` 把字面量交给 RE2 的 `CASE_INSENSITIVE` 做一遍线性扫描；只有**不带 `-i` 的 `-F`** 用 JDK 的字面子串搜索。没有一条路径是逐起点 `regionMatches` 的 O(行 × pattern) 循环。

## 理由

**为什么不是做法 1。** Java 的正则匹配是不可中断的纯计算；没有超时 API，`interrupt` 不改变它的控制流，唯一能停止它的方式是杀掉线程——而 `Thread.stop` 已废弃且不安全。一个「超时」若不能真的停止扫描，就只是把连接池的耗尽推迟几十秒。

**为什么不是做法 2。** 灾难性回溯的规模是表达式与输入共同决定的：`(a+)+$` 在几十个字符上就能耗尽 CPU。限制 pattern 长度或行长度只能降低触发难度，不能把最坏情况变成有界；而「有界」正是这条命令的交付条件。

**为什么不是做法 3。** 用模式匹配去识别「危险的正则」本身是一个不可判定的问题；能识别的那一小撮写法总有等价绕法。被拒绝的合法表达式也会变成一次没人预期的语义变更。

**为什么接受语义差异。** [0062](0062-grep-is-a-scoped-scan-not-an-index.md) 已经承认「正则的语义与本地 `grep -E` 有差异」，TD 的开放问题也把「反向引用、lookbehind、`\p{…}` 要不要支持」列为待定。RE2 让这条边界变成一个确定的答案：不支持就不支持，`bad_pattern` 说出来，并写进帮助。`-F` 是精确路径，想与本地逐字一致时用它。

**为什么 pattern 还要单独设上限。** 引擎线性不等于编译免费；1000 字符对真实的搜索绰绰有余，同时让「一次请求里 pattern 自己占多少内存/时间」也有界。

## 后果

- **依赖**：服务端多一个 `com.google.re2j:re2j`，版本在 `pom.xml` 里钉死；它只被 `GrepDraftUseCase` 使用。
- **帮助是契约的一部分**：`skill grep --help` 必须列出「线性时间、不支持反向引用与 lookaround、二进制不参与、截断」；改动这条 ADR 时一起改帮助。
- **测试**：一条 IT 用 `(a+)+$` 对 20 万字符的长行，证明它在线性时间内返回；一条断言反向引用得到 `bad_pattern`；一条断言超长 pattern 得到 `too_long`；`-F -i` 由同一条线性路径覆盖。
- **将来若要 PCRE 的写法**：先回来重读这一条。引入第二种引擎意味着两条路径的语义都要解释，而不是「顺手补一个」。
