# ADR 0012 · 寻址：`namespace/name` + 版本钉

- **状态**：已采纳
- **日期**：2026-09-28
- **修订**：[ADR 0004](0004-opaque-id-primary-key.md) §后果 里「URL 一律用 `id`」与「agent 用 `id` 做后续调用」两处。**该 ADR 正文四段保持原样**，改动记在这里。
- **依赖**：[ADR 0001](0001-server-authoritative.md)、[ADR 0005](0005-content-addressing.md)
- **被修订**：[ADR 0031](0031-submitting-and-publishing-are-two-actions.md) §决定 5「v1 不做草稿，也不做废弃」与 §理由 里「为什么 v1 不做草稿」那一节（**正文不变**；v1 现在有草稿，版本有 `draft` / `published` / `discarded` 三态。§决定 2、3、6 与 §后果 里那条「草稿一旦引入，GC 必须认识它」不受影响——这一版把草稿做成了普通 `skill_version` 行，那个坑因此不成立）。**又被 [ADR 0033](0033-version-names-are-semver.md) 修订**：§决定 3 里的别名从**服务端自增的整数**换成**作者在 frontmatter 声明的 semver**，`number` 降级为内部排序键（**正文不变**）。§决定 2 的形式不变——`@` 后缀、`latest`、`@sha256:…` 都留着，只是 `@` 后面那一段换了写法。**又被 [ADR 0035](0035-the-pin-lives-on-the-client-machine.md) 修订**：§理由 里「为什么把钉做进清单里的 URI，而不是让客户端记住版本号」那一节（**正文不变**；钉现在由 CLI 记在本机、用 `X-Skill-Version` 发出去，地址不带版本）。§决定 2、4、6 都不受影响——`@` 后缀还在、清单里的 URI 仍然每条带钉、服务端仍然无状态

## 背景

ADR 0004 定了 `id` 作主键，并把 URL 也定成 `/v1/skills/{id}`。P0a 实现完之后，那个后果暴露了两件事：

1. **对 agent 不友好。** 26 字符的不透明串**不可推导**（从「飞书任务」推不出 `01M3HTG7…`）、**没有校验位**（错一个字符就是 404，而 agent 分不清「抄错了」还是「这东西没了」），而且一次任务里要被逐字携带好几遍——搜索一次、详情一次、取文件再一次。
2. **L2/L3 钉不住版本。** `GET /v1/skills/{id}`、`/body`、`/files/{relpath}` 各自独立解析 `skill.current_version_id`。所以「看完清单再取文件」中间只要发生一次发布，取到的就不是清单里那个文件——**而且没有任何东西会报错**。清单里给每个文件带 `sha256` 本意是让客户端能校验，但那只是把「发现不一致」的责任推给了客户端。

同时有两条外部事实指向同一个方向（§1.5）：well-known 索引本来就是按名字的（客户端拼 `<base>/<name>/<file>`），MCP 扩展的资源 URI 也是 `skill://<name>/SKILL.md`。**只有我们的 REST API 是按 id 的。**

## 决定

1. **地址是 `namespace/name`，不是 `id`。** `id` 仍是主键与内部身份——外键、审计、版本归属都指向它——只是不再出现在 URL 里。
2. **版本用 `@` 后缀**：`ns/name@3`、`ns/name@sha256:…`；省略即 `latest`。
3. **`skill_version` 加一列序号 `number`**，它是**不可变的别名**，不是身份（身份仍是 `digest`）。
4. **详情响应里每个文件带一条已经钉好版本的 URI**，客户端照抄它。
5. **v1 不做草稿，也不做废弃。**
6. **服务端仍然完全无状态**：钉版由客户端携带，不由服务端记忆。

## 理由

- **为什么不用服务端会话钉版。**「在这一次任务里版本钉死」听起来像会话，但服务端**不知道什么是「一次任务」**——v1 是无状态的（bearer 令牌、`STATELESS`），没有任何东西能标识「这是同一任务的第二次请求」。要记住就得引入会话，那是把整个架构反过来。**所以钉必须是数据，随响应发出去。**
- **为什么把钉做进清单里的 URI，而不是让客户端记住版本号。** 因为这样就不需要任何机制：agent 从入口进一次，之后照抄清单给的 URL，而那些 URL 里已经写着 `@3`。中间谁发布了 `@4` 都不影响它——不是服务端记住了什么，而是它**根本没再问过 latest**。这同时满足了 §1.5 对清单的硬要求（**每项必须带 URI**），而我们此前只发了 `relpath` 加一个 `{id}` 模板。
- **为什么序号是「不可变的别名」而不是「序列号」。** 如果 `@3` 日后可能指向别的内容，地址就不稳定，缓存与校验全崩。所以它等价于 git 的 **tag**，不是分支。配套：**重发相同内容不消耗号码**（否则 ADR 0005 的幂等就死了——同一个 digest 会拿到两个号），号码的含义是「这个 skill 的第 N 份**不同**内容」。
- **为什么序号不需要新的并发机制。** 发布时 `upsertLive` 已经对 `skill` 行做了 `DO UPDATE`，也就是已经持有那行的锁；在同一个事务里取 `max(number)+1` 天然串行。
- **被否掉：继续用 `id` 寻址。** 代价是 agent 每次调用都要逐字携带一个不可推导、无校验位的 26 字符串。而「名字会变所以不能做地址」这个顾虑的真实代价是**旧地址失效**——ADR 0004 真正要保的东西（外键、审计、版本归属不因改名而迁移）用的是 `id`，不受影响。
- **被否掉：用 `(namespace, name)` 作主键。** ADR 0004 已经否过一次，这里不变——**主键是 `id`、地址是名字，两件事可以分开**。
- **被否掉：短前缀寻址**（类 git short SHA）。ULID 前 10 个字符是时间戳，同批创建的会聚在一起，短前缀很容易撞，得跳过时间戳取位，还得处理歧义。
- **被否掉：把 `id` 本身缩短。** 会丢掉 ULID 的时间有序性，而 `id ASC` 是排序元组的破平局项。
- **为什么 v1 不做草稿。** 最强的一条：v1 里所有 skill 都是 `private`、只有作者能读，所以「草稿」与「已发布」**在可见性上没有任何区别**——为一个不存在的差别引入一张表、一条状态机、一处 GC 集成，不划算。其次，**作者的本地目录就是草稿**，`publish` 就是 commit（与 git 同构）。这个概念要等「别人能看到你的东西」（P2）才有意义。

## 后果

- **`V1__baseline.sql` 的 `skill_version` 要加 `number` 列**与 `UNIQUE(skill_id, number)`。**尚未实现**——P0a 已经按旧寻址写完且测试全绿，见 [`technical-design.md`](../versions/v1-hosting/technical-design.md) §7 的说明。
- **改名会断掉旧地址。** ADR 0004 想要的「改名不断链」在**外部**消失了；内部一切照旧。**是否保留旧名作别名尚未决定**（TD §8 开放问题）。
- **`resources` 里那个 `{relpath}` 模板被「每项自带 URI」取代。** 两个都能拼出同一个 URL，留着就是第二个真相来源。
- **钉住的版本在任务中途被软删**，请求应当 `404`。所以判断必须是「**skill 活着 且 这个版本存在**」，不能写成「版本行还在就发」——软删之后 `skill_version`/`version_file` 行**都还在**（TD §3.3 点 5），写漏了就变成「删了还能读到」。
- **草稿一旦引入，GC 必须认识它。** 现在的清扫算的是 `SELECT DISTINCT blob_sha256 FROM version_file`；草稿的文件如果只被草稿表引用，**下一次发布就会把草稿的字节删掉**，而且不报错。记在这里，免得 P2 踩。
- **与外部两条通道从此一致**——well-known 索引与 MCP 资源 URI 本来就是按名字的。
