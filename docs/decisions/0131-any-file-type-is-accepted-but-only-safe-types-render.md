# 0131 · 任何类型都收，但只有位图与 PDF 内联

- **状态**：已采纳
- **日期**：2026-11-02
- **依赖**：[ADR 0130](0130-large-blobs-live-in-object-storage.md)

## 背景

v39 要支持「所有文件」。平台会把用户上传的字节原样存下、再通过自己的域名发回浏览器。这带来两类风险，必须分开处理：

1. **文件类型太杂**：如果按扩展名白名单拦，冷门但合法的格式会被误伤；黑名单永远漏。
2. **同源执行**：HTML、SVG、JS 如果以可渲染的类型、`inline` 地返回，就成了在平台域名下执行任意脚本的入口。这不是「文件不好看」，是安全边界。

## 决定

1. **不按扩展名拦任何文件。** 任何字节都可以进版本清单，路径规则（相对、无 `..`、无符号链接）照旧。
2. **内联白名单只有：`png`、`jpg`、`jpeg`、`gif`、`webp`、`pdf`。** 只有这几类可以 `Content-Disposition: inline` 并带真实 `Content-Type`。
3. **其余一律** `Content-Type: application/octet-stream` + `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`。包括 SVG、HTML、JS、Office 文档、音视频、可执行文件。
4. **CLI 只把文件写到磁盘，从不执行。** `read` 对二进制落临时文件并打印路径，宿主是否渲染由宿主决定。
5. **本版不做病毒 / 恶意软件扫描。** 这不是「以后再说」，而是明确记在 v39 PRD 的「不做」里，理由是平台只存字节、不执行，扫描要接第三方服务、成本与误报要单独评估。

## 理由

**否掉「扩展名白名单」。** 白名单一旦上线就开始腐烂：新格式要发版才能加，冷门但合法的格式被拒，而真正的风险不在扩展名上——攻击者可以把 HTML 改名成 `.txt`。判断依据应该是**浏览器会怎么处理响应**，不是文件名。

**否掉「按扩展名给类型、全部内联」。** 这正是同源脚本执行的入口。`nosniff` 能挡住一部分，但 `inline` + 正确类型仍然让 SVG / HTML 在平台域名下运行；一个被分享的私有 skill 里的 SVG 就可能读到同源的会话。

**为什么 PDF 可以内联。** 浏览器内置的 PDF 阅读器不执行页面脚本（主流实现如此，且可以用 CSP `sandbox` 再收一层）。PDF 是这一版最需要预览的文档类型，收益明确。**这是一个基于观察的取舍，不是形式证明**；如果将来某款浏览器的 PDF 查看器出问题，把 PDF 移出白名单只需要改一张表。

**为什么 SVG 不算位图。** SVG 是 XML，可以带 `<script>`；它在浏览器里的处理方式与 HTML 同源。要安全地内联，得做 SVG 消毒，那是另一条产品线。

## 后果

- **Office 文档、音视频只能下载**，控制台不内嵌预览；这是有意换来的安全边界。
- **作者想内联 SVG 图标时**，需要自己转成 PNG；平台不安检、不转换。
- **没有恶意软件扫描**：平台可能托管恶意文件，但浏览器不会执行它们；下载后的风险由用户与宿主承担。若将来开放公开下载或出现滥用，这条要重新评估。
- **没有下载类型提示表**：这一版只有内联白名单与正文的 markdown，其余一律 `application/octet-stream`。将来若加下载提示，**内联白名单不随它扩充**——两者必须是两张表，改一张不会顺带改另一张。
