# ADR 0124 · 文件行数上限用只减不增的基线强制执行

- **状态**：已采纳（§决定 1 的分语言数值由 [ADR 0162](0162-file-size-limit-is-one-threshold.md) 取代为统一 1,000；基线机制与其余各条不变）
- **日期**：2026-11-01
- **依赖**：[ADR 0122](0122-architecture-refactor-is-structural.md)

## 背景

仓库已经有前端行数约定（页面约 600 行、组件约 400 行，见 dev-sop §三），但没有任何可执行检查；服务端与 CLI 没有行数约定。结果是 `main.go` 3,673 行、`SkillVersionService` 1,265 行、`SkillPage.tsx` 1,914 行。业界常见区间：ESLint `max-lines` 文档说「多数人同意不应到几千行，建议 100–500」，默认 300；Go 的 `funlen` 默认函数 60 行 / 40 语句；常见团队文件上限 500–800。

## 决定

1. 设一组**分语言 / 分种类**的上限：页面 600、组件 400、通用源码 500、Java 类 500、Go 文件 600、CLI 主入口 `cmd/skillmaster/main.go` 300、测试文件 1,000。
2. 新增 `scripts/check-file-size.mjs`，扫描服务端、CLI、控制台、站点的源码；超限即失败。
3. **现有超限文件进入 `scripts/file-size-baseline.json`**：基线内的文件允许暂时超限，但**基线只减不增**；新增超限文件一律失败。
4. 基线只能通过显式 `--update-baseline` 修改，且该参数在 CI 中不可用；review 时必须看到基线变小。
5. 检查进 CI（新增 `arch.yml`），在 PR 上跑；不做自动修复。

## 理由

**否掉「不设检查」。** 仓库已经用 ArchUnit 证明「规则不变成检查就会漂」；行数同理，拆完没有护栏就会长回来。

**否掉「一次性全部达标」。** 引入时基线有 47 个文件超限，一次拆完会把 P1–P3 的范围全部压进一个 PR；基线让 CI 第一天是绿的，同时把债务显式化。

**为什么阈值不取业界最严的 300。** 这个仓库的页面 / 组件已经有 600 / 400 的约定，Java 的控制器与仓储天然偏长；先按可达到的线定，再逐次收紧。阈值是启发式，不是 correctness 证明。

## 后果

- 新增文件超过上限会被 CI 拦下；合理例外要写进基线并在 review 里说明。
- 测试文件上限放宽到 1,000，但超过 1,000 的测试应按场景拆分（不阻塞本版）。
- 基线文件会成为一份「待还债务清单」；每次拆分都应让它变小。
