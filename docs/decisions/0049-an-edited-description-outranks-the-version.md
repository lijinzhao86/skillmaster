# 0049 · 作者改过的那句描述压着版本，直到他自己清掉

- **状态**：已采纳
- **日期**：2026-10-17
- **所属版本**：**元数据那一版——尚未开**。[v5](../versions/v5-skill-management/prd.md) 讨论时定下了它，但把元数据整块留给了下一版（那里 §不做 #8 记着这条与理由），所以**本版不实现它**。它落在 `decisions/` 里是对的：决策跨版本存活。
- **依赖**：[0031](0031-submitting-and-publishing-are-two-actions.md)（提交与上线分开）、[0047](0047-permissions-are-a-ladder.md)（「维护」档能做的一件事就是改描述）
- **修订**：[0031](0031-submitting-and-publishing-are-two-actions.md) §决定 9——「`skill` 行是**当前上线版本的投影**：`title` / `description` / `frontmatter` 只在 promote 时写入」。**该 ADR 正文四段保持原样**，改动记在这里；`title` 与 `frontmatter` 仍然照 §决定 9 说的做，只有 `description` 多了一个来源。

## 背景

[ADR 0031](0031-submitting-and-publishing-are-two-actions.md) §决定 9 把 `skill` 行定成当前上线版本的投影，理由写得很实：「那三列是搜索热路径读的东西。若提交时照旧写它们，提交 v2 会立刻改掉消费面的标题与描述、而正文还是 v1——**等于提交已经部分上线了**」。**那个理由今天依然完全成立**，本决定一个字都不推翻它：那三列**只在建行那一刻写一次**（提交带上来的那份），**此后只由 promote 重写**——`SkillCatalogRepository` 的注释原话就是「written by findOrCreate and by a publish and *never* by a submit」。

但它带来一个没有被回答的问题：**作者想单独改一句描述的时候怎么办？** 今天唯一的路是发一个新版本并上线它——而那会把**正文**一起换掉。真实情形是「描述里有个错别字」，代价却是「产生一个没人想发的版本、并把线上内容换一遍」。

设计件已经把这条能力画出来了：梯子的「维护」档（`design/README.md:590`）能做的事里就写着**改描述**。

摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 不做独立编辑，描述只能靠发新版本改 | 那就得把设计件梯子里的「改描述」删掉，并解释为什么一个被明确画出来的能力做不到。而且它会**继续制造无意义的版本**——为了改一句话而产生一个版本，那个版本在版本列表里永远是一条噪声 |
| b | 直接让接口写 `skill.description` | 下一次上线就被版本里那句话冲掉。作者改完、发了版、描述变回去，而**没有任何地方说过会发生这件事** |
| c | **加一列显式覆盖，压着投影** | 采纳 |

## 决定

1. **`skill` 行加一列可空的覆盖**，只作用于描述。
2. **读到的描述 = 覆盖（若有），否则读者本来会看到的那一句。** 那「本来会看到的那一句」今天已经有一条定好的规则，而且**不是** `skill` 行那一列：**当前上线版本里的那句；没有上线过时取最新未丢弃的那一版；再兜底到 `skill` 行那一列**（`SkillCatalogRepository.authorPage` 的 `COALESCE(cv.description, a.newest_description, s.description)` 就是它）。覆盖压的是**这个组合值**。`skill` 行照旧由建行与 promote 维护，**不动它**。
3. **清掉覆盖 = 把它设为空**，之后读到的**立刻**变回「读者本来会看到的那一句」——不是「空描述」，也不是「上一次改之前的那个值」。
4. **搜索读的是组合之后的那句**（搜索是描述最重要的读者）。
5. **只做描述。** 梯子点名的能力里只有它。**`title` 与 `frontmatter` 不在本决定里**——`title` 是产品自己加的**可选扩展**字段（Agent Skills 规范里没有它，规范允许未知字段），2026-10-17 定下**与规范对齐**：不设必填、不许因为它卡住上传。所以它不是「投影」问题，是它自己的地位问题，留给元数据那一版连着 `description` 一起看。

## 理由

**为什么是「覆盖压着」而不是「编辑只是临时的」。** 因为作者改那句话**是在陈述一个事实**：「这个 skill 是干什么的，我说的是这一句」。而版本里那一句是**另一次陈述**——它写在某个版本的 `SKILL.md` 里，属于那一版。两者是**两个事实**，不是一个事实的两个副本。让其中一个静默地覆盖另一个，等于说作者第二次说的话不算数，而他从界面上看不出来这件事。

**为什么清掉之后回到的是「当前版本的那句」而不是「改之前的那句」。** 因为覆盖是**一句话**，不是一条历史。「恢复成版本里的」只有一个自然的含义：现在线上的那一版是怎么说的。若回到「改之前」，系统就要记住一次它并不需要记住的编辑——那是一条隐形的第二历史，而它只在一种情况下被读到，就是这一种。

**为什么投影列不干脆不写。** 让 promote 照旧写投影，换来一个很实在的性质：**清掉覆盖是一个纯读侧的动作**——删掉一个值，没有任何数据需要重建、没有任何东西需要回填。若反过来（描述只由编辑维护、promote 不再写），清掉覆盖就变成一个「从当前版本重新投影一次」的写操作，而它在并发上要处理「清掉的那一刻当前版本刚变了」。

**为什么只做描述。** 梯子说的是「改描述」，不是「改元数据」——把标题一起做了，就是把一个没有产品理由的字段变成有写入路径，而写路径是**要有人对它负责**的东西（谁能改、改了谁看得见、审计记什么）。机制已经在这里了，加标题是加一列的事，不是一次设计。

## 后果

- **`skill` 行不再是纯投影**：它仍然由建行与 promote 维护，但读出去的那一句可能来自另一个地方。**每一处读描述的地方都要先把覆盖合进去**——这是本决定唯一的实现风险：漏掉一处，那个地方读到的是一句没人编辑过的话，而它看起来完全正常。已知的读者至少有三处：搜索、详情、作者面列表（`authorPage` 那条三层 `COALESCE` 要变成四层）。
- **搜索索引跟着组合值走**：改了描述要重新索引（与今天 promote 之后重新索引同一条路）。
- **界面上一处语义必须说清楚**：**清空输入框并保存 = 回到版本里的那句**，不是「描述变成空」。设计件里没有这个控件（那一句现在是死文本），所以这一处要在设计稿阶段画出来，并把这条语义写进那一屏的提示。
- **审计多一种动作**：改了描述要留痕（谁、什么时候、改成了什么）。清掉覆盖也是一次改动，同样留痕——它改的是读者看到的东西。
- **一条不算后果但要记住的**：这**没有**让版本不可变这件事打折扣。版本里的 `SKILL.md` 一个字节都没变；变的只是「对外那一句话取自哪里」。
- **两条顺手量出来、但要留给元数据那一版一起处理的**（2026-10-17 核实，都不是本决定的后果，记在这里免得丢）：
  1. **`title` 缺席时退回 `name`，于是控制台列表上名字出现了两次。** 校验器那一行是 `optionalText(frontmatter, "title").filter(value -> !value.isBlank()).orElse(name)`（`SkillUploadValidator.java:57-58`，中间那个空串过滤让 `title: ""` 与「没写」同一条路）；而全仓库——网关那份真实的 `SKILL.md`、所有测试夹具——**没有任何一个 skill 写过 `title`**，所以今天每一行都是这样。设计件的 24 条夹具**全都写了 `title`**，所以它画的那一行依赖一份现实中不存在的输入。
  2. **`name` 的校验比规范松。** 规范（`references/gitlab/.../skill_frontmatter_v1.json`，vendored from agentskills.io）要求 `^[a-z0-9]+(-[a-z0-9]+)*$`、最长 64；`SkillUploadValidator.requireUsableName` 只挡空白、`/`、`\`、`.`、`..`、`@`、`%`、`;` 与长度——**大写、下划线、中文都提交得进来**。形状一旦收严，要先想清楚**已经进来的那些名字怎么办**（它们是不可改的地址）。
