# ADR 0179 · 行为明细只给本人，聚合给所有者，保留 90 天

- **状态**：已采纳
- **日期**：2026-11-10
- **所属版本**：[`v58-usage-history`](../versions/v58-usage-history/README.md)
- **依赖**：[ADR 0149](0149-use-is-counted-per-account-per-day.md)（账号 × 天去重、公开面只给分桶）、[ADR 0153](0153-usage-metrics-is-its-own-module.md)（度量是独立模块）

## 背景

v49 只把使用做成公开面的分桶聚合，ADR 0149 决定 5 写着「不存 IP、UA、调用了哪个文件」，后果段又写「没有『谁用过』的接口」，为的是不让计数变成可还原的个人行为记录。

2026-11-10 产品负责人提出三件新事：

1. 用户要能看到**自己**搜过什么、invoke 过什么、读过 / 写过什么；别人分享给自己的 skill 也一样，只看得到自己的行为。
2. 所有者要看得到**自己的 skill** 的使用：公域里看总统计；分享给协作者时，按协作者看使用量，但不需要看到对方的操作明细。
3. 内部需要一份**可按账号还原**的行为明细，用于分析与审计——搜索、浏览、读取今天完全没有留痕，`audit_event` 只覆盖写操作。

三者都要求存下比「账号 × 天」更细的数据，与 ADR 0149 决定 5 直接冲突。可选项有三：不记、只记聚合、记明细但按层限制可见性。

## 决定

1. **记行为明细**：已登录用户的全部行为都留痕。完整日志 = `audit_event`（写入 / 管理 / 授权 / 凭据 / 标签 / 同步，事务内写）与新增 `activity_event`（检索 / 使用 / 账号会话，best-effort 写）的**并集**。写入类不复制到 `activity_event`。
2. **可见性分四层**：
   - **第 1 层 公域**：公开 skill 的所有者只看到聚合——不同账号数（分桶）、累计调用次数（分桶，[ADR 0152](0152-cumulative-calls-are-their-own-signal.md)）、入库人数。
   - **第 2 层 共享**：私有 skill 的所有者看到每个协作者的 **调用次数 + 提交版本数**（采用 + 贡献）与最后活跃；**不含读取 / 写入次数、搜索词与操作明细**（2026-11-10 用户定：读取基本是调用的影子，文件级写入噪声大）。
   - **第 3 层 本人明细**：每个账号只看自己的明细。
   - **第 4 层 内部**：运营 / 审计通过数据库看全量，不建产品界面、不做导出。
3. **协作者之间互不可见**；协作者看不到自己以外的任何人。
4. **分层保留**：明细在 PG 保留 90 天；90 天前的分区先导出 **NDJSON.gz** 到 OSS 低频访问层、核对行数后再 `DROP`；日汇总保留 1 年；M15 的累计值与 `audit_event` 永久保留。
5. **调用口径**：一次调用 = API 的 `/api/v1/.../body` 成功加载正文；网页的 `/web/.../body` 是控制台预览，记 `file_read`，不算调用；`/files/SKILL.md` 同样是「读取」；整版下载（`run` / `get`）记入日志，但不展示成「调用」。
6. **搜索与调用的关联**：搜索事件记录当次搜索（合并后的结果集）返回的 skill 列表与总命中数；调用事件写入时按「同账号 + 30 分钟 + 该 skill 在结果里 + 取最近一次命中的搜索」做时序匹配，匹配不上就是「直接调用」。**不引入 `search_id` 透传**，CLI 与 agent 不为关联改动。
7. **账号注销**：账号资料与个人命名空间内容按 v56 的 30 天窗口删除或去标识化（`PurgeAccountsUseCase` 不变）；**行为明细与日汇总不随注销删除**，它们是内部安全、审计与产品分析记录，按各自保留期保存（明细 90 天、汇总 1 年、冷归档 1–3 年）。日志里的账号引用是去标识化的账号 id——账号行只余占位 handle，不含手机号、密码、凭据或同意记录；这是去标识化，不是匿名化。本人命名空间里的 skill 被删除时，指向它的日汇总行随 `skill_id` 外键级联删除；`activity_event` 没有外键，连本人在别人 skill 上的汇总行一起保留。
8. **存储分层**：热明细在 PostgreSQL（同实例、同 schema、原生周分区，90 天）；温层是 PG 日汇总（1 年）；冷层是 **OSS 低频访问层里的 NDJSON.gz**（一周一个对象），存 90 天前明细（1–3 年，离线分析，不参与在线查询）；审计 `audit_event` 永久在 PG。选 NDJSON 而不是 Parquet，是因为服务端没有 Parquet 写入依赖，而 `COPY` 流式导出 + gzip 已经是现成的；DuckDB 的 `read_json_auto`、Spark、Trino 都能直接读，不锁死也不需搬迁。不引入 SLS 或 TimescaleDB（阿里云 RDS 的 TimescaleDB 是 Apache-only 构建，压缩与保留策略不可用）。

## 理由

- **「自己看自己」不产生他人可见的个人行为记录。** ADR 0149 要守的是「别人看不到你的」，不是「你自己也看不到」。这条 ADR 把两件事切开，是它对 0149 决定 5 的修订，而不是推翻隐私原则。
- **所有者看聚合、不看明细。** 公域的不同账号数沿用 0149 的分桶；共享给协作者时，所有者需要「谁在用、用了多少」来管理，但「谁在何时读了哪个文件」属于协作者的个人行为，不给。
- **明细而不只是聚合。** 「找回上周用过的 skill」需要时间与对象；「排查某账号用了哪一版」也需要。聚合回答不了。
- **完整日志是并集而不是一张表。** 写入类必须与业务写入同事务（否则会出现「授权写进去了而审计没有」），这是 `audit_event` 的既有语义；消费类高频、失败不能影响读（ADR 0153），必须另走 best-effort。把两者硬塞进一张表，会同时破坏这两个性质。
- **90 天与公开信号的清理期一致。** 需要更长趋势时看日汇总与 M15 的累计值。
- **同实例 PG 起步。** 现阶段量小，用户侧要「写完立刻看到」，所有者统计要与业务表 join；同库最省。高量后的迁移触发条件写在研究文档里。

被否掉的：**不记**（产品需求要）；**只记聚合**（回答不了具体历史）；**明细对作者 / 协作者开放**（扩大可还原面，与 0149 冲突）；**明细永久保留**（数据面过大）；**另建一条写入流**（与 `audit_event` 重复）；**SLS 起步**（近实时而非读己之写，不能与业务表 join）；**TimescaleDB**（阿里云只有 Apache-only 构建）。

## 后果

- 搜索词与文件路径成为**存储的个人信息**，隐私政策需要补充说明；并且要写明**账号注销后行为日志仍按分层保留期保存**（在线明细 90 天、归档最多 3 年、汇总 12 个月），账号已去标识化。这是 v58 上线的前置。
- 90 天外的明细不可查，趋势只能看日汇总与聚合。
- 运营分析明细需要数据库权限；没有界面，也就没有「谁看了明细」的审计记录——这是本版的已知缺口，留给运营侧策展工作台。
- 同实例的 1 核 1G 与 20 GB 存储是硬约束：上线前扩容存储，并持续盯 CPU 与查询延迟；达到触发条件时拆独立实例或接 SLS。
- M15 的公开分桶口径不变；本 ADR 不改 `skill_usage_day` / `skill_usage_total` 的展示。
