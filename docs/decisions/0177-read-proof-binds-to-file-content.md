# 0177 · 读凭证绑文件内容，不绑整版摘要

- **状态**：已采纳
- **日期**：2026-11-10
- **所属版本**：[`v57-draft-loop`](../versions/v57-draft-loop/README.md)
- **取代**：[ADR 0136](0136-cli-file-verbs-follow-intent.md) §决定 4 的放行条件（「读后版本摘要未变」与「值是读时的版本 ETag」两句）
- **依赖**：[ADR 0101](0101-the-cli-never-deletes-files.md)（CLI 不删东西）

## 背景

[ADR 0136](0136-cli-file-verbs-follow-intent.md) §决定 4 把 `--overwrite` 的读凭证定成「读时的版本 ETag」，理由是「版本 ETag 同时覆盖『同一草稿里别的文件变了』」。

2026-11-09 的实录推翻了它：在 `lijinzhao/bilibili@JD0T518T` 上批量覆盖 6 个文件，每成功写入一个，整版摘要就变一次，其余文件（字节没动）的凭证一起作废，从第 2 个起连环被拒。**一条命令带多个 `--from` 也一样**——`write_local.go` 每传完一个就重取 `etag` 再比对。3 轮才把 6 个文件传上去，脚本化上传做不了。

这道闸要回答的问题只有一个：**我马上要覆盖掉的这份字节，是不是我读过的那份**。版本 ETag 把「同一草稿里别的地方变了」也算了进来，那是另一个问题（我手里的草稿是不是最新），不该由覆盖闸回答。

当时的选项：

1. 保持现状，加 `--force` 放行
2. 一条命令开始时做一次整版检查，之后不再检查
3. 凭证改绑文件内容哈希——服务端文件清单里每个文件本来就带 `sha256`

## 决定

1. 读凭证 = 该文件**在当前版本文件清单里的 `sha256`**。写入任何文件都不影响其他文件的凭证。
2. **读侧**记账的命令与 ADR 0136 相同：整份 `read`（没被行数或字节上限截断）、`cat`、单文件 `get` 记；`--offset` / `--limit` 的部分读、被上限截断的 `read`、`head` / `tail`、`get --all`、`get -o -` 不记。
3. **两侧任一为空都按「没读过」处理**：旧记录（只有 `etag`）或服务端清单没给 `sha256` 时，闸门一律关闭——这道闸的存在意义就是拦住写入，不是在没有依据时放行。
4. 仍然**没有 `--force`**。
5. **写入成功也记一条凭证**：`write --from` 写成功一个文件后，用紧接着的文件清单把该文件的新 `sha256` 记下（服务端归一之后存下的内容，清单里就是这么写的）。只覆盖 `--from` 的批量路径；`write` 从标准输入、`edit` 仍不记，写完再覆盖同一文件要重读一次。少了这一条，批量失败提示的「重跑同一条命令」必然在第一个已写文件处被拒。
6. 一条命令里的多个文件仍然逐个 PUT，不做整批原子（理由见 [`v57` PRD §不做 2](../versions/v57-draft-loop/prd.md)）；每写一个都以最新清单刷新判断依据。

## 理由

- 每个文件都有自己的 `sha256`，覆盖前比它，恰好回答了唯一要回答的问题。写过 A 之后 B 的字节没变，B 的凭证继续有效。
- **否掉 `--force`**：ADR 0136 的理由今天仍然成立——它会变成习惯性的确认键；而且它解决的是「被拒了怎么办」，不是「为什么连环被拒」。
- **否掉「一条命令开始时检查一次」**：它把 N 个文件的判断压成一次，任一文件变了就整批拒绝，误报更宽；循环写（每个文件一条命令）依然没有变好。
- **否掉 mtime / 大小**：mtime 是客户端时钟，大小不区分内容。

## 后果

- 本机旧读记录（字段是 `etag`）升级后一律不匹配，覆盖前要重读一次；不会写错内容，只多一步。**不做迁移**：读出来没有 `sha256` 就按「没读过」处理。
- 保守性变化：以前「同一草稿里别的文件变了」也作废凭证，现在不会。这是有意的——那个变化不影响「我要覆盖的这份字节是不是我读过的那份」。
- ADR 0136 其余各条不变；只取代 §决定 4 的放行条件（「读后版本摘要未变」与「值是读时的版本 ETag」两句）。0136 的文件头据此标为「部分被取代」。
- 批量失败时 CLI 报出「已写入 / 失败 / 未开始」三组文件，按提示重跑同一条命令即可补齐。重跑成立靠的是 §决定 5，不是「内容没再变」——写成功之后服务端的内容**已经变了**。
- 本机记录不再能证明「手里这份是当前草稿」：同版别的文件变了，凭证仍有效。这是有意的取舍（见上）；要判断草稿整体是否最新，用 `skmr skill files` / `version diff`，不是覆盖闸的职责。
- `pins.Reads` 的记录字段随之改名。
- 读记录是缓存，有上限（见 `internal/pins/reads.go` 的 `maxReadProofs`）：一次批量超过上限、或其它 skill 的读把记录挤掉时，早先写入的文件在重跑时仍会被要求重读。上限之内的常规批量不受影响。
