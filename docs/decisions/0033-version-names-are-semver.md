# ADR 0033 · 版本名是作者声明的 semver，身份仍是 digest

- **状态**：已采纳
- **日期**：2026-10-07
- **依赖**：[ADR 0005](0005-content-addressing.md)（内容寻址与幂等）、[ADR 0012](0012-addressing-and-version-pinning.md)（寻址与版本钉）、[ADR 0031](0031-submitting-and-publishing-are-two-actions.md)（提交与上线分开）
- **修订**：ADR 0012 §决定 3「**`skill_version` 加一列序号 `number`**，它是**不可变的别名**，不是身份」与 §理由 里「为什么序号是「不可变的别名」而不是「序列号」」「为什么序号不需要新的并发机制」两节（**正文不变**；别名从**服务端自增的整数**换成**作者声明的 semver**，`number` 降级为内部排序键）。§决定 2「版本用 `@` 后缀」的**形式**不变——`@` 后面那一段换了，`latest` 与 `@sha256:…` 两种写法原样保留
- **扩展**：[ADR 0012](0012-addressing-and-version-pinning.md) 的地址语法——`@3` 换成 `@1.2.3`；另加一个只给 L1 的读端点与一个版本请求头（这两条不在 0012 的范围内，是新加的）

## 背景

P0a–P0d 里，版本的名字是**服务端自增的整数**：`alice/pdf-tools@3`。它是一条**不可变别名**——身份是 `digest`（ADR 0005），序号只是人能读的那个句柄，等价于 git 的 tag。ADR 0012 选它有三个实在的理由：唯一、单调、**由 `skill` 行的锁保证**，而且作者什么都不用做。

2026-10-06 用户提出：这个命名方式不符合通用软件的版本规范。核实之后，他的判断有两条外部依据：

1. **Agent Skills 规范本身的 frontmatter 没有 `version` 字段**（只有 `name` / `description` / `license` / `compatibility` / `metadata` / `allowed-tools`）。版本属于**发布方扩展**——飞书在 `open.feishu.cn` 的索引里就发了顶层 `version`（[TD §1.5](../versions/v1-hosting/technical-design.md)），而本项目本来就要求原样透传未知字段。
2. **宿主自己的清单规范用的就是 semver**：`plugin.json` 里 `name` 与 `version` 是仅有的两个必填字段，`version` 必须是 SemVer 2.0.0（`MAJOR.MINOR.PATCH[-预发布][+构建元数据]`），`1.0` / `v1.0.0` / `latest` 会被 loader **拒收**；**省略**它时，身份就是 git commit SHA，每次提交都算一个新版本。

第二条的后半句正是本项目**已经有的那一半**：没有声明 → 身份是内容哈希。所以这次要补的是「声明版」，而它的形状生态已经给好了。

同一次讨论里还有另外两件事要一起落地，它们与版本命名无关、但同属「让读取像本地那样渐进加载」：

- **「默认加载的那一层」今天没有便宜的路。** 要拿到它必须调详情，而详情按设计会把整份文件清单一起给（清单是零内容的元数据，所以它不违反渐进加载；但为一个「这 skill 是不是我要的」的判断付几十条清单条目的钱，正是渐进加载要避免的）。
- **版本只能写进地址**，没有请求级的写法。

摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 保持服务端自增整数 | 名字不带任何兼容性含义——就是这次要改的那件事 |
| b | 服务端按某种规则自增出 semver 形状 | 服务端无法知道一次改动是不是破坏性兼容。**伪造的 semver 比诚实的计数器更坏**，因为它看起来像有含义 |
| c | **作者在 frontmatter 声明 semver** | 采纳 |
| d | 保留整数地址，另加 semver 只作显示元数据 | 两套编号并存，而「两套编号」正是要消掉的东西；且地址里那个数字会与作者源文件里的对不上 |

## 决定

1. **版本名 = 作者在 `SKILL.md` 顶层 `version:` 声明的 semver 字符串。**
2. **校验判据与宿主 plugin loader 同一套**：合法 SemVer 2.0.0；拒 `1.0`、`1.2`、`v1.0.0`、`01.2.3`、`latest`。**YAML 里 `1.0` 是浮点数**，会撞上「必须是文本」这条既有检查——拒绝是对的，但消息要专门写，告诉作者加引号（`version: "1.0"`）。
3. **不声明就没有名字。** 这一版只能按 `@sha256:<hex>` 钉。声明与否都是合法的提交。
4. **地址的三种写法**：`ns/name`（`latest`，由指针决定）、`ns/name@<semver>`、`ns/name@sha256:<hex>`。**原来的 `@N` 不再解析**，一律 404。
5. **`latest` 仍由 `skill.current_version_id` 指针决定**，可以前移也可以回移。它**不是**「已上线版本里版本号最大的那个」。
6. **一个 skill 内版本名唯一且不可变**：`UNIQUE (skill_id, version)`。**同号不同内容 → 400 `version_already_exists`**；同号同内容仍是 ADR 0005 的幂等（200，返回已有那一版）。
7. **内部整数 `number` 保留，降级为未公开的排序键**（提交序）。它从地址语法与**所有**线上记录里撤出。
8. **新增只给 L1 的读端点**，返回 `name` / `title` / `description` / `visibility` / `frontmatter` / 版本（名字与 digest），**不含文件清单**。详情端点不动。
9. **版本头 `X-Skill-Version`**，语法与 `@` 后缀同一套（`1.2.3` 或 `sha256:…`），只在 `/api/v1` 的读接口上生效。与地址里的钉**同时给出且不一致 → 400**；头本身畸形 → 400。
10. **客户端仍是 CLI**（令牌进钥匙串，不进模型上下文），**不新增匿名读面**。

## 理由

- **为什么 semver 是作者的声明，而不是服务端的保证。** 「1.2.3 相对 1.2.2 只有补丁级改动」这句话服务端**无法验证**——它既不知道作者改了什么，也不知道什么算破坏性。所以版本号的可信度是社会的，不是技术的：**真正保证「取到的字节是哪一份」的仍然是 `digest`**。这一条不写清楚，将来会有人把版本号当成可信的兼容性信号去自动升级。ADR 0005 的内容寻址地位不变。
- **为什么 `latest` 不能是「版本号最大的那个」。** 上线 `1.0.0` → 上线 `2.0.0` → **回滚**（把 `1.0.0` 再上线一次）。第三步如果按「取最大的版本号」算，`latest` 仍然是 `2.0.0`，**回滚等于没做**——而回滚是 ADR 0031 已经做了、且网关强制要求存在的能力（源文件回退后 digest 相同、提交是幂等的，只有把指针移回去才能让服务中的网关与运行的代码一致）。这个形状本来就是业界的：

  | 本项目 | npm |
  |---|---|
  | `@1.2.3`（不可变） | `pkg@1.2.3`（不可变版本） |
  | `latest`（`current_version_id`，可移动） | `latest` dist-tag（可移动） |
  | `@sha256:…` | `integrity` 哈希 |
  | 同号不同内容 400 | `cannot publish over previously published version` |

- **为什么作者声明，代价照实说。** 分配权从服务端挪到作者之后，「改完忘了改版本号」从**不可能发生**变成**一次普通提交就 400**。这是 npm 的真实行为，也是这套规范能成立的前提（版本号一旦可以被服务端随便改，它就不再是作者对兼容性的声明）。代价是流程上的：CLI 必须把 `version_already_exists` 说清楚——直接说「`SKILL.md` 里的 `version` 还是 1.2.3，请改成新的版本号」，否则人会以为提交成功了。
- **为什么名字可以不声明。** 宿主 `plugin.json` 省略 `version` 时身份就是 commit SHA——**没有人类可读的名字，不等于没有身份**。本项目已有的那一半（digest）正好接得上。强制要求声明会让「只想放一份草稿」的人先去做一次版本决策。
- **为什么 `number` 保留却撤出线上。** 它还在承担两件事：`MAX(number)+1` 的分配与 `UNIQUE (skill_id, number)` 一起保证了**提交序**这个稳定的排序键，而排序不能用 semver：作者完全可能先发 `2.0.0`、后发 `1.9.0`（修老线），此时「我最近提交了什么」的答案是 `1.9.0`，而「版本号最大」的答案是 `2.0.0`。作者面的列表要的是前者。它撤出线上的理由与 ADR 0004 把 `id` 撤出 URL 是同一条：**内部身份不该出现在外部契约里**，否则它会被别人依赖。
- **为什么加一个只给 L1 的端点，而不是让详情少给一点。** 详情的清单是整个设计的枢纽（[TD §4.2](../versions/v1-hosting/technical-design.md)）：给出完整清单但零内容，客户端不必下载就能枚举 L3，MCP 的 `skills/list` 要的正是它。把清单变成可选会让 `show` 与那条「从入口进一次、之后照着清单里的 URI 走」的主流程各多一次往返。所以是**加一条便宜的路**，不是**把原来的路改贵**。
- **为什么头与地址冲突时是 400，而不是谁优先。** 两个来源说不同的话，说明客户端自己也不知道要哪一版——那是一个 bug，必须响。任何「谁优先」的规则都会把它变成静默地给出**与地址不同的字节**：一条 URL 不再唯一决定响应，缓存与「抄走的地址」同时失效。
- **被否掉：头覆盖地址。** 同上，且更坏——地址里写着的版本被无视，而复制那条地址的人不会知道。
- **被否掉：版本头也放到浏览器面。** 浏览器面已经有两条选择路径（地址后缀、diff 的 `?to=` / `?from=`），再加第三条会把冲突矩阵翻三倍，还要动 CORS 的 `allowedHeaders`。头是给 agent 那条通道用的。

## 后果

- **`@N` 地址从此刻起全部 404。** 没有已部署的库（v1 尚未交付），所以外部没有损失；**本机那台 dev 库的版本会变成无名版本**，只能按 digest 寻址。**重新提交不是回填**：加了 `version:` 就改了字节、也就改了 digest，那是**新建一个版本**，不是给旧版本补上名字。这条要写进 `V11` 的注释。
- **`number` 的含义变了**：它不再是「地址里的那个数」，只是提交序。`UNIQUE (skill_id, number)` 保留，但它不再是契约的一部分。
- **提交响应新增 `skill_created`。** CLI 原来用 `version.number == 1` 区分「已创建」与「已提交」，而 `created` 不能替代（它的含义是「这次调用创建了一个版本」，新 skill 与新版本都为真）。语义与原来的 `number == 1` 等价：这次插入之后该 skill 的版本数为 1。
- **动作（上线 / 丢弃）改按「钉」指版本**，因为**没有名字的版本也必须能被上线与丢弃**——digest 永远在，semver 可能没有。
- **网关保持无名**（`gateway/skillmaster/SKILL.md` 不加 `version:`）：它是机器寻址的，没有人读它的版本号，而 `metadata.platform_api_version` 已经在管「本地网关是否过期」。这也避开了下面那个陷阱。
- **网关的启动陷阱。** 网关每次启动自举重发，而 `GatewayConfig` 的 `ApplicationRunner` 失败**会中止启动**（刻意如此）。一旦网关源文件写了 `version:`，改动正文却忘了改版本号就会撞 `UNIQUE (skill_id, version)`、于是**应用起不来**。行为是对的（应当响亮地失败），但错误消息必须可行动。
- **`+` 构建元数据能不能穿过 servlet 防火墙要实测**（已知 `;` 与 `%` 会被 `StrictHttpFirewall` 挡）。穿不过就把构建元数据从**地址形式**里禁掉并写明。
- **校验判据多了一处需要同步的地方**：宿主 loader 的判据若变化，这里要跟。今天的依据是官方文档与 SemVer 2.0.0 规范。
