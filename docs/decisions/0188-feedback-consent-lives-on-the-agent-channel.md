# 0188 · 反馈的同意在 agent 通道里记录，不放到浏览器

- **状态**：已采纳
- **日期**：2026-11-13
- **所属版本**：[`v64-feedback`](../versions/v64-feedback/README.md)
- **依赖**：[0181](0181-text-limits-use-unicode-code-points.md)（文本上限按码点）、[0175](0175-account-deletion-is-immediate-with-a-fixed-retention.md)（注销与去标识化）
- **相关**：[`research/agent-feedback-legal-risk.md`](../research/agent-feedback-legal-risk.md)（条文与风险）

## 背景

v64 让 agent 写一份反馈文档提交给平台。平台是个人信息处理者，处理前要有告知与同意；但提交发生在 CLI 里，agent 既能打印内容，也能自己按发送。摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 浏览器批准：CLI 建 pending，用户在浏览器（登录会话）里点同意 | 平台能举证「用户本人批准」，但每次提交要打开一个页面；用户明确选择不放到页面端 |
| b | **agent 通道：预览与发送分离 + 站内回执 + 撤回** | 采纳 |
| c | 只靠 `--consent` 标志与服务端审计 | 没有任何「用户看过」的痕迹；预览、回执与撤回都不存在 |
| d | 会话级一次性授权：skill 启动时问一次，之后直接提交 | 同意不覆盖当次内容；一次授权可以送出任意文档 |

## 决定

1. **提交只在 CLI / agent 通道完成**；不做浏览器批准，也不做「严格模式」。浏览器批准留作将来的可选项（[`v64-feedback`](../versions/v64-feedback/prd.md) 不做 9）。
2. **预览与发送分离**：不带 `--consent` 只打印将发送的完整文档（密钥前缀已替换）、同意说明与将发送的字段，不发送；带 `--consent` 才提交。这一步只防「顺手发」，不作为同意的证明。
3. **服务端记录**：同意版本（当前隐私政策版本，不接受客户端指定）、内容哈希、时间、来源（CLI）。每次提交都按当前版本记录，政策改版不需要额外追认。
4. **提交后给用户一条站内通知**（复用 `announcement` 形状），含回执号与 `skmr feedback delete <回执> --yes`；删除同时移除对象存储副本。
5. **平台不宣称「每次提交都有用户本人同意」。** 服务条款写明「用户指示 agent 提交，视为用户提交；用户对自己让 agent 做的事负责」；隐私政策写明「平台无法核验 agent 是否在提交前征求过同意」。
6. **残余风险如实记录**：个人信息保护影响评估里写「agent 可能代签」，对策是事后回执、删除权、最小必要与合同分配责任，不是技术上的不可能。

## 理由

**为什么不做浏览器批准。** 它是唯一能证明「用户本人点过」的通道——CLI 的 API key 与浏览器的会话 cookie 是两套凭据，批准接口只接受后者，agent 就完不成最后一步。代价是每次提交要开页面，而这条链路的场景恰恰是 agent 在终端里卡住；用户明确选择留在 agent 通道。

**为什么不是纯标志。** 只传 `--consent` 连「用户看没看过」都没有痕迹。预览把内容推到眼前，回执把「发生过什么」推到用户眼前，撤回给出一条真正的补救路径——三者合起来，把「代签」从无从发现变成可被发现、可被纠正。

**为什么同意版本由服务端决定。** 客户端能指定版本，就能拿旧条款给新内容背书；记录当前版本，政策一改，下一次提交自然落在新版本上。

**被否掉的：** 浏览器批准（用户选择不走）；纯标志（无痕迹）；会话级授权（不覆盖当次内容）。

## 后果

- **隐私政策与服务条款必须同步改**：两处 `legalText.ts` 各加一节，写清收集什么、用途、长期保留、不回传第三方，以及「平台无法核验 agent 是否征求过同意」。
- **需要一份个人信息保护影响评估**：反馈可能含敏感个人信息且要写对象存储，属于 PIPL 第 55 条的情形；报告至少保存三年。
- **将来要做「可举证的本人同意」**，新增浏览器批准或严格模式即可，不改本 ADR 的其余决定。
- **运营读库**：本版不做运营界面与推送；运营按回执号或时间范围直接查 `user_feedback`。
