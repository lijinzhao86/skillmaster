# 0052 · 申请不是授权：申请一档，由管理与所有者批准

- **状态**：已采纳
- **日期**：2026-10-17
- **所属版本**：[`v5-skill-management`](../versions/v5-skill-management/README.md)
- **依赖**：[0047](0047-permissions-are-a-ladder.md)（权限是一条梯子）、[0048](0048-visibility-hands-out-a-rung.md)（公开是把某一档交给所有人）、[0034](0034-skill-level-sharing.md)（共享是 skill 级的授权）
- **补充**：[0073](0073-asking-for-access-splits-by-plane.md) 定下五条动作各自落在哪个平面——申请 / 撤回 / 读自己的在消费面 API，批准 / 拒绝与待批列表只在网页。**正文按原样保留**。

## 背景

梯子把授权从「只有所有者」放开到「`管理` 及以上」，但**怎么开口**这件事一直没有答案。一个人看得见这个 skill（公开档覆盖了他，或者他被授了任一档——`调用` 及以上），想做点更多的事——提交一个版本、修一句描述、把它上线——他在产品里没有任何地方能说这句话。今天的替代做法是**在产品之外开口**：找他认识的协作者，在聊天里说一句。这与 v5 要解决的第 1 条是同一个毛病：**一条真实存在的流程绕过了产品，所以它不留痕迹**。

两家参照产品都把「开口」做成了一个对象：

- **GitLab**：项目页 `⋮ → Request Access`；请求内部就是一条 `pending` 状态的成员行，Maintainer / Owner 在 **Members 页**批准或拒绝，申请人可以撤回。入口只对**看得见的项目**开放。
- **GitHub**：组织侧的 access request 出现在仓库的 Manage access 里，管理员批准；个人仓库则直接是邀请。

摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 不做，继续在产品之外开口 | 一条流程在产品外走，就没有记录、没有入口、也没有任何东西提醒有权的人去处理。这正是本版要修的那一类问题 |
| b | 申请就是一条「还没生效的授权」（照 GitLab 的内部模型） | 每一处读授权的地方都要多问一句「这一行还没生效」：名单、「谁能碰它」、审计、按档位滤内容的每一条路径。`skill_grant` 从建立起就只表示**已经授了**；把一个流程状态塞进它，是让数据模型去背流程 |
| c | **申请是独立的对象；批准时按最终那一档授权** | 采纳 |

## 决定

1. **申请是独立的对象**：它是谁、对一个 skill、想要哪一档、什么时候提的。**它不授予任何东西**，也不出现在「谁能碰它」的名单里——名单里只有真正有权限的人，加上所有者。
2. **只有看得见这个 skill 的人能申请**：梯子第一档（`调用`）及以上，或者公开档覆盖了他。**私有的 skill 对陌生人仍然是 404**：不存在「申请访问一个你不知道存在的东西」的入口。
3. **申请带着想要的那一档**；**批准时管理者可以改**。批准 = 按最终那一档授权（复用已有的授权能力，`管理` 及以上）；拒绝只是让申请消失。一个人对一个 skill 最多一条待处理申请；**申请人可以撤回**。
4. **没有通知系统**：待处理的条数出现在 **设置 › 协作者** 的二级菜单与那一块本身。将来有了通知面，它挂在这同一个对象上，不改变这个模型。
5. 申请、撤回、批准、拒绝**各记一条审计**——这四件事都是「某个人对某个人做了什么」，而这正是审计要回答的。

## 理由

**为什么不做成「未生效的授权」（选项 b 被否）。** GitLab 内部这么做是因为它的成员模型本来就是**一行带状态**的东西：邀请、请求、成员是同一个对象的三个状态。我们的 `skill_grant` 不是那个形状，而且从 v1 起它的含义只有一句——「这一档已经给了这个人」。把它变成状态机，代价会落在每一处读它的代码上，而收益只是省一张表。

**为什么只给看得见它的人（决定 2）。** 「私有」在本产品里的定义是**只有名单里的人知道它在**（[0048](0048-visibility-hands-out-a-rung.md)）。一个会说「这里有个 skill，你要不要申请」的 404 页面，等于把那个定义撕开一道口子：它的全部价值就在于那道口子不存在。参照产品也是同一条线——GitLab 的 Request access 只对可见项目出现。

**为什么让申请人选一档（决定 3），而参照产品不让。** 两家的申请人说的是「我要看这个仓库」，角色是管理员加的，因为它们的角色只有三四个、且申请入口的主语是**看得见**。我们的梯子有五档，而「我想参与」落在哪一档并不唯一：想提交版本是 `写入`，想上线是 `维护`，想管人是 `管理`。让审批者去猜，比让申请人说清楚更差；而批准时仍然可以改，**定档的权力没有被让出去**——留在有权授权的那个人手里。

## 后果

- **一张新表、五条路由**：`skill_access_request`；申请、撤回、列申请、批准、拒绝。`ModuleMap` 加一行（`TableOwnershipTest` 自己从迁移里收表对账，没有第二处清单），迁移编号接着排。
- **没有通知，就没有时效承诺。** 申请可能一直躺在那里没人看见；数字标是唯一的提示。本版不承诺「多久之内答复」，也不做自动过期。
- **申请可以撤回或被拒绝，且不留理由。** 拒绝只是让那一行消失；理由要另开一个字段与一种界面，本版不做。
- **申请人拿到的档位由批准者定**，可能与他申请的不同。**批准之前**，那一行要把「他申请的」与「将要批准的」分成两个可见的东西（名字下面写他要的那一档，控件预填它、可以改）——否则改档这件事在界面上不存在。**批准之后整行消失。** 申请人下次打开那一页时看得到自己**现在的档位**（信息页「申请」块那句「当前档位为…」；拿到「管理」的人在设置 › 协作者里看到自己那一行）——但**没有任何界面**会说「你申请的那一档被改了」：本版没有通知面，所以这件事在界面上说不了（申请与批准各留一条审计，那是给管理者的记录，不是给申请人的提示）。这是一个知情的代价，要补它得等通知面，不是在设置 › 协作者上加一行。
- **删除一个 skill 时，它的申请跟着走**：软删只写 `skill.deleted_at`，不碰这张表；恢复之后它们随 skill 重新出现，所以不需要单独清理。
