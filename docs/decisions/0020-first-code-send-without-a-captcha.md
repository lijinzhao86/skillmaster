# ADR 0020 · 注册的第一个发码请求免图形验证码

- **状态**：已采纳
- **日期**：2026-10-02
- **依赖**：[ADR 0013](0013-phone-login-and-username-slug.md)（手机号登录与用户名 slug，三条防刷在这里）、[ADR 0018](0018-caller-address-behind-the-proxy.md)（「调用方地址」这件事本身是它定的）

## 背景

注册与找回密码都要发短信，而短信按条计费。ADR 0013 因此定下三条防刷，第三条是图形验证码——**唯一能挡多 IP 攻击者的一条**：前两条（每号码冷却、每地址上限）只对有耐心的调用方有效，一台换 IP 的机器两条都不太受影响，而读一张图要一双人的眼睛。

代价落在最不该落的地方：**绝大多数人一辈子只注册一次**，那一次也必须读一张图。而注册被拆成「填资料 → 填验证码」两页之后，「下一步」就是发码那一刻——把一道人机题放在一个人刚刚认真填完表单、最想往前走的位置。

要决定的是：那一次到底要不要免。选项：

1. **每条都过图形验证码**（现状，不动）；
2. **每个地址每个窗口的第一次注册发码免图形验证码**，之后的照旧；
3. **按手机号给一次免费**，同一个号码第一次不用读图；
4. **取消图形验证码**，理由是反正已经有按地址的频控上限。

## 决定

**选 2。** 规则落成 `auth_throttle` 的一条新 scope：`sms:free`，窗口 86 400 秒、上限 1，键是**调用方地址**（[ADR 0018](0018-caller-address-behind-the-proxy.md) 定义的那个地址）。发码用例在发短信前**认领**它：认领到手就跳过图形验证码这一步，没认领到就照旧要求并校验。

四条边界与决定一起生效，缺一条这个设计就不成立：

- **只给注册。** 找回密码每次都过图形验证码。
- **地址取不到就不认领**（`clientIp == null`）：宁可多要一张图，也不要一条没有归属的免费额度。
- **认领排在频控之前、发送之前。** 被频控拒掉时整笔事务回滚，额度自动退回——没发出去的短信不该花掉它。
- **手机号格式校验排在认领之前**：格式错的请求不该认领额度。

## 理由

**为什么不是 3（按手机号）。** 按手机号发免费短信，等于让调用方**用号码的个数换短信的条数**——号码是无限的，地址不是。选 2 之后，白送的那条短信仍然落在每地址每小时 30 条这个硬顶之内；选 3 则把它挪出了硬顶，那不再是「每个地址多一条」，而是「每个号码一条」。

**为什么不是 4（取消图形验证码）。** 它是唯一能挡多 IP 攻击者的一条。取消之后，上限从「每小时 30 条 × 需要一个真人读图」变成「每小时 30 条 × 全自动」，中间那道最贵的人力成本消失了。要换注册摩擦，选 2 只让出**一个地址一天一条**；选 4 让出的是整条曲线的斜率。

**为什么不是 1（不动）。** 那等于承认第一次注册必须读一张图，而这一次的摩擦换来的防刷收益是所有情形里最小的：一个真人一次性注册，本来就是全流程里最不像攻击者的那个请求。

**这是一次放宽，不是加固。** 说清楚它是什么：在此之前每条短信都要过图形验证码；在此之后，**每个地址每个窗口白送一条**。硬上限（每 IP 每小时 30 条）一条没动——多出来的是每个地址每个窗口一条**不需要人力**的短信，规模是「地址数 × 一天一条」。这是明知故犯的取舍，换的是注册成功率。

**窗口是 UTC 当日，不是滚动 24 小时。** 与 `sms:daily` 同一口径（epoch 取整）。所以跨 UTC 零点时，同一个地址可能两条免费相隔只有几分钟。这是固定窗口的已知不精确，与那张表其余规则一致——不一致会更糟。

**为什么需要一个新的只读端点。** 前端要知道「这次开页要不要把图形验证码摆出来」。没有它，回来的人只能靠「点了下一步被拒」学到这件事，而那个拒绝对一个什么都没做错的访客来说是白挨的。所以有 `GET /web/register/code/captcha-required`，而且它**只读**：不认领也不消耗——否则一个开页就问的表单会替每个人把那次免费额度问掉，免费就等于没给。

## 后果

- **每个地址每个窗口白送一条短信。** 上限不变，但这是真金白银：按「每地址每天一条」计。ADR 0013 第三条防刷的强度因此下调一档，代价有界，但要说出来。
- **任何一次重发都要过图形验证码。** 「没收到，重发」这条常见路径一定撞上图形验证码。这是本意，但它落在最需要顺滑的时刻。
- **多一个可枚举的只读端点**（`captcha-required`），因此它也要限流（`register:policy`，900 秒 120 次）。
- **前端多一个状态**：图形验证码从「每次都在」变成「可能要在」。它要么在开页时问一次，要么在第二页返回时主动摆出来——两条路都实现了，见 [`iterations/0011`](../versions/v1-hosting/iterations/0011-register-flow-and-sms-state.md)。
- **没有放松任何其它一层**：手机号格式、每号码冷却、每日上限、每地址上限、图形验证码本身的单次使用与寿命，一条没动。
