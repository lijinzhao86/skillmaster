# 0170 · 凭据的根密钥在云 KMS，一个 CMK 覆盖全部凭据

- **状态**：被 [0172](0172-the-root-key-is-huawei-cloud-kms.md) 取代
- **日期**：2026-11-08
- **依赖**：[ADR 0168](0168-hosted-credentials-are-api-keys-not-identity-passwords.md)（托管边界）

## 背景

凭据落库只有一种做法：AES-256-GCM，每条一组密文，IV 随密文走。仓库里已有同形状的实现（`AesGcmPhoneCipher`，手机号），不需要发明密码学。

要定的是**根密钥放在哪**。三条路：

| | 做法 | 成本 | 拖库 | 拖主机 |
|---|---|---|---|---|
| A | 阿里云 KMS，一个对称 CMK，服务端调 `Encrypt`/`Decrypt` | 一个 CMK 0.3 元/天 + QPS 3 元/天/QPS | 密文不可读，KMS 不在库里 | 主机上有调用凭据，但动作进 ActionTrail |
| B | 自管主密钥，沿用 `SKILLMASTER_PHONE_ENC_KEY` 的形状（32 字节放 `deploy/server.env`） | 0 | 密文不可读 | **根密钥与密文同处一台机器、同一份备份** |
| C | 每条凭据一个密钥 / 阿里云凭据管家 | 约 3–9 元/月/**条** | 同 A | 同 A |

计价口径来自 [2026-10-31 调研](../research/third-party-credentials.md) §四（阿里云官方按量付费页，2026-04-08）。

## 决定

- **A**：阿里云 KMS 共享版，**一个对称 CMK**；服务端调 `Encrypt` / `Decrypt`，根密钥从不进入应用。
- **第一版不上信封加密**（不做「每条凭据一个 DEK、KMS 只包 DEK」）：KMS 返回的密文自带 CMK 与版本，轮换后旧密文照样能解，不需要我们存 `wrapped_dek` 与 `key_version`。
- **单独开一个 RAM 用户**，只授该 CMK 的 `kms:Encrypt` / `kms:Decrypt`；不给 `CreateKey`、`ScheduleKeyDeletion`，也不与 SMS / OSS 共用。
- 成本按「一个 CMK + 峰值 QPS」计，**不随凭据条数增长**；`lease` 时解密一次，不缓存明文。

## 理由

- **否掉 B**：自管密钥的失败模式正好是「拖库」要防的那一种——密文与密钥同处一台机器、同一份部署材料，一次主机失守或备份回捞两样一起到手。手机号能用 B，是因为值与密钥的风险面接近；这里存的是用户**第三方账号的活凭据**（火山引擎 AK/SK、飞书 app secret），泄露后果重一个量级。KMS 还顺带回答「谁在什么时候解了」——`lease` 本身就是解密预言机，没有审计日志，出事时连哪次异常都查不出来。
- **否掉 C**：按条线性计价，1 万条凭据就是 3–9 万元/月，与凭据管家的成本模型同病。
- **否掉信封（仅第一版）**：值只有几十到几百字节，远低于 KMS 单次加密的体积上限；直连加解密少两个字段、少一个重包迁移、少一层要保管的东西。将来若值变大（例如存整份 OAuth token 集）、需要离线可解、或要批量解密省 QPS，再升级成信封，表里加两列即可。
- **为什么是 1 个 CMK**：成本与凭据条数解耦；「每条一个 CMK」只有在需要「删了备份也解不开」时才值得，而那个承诺按条线性计价，不成立。

## 后果

- **每月约 100 元量级**（1 个 CMK + 1–2 QPS），不随条数涨；凭据从 1 千涨到 10 万，账单不变，只多几 MB 存储。
- **KMS 成为 P2 的可用性依赖**：`lease` 要加超时、有限重试与可读错误；**不缓存明文**来省 QPS（省下的钱是零头，增加的泄露面是真的）。
- **开通与运维前置**：KMS 开通、RAM 用户、监控与告警；第一个月账单要核对两个**未核实项**——按量付费是否另收调用费、共享版的默认 QPS 配额。
- **删除承诺受备份约束**：KMS 保护的是「库里与备份里的密文」，不解决「删行之后备份里仍可解」——对外只能承诺「生产库立即删除 + 备份 30 天保留期过期」（[0168](0168-hosted-credentials-are-api-keys-not-identity-passwords.md)）。
- **手机号加密不动**：`SKILLMASTER_PHONE_ENC_KEY` 这一套仍按原样工作，本 ADR 不要求迁移。
