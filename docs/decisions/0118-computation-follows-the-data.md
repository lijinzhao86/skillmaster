# 0118 · 计算跟着数据走：单文件的算在客户端，跨文件的算在服务端

> **状态**：已采纳
> **日期**：2026-10-30

## 背景

给 agent 补齐在线编辑的命令面时（v34），每个命令都面临同一个选择：把结果在服务端算好再传，还是把原始数据拉到客户端再算。

- 单文件的读取与改写（`read`、`head`、`tail`、`edit`）：客户端本来就只拉一份内容，在本地切片与匹配不需要服务端参与。
- 跨文件的计算（`grep`、`wc`、`check`）：如果拉到客户端算，就要先把候选文件的**全部内容**传下来——N 次请求、整个版本进上下文、同一套匹配规则还得在两端各写一份。

曾经的做法是不成文的：`grep` 在服务端（ADR 0062）、`wc` 在服务端、`edit` 在客户端，但没有任何地方说清判据，所以每加一个命令都要重新争一次。v34 要加 `ls` / `find` / `stat` / `head` / `tail` / `grep -C`，这个判据必须先定下来。

## 决定

**计算跟着数据走**：

1. **单文件**的读取、切片、改写 → 客户端。客户端拿到的本来就是一份内容，在本地做不增加传输。
2. **跨文件的「算一个答案」**（搜索、统计、链接检查）→ 服务端算完，只把答案给客户端（命中行、计数、断链），不把内容传下去。
3. **清单是元数据，不是内容**：`ls` / `find` / `stat` 只依赖一次清单请求的结果，在客户端过滤与排版（裸地址另有一次版本解析；没有上线版本时，按档位再探一到两次）；这不违反第 2 条，因为传下来的是路径、大小与摘要，不是文件内容。
4. **显式取内容**（`cat`、`read`、`head`、`tail`）不受此限：把内容给出去就是它的语义，传输不是中间结果。

## 理由

- **否掉「全部拉到客户端算」**：`grep` 一个 16 MB 的版本会把全部文本搬进 agent 的上下文，而它只需要几十行命中；也把「同一套匹配规则」变成两处实现，迟早漂。
- **否掉「单文件也算到服务端」**：`edit` 的匹配已经在客户端，且必须与本地 `Edit` 的匹配规则逐条对齐（v32 §匹配与写回；写回方式的差异——整份重编码、BOM——也在那一节写清）；挪到服务端等于把那份对齐再写一遍，还要为每次改一处多一次请求。
- **清单单独算一类**：它小、结构稳定，过滤是廉价的客户端操作；为 `ls` 的每种排序与过滤都加一个服务端参数，只会把接口吹大。

## 后果

- 服务端只增加这三处：`grep` 的上下文与筛选参数，清单补上 `sha256`（v34——第 3 条说清单带摘要，作者面原来没发这个字段），以及 invoke 头部的能力清单（v34，[0119](0119-permissions-carry-commands.md)，与计算位置无关）。其余新命令**不新增端点、不改授权**。
- 视图里**算行的那一层**（目录推导、名字匹配、目录汇总）是纯函数，输入是清单（或一份内容），输出是行——可单测、不碰网络；取清单仍是命令自己的事。
- 未来若要加「跨文件的聚合」（例如按目录统计 token 数），默认落在服务端，并沿用「只回结果」的响应形状；反过来，任何把整份内容拉到客户端再算的提议，都要先推翻这一条。
- 与 [ADR 0116](0116-editing-happens-online.md) 的关系：那条说的是**编辑发生在哪里**（服务端草稿），这条说的是**计算发生在哪里**（数据旁边）；两条一起构成在线编辑的成本模型。
