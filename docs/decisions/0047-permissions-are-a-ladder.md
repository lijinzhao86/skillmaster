# 0047 · 对一个 skill 的权限是一条梯子，不是一个开关

- **状态**：已采纳
- **日期**：2026-10-17
- **所属版本**：[`v5-skill-management`](../versions/v5-skill-management/README.md)
- **依赖**：[0034](0034-skill-level-sharing.md)（共享是 skill 级的授权）、[0031](0031-submitting-and-publishing-are-two-actions.md)（提交与上线分开）、[0046](0046-deleting-a-skill-happens-in-the-browser.md)（删除只在浏览器面）
- **修订**：[0034](0034-skill-level-sharing.md) §决定 3（角色复用 `namespace_member` 的 `viewer` / `editor` 两个词）、§决定 5（`editor` 能做的恰好两件）、§决定 6（**授权不传染**、只有能写它的人能授权）。**该 ADR 正文四段保持原样**，改动记在这里。
- **更正**：梯子表与 §决定 3 里那句「创建它的人」按 §决定 2 读——所有者是 `skill.namespace_id` 的所有者，**不是 `created_by`**（v5 没有组织模型，两者今天总是同一个人）。正文保持原样，更正记在这里。

## 背景

[ADR 0034](0034-skill-level-sharing.md) 给了共享两档：`viewer`（只读）与 `editor`（读 + 提交版本 + 丢弃自己提交的草稿）。它当时明确写下 `editor` **不能上线**，理由是「上线改变的是每一个读者拿到什么……editor 若能上线，owner 只会在事后发现自己的 skill 被换掉了」。

那个理由今天仍然成立，但它**只证明了「editor 不能上线」，没有证明「上线只能由所有者做」**。中间那一档——一个可以上线、但改不了归属也删不掉东西的人——在 0034 里不存在，于是实际发生的是：想找一个能维护 skill 的同事，只能把他变成所有者（做不到，所有权是命名空间的，不给）或者什么都不给。

设计件已经画完了这条线。控制台的协作者页是一条梯子——**六行**（五档可授，加上不授的所有者，`design/README.md:581-596`），每一档包含它下面的全部：

| 档 | 在下面全部之上，另加 |
|---|---|
| 调用 | 能调用，能按路径点名取单个文件——**列不出目录** |
| 浏览 | 列目录、一个个读过去；网页上的文件栏与详情 / 正文也打开了 |
| 写入 | 提交新版本、丢弃**自己的**草稿 |
| 维护 | 上线 / 回滚、丢弃**别人的**草稿、改描述（设计件那一行写着它，而**本版不做改描述**——见 [prd §不做 #8](../versions/v5-skill-management/prd.md)；与「管理」的改名同一类：画了，本版不交付） |
| 管理 | 授权 / 撤销、改可见性、**改名**（设计件那一行写着它，而**本版不做改名**——见 [prd §不做 #2](../versions/v5-skill-management/prd.md)；于是这一格是设计件画了、而这一版不交付的能力） |
| **所有者** | 删除这个 skill。只有一个，是创建它的人，**不授予任何人** |

于是问题不是「加几个词」，而是**三个能力边界同时被移动**，每一处都与 0034 的某一条决定正面相撞：

1. `editor` 今天不能上线，而梯子的「维护」能。
2. 0034 §决定 6 说**授权不传染**（「一个 editor 若能再授权，一条授权就会自己扩散，而扩散链上的每一环都不在 owner 的视野里」），而梯子的「管理」能授权。
3. 0034 的词表是从 `namespace_member` 借的两个词，而梯子是六个——**借词这件事本身失效了**，因为被借的那张表只有一个值。

摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 保持两档，需要更多就多加一个 `publisher` | 每加一个场景就加一个词，而**「哪些能力可以拆开」这个问题一次都没被回答过**。第三档会带来第四档（能不能丢弃别人的草稿？能不能改可见性？），每一次都是一次迁移 |
| b | **一条有序的梯子，每档包含下面全部** | 采纳 |
| c | 自由的权限位组合（`can_publish` / `can_share` / …各一列） | 组合是乘积，界面要画一张勾选矩阵，而**「谁是管理、谁是维护」这个问题在列表里读不出来**——一列勾选读不出「他比我低一档」这件事 |

## 决定

1. **一列、五个值、有序**：`skill_grant.role ∈ {invoke, browse, write, maintain, admin}`，**每档包含它下面的全部**。判定因此是「档位 ≥ 某档」，不是一个开关。
2. **所有者不是一档，也不进授权表。** 它就是 `skill.namespace_id` 的所有者——一个 `skill` 行已经带着的事实，与 [V12 的注释](../../skillmaster-server/src/main/resources/db/migration/V12__skill_level_sharing.sql) 当时说的完全一致。它**不可授予、不可让渡**，也没有任何接口能改它。
3. **删除是所有者独有的**，不是「管理」档的能力。这是设计件明写的一条（`design/README.md:592`），也是 [ADR 0046](0046-deleting-a-skill-happens-in-the-browser.md) 那条规矩的落点：把一个 skill 从所有读者手里拿走这件事，只有创建它的人能做。
4. **每个操作声明自己的最低档**，不再有两个布尔谓词（`mayWrite` / `mayAdminister`）。逐条见 [`technical-design.md`](../versions/v5-skill-management/technical-design.md) §接口。
5. **「授权不传染」被推翻**：`admin` 档能授权与撤销，包括把他自己加进来的人往下挪。但**所有者永远能撤销任何一条授权**，而且他不在那个名单里、也不是授出来的。
6. **词表照搬参照产品的原词**：中间三档是 GitHub 官方简中的 `Write` / `Maintain` / `Admin`（「写入 / 维护 / 管理」，一个没改）；底下两档来自 `get` / `list` 那条切分（S3 的 `GetObject` / `ListBucket`、K8s RBAC 的 `get` / `list`、NTFS 的「遍历文件夹」与「列出文件夹」）；「所有者」是我们加的。
7. **迁移按语义平移**：`viewer → browse`（今天 viewer 能读、能列、能 invoke——正是浏览）、`editor → write`（今天 editor = 浏览 + 提交 + 丢弃自己的草稿——正是写入）。**消费面的能力一条不变**，这是迁移的验收判据；唯一的新增是 `browse` 按 [ADR 0051](0051-the-author-plane-serves-by-tier.md) 获得了**作者面读**——那是本版有意加的，不是迁移带来的翻转。

## 理由

**为什么「能读」要拆成两档。** 调用与浏览的区别不是粒度洁癖，是**发现与取用的区别**：能调用它的人拿到的是正文，而**他只知道正文点名提到的那些文件**；能浏览的人先看见整个目录。这两件事在访问控制里被拆了四十年（`get` / `list`），因为它们的**信息含量不同**——目录本身就是一份内容。

**这条边界是「不知道」，不是「取不到」，而那个区别要写清楚。** 只有「调用」档的人仍然可以按路径取任何一个文件——路径是猜得到的，而他要是从别处知道了文件名，服务端**不拦**。所以这一档挡的是**发现**：他列不出目录，就翻不完一个仓库。把它写成「取不到」会让人以为有一条按正文白名单过滤文件的实现，而那条实现既不存在、也不该存在（正文的语法是作者的散文，不是一份可以照做的清单）。

**为什么让「管理」能授权，而 0034 当初恰恰否掉了这件事。** 0034 的反对是「扩散链上的每一环都不在 owner 的视野里」——那个论证成立的前提是**授权是这个系统里唯一一种让别人获得能力的方式**，而所有者没有任何地方能看见他名下发生过什么。今天那个前提不成立了：梯子给了所有者一个**永远在最上面、永远撤得掉**的位置（决定 2），而他把一个人提到 `admin` 这件事本身是他做的决定。用一句话说：0034 怕的是**授权在所有者不知情的时候扩散**，而梯子把「谁被提到了哪一档」变成了所有者自己名单上的一行。**这不是把那个顾虑驳倒了，是把它换成了一个能被看见的形状。**

**为什么写成有序的梯子而不是能力位。** 因为产品上真正要说出口的句子是「他是**维护**」而不是「他能上线、能改描述、不能改可见性」。梯子让这句话只有一个来源：说出一档，下面全部被包含；而能力位要求说的人和读的人各自在心里做一次加法，两处一旦不一致，就没有第三个地方能判谁对。

**为什么所有者不是一个可以给的档。** 若所有者可授，就存在「把最后一个人降级之后没人管得动」这个状态，而参照产品正是为它写了「你必须至少留一个管理员」。我们不需要那条提醒，因为顶上是**不可授的所有者**——他不在名单里、也不是授出来的，所以**永远有人兜着**。这是把一个问题消灭掉，而不是给它写一条规则。

## 后果

- **`skill_grant.role` 的词表换了，迁移要回填**：`viewer → browse`、`editor → write`，就地改 CHECK 约束（迁移 `V18`）。**不是加值**——`viewer` / `editor` 这两个词从此不再出现在 `skill_grant` 里、那条接口里、以及界面上（`namespace_member.role` 是另一张表，本版不动它）。
- **`GrantRole` 不再是一对 String 常量，它要有序**。今天那个类刻意不是 enum，理由是「值与列同一套词表、原样送到浏览器，enum 只会买来一对映射方法」（`GrantRole.java:5-9`）——**那条理由被有序这一条要求推翻了**：现在需要 `atLeast(...)` 这个比较，而 String 常量给不出它。
- **三个能力边界同时移动，每一条都要有对应的测试**：`editor` 迁到 `write`（**不能**上线；上线从此归 `maintain`）、`admin` **能**授权、`admin` **不能**删除。前两条是**放宽**，第三条是**收紧**——收紧的那一条是新加的边界，最容易在实现里被漏掉。
- **控制台的协作者页要重做**：今天产品里那块面板只认两个角色，而设计件已经有它该长成的样子（可改档的档位菜单、只列比公开档高的档位**外加该行自己当前那一档**——公开之前授出去的「浏览」要留得住；名单里只列单独授给个人的那些，公开盖住的行不再加注）。
- **CLI 的 `skill share --role` 换词表**，并且旧的 `viewer` / `editor` 要被**明确拒绝**而不是静默当作某个新档——一个说「已授权」而实际授了别的档的命令，比报错坏得多。
- **一处要连带回答**：0034 §决定 5 里「`editor` 能丢弃自己提交的草稿」与梯子「`维护` 能丢弃别人的草稿」是两句话，实现里必须合成一句（`维护` ∨（`写入` ∧ 提交人是我）），否则那个能力会在迁移中丢掉。
