# 0161 · 导入 skill 的来源状态在草稿创建时定稿

- **状态**：已采纳（取代 v49 技术设计 §刷新时机的「发布后刷新」与「每日全刷」）
- **日期**：2026-11-07
- **所属版本**：[`v50-open-source-sync`](../versions/v50-open-source-sync/README.md)
- **取代**：[`v49` 技术设计 §刷新时机](../versions/v49-public-signals/technical-design.md#刷新时机)里「发布后同步尝试刷新一次」与「每天一次扫线上版本刷新」两条时机
- **依赖**：[ADR 0147](0147-a-source-is-a-typed-connection-plus-signals.md)（来源是连接 + 信号）、[ADR 0157](0157-sync-is-a-source-neutral-pipeline.md)（来源无关底座）

## 背景

v49 定的刷新时机是三条：发布事务提交后同步尝试刷新一次（3 秒超时，失败写 `error`，不阻塞发布）；每天一次扫线上版本的来源快照逐个刷新；页面只读快照。当时的场景是官方手工发布、数量很少，每次发布顺手把来源刷新一次是合理的。

2026-11-07 首次按名单批量导入，53 个 skill 全是同步进来的，撞到两件事：

- **每条发布 2.2–2.9 秒**，几乎全花在发布后那次刷新上。刷新一次要 3–5 次 GitHub 往返（仓库元数据、目录最近 commit、许可文件逐级向上找），而同一仓库的 38 个 skill 各刷一遍，取的是同样的仓库元数据。
- **53 条批量发布在 30 秒被容器截断**：流式接口走 Spring 异步请求，默认 30 秒超时；界面显示 12 条已上线、41 条没有结果，库里实际 13 条（记在 [`TODO.md`](../current/TODO.md) 第 14 条）。

更根本的是对同步进来的版本，发布时刷新是重复劳动：几分钟前同步刚按同一个 commit 取过内容、落定了许可，只差 stars / forks / 最近提交这类慢变信号；而这些数每天都在变，发布那一刻是不是最新并不重要。

2026-11-07 产品负责人定：**skill 的所有状态在同步时就定下来，后续发布、回滚都不更新**；每日只为发现新版本、建草稿（发布仍由人做）——这件事本来就是 `SyncJob` 的职责，`SourceRefreshJob` 只负责补快照的缺口；stars / forks / 最近提交不做每日刷新，以后改成每周（[`TODO.md`](../current/TODO.md) 第 15 条）；每日只处理有变更的 skill，判断粒度是 **skill 目录**而不是仓库——仓库别处有 commit 而某个 skill 目录没变，就不能动它、也不能给它建草稿。

可选的做法有四条：A 保持 v49（发布后同步刷新 + 每日全刷）；B 同步时定稿、发布不刷新、每日只补缺口；C 发布后改成异步刷新；D 不再保存来源信号。

## 决定

1. **同步建草稿时把来源状态写全**：快照里有 revision 与 stars / forks / 最近提交，取得到时 `status=ok`，`written_by_sync` 为真；许可按现有路径（`skill_version_license`）同时落定。日期取上游的值，不取本机时刻。
2. **仓库元数据按 `(kind, locator)` 每轮最多取一次**：条目通过全部闸门后取；同轮全部条目都因 revision 未变而跳过时一次也不取（replay 或写入失败的条目可能先取一次，上限不变）。同一仓库的 N 个 skill 共用这一次结果；取不到时快照留 `pending`，草稿照建。
3. **发布与回滚不读来源平台**（对所有版本，不只同步导入的）：删除发布用例里的 `refreshSource`；快照在发布前后逐字段相同。发布仍按既有设计在内容首次上线时同步算一次检索向量（`EmbeddingIndex`，同一内容已有向量时跳过），那与来源无关。
4. **每日任务只补缺口**：只处理**当前线上版本**里 `pending` / `error` / `stale` 的快照，不再按「超过一天」刷新 `ok` 的快照，也不再重试 `declared-only` / `missing` 许可。手工上传（非同步）的 skill 仍由它补信号；补缺口时只写数字，不改同步版本的许可。
5. **变更判断按 skill 目录**：用该目录的最近 commit 作为 revision；同一个 commit 再同步不做任何写入，仓库别处的 commit 不触发该 skill。
6. **每周刷新是后续方向**，频率、失败重试与陈旧展示口径不在本次决定内。

## 理由

- **A 被否**：对同步版本是重复劳动；按 skill 逐条刷新会把同一仓库的元数据取 N 遍；把第三方可用性放进发布路径，3 秒超时只是缓兵，慢的时候发布仍然慢。
- **C 被否**：产品负责人明确发布不做刷新；异步刷新仍要一条额外的任务与状态，只是把网络请求挪到发布后不久，问题没消。
- **D 被否**：来源信号是 v49 已交付的对外能力（信息页与 CLI 显示 stars、最近提交），同步导入的 skill 更需要它；删掉是退步。
- **周刷新没有并进来**：它要单独定 cron、失败重试与「多久算陈旧」的展示口径，且不阻塞本次导入；方向已记待办。
- **定稿让发布不再依赖来源平台**：不再受 GitHub 的可用性与限流影响；剩下的耗时是本地写入与（内容首次上线时的）一次向量计算。批量发布的耗时随之从每条约 2.5 秒降到约 0.2 秒（估算，未实测），53 条没有再撞 30 秒；更大的批量仍会，按第 14 条单独修。

## 后果

- 同步导入的 skill，stars / forks / 最近提交定格在草稿创建那一刻；草稿放几天才发布，展示的仍是那时的数。信息页与 CLI 不显示快照时间，用户看不出数有多旧——周任务落地时要一并定展示口径。
- 手工上传的 skill 没有同步时刻，信号由每日任务在它发布后补，最多晚约一个周期。
- 信号读取失败的同步草稿，快照停在 `pending` 直到它被发布：每日任务只扫当前线上版本，草稿期间不会补。这是「每日只补线上版本」的直接后果。
- v49 技术设计 §刷新时机 的三处承诺不再成立：「发布后刷新」（所有版本都删了，不只同步导入的）、「每天一次全量刷新」（改为只补 `pending` / `error` / `stale`）、「`declared-only` / `missing` 每日重试」（许可在草稿阶段或首次刷新时落定，不再随 HEAD 变化）。「页面只读快照」与信号契约不变。v49 的正文不改，以本 ADR 为准。
- 发布用例不再依赖来源适配器；测试要能断言发布与回滚过程中适配器调用次数为 0。
- 同一 skill 目录的 revision 没变时，每日读取只花 1 次 commits 请求，不下载、不写草稿。
