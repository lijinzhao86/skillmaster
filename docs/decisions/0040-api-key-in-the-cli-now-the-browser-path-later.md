# ADR 0040 · CLI 现在收 key；「点一下」那条路留到后续，而且它铸的是 key

- **状态**：已采纳
- **日期**：2026-10-15
- **依赖**：[ADR 0038](0038-default-credential-is-an-api-key.md)（第一方的默认凭据是用户自己签发的 API key）、[ADR 0039](0039-api-key-defaults-and-their-edges.md)（缺省值：90 天、写蕴含读、配置只约束新建）、[ADR 0025](0025-cli-credential-storage.md)（凭据存在哪：钥匙串优先、0600 文件兜底）、[ADR 0028](0028-cli-uses-a-fixed-loopback-port.md)（loopback 固定端口——将来那条浏览器路要用它）
- **不改**：0038 的其余部分（为什么换形态、为什么是 API key、`logout` 只删本机、不做组织 key）一条不动

## 背景

用这个 CLI 的有两类人，而他们对「怎么把凭据交出去」的耐心不一样：

- **坐在自己电脑前的**：有浏览器。对他们，「点一下授权」是**一个概念**；而「去控制台签一把 key、复制、粘贴、记着它 90 天后过期」是四五个概念。**key 是更进阶的操作**，这一点不该被技术上的整齐掩盖。
- **在没有浏览器的机器上的**：服务器、容器、CI、别人机器上跑的 agent。他们**只能**粘贴（或设环境变量），没有第二条路。

v1 的 CLI 只有第一条路（浏览器 loopback PKCE），而 0038 之后第一方的凭据形态换成了 key——于是「本版 CLI 收哪种凭据、那条浏览器路怎么办」需要一条决定。同时要回答的一个问题是：**签发（造一把新的 key）要不要也搬进 CLI。**

## 决定

1. **本版签发只有一个入口：控制台。** 能造凭据的东西必须是**浏览器会话**——CLI 侧没有任何路径能铸出一把 key。
2. **本版 CLI 的凭据来源只有两个**：`login --with-key`（从 **stdin** 读）与环境变量 `SKILLMASTER_API_KEY`（优先于本机存储，且什么都不落盘）。不收命令行参数。
3. **「点一下」那条浏览器路推迟到后续版本**，但**它是要做的**（不是可选项）。它将来落地时**以「给这台机器铸一把 key」的形式**出现：`login`（不带参数）打开浏览器 → 在页面上点一下（名字 / 权限 / 有效期，默认值与控制台一致）→ 经 loopback 用**一次性码**换回**一把 key** → CLI 存下。**不是**换一张 OAuth 令牌。
4. **CLI 永远不签发、不列出、不撤销、不续期 key**——四件事都在控制台。
5. 本版 `login`（不带 `--with-key`）**保持 v1 的浏览器 OAuth 登录原样**：它是过渡形态，将来被第 3 条替换。

## 理由

- **为什么签发不搬进 CLI。** 一个能造凭据的东西，必须能证明「是本人现在的这个动作」，而那正是会话。用 key 来造 key 有两个真问题：**① 泄漏之后撤不干净**——攻击者用你泄漏的那把造出新的，你撤销原 key 只杀掉了原 key，新造的那把照样活着；要堵住就得引入**家族/血缘**（撤销一把连带撤掉它造出来的），那是另一块机制，不是顺手能加的。**② 会话天然带着另外三件我们已经在做的事**：CSRF 保护（写操作）、审计（谁在什么时候签了什么）、以及「签出来的东西出现在你能看见的那一屏上」。
- **为什么那条路将来铸的是 key，而不是 OAuth 令牌。** 铸 key 的话，凭据**仍然只有一种**：报错只有一套说法、控制台那一屏看得见、能单独撤销、能换到别的机器上。换成令牌就会引入第二种凭据，而它恰好是**看不见的那一种**——账号页的注释自己写着「the authorizations a CLI holds cannot be listed or revoked individually in v1」，而且那是**故意**不放入口的（免得开一扇通向空处的门）。
- **为什么推迟。** 先把一条链路做透：签发 → 使用 → 过期 → 报错 → 换一把。两条一起做，等于两条都只做一半——而「点一下」那条路要做的东西并不小（loopback 一次性码、一个签发界面、CLI 侧的一套新流程）。
- **为什么它仍然是必要的**（写在这里，是因为推迟很容易被读成「不重要」）：不熟悉技术的用户不该被迫理解 key、权限、有效期、复制粘贴这一套。**默认应该是点一下**；key 是给没有浏览器的机器的那条路。

## 后果

- **本版那批用户只能粘 key。** 这是这条决定真实的价钱：他们要懂 key 是什么、选权限、看着它 90 天到期、再回控制台换一把。控制台那一屏有「两周内到期」的提醒，CLI 的报错也会直接把续期地址给出来——但概念的数量摆在那里，不因为界面友好就少。
- **本版仍然有两种凭据并存**（`login` 不带参数那条路仍走 OAuth 令牌，见决定 5）。「两种凭据、两套说法」的复杂度本版**没有**去掉，只是不再往里加东西。
- **将来那条路要做两件具体的事**：① CLI 侧——loopback + 一次性码 + 存（复用 ADR 0028 的固定端口与既有的回调实现）；② 网页/服务端侧——一个「给这台机器签一把」的界面（名字 / 权限 / 有效期默认值与控制台一致）。**签出来的就是一把普通 key**，进同一个列表、用同一套撤销与续期——**所以那条路将来不会产生「看不见的授权」**，它产出的是 key，不是又一种令牌（第三方那半见 [ADR 0041](0041-third-parties-reach-us-through-the-cli.md)）。
- **过渡期的 `login` 换来的授权，用户看不见、也撤不掉。** 这个缺口本身不是新的（v1 就没有那个入口，账号页的注释写着「a door that opens onto nothing」，是**故意**不放入口），但本版让它更值得说清：`logout` 改成只删本机之后，一条 `login` 留在服务端的授权**没有任何入口能单独撤销**——能连带撤掉它的只有重置密码那一类动作（它会撤掉该账号的全部授权）。**走 `--with-key` 的人不受影响**：key 在控制台看得见、能单把撤销，这也是为什么那条路是本版要推荐的路。**等「点一下铸一把 key」落地，这个缺口随之消失**——那时 `login` 产出的是 key，而 key 有它自己那一屏。
- **本版不提供任何「用 key 换一把新 key」的路径**：`/web/keys` 的四个端点都在会话面（浏览器），API 面不铸凭据。这是决定 1 在接口上的样子，也是将来要加「key 造 key」时**必须先加家族/血缘**的原因。
