# 0137 · `edit` 接 stdin 与批量 JSON，一批只写一次

- **状态**：已采纳
- **日期**：2026-11-04
- **依赖**：[v44 PRD](../versions/v44-cli-read-write-contract/prd.md)、[ADR 0064](0064-a-draft-may-change-a-published-version-may-not.md)（草稿可改，一次写只落一版）

## 背景

`skmr skill edit` 只有两种输入：命令行内联的 `--old` / `--new`，或本地文件 `--old-file` / `--new-file`。改多行中文时命令行塞不下，只能先写临时文件；一次改三处要跑三次命令、写六个临时文件。2026-11-04 改 `lijinzhao/code-dev-sop` 用了 14 次 `edit`，每次都是「写 old 文件 + 写 new 文件 + 跑命令」。

CLI 的 `edit` 已经是**客户端取回、应用、整份写回**（`editRemote`：读文件与 ETag → `change(content)` → `AuthorWriteFile` 带 If-Match），不是服务端按子串匹配。因此「一批改动只落一版」不需要服务端新接口，只要一次读、在内存里连做几处替换、一次写。

## 决定

1. **stdin 两端**：`--old-file -` / `--new-file -` 表示从标准输入读。两端都写 `-` 时拒绝——同一条 stdin 不能同时装两份文本。
2. **`--stdin-json` 单条**：一次读 `{"old": "...", "new": "...", "replace_all": false, "regex": false}`；键名用 JSON，不用自定义分隔符——分隔符可能出现在正文里，JSON 有标准转义、格式错能当场拒绝。
3. **`{"edits": [...]}` 批量**：数组里每项同上面的形状；CLI 读一次文件、在内存里按顺序应用，全部匹配成功才写一次（一个版本）；任一处失败则整批不落盘，并指出第几处、失败原因。写回时带读到的 If-Match，期间别人改过就是 409，不会静默覆盖。
4. **JSON 与 flag 互斥**：`--stdin-json` 不能与 `--old` / `--new` / `--old-file` / `--new-file` / `--replace-all` / `--regex` 同给；同时出现按用法错误拒绝。
5. **不改服务端**：`edit` 的匹配、行尾风格、归一与错误诊断继续由 CLI 承担；服务端只接收整份写回。

## 理由

**为什么用 JSON 而不是分隔符。** 要替换的文本里出现分隔符是常态；自定义分隔符要么要求转义（等于发明一门小语言），要么悄悄截断。JSON 有标准转义与现成解析器，格式错还能给出位置。

**为什么批量在客户端做。** 服务端没有「一次请求多处替换」的接口，而 `editRemote` 已经是「取回 → 变换 → 整份写回」。在客户端连做几处替换再写一次，天然满足「一次请求落一个版本」与「任一处失败整批不落盘」，也不用把匹配规则复制到服务端。

**为什么两端不能都读 stdin。** 两次读取同一份流没有可解释的结果：第一份读到 EOF，第二份是空的。显式拒绝，让调用方选择 `--stdin-json`。

## 后果

- **一条命令只能有一个标准输入来源**：要替换的文本和替换成的文本不能同时走 stdin；两端都长时用 `--stdin-json`。
- **批量失败不产生中间版本**：`version list` 不会多出一份只改了一半的草稿；错误带索引，调用方知道从哪一处修。
- **批量大小受文件大小与内存限制**：与单次 `edit` 相同，没有新增上限；超大文件仍走 `write`。
- **`--regex` 是逐项属性**：批量里可以让一项按正则、另一项按字面，不引入全局开关。
