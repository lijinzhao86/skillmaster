# 0183 · 删除释放名字，数据仍然保留

## 背景

今天的删除是软删：写 `skill.deleted_at`，行、版本、字节与授权全部留着；恢复就是把这一列清掉。但名字被 `UNIQUE (namespace_id, name)` 永久占住——已删的行还在表里，所以同名的新 skill 建不出来，创建与提交会得到 409 `skill_deleted`。控制台与 CLI 的文案都写着「名称不会被释放」。

[0050](0050-deleting-a-skill-can-be-undone.md) 当年给了三条理由：恢复需要一个稳定的名字；地址一旦发出去就有引用；被删的名字若可重新注册，会变成一条钓鱼路。

2026-11-11 讨论时出现了三条新事实：

1. **名字在所有者自己的个人命名空间下。** 今天只有所有者能往 `alice/` 里建 skill，别人无法抢注；第三条理由在当前模型下没有落点。等「命名空间成员可写」那条待办（[`docs/current/TODO.md`](../current/TODO.md)）落地，能建的也只是成员，不是陌生人——到那时再重新评估。
2. **用户不应该被迫理解软删与硬删。** 他要的是「删掉，然后用同一个名字重新开始」；今天这个最自然的动作被一个他看不见的墓碑挡住。
3. **参照产品已经这么做了。** GitLab 删除时把路径改成 `原名-deletion_scheduled-<id>`，原名字当场释放；GitHub 删除后名字立即释放，90 天内可恢复，**同名已被新建就不能恢复**。两者都保留数据，也都没有把名字锁死（2026-11-11 在两家产品的删除流程实测）。

摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 保持 [0050](0050-deleting-a-skill-can-be-undone.md)：软删、可恢复、名字永久占用 | 防抢注的理由在个人命名空间下不成立；名字永久不可用，等于把删除变成陷阱 |
| b | 定时释放：删除 N 天后自动清理并释放名字 | 名字的生命周期被绑在一个看不见的计时器上，静默且不可解释；还要引入真删 |
| c | **删除即释放名字，恢复冲突时自动改名** | 采纳 |
| d | 删除即释放名字，但同名已被新建时拒绝恢复 | 旧内容与版本从此拿不回来；恢复的价值被砍掉 |

## 决定

1. **删除立即释放名字。** 删除后可以马上用同一个名字创建新 skill；创建与提交不再返回 `skill_deleted`。用户侧不区分软删与硬删。
2. **数据仍然软删保留。** 不真删行、版本、字节或授权；「已删除」列表里仍能看到并恢复。
3. **恢复冲突时自动改名。** 原名字已经被新 skill 占用时，恢复仍然成功，但地址变成 `原名-restored-<id>`（GitLab 式）；版本、授权与可见性原样回来，回执写明新地址。
4. **恢复按条目，不按可能已属他人的名字。** 入口仍在「已删除」列表；同名新 skill 存在时，列表里的旧条目恢复成带后缀的地址，而不是拒绝。
5. **公开 skill 删除后的地址语义由 [0184](0184-taking-a-public-skill-down-is-a-service-lifecycle.md) 定**：公开且曾发布返回 410 + 原因；公开但从未发布、以及私有，保持 404。

## 理由

**为什么不再锁住名字。** 防抢注的前提是「别人能注册它」；在个人命名空间下这个前提不成立。剩下的真实代价是「旧引用会静默指向新内容」——但那是所有者自己决定用同一个名字放不同的东西，参照产品都接受这个代价；真正需要稳定的人有版本钉住与 `copy` 两条路。

**为什么不做定时释放。** 它把「什么时候能再用这个名字」交给一个计时器，用户既看不见也解释不了；而且它要求真删，推翻了 [0050](0050-deleting-a-skill-can-be-undone.md) 决定 1「一条都不改」。

**为什么恢复冲突要自动改名，而不是拒绝。** 拒绝等于说「你删过的东西从此拿不回来」，而数据明明还在；自动改名保留了数据可达性，也是 GitLab 已经验证过的形状。代价是地址不漂亮——那是所有者自己先占用了原名，不是系统强加的。

**被否掉的：** 保持永久占用（防抢注已无落点）；定时释放（静默、要真删）；拒绝恢复（丢失可达性）；真删（推翻软删，且用户明确要求系统层保留数据）。

## 后果

- **唯一约束要改。** 实现二选一，写进技术设计：partial unique index（`WHERE deleted_at IS NULL`，列继续显示原名，恢复按条目 id）或删除时改名（GitLab 式，另存展示名）。
- **`skill_deleted` 退役。** [0071](0071-a-deleted-name-answers-with-its-own-code.md) 的正文保留，代码、控制台文案、CLI 错误表与测试里对它的引用要清掉；`skills list --show deleted`、`skill restore` 的语义跟着改。
- **已删除列表可能出现多条同名条目。** 恢复冲突是正常结果，不是错误；恢复按条目 id 而不是按名字。
- **旧地址可能指向新内容。** 同一所有者用旧名字建了新 skill 时，旧引用会静默指向新东西；缓解手段是版本钉住与 `copy`，不额外加拦截。
- **命名空间成员可写落地时要重看。** 那时「谁能往这个命名空间里建名字」变成多人，防抢注的论证需要重新检查。
