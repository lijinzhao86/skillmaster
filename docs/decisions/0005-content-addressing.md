# ADR 0005 · 内容寻址与幂等发布

- **状态**：部分被取代（§后果里「上传时不得改写内容」这一句由 [0117](0117-content-is-canonicalized-at-the-door.md) 取代）
- **日期**：2026-09-26
- **依赖**：[ADR 0004](0004-opaque-id-primary-key.md)

## 背景

系统必须能回答"这个 skill 的内容变了吗"。更新检测、缓存、完整性校验、事后追溯都依赖它。而且标准侧（Agent Skills / MCP Skills 扩展）已经把内容摘要作为一等公民：扩展要求文件清单里每个文件带 SHA-256 与字节大小，并要求宿主逐文件校验。

## 决定

- **每个版本对其文件集合计算一个确定性 digest**；版本不可变（`skill` 是身份，`skill_version` 是不可变快照）。
- **文件字节按 sha256 内容寻址**存入 blob store；`version_file` 只存引用。
- **`UNIQUE(skill_id, digest)` 保证幂等发布**：同样内容重复发布不产生新版本。
- **digest 算法写死**：对按 `relpath` 字典序排序的文件，逐个拼入 `relpath + "\0" + blob_sha256 + "\0"`，再整体取 sha256。

## 理由

- **不依赖文件系统遍历顺序、不依赖时间戳**——同一份内容在任何时刻、任何机器上都得到同一个 digest。这是可复现的前提。
- **幂等由唯一约束直接实现**，不需要额外代码或"先查再写"的竞态-prone 逻辑。
- **内容寻址天然去重**：不同 skill、不同版本共享同一份文件（共享的 `references/`、重复模板）时只存一份。
- **与标准的完整性语义一致**：sha256 + size 是可核对的。将来若上 MCP 适配器，扩展要求"approval 绑定完整的 URI+digest 集合、文件增删改即吊销"——我们的 digest 正好满足，不需要自创版本锁定机制。

## 后果

- **manifest 的顺序必须显式排序。** 依赖数据库返回顺序会让 digest 不稳定，客户端就会**永远认为有更新**、反复重拉。这是最容易在实现时无意破坏的一条，必须写成测试。
- **blob 只增不删**（可能被其他版本引用），需要后台 GC 按引用计数回收；删除版本不等于删除 blob。
- **上传时不得改写内容。** 托管要保真——不做格式化、不重写 frontmatter、不做"顺手"的换行符或编码规范化，否则 digest 会变、且内容与作者上传的不一致。
- 发布新版本即改变 digest 集合，客户端据此重新取得信任（重新批准）。
