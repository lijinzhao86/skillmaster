# 0070 · 新建 skill 与它的第一份草稿是一个动作

- **状态**：已采纳
- **日期**：2026-10-21
- **依赖**：[0005](0005-content-addressing.md)、[0031](0031-submitting-and-publishing-are-two-actions.md)、[0050](0050-deleting-a-skill-can-be-undone.md)（删除留名、恢复在网页）、[0055](0055-drafts-have-a-required-name.md)（草稿有必填名称）

## 背景

给网页加一个不经过上传的入口（「新建 skill › 在线编辑」）时，有两种落法：

1. **两步**：先建 `skill` 行，再进编辑页，等用户第一次改文件时落第一份草稿（v8 的「第一次内容改动才落库」）。
2. **一步**：提交表单的那一刻，把 `skill` 行与第一份草稿（含一份根 `SKILL.md`）落在同一个事务里。

两步会留下一个中间态：一个没有任何版本的 skill。它出现在列表里、占着名字、地址可解析却没有内容，用户关掉标签页就永远留在那里；删除与恢复都要为一个「从没写过内容」的空壳服务。而且 v6 之后一个版本必须有内容，空壳恰好是内容模型里不存在的东西。

## 决定

1. **新建 skill 是一个事务**：`skill` 行 + 第一份草稿 + 它的根 `SKILL.md`，要么全落、要么全不落。
2. **第一份草稿有内容**：一份最小的 `SKILL.md`，frontmatter 的 `name` / `description` 就是表单填的两个值，正文是 `# <名字>`；它走与上传同一条 `SkillDocument.parse` 与 `Uploads.store`，不另写一套。
3. **名字冲突是拒绝，不是复用**：同名 live skill → 409 `skill_already_exists`，并给「查看 `<名字>`」；同名已删除 skill → 409 `skill_deleted`，并给「去恢复」。创建不能用 `findOrCreate`——那是「有就返回」的提交语义。
4. **锁序与提交逐字相同**：blob 在 GC 锁之外存，`skill` 行与草稿在 `underExclusiveWrite` 之内写；GC 表锁先于 `skill` 行锁。短码碰撞由控制器上的 `DraftRecorder` 换事务重试，用例内部不重试。
5. **创建只发生在调用者自己的个人命名空间**，因此不泄露「别人有没有这个名字」。

## 理由

**为什么不留空壳。** 「一个 skill 至少有一版」是内容模型的底线：列表要显示它、版本页要落它、分享与可见性都以「有内容」为前提。两步法把这条底线交给用户去完成，失败率就是用户关掉标签页的概率。

**为什么第一份草稿真的带内容。** 编辑页打开的就是这份 `SKILL.md`，不是一张空表；「描述必填」也才有地方落——描述是 `SKILL.md` 的 frontmatter，不是 `skill` 行的独立字段。

**为什么冲突要拒绝并给链接。** 用户想新建的名字已经存在时，正确的下一步是去那一版继续，而不是悄悄在它下面加一版（那是导入的语义）。把两个名字（地址名与内容名）摆在一起的那类错误也归导入管，创建这里只有「有」与「已删除」两种。

## 后果

- 一个新用例 `CreateSkillUseCase`，与 `SubmitSkillUseCase` 共享 `Uploads` / `SkillVersionService.submit` / 审计，不新增表、不新增列。
- M12 多一个 create-only 入口（`ON CONFLICT DO NOTHING` 后读含已删除的行）：`findOrCreate` 的「有就返回」语义与创建相反，不能复用。
- 「在线编辑」与「导入本地 skill」成为同一条产品承诺的两种来源：一次动作产出一个有内容的 skill。
- 事务失败或短码碰撞时，三张表都新增 0 行——这条由测试钉住。
