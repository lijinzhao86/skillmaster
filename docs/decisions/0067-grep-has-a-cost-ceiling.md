# 0067 · grep 的执行成本必须有硬上界

- **状态**：已采纳
- **日期**：2026-10-20
- **依赖**：[0062](0062-grep-is-a-scoped-scan-not-an-index.md)（grep 是有界扫描）、[0066](0066-grep-uses-a-linear-time-regex-engine.md)（用线性时间引擎）
- **这一条修正 [0066](0066-grep-uses-a-linear-time-regex-engine.md) 的决定 1 与 6**：引擎选择不变，但「线性」不等于「成本有界」，`-F` 也不再经过引擎。

## 背景

[0066](0066-grep-uses-a-linear-time-regex-engine.md) 把正则从 `java.util.regex` 换成 RE2/J，理由是前者的指数回溯能卡死一个请求。第三轮审计实测发现 RE2 的线性是**在输入长度上**，常数却随自动机规模增长：

| 请求（16 MiB 单行全 `a`） | 实测 |
|---|---|
| `a{999}b`（7 个字符） | 67 秒 |
| `-F -i`，字面量 1000 字符 | 75 秒 |
| `((a{100}){100}){100}`（20 万字符的行） | 108 秒 |
| `(((a{100}){100}){100}){100}`（27 个字符，**编译期**） | 6 GB 堆上 4.7 秒后 `OutOfMemoryError` |
| `a+b` | 0.3 秒 |

原因各不相同：`a{999}` 让自动机多出近千个状态；`-F -i` 把字面量交给引擎后同样付出自动机成本（0066 的决定 6 以为引号字面量是「一遍线性扫描」，实测不是）；嵌套计数重复把状态数乘起来。pattern 长度上限 1000 管不住它们——`a{999}b` 只有 7 个字符。

最后一行更糟：RE2 在**编译**期展开计数重复，所以嵌套是乘积。`compile` 又把这一步放在 `accessFor` 与 `openDraftForRead` **之前**——一个语法合法的行 id 就够触发，skill 与版本都不必存在，`grep` 还是 GET。`OutOfMemoryError` 是 `Error`，异常处理器接不住，影响的是整个进程。

`grep` 是 `@Transactional(readOnly = true)`，卡住的线程还占着一条连接；默认连接池 10，十个这样的请求就能让全站等一分钟。任何有 `write` 档的账号都能触发。这与 0066 要解决的是同一类事故，只是入口换了。

## 决定

1. **`-F` 的两种大小写模式都改用 KMP 字面量搜索**，不再经过 RE2。线性、常数小，1000 字符的字面量在 16 MiB 上也是毫秒级；大小写折叠用 Unicode 的简单小写映射（`Character.toLowerCase(int)`）。
2. **正则里任何 `{n}` / `{n,m}` 的计数超过 100，或者「所有计数相乘 × pattern 长度」超过 1,000,000**，在解析请求时直接拒绝：400 `invalid_request`，detail `pattern=too_expensive`。后者是编译期展开的上界（RE2 按乘积展开嵌套计数，被重复的子表达式本身也有长度）；两侧并排的计数在这个上界里也会相乘，所以只会多拒、不会漏拒；**每个计数至少按 1 计**——`{0}` 不会把乘积归零，因为 RE2 仍会展开它外层的计数（实测四条 `{100}` 中间夹一个 `{0}`，照样 OOM）。静态扫描跳过转义、字符类与 `\Q…\E`，只认真正的计数重复。
3. **一次请求有一个 1 秒的匹配截止时间，作用范围是整个请求，从扫描开始计时。** 交给 RE2 的 `CharSequence` 包装在每 1024 次 `charAt` 时看一次时钟；同一份预算里，行循环每 64 行也在行边界看一次。前者管一条超长行，后者管大量短行（短行到不了 1024 次读取，字面量搜索更是一次都不经过）。超时抛异常、请求以同一个 400 `too_expensive` 结束。它覆盖静态规则看不见的放大（嵌套计数、多个计数相加）。权限解析与清单读取不算在预算里——它们不是匹配，把慢读算进去会让第一条字符就假报 `too_expensive`。
4. **`too_expensive` 与 `bad_pattern` / `too_long` 是三个不同答案**：写法合法、只是太贵，调用方该收窄它，而不是修语法。
5. **CLI 把 `too_expensive` 翻成一句可执行的提示**：收小 `{n}`、改用 `-F`、或用 `cat <地址> <文件> | grep` 在本机过滤。

## 理由

**为什么字面量不用引擎。** `-F` 的承诺是「按字面量找」，没有自动机可言；用 KMP 是这条承诺最短的实现，也是唯一能在常数上不被 `{n}` 或长字面量放大的实现。代价是大小写折叠的少数特例与 RE2 不同（见后果），而需要精确 RE2 折叠的人可以用 `-F` 之外的正则写法。

**为什么保留 RE2 而不是给正则也写一个引擎。** 正则的语义面比字面量大得多；0066 选 RE2 是为了避开不可中断的回溯，这一点仍然成立。剩下的问题是成本常数，用「拒绝放大写法 + 截止时间」解决，不换引擎。

**为什么静态上限是乘积乘长度。** 危险发生在编译期，而编译发生在权限门之前：四条计数各 100 的 27 个字符，展开是一亿个节点，堆先倒下，`OutOfMemoryError` 不是 `Exception`。只限制单个计数看不见乘积；只乘计数又漏掉「被重复的子表达式有多长」——`((a×955){100}){100}` 乘积只有 10⁴，展开却是一千万节点，在 512 MB 堆上照样 OOM。`乘积 × 长度` 是展开量的上界，可以在 `compile` 之前用一次扫描算出来。它会把并排的计数也乘起来（`a{100}b{100}c{100}` 被拒，尽管自动机并不大），这是有意的保守——多拒一个罕见写法，换掉一个进程级事故。

**为什么还要有截止时间。** 静态上界管的是编译；乘积 10⁴ 以内的自动机在 16 MiB 上仍可能扫上几秒。要让「最坏情况有界」成立，就必须还有一个运行时兜底，而不是不断增加静态规则。

**为什么截止时间是 1 秒。** 实测一次 16 MiB 的普通扫描约 0.3–0.4 秒；1 秒给正常请求留了余量，同时把单个请求占住连接的时间压到一秒量级。更小会误伤大草稿的合法搜索，更大则连接池仍可能被持续占满。

**为什么拒绝而不是降级。** 静默改用别的语义（截断行、跳过文件）会让 grep 的答案在没人知道的地方变错；`content_already_exists` 等 v7 拒绝都遵循同一条：说清楚，由人决定下一步。

## 后果

- **`-F -i` 的大小写折叠与 RE2 不完全相同**：RE2 把希腊末尾 sigma（`ς`）与 `σ` 视为相同、把 `İ` 与 `i` 视为不同；小写映射恰好相反。`-F -i` 按后者。帮助里写「大小写折叠是 Unicode 小写映射」，需要 RE2 折叠时用正则（不带 `-F`）。
- **少数合法但昂贵的正则得到 400 `too_expensive`**：调用方改用 `-F`、收窄 pattern，或 `cat | grep`。并排的多个计数会按乘积计算，所以 `a{100}b{100}c{100}` 也会被拒；这是有意的保守。
- **`\Q…\E` 里的 `{n}` 不算重复**：静态扫描跳过引号文本，`\Q{999}\E` 照常搜索（0066 的实现曾把它误判成计数重复）。
- **一个请求最长占连接约 1 秒（加一次行边界检查的间距）**：并发压力仍有上限，但不是无限期；若要更严格，下一步是对 grep 单独限流，而不是继续压低截止时间。
- **ADR 0066 的决定 1 与 6 不再描述实现**：文件头标注被本条修正的部分；0066 的决定 2–5（RE2 的语义边界、pattern 长度上限、逐行推进、帮助口径）仍有效。
