# ADR 0090 · 批量发布：一次确认放行多次，但确认单必须逐条列出

- **状态**：已采纳
- **日期**：2026-10-25
- **依赖**：[ADR 0031](0031-submitting-and-publishing-are-two-actions.md)（提交与发布是两个动作，发布只在浏览器面）、[ADR 0056](0056-dangerous-actions-are-confirmed-in-a-modal.md)（改变用户看到的东西之前先确认）、[ADR 0081](0081-every-console-operation-has-a-cli-command.md)（控制台操作与 CLI 对应）
- **修订**：§决定 4 的「版本号取该草稿自己的名字」已被 [ADR 0091](0091-release-type-decides-the-version-number.md) 取代——草稿只声明**版本类型**，号在发布时按类型与基线算出来；草稿自己的那一行名字仍叫 `draft_name`，它不再是版本号（[ADR 0055](0055-drafts-have-a-required-name.md)）。**同一条取代表面上也覆盖 §理由里那句**「那个号在提交那一刻已经由人定过」——0091 之后提交时只有类型，没有号。
- **勘误（2026-10-25）**：§背景引 ADR 0031 的原话是「能跑 CLI 的人不该因此获得**上线**的权力」，正文写成「发布」——0031 的正文用的是「上线」，以它为准（界面也不再出现「发布」，见 [voice-spec](../../design/voice-spec.md) §三）。
- **补注（2026-10-25）**：§决定 7 的「`maintain` 以上」**包括 `owner`**——自己建的 skill 在服务端写作 `owner`，按字面读会把用户自己的 skill 全筛掉（v18 的三份文档写的是 `owner` / `maintain` / `admin`）

## 背景

[ADR 0031](0031-submitting-and-publishing-are-two-actions.md) 把提交与发布拆开，理由是发布要一个「刻意的人工动作」：它改变 agent 能读到什么，所以不能是提交的副作用。它同时把发布限定在浏览器面，并明说「能跑 CLI 的人不该因此获得发布的权力」。

这套规则在一份一份写的时候成立。但它假设了**同一时刻只有少数几份草稿在等**。实际上有三类人同时有多份：

- 刚把本机几十个 skill 搬上平台的人：搬运产生的是几十份草稿，一份都没发布过。
- 一次改了好几个 skill 的人：每个都是一份新草稿，分散在不同的 skill 页里。
- 一批提交完就一直放着的人：它们躺在各自的 skill 页里，没有一个地方能把它们一起摆出来。

对这三类人，逐条发布不是几十次判断，是同一件事重复几十遍——每次确认携带的信息完全一样。

三个选项：

1. **不做批量**，逐条点（现状）。
2. **批量，一次确认放行全部**。
3. **批量，但仍然逐条确认**——省掉导航，几十次确认一次不少。

## 决定

1. **可以多选，一次确认放行所选的全部。**
2. **确认单必须逐条列出「skill 名字 → 将要发布的版本号」**。这是这次决定的可接受性条件，不是排版偏好。
3. **逐条成功或失败**，不全有全无——一条撞名不该让其余几十条陪着失败。
4. **版本号取该草稿自己的名字**（提交时定下的那个），批量里不再逐个询问。
5. **只在控制台**。CLI 不提供批量发布（[ADR 0081](0081-every-console-operation-has-a-cli-command.md) 例外 1，理由沿用 [ADR 0031](0031-submitting-and-publishing-are-two-actions.md)：面的边界决定谁能触发）。
6. **它是一个常设的工作队列，不是某个流程的附属步骤。** 「有哪些草稿在等我发布」本身就是一类日常问题，批量只是在这个队列上多出来的一个动作。
7. **队列只列我够得着发布的 skill**（`maintain` 以上）。`invoke` / `browse` / `write` 的 skill，它的草稿不进队列。

## 理由

- **被否掉的第 1 条**：把同一件事重复几十遍不会提高任何判断质量，只会训练人闭眼点。批量恰恰是因为**那几十次确认里没有任何一次需要不同的信息**才成立。
- **被否掉的第 3 条**：它省掉的是导航，不是确认。每一次确认携带的信息都是同一份（这一版是什么、发布后会怎样），第 2 次到第 40 次不增加任何判断。
- **「逐条列出」是这次决定成立的条件。** ADR 0031 要的不是"多点几下"，是"人知道自己放行了什么"。一张写着几十个名字与版本号的确认单满足这一点；一句「确定要发布选中的 40 个吗？」不满足，它把唯一有信息量的部分藏了起来。
- **逐条而不是全有全无**：这些草稿之间没有任何关系，每条都是独立的 skill。整批回滚会把本来能成功的那几十条挡在一条失败后面，而用户还得再弄一次。
- **版本号不在这里问**：草稿在提交时没有发布版本号（`skill_version.version` 为 `NULL`，提交时给的写在 `draft_name`），发布必须给一个。但那个号在提交那一刻已经由人定过；批量里再问几十遍，是把同一个决定重复几十遍。
- **为什么是常设队列而不是流程的一步**：若把它绑在搬运上，日常那两类人（改了多个 skill、攒了一批）依旧没有入口，而他们要面对的正是同一个问题——分散在几十个 skill 页里的草稿。
- **为什么发不了的不进来**：队列回答的是「哪些事在等**我**做」。一份我这辈子都发不出去的草稿，摆在这里只会让我点开、读完、发现做不了——把这类行留着、在结果里报"权限不足"，是把决定推到最后一刻才说明它不存在。这与「确认单逐条列出」是同一条原则的两面：**列出来的每一行，都得是我真能放行的**。

## 后果

- **ADR 0031 的「刻意的人工动作」从每版一次变成每批一次。** 这是这次决定付出的代价，如实记在这里：一次确认放行 N 次发布，人对单条的注意力被摊薄。可接受性押在确认单逐条列出上；哪天发现那个列表没人看，这条决定要重新审。
- **控制台多一屏**：队列、多选、动作条、列表式确认单、部分失败的呈现。四样都要先进设计稿——尤其「部分失败」不能只用一句「部分失败」带过。
- **服务端多一条批量发布路由**，复用既有的发布用例，只负责循环与汇总；发布规则仍然只有一份。
- **没有 CLI 对应**，按 [ADR 0081](0081-every-console-operation-has-a-cli-command.md) §3 记为高风险例外，写进当版 PRD 的映射表。
