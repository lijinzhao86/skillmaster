# 0116 · 改 skill 走在线，不走本地往返

> **状态**：已采纳（2026-10-30）
> **一处事实以 v32 PRD 为准**：背景里「`skill write` 原样上传」中的命令名，[v32 PRD §用户与场景](../versions/v32-online-editing/prd.md) 记为「走的是 `write` 还是 `submit` 没有留证」；不改正文，以 v32 PRD 为准

## 背景

agent 改一份托管 skill 有两条路：

- **在线**：`skill read` 看、`skill edit` / `skill write` 改，改动直接落在服务端草稿上。
- **本地往返**：`skill download` 取一版到目录，用本机编辑器改完，`skill submit` 交回去。

实测里 agent 明显偏向第二条。原因不是习惯，是两条路的形状不同：在线一次只能改一个文件，而且 `submit` 按内容建**新版本**（幂等只对同内容成立），本地改两轮就会留下两份草稿；本地那条能一次交整包、能 `git diff`、能用 agent 的第一等文件工具。但本地往返也带来了真实事故：agent 把 `skill read` 的行号渲染（`12\t…`）当成原文写回整份 `SKILL.md`，`skill write` 原样上传，服务端只校验 frontmatter 与路径，没有任何一层拦住它。

当时有两个方向：把本地目录扶成一等公民（`checkout` / `commit` 回同一个草稿），或者把在线编辑的闭环补齐。

## 决定

**改 skill 走在线。** 本版的投入全部放在让在线这条路可信、可自查上；`skill submit` 继续只服务「首次导入」（[ADR 0108](0108-importing-local-skills-is-optional.md)），不扩展成草稿更新器。

## 理由

- **草稿身份只有在服务端才成立。** 本地目录是一个无名快照；`download` 是一次性导出（[ADR 0068](0068-export-is-a-one-shot-snapshot.md)），与哪一份草稿无关。要让它回落到同一份草稿，就得在目录里维护「我是哪一版」的第二个真相源——这正是 Anthropic 在 Claude 4 的文本编辑器工具里删掉 `undo_edit` 的理由。
- **在线缺的是反馈，不是提交形态。** Claude Code 的 `Edit` 只回一句话，是因为调用方自己能 `git diff`、宿主还替它盯着文件；CLI 没有这两样，所以它必须自己回显 hunk、自己解释为什么没匹配上。把这三件事补上，在线路的短板就补上了。
- **本地往返的收益抵不过它的代价**：多文件一次交、能跑 `git diff`——这些在 skill 这种小体量文件上不构成优势，而「每轮换一个草稿身份」和「读的渲染被写回」是实打实的损失。

## 后果

- `skill edit` 必须携带自己的验证信号：成功的 hunk、失败的位置诊断。这是命令契约的一部分，不是可选美化。`skill write` 是整文件覆盖、没有「匹配不上」的机会，它的防线（拒绝行号渲染的内容）放在二期，回显不在本决定的范围里。
- 不做 `checkout` / `commit`、不做 patch 语法、不做多文件原子操作（见 v32 PRD 的「不做」）。
- `skill download` + `skill submit` 仍可用，但只推荐给「第一次把本地 skill 带上来」；文档与帮助不再把「本地改完交回」当作更新路径。
- 若将来出现「一次要改十几个文件」的真实需求，再重新评估补丁形态；届时需要一条新 ADR 取代本条的部分结论。
