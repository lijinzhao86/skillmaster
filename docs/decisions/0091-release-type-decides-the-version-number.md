# ADR 0091 · 发布类型决定版本号，号仍然在发布时算出来

- **状态**：已采纳
- **日期**：2026-10-25
- **依赖**：[ADR 0031](0031-submitting-and-publishing-are-two-actions.md)（提交与发布是两个动作）、[ADR 0033](0033-version-names-are-semver.md)（版本号是 semver）、[ADR 0055](0055-drafts-have-a-required-name.md)（草稿名是标签，不是版本号）、[ADR 0090](0090-batch-publish-confirms-once.md)（批量发布）
- **修订**：ADR 0033 §决定 2 的执行面——版本号**仍然**是 semver、仍然在发布时分配；这一条只增加"这个号从哪来"的第二个答案
- **勘误（2026-10-25，审计时记下；正文按规矩不动，以本行为准）**：
  - **权限口径**：「与改草稿名、改说明同档」写错在 **§后果 的 CLI 那条（第 8 条）**——权限是 `write`，与那两条**不同档**，以 §后果第 3 条为准（那两条是「`write` ∧ 提交人是我，或 `maintain` 以上」）。§决定 1 里的「同一档」**不是这个意思**：它说的是生命周期（都在发布时冻结），那一句是对的。
  - §决定 6 的 `version_name_taken` 在仓里叫 **`version_already_exists`**（`ErrorCode` 既有），v18 的三份文档已统一。
  - §后果那两句界面原文写的是「发布」，**界面上这个动作叫「上线」**（[voice-spec](../../design/voice-spec.md) §三），v18 起界面不再出现「发布」。
  - §后果里那两句界面原文还有两处与 v18 不同：「**基于 `1.2.3`**」已删——基线挪进了队列的状态列（PRD 做 #4），那句话只留「将以 `1.3.0` 上线（次版本）」；「**草稿页与批量页都写**」不成立——v18 只把类型放进队列这一处，单版页仍是旧形态（PRD「不做」：下一版若还要改单版页就一并换掉，2026-10-25 定）。
  - §决定 8 引的「仓库的 `RELEASE.md`」**在仓库里并不存在**——三档的名字（主版本 / 次版本 / 修订）仍成立，依据是 SemVer 2.0.0 自己的术语，不需要那份文件
  - §决定 2 的「两者都给时以显式为准」数漏了**第三个来源**：一类草稿在提交时就带着 `skill_version.version`——今天的提交路径对草稿一律写 `NULL`（V11 加这一列时也没有回填），所以这类行只能由直接改库造出。这类草稿发布时**沿用它**，请求另给一个不同的号是 400 `version_name_is_assigned`——即显式号在这一档上**不**优先。算号只在草稿没有号的时候发生；v18 PRD 做 #2 与 TD §算号已按三种来源写全

## 背景

发布一份草稿时必须给一个版本号，不给就 400 `release_name_required`（`SkillVersionService`）。这在控制台里是一个输入框，问题不大；到了批量发布就是死结：几十份草稿就是几十个输入框，而批量发布的全部意义就是不再逐个问（[ADR 0090](0090-batch-publish-confirms-once.md)）。

三个选项：

1. **保持现状**：发布时必须填一个号。
2. **提交时就分配号**——[ADR 0055](0055-drafts-have-a-required-name.md) §理由已经否掉：草稿占号、丢弃烧号，发布时刻反而不命名。
3. **草稿携带「发布类型」**（主 / 次 / 修订），发布时按当前线上版本算出号。

选项 2 与 3 看起来像，其实不是一回事：**2 是提前把号定下来，3 只是提前声明"这次改动的量级"，号仍然在发布那一刻才产生。** [ADR 0055](0055-drafts-have-a-required-name.md) 否掉的是前者，它不该被用来否掉后者。

同一次讨论里还有两个事实决定了这个方案的形状：

- **知道量级的人在提交那一端。** 一次改动破不破坏兼容，是写它的人知道的；几天后去发布的人，多半不记得上次发到哪一版。
- **号码只有在发布时才知道算不算数。** 中间可能有别人发布了别的版本，基线上移；也可能这份草稿最终被丢弃。预先把号写进草稿，等于把一个会过期的判断变成契约。

## 决定

1. **草稿有一个可选属性 `release_type`**，取值 `major` / `minor` / `patch`。它不属于内容、不进 digest、草稿期可改、发布后冻结（与草稿名、说明同一档）。
2. **发布时号从两处来**：请求里给了显式版本号就用它；没给则按 `release_type` 与**当前线上版本**算出。两者都给时以显式为准。
3. **算的规则**（SemVer 2.0.0）：`major` → `X+1.0.0`；`minor` → `X.Y+1.0`；`patch` → `X.Y.Z+1`。
4. **从未发布过的 skill 一律得到 `1.0.0`**，`release_type` 不参与，这类行上也不提供选择（理由见下）。
5. **基线必须是正式版**。当前版本带预发布标记（如 `1.0.0-rc.1`）时 `release_type` 不可用，必须显式给号——从预发布往上递增的答案各家不同，这里不发明一套。
6. **算出的号撞上已有版本 → 这一条失败**（`version_name_taken`），不偷偷换成下一个号。号是契约，不是"尽力而为"。
7. **号仍然在发布那一刻分配、且不可改**——ADR 0033 与 ADR 0055 的这条不变。
8. **三档的叫法是 主版本 / 次版本 / 修订**，CLI 旗标为 `--release major|minor|patch`。用 `patch` 而不是 `fix`：第三段在 SemVer 里就叫 PATCH，仓库的 `RELEASE.md` 也写「主版本 / 次版本 / 修订号」。
9. **提交时不给类型，草稿的类型就是空——不继承。** 不沿用同一 skill 上一次提交的类型，也不从任何地方推断。空就是空，发布时要么由发布者选，要么显式给号。

## 理由

- **为什么不是保持现状**：批量发布问不出几十个号，于是要么放弃批量，要么让人在批量里瞎填。前者是产品缺口，后者更糟——填错的号是不可改的契约。
- **为什么不是提交时分配**：ADR 0055 的理由今天仍成立，而 `release_type` 不占号、不烧号，丢弃一份草稿不会让任何数字消失。
- **为什么号在发布时才算**：基线在那一刻才确定。预先算好的号在"别人先发了"之后就是错的，而错号一旦发出去不可回收（ADR 0031 §理由）。
- **为什么首次是 `1.0.0` 而不是 `0.1.0`**：`0.x` 的语义是"API 随时可能变"，而搬运上来的 skill 本来就在被使用，不是实验品。
- **为什么撞号就失败而不是顺延**：如果算出来是 `1.2.4` 而它已被占用，静默给出 `1.2.5` 会让确认单上的预演与实际不一致，而确认单正是 ADR 0090 的可接受性条件。
- **为什么保留显式号**：预发布（`1.0.0-rc.1`）、从预发布往上递增、以及"我就要钉这个号"都是真实需求，量级三档表达不了。
- **为什么不继承上一次的类型**：类型是对**这一次**改动的判断，上一次的判断不构成这一次的依据。若沿用，一次本该是修订的改动会因为上次填了次版本而被发成 `1.3.0`——而人会以为是系统算错了。**静默的默认值在这里是最坏的一种**：它足够隐蔽，又足够有后果。空是诚实的状态，界面会明确要求选一档。

## 后果

- **`skill_version` 多一列** `release_type`（可空，带 CHECK 约束），迁移 V29。它不进 digest、不改地址。
- **三处接口都要接它**：提交（可选）、改草稿（可改、可清空）、发布（显式号缺席时启用）。
- **改类型的权限是 `write`，不是 `maintain`。** 能提交草稿的人就能声明这次改动多大；`maintain` 管的是发布、回滚、丢弃别人的草稿——那几样改变对外可见的东西，类型不改变任何东西，它只是发布时的一个输入。**这与改草稿名、改说明不同档**（那两条是「`write` ∧ 提交人是我，或 `maintain` 以上」），因为它改的不是别人写下的标识。
- **由此带来一个后果，如实记**：一个只有 `write` 的人可以改**别人草稿**的类型。这不会改变任何已发布的东西，但会让下一次发布跳得比原作者想要的大。若实际用起来发现这不该发生，收紧到"提交人是我"只需要改一处判定。
- **发布接口的版本号从必填变可选**，向后兼容：老调用方照旧给号。
- **控制台要显示预演**：草稿页与批量页都写「将以 `1.3.0` 发布（次版本，基于 `1.2.3`）」。**预演不是承诺**——结果里必须回实际的号，且与预演不同时说出来（撞号、或有人抢先发布了更高版本）。
- **批量页的选中条件变成"号能算出来"**：从未发布的直接可发（`1.0.0`）；已发布但没类型的，要先在行上选一档，选完写回服务端——不是客户端状态，否则 CLI 与控制台会各说一套。
- **CLI 多一个入口**：提交时 `--release`，以及一个改草稿属性的命令（与改草稿名、改说明同档）。
- **一个长期负担**：`major` 之后 `minor`/`patch` 归零这件事，是 SemVer 的规矩，不是我们的。若将来要支持"只升次版本、不清修订号"这类玩法，那是另一条 ADR。
