# ADR 0022 · 无人值守的客户端绑到一个用户

- **状态**：已采纳
- **日期**：2026-10-02
- **依赖**：[ADR 0007](0007-self-built-oauth-as.md)（CLI 无人值守走 Client Credentials）、[ADR 0013](0013-phone-login-and-username-slug.md)（账号与身份模型）
- **回答**：TD §8 问题 5 的前半

## 背景

[ADR 0007](0007-self-built-oauth-as.md) 定下 CLI 的无人值守路径用 **Client Credentials**——CI 里没有浏览器、也没有人，所以没有「同意」这一步。于是有一个必须回答的问题：**这样换来的令牌代表谁？**

TD §8 问题 5 把它写成三问：谁有权创建、绑哪个用户身份、scope 怎么限。而 schema 给了它一个硬约束：

- `access_token.user_id`、`refresh_token.user_id`、`auth_code.user_id` **都是 `NOT NULL REFERENCES app_user(id)`**（`V1__baseline.sql`）；
- 而 **`oauth_client` 上没有用户的位子**。

也就是说，一个无人值守的客户端在今天**无法被表示为它代表的那个人**。不回答这个问题，schema 就落不下去。

三个选项：

1. **客户端注册时绑一个用户**（`oauth_client` 加一列）；
2. **令牌不带用户**（`user_id` 变可空，`AuthenticatedSubject` 允许 userId 为空）；
3. **只发系统账号的令牌**（不改 schema，所有 CI 动作归到 V2 种下的 `skillmaster` 系统账号）。

## 决定

**选 1。** `oauth_client` 加一列 `user_id`：需要 Client Credentials 的客户端在注册时指定它代表哪个账号。

- 这一列**只对无人值守那一路是权威**。交互式的公共客户端（CLI 走授权码 + PKCE）的 user **来自同意页**，不来自这一列。
- **`access_token.user_id` 保持 `NOT NULL`** —— 这是本条决定的主要好处，它一个字都不用改，M3 已经写好的 `AuthenticatedSubject(userId, scopes)` 也不用改。
- scope 上限挂在客户端上（注册时定，且不能超过那个用户的权限），而不是每次 token 请求时现判。

## 理由

**为什么不是 2（令牌不带用户）。** 机器确实是机器，但**这个项目的授权模型里没有「机器」这个主体**：能不能读一个 skill 由 M4 按 userId 与命名空间判定——`AuthenticatedSubject` 的 javadoc 明说权限判定在用例层、按 subject 走，而 security 层刻意不判权限（那是「未授权渲染成 404 而不是 403」成立的前提）。一个没有 userId 的令牌进到 M4 就没有谓词可用，等于要在整套权限模型里开一条旁路。这是三个选项里最贵的一条：改的是已经写好的接缝，不是加一列。

**为什么不是 3（只发系统账号的令牌）。** 省一列，代价是审计里所有 CI 动作挤在同一个 actor 上——而 `audit_event` 存在的理由正是「内容被拿走、用在管不到的环境里，事后归属是唯一的痕迹」（§3.5）。把多台机器、多个团队的动作合并成一条，等于把这个模块最该回答的问题答成「不知道」。而且 scope 无法按客户端收窄：任何一个 CI 拿到的是那个系统账号的全部权限。

**绑用户顺手答了 scope 那一问。** 上限挂在客户端上是**注册时的一次决定**，不是每次换令牌时的判断——后者要在每条 token 请求上重复一遍「这个客户端该被允许什么」，而那是部署时就知道的事。

## 后果

- **需要一条新迁移。** `oauth_client` 已由 `V1__baseline.sql` 建出，而 V1 已合进 `main` 并在本机应用过——Flyway 按校验和拒跑，**改 V1 等于要求每台已有库重建一次**。所以是一条 `V5`。同一条教训在 §7 P1 的 M01 那一段里记过（那一版选了新增 `V3` 而不是改 `V1`），这里照办。
- **审计语义变清楚**：CI 的动作归属于**人**，`actor_user_id` 不为 null。
- **但审计里仍分不出「这个人亲手做的」还是「他的 CI 做的」**。要区分不需要加列——把 `client_id` 放进 `AuditEvent.detail` 即可（`detail` 存 JSON，设计上就不按字段查询，§3.5）。
- **「谁有权创建这样的客户端」仍未定。** v1 只有一行手工种下的客户端；管理端写接口在 §7 P1 里还没做。这是 TD §8 问题 5 的**后半**，本条只回答了「绑哪个用户身份」。
- **一个用户停用后，他绑的 CI 客户端不会自动失效。** 令牌不因 `status` 变更而失效——M1 只在**登录那一刻**校验 `status = 'active'`，已签发的凭据不在它的管辖里。所以「停用一个人」今天停不掉他机器上的令牌，得另外撤销（`revokeAllFor`）或者让验令牌那条路也看一眼 `app_user.status`。**这是要还的债**，记在这里。
