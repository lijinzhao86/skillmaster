# 0193 · 公域标签是可扩展的「定义 + 挂载」，标签是主张不是评价

- **状态**：已采纳，**部分被 [0195](0195-labels-p0-narrows-two-adrs.md) 与 [0197](0197-production-tables-hold-only-final-claims.md) 取代**（0197 的存储形状自打标版生效）（§决定 3 的 `api_key` 写法与 §决定 7 的冲突留痕时点）
- **日期**：2026-11-13
- **所属版本**：[`v66-skill-labels`](../versions/v66-skill-labels/README.md)
- **依赖**：[0192](0192-public-categories-are-thirteen-shelves.md)（13 个一级分类）、[0181](0181-text-limits-use-unicode-code-points.md)（文本上限按码点）
- **相关**：[`docs/research/skill-taxonomy-and-labeling.md`](../research/skill-taxonomy-and-labeling.md)（SkillHub 与讯飞的标签模型）

## 背景

v66 要给公域 skill 加「运行环境（含 API key）、定价」这些描述性字段，还要加一句「预期结果」。摆在我们面前的第一个问题是：这些字段怎么放？

三种做法：

| | 做法 | 代价 |
|---|---|---|
| a | 每个维度一列 | 加一个维度就是一次 Flyway 迁移 + 一次接口 + 一次控制台改动；维度会继续长 |
| b | 一张通用 key-value 表 + 一份词表 | 加维度只插词表行；代价是校验在应用层、查询要 JOIN |
| c | 把所有信息压成一个综合评分 | 不可解释；调研明确说流行度不是质量，身份/来源/安全/效果不能压成一个分 |

第二个问题是 `outcome` 与未来产品的关系。用户未来可能让运营和用户提交评测视频、评论、评分。如果 `outcome` 是一段可以随便塞的长文本，这些内容迟早会被塞进去——然后「skill 声称会产出什么」「用户说它实际怎么样」「评测证明它做到了什么」就混成同一个字段，生命周期、权限与审核规则全部打架。

第三个问题是「公域」：同步进来的 skill 没有作者替我们填这些字段；平台必须自己产，而且产出来的东西要可解释、可纠正、可重算。

## 决定

1. **属性标签用「定义 + 挂载」两张表。**
   - `label_definition`：`key`（如 `runtime`）、`value`、短显示名、完整语义、所属维度与分组（运行环境下的语言 / 系统 / 工具 / 凭据）、**是否进筛选**、状态（启用/停用/退休）、排序。
   - `skill_label`：`skill_id`、`definition_id`、来源（Agent / 运营 / 作者 / 上游）、置信度、证据、模型与版本、**评的是哪一版**、时间。
2. **加一个新维度 = 往词表插行，不改表结构。** 新维度可以先进「只展示、不进筛选」，等数据够了再打开筛选。
3. **首批两个维度**：`runtime`（运行环境，**多值**：语言 / 系统 / 工具 / 凭据，含 `api_key` 与 `account`）、`pricing_type`（定价）。**`output_type`（产出形态）不做**：预期结果已经说了「得到什么」，再挂一个粗粒度产出类目是同一件事的重复，还多一个维度要打标和维护。`input_type` 推迟；`requires_api_key` 不再单列，SkillHub 的 `requires_api_key` 映射为 `runtime=api_key`。词表可扩展，这两个只是第一批。
   - 一个维度可以有多个值：同维度下不同 `value` 是不同的 `label_definition` 行，`skill_label` 按 `(skill_id, definition_id)` 唯一；多选不改表结构。
4. **`outcome` 是一句话的主张，独立存放**：写「预期结果」，不覆盖原 `description`，不承担证据与评价。
5. **四层分开，永不合并**：**主张**（`outcome`、属性标签）· **证据**（评测结果、演示视频、截图）· **评价**（评分、评论）· **信号**（调用量、入库数）。四层各有自己的来源、权限、审核与保留期。
6. **低置信度留空，不猜。** 页面上只展示高置信或经运营确认的值；没有证据的标签不落库、不展示。
7. **标签挂在 skill 上，但记「评的是哪一版」。** 上游发新版就重抽；运营改过的值保留，冲突时运营优先并留痕。
8. **胶囊只写短名，类别用颜色与图标区分。** `Python`、`API key`、`macOS`、`付费` 上胶囊；`需要 Python`、`仅 macOS` 等完整语义**只留在词表数据里**（抽取证据 / CLI / 运营），**不在前端重复**——不进胶囊、tooltip 或读屏。语言 / 系统 / 工具 / 凭据 / 定价各一套颜色与图标；颜色不是唯一信号，文字与图标同时在场。
9. **运行环境的三个高歧义值按严格口径抽取。** 它们描述的是「用户侧真的缺什么」，不是 skill 在讲什么：
   - `gpu`：只算本机或本地集群必须有 NVIDIA GPU。云 GPU（如 Modal / 云训练服务）归一为 `online-service` + `api-key`，不标 `gpu`。
   - `docker`：只算 skill 自己的步骤要求运行 `docker` / 容器。只写 Dockerfile、生成 compose / K8s 清单、讲 Docker 主题，不标 `docker`。
   - `database`：只算 skill 的步骤要连接或执行到数据库（`EXPLAIN`、迁移、复制、监控）。教 SQL、设计 schema、查公开数据库 API，不标 `database`；`database-lookup` 这类公开数据 API 走 `online-service` + `api-key`。
   - 证据必须是命令、前置条件或安装步骤；简介里出现关键词不算。

## 理由

- **为什么是通用 key-value 而不是固定列。** 用户明确要求「属性标签在技术设计上可扩展」。固定列每加一个维度都要迁移、接口、控制台三处一起改；通用表把「加维度」降成一次词表插入。代价是查询要 JOIN、校验在应用层——这是可接受的，因为标签是读多写少、量级远小于 skill 本身。
- **为什么把「运行前提」与「API key」合成运行环境。** 它们回答的是同一个问题——「要把它跑起来，我还缺什么」；分成两个维度，列表上会出现两枚同义的阻拦胶囊，用户还要自己拼。合成一个多值维度后，Python + Node.js + API key 可以同时存在，每个值一枚。
- **为什么运行环境多选不改表结构。** `skill_label` 的唯一约束是 `(skill_id, definition_id)`，不是 `(skill_id, key)`；一个维度下的每个值有自己的 definition 行，所以 Python 与 Node.js 可以同时挂。词表加的是值行，不是新表。
- **为什么输入要求推迟。** 运行环境能从 `requirements.txt`、`package.json`、`pom.xml`、`Dockerfile` 与 SKILL.md 里的命令取证；输入要求要判断「必需还是可选」「用户要准备什么」，同一个 skill 的不同用法答案不同。标错的代价是用户按标签准备错材料。第一期先不做；有搜索日志证明用户按输入类型找时再加。
- **为什么胶囊写短名、类别用颜色。** 列表一行只有三行，`需要` 在每颗胶囊上重复一次；把类别交给颜色与图标，胶囊回到名词，扫读更快。完整语义不丢，但**不在前端重复**：`macOS` 可能是「支持」也可能是「仅支持」，这个区别留在词表数据里给抽取证据、CLI 与运营看；前端只承担「这枚标签是什么值」，不承担一句解释。代价是读屏只读到 `Python` / `macOS`，丢了「仅」这类限定；如果实测出现误读，再单独给系统类胶囊补一个最小限定，不在所有胶囊上铺开。颜色只做分类，不做状态；状态仍由文字（`API key`、`付费`）说。
- **为什么不做产出形态。** 预期结果是「用了会得到什么」的具体一句话，已经比「文档与报告 / 数据与表格」这类粗类目更可判断；再挂一个 `output_type`，用户在列表上读到的是同一件事的两遍，平台还要多维护一套词表与抽取规则。少一个维度，首批的抽取与审核面也小一圈。
- **为什么 GPU 只算本地。** 用户问「GPU」时，实际要判断的是「我这台机器/这个集群跑不跑得动」。云 GPU 是另一件事：它要的是账号、额度和网络，不是本地显卡；把它标成 `gpu` 会让没有显卡的人以为自己缺硬件，也会让有显卡的人以为平台会提供云算力。
- **为什么 Docker 只算运行时调用。** 「会写 Dockerfile」和「要运行 Docker」是两种不同的准备：前者只要文本编辑，后者要装引擎、拉镜像、给权限。按主题标会让大量 DevOps 教学 skill 误标，用户点开发现只要看一份 YAML。只认 skill 自己的步骤里真的执行 `docker` / 容器，才把「装 Docker」变成可执行的准备项。
- **为什么 database 收窄成「连接数据库」。** 「数据库」在公开库里同时指三件事：连一个库跑 `EXPLAIN` / 迁移、教 SQL 与 schema 设计、查公开数据库 API。只有第一种是运行前提；后两种标成 `database` 会让用户去准备一个根本不需要的库。收窄后它仍然是高频筛选词，但误标代价从「白装一个库」变成「多看一眼」。
- **为什么词表与挂载分开。** 词表是平台数据（谁能造词、哪些词停用、哪些进筛选），挂载是每条 skill 的事实（谁标的、置信度多少、证据是什么）。混在一张表里，改一个显示名会碰到所有 skill 行。
- **为什么 `outcome` 不做成大容器。** 它回答的是「我会得到什么」，是一句可扫描的主张。评测视频、评论、评分回答的是另外三个问题；把它们塞进 `outcome` 会让「主张」与「证据」无法区分，将来做推荐时也说不清「这条为什么排在前面」。
- **为什么低置信留空。** 一个错的标签比一个空的标签更贵：用户会按它做决定，运营会按它做统计。空值至少是诚实的。
- **为什么记「评的是哪一版」。** 标签描述的是内容；内容变了，标签可能不再成立。没有这一列，上游发新版后我们无法知道哪些标签需要重算。

被否掉的：**每个维度一列**（迁移与接口成本随维度线性增长）；**一个综合评分**（不可解释，且调研明确反对把身份/来源/安全/效果压成一个分）；**复用 `description` 当 `outcome`**（主张与正文混在一起，且会覆盖作者原文）；**把评论/评分塞进 `outcome`**（生命周期、权限、审核规则都不同）；**标签跟版本走**（标签是发现用的元数据，改完应立即生效；版本是内容快照——两者粒度不同）；**输入要求进首批**（取证难、标错代价高，推迟）；**把 API key 单列成维度**（与运行前提回答同一个问题，列表上会重复）；**产出形态进首批**（预期结果已覆盖，重复且多一个维度要维护）；**云 GPU 算成本地 GPU**（要的是账号与网络，不是显卡）；**Docker 主题算成 Docker 运行前提**（写 Dockerfile 不需要装引擎）；**SQL / schema / 公开数据库 API 算成数据库连接**（用户会被要求准备一个不需要的库）。

## 后果

- **新增两张表与索引**：`label_definition`、`skill_label`；`skill_label` 上有 `(skill_id, definition_id)` 唯一约束、按 `definition_id` 的筛选索引。具体 DDL 进技术设计。
- **`runtime` 的词表首批 21 个非默认值 + `prompt-only` 默认值**，分语言 / 系统 / 工具 / 凭据四组；新增语言、系统或工具只是插词表行，不改表结构。每个值带短名、完整语义与分组；UI 用 `data-group` 着色，颜色与图标一一对应，**但只画短名**。完整词表见 [`v66 PRD`](../versions/v66-skill-labels/prd.md) §范围。
- **`gpu` / `docker` / `database` 三个值都进筛选**（2026-11-13 用户定）：收窄定义，但不把筛选入口藏起来；用 A14 与每周抽样盯误标。若 `database` 的误标率在抽样中明显高于其他值，先关它的筛选，不改标签契约——这是运营动作，不是新 ADR。
- **`outcome` 新增字段**：可以放在 skill 的读模型表上，也可以单独一张表；无论放哪，都带来源、置信度、证据与「评的是哪一版」。
- **接口与 CLI 新增字段**：读接口返回 `outcome` 与标签；`skmr skill show` 输出同一组字段，`skmr skills search` 在每条结果下输出属性短名；CLI 不做自己的判断。
- **抽取流水线写标签**：同步建草稿或发布时触发；每个值带证据；模型与词表版本入库。
- **未来的评价/证据对象可以引用 skill 与 `outcome`**：做「声称 vs 实际」的对比，不需要改 `outcome` 的表结构。
- **展示层只读高置信或已确认的值**：低置信不展示；中置信进异常队列。具体分档与验收见 [0194](0194-public-labels-are-agent-produced-and-sampling-audited.md)。
