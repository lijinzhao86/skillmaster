# ADR 0004 · 身份模型：不透明 id 作主键，name 为属性

- **状态**：已采纳（§后果 里的**寻址**部分被 [ADR 0012](0012-addressing-and-version-pinning.md) 修订）
- **日期**：2026-09-26
- **取代**：无
- **后续**：[ADR 0012](0012-addressing-and-version-pinning.md) 修订了本 ADR §后果 中的两处——「URL 一律用 `id`」与「agent 用 `id` 做后续调用」。**`id` 作主键这一决定不变**，改的只是「什么出现在 URL 里」。**正文四段保持原样**，理由见那份 ADR。**§理由 里那句「以及将来的权益记录」已经被兑现**：[ADR 0034](0034-skill-level-sharing.md) 的 skill 级授权就挂在 `skill.id` 上，理由正是这里的「改名就等于换了一个 skill」。

## 背景

skill 需要一个稳定标识。直觉方案是用 `(用户, 名称)` 当主键——"每个用户自己的命名空间内不重名"是个自然约束，而且全局唯一不可行：两个人都会给自己的 skill 起名 `pdf-tools`。

但**名称是会变的**，而主键不能变。

## 决定

- **`id`（不透明 ULID）是主键，永不变。**
- **`name` 是属性**，唯一约束在 `(namespace_id, name)`。
- **注册时自动为每个用户创建个人命名空间**（slug = handle）。

## 理由

- **若用 `(owner, name)` 作主键，改名就等于换了一个 skill。** 所有 version、安装记录、审计日志、以及将来的权益记录都要跟着迁移。改名是应该被允许的常规操作，不该有这种代价。
- **`(namespace_id, name)` 一个约束同时覆盖两种场景**："个人内不重名"（个人命名空间）与"团队内重名"（团队命名空间）。而且**从个人升级到团队命名空间不需要迁移**——只是换一个 `namespace_id`。
- 不透明主键不泄露数量、可按时间排序、不依赖业务字段。

## 后果

- **URL 一律用 `id`**（`/v1/skills/{id}`），所以改名不会断链。`name` 只用于展示与检索命中。
- **分发端仍要处理同名。** 两个命名空间下的同名 skill 在存储层合法，但在"扁平寻址"的场景下会撞——远程模型下靠 `id` 或命名空间前缀区分。
- 检索结果里必须同时返回 `id`（供寻址）与 `name`（供人读），agent 用 `id` 做后续调用。
- 相关：`skill` 与 `skill_version` 分离——`skill` 是身份，`skill_version` 是不可变快照（见 [ADR 0005](0005-content-addressing.md)）。
