# ADR 0054 · 生命周期动作发生在一个版本自己的页面上

- **状态**：已采纳
- **日期**：2026-10-18
- **依赖**：[ADR 0031](0031-submitting-and-publishing-are-two-actions.md)（提交与上线是两个动作；上线只在浏览器面）、[ADR 0047](0047-permissions-are-a-ladder.md)（权限是梯子）、[ADR 0033](0033-version-names-are-semver.md)（版本名是作者声明；发布时命名由本版另一条 ADR 修订 0033）

## 背景

v6 的第一稿把版本生命周期画成了**行内动作 + 一次确认**：上线、废弃、收回都写在版本表那一行上，点下去弹一张确认表，确认即生效。它与 v5 的「管理动作都在它们发生的那一行上」一致，写起来也省事。

但上线与收回改变的是**所有调用者 agent 读到的内容**——[ADR 0031](0031-submitting-and-publishing-are-two-actions.md) §理由 把上线放在浏览器面，理由正是「一个人当场确认」。确认之前得先**看得见**：这一版改了什么、跟当前线上差在哪、它的说明与发布名是什么。确认表只能写一句后果，装不下这些；关掉之后它也什么都不留下。

2026-10-18 用户提出把生命周期动作挪到一个**单独的页面**上，参照 GitLab 的 merge request：版本表可以列出有哪些动作，但高风险动作不在点下去的那一刻生效，而是由那条版本自己的页面承接。

第一版实现又多加了一个「发布」tab，入口是一屏**选择版本**。它立刻暴露了问题：版本 tab 与发布 tab 的入口都是**同一份版本清单**，用户看到两个长得差不多的页面，不知道该从哪一份开始。查了同类产品后确认这不是个例：

- [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)：一份 releases feed；每条 release 上直接有编辑/删除，创建与草稿是一个表单。
- [GitLab Releases](https://docs.gitlab.com/user/project/releases/)：一份 releases 列表；编辑打开单独的 Edit Release 表单页。
- [Vercel Deployments](https://vercel.com/docs/deployments/managing-deployments)：一份部署列表；每行 `…` 菜单做 Promote/Rollback，点部署才进详情页。
- [Heroku Releases](https://devcenter.heroku.com/articles/releases)：一份发布历史，每行一个「Rollback to here」。

**没有一家做第二份版本清单。** 摆上桌的做法：

| | 做法 | 问题 |
|---|---|---|
| a | 保持行内一键触发 | 误点的代价是消费面立刻换内容或被收回；没有审阅的余地 |
| b | 行内入口 + 确认表 | 比 a 安全，但仍然只有「你确定吗」，没有差异、说明、影响面；地址不可分享 |
| c | **版本 tab 的单版页承接动作** | 多一次导航；换来可审阅、可寻址、可扩展的承接面，且清单只有一份 |
| d | 另开一个「发布」tab，入口再选一次版本 | **被否**：第二份清单，与版本 tab 重复，用户要选两次 |

## 决定

1. **版本 tab 是唯一的版本清单。** 上线、废弃、取消废弃、收回、恢复这五个生命周期动作发生在**这一版自己的页面上**——地址钉住某一版时，版本 tab 从清单换成那一版，不是第二份清单。
2. **清单只列入口，不执行动作。** 行末的 `上线` / `废弃` / `收回` / `恢复` 是链接，点进去只导航；没有任何生命周期动作会在清单上一键生效，也没有确认弹层。
3. **单版页是「一个版本」的页面，不是「一个动作」的页面。** 标题是版本身份（发布名，或草稿的说明/`sha256:` 短号），同一屏上给出状态、说明、与当前线上版本的差异，以及这一版能做的动作。动作随状态与档位出现，够不到的画都不画。
4. **两个低风险动作仍留在清单的草稿行内联**：改说明与丢弃。前者是高频、可逆的编辑；后者只影响作者自己的草稿、不改变任何调用者读到的东西，且已有原地二次确认。它们不是生命周期动作。
5. **单版页遵守梯子**：上线 / 废弃 / 取消废弃要 `maintain`；收回 / 恢复只有所有者。被收回的版本只有 `maintain` 及以上打得开，`write` / `browse` / `invoke` 看到的是「没有这一版」——与不存在同一个答案。
6. **单版页可寻址。** 地址里带着版本钉，所以「你看这一版能不能上」可以像发一个 MR 链接一样发给另一个维护者；返回回到清单。
7. **不做评论、审批流、多人签署。** v6 没有那个需求；单版页的形状留了扩展的位置（影响面、调用量、审计记录），但现在不画空位。

## 理由

**为什么「确认」不够，需要「审阅」。** 上线改变的是消费面：所有按裸地址调用的人，下一次请求就会读到这一版。读者要回答的不是「我确定吗」，而是「我改的东西对吗、它会替换掉什么」。差异与说明是回答这个问题的材料；一张确认表放不下它们，所以它只能要求人凭空确认。

**为什么是单版页，而不是第二份清单。** 清单已经回答了「有哪些版本、各自什么状态」；再放一份同样的清单只是把同一个问题问两遍。单版页回答的是另一个问题：「对**这一版**做这件事会发生什么」——它是一条记录，不是一份列表，所以两屏不会长得一样。GitLab 的 Edit Release 就是同一个分工：列表负责找，表单负责改。

**为什么不做选择页（第一版的错误）。** 选择页把「选哪一版」从清单里搬出来，等于让用户在两份看起来一样的清单之间做选择；它既没有增加信息，也没有降低风险。版本钉由清单的入口带过来，选版本这一步已经在清单里发生了。

**为什么版本表还要列入口。** 把入口藏进「点版本名」会让人猜；把可做的动作写出来，是把「这一版现在能做什么」也当成清单要回答的问题。入口与执行分开，是这次决定的核心：**清单回答「能做什么」，单版页负责「做」。**

**为什么改说明与丢弃留在行内。** 两者都不改变调用者读到的东西：说明不进内容、不进地址；丢弃的是从未上线过的草稿。把它们也搬进单版页，会用一次导航换一次高频编辑，摩擦没有对应的风险。

**被否掉：所有动作都走单版页，连说明编辑也搬走。** 那会让「改一句错字」变成一次页面往返；而且说明编辑的结果要立刻在清单里看得见，行内编辑正好是这个形状。

**被否掉：侧边抽屉 / 行内展开。** 抽屉在窄屏会退化成整屏，且发布表单与差异并排在一个窄栏里读起来挤；行内展开会把多字段的发布表单塞进表格行，破坏清单的可扫读性。单版页给差异与表单足够的宽度，也是 GitHub / GitLab / Vercel 都采用的形状。

## 后果

- 版本 tab 的标签条仍是 **信息 / 文件 / 版本 / 设置**，不新增 tab。
- 版本 tab 有两个地址：清单（`/skills/{ns}/{name}?tab=versions`）与单版页（`/skills/{ns}/{name}?tab=versions&version=<pin>`）；演示件对应 `?page=skill&tab=versions` 与 `?page=skill&tab=versions&version=<pin>`。两屏都读作者面已有的版本数据，不新增接口。
- 上线草稿时的发布名选择与说明确认移进单版页；收回时的原因与后果也移进去。两个确认弹层删除。
- 组件测试要覆盖：清单不执行动作（只有链接）、单版页按状态与档位画动作、没有权限的人看不到动作、地址钉住一版时清单收起。
- 视觉验收仍由人做；这次改动让「上线」多一次导航，是刻意的代价。
- 后续要加「谁在调这一版」「废弃后哪些调用会失败」「操作记录」时，加在单版页上，不再往清单塞列。
