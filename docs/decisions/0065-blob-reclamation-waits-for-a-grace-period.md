# 0065 · blob 回收等一个 grace period，文件写不拿表锁

- **状态**：已采纳
- **日期**：2026-10-20
- **依赖**：[0005](0005-content-addressing.md)（内容寻址、blob 只增不删、需要 GC）、[0010](0010-storage-in-postgres.md)（字节也落在 PostgreSQL）、[0062](0062-grep-is-a-scoped-scan-not-an-index.md)（写路径的性能是设计约束）、[0064](0064-a-draft-may-change-a-published-version-may-not.md)（草稿内容可变，`rm` 会造出孤儿）

## 背景

v6 的回收路径假定「写 `version_file` 的每一笔都发生在 `underExclusiveWrite` 的表锁里」：提交与软删除拿锁，顺手扫一遍未被引用的 blob。锁成立时，`blob.put` 与 `version_file` 的引用在同一个临界区里，GC 不可能看见「刚写进来、还没来得及被引用」的 blob。

v7 加入草稿的文件写，这个前提不再成立：

- 文件写如果也拿 `version_file` 表锁，所有写、所有提交、所有 GC 会全局串行——直接违反 §性能预算（单写 P95 < 300 ms）。
- 不拿锁，就有「`put` 已提交、引用还没写」的窗口。此时若并发 sweep，会把这份新 blob 当孤儿删掉，随后那次写撞外键失败。
- 反过来，`rm` 删掉引用之后，blob 立即变成孤儿；「删完马上重写同样内容」会复用这条老 blob——回收方按创建时间判断，不能把它当新 blob 保护。

## 决定

1. **sweep 只删「未被引用、且 `blob.created_at` 早于 cutoff（now − 10 分钟）」的行。** `blob.created_at` 是既有列，不加列。写事务里 `put` → `version_file` 的窗口是秒级，远小于 10 分钟。
2. **文件写不拿 `version_file` 表锁**：一次 `put` + 清单增量 + 一行 `UPDATE`，行锁只锁同一版。锁由 [0064](0064-a-draft-may-change-a-published-version-may-not.md) 允许的「只有草稿可变」这一前提保护——同一行由 `SELECT … FOR UPDATE` 串行化。
3. **文件写不跑 sweep。** 回收只发生在仍然走 `underExclusiveWrite` 的路径：**提交**与**软删除**。**发布与丢弃不 sweep**（它们在 v6 里也从不扫）。
4. **复用老 blob 的竞态如实接受**：sweep 删掉一条老孤儿后，重写同样内容可能撞外键失败——这次写可见、可重试，客户端重跑 `write` 会重新插入 blob。不为此新增 `last_written_at` 列或 `touch` 逻辑。
5. **grace 是回收方的属性，不是写方的约定**：`BlobStore.deleteUnreferenced` 收一个 cutoff 参数，由 `BlobGc` 传入；写路径不需要知道 grace 存在。

## 理由

**为什么不是「文件写也拿表锁」。** 表锁是全局的：一次 `rm` 会让所有提交、所有写排队。16 MiB / 512 文件的写入本来就要几百毫秒，再叠一把全局锁，单写 P95 的预算守不住；而草稿写是这一版新增的高频动作。

**为什么不用「引用计数」或「两阶段删除」。** 引用计数要为每次写增删计数并防止漏减，漂移后删错东西；两阶段删除要多一张表或一列，回收也仍然是全表扫。10 分钟的年龄线用既有列就能表达同一个保护，且失效模式是「晚删」，不是「删错」。

**为什么 grace 取 10 分钟。** 它要覆盖的是 `put` → 引用之间的事务窗口（秒级）与客户端重试的时间尺度；再长只会让孤儿多躺一会儿，不影响正确性。这个值是 `BlobGc` 里的常量，改动即改这一条。

**为什么发布 / 丢弃不 sweep。** 它们不产生也不删除 `version_file` 行（发布改状态与版本号，丢弃改状态），扫一遍没有新孤儿可收，只是把表锁多拿一次。回收点放在真正会造出孤儿的动作上：提交（可能被校验挡掉一半）与软删除。

**为什么接受「删后重写」的失败。** 失败是可见的（写请求报错）、可重试的，而且只在「旧 blob 已过 grace、又恰好被 sweep 选中」时出现。加 `last_written_at` 或复用时 touch `created_at` 都能消掉它，但那要改表、改 `put` 的语义，把一次罕见竞态换成一条永久的写路径成本。本版选可见的失败。

## 后果

- **孤儿 blob 会一直躺到下一次提交 / 软删除**：长期不发布的草稿被 `rm` 掉的内容不会立刻回收。这是明写的代价，记在 test-plan 的已知问题里，不是遗漏。
- **`BlobGc` 与 `SkillVersionService.underExclusiveWrite` 的 javadoc 要改**：它们今天写的是「写 `version_file` 之前必须拿锁，顺序不可协商」；v7 的文件写有意绕开它，注释必须说清「提交 / 软删除必须拿；文件写由 grace 保护」，否则代码与注释互相打脸。
- **并发用例要覆盖两条边**：grace 不删新 blob；`rm` 后复用老 blob 撞外键的失败可重试（test-plan T-CONC 一组）。
- **将来若要更快的回收**：先有「高频写造成大量长期孤儿」的实测，再考虑按 `sha256` 的引用计数或复用时 touch；不要因为一条罕见竞态就改表。
