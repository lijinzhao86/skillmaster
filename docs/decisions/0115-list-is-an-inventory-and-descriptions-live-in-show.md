# 0115 · `skills list` 是清单，描述在 `search` 与 `show`

> **状态**：已采纳
> **日期**：2026-10-30

## 背景

`skills list` 一直是「地址 + 描述 - 适用场景」的卡片，v13 §3 把这个形状写成了契约，理由是它是会话开始时加载的那一层，就像 Claude Code 自己的 skill 清单：名字加描述，一次读完就知道有什么。

这个前提在 v27 之后变了：规则段默认先 `skills search`，**发现**这一步由检索承担；`list` 退化成「把库列一遍」。而卡片的成本没有跟着降——本机 25 条的库，一次 `skills list` 是 15,896 字节 / 76 行，每条约 0.6 KB，每次调用整份重进上下文。

## 决定

- **`skills list` 默认每条只打地址**（`命名空间/名字`，不带版本），一行一个、卡片之间不加空行；页脚仍是「（共 N 个。加载某一个：…）」。
- **默认列出全部**：内部翻完所有页，不再默认停在前 50 条。`--all` 保留但不再改变行为（1.x 内命令面只增不减，`RELEASE.md` §1）。
- **`--verbose` 保留描述**：地址 + 「描述 - 适用场景」+ 「来源 / 状态 / 版本 / 更新于」。
- **`skill show` 不动**，仍是单个 skill 的全量详情。
- **`skills search` 不动**，仍是地址 + 描述（v30 刚定完它的形状）。
- **默认行不加任何其它字段**：状态、来源、版本、更新于都由命令自己的 flag 表达（`--show` / `--source` / `--sort`），输出不重复「你是用哪个维度筛出来的」。

## 理由

**为什么是「只给地址」而不是「截短描述」**：截短描述既保留了一条要维护的文本，又在需要一个判断时给不出完整信息——两头不落地。地址是唯一不会错的身份，描述有一个专门的命令（`show`）与一个批量的入口（`--verbose`）。

**为什么 `--verbose` 保留描述**：它是「更多」的那一档。去掉之后，批量看完一个库要么 N 次 `show`，要么没有路；保留它，默认不付成本，想要的人显式要。

**为什么默认列全**：50 条上限是照 0.6 KB/条定的（约 30 KB）。只给地址后约 25 B/条，50 条只有 1.2 KB，上限失去了依据；而「清单」这个东西的价值就在完整——一半的清单要配一句「还有更多」，反而更贵。

**否掉的方案**：

| 方案 | 否掉的原因 |
|---|---|
| 保持现状（地址 + 描述） | 体积问题就是这一版要解决的 |
| 描述截到第一句 | 截断点不可靠（作者写法不一），且仍然每条 100+ B |
| 新增 `--describe` 开关 | `--verbose` 已经是那个开关；两个同义开关只会让人猜哪个是「全的」 |
| 保留 50 条上限 | 上限的依据（描述的体积）已经不存在 |
| 默认行加状态等小字段 | 与筛选维度重复；需要的人用 `--verbose` |

## 后果

- **v13 §3 的卡片契约在 `list` 上被取代**（v30 已取代 `search`）：`list` 的默认输出不再是「地址 + 缩进描述」，而是一段纯地址。任何把「缩进行 = 描述」当格式的消费方要改；`--verbose` 保留了原来的形状。
- 浏览式用法（不搜索、直接翻库挑）会多出 `skill show` 的调用；发现路径以 `search` 为准。
- 超大库的默认输出会变大：地址约 25 B/条，1,000 条约 25 KB，逼近 Claude Code 的成功输出内联上限（约 30,000 字符）。收窄靠 `--show` / `--namespace` / 分类 / 标签 / 关键词；本版不加新的硬上限。
- `--all` 在一个主版本内保持「被接受但不改变行为」；删除它要等到下一个主版本。
- 平台技能 `skillmaster/startup` 若描述过 `list` 的输出形状，需另走草稿同步（不在本仓库代码里）。
