# 0163 · 一个仓库在一轮同步里只下载一次

- **状态**：已采纳（取代 [v50 TD](../versions/v50-open-source-sync/technical-design.md) 里「每个条目按自己的 revision 各拉一次整包」的取数口径；[ADR 0157](0157-sync-is-a-source-neutral-pipeline.md) 的底座与适配器分工不变）
- **日期**：2026-11-07
- **依赖**：[ADR 0157](0157-sync-is-a-source-neutral-pipeline.md)（来源无关底座）、[ADR 0158](0158-sync-runs-inside-the-server.md)（同步跑在服务进程里）、[ADR 0161](0161-imported-skill-state-is-fixed-when-the-draft-is-created.md)

## 背景

2026-11-07 首次全量导入暴露：`K-Dense-AI/scientific-agent-skills` 的 177 个 skill 一条都没进来，全部 `upstream_timeout`。实测原因不是网络断了，是**同一个仓库被反复整包下载**：

- 走的是「按 skill 目录自己的 revision 拉 codeload 整包」——revision 是该目录最后一次提交的 SHA，177 个目录落在 **128 个不同的 revision** 上；
- 每个 revision 都要下一个**完整仓库**：实测该包 **232 MB**，部署机到 codeload 约 1.2 MB/s，一次要 **191 秒**，而读取器的超时是 **60 秒**——每一次都超时；
- 128 × 232 MB ≈ **30 GB** 流量（不是 5.4 GB：42 MB 是 70 秒时还没下完的字节数）。即使把超时调大，这轮导入也要以小时计，并把 GitHub 出口带宽当缓存用。

同样的问题在缩小版上一直存在：`wshobson/agents` 185 个条目、`browser-act/skills` 约 100 个，都在重复下载各自 2 MB 上下的整包。

可选做法：

- **A 按 `(locator, revision)` 缓存**——K-Dense 有 128 个不同 revision，仍然要下 128 次，等于没修。
- **B 每个仓库每轮只下一个整包，取仓库默认分支的最新提交**——一次下载服务全仓库。
- **C 只调大超时**——流量与时间都不变，只是不再报超时。
- **D 改回逐文件 API**——2026-11-06 已实测：未认证 60 次/小时，且逐文件请求不划算（v50 TD 的取舍）。

## 决定

1. `ContentSource` 增加运行生命周期：`beginRun()` / `endRun()`，由 `SyncPipeline.run()` 在展开前调用、在 `finally` 里收尾（异常也调用）。默认空实现，不认识缓存的来源不用改。
2. `GitHubContentSource` 在一轮里为每个 `locator` 下载**一个**整包：第一次遇到该仓库时取仓库默认分支的最新提交（`revision(locator, "")`），下载 `codeload/<repo>/tar.gz/<sha>` 到临时文件；同一轮里该仓库的每个 skill 都从这一个文件里解出自己的目录。**失败也缓存**，一个不可达的仓库只打一次，不让它的 177 个条目各打一次。
3. 下载超时 **600 秒**（原 60 秒）；解包仍是每条约 60 秒的上限。
4. 临时文件由 `endRun()` 删除。进程被强杀时残留的文件在系统临时目录里，等操作系统清理。
5. 记录在快照里的 revision **仍是该 skill 目录自己的最近提交**，变化检测不变；只有「这次读哪棵树」从目录 revision 改成了仓库默认分支 tip。因此 revision 是**变化检测的身份，不是内容所在的树**——草稿说明里的 `@<短sha>` 也是这个身份，回上游核对时 checkout 到的可能比内容新。

## 理由

- **B 是唯一把流量降回一次的方案。** 232 MB 的仓库，177 个 skill，一轮一次下载；A 仍要 128 次。
- **许可与内容仍来自同一棵树。** 只是那棵树从「skill 目录自己的提交」变成「仓库最新提交」——对「现在上游长什么样」这个问题，后者才是正确答案。代价写在「后果」里。
- **写入顺序、并发、失败隔离都不动。** 改的只是取数粒度；`select: all` 的展开、闸门、串行写入、`duplicate_address` 这些结构保持原样。
- **C 与 D 被否的理由是实测数字**：C 约 30 GB 与数小时；D 在 2026-11-06 已量过。

## 后果

- **许可可能比 skill 的 revision 新。** 上游只改根 `LICENSE` 时，下一次内容提交会带下新许可——这正是 v50 本来就接受的行为（TD「仅许可变化不触发同步」）。同一棵树的约束仍然成立，只是那棵树是 tip。
- **上游删掉某个目录后，那一条会落成 `skipped`**（`missing_skill_md`），而不是按旧 revision 重建。同步表达的是「上游现在有什么」，这条符合预期，但和以前的行为不同。
- **大仓库需要放宽上限。** 232 MB 的包超过 `max-repo-bytes` 默认 64 MB、解压 280 MB 超过 `max-unpacked-bytes` 默认 256 MB；部署工作流因此新增两个可选变量 `SKILLMASTER_SYNC_MAX_REPO_BYTES` 与 `SKILLMASTER_SYNC_MAX_UNPACKED_BYTES`，默认值不变。要让 K-Dense 进来，必须显式把它们调到 268435456 / 536870912 以上。
- **每条仍要解一次包。** 232 MB 的包解 177 次约是分钟级的 CPU（不是内存：解包仍是流式的，只保留配置目录与许可文件）。再加「解一次到临时树」是下一次优化的方向，本轮不做。
- **暂时性失败也缓存整轮。** 限流（`rate_limited`）、超时、IO 失败与「仓库不可达」一样，只在第一次尝试时发生，该仓库本轮的其余条目直接拿到同一个原因。这是有意的：缓存的目的就是「一个仓库每轮只打一次」，若对限流放开重试，177 个条目会在额度已经用完时各打一次。下一轮会重试。
- **一轮的磁盘峰值**是同时打开的仓库包之和（每个仓库一个文件），22 个仓库按各自包大小合计约 300 MB；部署机 34 GB 可用，安全。
- `ContentSource` 的生命周期是给所有来源的：以后接 SkillHub 之类，如果有「一轮只取一次」的共享单元，也走同一对方法。
