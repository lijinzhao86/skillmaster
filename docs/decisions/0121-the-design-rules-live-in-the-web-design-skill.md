# ADR 0121 · 设计件那套规则搬进 web-design 的项目页

- **状态**：已采纳
- **日期**：2026-11-01
- **依赖**：[ADR 0076](0076-the-design-file-is-react-source.md)（决定 #6 被本条取代）；外部 skill `lijinzhao/web-design`

## 背景

2026-10-22 的设计稿迁 React 定了一条配套规矩（[ADR 0076](0076-the-design-file-is-react-source.md) 决定 #6）：新增 `design-react` skill，把「设计稿怎么写、怎么验、怎么搬进前端」写成后续每次改设计都要走的规则。它落成了仓库内 `.claude/skills/design-react/SKILL.md`，一个文件 185 行。

同一段时间，作者另有一个**通用**的网页设计 skill：`lijinzhao/web-design`，放在 SkillMaster 库里（远端、带版本号）。它有自己的层次——宪法、六步流程、门禁、参考库、系统库——其中**项目层**（`projects/`）专门留给「通用层不该写的、某个项目特有的东西」，一个项目一页、四块模板（系统库 / 参考库偏好 / 门禁追加 / 禁跑项）。这个抽屉一直是空的。

两者覆盖面重叠的方式不是内容重复，而是**层次错位**：`web-design` 回答「方向怎么定、门禁怎么过」，`design-react` 回答「这个仓库的设计件怎么改、怎么搬」。放在一起看，`design-react` 就是 `web-design` 缺的那张项目页。但两边从来没有互相引用过，所以一个任务里同时加载时，会出现两套措辞不同的门禁说法。

被否掉的选项：

1. **保持两份，靠 `dev-sop` 的链接串联**（就是今天的样子）。
2. **只把通用洞察上提到 `web-design`，项目页仍然空着**。
3. **在仓库里留一个指向远端的 stub**。

## 决定

1. **`design-react` 的内容整体并入 `lijinzhao/web-design` 的 `projects/skillmaster.md`**，仓库内 `.claude/skills/design-react/` 删除。
2. **并入的形状照 `web-design` 的架构**：前四节严格按项目层模板的四块；四块之外的项目做法（组装与构建、组件怎么写、复制到前端的清单、开工/交付检查）作为项目页的五～九节——项目层规矩允许「只做加法」，这些是不进通用层的项目机制。
3. **`design-react` 里唯一与通用门禁冲突的一条按「在案例外」记录**：`gates.md` 要求「无裸值（hex / px / ms 全走 token）」，而本仓库的颜色与字号走 token、**布局尺寸直接写 px**（设计件百余处、前端千余处）。项目页写明它只覆盖布局尺寸，不覆盖颜色字号时长，并禁止再新增裸色值。
4. **三处仓库内引用改为指向远端**：`design/README.md` 两处、`.claude/skills/dev-sop/SKILL.md` 一处，读法统一写成 `skmr skill read lijinzhao/web-design projects/skillmaster.md`。
5. **不保留仓库内 stub**。仓库里不再有叫 `design-react` 的 skill。

## 理由

**为什么不留两份。** 同一个事实不能有两个权威位置——这条是仓库自己的铁律（`.claude/skills/docs-architecture/SKILL.md` §2.3），09 月的审计就是为它开的。两份文件今天内容一致，没有任何机制阻止它们明天不一致：`design-react` 改一次构建命令，`web-design` 那边不会知道，反过来也一样。

**为什么是「搬进项目层」而不是「合进通用层」。** `design-react` 里九成是项目机制——`npm run build:console`、`console-states --only` 的十个组、`design/scripts/dom-compare.mjs`、`fixtures/` 的规矩、共享登录浮层住在 `src/shared/auth/`。这些放进通用层，等于让每一个用 web-design 的项目都读一遍 SkillMaster 的构建命令。通用层留的是「怎么做设计决定」，项目层留的是「这个仓库怎么落地」。

**为什么否掉「保持两份、靠 dev-sop 串联」。** 现在串得住，是因为两边都还没长。串联不构成约束——它只是两处文字里的一处链接，删掉或改掉不会有任何东西报错。

**为什么否掉「只上提通用洞察」。** 那样 `web-design` 的项目抽屉仍然空着，下次改界面时两个 skill 还是各缺一块：通用那边没有 skillmaster 的构建与检查，项目那边（仓库里）没有门禁与方向。合并之所以值得做，是因为抽屉本来就在那儿。

**为什么否掉「仓库里留 stub」。** stub 不解决问题，只把问题藏起来：它仍然要 `skmr skill read` 才能拿到规则，同样依赖远端与凭据；同时它让「仓库里有一份能读的规则」看起来还成立，于是没人会去确认远端那一版到底有没有上线。

## 后果

- **仓库的 SOP 从此依赖远端 skill。** `dev-sop` 与 `design/README.md` 指向的内容要 `skmr skill read` 才拿得到，这是需要凭据与网络的一步。谁 clone 了仓库、但没有 `skmr` 登录，能看到的只有 ADR 0121 这一句线索，拿不到具体规则。这是这次合并的主要代价，显式写下。
- **改规则要发版、要在网页上点上线。** `web-design` 的版本由作者在网页上发布，CLI 只能建草稿（`skmr version publish` 只在网页）。规则与代码不再在同一个 commit 里。
- **「无裸值」的例外第一次被写下来，它比通用门禁更松。** 项目层的规矩是「只做加法，不能更松」；这一条是记录在案的破例。边界（只覆盖布局尺寸、不许新增裸色值）与改正时机写在项目页 §五，不在这里复述。
- **ADR 0076 的决定 #6 被取代，其余五条不受影响。** 0076 的文件头会标出取代关系，正文不动。
- **「怎么搬进前端」的清单从此只有一处权威。** 那六步（复制文件、删演示层、接产品层、保留类名与 aria、补测试、请人看）在项目页 §八。
