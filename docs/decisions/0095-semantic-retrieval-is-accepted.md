# ADR 0095 · 接受向量检索；索引在发布事务里完成

- **状态**：已采纳
- **日期**：2026-10-25
- **依赖**：[ADR 0006](0006-search-server-side.md)（检索在服务端、可解释）、[ADR 0082](0082-public-and-private-with-my-library.md)（私域与公域同一套谓词）、[ADR 0084](0084-l1-search-extension.md)（本节取代其中「向量检索」的否决）、[ADR 0031](0031-submitting-and-publishing-are-two-actions.md)（提交与上线是两个动作）
- **取代**：[ADR 0084](0084-l1-search-extension.md) §理由里「**向量检索**（要独立信号与基础设施，先做可解释的关键词 + 标签）」这一条否决。0084 的其余决定（匹配面扩展到 `when_to_use` 与公开标签、多词取「且」、标签过滤在访问谓词内、不做标签权重）**继续有效**，本 ADR 不碰它们。

## 背景

0084 否决向量检索时，理由是两条：**需要独立信号与基础设施**，以及**可解释**。当时没有数据支持"向量值得这笔代价"，而关键词 + 标签的规则可回归。

v19 之前，2026-10-25 在真实的 33 个 skill 上做了一次标注实测（66 条按描述生成、人工过一遍的语义式问题 + 33–40 条名字式问题，`Recall@10`）：

| 查询集 | 关键词 | 向量 | 混排 |
|---|---|---|---|
| 语义式 66 | 0.73 | **0.92** | 0.91 |
| 名字式（33–40） | 0.95 | **1.00** | 0.97 |
| 合计 | 0.81 | **0.95** | 0.93 |

**这一版随仓库走的是 99 行的那一份**（66 + 33；spike 的 40 条名字式里有 7 条同义变体没有保存），用 `skillmaster-server/scripts/retrieval-eval.py` 复跑得语义式 **0.909**、名字式 **1.000**。
语义式那 0.92 与 0.909 差一个命中（61/66 对 60/66）；spike 的中间产物没有保存，**原因查不到，不猜**——本版基线以那 99 行为准。

0084 面对的第一个理由（"要独立信号"）被这组数字回答了：**信号就是用户自己的问题**，而关键词在口语问题上只有 0.73。第二个理由（可解释）没有消失，只是可以补——见 §决定 4。

同一次工作还有两个基础设施事实变了：目标 RDS 已确认提供 `pgvector` 扩展，而库里的量级（几十到几千条）用同一个 PostgreSQL 就够，不需要第二个数据存储。

## 决定

1. **接受向量检索，作为检索的第二条路，不替换关键词。** 关键词那条（0084 定义的匹配面与排序）一行不动；`semantic=false` 永远可用，它是退路而不是"融合"。
2. **只用纯向量，不做混排。** 实测里混排三组全输（0.93 / 0.91 / 0.97）：RRF 只看向对名次，弱的那条臂会用错误结果稀释强信号。保留两条独立的路，让调用方选，而不是合成一个分数。
3. **向量在发布事务里写，发布成功即已索引。** 事务提交才算发布成功；向量写失败就整笔回滚（指针、审计、向量一起），接口给 `503 semantic_unavailable`。**没有待办表、没有 worker、没有"发布成功但还没索引"的窗口。** 代价是发布要等一次 provider 往返，且 provider 不可用时发布不可用——退路是把语义开关关掉。
4. **可解释性由三件事补，而不是靠"看分数"**：
   - 每条结果带 `score`（余弦相似度，0–1）；
   - **低于阈值的行不返回**；
   - 整批为空时明确说"没有足够相关的 skill"，不拿 10 条凑数。
   语义检索永远有"最近的一条"，所以**沉默是它最危险的失败方式**——这三条是它的对冲。
5. **隐私边界：描述出境到百炼，由一个部署级开关控制。** 被送出的是已发布 skill 的 `name` / `title` / `description` / `when_to_use`，**不含正文与文件**（与 ADR 0006 的 L1 边界一致）。开关默认**关**；关掉之后不构造客户端、不发任何请求、检索退化为关键词，其余功能不受影响。查询文本**不进日志**（只记耗时、条数与 token 数）。
6. **一个 skill 一条向量，不存在"多版本向量"。** 被向量化的是发布时投影到 `skill` 行上的那四个字段——一个 skill 一个已发布文本。草稿不索引。
7. **可见性不在向量里复制。** 向量表没有状态列；检索时先由 skill 模块按可见性收窄候选集（集合小则枚举 id、在集合内取 top-N，集合大则过度取回后过滤），上下线与改可见性**不产生任何向量工作**。
8. **换模型是加法，不是迁移。** 模型名是向量表主键的一部分；换模型＝用新模型名算一遍、切读、删旧行。维度变化才是迁移。

## 理由

- **数据把"要不要"回答了，而且是逐项回答的。** 语义式 0.73 → 0.92 是这一版存在的理由；混排那三行则回答了"要不要合成"。没有这组数字，0084 的否决是对的——它的理由正是"还没有数据"。
- **发布与索引合成一件事，是为了不给产品留一个解释不了的故障。** 用户看到的"发布成功"必须意味着"别人搜得到"。分开做（待办表 + worker）能少一次等待，代价是一个几百毫秒的窗口，以及一整套常驻机制；而发布是人在浏览器里做的一次动作，不是热路径。仓库里已有同形的取舍——短信发送同样在事务里调外部服务，"没发出去就不算发"。
- **可解释不是"能解释分数"，而是"能回答没有"。** 一条 0.42 的相似度对人毫无意义；阈值 + 明确的无匹配才是产品能承诺的东西。
- **隐私边界用"索引什么"划，不用"存哪里"划。** 送出的是清单里的元数据，与 0006 的 L1 完全一致；正文和文件从未离开，这条边界没有因为换了个检索后端而移动。开关是部署级的而不是用户级的，因为默认状态必须是"什么都不发"。
- **两套状态永远会漂。** 向量表里如果存一份 `live/draft/offline`，上下线就得同步它，而同步不到的那天没有任何东西会报警。问 skill 模块是慢一点，但它只有一个真值。

被否掉的：**混排 / RRF**（实测不如纯向量，且让"为什么这条在前"变成两个不可比的分数相加）；**待办表 + 后台 worker**（多一套常驻机制，换一个一致性窗口；发布不是热路径，不值得）；**独立向量库（DashVector / Milvus）**（几十到几千条，同一台 PostgreSQL 够用，外部索引会变成第二份真相）；**把向量存进 `skill` 表**（`SELECT s.*` 是每一条列表与检索的共同底座，4 KB 的列会给全产品的读路径加税，也让换模型变成一次热表迁移）；**每版一条向量**（一个 skill 只有一个已发布文本，多这一维只有单值）；**索引草稿**（草稿不是谁能搜到的东西，且每次保存都要重算）。

## 后果

- 检索多了一条路：`GET /api/v1/skills` 增加 `semantic=true`，`skills search` 默认走它。关键词路径的契约（`limit` 公域默认 20、私域默认 50，上限都是 100，游标翻页）不变——语义在接口层是**显式开启**的，因为同一条路由还服务着两版之前的列表与翻页。
- **发布慢一次 provider 往返**（spike 实测约 350 ms）；批量发布按条累加。控制台沿用既有的"正在上线…"进行中态，不需要新画面。
- **百炼不可用时发布不可用**。退路是关掉开关；那条路要在运维手册里写清。
- 数据库要多一个扩展 `pgvector`；CI 与本地 compose 的镜像随之换成带扩展的版本。迁移账号需要能 `CREATE EXTENSION`（RDS 上要 `rds_superuser` 一档），上线前必须确认。
- 描述与 `when_to_use` 从此会离开本系统一次，**开关默认关闭**；打开是一个明确的部署动作。
- `Recall@10` 的达标线写进 v19 PRD（语义式与名字式**两组各自** ≥ 0.90），但**阈值不是常数**：它要按标注集的分数分布定，改评测集就要重新定。这一条没有"一次定终身"的版本。
- 0084 的"排序可解释"仍然成立，只是现在有两套排序；调用方用 `semantic` 选哪一套，而不是看到两套混在一起。
