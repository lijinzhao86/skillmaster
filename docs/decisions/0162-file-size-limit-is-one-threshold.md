# 0162 · 文件行数上限统一为 1,000 行

- **状态**：已采纳（取代 [ADR 0124](0124-file-size-limits-are-a-shrink-only-baseline.md) §决定 1 的分语言数值；基线机制不变）
- **日期**：2026-11-07
- **依赖**：[ADR 0124](0124-file-size-limits-are-a-shrink-only-baseline.md)（只减不增的基线）、[ADR 0122](0122-architecture-refactor-is-structural.md)

## 背景

ADR 0124 设了分语言 / 分种类的上限——页面 600、组件 400、通用源码 500、Java 类 500、Go 文件 600、CLI 主入口 300、测试 1,000——并用只减不增的基线让存量债显式化。

运行一个月后，这些线落在「一件正常职责再长一点就撞线」的位置。最近一次是 v50 的 `SyncPipeline`：它从 481 行长到 536，仍然只做一件事（同步编排），却被 `Guards` 拦下，只能为过检查把清单展开拆走。拆出来的类本身没问题，但触发它的不是「这个文件难读了」，是「它比 500 多 36 行」。

团队实际在意的界线是「一个文件是否已经很难读」，那更接近一千行，而不是五百行。

可选做法：A 保持分语言数值；B 统一抬到 1,000；C 取消检查；D 各语言只抬 Java。

## 决定

1. **所有种类统一 1,000 行**：页面、组件、通用源码、Java、Go、CLI 主入口、测试都按同一阈值；超过才失败。
2. **基线机制不变**：现有超限文件仍进 `scripts/file-size-baseline.json`，只减不增，`--update-baseline` 在 CI 中不可用。
3. **基线按新阈值重生成**：只保留仍超过 1,000 行的文件。

## 理由

- **B 比 A 简单。** 分语言的差别只有 100–300 行，换来的是每次新增文件类型都要再调一次表、每处文档都要抄一组数字；统一阈值一条就够解释。
- **B 比 D 一致。** 只抬 Java 会让「为什么 Java 能长到 1,000、Go 只能 600」变成一个没有产品含义的问题。
- **C 被否。** 拆完没有护栏就会长回去，这是 ADR 0122 已经证明的事。
- **500 的代价是具体的。** 为过检查而拆文件，拆出来的边界常常不是职责边界；本轮 `SyncPipeline` 的拆分恰好合理，但不能假设每次都合理。

## 后果

- 原本 600 / 500 / 400 / 300 的线不再有强制力；检查只在 1,000 行处报警。
- `.dev-sop/profile.md` 里「当前：页面约 600、组件约 400」一句需要同步改成 1,000——该文件只有用户能改，agent 只提议。
- `docs/current/rules.md` §五 已改为统一阈值。
- 基线从 35 条降到 12 条。这不是「债务还清」：只是阈值放宽后这些文件不再算超限，仍然长的文件照旧在基线里。
