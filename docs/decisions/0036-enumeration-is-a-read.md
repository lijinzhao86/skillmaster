# ADR 0036 · 枚举一个版本的文件是读取的一部分，而且由 CLI 给

- **状态**：已采纳
- **日期**：2026-10-07
- **依赖**：[ADR 0001](0001-server-authoritative.md)、[ADR 0005](0005-content-addressing.md)、[ADR 0031](0031-submitting-and-publishing-are-two-actions.md)、[ADR 0034](0034-skill-level-sharing.md)、[ADR 0035](0035-the-pin-lives-on-the-client-machine.md)
- **修订**：[`technical-design.md`](../versions/v1-hosting/technical-design.md) §4.6 里「`describe` 与 `show` 被本轮撤掉了」那段中关于 `show` 的一句（原文：枚举「在本地由普通的 `ls`/glob 承担，不是 skill 自己的动词」）。该段的其余部分与 ADR 0034 的正文四段都不受影响

## 背景

ADR 0034 那一轮把 `show`（详情 + 文件清单）从 CLI 撤掉了，理由不是它不好用，而是**它在协议里没有位置**：

> 远程缺的是「枚举」，而枚举在本地由普通的 `ls`/glob 承担，**不是 skill 自己的动词**。

那段还留了「先去掉，后面再加」。**那句话成立的前提是本地有目录可以 `ls`**——而它在这里不成立：

- **本设计没有本地副本**（[ADR 0001](0001-server-authoritative.md)：服务端是唯一真相）。没有副本就没有目录，没有目录就没有可 `ls` 的东西。
- **宿主加载 skill 时也不给清单。** 2026-10-07 对着装好的 CLI（2.1.292）核实过：`Skill` 的输出是**正文**，前面加一行 `Base directory for this skill: <目录>`——**只有目录、没有文件列表**，而且那一行只在 skill 真的带文件时才加。模型之所以能枚举，是因为那一行指向一个被解开的本地目录，它接着用 `Glob` / `Read` 去看。**给模型一个目录是宿主能做的事，我们做不到。**

于是「一个 skill 有哪些文件」在远程**没有任何东西承担**：正文里指向同目录文件的那些链接是唯一线索，而那是正文作者写没写的问题，不是这一版有什么的问题。

而清单**本来就在响应里**：§4.2 的详情接口按设计就给「详情 + 完整文件清单（零内容）」，每项带 relpath / URI / SHA-256 / 大小（MCP 的 Skills 扩展明确要求，理由是「清单让客户端无需下载即可枚举 L3」）。`invoke` 取的是同一份响应里的 `resources.body`，**清单到手后被丢掉**。

要回答的是：枚举该由谁给、挂在哪个权限下。

## 决定

1. **`skillmaster skill files <地址>[@版本]` 列出这一版的文件**：每个相对路径独占一行（那一行就是随后要传给 `read` 的东西），正文那一条与二进制那几条各带一句说明。**不印 `uri`、不印 digest**。
2. **它是一个读，不是第二个门。** 清单来自与正文同一个详情接口，走同一个授权（`ReadSkillUseCase` → `SkillRepository.permitted`），所以**能读这个 skill 的人才枚举得了**；无权者是**同一个 404**——不是 403（会确认它存在），也不是「200 + 空清单」。
3. **钉与 `read` 完全一致**：地址里的 `@版本` 优先，否则用 `invoke` 记在本机的那一版，两者都没有则按当前已发布版本，**并在输出里说出来**。
4. **不新增权限、不新增开关。** 没有「可枚举」这个位，也没有作者侧的开关；**共享时给 `viewer` 就够**——共享出去的是「能读」，枚举随着读走。
5. **`read` 落空时指路到 `files`。** `read` 是精确匹配，报错只说「没有这个路径」的话，唯一的出路就是猜名字。

## 理由

- **为什么枚举算读，而不是另一个权限。** 它够不到任何 `read` 够不到的东西：清单里的每一项，有权者本来就能用 `read` 一个不落地取走。为它新造一个权限位只会制造一种「读得到但数不出来」的中间态，而没有任何用户场景要求那种状态。
- **为什么不是把清单放进 `invoke` 的输出。** 那是同一份响应的两次呈现，代价是常见路径（加载正文、取一两个文件）每次都要多付十几行路径的上下文——而绝大多数任务用不到。宿主的选择正是这个形状：加载只给一行目录，枚举另外去做。
- **为什么不是继续不做。** 「后面再加」的条件已经出现：正文提到的路径是唯一线索，正文没提过的文件对本设计里任何客户端都等于不存在，而 §4.2 给客户端的承诺恰恰是「不必下载就能枚举 L3」。承诺写在那里、唯一那个客户端却从不显示它——这件事不该留给读者自己去发现。
- **为什么 `uri` 与 digest 不印。** 这一轮的前身（[ADR 0035](0035-the-pin-lives-on-the-client-machine.md)）刚把「让模型逐字符复现任意长串」定为要消灭的失败类型（分页令牌 191 字符、临时路径 79 字符、digest 71 字符），清单里那两串正是同一形状。定位一个文件需要的是**相对路径**——它与钉一起就够了。
- **为什么 `files` 而不是把 `show` 加回来。** `show` 是「详情 + 清单」两件事捆在一起，而详情那一半现在有了更好的去处：L1 卡片由 `list` / `search` 给，正文由 `invoke` 给。留下的是清单这一件事，所以是一个只说清单的动词。
- **为什么不做过滤 / 通配。** 一个版本的清单被 `IngestLimits` 封在 512 个文件以内，全列出来是几十行；先加一个模式参数，等于在还没有读者的时候先造一门语法。

## 后果

- **`files` 是 `show` 那一半的回归，`show` 本身不回来**：L1 由 `list`/`search` 给，正文由 `invoke` 给，文件清单由 `files` 给。
- **网关正文与 CLI 必须同一次改**：`metadata.platform_api_version` 从 `"7"` 到 `"8"`——与 [ADR 0035](0035-the-pin-lives-on-the-client-machine.md) 同一条约束、同一个理由（服务端每次启动都发布那份正文）。
- **清单里没有 digest，所以调用方无法自己核对字节。** 校验仍然发生在签发清单的服务端（清单里的 digest 来自内容寻址的存储，[ADR 0005](0005-content-addressing.md)）。**想自己核对的人今天做不到这件事**，如实记着。
- **枚举不覆盖草稿**：`files` 走消费面的详情接口，未上线的版本对它等于不存在（[ADR 0031](0031-submitting-and-publishing-are-two-actions.md)）。作者要看草稿的文件清单，那是作者面的事。
- **按内容检索（在一个版本里 grep）仍然没有。** 它是独立的一步，取舍另写一条；它与本条**共用同一把锁**（同样只够得到读得到的东西），但它是本设计第一个「服务端翻自己不下发的内容」的接口，值得单独记。
