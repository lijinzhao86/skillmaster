# ADR 0122 · 架构重构是结构性的，不是战术 DDD 重写

- **状态**：已采纳
- **日期**：2026-11-01
- **依赖**：[ADR 0123](0123-modules-publish-an-explicit-interface.md)、[ADR 0124](0124-file-size-limits-are-a-shrink-only-baseline.md)、[ADR 0125](0125-cli-splits-by-command-group-in-one-package.md)

## 背景

2026-11-01，v35 已实现、`main` 干净。服务端已经是模块化单体：12 个模块（M11 已退休）、`usecase` 编排层、`internal` 仓储，外加 ArchUnit 的环 / 分层 / 事务 / 内部包检查与表归属 lint。问题集中在三处：几个 god class（`SkillVersionService` 1,265 行、`TokenStore` 853 行、`VersionRepository` 866 行）、一处未写明的跨模块耦合（M7 依赖 M12 的 `Access` / `GrantRole` / `SkillMetadata` 等；其中 `Access` / `GrantRole` 后来被定为共享内核，其余类型在 v36 的发布清单里显式化）、以及 CLI 的 `main.go` 3,673 行与控制台两个页面 1,914 / 1,381 行。

产品负责人要求「更匹配 DDD、高内聚低耦合、模块可扩展、拆长文件」。面对三条路：

1. **全面战术 DDD 重写**：聚合根、领域事件、仓储接口、CQRS / Event Sourcing 全上。
2. **结构拆分 + 边界加固**：拆长文件、把跨模块依赖收成显式契约、补可执行检查。
3. **不做**。

## 决定

选 2。范围是 v36 的 P0–P4：护栏、CLI 拆分、控制台拆分、服务端 god class 拆分、边界加固与收口。**不引入聚合根、领域事件、CQRS / Event Sourcing，不换框架，不改对外接口、表结构与界面。**

## 理由

**为什么否掉 1。** 服务端的战略 DDD 已经做了：限界上下文按模块切、用例层划定跨模块事务、仓储在 `internal`、ArchUnit 已经在 CI 里卡边界。当前大量业务是事务脚本 + 仓储，这对这个规模是合适的；把它改写成富领域模型，是一次 3.8 万行主代码 + 2.5 万行测试的重写，而对外能力边界不变。业界对战术 DDD 的共识也是「只在核心子域的本质复杂度值得时才用；CRUD / 通用子域用事务脚本是诚实的选择」。收益主要是「更像教材」，代价是真实回归风险。

**为什么否掉 3。** 长文件已经在影响维护与 AI 改动：`main.go` 一个文件装 10 组命令，控制台两个页面超过仓库自己定的 600 行上限，服务端三个类超过 850 行。这些不是审美问题，是「改一处要在两片作用域之间来回找」的具体成本。

**为什么是「结构 + 边界」而不是「只拆文件」。** 只拆文件不改变依赖方向：M7 仍然依赖 M12 的类型，`api` 仍然可以直接调模块服务，新代码仍可以绕过模块契约。拆完文件，边界问题原样留着，下一次还会长回来。

## 后果

- v36 的验收是「行为不变 + 对外契约不变 + 行数只减不增」：所有既有测试通过、对外契约不变、行数上限只减不增。
- 服务端会先保留 `SkillVersionService` 等门面（facade），把实现拆到协作者；这是有意的过渡，避免一次性改 76 处调用点。门面是否长期保留，由 P4 的模块接口规则回答。
- 这次不做的事会以「不做」写进 v36 PRD：战术 DDD、新框架、表结构、接口形状、界面重画、测试重写。
- 重构不是一次性清扫：P0 的护栏（行数基线、模块接口白名单）负责阻止回涨；没有护栏的拆分会在几个月内回到原样。
