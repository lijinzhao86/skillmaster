# ADR 0016 · 密码用黑名单，不用组合规则

- **状态**：已采纳
- **日期**：2026-10-02
- **依赖**：[ADR 0013](0013-phone-login-and-username-slug.md)
- **相关**：正文里「密码策略保持只看长度」那句话的**字符集范围**已被 [ADR 0017](0017-password-printable-ascii-only.md) 收窄（密码限 ASCII 可打印字符）。黑名单这条决定不受影响。

## 背景

M01 的密码策略原先只有一条：**长度 8–72 字节**，外加「不得等于用户名或手机号」。字符类要求被明确否掉，理由写在 `PasswordPolicy` 的类注释里：它们把人推向 `Password1!`、远离任何够长的东西。

2026-10-02 提出：密码是不是该像 Apple 账户那样，至少要求一个大写、一个小写、一个特殊字符和一个数字？这必须正面回答，因为参照物是一个用户会拿来比较的真实产品。查证结果：

1. **Apple 的注册表单确实要求四类字符。** `account.apple.com` 注册页的「密码要求」列了五条：至少 8 个字符、至少 1 个数字、至少 1 个大写字母、至少 1 个小写字母、至少 1 个特殊字符（2026-10-02 现查）。Apple 自己的支持文档在「改密码」处写的是「八位以上，含大小写字母和至少一个数字」——两处口径不一致，以注册表单为准。
2. **规范明确反对。** NIST SP 800-63B 与 OWASP 的 Authentication Cheat Sheet：不要组合规则；最小长度 8（推荐 15+）；允许全部可打印字符，含空格与 Unicode；**并且要求（must）用一份泄露/常见密码黑名单**；不做定期改密。

两边都是权威，却给出相反的建议。差别不在「谁更安全」，而在**代价落在谁身上**：Apple 有巨大的客服体系来接「我想不出该敲哪个符号」这类问题，也有全线 2FA 兜底；这两样我们都没有，而在线爆破是有天花板的（同手机号 15 分钟 10 次）。

## 决定

密码策略保持「只看长度」，**新增一份常见密码黑名单**，并把「用户名 / 手机号加后缀」这一族从「只判相等」扩到「判派生」。命中与否一律回同一个码 `too_common`。

- 数据是 **vendored 的 SecLists**（`Passwords/Common-Credentials/10k-most-common.txt`，MIT，© 2018 Daniel Miessler，10001 条，sha256 `68782d6a4a19a4768d5f15dd66bd534e7a33055cc755411e33f16d18c50fdcce`），逐字节入库。`PasswordBlocklist` 的类注释记来源与校验和，`PasswordBlocklistTest` 断言这个校验和，`WebRegistrationIT` 断言端点真的查了它。
- 派生规则：**以 handle 开头、其后只剩数字**（`demo-user123`）算命中；手机号只要**出现在密码里**（`a13800138000`）就算命中——11 位数字连排不可能是巧合。
- 前端镜像**只镜像能在本地判定的派生规则**，不镜像黑名单：几千条数据下到浏览器，只为省一次**不花短信费**的往返，不划算。这是有意留下的缺口，写在 `validation.ts` 里而不是省略掉。

## 理由

**被否掉的「照 Apple 加四类字符」，否的是收益，不是它能不能用。**

- 它挡住的是 `password`、`12345678` 这类最弱的密码——而**黑名单挡得更彻底**、对用户零成本，并且正是 NIST 的 must。
- 它挡不住用真名、生日、拼音拼出来的密码。那是中文用户最可能的弱选择，一份英文泄露语料覆盖不到，字符类规则同样覆盖不到；能覆盖的是「手机号 / 用户名派生」这条规则——而手机号做登录名正是 [ADR 0013](0013-phone-login-and-username-slug.md) 定的模型，所以这条对我们**最相关**。
- 代价那一侧是实的：被迫加符号的人常常得到 `Password1!`，而它本身就在黑名单里；被拒的人会去改一个更短更好记的东西，这是组合规则已知的反效果。另外「必须含特殊字符」会稳定产出一类客服问题（手机键盘上打符号要切两下），我们没有接这类问题的能力。

**钱的这一侧花在长度和「别用所有人都用的」上，而不是花在类别上**：在线爆破受退避限制，真正的暴露面是库被拖走后的离线爆破，而那时 16 位随机字母数字（≈95 bit、不含任何特殊字符）远胜一个凑出来的 `Password1!`。

## 后果

- **新增 issue 码 `too_common`**，前端码表随之加一条；`PasswordPolicy.problemWith` 多一个参数（黑名单），调用点三处、构造点两处。
- **向后兼容。** 登录从不校验密码形态（实测：`/web/login` 传空密码得到 401 `invalid_credentials`，不是 400 字段错），`PasswordPolicy` 只在**注册**与**重置**被调用。所以存量账号不受影响，**不需要重置任何人的密码**。
- **名单会过期**，而且它是一份 2018 年的语料。更新它要**同时**更新类注释里的校验和与 `PasswordBlocklistTest` 里的那一条——测试故意让这件事有摩擦，因为这是一份安全数据，换掉它应当是一次有意识的动作。本文不因换名单而失效：换数据不是推翻决定。
- **覆盖的真相要写在明处。** 10001 条里只有 **2087 条长到能被提交**（其余 4–6 位先被 8 字节下限拒掉，是死重量而不是漏洞）；整份名单偏英文语料，中文场景的高频弱口令只覆盖一部分。**产品侧不要对外承诺「我们挡住了所有弱密码」**——挡住的是「所有人都在用的」和「与你自己的手机号/用户名有关的」这两类。
- **一条实现上的教训，值得单独记**：派生规则写成「去掉密码尾部数字再与 handle 比较」是**错的**——`u3f0a` + `123` 会被漏掉，因为剥离后缀会吃掉 handle 自己的末位数字。正确写法是「以 handle 开头，其后只剩数字」。这个是**集成测试用随机 handle 抓出来的**（`randomUsername()` 生成 `u` + 16 位十六进制，天生于数字结尾），手挑的 `demo-user` 永远抓不到。已写进两侧的注释与测试。
