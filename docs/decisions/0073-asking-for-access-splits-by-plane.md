# 0073 · 申请访问按平面分：申请、撤回、读自己的走 API；批准与拒绝留在网页

- **状态**：已采纳
- **日期**：2026-10-21
- **所属版本**：[`v10-cli-lifecycle`](../versions/v10-cli-lifecycle/README.md)
- **依赖**：[0052](0052-a-request-is-not-a-grant.md)（申请不是授权）、[0061](0061-what-a-credential-may-do-to-versions.md)（判据是改不改变调用者读到什么）、[0047](0047-permissions-are-a-ladder.md)（权限是一条梯子）、[0039](0039-api-key-defaults-and-their-edges.md)（写蕴含读；「按方法分 scope」是 `SecurityConfig` 的规则，不在 0039）

## 背景

[0052](0052-a-request-is-not-a-grant.md) 把「开口」做成了一个对象：看得见 skill 的人可以申请一档，`管理` 及以上与所有者在**设置 › 协作者**里批准或拒绝。那时它只回答了「产品里有没有这件事」，没有回答**哪条平面承接其中的哪些动作**——五条动作（申请、撤回、读自己的申请、列待批的申请、批准 / 拒绝）当时都在网页那条路上。

v10 要让 agent 只凭 CLI 走完生命周期，其中一步是「我还不够，去申请一档」。于是同一个问题第二次出现，形状与 [0061](0061-what-a-credential-may-do-to-versions.md) 面对版本时一模一样：**凭据能对访问申请做什么，到哪里为止？**

摆上桌的选项：

| | 做法 | 被否的理由 |
|---|---|---|
| A | 五条动作都上 API：申请、撤回、读自己的、列待批、批准 / 拒绝 | 批准改变的是**申请人下次读到的档位**——[0061](0061-what-a-credential-may-do-to-versions.md) §决定 1 的判据正好落在它上面。凭据自己能批，等于「申请 → 批准」一个人跑完，[0052](0052-a-request-is-not-a-grant.md) 要的那道人为确认就没了 |
| B | 申请也留在网页，CLI 不承接 | agent 卡在「想提交，但没有写入档」这一步，只能回去找人；而「找人」正是 0052 想从产品之外搬进产品里的那件事。申请本身不改变任何人读到什么，凭据做它没有风险 |
| C | **申请、撤回、读自己的申请上 API；批准 / 拒绝与待批列表留在网页** | 采纳 |

## 决定

1. **申请、撤回、读自己的申请在消费面**：
   - `POST /api/v1/skills/{namespace}/{name}/access-requests`
   - `GET /api/v1/skills/{namespace}/{name}/access-requests/me`
   - `DELETE /api/v1/skills/{namespace}/{name}/access-requests/me`

   这三条路由落在消费面，因为它们服务的正是「看得见这个 skill 的人」——那也正是消费面的入口条件。
2. **对一条申请的「决定」——批准、拒绝——以及待批列表只在网页面**（`/web/skills/…`，会话 + CSRF）。API 平面**没有这三条路由**。批准要同时落下一行 `skill_grant` 并删掉申请行；前者按 [0034](0034-skill-level-sharing.md) / [0047](0047-permissions-are-a-ladder.md) 早就是 `管理` 凭据能做的事（`POST /api/v1/skills/{ns}/{name}/grants`），本决定把**「处理某一条申请」**留在网页，而不是把「授予」重新收回去。
3. **只读密钥申请不了，这是有意的，不是漏洞。** `/api/v1/**` 的 scope 按方法走：`POST` / `DELETE` 要 `skills:write`，`GET` 要 `skills:read`（`SecurityConfig.java:221-224` 的 matcher 配 `Scopes.requiredForMethod`（`Scopes.java:73`）；「写蕴含读」见 [0039](0039-api-key-defaults-and-their-edges.md) §决定 2）。申请会写下一行**给批准者看**的东西，所以它是一笔写；不为它开按路由的例外——那会让 scope 的含义按地址变动，并留下「为什么这里只读凭据能写」这种要逐个回答的问题。持只读密钥的人仍可在网页上申请。
4. **建 skill 落在作者面路径族的根**：`POST /api/v1/author/skills`，命名空间不进路径（只写调用者的个人命名空间）。这是路径族**唯一一条没有 `{namespace}/{name}` 的写路由**，理由是这个动作发生时那个名字还不存在；而消费面已经有自己的创建路径（整包提交的 `POST /api/v1/skills`，见 §理由），把第二种创建形状也塞进去，会让那一族同时承接「提交一份内容」与「从零起一个作者对象」两件事。例外写在接口表旁边，不靠读者自己发现。
5. **`--role` 的目标档位由服务端判**（严格高于当前、五档之内、所有者不能申请），CLI 只做用法校验；服务端的拒绝原样翻成中文，不另造一套判断。

## 理由

**为什么申请不算「改变调用者所读」。** 申请之后，申请人自己读到的仍是原来那些，skill 的可读性对任何人也没有变——[0052](0052-a-request-is-not-a-grant.md) 的标题就是这句话。真正改变可读性的那一刻是**批准**，它新建一行 `skill_grant`。所以按 0061 的判据切，切出来的线在「提交一条申请」与「处理某一条申请」之间——不是「授予」本身（授予早就是 `管理` 凭据能做的事，见 §决定 2），也不是「网页」与「CLI」之间。

**为什么读自己的申请也在 API 上。** 它只回答「我还在等哪一档」，不泄露任何别人的东西，也不需要 `admin`；不给它，agent 就无法知道自己前一步提交的申请还在不在，只能反复申请。

**为什么待批列表不跟着上 API。** 它读的是**别人**的申请与别人当前的档位，是管理视图的一部分；它和批准 / 拒绝在同一屏、同一个判断里。把读给它、把写留下，只会让凭据多知道一些它做不了任何事的信息，而管理视图的形状（分页、申请人当前的档位）又会被钉进一份对外契约里，以后改那一屏就要改契约。

**为什么建 skill 单开一条根路由，而不是 `/api/v1/skills` 上再加一个 POST。** 消费面已经有一条创建路径——整包提交的 `POST /api/v1/skills`（[0034](0034-skill-level-sharing.md) §后果），它做的是「把一份已有内容放进一个命名空间」。空起步的 create 是另一件事：**调用者手上还没有内容**，但服务端仍按 [0070](0070-creating-a-skill-creates-its-first-draft.md) 在同一个事务里建出 skill 与带根 `SKILL.md` 的第一份草稿。它是作者对本人命名空间的一次创建，所以归作者面那一族。**名字还不存在**这一点让它只能落在族的根上——这是路径形状对一个真实事实的让步，不是随手的选择。

**被否掉的：让 CLI 在申请之后顺便批准自己。** 那是选项 A 的一种走法，理由同上：0052 的整条 ADR 是在回答「为什么不直接把档位给自己」，任何绕过那道确认的路径都回到那个问题。

## 后果

- **API 平面多三条消费面路由**，没有新增 scope，也没有新增档位要求（能看见即可）。字段与错误码的权威在 [`v10 technical-design.md`](../versions/v10-cli-lifecycle/technical-design.md) §接口。
- **批准 / 拒绝仍然只有网页**：以后要把它们交给凭据，得另开一条 ADR，不能塞进一个 scope。
- **`skill request --status` 只能读到「我自己的 pending」**：被拒之后那一行就没了，[0052](0052-a-request-is-not-a-grant.md) §后果 已经接受「不留理由」，本版也不补拒绝历史。
- **只读密钥的用户会看到一句 403**，句子只说「这次请求需要 `skills:write`」（`InsufficientScopeAccessDeniedHandler`）——它不认识「申请」这个业务概念。**「申请是一笔写、因此只读密钥做不了」这句话由 CLI 帮助与 README 先说**，免得在运行时才发现。
- **建 skill 的那条根路由是作者面路径族的一个具名例外**，以后往这一族加路由时不要把「族里都有 `{ns}/{name}`」当成前提。
