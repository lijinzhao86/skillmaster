# 0135 · 草稿可以从一版原样复制出来，内容唯一性不再约束草稿

- **状态**：已采纳
- **日期**：2026-11-04
- **取代**：[ADR 0064](0064-a-draft-may-change-a-published-version-may-not.md) §决定 5 中「写后 digest 与同一 skill 的另一行相同时拒绝」适用于草稿的那一半
- **依赖**：[v44 PRD](../versions/v44-cli-read-write-contract/prd.md)、[ADR 0012](0012-addressing-and-version-pinning.md)（内容寻址）、[ADR 0055](0055-drafts-have-a-required-name.md)（草稿名）、[ADR 0101](0101-the-cli-never-deletes-files.md)（状态文件原地写）

## 背景

今天一份草稿只能在**第一次内容改动**时诞生：`CreateDraftFromVersionUseCase` 读底稿、在内存里应用第一处改动，再把行与文件一起插入。它不能先建一份原样草稿，原因是硬的——原样复制会带着底稿的 digest，而 `UNIQUE (skill_id, digest)` 拒绝同一 skill 下两行同内容。

这带来三个后果：

- 「建草稿」不是一个独立动作。想先建草稿、再分几次写，做不到；想从线上版本起一份草稿但暂时不改，也做不到。
- 建草稿只能挂在 `write` / `edit` / `rm` / `mv` 的 `@new` 上，于是「第一次写」与「建草稿」永远绑在一起。agent 每轮 `submit` 或 `@new` 都顺手留下新草稿（[TODO](../current/TODO.md) 的「不重复造草稿」）。
- 控制台的编辑器同样把底稿放在内存里，等第一次改动才落行；这不是实现偷懒，是模型限制。

可选的四条路：

| | 方案 | 问题 |
|---|---|---|
| 1 | 允许零文件的草稿 | 一版至少要有一个文件；空行会进入编辑器、下载、check 的每一条路径 |
| 2 | 把 `state` 纳入唯一键 `(skill_id, digest, state)` | 只允许「一份草稿 + 一份已上线」同内容；再建第二份草稿仍然失败 |
| 3 | **唯一约束只约束非草稿行** | 草稿之间、草稿与底稿之间都可以同内容 |
| 4 | 建草稿时塞一个占位文件 | 写了没人要的内容，digest 说谎，还要事后删 |

## 决定

1. **建草稿是一个独立动作**：`draft create` 从底稿整版复制文件（默认线上版本，`--from` 指定别的），内容不变；`write` / `edit` / `rm` / `mv` 不再接受 `@new`，只为起稿存在的 `--from <版本>` / `--name` / `--note` 一并退场。
2. **`UNIQUE (skill_id, digest)` 改成只约束非草稿行的局部唯一索引**（`WHERE state <> 'draft'`）。草稿可以与任何一行同内容，包括另一份草稿。
3. **写草稿不再因内容重复而拒绝**：`VersionSubmitter.submitFromBase` 与 `VersionDraftEditor.commitContent` 里的 `content_already_exists` 检查移除。非草稿行之间的唯一性由数据库索引与提交/上线路径继续保证。
4. **CLI 在新建前先看已有草稿**：`draft create` 与 `skill submit` 在「我自己（`submitted_by = 我`）在这个 skill 下还有未上线草稿」时默认拒绝，列出草稿码与下一步；隐藏的 `--new` 才新建。不做交互确认。控制台不受这条限制。
5. **CLI 写命令仍然必须带 `@<版本码>`**：不提供裸地址写入，也不做「自动选最新草稿」；多份草稿下，版本码是唯一不会写错的身份。

## 理由

**为什么不是零文件草稿。** 复制底稿总会得到至少一个文件（没有线上版本时，底稿是 skill 行的最小 `SKILL.md`），所以「至少一个文件」不需要被推翻。零文件草稿会让编辑器、下载、check 各多一条「空版本」分支，收益为零。

**为什么不是把 state 纳入唯一键。** 它只解决「草稿 vs 线上」一种碰撞；`draft create` 连跑两次仍然会撞。用户的真实需求是「同一份底稿开两条路」，那要求草稿之间也不受内容唯一性约束。

**为什么占位文件不行。** 它把一份没人要的内容写进版本，digest 描述的是占位符而不是作者想写的东西；事后再删又留下孤儿 blob。这是把一个模型问题伪装成一个内容问题。

**为什么只放宽草稿。** 已上线/已下架/已丢弃的行按 digest 唯一，是内容寻址与发布幂等的基础（ADR 0005 / 0012）。草稿是「正在编辑的那一份」，不是对外地址；它可以暂时等于任何已有内容，直到被提交或上线。

## 后果

- **同一 skill 下可以有两行同 digest**。任何仍假设 `(skill_id, digest)` 唯一的查询都要限定到非草稿；`version list` 会显示相同摘要的两行，这是模型允许的状态，不是 bug。
- **草稿写路径不再返回 `content_already_exists`**。控制台编辑器本来就在第一次改动时落行，不会因此少一个提示；`submit` 一个本地目录仍保留自己的「内容已存在 → 返回已有那一版」幂等语义。
- **上线一份与线上同内容的草稿**会被非草稿行的唯一索引挡住；上线路径要把约束冲突翻译成 409，而不是 500。
- **`--new` 是速度限制，不是墙**：agent 看到报错后可以自己补上。要真正的人工闸门就得有交互终端，而那会让 agent 卡住（v44 PRD §问题 7 已记）。
- **控制台与 CLI 行为分叉**：网页可以自由建多份草稿，CLI 默认拦。这是有意的——网页上的点击是人的动作，CLI 的循环是 agent 的动作。
