# 0069 · `.skillmaster/metadata.json` 是传输旁路，不是内容

- **状态**：已采纳
- **日期**：2026-10-21
- **依赖**：[0005](0005-content-addressing.md)（内容寻址与幂等）、[0031](0031-submitting-and-publishing-are-two-actions.md)（提交与上线分开）、[0055](0055-drafts-have-a-required-name.md)（草稿有必填名称）
- **这一条修订 [0055](0055-drafts-have-a-required-name.md) 的决定 1 的口径**：版本必须有名称，来源可以是显式参数**或包里的元数据**，而不是每次提交都必须由人当场给出

## 背景

一版 skill 带两样不属于内容的作者面事实：版本名称（必填，1–40 码点）与说明（可选，0–200 码点）。下载只给文件的话，导出的 zip 就丢掉了这两样；把它们塞进 `SKILL.md` 的 frontmatter 会改变内容身份，导回时会变成一个新 digest——往返一次就多出版本，正好打穿幂等。

v9 需要一个**随包走、但不进内容**的位置。

## 决定

1. **保留路径 `.skillmaster/metadata.json`。** 下载时它作为 zip 的最后一个条目写出；上传时它被剥出、解析成版本字段，**不进 manifest、不进 digest、不计入 512 文件 / 16 MiB**，文件列表与 `grep` / `cat` 都看不到它。
2. **schema 只有两项**：`schema_version`（整数 `1`）与 `version`（对象，只允许 `name` / `note`，字符串）。长度与空白规则不在解析器里做，交给 [`VersionLabels`](../../skillmaster-server/src/main/java/com/skillmasterai/usecase/VersionLabels.java)——那是全系统唯一一份口径。
3. **请求里的非空值优先**；空字符串与没给同义；两者都没有名称 → 400 `draft_name_required`。
4. **内容相同就幂等，元数据不覆盖既有版本。** 同一份内容再提交时，格式校验照常先跑（坏元数据仍具名拒绝），但既有那一版的名称与说明**不被包里的值改写**——内容身份优先，元数据只在新版本产生时使用。
5. **判别式一句话**：这个路径上的文件若是顶层带 `schema_version` 键的 JSON 对象，就按元数据处理（随后的每条 schema 规则都有自己的具名原因）；否则按「保留路径上的内容」拒绝（`reserved_path`），绝不静默当元数据丢掉，也绝不静默当内容收下。
6. **写路径的目标拒绝**：`write` / `mv` / `cp` 的目标落在保留路径 → 400 `reserved_path`；**删除与改名的来源不拦**（既有数据要能清理）。这条判定不进 `SkillPaths.check`——那个函数被解压与删除/改名共用，放进去会让 sidecar 永远传不上来、旧数据也删不掉。
7. **既有版本里已经有这个路径时，原样保留。** 下载照样成功，那个文件作为普通内容进包、不再渲染 sidecar；从它新建草稿也把它带过去（不静默丢文件、不把旧 skill 锁死在不能编辑）；把这样的包再导入 → 具名拒绝，并说清怎么改（**除非那条历史文件本身就是判别式的形状**：顶层带 `schema_version` 的 JSON 对象会被当作元数据剥掉、导入成功——否则平台自己导出的包就永远不能再导入）。

## 理由

**为什么不是 frontmatter。** `SKILL.md` 是内容，它的任何字节变化都改变 digest；把版本名称写进去，改名就成了发新版本，往返一次多一版。元数据必须**不进清单**，这是内容寻址的直接推论，不是便利选择。

**为什么请求优先。** 包里带的是「上一次的名字」，请求带的是「这一次想叫什么」。显式总是更近的意图；空串与没给同义，是因为 CLI 没法把「我要清空名字」表达成一个合法请求（名称必填）。

**为什么幂等时不应用元数据。** 内容相同意味着服务端认出「这就是那一版」；这时改名或改说明会让一次重放悄悄改写历史行的作者面字段。内容身份优先，元数据只属于新版本。

**为什么旧数据保留而不是清洗。** v9 之前这个路径只是普通文件名，可能是用户自己的文件。拒绝原版本、或复制时静默丢弃，都比保留更糟：前者把旧 live 版本锁死在不能编辑，后者改了用户看不见的内容。

## 后果

- 两个提交用例的名称解析多一层：请求 → 元数据 → 缺省；`SubmitResponse` / CLI 的 `--name` 因此可以省略。
- 拒绝按入口各站一层：上传侧是 `invalid_upload` + issue `reserved_path`（另加元数据 issue 家族 `metadata_unknown_field` / `metadata_schema_unsupported` / `metadata_field_invalid`），写路径是顶层 400 `reserved_path`；本 ADR 只新增 `reserved_path` 这一个顶层码（另两个新码 `skill_deleted` / `skill_already_exists` 属于 0071 / 0070）。
- 64 KiB 只是 reader 给这个路径的内部余量，不是产品上限，也不产生用户可见的错误码；真正过大的包是既有的 `too_large`。
- 一条已知边界：含该路径的历史版本不满足「下载后原样再导入」这条往返承诺；例外写在 v9 PRD 做 #9 与验收 #16。
