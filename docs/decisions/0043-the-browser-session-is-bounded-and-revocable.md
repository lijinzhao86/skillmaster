# 0043 · 浏览器会话有两条尺子，而且设备可撤销

> **状态**：已采纳
> **日期**：2026-10-15
> **用词**：正文里说的是「踢掉」——那是当时的话。产品与设计件上的名字是**「退出」**（[`design/voice-spec.md`](../../design/voice-spec.md) §二把暴力动词列进了禁用类别，参照产品那边叫 *Revoke*）。**决定本身一个字不变**，只是同一个动作在正文与界面里叫了两个名字。

## 背景

浏览器会话今天是**一条尺子**：`spring.session.timeout: 7d`，而它是**空闲**超时，并且**滑动**——每来一个请求就重新数 7 天。于是天天用控制台的人**永远不会被要求重新登录**，而这条规则里没有任何地方说得出「它最久能活多长」。没有绝对上限，也没有设备列表。

**为什么这件事在 v2 之后才浮上来**：会话本身早就在服务端（[0014](0014-browser-session-via-spring-session.md)），所以它一直是可撤销的——只是没有任何入口。而 v2 让控制台里最重的一件事变成了**签发一把 API key**：那是一件**活得比会话更久**的东西。于是一台被摸到的、开着控制台的浏览器，代价不再是「读几个页面」，而是「多一把长期凭据」。今天要结束它，唯一可用的开关是**重置密码**——它把所有会话一起结束，代价是要求人换一个密码，也就是让一次「我怀疑有人用过我的电脑」付出一次「我改密码」的代价。

摆在面前的是四个选项：

1. 什么都不做（继续滑动 7 天）
2. 只把空闲改短（例如 1 天），仍然滑动、仍然没有上限
3. 短空闲 + **绝对上限**
4. 在 3 的基础上，让人**看得见并踢得掉**自己登录过的设备

## 决定

1. **两条尺子**：空闲 **24 小时**、绝对 **7 天**。绝对的那条**从登录那一刻算，不滑动**。两者都部署可配，并且**启动时拒绝「绝对 < 空闲」**——照 `TokenPolicy` 已有的做法（与 [0042](0042-the-expiry-setting-is-a-cap.md) 同一个道理：一条永远不可能先到的尺子等于没有尺子，而静默禁用是最坏的形状）。
2. **登录设备可见、可撤销**：控制台列出当前账号的全部登录会话——设备/浏览器、登录地址、登录时间、最后活动、以及「当前这台」。可以踢掉一台，也可以「踢掉其他所有设备」。踢掉**立即生效**，那台设备的下一个请求就要重新登录。
3. **列表里不出现会话 id**：会话 id 等价于凭据（[0014](0014-browser-session-via-spring-session.md) 的 cookie 就是它）。对外用一个随机会话编号标识一台设备。

## 理由

**为什么否定「什么都不做」**：滑动的空闲超时对「天天在用」的人等价于**永久有效**，对「在别人机器上登录过一次」的人等价于**一周有效**。同一条规则在这两个方向上同时做错——对一直在用的人太松，对已经离开的人也太松。

**为什么否定「只改短、不加绝对上限」**：短空闲管的是「多久不碰」，管不住「一直在被碰」。一台被持续使用的会话，再短的滑动窗口也会被无限续下去。**绝对上限是唯一能保证「一个被遗忘的会话一定会死」的那条尺子**；两条尺子量的是两件事，缺一条就少一种保证。

**为什么否定「1 天」**：控制台是**天天要开的界面**。把重新登录的频率推到每天，代价不会消失，只会转移到别处——更弱的密码、写在便签上的密码、让浏览器替人记着。**摩擦加在主界面上，安全是净亏的。** 7 天是「人想得起来的单位」（一周，不需要记日期），也是参照产品在同一个位置选的数（GitLab 的 `session_expire_delay` 默认 10080 分钟）。而 24 小时的空闲尺子正好覆盖真正要防的那台机器——**借来的**那台：办完事走了，最长一天之后它自己死掉。

**为什么「能踢掉」是这条决定的一部分，而不是一个附加功能**：因为**寿命不应该是唯一的防线**。1 天挡不住「你今天忘了登出」——人走了、机器没锁，会话照样活到明天；而远端踢掉**立刻生效**，与寿命长短无关。两者的关系是：**有了能踢，默认值才可以从容地放宽到 7 天；如果撤不掉，那么设成 1 天还是 7 天都只是在给一扇关不上的门调门缝。** 这也是把两者放进同一个决定的原因——单独做任何一个都达不到目的：只缩寿命是把人挡在门外却还留着钥匙，只加列表而寿命仍是滑动 7 天，则那扇门本身还开着。

**为什么空闲不用参照产品的 2 小时**：那个数是给**未登录**会话的，防的是登录页上那把临时凭据，与「已经登录的人多久不碰就该重来」不是同一个问题。把两个数混为一谈，会得到一个让人每天重新登录、却并没有更安全的系统。

**为什么不做「登录时问一句这台设备是不是共用」**：那会把判断交给一个当下没法判断的人（他多半不知道），而且它是一次额外的设计交付。设备列表把同一件事变成了**事后能纠正**的：不问，但随时能踢。少一个问题，多一条出路。

## 后果

- **每天用控制台的人，每周要重新登录一次**（绝对上限先到）；**周末没开过控制台的人，周一要重新登录**（24 小时空闲先到）。这是这一版明确接受的代价，换来的是「一个被遗忘的会话一定会死」。
- 会话属性里会多出一份**设备描述**，含 User-Agent 与登录地址——**两者都算个人信息**。列表是给人看的，因此它必须有清除路径：踢掉那台设备即随之删除（会话属性随会话行级联删除），重置密码即全部删除。**这一条要在实现与界面里都成立，不能只写在文档里。**
- 「踢掉其他所有设备」是一个**破坏性动作**，界面上要照撤销/续期那套**先问后果、再给两个答案**，而不是弹一个「确定吗」。
- 这一版**不改权限模型**：会话仍然是「账号全权、不带 scope」，key 只能收窄。那条规则今天靠「浏览器这一侧不执行 scope」这个**缺席**成立——把它写成一条显式规则是**另一件事**（属于架构轴），不在这一版。写下这一句，是为了让下一个往 `/web` 加路由的人不至于以为权限模型在这里被改过。
- 一个账号最多同时留几行会话：**不设人为上限**。两条尺子已经把它限住了——被遗忘的会话最多活 24 小时，而常用的浏览器只占一行（同一浏览器里反复登录是复用同一行、只把会话 id 转一下）。理由与推论见 [`v3-sessions/technical-design.md`](../versions/v3-sessions/technical-design.md) §开放问题。
- 这条决定**不动** CLI 那条路的凭据：它今天是一对 OAuth 令牌，「不自动续期」要求那条路先改成「铸一把 key」（[0040](0040-api-key-in-the-cli-now-the-browser-path-later.md) §决定 3）。两者是同一件事的浏览器半边与终端半边，但**只有浏览器这半边能单独交付**。
