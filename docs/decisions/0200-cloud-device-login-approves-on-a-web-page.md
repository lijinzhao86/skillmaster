# 0200 · 云端设备的登录：批准在网页上，执行在设备上

> **状态**：已采纳
> **日期**：2026-11-14
> **依赖**：[0043](0043-the-browser-session-is-bounded-and-revocable.md)（浏览器会话可见可撤销）、[0185](0185-credentials-default-to-a-file.md)（凭据默认存文件）
> **取代**：[0028](0028-cli-uses-a-fixed-loopback-port.md)（固定回环端口）、[0044](0044-the-cli-serves-desktops-and-servers.md) §决定 1（服务器上走 API key）

## 背景

CLI 的登录要面对四类终端，它们的差别不在系统，而在**批准的人坐在哪台设备前**：

| 终端 | 批准时人在哪 | 这台机器能做什么 |
|---|---|---|
| 桌面 | 就在这台机器前 | 开浏览器、接收回环回调 |
| 云桌面 | 看着这台机器的屏幕 | 开浏览器、接收回环回调 |
| 无浏览器的云设备（云主机、容器、云端沙箱、云电脑） | 手机或另一台电脑 | 只能发 HTTPS 请求 |
| 无人值守（CI、常驻服务） | 没有人 | 只能发 HTTPS 请求 |

[0044](0044-the-cli-serves-desktops-and-servers.md) §决定 1 给出的答案是：桌面走浏览器回环，服务器走 API Key。这条划分把第三类逼进了一个新用户几乎不会走的路——去控制台「API 密钥」页新建、复制、回到终端粘贴。而这条路本身也有代价：key 会经过对话与历史，云设备常常是所有 agent 共享的一台电脑（[Grok Bot](https://docs.x.ai/grok-bot/computer-and-apps) 明写「command-line credentials are shared」），一把 key 等于全账号共用。

2026-11 的调研看了三家同类的云端 agent：WorkBuddy 用「服务端发授权链接、客户端轮询换令牌」，无回调端口；Grok Bot 用已有账号登录、运行时秘密走 Vault 与 Secure Form；千问 Go 用 OAuth 授权、可随时撤销。**三家都没有让用户为登录去申请 API Key**，共同形状是「授权端与执行端分离」：人在手机或浏览器上同意，设备只持有令牌。

## 决定

1. **设备批准是唯一的主登录流程。** CLI 发起后打印一条**一次性链接**；用户在任何有浏览器的设备上打开它、登录并批准；CLI 轮询取回凭据。批准页就是控制台现有的「授权请求」屏，**不让用户抄写或输入任何短码**。
2. **自动弹浏览器是尽力而为，不是流程前提。** 有启动器就尝试，失败或没有都不影响；链接必须始终打在屏幕上。
3. **只保留一个分支：没有人在时用 API Key。** 不再按「这台机器有没有浏览器」「用户能不能操作浏览器」分流——这两件事探测不到，也不改变用户要看到的指示。
4. **回环登录退役。** CLI 不再监听 `127.0.0.1`，固定回环端口不再使用；[0028](0028-cli-uses-a-fixed-loopback-port.md) 随之被取代。
5. **撤销沿用现有面。** 一次设备登录出现在控制台「登录设备」里，可单独撤销，「退出其他所有设备」也覆盖它。

## 理由

**为什么不做一个 App。** App 是第二套客户端、第二套授权、第二套存储，而它解决的问题（在没有浏览器的机器上完成登录）用一张网页就能解决。三家里只有千问 Go 把批准放在 App 里，那是因为它整个产品就在 App 里；我们不是。

**为什么不让用户输短码。** 短码是给「设备显示不了链接」的场景准备的。这里 CLI 与 agent 都能把整条链接交到用户手上，短码只剩摩擦——八个字符要念、要抄、还会抄错。它也不比链接更安全：能拿到短码的人本来就能拿到链接，真正的保护在一次性、十分钟的有效期，以及只留在 CLI 手里的那段设备码。

**为什么不让用户搬凭据。** 「本机登录后导出、拷到服务器再导入」确实能绕开无浏览器，代价是多一台机器、凭据落成一个文件经手、撤销面说不清是哪一份。它适合作为没有网络时的兜底，不适合当主路径。

**为什么不靠宿主注入凭据。** WorkBuddy 的沙箱会替连接器注入令牌，那是最顺的形态；但它要逐个宿主适配，不能当作通用解。通用解必须先成立，宿主注入以后可以叠在上面。

**为什么继续把 API Key 留给无人值守，而不是彻底取消。** CI 和常驻服务没有人在场，设备码的前提「有个人能点批准」不成立。两种凭据对应两种事实，不是同一个东西的两种说法。

**为什么连桌面的回环也退役。** 两套流程各自最优，合起来会漂：一套改了另一套不知道。回环在沙箱与容器里已经造成过真实故障——`open` 被拦、回调永远不来、命令等满五分钟。设备批准在桌面上的体验是「自动弹浏览器 → 已登录状态下点一次批准 → 两秒内终端完成」，与回环的差距只有一次点击，换来的是全终端一条路径。

## 后果

- **CLI 不再起回环监听**，`internal/auth` 的回调路径删除；固定端口那套注册与逐字比对不再被第一方客户端使用。
- **服务端多一份待批准状态**：短码与设备码、过期、一次性、错误次数、轮询限速。批准写下的仍是现有的授权行，撤销仍是「登录设备」。
- **一次性链接会被转发**：拿到链接的人可以用自己的账号批准，让等待的那台设备登进他的账号——不会让他拿到别人的账号，但会让登录结果不是发起人。缓解：链接一次性、十分钟过期、页面明确说「别转发」、批准页显示设备名与来源地址、CLI 完成时打印账号（不对就 `logout`）。页面的 GET 不改变任何状态，IM 的链接预览抓一下不会消耗令牌。
- **凭据寿命沿用浏览器会话的两把尺子**（24 小时闲置、7 天绝对）。服务器每周重新批准一次是刻意选的，嫌烦再单独放宽——那是另一个决定。
- **API Key 仍是无人值守的唯一凭据**，两条撤销面（登录设备 / API 密钥）继续分开，不要混为一谈。
