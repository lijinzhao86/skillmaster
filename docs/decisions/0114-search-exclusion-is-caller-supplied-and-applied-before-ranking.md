# 0114 · 搜索的排除项由调用方提供，在服务端排序之前施加

> **状态**：已采纳
> **日期**：2026-10-30

## 背景

agent 在一次任务里会反复搜索（规则段要求「没命中换说法再查一次」）。每次返回都带完整描述，于是同一份说明被搬进上下文多次。实测：`b8f8d834` 会话 9 次调用、21 个不同 skill、13 个地址重复出现（最多 4 次）。

要让第二次搜索不返回已经看过的东西，「看过的」这份清单必须来自某处。三个选项：

1. **CLI 在本地过滤**：收到结果后按地址去掉重复。
2. **服务端记住「这个账号最近返回过什么」**：客户端什么都不用传。
3. **调用方把看过的地址随请求传上去，服务端在候选集里减掉**。

另外还评估过「不写代码，只改规则段」：上下文重复照旧，只是提醒 agent 注意。

## 决定

- 排除项由**调用方提供**：`skills search --exclude <地址[,地址…]>`，请求里以重复参数 `exclude` 传递。
- 服务端在**候选集、排序与分页之前**施加：语义路径从 `admissibleIds` 里减掉再近邻排序；字面路径把排除作为取页窗口内的谓词（多取 `排除数 + 1` 行，过滤后切页，游标指向实际返回的末行）。
- 服务端**不记忆**任何「已返回过」的状态；同一条查询在同样的请求下结果一致（幂等）。
- 地址解析不到（不存在 / 看不见）时**静默忽略**；格式非法或数量超过 50 是 400。
- CLI 只解析、校验、转发；不读本机历史，也不做客户端过滤。
- 结果非空且没带 `--exclude` 时，CLI 在**首行**给一句提示。

## 理由

**为什么不是客户端过滤**：语义检索没有分页（`next_cursor` 恒为 null）。客户端排掉几条，这一页就少几条，调用方没有任何办法补满——只能再调一次，正好回到要解决的问题。服务端在候选集上先减后排序，返回的才是「没看过的 top-N」。

**为什么不是服务端记忆**：那会让同一条查询变成「只给新的」，搜索不再是幂等的读；状态跨 agent、跨机器共享，另一个 agent 会拿到它从没见过的「新的」；也没有自然的边界来「忘掉」。这与服务端保持无状态请求/响应的既有取向冲突。

**为什么不用规则段代替**：规则段随 CLI 二进制发布，v27 起 CLI 不再更新用户文件里那段说明，老用户根本拿不到；而且它是用户自己的指令文件，塞命令参数属于把细节焊死在一个没人再维护的地方。提示放在命令输出里，随二进制发布，永远和命令一致。

**为什么首行**：Claude Code 对**成功**命令只内联前约 30,000 字符，超出部分落盘、内联只给「文件路径 + 前 2,000 字符预览」；agent 又常把搜索输出接 `| head`。尾部的提示在这两种情况下都看不到，而它要影响的正是「下一步做什么」。

## 后果

- API 多一个重复参数 `exclude`（最多 50 个，`namespace/name` 形状，不带版本）；响应形状不变。
- CLI 多一个 flag、一段帮助、一条前置提示；`skills list` 不接受它。
- 排除**不改变**排序分数：被排除的只是从候选里消失，留下的顺序仍是原来的相关度。
- 调用方忘了带 `--exclude` 时行为与今天完全一致——这是一个显式的优化，不是默认行为的变化。
- 服务端需要为用户给的地址做一次只读解析（slug → namespace id，name → skill id）；解析不到的地址被丢掉。
- `skills list` 的同类处理留到下一版；本版不碰它。
- **`skills search` 的 stdout 现在以一行提示开头**，v13 §3 的「卡片第一行是地址、卡片之间不混其它内容」在 `skills search` 上被这一版取代（`skills list` 不变）。提示用全角括号、一眼不是地址；代价是任何把「非缩进行」一律当地址的消费方要跳过它——这一版选择接受，因为提示被截掉就等于不存在（见上一条理由）。地址仍在提示与可能的 `--limit` 夹取说明之后，卡片行本身一个字节没变。
