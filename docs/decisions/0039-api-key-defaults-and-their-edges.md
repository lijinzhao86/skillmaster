# ADR 0039 · API key 的缺省值与它的边界

- **状态**：已采纳
- **日期**：2026-10-15
- **部分取代**：[ADR 0038](0038-default-credential-is-an-api-key.md) 的 §决定 3、§决定 4，以及 §后果 里的「失去『盗窃会被发现』」那一条。**0038 的正文保持提交时的样子不动**——它记的是当时为什么那么选，那正是它的价值；本文改的是它提交之后被重新定过的四处，收法按仓库纪律走「新增一条、不改旧文」
- **依赖**：[ADR 0038](0038-default-credential-is-an-api-key.md)（第一方的默认凭据是用户自己签发的 API key）。**本文不动那个决定本身**，只动它的缺省值与边界
- **未改动**：[ADR 0021](0021-opaque-tokens-not-jwt.md)（不透明令牌、撤销立刻生效）——它连同 0038 的其余部分一条不改

## 背景

0038 与本文同一天写定，它把「第一方的默认凭据是 API key」定下来了，并在 §决定 3 里写下有效期**缺省 365 天、照 GitLab 的做法**。定稿 [`v2-credentials`](../versions/v2-credentials/prd.md) 的过程中，四件事被重新核过，而其中三件的结论与 0038 写下的相反：

1. **参照产品的「365 天」不是独立的一个数，它挂着一整套提醒。** 核实过它自己的树：没有显式指定时它的创建路径填 `max_expiration_lifetime_in_days`（`app/services/personal_access_tokens/create_service.rb`），而文档写着「an expiry date of 365 days from the current date is applied」（`doc/user/profile/personal_access_tokens.md`）；同一份文档的 "Personal access token expiry emails" 一节写着**到期前 60 天 / 30 天 / 7 天各发一封邮件**。**提醒才是那个默认值的前提。** 而本产品**没有邮件通道**（0038 §决定 11 把邮件提醒排在范围外）——也就是说，「照它的做法」这句话里被照抄的是那个数，没被照抄的是让那个数成立的那套东西。
2. **「只写」不是一个有意义的权限组合。** 0038 只写了「默认最小」，没说勾了写要不要补上读。
3. **部署开关该不该溯及已有的 key**，0038 没有写。
4. **「失去轮换检测」被 0038 整条买掉了**——它把这条代价写清楚了，但一条也没买回来。

## 决定

1. **界面预选 90 天**（可以另选），有效期做成**部署可配**（关掉则新 key 可以不过期），而**配置只约束新建，不溯及已有的 key**。
2. **写蕴含读，在签发时补进库里那一行**：勾了 `skills:write` 就在签发时自动带上 `skills:read`。界面上仍然是两个勾，第二个要显式选。
3. **续期的有效期按签发默认值重算，不继承旧的那个日期**；**已撤销的 key 不能续期**。
4. **补两条便宜的审计信号**：一把 key **第一次从一个新地址被使用**，以及**一把已撤销的 key 再次出现**，各记一条。

## 理由

- **为什么预选 90 天而不是 365 天。** 因为 365 天在参照产品那里是**有提醒托着**的（上面 §背景 1），而我们没有那个通道：一年之后 N 台机器会在同一天**同时静默失效**，而此前没有任何人被告知过——这正是这个产品最想避免的一种失败。**90 天是启发式起点，不是依据**：引擎里没有任何数据支持它。它短到能给一次泄漏封一个季度，长到不会让「贴一次、到处用」这件事每个月重来一遍。**将来有了通知通道，这个数该往上调**（参照产品正是这么做的：它有通道，所以敢设一年）——这一句写在这里，是为了它下次被改时有人知道它当初为什么是 90。
- **为什么写要蕴含读，而且补在签发时。** 参照产品有一张明确的 ability map（写仓库蕴含读仓库、`api` 蕴含全部），理由是人不会认为「能写但不能读」是一个有意义的权限组合。不定这一条，就会造出一把连 `skill list` 都做不了的「只写」凭据——而错在词表，不在用户。**补在签发时而不是改鉴权层**：这样库里那一行就是真相，不会出现「实际权限比声明的多」这种要看两处才知道的结果；而 M3 的鉴权链一行不用动，0038 §架构里「M3 不改」那条才立得住。
- **为什么配置不溯及已有的 key。** 参照产品在这一点上是相反的：它把上限调低会**撤销**超期的令牌。**改一个部署开关不该悄悄弄死别人正在用的凭据**——那些 key 是在旧上限下合法签出来的。
- **为什么续期要重新定日期。** 续期换出来的是一把**全新签发的**凭据，所以它拿的是签发的默认有效期。这不是风格问题：验收 1 要求终端在 key 过期时把那句话**指向控制台续期**，而把旧日期搬到新串上仍旧是过期——那条指向就落空了，而控制台没有任何别的地方能改一个有效期。参照产品的 `rotate` 同样给新令牌重新定日期；它另有一个「保持原有效期」的开关，我们的界面没有那个开关，所以不实现。**已撤销的不能续期**与参照产品一致（它那边是 `Token already revoked`）：撤销过的东西没有可延续的。
- **为什么是「两条审计」而不是每请求记录。** 每请求的记录不是审计信号，那是 `last_used_at` 的事，而它已经按陈旧窗口节流了。这两条信号各花一次写入，买回的是「一把静态凭据被人捡走去用」这一类里最便宜就能看见的那一半。

## 后果

- **0038 描述的这四处不再是当前设计。** 「有效期缺省 365 天」「scope 默认最小（只有这一条）」「失去『盗窃会被发现』（整条买掉）」现在分别是 90 天、写蕴含读、只买回一半。**0038 的其余部分完整有效**——为什么换形态、为什么是 API key 而不是 access token、为什么 `logout` 只删本机、为什么不做组织拥有的 key，一条都没变。
- **那个数字的权威位置是本 ADR §决定 1。** 版本文档复述它时必须连限定一起复述：「界面预选 90 天、可另选、部署可配、配置只约束新建」。**单独一个「90 天」是半句话**，而半句话正是 §2.3 那次事故的形状。
- **「失去轮换检测」只买回一部分。** 两条审计信号覆盖不到「被人从同一个地址慢慢地用」——那种用法一次审计都不会触发。所以这条仍然是代价，只是不再是一句空话。
- **有效期短了，续期就成了日常动作。** 那是「贴一次、到处用」要付的税，而它比「一年之后集体静默失效」便宜——但它确实是成本，尤其在没有提醒通道的前提下：控制台是用户唯一会知道「快到期了」的地方（[`prd.md`](../versions/v2-credentials/prd.md) §范围 第 8 条因此要有那一格统计）。
