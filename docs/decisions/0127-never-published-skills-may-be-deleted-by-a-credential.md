# 0127 · 从未上线的 skill 可以由凭据删除；页面命令先报权限

- **状态**：已采纳
- **日期**：2026-11-01
- **部分取代**：[0046](0046-deleting-a-skill-happens-in-the-browser.md) §决定（撤掉 API 平面的删除路由）——对「从未发布过任何版本」的 skill 不再成立；[0126](0126-page-only-actions-open-the-page.md) §决定 4 里「API 平面仍然没有这九个动作的路由」对删除不再成立。两份 ADR 的正文按原样保留。
- **实现注**：作者面实际新增三个字段（`owned`、`offline`、`ever_published`）——预检要判「是不是所有者」「有没有下线」「有没有上线过」，三个都读同一次作者页。正文 §决定 4 说的「一个增量字段」是 `owned` 这个起点，其余两个是同一次读的补充；§后果说的「服务端新增两处」实际是三处（作者页三字段、窄删除入口、V31 投影与发布侧并发保护）。删除语句读的是投影列 `skill.ever_published_at`（`recordPublish` 写、V31 从 `first_published_at` 回填），不是直接读 `skill_version`。§决定 5 的「`browse` 以下照常打开」按实现细化：作者面读不到时改读消费者面，**档位不够才拒绝**；档位够或不涉及档位时照常打开，并仍会说明「没能预检」（作者面没答，版本状态等事实未知）。两处都答不出时同样打开并说明。**正文按原样保留**。

## 背景

[0046](0046-deleting-a-skill-happens-in-the-browser.md) 当年**撤掉了** `DELETE /api/v1/skills/{namespace}/{name}`，理由是：删除的力量来自「把一个 skill 从所有读者手里拿走」，这股力量不该随凭据的寿命长在某个自动化里；而且「换一个凭据就能删」会留下两种答案。

现在有两件新事实。

**一是一个从未上线过的 skill 没有读者可失。** 它一个版本都没有发布过（所有版本行的 `first_published_at` 为空），发现面要求「published + online + 未删除」（[0082](0082-public-and-private-with-my-library.md)），调用者读不到它。按 [0061](0061-what-a-credential-may-do-to-versions.md) 的判据——**改不改变调用者读到什么**——删它和「丢弃一份草稿」是同一类：不可逆，但不从任何人手里拿走东西。0046 的判据没错，它当时面对的是「任何 skill 都能删」，而这一类当时没有被单独拿出来。

**二是误传的清理是真实的日常。** agent 建错名字、传错内容、试验完忘了收，这些 skill 大多根本没上线。逐个打开网页点删除，是把一件可脚本化的事交回人手；这也正是 [0081](0081-every-console-operation-has-a-cli-command.md) 要避免的那种欠账。

**三是页面命令的死路。** CLI 的页面动作（`version open`、以及 0126 新增的那些）只拼地址、开浏览器，不问档位。一个 `write` 档位的人敲 `version publish`，先被带到页面，再由页面说「你没有权限」；agent 更糟——它会把「页面打开了」当成交接完成。

## 决定

1. **新增一条窄的删除入口**（API 平面，动作形状），三条同时成立才删：**owner**、**从未发布过任何版本**（该 skill 的全部版本行 `first_published_at` 为空）、**未删除**。条件写在**同一条 `UPDATE … WHERE`** 里，不存在「先查后删」的窗口。**控制台那条路不变**：上线过的 skill 仍在网页上由人确认删除——这一条只关凭据那一侧。
2. **拒绝的形状沿用现有不泄露规则**：看得到但不够档 → 403；看不到 → 404；看得到、是 owner、但上线过 → 409（带自己的错误码，句子指向网页）。删除仍是软删。
3. **CLI `skill delete` 要 `--yes`**：不带它只打印后果与完整命令、退出非 0；带了才发请求。形状与 `version discard` 相同（[0056](0056-dangerous-actions-are-confirmed-in-a-modal.md) 的同一判据）。
4. **页面动作命令先读一次作者页再决定**：作者页返回调用者的 `rung`，并新增一个**增量字段 `owned`**（因为今天 API 平面把 owner 也报成 `admin`）。CLI 按「这个页面的动作要哪一档」判断：不够就**不打开**，说清档位并给出地址；够就打开。
5. **判定不了就不拦**：没有本机凭据、请求失败、或 `browse` 以下（作者页读不到）——照常打开页面，并写明没能预检。浏览器会话与本机凭据是两条路（[0040](0040-api-key-in-the-cli-now-the-browser-path-later.md)），预检失败不该让「只想打开页面」的人更差。
6. **`skill open` / `version open` 纳入同一套预检**；`skills pending` 结尾的提示不再断言「你去点上线」。
7. **同意屏跟着说真话**：`skills:write` 那行补上「从未上线过的可以删」（设计件先改，再同步两处产品页）。

## 理由

**为什么这一条不违反0046：** 0046 的力量论证成立的前提是「这个 skill 有人能读到」。从未发布过的 skill 没有调用者能读到；删它不改变任何人的下一次调用。判据仍是 0061 的那一条，只是把它用在了一个此前没被单独拿出来分类的子集上。

**为什么条件必须在服务端的一条语句里：** 客户端先读「有没有上线过」再发删除，中间协作者上线一版，就会删掉一个刚上线的 skill。而且客户端的判断可以被旧版本、被手写的请求绕过。条件只能和删除本身同生共死。

**为什么判定字段是 `first_published_at`：** 上线后再下架的版本 `state` 是 `revoked`，不是 `published`。用 `state = 'published'` 判断，会把「上线过、后来下架」误判成「从未上线」——这是这一类里后果最重的一处错误，要靠一条「上线 → 下架 → 尝试删」的用例钉住。

**为什么预检用服务端的回答而不是 CLI 自己算档位：** CLI 只需要一张「这个页面的动作要哪一档」的表，而「你是哪一档」「这一份是不是你的」都问服务端。表写错了，最坏是提示不准——真正执行的地方（服务端）仍然按自己的闸拒绝；权限表不会因此多出第二份权威。

**为什么判定不了不拦：** 拒绝一次打开，等于替一个可能有权的人做决定。预检是「能提前说就提前说」，不是新增一道闸。

**被否掉的：** 新开一个 `skills:delete` scope（又变成「换凭据就能删」，0046 已经否过）；CLI 先查后删（竞态且可伪造）；让 CLI 自己判断档位（第二份权限表）；不改同意屏（0046 的原话：沉默只有在确实做不到的时候才算实话）。

## 后果

- **0046 与 0126 各有一处被取代**，正文保留；新代码路径以本条为准。
- **同意屏文案要改**：`design/src/shared/auth/` 先改，再同步 `CliSignInPage` 与 `ConsentPage`；走设计检查并由人看。
- **服务端新增两处**：作者页的 `owned` 字段、一条窄删除入口；两者都要有自己的测试（含「上线 → 下架 → 删」「并发发布」）。
- **CLI 新增一张档位表**与预检路径；退出码沿用 [0087](0087-cli-exit-codes-are-a-public-contract.md) 的四种，不够档位是 1（命令写对了，事情不是它做的）。
- **名字仍然不释放**：删除后同名创建得到 `skill_deleted`，只能 restore；批量清理后想同名重传的人会撞上，输出里要说清。
- **以后新增页面动作**：CLI 侧要同时交代「要哪一档」，这条成为页面动作的交付条件。
