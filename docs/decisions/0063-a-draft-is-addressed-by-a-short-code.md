# 0063 · 版本由短码寻址，地址里不写状态

- **状态**：已采纳
- **日期**：2026-10-20
- **依赖**：[0004](0004-opaque-id-primary-key.md)（不透明 id 是身份，状态是属性）、[0055](0055-drafts-have-a-required-name.md)（草稿的身份与名称）
- **修订**：[0055](0055-drafts-have-a-required-name.md) 里 `draft:<row id>` 的**拼写与长度**——id 仍是那一行的身份，只是从 26 个字符的 ULID 换成 8 个字符的短码，地址也不再带 `draft:` 前缀。**该 ADR 正文四段不改**，改动记在这里。v6 的 PRD 与 TD 里同一条拼写由本条取代。

## 背景

v6 让草稿有了稳定地址 `draft:<skill_version.id>`，`id` 是一个 26 个字符的 ULID。当时有两个理由：草稿没有版本号，内容还会变，唯一不动的是行 id；`draft:` 让地址一眼看出「这是一份草稿」。

v7 把 CLI 的文件读写加进来之后，这个地址需要出现在**网页上、可复制**。于是两件事同时暴露出来：

1. **26 个字符加上前缀是 32 个字符**，作为给人读、给人核对的标识太长。
2. **`draft:` 把状态写进了地址，而状态会变。** 一份草稿被发布之后，`draft:<id>` 指向的是一条 `published` 行——地址开始说假话。v6 已经为此写过一条「钉过期」的处理（读的时候提示「已经上线」），那是在为地址里的一个错误前提做补偿。

## 决定

1. **`skill_version.id` 的生成方式改为 8 个字符的短码**：Crockford base32（没有 I / L / O / U），40 位，来自 `SecureRandom`。
2. **地址是 `namespace/name@<短码>`，没有状态前缀。** 地址只表达**身份**；草稿、已发布、已下架、已丢弃是同一行的不同状态，不是不同的地址。状态用查询回答。
3. **作者面按 id 解析，任何状态都可以**（可见性按档位：草稿要 `write`+，已下架与已丢弃要 `maintain`+）。**消费面不接受短码**——已发布版本的对外地址仍是版本号或 `sha256:` 摘要；短码是作者面的行标识，不是消费地址。
4. **旧行保持 ULID，不迁移**；解析接受 8 位短码与 26 位 ULID 两种长度。旧拼写 `@draft:<ULID>` 在过渡期继续接受，**规范输出不再带前缀**。
5. **唯一性由主键保证**；插入撞上已有 id 时换码重试（主键冲突会中止 PostgreSQL 事务，重试必须在**新事务**里换码重来）。因此 `insertIfAbsent` 的 `ON CONFLICT` 必须点名 `(skill_id, digest)`——不带目标的 `ON CONFLICT DO NOTHING` 会把一次 id 碰撞误判成「内容重复提交」。
6. **短码只给 `skill_version`**：`skill.id`、`app_user.id`、`namespace.id` 与它们的解析不动。
7. **网页显示并复制的是地址**：草稿 `namespace/name@<短码>`，已发布 `namespace/name@1.2.3`（无名为 `@sha256:…`）。复制到的整串 CLI 直接可用。**作者面另显示这一行的版本码（行 id）与复制**；调用档没有版本码。
8. **发现地址的入口已经存在**：`skillmaster version list <地址>` 已按名称、版本号、说明、提交人搜（`--query`），按状态筛（`--status`），并分页（`--limit` / `--cursor`）；每行第一段就是可复制的完整地址。不新增重复的搜索命令。

## 理由

**为什么地址里不写状态。** 状态会随动作改变：草稿 → 已发布 → 已下架，或草稿 → 已丢弃。身份不会。把状态写进地址，就等于要求「地址在状态变化时也正确」——它做不到，于是要么地址变成谎话，要么状态变化时必须换地址。后者与「草稿的地址一生不变」直接冲突。**ADR 0004 已经把这条分界放在身份模型里：不透明 id 是身份，状态是属性。地址跟着身份走。**

**为什么是 8 个字符。** 40 位，空间约 1.1×10¹²。有主键约束兜底，撞了重试，所以要看的是「每次插入撞上的概率」≈ n/S：100 万行时约 0.00009%，几乎不会重试。6 个字符（30 位）在百万行时约 0.1%，开始看得见重试；8 位是「足够短」与「几乎不重试」的平衡点。

**为什么不是行号。** 行号把内部计数暴露成对外地址：它的含义是插入顺序，包含已发布版本，不是「第几个草稿」。地址一旦发出去，这个误读就固定了。短码没有可被误读的含义。

**为什么不是 snowflake。** 它把「短」与「分布式唯一」绑在一起，而我们只需要前者；为此要引入 worker id 与时钟纪律。40 位随机 + 唯一约束 + 重试效果相同，机制更少。

**为什么不是别名。** 两列意味着两个身份：哪一个是真正的 id、哪一个进地址、旧行回填哪一个，每个问题都要在文档与代码里再答一遍。让 id 自己变短，这些问题不存在。

**为什么消费面不接受短码。** 已发布版本已经有两个公开身份——版本号与摘要；再加一个 id 就是第三种别名，而它没有任何新能力。接受它还会让「调用者用哪个地址」变成三选一。作者面需要 id，是因为草稿没有版本号；消费面不需要。

## 后果

- **混合格式**：`skill_version.id` 一列里同时有 26 位 ULID 与 8 位短码。所有校验、测试与文档都要接受两种；`Ulid.isValid` 不能再被当成「是不是一个版本 id」的判据。
- **解析**：`SkillAddress` 增加「8 位 Crockford」这一种 id 形式，接受两种长度；作者面允许，**消费面拒绝**（码形钉在消费面上是 404，与任何解析不出的后缀同答案）。旧的 `draft:` 前缀作为输入兼容。
- **状态变化不再换地址**：草稿发布后，同一个 `@<短码>` 仍指向那一行；作者面按状态与档位给出可见的结果，写命令要求 `state = draft`，否则说清「它已经是 @1.2.3」或「已丢弃」。不再有「地址说自己是草稿、行已经不是」这种矛盾。
- **插入**：`insertIfAbsent` 的冲突处理要改；id 冲突与摘要冲突分开，前者换码重试，后者返回已有版本。
- **响应与网页**：作者面对草稿的 `pin` 变成 `@<短码>`（不再带 `draft:`；旧行仍是不带前缀的 ULID）；网页草稿单版页显示完整地址与复制按钮；**草稿页的 `?version=` 随之变短，已发布页仍是版本号或摘要**。
- **CLI 要跟着改，不是零改动**：`version list` 打印的已经是服务端给的 `pin`；但 `invoke` 今天读的是消费面的 `Name` / `Digest`，本机 `pins.Pin` 也只有这两个字段——草稿钉要经作者面取到 `pin` 并记进本机，`read` / `files` 的钉表示随之扩展。`version list` 的搜索与分页不新增。
- **v6 文档**：PRD 与 TD 里 `draft:<id>` 的拼写由本条取代；它们不改写历史，读到时以本条为准。
- **其他表的 id 不变**：若要「所有主键都短」，那是一场涉及全部外键的迁移，不属于本条。
