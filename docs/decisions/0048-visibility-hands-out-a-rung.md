# 0048 · 「公开」是把梯子的某一档交给所有人

- **状态**：已采纳
- **日期**：2026-10-17
- **所属版本**：[`v5-skill-management`](../versions/v5-skill-management/README.md)
- **依赖**：[0037](0037-visibility-has-two-states.md)（可见性只有两态）、[0034](0034-skill-level-sharing.md)（可见性管「任何人」，授权管「某个人」）、[0047](0047-permissions-are-a-ladder.md)（权限是一条梯子）
- **收口**：[0037](0037-visibility-has-two-states.md) §后果 最后一段留下的那条待写的取舍——「控制台演示件照此实现：权限页上是三档……『公开 · 只能调用』要的是**一个新权限位**……那是另一条待写的取舍」。**该 ADR 正文四段保持原样。**（引号里是 0037 的原话，所以那里用的是它当时的档名「公开 · 只能调用」；本版叫「公开 · 调用」。**改名发生在设计件里，不在 0037 里**——`design/README.md` §可见性只有两态 那一节把两个值写成「公开 · 调用 / 公开 · 浏览」。两个名字指同一个东西。）

## 背景

[ADR 0037](0037-visibility-has-two-states.md) 把 `visibility` 收成两个值，并明确说「公开之后别人能做什么」**是另一个问题**，由权限回答。它同时如实记下：控制台演示件里那一页摆的是**三个**选项——`私有` / `公开 · 调用` / `公开 · 浏览`——并且指出这需要「一个新权限位」，而那个位当时还不存在。

[ADR 0047](0047-permissions-are-a-ladder.md) 之后它存在了。于是这条决定要回答的只剩一件事：**「公开」与那条梯子是什么关系？**

摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | `visibility` 三个值：`private` / `public-invoke` / `public-browse` | 它把 0037 刚刚收掉的那条轴重新打开一个口子：`private` 与另外两个值之间是**质变**（能不能被外人碰到），另外两个值之间是**量变**（够得到多少）。写成同一个枚举的三个取值，读的人要自己发现这件事，而「可见性有几态」这个问题就又有两个答案了 |
| b | **两态可见性 + 一个「陌生人拿到哪一档」** | 采纳 |
| c | 只用一条梯子，`visibility` 那一列删掉，「所有人」当成一个隐式的被授权者 | 委托方与所有人是**两个不同的东西**：一个是名单上的一行、能撤、有名字；另一个没有名单、没有名字、「给出去收不回」。这正是 0037 否掉 `unlisted` 时已经论证过的那条线 |

## 决定

1. **`visibility` 仍然是两态**：`private` / `public`。[ADR 0037](0037-visibility-has-two-states.md) 一条不改。
2. **另加一列：公开之后陌生人拿到哪一档**，取值 `invoke` / `browse`。`visibility = 'public'` 时**必须有值**，`private` 时**必须为空**——两个字段一起表达一个状态，不允许出现「私有但写着档位」或「公开但没说给哪档」的行。
3. **最多到「浏览」。** 公开不能给到 `write` 及以上：那意味着**任何人**都能提交版本、改描述。「写入」是一条关于**谁**的声明，而公开恰恰是「没有谁」。
4. **一个人实际拿到的档 = 他自己那一档与公开那一档里高的那个。** 公开不会把已经授出去的人降级，授权也不会被公开抹掉。两个来源合并成「他实际能做什么」，而不是互相覆盖。
5. **公开即被搜到。** 那是 0037 §决定 2 给 `public` 的定义（「谁都能搜到它、谁都能调用它」），因此**消费面的读与搜索必须跟着认这个档位**——公开之后不再需要授权就够得到。这一条是本决定里工作量最大的一句，不是一个附注。

## 理由

**为什么是两个字段而不是三个值。** 因为这是**两个问题**：这个 skill 外人碰不碰得到（两态），以及碰到的时候够得到多深（梯子上的一档）。合成一个枚举之后，「可见性是两态」这句话就变成一句需要解释的话——而 0037 花了一整条 ADR 把它定下来，正是为了让 `unlisted` 那种「同一个状态两个名字」不再出现。

**为什么公开给不了「写入」及以上。** 梯子的上半段回答的是「**谁**在维护这个 skill」——上线会改变每一个读者拿到什么，授权会改变谁能进来。这些动作全都要求**有一个人对它们负责**，而「所有人」不是一个能承担责任的主语。把它做成一个允许的取值，等于给了一条「任何人都能把你的 skill 换掉」的路，而那条路上没有一个可以去问的人。

**为什么公开要进搜索，而不是「公开但不出现在目录里」。** [ADR 0037](0037-visibility-has-two-states.md) §理由 已经否过一次这个想法，原话是「进不进目录是一个**搜索结果**的问题，不是这个对象的状态问题；而 `public` 的定义就是被搜到」。本决定不改那个结论，只是承认它的代价：**这一版起，公开的 skill 真的会被别人搜到**，而那意味着搜索的可见性谓词要跟着改。

**为什么公开与授权取高的那个，而不是谁覆盖谁。** 两个来源说的是同一件事的两种来源——「他为什么够得到」。若让公开覆盖授权，一个被授了「写入」的人会在 skill 变公开的那一刻**被降级**（降到「调用」），而没有人做过这个决定；若让授权覆盖公开，一个 skill 变公开之后**私有期间发出去的授权仍然在名单上**，列表读起来像是它们还在生效。取高值让两个来源都保留自己的意思，而「他实际能做什么」只有一个答案。

## 后果

- **`skill.visibility` 有写入路径了**，而它今天是一个「有列、有注释、值域三个、但完全没有写入路径」的字段——建行时写死 `'private'`，此后没有任何代码碰过它。本版给了它一条路（`admin` 档能改），所以它**第一次真的会被写**。
- **迁移要订正两处过期的列注释**：`V1__baseline.sql` 的 `skill.visibility` 与 `namespace.visibility` 都写着 `public | unlisted | private`，而 0037 之后 `unlisted` 已经不存在。0037 §后果 当时说「本次不改迁移……更正挂到下一次真正需要动这两张表的迁移上」——**就是这一次**。
- **消费面的读与搜索的谓词都要改**：今天它们是「拥有 ∨ 被授权」，要变成「拥有 ∨ 被授权 ∨（公开 ∧ 档位够）」。`SkillCatalogRepository` 的列表查询与 `SkillRepository.permitted()` 的访问谓词是两处，**都必须改**——只改一处会造出一个「搜得到但打不开」的 skill，而那比两处都不改更难发现。
- **「调用」档在网页上看不到它**（设计件原话）：控制台那一屏要 `browse` 及以上才进得去，所以只有「调用」档的人打不开它，只能用 agent。**而「浏览」档进得去**——那一屏因此要按档位把草稿滤掉，见 [ADR 0051](0051-the-author-plane-serves-by-tier.md)。这两个答案都不是疏漏，是设计件写下的分界。（**2026-10-17 同日补**：前半个答案被推翻了——`调用` 档打得开这一屏，看得到「信息」与「版本」两栏（版本只列已上线），见 [ADR 0051](0051-the-author-plane-serves-by-tier.md) §决定 2a。后半个答案反而更硬：现在连元数据那一条路也要求按档位过滤。）
- **本决定只定「公开之后拿到哪一档」，不定「谁能碰到这个 API」。** 后者于 2026-10-17 定为「**任何持凭据的账号**」——本版**不引入匿名读面**（理由与代价见 [`prd.md`](../versions/v5-skill-management/prd.md) §不做 第 7 条）。两个问题分开，是因为它们的代价不同：前者是权限的粒度，后者要连带回答速率限制、滥用防护与「公开即被爬」。
- **一条要还的债**：`namespace.visibility` 本版仍然没有任何读写路径（命名空间级的公开不在范围内）。它那处过期的列注释跟着这次迁移一起订正，仅此而已。
