# 0046 · 把一个 skill 删掉这件事，只在浏览器面存在

> **状态**：已采纳
> **日期**：2026-10-16
> **依赖**：[0031](0031-submitting-and-publishing-are-two-actions.md)（上线只在浏览器面）、[0040](0040-api-key-in-the-cli-now-the-browser-path-later.md)（凭据签发入口只有会话）、[0043](0043-the-browser-session-is-bounded-and-revocable.md)（会话的两条尺子）
> **这一条是 0031 §决定 2 那条规矩的第二次应用。** 那里把「上线」放在浏览器面、让 API 平面**没有**这条路由；这里把「删除」按同一条规矩收回来。0031 的正文不改。

## 背景

产品里有一类动作**把一个东西从别人手里拿走**：把版本对外公开（上线），把一个 skill 删掉（删除）。两者都不可逆、影响面都不只是自己，而产品对它们只定过一条规矩——**由人做、在浏览器里做、并且再确认一次**。0031 把这条规矩应用到了**上线**上：浏览器面有 `POST /web/.../publish`，API 平面（Bearer 凭据生效的那个平面）没有这条路由，所以任何凭据都上线不了。

**删除漏了，而且方向正好相反：**

| | 浏览器面 | API 平面 |
|---|---|---|
| 上线 | 有（`WebSkillController` PUBLISH） | **没有**（[0031](0031-submitting-and-publishing-are-two-actions.md) §决定 2） |
| 删除 | **没有**（控制台里根本没有这个入口） | **有**（`DELETE /api/v1/skills/{namespace}/{name}`） |

那条路由的闸只有两道：`skills:write`（`SecurityConfig`）+ **你是这个 skill 的 owner**（`SkillVersionService.softDelete`，`editor` 不行）。也就是说，任何一把带 `skills:write` 的 API key，以及 `skillmaster login` 换来的那份登录态（它申请的正是 `skills:read skills:write`），**都能删掉你名下的 skill——而控制台一个按钮都没有。**

**发现它的是 v4 的同意页。**「登录请求」那一屏把凭据的能力写成后果，其中一条写着「以你的身份提交新版本、管理共享、**删除 skill**」。**那句话是真的，而它的真实恰恰暴露了这条规矩没落实**——同一屏上另一条写着「它不能上线」，那一条成立，只因为 0031 已经做过一次这件事。

## 决定

**撤掉 API 平面那条删除路由**（`DELETE /api/v1/skills/{namespace}/{name}`），删除改为**只在浏览器面**发生：控制台一处入口，点下去**先问后果**、确认之后才删。凭据——API key 也好、CLI 登录换来的登录态也好——**都删不了**。

**控制台那处入口不在本版画**：它属于 skill 管理模块，v4 只做凭据那条线。**所以在这一版与控制台入口之间那一段时间里，删除在整个产品里无处可做**——这个空档是知情的，不是漏掉的。

**同意页只是不再列它**，不再另写一句「它不能删除 skill」：授权屏在 2026-10-16 当天把「它做不到什么」那一行整个删掉了（理由与代价见 [`design/README.md`](../../design/README.md) §怎么打开「登录请求」）。

## 理由

**为什么是撤路由，而不是给它加一道 scope 闸**（比如新开一个 `skills:delete`，登录态不发它）：加闸会留下**第二种答案**——「换一个凭据就能删」。而这条规矩要的答案是**唯一的**：凭据删不了，人才能在网页上删。两个答案并存时，读到「不能删除」的人会以为换个凭据就行，而那不是真的；这也正是 [0041](0041-third-parties-reach-us-through-the-cli.md) 那一族问题里最难解释的一类。更根本的是，删除的力量来自**它把一个 skill 从所有读者手里拿走**，那把力量不该随凭据的寿命长在某个自动化里——0031 对上线用的也是这条判断，不是 scope。

**被否掉的第三条：什么都不做，只把同意页那句删掉。** 那样一来，同意页那张清单就只是**没提**删除——而**沉默只有在它确实做不到的时候才算实话**。路由还在的那一天，凭据仍然删得了，那张清单就是一份不完整的说明书。0031 那次的教训正是这一类：**一个没人会执行的动作，写进承诺里是假话；一个真的能做到的动作，从清单里拿掉同样是假话。**

**为什么这条不需要一次数据迁移**：删除本来就是**软删**（写 `deleted_at`，行与字节都留着——回收的引用集是 `SELECT DISTINCT blob_sha256 FROM version_file`，不看 `deleted_at`）。撤掉路由影响的是**入口**，不是已经发生过的删除。

## 后果

- **删除在控制台入口画出来之前无处可做。** 今天也只有凭据能删，所以这不是「少了一条路」，而是**这条路暂时不存在**。真到了需要删一个 skill 的时候，只能等那一处入口。
- **无人值守的删除从此不存在**，而且这是有意的：将来若真出现自动化删除的需求，要另开一条 ADR 讨论它凭什么安全，**而不是把它塞回一个 scope 里**。
- **这是对已经交付出去的能力的一次收回**，而那条能力**从来没有被设计过**：[`v1-hosting`](../versions/v1-hosting/prd.md) 与 [`v2-credentials`](../versions/v2-credentials/prd.md) 的 prd 里**一个字都没提删除**（v2 给了 key 那把 `skills:write`，删除是路由开放时顺带能做的）。所以收回去要改的是服务端一条路由与它的测试，**不涉及任何版本已经写下的验收**。
- **同意页的权限清单里不再有「删除」**（`CONSENT_SCOPES`，两个演示件共享的那份片段），`interaction-check.mjs` 钉着这条：清单里不许出现「发布」，也不许出现「删除」。
- v4 的范围与验收跟着改：`prd.md` §范围 做 #10 只剩「撤路由 + 同意页那一半」，§不做 新增一行（控制台入口归 skill 管理模块）。
