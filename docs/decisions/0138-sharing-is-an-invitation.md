# 0138 · 共享是一条邀请，对方接受才生效

- **状态**：已采纳
- **日期**：2026-11-04
- **所属版本**：[`v45-notifications`](../versions/v45-notifications/README.md)
- **依赖**：[0034](0034-skill-level-sharing.md)（共享是 skill 级授权）、[0047](0047-permissions-are-a-ladder.md)（权限是一条梯子）、[0052](0052-a-request-is-not-a-grant.md)（申请不是授权）、[0139](0139-a-notification-points-at-a-business-object.md)（通知是业务对象的指针）
- **修订**：[0034](0034-skill-level-sharing.md) §决定 9 与 [0047](0047-permissions-are-a-ladder.md) §决定 5 的「共享即时生效」这一半——`admin` 仍能授权，但一次共享不再直接写出 `skill_grant`。**两条 ADR 的正文保持原样**，改动记在这里。

## 背景

从 v5 起，共享是一个即时动作：`admin` 档在「共享给」里填一个用户名、选一档，`skill_grant` 当场写下，对方立刻拿到权限（[ADR 0034](0034-skill-level-sharing.md) §决定 1、[ADR 0047](0047-permissions-are-a-ladder.md) §决定 5）。产品里没有「对方答不答应」这一步——被共享的人甚至不必知道发生过这件事。

这与同一个 skill 上的另一条流程不对称：**申请**在 [ADR 0052](0052-a-request-is-not-a-grant.md) 里被做成一个独立对象，批准之前谁也不多出什么权力；而共享是反方向的一步，却没有对应的一次确认。2026-11-04 与所有者对齐需求时，这条不对称被点名：**共享也要先确认**，否则「我把 skill 共享给你了」只发生在聊天里，产品里既没有知情、也没有拒绝的机会。

摆上桌的选项：

| | 做法 | 为什么被否 |
|---|---|---|
| a | 保持即时授权，通知只是告知 | 「确认」拦不住任何东西；B 没接受也已经有权限，A 也不知道对方到底要不要 |
| b | 给 `skill_grant` 加一个 `pending` / `accepted` 状态列 | [ADR 0052](0052-a-request-is-not-a-grant.md) §理由 已经逐条否过同一件事：每一处读授权的地方都要多问一句「这一行还没生效」，名单、可见性、审计、按档位滤内容的每一条路径。`skill_grant` 从建立起只表示「已经授了」 |
| c | **邀请是与申请对称的独立对象；接受时才写授权** | 采纳 |

## 决定

1. **邀请是独立对象**：`skill_invitation(skill_id, invitee_id, role, invited_by, created_at, expires_at)`，主键 `(skill_id, invitee_id)`。**它不授予任何东西**，也不出现在「谁能碰它」的名单里。
2. **接受才写授权**：接受 = 按邀请上的档位写一行 `skill_grant`（复用 `SkillGrantRepository.upsert`，与批准申请走同一条路），然后删掉邀请行。拒绝 = 只删邀请行，不产生授权。
3. **发出邀请的仍是 `admin` 档及以上**（[ADR 0047](0047-permissions-are-a-ladder.md) §决定 5 不变）。对方已有同级或更高授权时**不产生邀请**，直接回显现有档位。
4. **一条待接受邀请，30 天后失效。** 有效期是行上的 `expires_at`；到期不靠后台任务，读取时按 `expires_at <= now` 判定，接受时拒绝。过期之后 A 可以重新共享：旧邀请行被替换，旧通知记为「已过期」，新邀请重新计时。
5. **同一收件人同一 skill 最多一条待接受邀请。** 再次共享是 upsert，移动档位与 `expires_at`，不产生第二条。
6. **存量授权不动。** 这条决定只约束新共享；升级前已经生效的 `skill_grant` 继续有效，被授权的人不会突然失去权限。
7. **共享、接受、拒绝、撤销各记一条审计**，与 [ADR 0052](0052-a-request-is-not-a-grant.md) §决定 5 同一条理由：这四件事都是「某个人对某个人做了什么」。
8. **降档不是共享，升档才是。** 已生效授权的档位往下调，由 `admin` 直接改、立即生效并记审计——它不授予任何新东西，也不需要对方确认；往上调仍走邀请，因为那是新增访问。接受一条比现有授权更低的旧邀请，以现有更高档为准，绝不降级。

## 理由

**为什么不做成「未生效的授权」（选项 b 被否）。** 这是 [ADR 0052](0052-a-request-is-not-a-grant.md) 已经回答过的问题，答案一字不改：`skill_grant` 的含义只有一句——「这一档已经给了这个人」。把一个流程状态塞进它，代价会落在每一处读它的代码上，而收益只是省一张表。邀请与申请是同一种形状的两个方向：**一个是「我想要」，一个是「我给你」**，两者都不该改变授权表的语义。

**为什么到期不靠后台任务。** 一条邀请是不是还能接受，是「现在」与 `expires_at` 的比较；把它做成状态列再加一个清扫器，等于为一个可以当场回答的问题维护第二份状态。读取时判定、接受时拒绝，两处用同一个比较。过期后的旧行在下一次共享时被替换，不专门清理。

**为什么存量授权不回收。** 这一条不是遗漏，是边界：邀请制回答的是「以后怎么给」，不是「以前给出去的还算不算」。把存量授权变成待确认，会让所有已经依赖它的人在某次升级后突然失去权限——那是一次没有发起人的撤回。

## 后果

- **一张新表、三组路由**：`skill_invitation`；发出 / 列出 / 撤销邀请。`ModuleMap` 的 M12 表集合加一行（`TableOwnershipTest` 从迁移里收表对账，没有第二处清单），迁移编号接着 V33 排。
- **`POST /skills/{ns}/{name}/grants` 下线**：发出邀请取代了即时授权；`GET /grants` 与 `DELETE /grants/{handle}` 保留，前者列已生效授权，后者撤销已生效授权。旧客户端再直接授权会 404/405，必须改走 `POST .../invitations`。
- **共享不再是即时生效。** 控制台的「共享给」、CLI 的 `skmr skill share` 都改说「邀请已发出，等待对方接受」；`skmr skill shares` 要同时列出已生效的授权与待接受的邀请。**这是一次外部契约变化**，旧客户端读到的 `role` 不再意味着「已经生效」。
- **批准申请仍然直接写授权**，不经过邀请：申请人已经表达过意愿，再让他确认一次是把同一句话问两遍。[ADR 0052](0052-a-request-is-not-a-grant.md) 的模型不变。
- **邀请会过期，授权不会。** 过期只作用于「还没被接受」的那一行；已经接受的授权没有到期日。
- **通知面是这条决定的配套，但不是它的前提。** 没有通知，邀请仍然成立（待接受列表在协作者页）；有了通知，B 才在登录后知情。两者的关系由 [ADR 0139](0139-a-notification-points-at-a-business-object.md) 定。
- **一条要还的债**：邀请被接受 / 拒绝 / 过期 / 撤销之后，B 或 A 只能在通知的留档里回看；邀请行本身已经消失，`skill_invitation` 不保留历史。这是有意的——历史属于通知与审计，不属于授权表。
