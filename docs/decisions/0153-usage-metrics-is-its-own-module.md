# ADR 0153 · 使用度量是独立模块，按 scope 记录

- **状态**：已采纳
- **日期**：2026-11-06
- **所属版本**：[`v49-public-signals`](../versions/v49-public-signals/README.md)
- **依赖**：[ADR 0149](0149-use-is-counted-per-account-per-day.md)（按账号 × 天去重、只展示分桶）、[ADR 0152](0152-cumulative-calls-are-their-own-signal.md)（累计调用是独立信号）、[ADR 0123](0123-modules-publish-an-explicit-interface.md)（模块只发布显式接口）
- **修订**：[ADR 0149](0149-use-is-counted-per-account-per-day.md) §决定 1（主键加 `scope`）与 §决定 4（任何情况下都不下发精确账号数）；[ADR 0152](0152-cumulative-calls-are-their-own-signal.md) §决定 1（主键加 `scope`）与 §决定 2（记录改为读事务之后的独立事务）

## 背景

v49 的需求从公域上线开始：要让读者判断「这条公开 skill 有没有人在用」。使用统计因此和来源、许可一起进了同一个版本。但它是**度量**，不是公域展示——将来作者看板、协作者使用管理都会复用同一批事实，公域只是第一个消费者。

今天的实现把它和来源放在同一个模块 M12：同一个 `SourceRepository` 写 `skill_usage_day`，`ReadSkillUseCase` 直接调 `SourceService.recordUse`，公域判据（公开、非作者）写死在读路径里。这带来两个后果：

1. 来源与度量的规则互相拖拽：加一种来源要碰度量表，加一个度量要碰来源仓储。
2. 度量写入与正文读在同一个事务里：度量出问题会把读拖下水。

选项有三：继续留在 M12；同一版本里拆成独立模块；单独开一版。

## 决定

1. 新增 **M15 `metrics`**，拥有 `skill_usage_day` / `skill_usage_total`；表归属从 M12 移出，**表名不改**。
2. 表加 `scope`：本版只启用 `public`；将来 `owner`（作者与协作者的使用，给用户自己管理）走同一套接口与表。
3. **公域侧只保留策略**：哪些加载算公域信号（公开、有线上版本、非作者）由读路径判断；M15 不认识公开 / 私有。
4. 记录在**读事务结束之后**走独立的 `RecordSkillUsageUseCase`（`REQUIRES_NEW`），失败只记日志，不影响正文读。
5. 入库数留在 M12（它是库关系，不是行为度量），由读模型拼装。

## 理由

- **度量会继续长，公域只是第一个消费者。** 现在拆，代价是一个模块与一次迁移；以后再拆，要动已经写进读路径的规则和已经发出去的 API。
- **同一版本交付不等于同一个模块。** 需求可以一起上，代码边界不必一起烂。
- **只记 `public` 是隐私最小化。** [ADR 0149](0149-use-is-counted-per-account-per-day.md) 已定「不成为个人行为记录」；记录所有加载再在展示层过滤，会先把私有使用采进来——那正是要避免的。
- **`scope` 表达「度量的用途」，不表达「谁能看」。** 把两者混在一起，将来开作者看板会把授权问题带进度量表。
- **故障隔离是硬判据。** 度量是旁路，不能反过来决定正文能不能读。

被否掉的：**留在 M12**（两个职责一个模块）；**每个 scope 一张表**（复制去重、保留与清理）；**记录所有加载**（扩大个人行为记录面，今天没有消费者）；**提交后事件**（仓库没有事件基础设施，收益与 `REQUIRES_NEW` 相同）。

## 后果

- 多一个模块、一次迁移 `V37__usage_scope.sql`、`ModuleMap` 与 `system.md` 的变化；架构检查会强制表归属。
- 度量是旁路：进程崩溃或记录失败会丢计数，不保证精确；界面只展示分桶，不展示精确次数。
- 将来开 `owner` scope 要一条新 ADR，并确定保留期与展示授权；M15 的采集与聚合不改。
- 公域读路径保留一条策略判断；它属于公域，不属于度量。
