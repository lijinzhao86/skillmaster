# ADR 0035 · 版本钉记在客户端本地，地址不带版本

- **状态**：已采纳
- **日期**：2026-10-07
- **依赖**：[ADR 0012](0012-addressing-and-version-pinning.md)、[ADR 0001](0001-server-authoritative.md)、[ADR 0025](0025-cli-credential-storage.md)、[ADR 0033](0033-version-names-are-semver.md)、[ADR 0031](0031-submitting-and-publishing-are-two-actions.md)
- **修订**：[ADR 0012](0012-addressing-and-version-pinning.md) §理由 里「为什么把钉做进清单里的 URI，而不是让客户端记住版本号」那一节（**该 ADR 正文四段保持原样**）。§决定 2、4、6 都不受影响：`@` 后缀还在、清单里每条 URI 仍然带着钉、服务端仍然完全无状态

## 背景

ADR 0012 把「一次任务里版本钉死」做成了**数据随响应发出去**：`list` 印的地址带 `@版本`，抄进后面的命令就行；详情里每条文件 URI 也已经写着版本。当时明确否掉过「让客户端记住版本号」，理由是**那样不需要任何机制**——照抄一串现成的 URL 就够了。

问题出在「现成的」这三个字要由谁来抄。地址里的版本对两类版本是两种东西：

- 作者声明了 `version:` → `@1.2.3`，六个字符，可读、有语义。
- 作者没声明（ADR 0033 明确允许）→ `@sha256:` 加 64 位十六进制，**71 个任意字符**。

而它要模型**逐字符复现**：人有一条位精确的通路（复制粘贴，绕过认知），模型没有，它是从上下文里**重新生成**。同一类问题在这一轮里已经撞了两次，都是同一形状：

1. `list` 的分页令牌——CLI 铸的 base64 信封，**实测 191 个字符**。已撤掉，换成「默认一页 + `--all`」。
2. `get` 把正文落到临时目录后**只印路径**。本机实测那个路径 **79 个字符**（`/var/folders/cz/t6vtwdxx3nv79x9_v0p0fppm0000gn/T/skillmaster-603126623/SKILL.md`），其中两段是任意字符。模型要把它复现给 `Read`，错了就是「文件不存在」——而这个 skill 明明有正文。

还有第三件与之独立的事：`invoke` 与「取一个文件」在 CLI 里是同一个动词 `get`，两个形态只差一个位置参数；而宿主是两个工具（`Skill` 加载、`Read` 读文件），两边对不上。

于是要回答的是：**钉能不能不从调用方的文本里过，同时又保住 ADR 0012 的那条性质**（同一任务里的两次读是同一版）。

## 决定

1. **`skill invoke <地址>[@版本]` 解析版本，并把它记在本机**：解析默认是当前已发布版本（指针，ADR 0033），也可以由地址里的后缀指定。载体是 `~/.config/skillmaster/pins-<server 哈希前 6 字节>`——**按 server 分**，与回落凭据（ADR 0025）同一个惯例、同一个理由。文件里存 `{name, digest}` 两半，0600，原子替换。
2. **`skill read <地址> <相对路径>` 从那里取版本**，用 §4.2 已有的请求头 `X-Skill-Version` 发出去。**地址永远是裸的 `命名空间/名字`**，调用方一个字版本都不用写、也不用记。
3. **`skill list` 印的地址不带钉。** 卡片上的 `version` 字段随之失去读者，删掉；`id` 那个「为了让客户端能钉版」的理由也不再成立（字段本身这一轮不动）。
4. **`invoke` 每次重新解析**，与记录不同就覆写，**并印一行说钉从哪一版移到了哪一版**。
5. **记录里的版本解析不到时响亮报错**（让人重新 `invoke`），**绝不静默回落到当前版本**。
6. **新增消费面端点 `GET /api/v1/skills/{ns}/{name}/versions`**，只列已发布版本——这是全系统唯一印钉的地方，而且是调用方主动要的。
7. **`@版本` 后缀继续存在**，作为显式覆盖（`read` 时它优先于记录，且两者不同时发送：服务端对两个来源不一致答 400）。

## 理由

- **为什么不是服务端记住。** ADR 0012 已经写过：服务端是无状态的（`STATELESS`、bearer 令牌），没有任何东西能标识「这是同一任务的第二次请求」，要记住就得引入会话，那是把整个架构反过来。这一条没有变，也不需要变——**钉仍然由客户端携带**，只是「客户端」从模型的上下文扩到了客户端的磁盘。
- **为什么 CLI 这次可以记，而 §4.6 当时否掉过「lockfile 式」。** 当时否的理由是「任务的边界在 CLI 里同样不清楚，而且要多维护一份状态」。**前半句在这里不成立**：CLI 不需要猜边界——**模型调 `invoke` 的那一刻就把边界声明了**。这不是启发式（TTL、上次用过），是一个显式事件，由唯一知道边界的那一方给出。状态仍然要多一份，代价如实记在 §后果。
- **为什么不是「一次把整版落到本地」。** 那正是 2026-09-26 删掉的 `materializer.py`，[`technical-design.md`](../versions/v1-hosting/technical-design.md) §6 写了不重建：它与 ADR 0001「服务端是唯一真相、skill 不落本地」直接冲突。这一版只落一个版本的名字和摘要，不落内容；`read` 仍然按清单里那条已经带钉的 URI 取字节，内容不落地（二进制除外，那是模型唯一能看到它的路）。
- **为什么不是让调用方继续写版本。** 那就是现状，代价是上面那 71 个字符要模型逐字符复现，而它没有位精确通路。三篇外部材料方向一致（第一方工具设计指引「避开低层技术标识符」、宿主自己的 `Read` 用整数 `offset`/`limit`、以及 coverage collapse 这个失败模式），细节与折价记在 [`technical-design.md`](../versions/v1-hosting/technical-design.md) §4.6 的设计点里。
- **为什么地址不带钉也不会漂。** 因为钉没有消失，只是换了存放处：`invoke` 之后每一次 `read` 都带着同一个 `X-Skill-Version`，服务端据此回同一版的清单，清单里的 URI 又已经带着同一版——**两次读之间发生发布，影响不到它们**。ADR 0012 要的那条性质完整保住。
- **被否掉：digest 缩写**（`@6b8f2a1c`，照 git 短哈希的惯例，服务端按前缀唯一解析）。它能把 71 字符降到 8，代价是地址语法多一个短形态、解析多一条歧义路径。**这一版不做**，因为这条路上已经没有调用方需要复现 digest 了；真需要时它是独立的一步。
- **被否掉：`invoke` 复用记录而不是重新解析。** 那样「重读一次正文」会悄悄把版本换掉（同一任务里再 invoke 一次，而这中间有人发布），比不跟随指针更坏。选的是「重新解析 + 变了就印出来」。
- **命名**：`get` 拆成 `invoke` 与 `read`，与宿主的 `Skill` / `Read` 一对一——**而且这次拆分有实质**：`invoke` 有副作用（解析并记下钉），`read` 没有。此前两者都只是取字节，所以那时它们是「一个操作的两个拼法」。

## 后果

- **本地多了一份状态，而它不在请求里。** 这是这个方案最该被记住的代价：记录错了，请求本身看不出来。所以**命令印出的那几行不是装饰**——`invoke` 印「已按 X@Y 加载」（以及钉移动时的那一行），`read` 印「按 X@Y 取」或「还没 invoke 过」。这些行是这份本地状态唯一的可见性。
- **同一台机器上两个 agent 同时用同一个 skill 的不同版本时，记录只有一个槽，后写的赢**，先那个的 `read` 会取到别人的版本。这是已知且未解决的；真发生时会印出来（那一行说的是另一版）。
- **跳过 `invoke` 就退回「每次重新解析」**，也就是 ADR 0012 时代那个会漂的行为。这不是新缺陷（今天默认就是这个），但网关正文要把顺序写成硬要求。
- **`list` 不再印钉**，卡片上的 `version` 字段随之删除（服务端改动）；这是「没有读取方就删」那条标准第三次用在卡片上（前两次是 `title` / `visibility` / `updated_at`）。
- **网关正文与 CLI 必须同一次改**：服务端每次启动都会把 `gateway/skillmaster/SKILL.md` 发布出去，`metadata.platform_api_version` 随之从 `"6"` 到 `"7"`。单独改一边等于让服务端发布一条「去跑一个还不存在的命令」的协议。
