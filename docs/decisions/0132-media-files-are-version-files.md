# 0132 · 媒体文件是版本文件，不是独立素材库

- **状态**：已采纳
- **日期**：2026-11-02
- **依赖**：[ADR 0005](0005-content-addressing.md)、[ADR 0012](0012-addressing-and-version-pinning.md)、[ADR 0031](0031-submitting-and-publishing-are-two-actions.md)

## 背景

支持媒体文件时，有两条路：

- **普通文件**：媒体和 `SKILL.md` 一样进版本清单，参与 `digest`，上线即冻结。
- **独立素材库**：版本里只存引用（素材 id 或 URL），素材本身可以替换、删除、跨版本共享。

素材库的吸引力很直接：换一张图不用发新版本，多个版本共用一份大文件，存储更省。但它要回答一组新问题：素材的引用计数、素材被删了版本怎么办、素材的权限跟谁走、版本 `digest` 还能不能代表内容。

## 决定

**媒体文件是版本文件。** 它和文本文件在模型里没有区别：

- 身份是 `(version_id, relpath)`；
- 字节按 sha256 内容寻址，跨版本、跨 skill 去重；
- 上线冻结；换一个媒体文件 = 产生一个新版本；
- 权限、可见性、分享、`@版本` 钉、`latest` 指针全部复用现有规则。

## 理由

**否掉独立素材库。** 它的核心代价是**版本 `digest` 不再代表内容**。这个仓库的模型（[`model.md`](../current/model.md)）建立在「同一份字节 → 同一个 sha256 → 同一个 digest → 同一个版本」之上：客户端据此判断有没有变、`@sha256:` 据此钉住一版、发布幂等据此成立。素材库让同一版本在不同时间返回不同字节，这四件事同时失效。

**否掉「引用 + 哈希混合」**（引用里带上素材的 sha256）。它保住了可复现性，但素材仍然没有版本、没有权限、没有回收边界；要补齐就是再做一个版本系统——不如直接用现有的这个。

**为什么接受「换图要发版」。** 这是可复现性换来的：拿到 `@1.2.3` 的人，永远拿到同一张图。对 skill 这种要被人依赖、被 agent 反复加载的内容，可复现性比「改素材不产生版本」重要。作者想改素材，就走和改文本一样的路：建草稿、改、上线。

**为什么去重仍然成立。** 内容寻址是字节层的，与「在不在同一个版本里」无关。两个版本引用同一张图时，存储里只有一份字节；版本清单各记一行，指向同一个 sha256。

## 后果

- **替换媒体需要新版本**，会出现在版本列表里；这是有意的。
- **整包下载会带上全部媒体**。服务端的归档路径支持 512 MiB；但 CLI 的 `skill download` 客户端在本版仍把整包读进内存，**17 MiB 以上会被它自己拒绝**（TD P3 的流式落盘才解除）。在此之前，大包要拿单文件用 `skill get`。不提供「只下文本」的选项，若将来需要再单独做。
- **回收沿用现有引用计数**：`version_file` 是唯一引用来源，版本被丢弃 / 删除后字节才可能被清扫；素材没有独立的生命周期。
- **不做素材库的那些能力**：没有跨版本的素材管理界面、没有「替换素材」按钮、没有素材级权限。这些都不在本版，也不在 roadmap 上。
