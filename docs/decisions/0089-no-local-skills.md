# ADR 0089 · 本机不装任何 skill，三条规则写进系统提示词

- **状态**：已采纳（取代 [ADR 0002](0002-gateway-skill-and-cli.md) 的决定 1）
- **日期**：2026-10-25
- **依赖**：[`versions/v17-cli-startup/`](../versions/v17-cli-startup/)（旅程第三步写的就是这三条规则）

## 背景

[ADR 0002](0002-gateway-skill-and-cli.md) 定的是：客户端只装两样东西——**一个通用网关 skill** 加 **一个自研 CLI**。网关 skill 的 frontmatter 常驻上下文负责触发，正文记录服务地址与调用协议；CLI 负责安装与更新它。

当时这么做是对的：MCP 注入不了 skill，本地下发目录又与"服务端权威"矛盾，在客户端放一个薄薄的引导物是唯一可行的入口。

现在情况变了：**产品本身就是 skill 平台**。把一个不是 skill 的"网关"塞进用户的技能目录，与"所有 skill 都放云端、按需取用"自相矛盾——用户打开技能目录会看见一个既不是他写的、也不归平台托管的条目。而 v17 的旅程第三步本来就要改用户的系统提示词，触发这件事已经另有落点。

问题只剩一个：**用法说明放哪。** 三条候选：

1. **保留网关 skill**（现状）——触发最可靠，但与产品主张自相矛盾，且同一份内容有两个来源。
2. **新增一条命令，从服务端取**——不用发版就能改；但流程描述的是**这版二进制有哪些命令**，服务端更新一份通用流程，会让老二进制读到它根本没有的命令。
3. **作为 `help` 的一个主题，编进二进制**——本次采纳。

## 决定

1. **本机不安装任何 skill**，包括网关 skill。技能目录里只有用户自己的东西。
2. **系统提示词里写一段带起止标记的规则**：

   ```
   <!-- skillmaster:begin -->
   skill 一律用 SkillMaster 管理，全部通过 skillmaster CLI 操作。
   1. 需要一项具体能力时，先查我的库（skills list）；没有再去公域搜（skills search）。
   2. 取用先 skill invoke，再按它返回的权限操作。
   3. 无法检索到匹配的 skill 时，不要逐个试。
   <!-- skillmaster:end -->
   ```

   起止标记让写入幂等、可回退（v17 验收 17–18）。

   **这段文字的家在 `skillmaster help usage`**，写进用户文件的是它的一个**快照**。

   **前面可以多一行可选的限定**，按 agent 填：

   ```
   只使用带 agent:claude、agent:common 标签的 skill。
   ```

   它确实每个 agent 都不一样（这正是它不能写死进 `help usage` 那份通用块的原因）。**默认不限定**——不写这一行，整个库都能用；用户明确选了标签才写。选的时候要提醒一句：`agent:*` 记的是来源目录、不是用途，漏掉 `agent:common` 会让通用位置那批本该共享的 skill 集体消失。
3. **`help` 新增 `usage` 主题，它是这三条规则的唯一来源。** 页面前半是给人读的规则，最后一段是带起止标记、可直接粘贴的那块；**不写收窄路径**（默认 50 条一页，列不完时 CLI 自己会说「先看有哪些标签」）；旅程第三步只说「跑 `skillmaster help usage`，把最后那段写进系统提示词」，**正文里不再自带一份拷贝**。这样 agent 忘了提示词能回头找回来，人也能自己看，而改措辞只改这一处。**不新增命令**（用户 2026-10-25 明确否掉了 `skillmaster prompt`）。
4. **旅程正文（`skillmaster startup`）仍从服务端取。** 它讲的是生态——哪些 agent、目录在哪、登录之后三步怎么走——与 CLI 版本无关，改了不该逼所有人升级。这与 `usage` 刚好相反，分开正是因为它俩的耦合对象不同。
5. **网关 skill 与 `setup` 一并删除**——不是弃用、不是搁置（2026-10-25 用户定）。`gateway/skillmaster/SKILL.md` 的正文压缩成三条规则，进 `usage` 主题；`setup` 命令、它的声明与测试、服务端那条 `BODY_PATH` 一起删掉。`/gateway/{file}` 这条通用文件路由留着，`STARTUP.md` 走它。**1.0.0 之前删是免费的**；发出去之后再删就是破坏性变更（[ADR 0088](0088-cli-major-version-is-the-api-generation.md)）。

## 理由

- **零副本与本产品的主张一致。** 我们卖的就是"skill 不装在本机、按需取用"。再往本机放一个"引导用 skill"，等于让用户在技能目录里多看见一个不归他管的东西——而这正是产品要消灭的那种散落。
- **三条规则进系统提示词，是因为它们稳定到可以常驻。** 先库后公域、先 invoke 再取用、别蛮力试——这三条说的是**行为**，不是命令面，加了新命令也不会变。常驻的收益是 agent 不必每次先去查一遍；代价是它对所有会话都占上下文，所以只放得下三条，多一条都不行。
- **`help` 随二进制走，这一点和成熟 CLI 一致。** `gh` 的帮助是编进去的、离线可查（它也有 `gh help formatting`、`gh help exit-codes` 这类跨命令主题）；AWS CLI 与阿里云 CLI 的三级 `--help` 同样随二进制；阿里云甚至在自己的 agent skill 里明写「`--help` 是参数的唯一权威」。`usage` 主题放在这里，是因为**这几条规则描述的是这版二进制能做哪些操作**——服务端下发一份通用规则，老二进制照着跑会得到「未知命令」。
- **写进用户文件的那份只是快照，不是第二个权威。** 它冻结在写下的那一刻，这是常驻上下文的代价；真正要改的时候，改 `usage`，新旅程自动拿到新的，旧用户的那份不会漂成"另一个版本的说法"——因为它本来就不声称自己是最新的。
- **被否的第 2 条有一个具体的坏结局**：服务端加了一条新命令后更新了流程，而老二进制照着跑会得到「未知命令」——**远程流程对老版本是错的**，而且错得不明显。
- **旅程正文留在服务端，是因为它讲生态而不是讲命令。** 新客户端、新目录约定这类事与 CLI 版本无关，改一次对所有人生效才是对的。两份文档归属不同，是因为它们的耦合对象不同。
- **被否的第 1 条不是错的设计**，它只是把"引导物"放在了技能目录里。那个位置的语义是"技能"，而网关不是技能——放错位置比放错内容更难纠正，因为用户会以为它是自己的东西。

## 后果

- **触发从"常驻 frontmatter"退化为"系统提示词里的三句话"**，发现率因此更依赖那三句写得够硬。ADR 0002 §后果第一条说的"`description` 是全项目最需要打磨的一段文字"，现在指的就是这段指针。
- **ADR 0002 的决定 1 被取代**，其余（CLI 主导、凭据不进模型上下文、服务端权威）仍然有效。
- **`skillmaster setup` 与网关 skill 从代码里消失**，不是标弃用。`SKILLMASTER_SKILLS_DIR` 保留——`submit` 仍然用它。
- **`help` 多一个 `usage` 主题**，顶层 help 的「流程：`skillmaster help usage`」指向它；那个一直没填的 `文档：（待定）` 占位行顺手删掉。**不新增任何命令。**
- **两个权威，各管一摊**：`usage` 说三条稳定规则，各命令的帮助说参数与输出。**规则里出现参数名就是错**——那会变成会过期的第二份说明。写进用户文件的那份是 `usage` 的快照，不声称自己最新。
