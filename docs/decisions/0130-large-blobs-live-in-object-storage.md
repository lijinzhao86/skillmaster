# 0130 · 大字节进对象存储，小字节留 PostgreSQL

- **状态**：已采纳（决定 4 中关于 `wc` 的一半被 [ADR 0133](0133-wc-streams-and-is-not-text-capped.md) 取代）
- **日期**：2026-11-02
- **依赖**：[ADR 0010](0010-storage-in-postgres.md)（接缝与「不引入对象存储」的原决定）、[ADR 0005](0005-content-addressing.md)

## 背景

v39 要让 skill 装下 Word / PDF / 图片 / 音视频，上限从每 skill 16 MiB 提到**每版本** 512 MiB（单文件 100 MiB；同一 skill 的多个版本不合计）。ADR 0010 当时把字节放进 PostgreSQL `bytea`，并写明「搬 OSS 的触发条件是容量 > 0.5–1 TB、备份恢复超出 RTO、IO 压过单个 PostgreSQL」。按新上限，1000 个 skill 各一个版本满载就是约 500 GiB（1000 × 512 MiB）——已经踩到那条触发线；多版本还会成倍增加，数据库备份与恢复会被媒体拖慢。

ADR 0010 同时留了接缝：`BlobStore.get/put(sha256)`，三个实现按序是 `PgByteaStore` → `OssStore` → `CachedStore`。这一版落的是第二步。

需要选的是**字节放哪**，不是**文件怎么算版本内容**——后者是 [ADR 0132](0132-media-files-are-version-files.md)。

## 决定

1. **按大小分流，不看类型。** 大于 1 MiB 的 blob 进私有 OSS 桶，不超过 1 MiB 的留在 `blob_content`。文本与二进制同一条规则。
2. **对象键是 `blobs/<sha256>`，桶私有，不发预签名 URL。** 字节只经 API 到达；OSS 在这里是一块更便宜的盘，不是一条分发通道。
3. **`blob` 表增加 `storage` 与 `location` 两列**，写入时由 `BlobStore` 的路由实现决定；读路径按这两列路由，对调用方透明。
4. **文本处理设 16 MiB 上限**：`grep` / `wc` 只扫描不超过 16 MiB 的文本文件，超过的文件明确跳过并说明。这个上限等于本版之前**整个 skill** 的上限，因此不存在「今天能扫、明天扫不了」的文件。
5. **回收用 outbox**：删除 `blob` 行的同一个事务里写一条 `blob_deletion`；OSS 对象由清扫器删除，删成功后再删 outbox 行。OSS 的删除无法和数据库事务一起提交，outbox 是让「引用已消失」与「对象待删」两件事不互相撒谎的办法。
6. **已有的 blob 不迁移。** 旧行 `storage='db'`，读路径两种都认；主动迁移是独立的运维动作。

## 理由

**否掉「全部留在 PostgreSQL」。** 存储单价与备份代价都不对等：RDS ESSD 100 GB 档报价 110 元/月，折算 1 元/GB/月（阿里云 `DescribePrice`，cn-shanghai，2026-09-27；促销会变），而对象存储的单位存储成本低一个数量级（**OSS 单价本项未核实，下单前复核**）。更麻烦的是行为：几百 MB 的媒体会让整库备份、恢复、WAL 与主从复制都变重，ADR 0010 的触发线正是为这个写的。

**否掉「全部进 OSS」。** 文本的读路径是热路径：`grep -F` 的预筛直接查 `blob_content`（`BlobStore.containing`），`diff` 只对文本逐行比较，编辑器保存前的基线摘要来自清单。小文件留在库里可以省一次 OSS 往返；skill 里的文本天然小，留在库里几乎不增加备份负担。

**否掉「按请求缓存 / 双层存储」。** ADR 0010 预想的 `CachedStore` 是第三步；现在还没有证据表明需要。1 MiB 的阈值先用起来，真实分布出来再决定要不要缓存。

**为什么按大小切、而不是按「是不是文本」切。** 两个原因。其一，文本判定是 UTF-8 探测，一个 100 MiB 的全 ASCII 文件会被判成文本并留在数据库——这正好是最该搬走的那种内容。其二，内容寻址要求「同一份字节只有一个位置」，位置如果依赖一个会变的探测，同一份内容就可能被写到两处。按大小切让位置成为 `size` 的函数，去重与回收都简单。

**代价是 `grep` / `wc` 可能遇到 OSS 里的大文本。** 用一个 16 MiB 的文本处理上限挡住：超过它的文件不扫描，并明确说明。本版之前整个 skill 才 16 MiB，所以没有既有的文件会因此失去能力。`containing` 对 OSS 里的文本按流式读取，候选集本身已经被这个上限收窄。

**为什么不做预签名 URL。** ADR 0010 已经论证过：内容寻址让字节层的 ACL 在结构上不成立——一个 blob 会被不同受众的 skill 共用，它的可达性取决于谁引用了它。预签名会把这条关系绕过去。

## 后果

- **数据库备份不再包含全部字节。** 只恢复数据库会得到清单而没有媒体；OSS 桶需要自己的版本控制 / 生命周期与恢复演练。这是这一版最需要写进运维文档的一条。
- **新增外部依赖**：桶、凭据（优先 ECS RAM 角色）、网络与 OSS SDK。OSS 不可用时，媒体上传与读取失败；不超过 1 MiB 的文本仍在库里、不受影响，更大的文本与媒体一样依赖 OSS。
- **上传需要服务端临时磁盘**：大文件先落临时文件、边算 sha256 再上传；临时目录至少能容纳一次 512 MiB 的导入。
- **删除变成最终一致**：数据库行删了，OSS 对象可能还在 outbox 里等清扫。清扫失败会重试，不阻塞发布。
- **阈值可调**：`storage` 列让「以后把文本也搬走」或「把小文件也搬走」不需要改调用方；改的是路由实现与一次数据迁移。
- **ADR 0010 的决定 2「不引入对象存储」与决定 4「字节回收与版本变更在同一事务里完成」被本 ADR 部分取代**（OSS 删除走 outbox，无法与数据库事务一起提交）；`BlobStore` 接缝与其余结论仍然有效。
