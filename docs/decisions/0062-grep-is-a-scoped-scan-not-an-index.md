# 0062 · 作者面的 grep 是有界扫描，不是索引

- **状态**：已采纳
- **日期**：2026-10-20
- **依赖**：[0001](0001-server-authoritative.md)（本地不落 skill 副本）、[0005](0005-content-addressing.md)（内容寻址、blob 不可变）、[0006](0006-search-server-side.md)（检索只索引 L1，正文不进索引）、[0010](0010-storage-in-postgres.md)（字节也落在 PostgreSQL）、[0035](0035-the-pin-lives-on-the-client-machine.md)（客户端只记钉，不记内容）
- **这一条只回答作者面对**草稿**的 grep**（`write` 及以上能读到的草稿，不限提交人），不改变消费面的检索（0006 管那一半），也不预先为「上限抬高之后」做实现。

## 背景

草稿内容开始可以由作者与 agent 在线编辑之后，agent 需要的下一件事是 `grep`：在**这一份草稿**里找哪一行写了什么。它与本地编辑的 `grep -rn` 是一对，而不是与产品的搜索框。

数据的样子决定了可选做法：文件清单在 `version_file(version_id, relpath, blob_sha256)`，字节在 `blob_content(sha256, bytes)`，**没有任何内容索引**。所以无论怎么做，都有人必须把这一版的字节读出来扫一遍；差别只在「谁扫、扫几轮、多少字节过哪一段网络」。

摆在桌上的四个做法：

| | 做法 | 代价 |
|---|---|---|
| 1 | CLI 逐文件请求，本地匹配 | 最多 512 次往返；本地每次 1 ms，公网每次 20–100 ms |
| 2 | 一次把整版字节取回 CLI，本地匹配 | 一次往返，但**每次 grep 都把 16 MiB 放到用户网络上** |
| 3 | 服务端扫描，只回命中行 | 扫描留在内网；用户网络只承担命中结果 |
| 4 | 给内容建 n-gram 索引（`pg_trgm` / `pg_bigm` / PGroonga / 外部引擎） | 索引通常不小于内容；每次写入要维护；托管可用性与崩溃语义另算 |

两份硬约束排除了两条路：单份 skill 的上限是 **512 文件 / 16 MiB**（`IngestLimits.STANDARD`，提交时就挡），所以扫描有界；而 [ADR 0001](0001-server-authoritative.md) / [0035](0035-the-pin-lives-on-the-client-machine.md) 规定**本地不落可复用的内容副本（缓存）**，所以做法 2 不能靠磁盘缓存修补——第二次 grep 仍然要重新拉 16 MiB。

## 决定

1. **grep 在服务端执行，按版本作用域扫描，不建内容索引。** 查询只碰这个 `version_id` 的 `version_file` 行，不扫全库的 `blob_content`。
2. **固定字面量先在数据库内预筛。** M7 把这一版的 sha 集合交给 M6，M6 在该集合内用 `position()` / `LIKE` 筛出候选，只把候选字节读到应用层；正则的精确匹配与行号在应用层算。**字节始终不出「数据库 → 应用」这一段内网。**
3. **回给 CLI 的是命中，不是整版。** 输出照本地 `grep`：`path:text`；`-n` 时 `path:line:text`，`-l` 只列路径。带结果上限（超出时说「还有更多」），不回传未命中的文件。
4. **不做客户端内容缓存。** 这不是性能取舍，是 0001 的规矩；重复 grep 的缓存只能发生在服务端内存里（按 `sha256` 缓存解码后的文本——blob 不可变，缓存永不过期）。
5. **升级信号写死在这条 ADR 里**：只有出现「单份上限抬到几十 MB 以上」或「grep 成为每次编辑都跑的高频操作」时，才考虑按 blob `sha256` 建 2-gram 索引（`pg_bigm`，与元数据搜索同一条运维路线）。**不选 PGroonga**（崩溃后要 REINDEX、托管 RDS 可用性未核）**也不选外部引擎**（为 16 MiB 引入一套要运维的系统）。
6. **作者面 grep 与消费面检索是两回事。** 0006 的「正文不进检索索引」对消费面继续成立；这一条不给正文建索引，也不把 grep 的结果暴露给任何消费面入口。

## 理由

**为什么不是做法 2。** 它在本地网络与很小的 skill 上没问题，但在「CLI 在用户机器、服务端在云端」这个部署形态下，每次 grep 都要把整份草稿过一遍用户网络。按 16 MiB 上限算：10 Mbps 约 13 秒，100 Mbps 约 1.3 秒。这不是「慢一点」，是不可用；而且「本地不落副本」把缓存这条退路也关掉了。

**为什么不是做法 1。** 病根是往返次数而不是字节数：512 次请求，每次都有鉴权与一次 SQL 的固定开销。

**为什么现在不建索引。** 扫描的常数已经被现代实现压到 GB/s（ripgrep 在缓存命中时约 9 GB/s），16 MiB 是几毫秒到几十毫秒的量级；拖慢一次 grep 的是网络，不是 CPU。业界建索引的门槛是 GB–TB 级语料——Google Code Search 的 trigram 索引约为语料的 20%，Zoekt 约 3 倍，GitHub Blackbird 对 115 TB 代码建了约 25 TB 索引；那是在 640 QPS 的量级上摊薄的。我们单份 16 MiB、grep 是编辑时的偶发动作，索引的存储与写放大换不来可感知的收益。

**为什么 `pg_trgm` 与 PGroonga 不合适。** 前者的 3-gram 对 1–2 个汉字（最常见的查询）基本失效，这正是 [ADR 0010](0010-storage-in-postgres.md) 里 FTS5 失败的原因；后者更快，但索引更大、崩溃后要 REINDEX、且阿里云 RDS 上没有核实过可用性。`pg_bigm` 的中文短查询与索引体积都合适，所以它是「将来万一要索引」时的唯一候选——留给升级信号触发，不是现在。

**为什么字节要关在数据库里。** PostgreSQL 读 `bytea` 比读文件系统慢约 10 倍（Cybertec 实测：350 MB 下 46 ms vs 590 ms），所以「把所有字节搬到应用层再筛」本身就有成本。固定串能在 SQL 里筛掉的，就不要搬出 RDS；这条在字节量变大时收益更明显。

**为什么仍要承认代价。** 正则的匹配在应用层（Java）算，语义与本地 `grep -E` 有差异；固定串（`-F`）可以做到完全一致，正则做不到。这个差异要写进命令帮助，而不是让用户自己撞上。

## 后果

- **M7 多一条编排、M6 多一个面**：M7 负责「这一版有哪些 sha」，M6 负责「在这些 sha 里哪些包含这个串」。两步写，不在一条 SQL 里同时点名两张表（§2.5 规则①）。
- **服务端内存缓存**：按 `sha256` 缓存解码后的文本，有界 LRU。blob 不可变，所以缓存没有失效问题；它只影响重复 grep 的延迟。
- **CLI 新增 `grep`**：参数先承诺 `-F`、`-i`、`-n`、`-l` 与路径前缀；正则的语义边界写进帮助。输出照本地 `grep`：`-n` 时 `path:line:text`，否则 `path:text`，`-l` 只列路径。
- **结果上限**：命中过多时截断并说明，不静默截断；上限是响应的属性，不是查询的。
- **将来若升级到索引**：索引键是 `blob.sha256` 而不是 `version_id`——内容寻址让同一份字节在所有版本之间共用一条索引，且**只增不改**；GC 删 blob 时要一起清索引。
- **不改变上限**：512 文件 / 16 MiB 是这条决定成立的前提。要动它，先回来重读这一条。
