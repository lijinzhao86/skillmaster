# 0156 · 同步以服务端身份写入官方命名空间，按上游 commit 幂等

- **状态**：已采纳
- **日期**：2026-11-06
- **所属版本**：[`v50-open-source-sync`](../versions/v50-open-source-sync/README.md)
- **依赖**：[ADR 0144](0144-a-new-account-starts-with-the-official-skills.md)（官方清单放服务端配置）、[ADR 0146](0146-public-is-platform-endorsement.md)（公开只留给官方命名空间）、[ADR 0155](0155-open-source-sync-passes-three-gates.md)（三闸与人工发布）

## 背景

今天创建 skill 与提交新 skill 都被强制落在调用者的个人命名空间（`CreateSkillUseCase` 与 `SubmitSkillUseCase` 走 `personalNamespaceOf`）；官方内容靠运营者登录官方账号、用普通作者路径手工发布；`namespace_member` 表存在但不参与授权。平台没有运营后台，也没有通用任务队列。

v50 要按清单自动把内容写进官方命名空间。它必须回答三个问题：用什么身份写、写到哪个地址、上游 commit 与平台版本怎么对应。

## 决定

1. **同步用服务端内部用例写入官方命名空间，不经过任何人的登录凭据。** 同步任务在进程内调用 skill / version 模块，把目标命名空间固定为官方命名空间（`namespace.official = true`，今天只有 `skillmaster`）；不读官方账号密码、不依赖 `namespace_member`。
2. **清单条目对应官方命名空间下的一个固定地址，地址由上游 `SKILL.md` 的 `name` 决定，清单不做覆盖。** 地址已存在时给该 skill 加草稿，不存在时创建；两条清单落到同一地址、或该地址已被另一个来源占用时阻断并记录（`result=blocked`），不自动改名。**不覆盖的原因**：现有提交路径强制「地址 = `SKILL.md` 的 `name`」，覆盖就要改写上游正文，与「不改写上游内容」冲突。
3. **同一仓库、同一目录、同一 commit 只同步一次。** 以版本级来源快照的 `revision` 为准；`revision` 相同则视为无变化，不建草稿。commit SHA 是内容寻址，本版不做摘要兜底。
4. **新 commit 产生一份新草稿；草稿不预分配版本号。** 版本号沿用现有发布机制：首次发布为 `1.0.0`，之后按补丁号递推（运营者可在发布时改成别的版本名）。
5. **同步只追加草稿，不改写已发布版本、不回滚、不删除。** 已有 skill 的线上版本与历史版本保持原样。
6. **来源事实由同步写入，不要求上游 `SKILL.md` 声明 `source`。** 同步把 `kind=github`、`locator`、`path` 与版本级 `revision` 写进 v49 的来源表；发布时沿用 v49 的刷新路径补许可与指标，不另立一套读模型。
7. **新 commit 建出新草稿后，丢弃同一 skill、同一来源、仍未发布的旧同步草稿。** 运营手工改过的那份也会被丢弃（2026-11-06 用户定）；清理失败只记日志，下次运行继续清。
8. **丢弃或撤销过的 revision 视为「已见过」。** 上游回滚到更早的 revision 时锚点仍指向更新的同步快照，会重新下载一次；摘要命中已有版本报 `unchanged`，否则新建草稿（见 TD §「已见过」）。 底座取该 skill **同步写的快照里最新的那一个版本**（`written_by_sync`，含 `discarded` / `revoked`）的 revision——M12 的 `SourceService.anchors` 给出同步快照，M7 的 `SkillVersionService.newestVersionIdAmong` 给出最新版本 id，两者配对；发布后刷新写的快照不参与。同 revision 不再重建；要重试只能等上游出新 commit。

## 理由

- **为什么不用官方账号凭据。** 官方账号的密码不该成为运行时依赖：它会被轮换、会被人持有，而且今天官方账号在种子里没有凭据。内部用例把「谁能写官方命名空间」收进一次代码评审，比一份散落在部署环境里的密码更可审计。
- **为什么不等「命名空间成员可写」。** 那条待办要改授权模型、控制台与 CLI，是另一条交付单元；同步只需要一条服务端内部路径，两者可以在将来合流，不必互相阻塞。
- **为什么地址由上游 `name` 决定、冲突就阻断。** 地址是内容自己的名字；允许清单覆盖就要改写上游正文，溯源会失效。自动改名会让同一个上游在不同时间落到不同地址，幂等也会失效；阻断并记录，把冲突交给人决定，代价可见。
- **为什么按 commit 幂等。** commit 是上游「这一版是什么」的稳定标识；没有它，每次同步都会重复建版，公域里会出现一批内容相同、版本号不同的条目。
- **为什么自动丢弃旧草稿。** 不清会每个周期堆一份未发布的同步草稿，运营在草稿列表里分不清哪份是当前上游；自动丢弃让「草稿列表 = 当前待审」保持成立。代价是运营对旧草稿的手工修改会丢，这是明确接受的取舍。
- **为什么丢弃/撤销也算见过。** 运营丢弃一份草稿是决定「这一版不要」；第二天同 revision 又建回来，等于推翻他的决定。把状态也算进「已见过」，丢弃才是一个会生效的动作。
- **为什么草稿不预分配版本号。** 版本号在发布时才确定（现有机制），草稿阶段预分配会让「未发布的版本」看起来已经占了一个号；发布时按补丁号递推，运营者仍有最终决定权。
- **为什么来源由同步写。** 上游 `SKILL.md` 不一定声明来源，而平台必须能回答「这一版来自哪个 commit」。来源是平台的事实，不应要求上游配合修改内容。

被否掉的：**用官方账号凭据跑同步**（运行时依赖一个人的密码）；**直接写数据库或复制 skill 表**（绕过版本与内容模型）；**沿用 `personalNamespaceOf`**（同步不属于任何个人）；**地址冲突时自动加后缀改名**（溯源漂移）；**优先采用上游版本号**（上游可能回退或重复，平台版本号会失去单调性）；**每次同步都建新草稿**（重复内容淹没公域）；**草稿阶段预分配版本号**（让未发布内容占用号段）。

## 后果

- 官方写入多了一条不经 HTTP 的路径；它需要与作者面用例共享同一套校验（名称、内容摘要、状态机），并由集成测试覆盖。
- 同步清单里改地址等于新建一个 skill；旧 skill 不会自动迁移或删除，需要时由人处理。
- 运营者的发布步骤保留；同步只负责把内容准备好。
- 单实例部署的假设继续成立；若将来多实例，同步任务需要数据库锁（见 `technical-design.md` §开放问题）。
- 上游改写同一 commit 时本版不会察觉（只认 revision）；强行改写 SHA 的内容本身也不是 git 的正常路径。
