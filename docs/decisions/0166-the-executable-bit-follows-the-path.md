# 0166 · 可执行位由路径决定，不由文件携带

- **状态**：已采纳
- **日期**：2026-11-08
- **所属版本**：[`v51-skill-runtime`](../versions/v51-skill-runtime/README.md)
- **修订**：[ADR 0064](0064-a-draft-may-change-a-published-version-may-not.md) §决定 1 里「`published` / `revoked` / `discarded` 的 `version_file` 不变」——`mode` 是派生值，允许一次按路径重算的数据迁移（V41）改它；内容、digest 与其余列仍按 0064 冻结

## 背景

v51 的第一版把可执行位当成**文件携带的一个属性**，一路搬运：上传时从 zip 的 unix mode 读，同步时从 tar 读，入库写 `version_file.mode`，分发时写回归档。带上它之后，三个问题同时出现：

- **位可以从哪来**：本地 `zip` 里有、控制台编辑器里没有、同步的 tar 里有。同一个 skill 换个入口，结果不同。
- **平台新建的文件拿不到位**：控制台/`skmr write` 新建一个 `scripts/run.sh`，没有任何地方能说「它是可执行的」，它落成 0644，`get --all` 之后 `./run.sh` 跑不了。
- **只改位无法表达**：内容不变、只想把 0644 改成 0755，命中同 digest 的重放——要么静默吸收（把旧位改成新位，等于改已发布版本），要么拒绝（作者没有别的路可走）。两条都不是好答案，而且后者在同步链路上会变成永远失败的条目。

这些都不是边界情况：它们是「位是文件属性」这个前提的直接后果。

## 决定

1. **可执行位是 `relpath` 的函数**：`scripts/` 之下的文件一律 `0755`，其余一律 `0644`。与它从哪来无关——本地打包、GitHub 同步、控制台新建、编辑、改名，都算同一条规则。
2. **一条数据迁移把存量对齐**（`V41__mode_follows_the_path.sql`）：已发布版本也按路径重算 `version_file.mode`。只改这一列，不动内容与 digest。
3. **删除重放时的权限对账**：`mode_changed_on_replay`、那条错误码和它的处理分支一起删掉——同一份内容不可能再算出两个位，没有可对账的东西。
4. **`run` 的解析范围不变**：只在 `scripts/` 内解析要执行的脚本。现在「能改写的路径」与「可执行的路径」是同一个集合，不是两条各自维护的规则。
5. **凡是要读这个位的地方，都问 `relpath`**，不问任何一份存的副本：分发读 manifest 时按路径重算，同步的安全闸按交付后的路径判断，缓存目录名带规则版本。存下来的 `version_file.mode` 与上传 zip 里的位都只是记录，不是判据。

## 理由

- **为什么不让位跟着文件走。** 它把一个本该由约定回答的问题（这个仓库里哪部分是可执行代码）变成了每个文件各自的状态，于是每个入口都要正确地产出它、每次重放都要对账、每个新建路径都要发明一个默认值。规则越分散，越会有一个入口出错——v51 自己就错了两处（CLI 打包、平台新建）。
- **为什么用路径而不是内容。** 按 shebang 推断是在猜作者的意图，而且猜错了没法撤销（没有地方说「不要执行」）。路径是作者已经在遵守的约定——`run` 本来就只在 `scripts/` 里找脚本；把它升格为权限规则，是让同一个事实只出现一次。
- **为什么连存量一起改。** 不改的话，v51 之前发布的版本永远停在 0644，「统一」只是对新东西成立。V41 是纯数据迁移：digest 不含 mode，任何地址都不变；按 digest 缓存的客户端要自己把规则版本算进键（见后果）。
- **被否掉的：**
  - **按 shebang 推断**：猜意图，且不可撤销。
  - **显式声明**（CLI `--executable` + 控制台开关）：最准，但要新 UI、新 API 字段，还要让「只改位」不再被拒——把一条能自解释的规则换成一个要教用户的概念。
  - **只对新版本生效**：存量永久不一致，两个 v51 之后的版本行为不同。

## 后果

- **`scripts/` 里的数据文件也带 `+x`**：`scripts/data/input.csv` 在 `get --all` 之后是 `-rwxr-xr-x`。功能无害，观感上要说一句。
- **`scripts/` 之外的脚本不可执行**：`bin/x.sh` 之类在平台上落成 0644。这与 `run` 只解析 `scripts/` 一致；真需要执行的脚本应放在 `scripts/` 下。
- **`version_file.mode` 是派生值**：它可以被重算（V41 就是），不要把它当成需要保真的原始事实。读 manifest 时按 `relpath` 重算、不读这一列——列对了与列错了，交付都是对的；列只留给运维查询与迁移。
- **`@sha256:` 钉的是文件字节，不带权限位。** 同一个 digest 的归档会随派生规则变化：这次改了一次，以后每改一次规则再变一次，「只发生一次」只对这一版成立。[ADR 0068](0068-export-is-a-one-shot-snapshot.md) 说「ETag 与包内容同源」——同源的是包里的**文件字节**，不是 zip 的全部字节。因此**按 digest 做缓存键的客户端必须把规则版本算进键里**：`skmr run` 的缓存目录变成 `<digest16>-r2`，旧目录一律当未命中；否则修复前缓存的 0644 脚本会永久跑不起来，而缓存不会自动删（[ADR 0101](0101-the-cli-never-deletes-files.md)）。
- **V41 是单向的。** 迁移之后，原「文件携带」的位没有任何副本，回滚 jar 不回滚数据；要回退只能写一条新的前向迁移（例如统一写回 0644），旧位不可恢复。回滚到仍带重放对账的旧代码会让库里出现两套规则，所以行为回滚只到「规则仍按路径」的版本为止。
- **V41 不写审计事件。** 它重算的是派生列：内容、digest 与地址都没变，审计要记的「谁对内容做了什么」没有发生；把派生值的重算记成一次内容事件，反而会让人以为版本被动过。
- **同步的安全闸改看路径。** [ADR 0155](0155-open-source-sync-passes-three-gates.md) §决定 4 的「可执行二进制」，判定的是交付时会不会可执行：`scripts/` 下的二进制**即使上游没标可执行也阻断**（平台会把它落成 0755），`scripts/` 外标了可执行的二进制**不再阻断**（落成 0644，跑不起来）。代价是前者会误伤「把二进制数据放在 `scripts/` 里」的仓库——把数据挪到 `scripts/` 外即可。
- **Windows 上这条规则什么也没改变**：值照常按路径派生，但那台机器没有可执行位可读（`Chmod` 对它无效），`run` 按扩展名与解释器执行；`doctor` 不为它加平台文案。
- **CLI 仍然把本地 mode 写进提交的 zip**（v51 的 `Archive()`）：服务端已经不读它（位由路径决定），但归档自描述没有坏处；哪天有别的消费者，位在那里。
