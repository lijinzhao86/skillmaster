# ADR 0143 · 公域 skill 的调用先确认：CLI 的一条确认轨，不是权限门禁

- **状态**：已采纳
- **日期**：2026-11-05
- **依赖**：[ADR 0048](0048-visibility-hands-out-a-rung.md)（可见性只是发一张票）、[ADR 0082](0082-public-and-private-with-my-library.md)（公域 / 私域：库是引用）、[ADR 0087](0087-cli-exit-codes-are-a-public-contract.md)（退出码是公开契约）、[ADR 0128](0128-cli-help-does-not-advertise-the-confirmation-switch.md)（帮助不宣传确认开关；`invoke` 借用它的理由，不是它的外推）

## 背景

v14 把 skill 分成公域与私域，并明确**加入是组织动作，不是权限动作**：未加入的公开 skill 仍然可以直接 `skill invoke`（[ADR 0082](0082-public-and-private-with-my-library.md) §决定 2）。这条保住了 [ADR 0048](0048-visibility-hands-out-a-rung.md) 的语义——公开就是发给所有人一张票。

实际使用里出现了另一类问题：agent 搜到一条公域 skill，就会直接加载它。用户未必知道这条 skill 来自别人的命名空间，也未必想用；**误调不是权限问题，是没有人被问过一句**。现在的替代做法只有提示词里那句「加载前先问用户」，agent 可以不听，也没有任何东西能让它停下来。

产品负责人 2026-11-05 定的形状是：

- 公域且不在我的库里的 skill，调用前先确认；
- 确认给**两个选项**：只这一次（`--yes`），或者收进库（以后不再问）；
- `--yes` **不写任何状态**，下次还会问；「以后不问」只能靠 `skill join`。

## 决定

1. **确认发生在 CLI 的 `skill invoke`**。服务端仍按 [ADR 0048](0048-visibility-hands-out-a-rung.md) 发票；确认不改变「谁能读」，只改变 CLI 在加载前停不停。
2. **公域且调用者没有库关系**（既不是自己创建的、没有共享给他、也没有加入引用）时，`invoke` 不加载正文，退出码 1，输出两条命令：
   - 只这一次：`skmr skill invoke <地址> --yes`
   - 收进你的库，以后不再确认：`skmr skill join <裸地址> --yes`（`skill join` 的地址不带版本）
3. **`--yes` 只对本次生效**：不写库、不记「已同意」；`invoke` 本来就要写的那条版本钉住照旧。
   **它不进 `invoke` 的帮助**（用法、参数、例子都不列），只出现在拒绝的那两条命令里，以及分块续读时那一条续读命令里（否则第二块会被同一道闸拦住）。这是本 ADR 自己的一条规则，不是 [ADR 0128](0128-cli-help-does-not-advertise-the-confirmation-switch.md) 的外推——0128 只管「拿走东西」的命令（`delete` / `discard`），而 `invoke` 不拿走任何东西。借用的是它的理由：帮助是复制入口，列出来就等于把「不先问」放在第一条可复制的命令上。
4. **服务端给结论，客户端不推导**：`/metadata` 与 `/detail` 响应新增只读布尔 `invoke_requires_confirmation`。CLI 只读它。
5. **作者面的行 id 也走这道判断，但消费者面答不出的状态除外。** 行 id 是作者面的地址，`browse` 档能拿到别人公开 skill 的版本行 id，所以它也要过闸。消费者面答不出的时候（草稿、已下线、当前版本已撤）放行：这些状态按 [ADR 0082](0082-public-and-private-with-my-library.md) §决定 1 的定义不属于公域，读的又是作者面自己的授权；在这里失败关闭会把作者读自己的草稿也拦下，还会把确认变成第二道权限。
6. **只拦 `invoke`**。`read` / `cat` / `head` / `tail` / `grep` 不拦——它们是显式读文件，不是「加载一个 skill 来用」；而且裸地址读 `SKILL.md` 已经被要求先 `invoke`。
7. **`skillmaster/` 命名空间不豁免**（产品负责人 2026-11-05 定）：官方 skill 不在库里时，`invoke` 同样拒绝。**平台自己的 skill 正文给出常驻同意**——官方地址直接带 `--yes`，所以用户不会在对话里被问；那是提示词层的预授权，不是 CLI 的例外，CLI 该拒绝仍然拒绝。
8. 注册时把官方 skill 默认收进新账号的库，是同一版里独立的一条（[ADR 0144](0144-a-new-account-starts-with-the-official-skills.md)）。按这一条，在库就不确认，两件事因此不会互相绊住。

## 理由

- **为什么不是服务端 403。** 那会把组织动作改成权限动作，推翻 [ADR 0048](0048-visibility-hands-out-a-rung.md) 的核心；而且直接走 HTTP 的调用者并没有「刚刚没确认」这个状态，服务端一拦就是新增一种拒绝。确认是交互轨，应该留在交互的地方。
- **为什么不是「同意一次就入库」。** 产品负责人 2026-11-05 明确要两个选项。只做入库会让「我想先用一下」必须先做一次组织动作；只做 `--yes` 又没法「以后不问」。两条路各给一条命令，语义各自诚实。
- **为什么只拦 `invoke`。** `read` 的语义是「读这个 skill 里的一个文件」，不是「把它加载来用」；把读也拦了，连「先看一眼再决定要不要用」都要先付出入库代价。裸地址读 `SKILL.md` 已有前置规则，绕不过去。
- **为什么用显式布尔，而不是让客户端从 `source` 推导。** 滚动升级时旧服务端没有这个字段：布尔缺省 `false`，新 CLI 在旧服务端上保持今天的行为；若让客户端把「`source` 为空」当成「必须确认」，旧服务端上每一个自有 skill 都会被拦。策略由服务端一处决定，客户端不做第二份推导。

被否掉的：**服务端权限门禁**（推翻 0048）；**`--yes` 顺带入库**（产品负责人要两个选项）；**客户端从 `source` 推导**（滚动升级会误伤自有 skill）；**拦全部读命令**（把「先看一眼」变成入库动作）；**`skillmaster/` 豁免**（产品负责人选了规则单一）。

## 后果

- [ADR 0082](0082-public-and-private-with-my-library.md) §决定 2 的「不挡加载」被**部分取代**：服务端语义不变，CLI 的 `invoke` 多一道确认。加入仍是组织动作，不是权限。
- 退出码契约不变：确认被拒是普通失败（1），不是用法错误（2）。
- `/metadata` 与 `/detail` 新增一个只读字段；旧客户端忽略它。
- `skill join --yes` 现在同时是「以后不再确认」的开关，帮助文本要写清这一点。
- 平台 skill 的正文要写明：官方地址可以直接带 `--yes`，不需要先问用户。
