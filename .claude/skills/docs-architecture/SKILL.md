# 文档架构与版本化约定

本仓库的文档分**五个轴**。写新文档前先决定它属于哪个轴——**放错轴是本仓库历史上最大的混乱来源**。

## 一、五个轴

| 轴 | 目录 | 随版本变？ | 放什么 |
|---|---|---|---|
| 开放性调研 | [`docs/research/`](../../../docs/research/) | ❌ | 竞品、生态、行业事实等长期参考 |
| 目标态 | [`docs/target/`](../../../docs/target/) | ❌ | 远期**完整形态**的产品文档；外加一份「与当前决策的差异」清单 |
| 决策记录 | [`docs/decisions/`](../../../docs/decisions/) | ❌ | **跨版本存活**的取舍，逐条编号 ADR |
| 工程架构 | [`docs/architecture/`](../../../docs/architecture/) | ❌ | 系统怎么切、模块契约与依赖规则、资源与数据的身份模型 |
| 版本 | [`docs/versions/vN-主题/`](../../../docs/versions/) | ✅ | 每一版的 PRD / 技术设计 / 测试文档 |

**判断口诀：「这个事实三年后还成立吗？」**
- 成立 → **不进版本文件夹**（在 research / target / decisions / architecture 里四选一）
- 只对某一版成立 → 进那个版本

**决策记录与工程架构的区别**：ADR 记的是「**当时为什么这么选**」——一条一个决定，正文一旦写下不再改动，价值在于历史。架构写的是「**现在长什么样**」——是活文档，随实现改，并承载模块边界这类**由代码强制**的约定。两者会互相链接，但不重复：ADR 不复述当前形状，架构不复述取舍理由。

## 二、大版本：`versions/vN-主题/`

命名 `vN-主题`（`v1-hosting`、`v2-payments`）：`主题` 用**小写 ASCII 连字符**——版本目录名是长期标识符，会出现在路径与 URL 里。**小版本不体现在目录名上。**（`iterations/` 与 ADR 的文件名 slug 不受此限，可用中文。）

一个大版本文件夹 = **四份必需文档**（+ 有记录时才有的迭代子目录，+ 一份可选缺陷清单）：

```
versions/vN-主题/
├── README.md            版本记录主页（薄）：状态 + 链接 + 五问的一句话摘要
├── prd.md               需求：用户与场景 / 范围 / 验收与指标
├── technical-design.md  技术设计：架构 / 表结构 / 接口 / 分期 / 开放问题
├── test-plan.md         测试：验收映射 / 用例 / 环境和数据 / 结果 / 已知问题
├── known-issues.md      （可选）**本版范围内不修**的历史代码缺陷
└── iterations/          （可选）小版本记录，**只增不改**——写第一条时才建
    └── 0001-<slug>.md
```

**`iterations/` 不要求存在**（2026-10-16 改，改的是校验器自己的一个错误）。一个从没做过小版本改动的版本，这个目录里**没有任何文件**，而 git **不跟踪空目录**——所以「要求它必须在」实际要求的是「每个版本都得有过小版本改动」，而全新 clone 上它会直接报「缺失」。实测：`main` 上一份干净的 `git archive` 跑校验器，报 `v2-credentials/iterations/ 缺失` 与 `v3-sessions/iterations/ 缺失`，退出码 1。现在校验器**有文件才检查文件名合规**，目录本身可有可无；因此版本 README 里那一行**在空的时候不要写成链接**（链接指向一个 clone 后不存在的目录＝死链）。

### 2.1 四份文档各自必须回答什么

**校验器实际查的是关键词**——它只确认标题里出现了下列词，所以小节名可以换说法：

| 文档 | 校验的关键词 |
|---|---|
| `README.md` | 状态 / 目标 / 不做 / 验收 / 目标态（「状态」允许写在标题下的引言块里） |
| `prd.md` | 用户 / 范围 / 验收 |
| `technical-design.md` | 架构 / 模型 / 接口 / 分期 / 开放问题 |
| `test-plan.md` | 验收 / 用例 / 结果 |

下面写的是每份文档**应该**回答的问题——校验器只保证关键词在，内容是否到位靠人。

#### `README.md` —— 版本记录主页（**薄**）

固定问题（小节名可微调）：

| 小节 | 必须回答 |
|---|---|
| `## 状态` | 进行中 / 已完成 / 已放弃；是否已实现 |
| `## 目标` | **一句话**说清这一版交付什么，然后链接到 `prd.md` |
| `## 这一版明确不做什么` | 表格：不做 / 原因（每条必须给理由） |
| `## 验收标准` | 一句话摘要 + 链接到 `prd.md` 的验收一节 |
| `## 与目标态的关系` | 这一版是 `target/` 的哪个子集、在哪些地方已经分叉 |
| `## 本版文档` | 表格：本文件夹内每份文档 + 一句话说明 |

**README 是「记录」，不是「详述」。** 目标、范围、验收的**细节都写在 prd.md**，README 只写一句话 + 链接。这不是风格偏好——见 §2.3。

#### `prd.md` —— 需求

| 小节 | 必须回答 |
|---|---|
| `## 用户与场景` | 谁在用、在什么场景下用、现在的替代做法是什么 |
| `## 范围` | **同时**写「做」与「不做」。不做的每条必须给理由 |
| `## 验收与指标` | 可判定的验收标准（能回答"过没过"）；指标说明怎么量 |
| `## 依赖与前置` | 依赖哪些外部条件、哪些决策 |

范围里**不许出现**「后续再看」「视情况而定」——不确定的进 `technical-design.md` 的开放问题，并且必须是一个**能回答的问法**。

#### `technical-design.md` —— 技术设计

| 小节 | 必须回答 |
|---|---|
| `## 架构` | 组件、边界、数据流。**不复述 ADR 的理由**，只链接 |
| `## 数据模型` | 表结构 / 实体关系。写 DDL 意图，不写实现细节 |
| `## 接口` | 接口形状（路径、入参、出参、错误码）。**主契约优先于适配器** |
| `## 分期` | 每一期交付什么、验收什么 |
| `## 开放问题` | **编号**，每条必须是一个能回答的问法 + 当前倾向 |

#### `test-plan.md` —— 测试

| 小节 | 必须回答 |
|---|---|
| `## 验收映射` | 把 `prd.md` 的**每一条**验收标准映射到具体用例；允许一条对多例 |
| `## 用例` | 用例清单：前置 / 步骤 / 期望 |
| `## 环境与数据` | 怎么造环境、用什么数据、如何清理 |
| `## 结果` | 实现完成后填写：通过 / 失败 / 未执行，附证据 |
| `## 已知问题` | **本版范围内**的未修缺陷（附状态与复现） |

> **`known-issues.md` 与 `test-plan.md` §已知问题 的分工**：
> - 缺陷在**本版交付范围内**、本版应该修 → 记在 `test-plan.md` §已知问题
> - 缺陷在**本版范围外的历史代码**里、本版决定不改 → 记在 `known-issues.md`
>
> 两者都不要用「大概、可能」描述状态——每条必须标 `已复现` / `部分复现` / `未验证` / `已修复`。

### 2.2 什么时候必须开一条 ADR

出现**跨版本的取舍**时——即"这个决定三年后还成立吗"答"是"——就写一条 ADR 进 `docs/decisions/`：

- 文件名 `NNNN-<slug>.md`，编号**四位递增，永不复用**；slug 不限语种，但不能含空格或斜杠
- 固定四段：`## 背景`（当时面对什么、有哪些选项）、`## 决定`、`## 理由`（**被否掉的那条为什么被否**）、`## 后果`（代价与后续影响）
- **决策绝不写进版本文件夹**
- 唯一允许的就地修改是**文件头的状态与引用**（改成"被取代"、标出取代它的编号）。**正文四段一旦写下不再改动**——它的价值正在于"当时是这么想的"
- 要推翻某条 → 新增一条"取代 000N"，**不改旧 ADR 的正文**

### 2.3 铁律：一个事实只有一个权威位置

**这是本仓库踩过的最大坑。** 2026-09 审计发现：同一个数字被抄进三条文档、抄的时候丢了限定条件（样本量、口径），于是从"实测 30 个样本"变成了看起来放之四海的普遍事实；同一个模型被两份文档用两种方式描述，然后漂移。

规则：

1. **版本 README 不复述 prd 的内容。** 只写一句话 + 链接。
2. **版本 TD 不复述 ADR 的理由。** 只链接——`decisions/README.md` 有同样的规定。
3. **目标态与当前决策的差异，只写在 `docs/target/README.md` 一份清单里。** 别处只链接，不重复。
4. **引用外部事实（数字、日期、引文）必须带出处**；引文和数字要能被读者复算。
5. **同一数字在多处出现时，只有一处是权威，其余指向它。** 如果不得不复述，**必须连限定条件一起复述**（"本机 30 个样本实测"不能变成"实测"）。
6. **测出来的数字要写口径。** 表格里给一列"口径/定义"，让读者能自己复现。定义变了数字就变了——中位数是否计入零值、字符类怎么划，都要写明。

## 三、工程架构：`docs/architecture/`

**这一轴放不随版本变的东西**：系统怎么切、模块之间的契约与依赖规则、以及资源与数据的身份模型。判断依据仍是 §一 的口诀——某一版 TD 里的模块表甚至带一列分期（P0/P1/P2），它本身就横跨版本。这一轴的入口是 [`docs/architecture/README.md`](../../../docs/architecture/README.md)，那里写清了它与版本 TD 的分工。

**为什么单开一轴**：这类内容原先没有家，只能挤在某一版的 `technical-design.md` 里。挤的代价是具体的——同一份 §2 会在每一版各留一份，而 §2.3 的铁律说同一个事实只能有一个权威位置。

```
docs/architecture/
├── README.md      必需。索引：这一轴是什么、与谁分工、现在有什么
├── rules.md       可选。依赖规则与它们的可执行检查
├── model.md       可选。资源与版本模型：从用户到字节的实体与身份
├── *.svg / *.png  可选。文档旁的插图，文件名随意
└── modules/       可选。每个模块一篇，名为 MNN-slug.md
```

**除 `README.md` 外全部只在存在时才检查。** 这与 `iterations/` 同一做法：架构内容边讨论边迁入，要求一个空文件先就位，等于邀请一份与它要取代的东西重复的副本。

**插图是唯一不按名字白名单放行的一类**（`ASSET_SUFFIXES`：`.svg` / `.png`）。图与文档不同——它没有散文，不可能成为某个事实的第二个权威，而封闭形状防的正是这个。所以图的名字随便起，将来加图也不用再动校验器；版本文件夹同样允许插图。

### 3.1 各文件必须回答什么

| 文件 | 必须回答 |
|---|---|
| `README.md` | 这一轴是什么、与版本 TD / 目标态的分工、现在有哪些文档 |
| `rules.md` | 每条依赖规则是什么、靠什么机制强制、**强制强度如实标注**（编译期／测试／lint，lint 不是证明） |
| `model.md` | 有哪些实体、**每个实体的身份是什么**、关联、如何寻址 |
| `modules/MNN-slug.md` | 那个模块的职责、拥有哪些表、对外契约是什么、为什么这样切 |

### 3.2 迁移规则：单向，且不预先造副本

内容**从版本 TD 讨论清楚、落到本目录，版本 TD 里那一段改成链接**。

- **不先在这里造一份副本再慢慢改**——两个权威一定会漂（§2.3）。
- **迁移完成之前，版本 TD 里的位置仍是权威**。只有搬完了，链接才反向。
- **本目录不重列模块表**——那张表的权威在版本 TD §2.5 与代码侧的 `ModuleMap`。`modules/` 下每篇写的是那个模块**自己的事**，不是那张表的又一份副本。

## 四、小版本：`versions/vN-主题/iterations/`

**判据：是否改变「对外可验收的能力边界」——不是看改了多少行代码。**

| 情形 | 归类 |
|---|---|
| 修 bug、调优、补接口参数、补一个已规划模块的实现细节、改内部表结构 | **小版本** |
| 新增一类用户可以做的事、改验收标准、改对外契约、换交付形态 | **大版本**（新开 `vN+1-主题/`） |

> **版本尚未实现时不适用本表。** 一个还没实现的版本，它的四份文档仍在**定义**阶段——补充范围、加一条验收标准、把某个机制标记为推迟，这些都是**定义**，不是迭代：就地改文档即可，不必开 `iterations/` 记录，也不必新开版本文件夹（为什么这么定，写在 commit message 里就够了）。本表针对的是**已经交付**的版本。

小版本的动作**恰好三件**：

1. **追加**一条迭代记录 `iterations/NNNN-<slug>.md`（NNNN 四位递增，**永不复用、永不改写**；slug 不限语种，不能含空格或斜杠）
2. **就地修订** `prd.md` / `technical-design.md` / `test-plan.md`——它们在版本内是**活文档**，直接改成当前真相
3. 若改动触及**跨版本取舍** → 按 §2.2 新增 ADR

迭代记录固定三段：

| 小节 | 必须回答 |
|---|---|
| `## 改了什么` | 具体到文件 / 接口 / 表 |
| `## 为什么` | 触发它的原因（bug 报告、实测数据、依赖变化） |
| `## 影响` | 影响哪些已交付行为；需要同步改哪些文档 |

**永远不要**：
- 为一次小改动新开 `versions/` 文件夹（文件夹爆炸，读一个功能要翻三个文件夹）
- 改写历史迭代记录（它只增不改；真相在 TD 里，历史在 iterations 里）
- 把迭代记录当成 changelog 抄一遍 TD 的内容

## 五、写完自查

```bash
python3 .claude/skills/docs-architecture/scripts/check_docs.py
```

校验器与它的测试都在 [`scripts/`](scripts/) 里——一个独立的小 Python 项目，测试与 lint 都从那个目录跑（`uv run pytest`、`uv run ruff check .`）。

校验器检查**可客观判定**的部分：版本四件套是否齐全、五个问题的小节是否在、迭代文件名是否合规、**所有相对链接是否可解析**、决策是否误进版本文件夹、ADR 是否四段齐全、以及**架构轴与版本文件夹一样是封闭形状**（认识的之外一律报错，`modules/` 下文件名必须是 `MNN-slug.md`）。退出码非 0 即有不合规项。

它**不**检查文字质量、事实正确性、口径是否写清——那些靠 §2.3 的规则和人。它也**不校验链接锚点**：`file.md#某节` 只确认文件存在，不确认那一节在。

## 六、模板

新建文件时从 [`templates/`](templates/) 复制骨架，不要从零写：

| 模板 | 用于 |
|---|---|
| [`templates/version-README.md`](templates/version-README.md) | 新大版本的 `README.md` |
| [`templates/prd.md`](templates/prd.md) | 新大版本的 `prd.md` |
| [`templates/technical-design.md`](templates/technical-design.md) | 新大版本的 `technical-design.md` |
| [`templates/test-plan.md`](templates/test-plan.md) | 新大版本的 `test-plan.md` |
| [`templates/iteration.md`](templates/iteration.md) | 一条小版本迭代记录 |

## 七、开工前检查清单

- [ ] 调用了本 skill（`docs-architecture`）
- [ ] 新文档已确定属于哪个轴（research / target / decisions / architecture / versions）
- [ ] 若是架构文档：是模块边界／数据身份这类跨版本的东西吗？是→`docs/architecture/`，且**不预先在那里造 TD 的副本**（§3.2）
- [ ] 若是版本内文档：大版本还是小版本？大版本→新文件夹+四件套；小版本→iterations/ + 就地改 TD
- [ ] 用到模板，没有从零写
- [ ] 没有复述别处已有的内容（§2.3）
- [ ] 外部事实带了出处；测出的数字带了口径
- [ ] 所有相对链接指向真实存在的文件
- [ ] 跑过 `check_docs.py` 且退出码为 0
