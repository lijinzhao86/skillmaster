# 开发流程（SOP）

**一句话**：**需求 → 三份文档 → 设计稿 → 校验 → 代码 → 循环审计 → 本地测试。每一步没锁住，不进下一步。**

**为什么按这个顺序**：这份 SOP 不是流程洁癖，它是从代价里长出来的。文档先行的理由是**改文档比改代码便宜**——同一条规则在文档里改一处，在代码里要改三处（服务端、网页、CLI），而三处一定会漂。设计稿先行的理由是**前端照搬比重新发明便宜**——照搬不会漂，重新发明会。审计放在最后的理由是**写的时候看不见自己的错**：2026-10-16 一次三路交叉审计在「已经定稿」的四份文档里找出 **30 处**不一致，其中 **3 处改的是这一版要做什么**（不是措辞）。

## 〇、七个阶段与各自的完成判据

**判据必须可判定**——能回答"过没过"，不能是"看起来差不多了"。

| # | 阶段 | 产出 | 完成的判据 |
|---|---|---|---|
| 1 | **需求** | `docs/versions/vN-主题/prd.md` | ① 范围**同时**写了「做」与「不做」，不做的每条都给了理由与"什么时候可能做"；② 每条验收**可判定**（能说清怎么量）；③ 每条验收都**能映射到用例**（没有对应用例的验收不合格）；④ 用户确认过 |
| 2 | **技术设计** | `technical-design.md` | ① 架构 / 数据模型 / 接口 / 分期 / 开放问题五节齐；② **开放问题要么已定、要么写成能回答的问法**（"后续再看"不是开放问题）；③ **每一条对代码的断言都指向真实存在的文件与符号**（见 §五 第 2 路审计——这一条最常错） |
| 3 | **测试方案** | `test-plan.md` | ① 验收映射覆盖 prd 的**每一条**，不多不少；② 每个用例有前置 / 步骤 / 期望；③ 环境与数据造得出来；④ 结果一节如实（未执行就写未执行） |
| 4 | **设计稿** | `design/` | ① **两套检查全绿**、② **图重出一遍**、③ **构建产物与源逐字节一致**、④ **有人看过**（Claude 看不到渲染结果）、⑤ 设计稿没覆盖的态**已经问过**（见 §三） |
| 5 | **代码** | 服务端 / 网页 / CLI | ① 前端**从设计件搬**（§四）；② 后端照 td 的接口与数据模型；③ **没有实现任何文档里没有的东西**——实现了就是文档漏了，回阶段 1–3 补 |
| 6 | **循环审计** | 一份发现清单 | ① 三路独立审计跑过（§五）；② 每条发现**先自己核实再采纳**；③ 每条发现都判成「改代码」或「回写文档」，回写文档的要复核设计件 |
| 7 | **本地测试** | 结果 | ① 改动那一处验过、附证据；② **视觉验收由人做**；③ 全量回归**由用户指令触发** |

**校验命令**（阶段 1–3 后、以及每次改完文档后）：

```bash
python3 .claude/skills/docs-architecture/scripts/check_docs.py   # 退出码 0 才算过
```

## 一、三份文档先锁：顺序不是并行

**prd → technical-design → test-plan，按这个顺序写，不要并行起草**：后一份的每一节都在回答前一份留下的问题，并行写出来的三份一定会在某处说两件不同的事。

**「锁定」是什么意思**（这一条要精确，否则要么僵化、要么偷偷改）：

- 锁定**不是冻结**。锁完之后仍可改——**但改动走"回写文档"这条路**：就地修订 + 在正文里写清改了什么、为什么（版本尚未实现时，定义阶段的改动是**就地修订**，不是迭代记录，见 [`docs-architecture`](../docs-architecture/SKILL.md) §四）。
- **跨版本的取舍要开 ADR**（`docs/decisions/`）——"这个决定三年后还成立吗"答"是"的，一律进 ADR，不进版本文件夹。
- **不许在代码里偷偷改需求**。实现时发现文档不对，正确动作是**停下、回写文档、再回来**；错的动作是把代码写成"对的"，让文档留在错的那里。

## 二、设计稿锁在文档之后

**设计稿是界面的唯一权威**（本仓库见根 [`CLAUDE.md`](../../../CLAUDE.md) 与 [`design/README.md`](../../../design/README.md)）。它锁在文档之后，因为**它要实现的是文档定的东西**——顺序反了，设计就会先画出文档里没有的能力。

**设计稿的"完成判据"是可执行的四件事**（本仓库的现成工具）：

```bash
# 1. 构建：源 → 交付件（两个演示件各一条）
node design/scripts/build-demo.mjs design/demos/dir3-hara.html        "design/skillmaster-首页演示.html"
node design/scripts/build-demo.mjs design/demos/dir3-hara-console.html "design/skillmaster-控制台演示.html"
# 2. 检查 + 出图：首页那套（--only <组> 可以只跑一处）
node design/scripts/interaction-check.mjs "design/skillmaster-首页演示.html" design/shots/states
node design/scripts/console-states.mjs    "design/skillmaster-控制台演示.html" design/shots/console [--only <组>]
# 3. 产物与源一致（交源不交产物是常见漏项）
node design/scripts/build-demo.mjs <源> /tmp/x.html && diff /tmp/x.html <产物>
```

**「测试全绿 ≠ 视觉验收」**——检查量的是结构与行为，量不到"像不像""这句话是不是真的"。所以第 4 件事是**请人看**：出图（`design/shots/`）+ 把页面打开。

**设计稿没覆盖的状态，先问，不许自己发明**：窄屏、空态、错误态、字段级校验、某个边角输入……设计稿里没有那一态时，要么把它补进设计稿，要么问用户。**不允许"先按我的想法实现，回头再对齐"**；也**不允许**实现完了才说"这一态设计稿没有"。

## 三、写代码：前端强制复用设计件

**规则：前端的结构、类名、CSS 数值、文案，从设计件里搬，尽量直接 copy-paste。**

| | |
|---|---|
| **搬什么** | HTML 结构、**类名**、**CSS 数值**（尺寸/间距/圆角/颜色/字号）、**文案**——一字不改 |
| **不搬什么** | 演示件的**替身机制**：`?page=` 那套假路由、夹具数据（`SESSIONS`/`KEYS`…）、进度条/演示带、为了能单文件运行而内联的东西 |
| **只允许改一件事** | 把片段**挪进框架**（变成组件/模板 + 数据绑定 + 真接口）。改了什么、为什么，写进提交信息或代码注释 |

**三条理由**：① **省 token**——理由、数值、文案都已在设计件里写过一遍，重新推导就是重付一次；② **少漂移**——数值与文案只有一个来源；③ **少返工**——漂移的代价是回头逐处对齐，那比搬一次贵得多。

**搬不动是设计件的问题，不是就地重写的理由。** 如果某一段搬不过去（样式没作用域、和演示件的全局缠在一起、夹着替身数据），正确动作是**回去把设计件改成可搬的粒度**（本仓库的样板是 [`design/partials/auth-overlay.html`](../../../design/partials/auth-overlay.html)：一处一个片段、样式全部收在 `.dialog` 下、宿主只欠一组自定义属性），**不是在产品里重写一遍**。

> **反例就在仓库里**：`skillmaster-web/src/pages/ConsentPage.vue` 与设计件的同一屏，逐行对下来差了**六处**（标题、名称字段、引子、权限两条、边界那一行、披露语那两句）。它们是**分别写的**，所以每一处都得靠人事后找出来。搬过去就不会有这六处。

**后端照 td 写**：接口形状、数据模型、分期以那一版的 `technical-design.md` 为准。**在实现里改接口形状而不回写 td** 是本仓库最容易发生的漂移（td 是接口的权威，代码不是）。

## 四、循环审计

**循环**的意思是：**审计 → 改 → 再审计**，直到没有 blocker / high 为止。**不是跑一遍就算过。**

**三路独立审计，输入固定**（三份文档 + 设计件 + diff），各查一个维度：

| 路 | 查什么 | 为什么单开一路 |
|---|---|---|
| 1 | **文档内部一致**：编号、交叉引用、验收映射、同一个事实在两处是否一致 | 同一份文档里自相矛盾只有专门找才找得到 |
| 2 | **文档所述事实 vs 代码**：每条对代码的断言（类名、方法、路由、配置键、注释原话）到代码里核实 | 文档最爱写"既有"——而"既有"经常不存在 |
| 3 | **文档 vs 设计件**：引用的文案、名词、界面状态是否与设计件一致 | 两边各自都对，合起来对不上，是最贵的一类 |

**每条发现先自己核实，再决定采纳。** 子代理会给出与代码相反的建议——2026-10-16 那一次，两路都建议按文档改，而**代码证明文档错了**（`auth.RevokeAuthorization` 就在那里）。**判定依据是代码与证据，不是投票。**

**发现的落点只有两种**，判完再动手：

- **改代码** —— 文档对、实现要跟。
- **回写文档** —— 文档错。这时**顺带复核设计件**：改的是需求或契约，设计件往往也要动。那意味着**流程回退到阶段 1–4**，不是"审计完就上线"。

## 五、本地测试

- **默认只验改动的那一处**；**全量回归由用户指令触发**（本仓库的约定，别自作主张跑全套）。
- **视觉验收由人做**：Claude 看不到渲染结果，所以"检查全绿"不是视觉验收——出图、或把页面打开请人看。
- **结果如实写**：通过写通过、没执行写未执行、失败附证据。**不许用"应该没问题"代替结果。**

## 六、什么时候可以不这么走（分级）

**这一节是防止流程被绕过。** 上面七个阶段是给**改行为**的改动准备的；把所有改动都套上去，只会让 SOP 被无视。分级照 [`docs-architecture`](../docs-architecture/SKILL.md) §四 那张表：

| 改的是什么 | 走什么 |
|---|---|
| **新增一类用户能做的事 / 改验收标准 / 改对外契约 / 换交付形态** | **全流程**（新开一个版本文件夹，七步走完） |
| **改界面**（结构、文案、样式、某一屏的状态） | **先改设计稿**（§二 的四件事），再同步产品——**文档那三步可以省，但设计稿不能省** |
| 修 bug、调优、补参数、改内部表结构 | 直接改 + 测试；跨版本的取舍才要 ADR |
| 改注释、改错字、改文档内部链接 | 直接改 + 跑 `check_docs.py` |

**判据只有一个**：**这次改动会不会改变"对外能验收的能力边界"**。会 → 走全流程；不会 → 按上表就近的一行走。

## 七、开工前 / 交付前清单

**开工前**

- [ ] 调用了本 skill（`dev-sop`）
- [ ] 说清**这一次改的是哪一类**（§六 分级表），以及**走哪几条阶段**
- [ ] 需要的文档已经锁住、`check_docs.py` 退出码 0
- [ ] 需要动界面时，设计稿已锁（§二 四件事都过）
- [ ] 说清**基准是什么**（版本文件夹 / 提交号）——不然审计时不知道自己锁的是哪一版

**交付前**

- [ ] 前端是**搬**来的，不是重写的；搬的过程中只改了"挪进框架"那一层，且写明了
- [ ] 没有实现任何文档里没有的东西；实现了的都已经回写进文档
- [ ] 循环审计跑过，发现的每一条都已判定并处理
- [ ] 改动那一处验过、附证据；视觉那部分**有人看过**
- [ ] `check_docs.py` 与设计件的检查都还是绿的
- [ ] 交付说明里说清了：做了什么、落在哪（路径 / 分支 / 提交）、**没做什么**
