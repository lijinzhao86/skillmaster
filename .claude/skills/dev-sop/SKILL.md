# 开发流程（SOP）

**一句话**：**需求 → 三份文档 → 设计稿 → 校验 → 代码 → 本地测试。每一步没锁住，不进下一步。**

**为什么按这个顺序**：这份 SOP 不是流程洁癖，它是从代价里长出来的。文档先行的理由是**改文档比改代码便宜**——同一条规则在文档里改一处，在代码里要改三处（服务端、网页、CLI），而三处一定会漂。设计稿先行的理由是**前端照搬比重新发明便宜**——照搬不会漂，重新发明会。

## 〇、六个阶段与各自的完成判据

**判据必须可判定**——能回答"过没过"，不能是"看起来差不多了"。

| # | 阶段 | 产出 | 完成的判据 |
|---|---|---|---|
| 1 | **需求** | `docs/versions/vN-主题/prd.md` | ① 范围**同时**写了「做」与「不做」，不做的每条都给了理由与"什么时候可能做"；② 每条验收**可判定**（能说清怎么量）；③ 每条验收都**能映射到用例**（没有对应用例的验收不合格）；④ **每一处控制台操作都有 CLI 对应**，例外已记在案（[ADR 0081](../../../docs/decisions/0081-every-console-operation-has-a-cli-command.md)）；⑤ 用户确认过 |
| 2 | **技术设计** | `technical-design.md` | ① 架构 / 数据模型 / 接口 / 分期 / 开放问题五节齐；② **开放问题要么已定、要么写成能回答的问法**（"后续再看"不是开放问题）；③ **每一条对代码的断言都指向真实存在的文件与符号**（这一条最常错） |
| 3 | **测试方案** | `test-plan.md` | ① 验收映射覆盖 prd 的**每一条**，不多不少；② 每个用例有前置 / 步骤 / 期望；③ 环境与数据造得出来；④ 结果一节如实（未执行就写未执行） |
| 4 | **设计稿** | `design/` | ① **两套检查全绿**、② **图重出一遍**、③ **构建产物与源逐字节一致**、④ **有人看过**（Claude 看不到渲染结果）、⑤ 设计稿没覆盖的态**已经问过**（见 §二） |
| 5 | **代码** | 服务端 / 网页 / CLI | ① 前端**从设计件搬**（§三）；② 后端照 td 的接口与数据模型；③ **没有实现任何文档里没有的东西**——实现了就是文档漏了，回阶段 1–3 补；④ **每个文件一件事**：页面超过约 600 行、组件超过约 400 行，要么已拆，要么说清为什么（§三 结构表） |
| 6 | **本地测试** | 结果 | ① 改动那一处验过、附证据；② **视觉验收由人做**；③ 全量回归**由用户指令触发**；④ `qa/` 在代码收口之后单独跑，**只在那一刻跑**（§四） |

**校验命令**（阶段 1–3 后、以及每次改完文档后）：

```bash
python3 .claude/skills/docs-architecture/scripts/check_docs.py   # 退出码 0 才算过
```

## 一、三份文档先锁：顺序不是并行

**prd → technical-design → test-plan，按这个顺序写，不要并行起草**：后一份的每一节都在回答前一份留下的问题，并行写出来的三份一定会在某处说两件不同的事。

**「锁定」是什么意思**（这一条要精确，否则要么僵化、要么偷偷改）：

- 锁定**不是冻结**。锁完之后仍可改——**但改动走"回写文档"这条路**：就地修订 + 在正文里写清改了什么、为什么（版本尚未实现时，定义阶段的改动是**就地修订**，不是迭代记录，见 [`docs-architecture`](../docs-architecture/SKILL.md) §四）。
- **跨版本的取舍要开 ADR**（`docs/decisions/`）——"这个决定三年后还成立吗"答"是"的，一律进 ADR，不进版本文件夹。
- **不许在代码里偷偷改需求**。实现时发现文档不对，正确动作是**停下、回写文档、再回来**；错的动作是把代码写成"对的"，让文档留在错的那里。

## 二、设计稿锁在文档之后

**设计稿是界面的唯一权威**（本仓库见根 [`CLAUDE.md`](../../../CLAUDE.md) 与 [`design/README.md`](../../../design/README.md)）。它锁在文档之后，因为**它要实现的是文档定的东西**——顺序反了，设计就会先画出文档里没有的能力。

**设计稿的"完成判据"是可执行的四件事**（本仓库的现成工具）：

```bash
# 0. 第一次动设计稿：装一次构建依赖（React + esbuild，见 ADR 0076）
cd design && npm install && cd ..

# 1. 构建：源 → 交付件（两个演示件各一条；动了共享浮层两条都跑）
cd design && npm run build:home && npm run build:console && cd ..
#    （等价的老命令；模板里只剩标记，源都在 src/）
#    node design/scripts/build-demo.mjs design/demos/dir3-hara.html        "design/skillmaster-首页演示.html"
#    node design/scripts/build-demo.mjs design/demos/dir3-hara-console.html "design/skillmaster-控制台演示.html"
# 2. 检查 + 出图：首页那套没有 --only（流程是点出来的）；控制台那套按组跑
node design/scripts/interaction-check.mjs "design/skillmaster-首页演示.html" design/shots/states
node design/scripts/console-states.mjs    "design/skillmaster-控制台演示.html" design/shots/console [--only <组>]
# 3. 产物与源一致（交源不交产物是常见漏项）
node design/scripts/build-demo.mjs <源> /tmp/x.html && diff /tmp/x.html <产物>
```

**「测试全绿 ≠ 视觉验收」**——检查量的是结构与行为，量不到"像不像""这句话是不是真的"。所以第 4 件事是**请人看**：出图（`design/shots/`）+ 把页面打开。

**设计稿没覆盖的状态，先问，不许自己发明**：窄屏、空态、错误态、字段级校验、某个边角输入……设计稿里没有那一态时，要么把它补进设计稿，要么问用户。**不允许"先按我的想法实现，回头再对齐"**；也**不允许**实现完了才说"这一态设计稿没有"。

## 三、写代码：前端强制复用设计件

**规则：前端的结构、类名、CSS 数值、文案，从设计件里搬，尽量直接 copy-paste。**

> **设计件本身是什么形态**：从 2026-10-22 起是 **React 源码**（[ADR 0076](../../../docs/decisions/0076-the-design-file-is-react-source.md)），改设计稿 = 改 `design/src/` 下的组件。那套写法、验证与「复制到前端」的清单在 web-design skill 的项目页 `projects/skillmaster.md`（[ADR 0121](../../../docs/decisions/0121-the-design-rules-live-in-the-web-design-skill.md)），用 `skmr skill read lijinzhao/web-design projects/skillmaster.md` 读——**改设计稿之前先读它**。下面「搬什么 / 不搬什么」仍是判据，只是「搬」的起点从 HTML 变成了组件。

| | |
|---|---|
| **搬什么** | HTML 结构、**类名**、**CSS 数值**（尺寸/间距/圆角/颜色/字号）、**文案**——一字不改 |
| **不搬什么** | 演示件的**替身机制**：`?page=` 那套假路由、夹具数据（`SESSIONS`/`KEYS`…）、进度条/演示带、为了能单文件运行而内联的东西 |
| **只允许改一件事** | 把片段**挪进框架**（变成组件/模板 + 数据绑定 + 真接口）。改了什么、为什么，写进提交信息或代码注释 |

**三条理由**：① **省 token**——理由、数值、文案都已在设计件里写过一遍，重新推导就是重付一次；② **少漂移**——数值与文案只有一个来源；③ **少返工**——漂移的代价是回头逐处对齐，那比搬一次贵得多。

**搬不动是设计件的问题，不是就地重写的理由。** 如果某一段搬不过去（样式没作用域、和演示件的全局缠在一起、夹着替身数据），正确动作是**回去把设计件改成可搬的粒度**（本仓库的样板是 [`design/src/shared/auth/`](../../../design/src/shared/auth/)：一个控件一件事、样式收在 `auth.css` 的 `.dialog` 下、宿主只欠一组 props），**不是在产品里重写一遍**。

> **反例就在仓库里**：`skillmaster-console/src/pages/ConsentPage.tsx` 与设计件的「授权请求」那一屏，逐行对下来差了**六处**（标题、名称字段、引子、权限两条、边界那一行、披露语那两句）。它们是**分别写的**，所以每一处都得靠人事后找出来。**这笔账在 v4 还上了——而还它花的钱，是照设计件把那一屏重写一遍**：CLI 那条路的实现换成了 `CliSignInPage.vue`（v12 起是 `.tsx`；结构、类名、CSS 数值、文案逐处从当时那份设计件搬来），旧的 `ConsentPage.vue`（现 `.tsx`）留在原地服务第三方那条路（`/consent` 与 `/oauth/*` 本版一个字节不动）。**搬过去就不会有这六处，也不会有这一次重写。**（v4 那次搬的是当时的片段，那份片段已随 ADR 0076 删除；设计件自 2026-10-22 起是 React，同类工作现在从 [`design/src/shared/auth/`](../../../design/src/shared/auth/) 复制。）

**后端照 td 写**：接口形状、数据模型、分期以那一版的 `technical-design.md` 为准。**在实现里改接口形状而不回写 td** 是本仓库最容易发生的漂移（td 是接口的权威，代码不是）。

### 前端的结构：一个文件一件事（2026-10-22 定）

**判据是「能力」，不是行数**——但行数超限就是能力的信号。出现下面任何一条，就该拆：

| 信号 | 该做什么 |
|---|---|
| 页面组件超过**约 600 行** | 找出「能独立画出来的那一屏/那一块」（列表、新建表单、密钥那一刻、文件树、文本面板、页头、横幅），搬成组件 |
| 组件超过**约 400 行** | 同上；或者它内部已经有两个互不相关的状态机 |
| 一个文件里有两套互不相干的状态 | 拆成两个文件 |
| 同一段逻辑被第二个文件用到 | 抽成模块——**不是复制一份** |

**页面组件只做两件事：状态机 + 编排。** 画东西的交给组件，算东西的交给纯模块。

- **搬的时候不许顺手改。** 结构、类名、文案、`display` 的值原样搬；**props 写实**——宽接口是事实（仓库里最大的一份是 27 个），不要用 context 或模块级变量把它藏起来。宽是给下一次收窄用的清单，不是缺陷。
- **框架无关的逻辑不进 React 文件。** 地址的读/拼/写（`address.ts`）、数字的读法（`format.ts`）、树与路径的计算（`editor/files.ts`）都不 import `react`。判据一句话：**这个文件真的需要 `react` 吗？不需要就别 import。**
- **依赖只有一个方向。** pages → components → 纯模块（`keyModel` / `treeState` / `files` / `address` / `format`）→ api。**组件不 import 页面**，**纯模块不 import 组件、也不 import `react`**。反向 import 就是循环——它就是「耦合」的准确定义，比「文件多大」更该先修。
- **不造层。** 没有 barrel（`index.ts` 转出口），没有「以后可能用得上」的抽象；一个模块出现第二个使用者时才抽。
- **一次拆一层，每拆一层验一次。** 拆完必须仍是同一屏：DOM 不变（设计件的检查 + 页面测试），行为不变（原有测试全过）。**拆分不是重写。**

> **这一条是从代价里写出来的。** v12 迁移完成时 `VersionEditorPage` 1,965 行、`AccountKeysPage` 1,530 行——它们各自装着一屏的全部状态机，读的时候要在两片作用域之间来回找。按上表拆完是 1,368 / 631 行，加六个各司一件事的文件；拆完 DOM 与行为都没有变（页面测试全过，对照台在收口后单独量过一次）。

## 四、本地测试

**`qa/` 不在写代码的循环里（2026-10-22 定）。** `qa/role-matrix` 是**代码完全写好之后的独立验收**——它从外面量「能力边界有没有变」，不是量「我这一笔改对没有」。所以：

- **写代码、调试期间一律不跑它**，也不拿它当护栏。那段时间的验证是：`npm test`、类型检查、构建、改动那一处的设计检查（`--only <组>`）。
- **它只在代码收口之后跑，作为交付前的最后一道**；全量仍按下面的约定由用户指令触发。
- **不许为了让 `qa/` 变绿而改 `qa/`。** 它是独立的尺；尺要改，只能因为它自己的口径错了，并且要有记录（`qa/role-matrix` 的自检用例）。
- 三条理由：① 它慢，而且要求两个 dev server 与夹具同时在线——中途的红分不清是"改错了"还是"还没改完"；② 一旦被当成开发时的护栏，它就不再是独立的那把尺；③ 它量的是结果，不是过程，改到一半跑它没有可用的信号。
- **默认只验改动的那一处**；**全量回归由用户指令触发**（本仓库的约定，别自作主张跑全套）。
- **视觉验收由人做**：Claude 看不到渲染结果，所以"检查全绿"不是视觉验收——出图、或把页面打开请人看。
- **结果如实写**：通过写通过、没执行写未执行、失败附证据。**不许用"应该没问题"代替结果。**

## 五、什么时候可以不这么走（分级）

**这一节是防止流程被绕过。** 上面六个阶段是给**改行为**的改动准备的；把所有改动都套上去，只会让 SOP 被无视。分级照 [`docs-architecture`](../docs-architecture/SKILL.md) §四 那张表：

| 改的是什么 | 走什么 |
|---|---|
| **新增一类用户能做的事 / 改验收标准 / 改对外契约 / 换交付形态** | **全流程**（新开一个版本文件夹，六个阶段走完） |
| **改界面**（结构、文案、样式、某一屏的状态） | **先改设计稿**（§二 的四件事），再同步产品——**文档那三步可以省，但设计稿不能省** |
| 修 bug、调优、补参数、改内部表结构 | 直接改 + 测试；跨版本的取舍才要 ADR |
| 改注释、改错字、改文档内部链接 | 直接改 + 跑 `check_docs.py` |

**判据只有一个**：**这次改动会不会改变"对外能验收的能力边界"**。会 → 走全流程；不会 → 按上表就近的一行走。

## 六、开工前 / 交付前清单

**开工前**

- [ ] 调用了本 skill（`dev-sop`）
- [ ] 说清**这一次改的是哪一类**（§五 分级表），以及**走哪几条阶段**
- [ ] 需要的文档已经锁住、`check_docs.py` 退出码 0
- [ ] 需要动界面时，设计稿已锁（§二 四件事都过）
- [ ] 说清**基准是什么**（版本文件夹 / 提交号）——不然复核时不知道自己锁的是哪一版
- [ ] PRD 里的「控制台操作 → CLI 命令」映射表已经填完：每一行要么有命令，要么是记在案上的例外（[ADR 0081](../../../docs/decisions/0081-every-console-operation-has-a-cli-command.md)）
- [ ] 前端**先说出这一版会有哪些文件、每个文件负责哪件事**（§三 的结构表）；要改的是已有的长文件时，先判它该不该拆

**交付前**

- [ ] 前端是**搬**来的，不是重写的；搬的过程中只改了"挪进框架"那一层，且写明了
- [ ] 没有实现任何文档里没有的东西；实现了的都已经回写进文档
- [ ] 每一处控制台操作都有 CLI 对应；映射表逐行对过，例外都是记在案上的（[ADR 0081](../../../docs/decisions/0081-every-console-operation-has-a-cli-command.md)）
- [ ] 改动那一处验过、附证据；视觉那部分**有人看过**
- [ ] **写代码期间没有跑过 `qa/`**；`qa/` 只在收口之后单独跑过一次，结果如实记录（§四）
- [ ] 前端每个文件仍是一件事：超过约 600 行的页面、约 400 行的组件，要么已拆，要么说清了为什么没拆
- [ ] `check_docs.py` 与设计件的检查都还是绿的
- [ ] 交付说明里说清了：做了什么、落在哪（路径 / 分支 / 提交）、**没做什么**
