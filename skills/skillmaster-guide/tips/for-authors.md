# 内容怎么组织：让 agent 真的用得上

> 你的 skill 是写给 **agent** 读的，不是写给人从头看到尾的。下面几条决定它会不会被用上、用得顺不顺。

## 1. 入口要薄，细节才下沉

`SKILL.md` 是每次都会被读的那一份。把它写成一本手册，等于每个用它的人都得多读一遍。

- 入口只放：什么时候用它、怎么找到下一篇、最容易踩的坑。
- 其余内容拆成文件，在入口里写清「什么时候读哪一篇」。

## 2. 一篇只回答一件事

判断方法：**单独拿出这一篇，给一个什么都不知道的 agent，它能不能把这件事办成？**

- 能，而且只讲了一件事 → 大小合适。
- 不能，因为依赖「先看上一篇」→ 太碎了。
- 能，但里面还讲了第二件事 → 该拆。

## 3. 每一行指路都要带「什么时候读」

不要写「详见某目录」，要写「接口报 4xx 时读 `errors.md`」——前者只是一句提示，后者才是一个决策。

## 4. 常见坑放在入口

agent 不知道自己踩了坑，就不会去翻那一篇。最容易出错的地方必须留在它一定会读到的那一份里。

## 5. 上线前检查断链

```bash
skmr skill check <地址>@<版本码>
```

退出码不是 0 就别上线——上线之后那一版冻结了，修一次就要再发一版。

## 6. `description` 决定它会不会被用上

别人手里的 skill 只有名字和描述。写「做什么 + 什么时候用」，别写形容词。见 [描述、标签与分类](../author/describe.md)。
