# 改一个已有的 skill

> 改的永远是草稿，线上那版在你上线前不受影响。**难的不是怎么改——是改动落在哪一份草稿上，以及用哪种方式改。**

## 先判断你是哪种情况

| 你的情况 | 怎么做 |
|---|---|
| 上次改到一半，还没上线 | 接着那份草稿改，**不要新开** |
| 线上那版要小修小补 | 从它开一份新草稿 |
| 上次改错了，想重来 | 丢弃那份草稿，重新开 |
| 只是想看看改了什么 | `skmr version diff <地址>@<版本码>` |

## 改的方式：就地改，别搬回本地

**默认就地改。** `edit` / `write` 指着版本码，改动落在**同一份草稿**上，每一步都有回显，改了几次就是几次。

**不要这样做**：`skmr skill download` 把整版取到本地，改完再 `skmr skill submit` 提交回去。原因是硬的——**`submit` 不会接着改你手上这份草稿**——它按目录内容另落一版（内容没变时直接返回已有的那一版）。结果是：你要改的内容和原来那份对不上，而且手上多出一份没人要的草稿。

**唯一的例外**：整个目录重排、大批文件一起动，本地改确实更顺手。那时要有意识地接受「这会开一份新草稿」，并且事后把旧的那份丢弃。

## 网页上也能改

控制台里：skill 详情 →「版本」→「新建版本」（或点开一份未上线的草稿继续编辑），进入编辑器直接改文件。

网页改完同样要评审、再上线——下面第 3、4 步对网页改的草稿一样适用。

## 第 1 步：看有没有开着的草稿

```bash
skmr version list <地址> --status draft
```

- 有：记下版本码，进第 2 步。
- 没有：第 2 步里用 `@new` 开一份。

## 第 2 步：改

```bash
# 改一处：有回显，能看见替换成了什么
skmr skill edit <地址>@<版本码> <相对路径> --old "旧文本" --new "新文本"

# 整个文件重写（内容从标准输入读）
skmr skill write <地址>@<版本码> <相对路径> --overwrite < ./本地文件

# 还没有草稿时，用它开一份（默认从当前线上版本起稿）
skmr skill write <地址>@new <相对路径> --name "这一版的名字" < ./本地文件
```

- **完成信号**：`edit` 打印出改动的前后对照；`write` 之后 `skmr skill ls <地址>@<版本码>` 能看到这个文件。

## 第 3 步：评审

上线前看三样东西：

```bash
# 1. 逐行看改了什么：对你改过的每个文件各跑一次
skmr version diff <地址>@<版本码> --file <改过的路径> --patch
# 2. 有没有断链
skmr skill check <地址>@<版本码>
# 3. 挑改动最大的几处读一遍
skmr skill read <地址>@<版本码> <关键路径>
```

**按文件逐个看，不要只看汇总。** 不带 `--file` 只给一张总表；对你改过的每个文件跑一次 `--file`，结果最可靠。

- **完成信号**：每个改过的文件都只有这一处差异；check 退出码 0。

## 第 4 步：上线

见 [把一版草稿上线](../ship/release.md)。**改完不上线，别人看到的还是旧的那一版。**

## 不想要这份草稿了

```bash
skmr version discard <地址>@<版本码>
```

`skmr version discard` 先说明后果、不执行；确认之后按它给出的完整命令重跑。

## 改这一版的名称、说明、类型

那是另一件事，不改变内容，见 [给这一版起名、写说明、定版本类型](draft-meta.md)。

## 改 skill 时要注意的

- **每轮都 `submit` 会攒出一堆草稿。** 接着改的时候先看有没有开着的草稿。
- **`edit` 比 `write` 安全**：只换你指的那一处，有回显；`write` 是整份替换，写错会把整个文件冲掉。
- **改完就发，别攒。** 攒成一大版，出问题时很难定位是哪次改动带来的。
- **评审别只跑 `check`。** `check` 只查断链，不查你改得对不对——diff 才是「改没改对」的证据。
